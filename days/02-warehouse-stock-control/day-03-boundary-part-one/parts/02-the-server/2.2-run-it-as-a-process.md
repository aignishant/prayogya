## One-line answer

Four lines make the boundary a program a client can launch, and the first real call across that
process line comes back with the protocol revision, the server's identity, a schema derived from
the function, and a bin.

## The idea

The scanner is not a scanner until there is a terminal answering it. A docket pinned to a wall in
an empty room is a document; a terminal that reads the docket and comes back with a bin's numbers
is a service.

Everything in the previous part exists inside the desk's own process — the server object was built
by an import. That is genuinely useful, and it is how most of this project's tests will talk to the
boundary, because it is fast and it still goes through the whole protocol. But it is not the thing
being built. **A boundary that only exists as an object in the caller's memory is a boundary the
caller can reach around**, and part 1.1 measured what that is worth: forty-five files.

So this part does two small things. It makes `stock_mcp` runnable — `python -m stock_mcp` — so a
client can launch it as a subprocess and talk to it down its standard input and output. And it puts
that command behind the door the project is operated through, so `./run mcp` starts the boundary
and the driver stops listing it as unbuilt.

One term, because it is the whole reason the next part exists: the **stdio transport** is the
arrangement in which a client launches the server as a child process and the protocol *is* that
process's standard input and output — one JSON message per line, and nothing else on standard
output, ever.

Read that last clause twice. It is the constraint the rest of this day turns on.

## The mechanism

The whole file, at `stock_mcp/__main__.py`:

```python
"""Run the boundary over stdio: `python -m stock_mcp`.

There is nothing else in this file on purpose. A client launches this module as a subprocess and
speaks the protocol down its standard input and output, so **anything else printed to standard
output would be read as a protocol message** and would corrupt the connection. The desk's logger
writes to standard error for exactly this reason.
"""

from __future__ import annotations

from stock_mcp.server import server

if __name__ == "__main__":
    server.run("stdio")
```

**Line by line:**

- **`__main__.py` is the file Python runs for `python -m stock_mcp`.** Not a script somewhere else,
  not an entry point in `pyproject.toml`: the package itself becomes runnable, and the command a
  client uses is derivable from the package name.
- **"There is nothing else in this file on purpose."** — every line added here runs before the
  protocol starts and inside the process whose standard output is the wire. A configuration read, a
  warning, a friendly banner: all of them are messages the client will try to parse.
- `from stock_mcp.server import server` — the same object part 2.1 built. **The tested thing and
  the shipped thing are the same object**, reached two ways: a `Client` can be handed it directly,
  or this file can run it.
- `if __name__ == "__main__":` — the guard, so importing `stock_mcp.__main__` does not start a
  server. It reads as boilerplate and it is the difference between a module and a process.
- `server.run("stdio")` — synchronous, blocking, and it does not return until the client goes away.
  `"stdio"` names the transport.

Then the driver gains the command. This is a **marked diff against the `run` printed on day 1**:
one dictionary entry added to `COMMANDS`, and the matching row removed from `PLANNED`:

```diff
     "setup": [["uv", "run", "python", "check.py"]],
+    "mcp": [["uv", "run", "python", "-m", "stock_mcp"]],
 }
 COMMANDS["check"] = COMMANDS["lint"] + COMMANDS["test"] + COMMANDS["setup"]

 PLANNED: dict[str, str] = {
-    "mcp": "day 3, the boundary that owns the ledger",
     "count": "day 7, the desk over the whole cycle count",
```

**Line by line:**

- `"mcp": [["uv", "run", "python", "-m", "stock_mcp"]]` — through `uv run`, like everything else,
  so the boundary runs on the pinned interpreter in the locked environment. A boundary started with
  a different Python is a boundary whose behaviour is not the one the tests exercised.
- **The `PLANNED` entry is deleted in the same change.** Day 1's driver wrote `"mcp": "day 3, the
  boundary that owns the ledger"`, and this is day 3. A driver that lists a command as unbuilt
  after it is built is worse than one that never mentioned it.
- **`mcp` is deliberately not added to `check`.** `./run check` must finish; the boundary runs
  until it is stopped. A gate that blocks forever is not a gate.

  each. The driver is still the map of the whole desk, and it is now one line more honest.
- `./run mcp` starts the boundary and blocks, speaking the protocol on standard output. There is
  nothing to see, which is correct: you are looking at one end of a wire.

Now the first call across a real process line:

```bash
uv run python -c "
import asyncio, json
from mcp import Client, StdioServerParameters

async def main():
    params = StdioServerParameters(command='python', args=['-m', 'stock_mcp'])
    async with Client(params) as client:
        print('protocol version:', client.protocol_version)
        print('server:', client.server_info.name, client.server_info.version)
        tools = await client.list_tools()
        for t in tools.tools:
            print('tool:', t.name)
            print('  input_schema:', json.dumps(t.input_schema))
        found = await client.call_tool('fetch_bin', {'bin_id': 'A-10-2'})
        print('found:', json.dumps(found.structured_content))
        print('is_error:', found.is_error)
        missing = await client.call_tool('fetch_bin', {'bin_id': 'Z-99-9'})
        print('missing:', json.dumps(missing.structured_content))
        print('is_error:', missing.is_error)

asyncio.run(main())
"
```

**Line by line:**

- **The first two lines are the child process's log**, on its standard error, arriving in your
  terminal because that is where a subprocess's standard error goes by default. They appear before
  everything else because the child wrote them while the parent was still collecting results. **Day
  1's decision to log to standard error is what makes this a convenience rather than a corruption**
  — part 3.2 is the other version.
- `StdioServerParameters(command='python', args=['-m', 'stock_mcp'])` — how to *launch* the server:
  a command and its arguments, and nothing about what the server can do. The client knows how to
  start a process; what that process offers, it has to ask.
- `protocol version: 2026-07-28` — **the current revision, reported by the client after the call.**
  There was no handshake to watch: in this revision every request carries its own version, so the
  version is a property of the exchange rather than of a session that was negotiated up front.
- `server: stock-boundary 0.1.0` — the identity from part 2.1, read back across the line. This is
  the first thing to check when a client is talking to the wrong thing.
- `input_schema: {"type": "object", "properties": {"bin_id": {"title": "Bin Id", "type": "string"}}, "required": ["bin_id"], "title": "fetch_binArguments"}`
  — **the schema was derived from `def fetch_bin(bin_id: str)` and nothing else.** The `title`
  fields were generated, `required` came from the parameter having no default, and `"type":
  "string"` came from the annotation. Nobody wrote this JSON, which is why it cannot disagree with
  the function.
- `found: {...}` — the bin, as structured content: the same dictionary the function returned,
  carried across a process line and rebuilt.
- **`is_error: False` on both calls.** The missing bin came back as `{"found": false}` with no
  error flag, exactly as the docstring promised. A tool that ran and answered "no" is not a tool
  that failed, and the difference matters to a model: an error is something to work around, an
  answer is something to act on.
- **Nothing in either result is a path.** The desk now has SKU, description and quantities, and no
  way to reach a file.

## When it breaks

Launch the server with a command the client cannot start, and the failure arrives as the subprocess
failing rather than as a protocol error:

```bash
uv run python -c "
import asyncio
from mcp import Client, StdioServerParameters
async def main():
    params = StdioServerParameters(command='python', args=['-m', 'stock_mcp_typo'])
    async with Client(params) as client:
        print(await client.list_tools())
asyncio.run(main())
" 2>&1 | tail -6
```

```
      |     raw = await self._dispatcher.send_raw_request(method, data.get("params"), opts)
      |           ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
      |   File "...\.venv\Lib\site-packages\mcp\shared\jsonrpc_dispatcher.py", line 336, in send_raw_request
      |     raise MCPError(code=CONNECTION_CLOSED, message="Connection closed")
      | mcp.shared.exceptions.MCPError: Connection closed
      +------------------------------------
```

The tail of a longer traceback, verbatim, with the site-packages path shortened. The client did its
job: it started a process, sent a request, and got nothing back because the process had already
died — Python could not find a module called `stock_mcp_typo`, said so on standard error, and
exited. **What the client can tell you is `Connection closed`, and that is all it knows.** The
reason lives in the child's own standard error, which the client is not showing you. Somebody hit
this after renaming the package and spent a while reading protocol documentation. The smallest fix
is to stop asking the client and run the command by hand — `python -m stock_mcp_typo` — where the
missing module names itself in one line.

## In production

**What a senior writes instead.** For anything long-lived, not stdio at all: the boundary becomes
an HTTP service with a health endpoint, started and restarted by something whose job that is. Stdio
is right when the client owns the server's lifetime — a desktop tool, a test, a single batch run —
and it is the transport to learn first because it makes the process line impossible to ignore.

**What degrades at scale.** One subprocess per client is fine for one cage. A distribution centre
running five cycle-count crews, each launching its own boundary, is five processes, five copies of
the ledger parsed into five heaps, and no shared view of anything — and the first time two of them
write a reconciliation, the atomic replace from day 2 is doing real work rather than being a
precaution. The answer is one boundary that several clients connect to, over a network transport
rather than a process each client owns.

**The review comment.** *"The boundary prints a startup banner. Take it out — on stdio that line is
the first thing the client tries to parse, and the failure will be a JSON error thirty lines away
from the print statement that caused it."*

**The interview question.** *"Your server communicates over its own standard input and output. Name
three ordinary things a Python program does that would break it, and say how you would stop each
one."*

## Check yourself

- **Run:** `./run mcp` and watch nothing happen. That is correct — the boundary is waiting for a
  client on its standard input. Stop it with Ctrl-C, then run the round trip above and watch the
  same server answer.
- **Say out loud:** The client printed `protocol version: 2026-07-28` and there was no handshake in
  the exchange. Where did that version come from, and what would a client have had to do to learn
  it under a revision that did have a handshake?
