## One-line answer

One `print` inside a tool put a line of English onto the wire, the client logged a parse failure —
and then answered the question correctly anyway, with no visible cost at all, which is what makes
this the worst kind of bug to find later.

## The idea

The scanner at the cage passes numbers through, and there is a convention: whatever comes back from
the terminal is a number, and the counter writes it on the sheet. Somebody wires the terminal to
print a friendly status line whenever it looks something up — *checking A-10-2...* — meant for a
technician standing at the console, not for the wire.

Nothing goes wrong for a while, because the status line looks like noise and gets ignored. Then one
day the console is gone and the terminal is talking to a machine that reads every line as an
instruction.

On the stdio transport this is not an analogy. The protocol **is** the child process's standard
output: one JSON message per line, and every line is parsed as a message. A `print()` anywhere in
that process — in a tool, in a library, in an import — is a line on the wire.

The thing worth learning here is not "don't print". It is what the failure actually looks like,
because it is not a crash. The client cannot parse the line, says so somewhere you are probably not
reading, **skips it**, and carries on. Your call succeeds. The system works. And it will keep
working until the day a print lands in the middle of a message rather than between two of them, or
until it silently swallows something that mattered.

Day 1 already made the decision that prevents this: the logger writes to **standard error**. That
looked like tidiness at the time — keep the program's output free for its result. This part is why
it was load-bearing.

## The mechanism

One line added to `fetch_bin` in `stock_mcp/server.py`, of the kind anybody adds while debugging:

```python
@server.tool()
def fetch_bin(bin_id: str) -> dict[str, Any]:
    """Look up one bin by its id.
    ...
    """
    print(f"looking up {bin_id}")  # broken on purpose: stdout is the protocol
    bin_ = store.bin(bin_id)
```

**Line by line:**

- `print(f"looking up {bin_id}")` — no logger, no prefix, no stream argument. It goes to standard
  output, which in this process is the wire.
- **The comment is in the printed code because this is a deliberate break**, and a reader who finds
  this file in that state should be able to tell in one line that it was on purpose.
- Everything else in the function is unchanged from part 2.1. **The failure needs no other
  ingredient**: one print, in one tool, in a process whose standard output belongs to the protocol.

Now call it across a real process line:

**Line by line:**

- **The first line is the boundary's own log, on standard error**, and it is fine. It is JSON, it
  carries the event and the bin id, and it never went near the wire. This is day 1's decision
  working, in the same transcript as the failure it prevents.
- `Failed to parse JSONRPC message from server` — the client's own message, and note where it is:
  in the middle of the output, unlabelled, with no request id attached to it. In a real run this is
  one line in a scroll-back of thousands.
- `mcp\client\stdio.py, line 221, in _parse_line` — **the client is parsing a line**, singular. The
  stdio transport splits the child's standard output on newlines and validates each one, so the
  unit of corruption is a line.
- `input_value='looking up A-10-2\r'` — **there it is.** The exact string the `print` produced,
  quoted back in a pydantic validation error, with the carriage return Windows added. This is the
  most useful line in the whole traceback and it is the eighth line of it.
- `Invalid JSON: expected value at line 1 column 1` — the parser got as far as the first character.
  Nothing about this message says "somebody called print"; it says the wire has a malformed message
  on it, which is true and unhelpful.
- **`connected, protocol 2026-07-28` and the result print come after the traceback**, because they
  are the parent's own standard output and the child's standard error was already flowing. Reading
  this transcript top to bottom gives entirely the wrong impression of the order things happened
  in, which is its own small lesson about interleaved streams.
- **`result: {'found': True, ...}` — the call succeeded.** The correct bin, all fields, no error
  raised. **The bad line was skipped and the protocol recovered**, because the stray text happened
  to land between two well-formed messages.
- So the state of the system is: one error logged where nobody is looking, one line of English
  discarded, and a correct answer. **A test asserting the result would pass.** That is the whole
  reason this part exists.

And it is not a thought experiment. With the print in place, the whole suite was run:

```
..............................                                           [100%]
30 passed in 1.72s
```

**Thirty passed. Not one test in this project goes red** — not the six boundary tests, not the
subprocess one, not the schema one. And here is the part worth sitting with rather than the tidier
story: run the same suite clean and it reports `1.71s`. **The timing did not move either.** A prior
version of this exact experiment, on a different project, found the corrupted run five times
slower — a stray line the parser had to recover from, costing real wall-clock. That was true there.
It is not true here, on this machine, today, and the honest conclusion is not "corruption always
costs time" but the harder one: **whether a corrupted wire costs you anything visible is not
something you can predict, and a gate that reads an exit status sees neither version of it.**

## When it breaks

The version above is the lucky one twice over — it recovered, and it did not even announce itself
by running slow. What makes it dangerous is what it costs when either of those stops being true:

1. The line is skipped, the exchange continues, and everything looks fine — the transcript above.
2. The line arrives while the client is waiting for a specific response, the response never parses,
   and the call hangs until a timeout the client may not have set.
3. Something writes to standard output **without a trailing newline** — a progress indicator, a
   partial write — and the next real message is concatenated onto it. Now a valid message is
   corrupted, not merely accompanied.

The one that gets shipped is the first, because it does not look like a bug and, as this transcript
shows, it may not even look slow. Somebody adds the print during an incident at eleven at night, the
fix works, the print stays, and it sits in the boundary for months writing a line per request into a
stream the client is quietly failing to parse.

The smallest fix is to delete the print. The fix that survives the next person is the one this
project already made on day 1 and stated again in `stock_mcp/__main__.py`: **the boundary's only
output channel for anything human is standard error**, and that sentence is in the module docstring
of the file that runs the process, where somebody about to add a line will read it.

## In production

**What a senior writes instead.** They configure the logging framework before anything else runs,
with a handler that writes to standard error, and they treat any library that prints as a
dependency problem rather than a nuisance — because a third-party import that writes a deprecation
warning to standard output will do this to you and it will not be your code that shows up in the
traceback. On a long-lived service they move off stdio entirely: an HTTP transport has a body per
response and no shared stream to corrupt.

**What degrades at scale.** One stray line per request, on a desk processing several hundred cycle
counts a night, is several hundred parse failures a night that nobody sees — and the moment a
message is large enough to be written in more than one chunk, the odds of landing inside one rather
than between two stop being negligible. The failure then is not a skipped line; it is a bin lookup
that hangs, on one count, intermittently, on a boundary that passes every test.

**The review comment.** *"There is a `print` in the MCP server. On stdio that is a message on the
wire — use `log()`, which goes to stderr. And while you are there: does anything we import print at
start-up? Run the module by hand and look at what comes out before the first request."*

**The interview question.** *"A server communicates over its standard output. A colleague adds a
debug print, the tests pass, and the feature ships. Describe what is actually happening on the wire,
and say what you would put in place so that the next person cannot do it."*
