## One-line answer

`data/counts.json` is tonight's cycle count against every one of the sixty bins — one count per
bin, fifty-one that agree with the ledger and nine that do not — and each of the nine carries the
counter's own note about why, written by hand, with the answer this desk is supposed to reach
attached and never read by the desk itself.

## The idea

A counter walks aisle B with a scanner and a torch. Bin by bin, they scan the label, count what is
actually on the shelf, and key the number in. Most of the night this is nothing: the number they
see matches the number the system already believes, and the scanner moves on without a word.

Then a bin disagrees. Bin B-18-2 should hold thirty-nine boxes of steel hose clips and the counter
finds thirty-six. They do not walk away. They think for a second — *a picker took three for a rush
order before the sheet was updated* — and they key that in too, in their own words, because the
system has no field for "reason" that is anything smarter than free text, and free text is what a
person actually has to give it at half past one in the morning.

`data/counts.json` is that night, for the sixty bins day 2's ledger holds. Sixty entries, one per
bin, each carrying who counted it, when, what they counted, and — only where it disagrees — the
note they left. Fifty-one of the sixty match exactly. Nine do not, and each of the nine is a
different kind of ordinary warehouse event: three receipts a picker shelved before goods-in booked
them, three picks that left the shelf before the ledger line was closed, two breakages with an
incident number on file, and one that nobody on shift can explain, which is the one that has to be
replenished tonight rather than explained away.

Every count also carries an `expected` block — the outcome, the reason and the delta this project
declares correct, decided by whoever wrote the fixture rather than by the desk. Day 2's rules never
read it. Part 3.1 is where it starts being asked questions.

**Line by line:**

- `"counted_qty"` — **the one number the counter is sure of.** Everything else in this project
  argues about whether that number agrees with the ledger; nothing argues about whether the
  counter counted correctly, because that is a different failure and this desk does not model it.
- `"counted_by": "C-02"` — **a badge, not a name.** Six counters worked this shift; naming them
  by badge is enough to ask "who counted this bin" without this project holding anybody's name.
- `"counted_at"` — **six minutes apart, from 22:00 on the 11th.** A real shift is not evenly
  spaced; this one is, because the spacing is not the subject of any rule this project has built
  yet, and an evenly spaced night is one fewer invented fact to justify.
- `"note": ""` — **empty on every one of the fifty-one matched bins.** A counter who found what
  the ledger expected has nothing to explain and nothing to write; the note field exists to be
  read, and it is only ever read where there is something in it.
- **The three receipt notes** — bin A-03-3 says "receiving", bin A-17-1 says "Goods-in"; both
  contain a word part 2.1's stand-in reader recognises. Bin A-10-2 says "the supplier's Wednesday
  drop" and "hasn't made it onto the sheet yet" — a receipt, described without the word receipt,
  and without "goods-in" or "booked in" either. Part 3.2 is what that costs a keyword scan.
- **The three pick notes** — "picked", "outbound pick", "Picker took three": three counters, three
  ways of saying the same ordinary thing, all readable.
- **The two breakage notes** — "too damaged to shelve" and "was crushed": different incidents,
  same category, both readable.
- **`"bin_id": "C-18-2"`, `"expected": {"outcome": "replenish", "reason": null, "delta": -3}`** —
  **the ninth variance, and the only one with no accepted cause.** The counter's own note says so:
  counted twice, three short both times, nobody knows why. This is the bin that has to be
  replenished tonight, and it is the only one of the nine whose `expected.reason` is `null`.
- **`—`** in A-10-2's note — **an em dash, written by Python's own JSON encoder.** It is the
  character a counter typed; the escape is how a JSON file spells it when it is not restricted to
  ASCII, and it decodes back to the same dash on the way in.

## When it breaks

Read a note the way the desk is tempted to on day 2, before a model exists to read it properly —
by checking whether it is merely present:

```bash
uv run python -c "
import json
data = json.load(open('data/counts.json'))
for entry in data['counts']:
    if entry['note'] and entry['expected']['outcome'] != 'explained':
        print(entry['bin_id'], entry['expected'])
"
```

```
C-18-2 {'outcome': 'replenish', 'reason': None, 'delta': -3}
```

**Line by line:**

- `C-18-2` — **a note that exists and still does not explain anything.** "Present" and
  "explained" are different questions, and a rule that conflated them would fast-track a
  replenishment past the one bin this whole fixture set was built to make somebody look at twice.

## In production

**What a senior writes instead.** The note field stays free text — nobody replaces a counter's own
words with a dropdown at one in the morning — but the system that receives it timestamps who wrote
it and locks it the moment a reconciliation is filed against the count, so a note cannot be edited
after the fact to make an unexplained shortfall look explained.

**What degrades at scale.** Six counters on one shift is a roster everyone on site recognises by
badge. Three hundred counters across a network of sites is a roster that needs its own directory,
and "who counted this" stops being a question the supervisor can answer from memory — it becomes a
query against a system this project has not built and does not need to, at sixty bins a night.

**The review comment.** *"Every matched count has an empty note and every variance has a full one.
A real shift also produces a note on a bin that turned out to match anyway — a counter who thought
they saw a problem and then didn't. Where does that note go, if nowhere in this file has a place
for it?"*

**The interview question.** *"You have free text written by a person under time pressure, and a
system downstream that needs a decision from it. Name the two failure modes on either side of
'read it carefully' — the scan that reads too little, and the automation that trusts it too much
— and say which this file is designed to demonstrate."*
