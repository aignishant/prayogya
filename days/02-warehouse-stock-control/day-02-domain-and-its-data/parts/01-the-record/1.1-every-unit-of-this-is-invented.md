## One-line answer

`data/ledger.json` is what a warehouse's stock system actually keeps about a bin, narrowed to the
seven fields some rule in this desk will read — sixty of them, every SKU, every quantity and every
supplier invented for this project and for no other reason than to be counted.

## The idea

A supervisor doing the morning handover does not say "aisle B has some hose clips". They say "bin
B-18-2, SKU-1037, thirty-nine boxes recorded, reorder at nine" — because the difference between a
shelf and a stock system is that the second one turns a physical thing into a record with a number
on it, and every later decision this desk makes is a decision about that number, not about the
shelf.

`data/ledger.json` is that record, for a synthetic three-aisle warehouse: three aisles, twenty bins
each, sixty bins in total, each holding one SKU. A hex bolt, a washer, a bearing, a cable tie — the
kind of thing a light-industrial site actually stocks, chosen because it is boring, and boring is
the property a fixture needs. Nobody argues about what a box of M8 washers is for.

Seven fields per bin, and each one earns its place because a rule in a later day reads it. `bin_id`
is the address a counter is sent to and the key everything else joins on. `sku` and `description`
are what is supposed to be there. `aisle` says where. `unit` says what one *thing* even means for
this SKU — a box, a bag, a bearing counted one at a time. `recorded_qty` is the number the ledger
believes, and it is the one number every later day argues with. `reorder_at` is a threshold nothing
reads yet — day 14's structured replenishment order is the day it starts to matter, and it is
written down now because a field invented on the day it is needed is a field nobody checked against
the rest of the book.

And a top-level `_synthetic` field, first in the file, that says outright what every number in it
is: invented, once, for this project, and for nothing else. No real warehouse ever held these
bins.

**Line by line:**

- `"_synthetic"` — **read this line first, on purpose.** It is the first key in the file and the
  first thing a stranger's editor shows them, and it says what every value below it is before they
  have a chance to wonder.
- `"bin_id": "A-01-1"` — **aisle, bay, level**, as two digits and one digit. `A` through `C`
  because this is a three-aisle warehouse; `01` through `20` because each aisle holds twenty bays;
  the last digit is the shelf level, one to four, and it repeats every four bays on purpose — a
  bay is a vertical column and the level says which shelf of it. Twenty bays times four levels
  used in rotation is not "every possible bin in this warehouse"; it is the sixty this project
  counts tonight.
- `"sku": "SKU-1000"` — **a flat, numbered catalogue**, one entry per bin here, because day 2 has
  not yet needed two bins to share a SKU. `explain_variance(sku, window)` — day 7's tool — is
  written to take a SKU rather than a bin precisely because a real warehouse keeps overflow stock
  in more than one bin; today's data does not exercise that, and the tool's own day says so.
- `"description"` — **for a person, never for a rule.** Nothing in this project compares
  descriptions; a rule that did would be a rule written against a sentence that changes if
  somebody edits the catalogue.
- `"unit": "box"` versus `"unit": "each"` — **what one count means.** A count of `52` for a box of
  M8 washers means fifty-two boxes; a count of `52` for ball bearings means fifty-two bearings.
  Nothing forces the two to be comparable, and nothing should: a counter walking aisle A counts
  boxes on one bay and bearings on the next, and the unit is what tells a reader which they did.
- `"recorded_qty"` — **the number the ledger believes**, and the whole subject of this project.
  Every value in this column is arithmetic, not narrative: bin *n* holds `20 + (n * 7) mod 60`,
  chosen so the sequence is dense across a useful range and reproducible by anyone who reads the
  rule rather than the number.
- `"reorder_at"` — **a quarter of the recorded quantity, floored at five.** Unread by anything this
  project has built so far. It is here because a field invented the day it is first needed is a
  field nobody checked belongs on the same record as the rest — day 14 reads it, and reads it
  against a book that has carried it since day 2.

## When it breaks

Ask the store for a bin this file does not have, before the store exists to answer honestly —
which is what a hand-rolled lookup with no `None` case looks like:

```bash
uv run python -c "
import json
data = json.load(open('data/ledger.json'))
by_id = {b['bin_id']: b for b in data['bins']}
print(by_id['Z-99-9']['recorded_qty'])
"
```

```
Traceback (most recent call last):
  File "<string>", line 5, in <module>
KeyError: 'Z-99-9'
```

**Line by line:**

- `KeyError: 'Z-99-9'` — **the honest failure of a dictionary asked for a key it does not hold**,
  and the reason part 2.2's `Store.bin` returns `None` instead of raising: a count against a bin
  the ledger has never heard of is not a bug in this file, it is a counter who misread a label, and
  it needs an answer a caller can act on rather than a traceback that stops the queue.

## In production

**What a senior writes instead.** The same shape, generated from a real warehouse-management
export with the values scrubbed and the SKUs replaced — never hand-typed at production scale,
because sixty rows is a fixture and sixty thousand is an integration. The generator that built this
file (arithmetic on an index, not a random draw) is the seed of that: reproducible, auditable, and
exactly as boring as the real export needs to be.

**What degrades at scale.** A three-aisle site with sixty bins is walked by one supervisor who
knows every SKU by heart. A regional distribution centre with sixty thousand bins across forty
aisles has no such person, and the ledger stops being a shared memory and starts being the only
place the business's belief about its own stock lives — which is the argument for day 4's rule
before this project has built anything the rule could apply to.

**The review comment.** *"`reorder_at` is a quarter of `recorded_qty`, computed once, on day 2, and
never touched again. On a real book this value comes from the supplier's lead time and this SKU's
sell-through, and it changes every quarter. Where does that update happen, and who is allowed to
make it?"*

**The interview question.** *"You are given a warehouse's stock export and asked to build a fixture
set from it. What do you keep, what do you invent, and how do you prove to a reviewer that nothing
real survived into the invented version?"*
