## One-line answer

`Store` is the one class in this desk allowed to open a path, and its write is atomic — a
reconciliation file is replaced in a single step or not touched at all — which is the property day
3 needs to move this whole class behind a process boundary without a single caller changing.

## The idea

A warehouse's stock system does not let a clerk edit the ledger file directly. There is a terminal,
and the terminal is the only door. Not because a clerk cannot be trusted with a text editor — because
if two doors exist, two clerks can walk through them at the same moment and the ledger ends up
holding whichever write landed last, with no record that the other one ever happened.

`Store` is this project's one door, today, before there is a second process to keep it honest. Every
line above this module that wants a bin, a count or a declared answer asks `Store` for it and never
opens `data/ledger.json` or `data/counts.json` itself — which is what makes day 3's move possible:
the day this project puts a boundary between the desk and its data, `Store` is the class that moves
behind it, unchanged, because nothing above it was ever touching a path to begin with.

And the write matters more than the two reads, because a read that fails leaves nothing behind and
a write that fails can leave a file that is worse than no file: present, half-written, and read by
the next thing that looks for it as if it were finished. `write_reconciliation` refuses to let that
happen by never writing to the real path at all. It writes to a temporary file next to it, finishes
completely, and only then swaps the temporary file in for the real one — a step the operating system
performs as one indivisible move rather than as bytes trickling into an open file.

## The mechanism

The whole file, at `stock_desk/store.py`:

```python
"""The only code in this desk that opens a file.

Two reads and one write, and the write is atomic. Everything above this module asks it for records
and never touches a path — which is what makes it possible, on day 3, to move this whole file
behind a process boundary without a single caller changing.

The read contract: ask by key, get a record or `None`, never a partially-loaded object.
The write contract: a reconciliation file is replaced in one indivisible step, or not at all.
"""

from __future__ import annotations

import json
import os
import tempfile
from collections.abc import Iterator
from pathlib import Path

from stock_desk.domain import Bin, Count

ROOT = Path(__file__).resolve().parents[1]
DATA = ROOT / "data"
RECONCILIATIONS = DATA / "reconciliations"


class Store:
    """The stock ledger, the cycle count queue and the reconciliation file, behind one object."""

    def __init__(self, data: Path = DATA) -> None:
        self.data = data
        self.reconciliations = data / "reconciliations"

    def _read_json(self, name: str) -> dict:
        """Read one JSON document whole. A half-read file is never returned to a caller."""
        return json.loads((self.data / name).read_text(encoding="utf-8"))

    def bins(self) -> Iterator[Bin]:
        """Every bin in the ledger, in file order."""
        for record in self._read_json("ledger.json")["bins"]:
            yield Bin.from_record(record)

    def bin(self, bin_id: str) -> Bin | None:
        """One bin by id, or `None` when the ledger has never heard of it.

        `None` rather than an exception: a count against a bin that does not exist is an ordinary
        night at a warehouse, and it has a reconciliation of its own.
        """
        for one in self.bins():
            if one.bin_id == bin_id:
                return one
        return None

    def counts(self) -> Iterator[Count]:
        """Every count in tonight's queue, in file order."""
        for record in self._read_json("counts.json")["counts"]:
            yield Count.from_record(record)

    def expectations(self) -> dict[str, dict]:
        """The declared correct outcome for each count, by bin id.

        Read by tests and, from day 18, by the evalset. **Nothing the desk itself runs may call
        this.** It is the answer key, and it lives beside the questions only because keeping them
        in one file is how they stay in step.
        """
        return {
            record["bin_id"]: record["expected"]
            for record in self._read_json("counts.json")["counts"]
        }

    def write_reconciliation(self, bin_id: str, record: dict) -> Path:
        """Write one reconciliation file: a reader sees the old contents or the new, never neither.

        Writing straight to the target truncates it first, so a reader arriving in that instant
        gets an empty file. This writes a temporary file **in the same directory**, forces it to
        disk, and moves it over the target in one step.
        """
        self.reconciliations.mkdir(parents=True, exist_ok=True)
        target = self.reconciliations / f"{bin_id}.json"
        text = json.dumps(record, indent=2, sort_keys=True) + "\n"
        handle, temporary = tempfile.mkstemp(
            dir=self.reconciliations, prefix=f".{bin_id}.", suffix=".tmp"
        )
        try:
            with os.fdopen(handle, "w", encoding="utf-8", newline="\n") as writer:
                writer.write(text)
                writer.flush()
                os.fsync(writer.fileno())
            os.replace(temporary, target)
        except BaseException:
            Path(temporary).unlink(missing_ok=True)
            raise
        return target

    def reconciliation(self, bin_id: str) -> dict | None:
        """One reconciliation file by bin id, or `None` if the desk has not written it yet."""
        path = self.reconciliations / f"{bin_id}.json"
        if not path.exists():
            return None
        return json.loads(path.read_text(encoding="utf-8"))
```

**Line by line:**

- `ROOT = Path(__file__).resolve().parents[1]` — **found from the module's own file, not from
  whatever folder a command happened to be run in.** `parents[1]` climbs from
  `stock_desk/store.py` past `stock_desk/` to the project root, so `./run check` from the root and
  a test run from inside `tests/` resolve to the same `data/` either way.
- `def _read_json(self, name: str) -> dict` — **one read helper, prefixed with an underscore.** It
  is this class's own implementation detail; nothing outside `Store` calls it, and the underscore
  is the only enforcement Python offers for that, which is exactly enough here.
- `Bin.from_record(record)` and `Count.from_record(record)` — **the read side hands every record
  to the type the moment it is read**, so nothing above `Store` ever holds a bare dictionary from
  either file. This is part 2.1's fix, applied at its one entry point.
- `def bin(self, bin_id: str) -> Bin | None` — **`None`, not an exception, for a bin the ledger
  has never heard of.** A count against `Z-99-9` is not this project's bug; it is a counter who
  misread a label or a fixture with a typo, and the caller decides what to do about it rather than
  being handed a stack trace that decided for them.
- `def expectations(self)` — **the answer key, one method, and a rule in its own docstring rather
  than in code that could enforce it.** Nothing today calls this from inside the desk's own
  decision path; only `tests/test_domain.py` does, in part 3.1, and the evalset will from day 18.
- `tempfile.mkstemp(dir=self.reconciliations, ...)` — **`dir=` is not decoration.** A temporary
  file created in the system's default temp location and then moved into `data/reconciliations/`
  can cross a filesystem boundary, and `os.replace` is only atomic within one filesystem. Creating
  it *in the target directory* is what makes the final `os.replace` a rename rather than a copy.
- `writer.flush()` then `os.fsync(writer.fileno())` — **two different guarantees, both needed.**
  `flush()` empties Python's own buffer into the operating system; `fsync()` tells the operating
  system to stop buffering too and put the bytes on disk. Without the second, a power cut between
  the write and the rename can lose data the program believed was already saved.
- `os.replace(temporary, target)` — **the one line that is actually atomic**, on every operating
  system this project runs on. A reader opening `target` at any moment either gets everything the
  temporary file held or everything the old file held; there is no instant in between where it
  holds neither or holds both.
- `except BaseException: Path(temporary).unlink(missing_ok=True); raise` — **clean up the
  temporary file on any failure, then let the failure through.** `BaseException` rather than
  `Exception` because a `KeyboardInterrupt` mid-write deserves the same cleanup as a `ValueError`
  does; `raise` with no argument re-raises exactly what was caught, so the caller sees the real
  failure and not a masked one.

## When it breaks

The naive version everybody writes first — straight to the target path, no temporary file — and a
process that dies mid-write, the way a killed container or a lost connection actually behaves:

```bash
uv run python -c "
from pathlib import Path
recon = Path('data/reconciliations')
recon.mkdir(parents=True, exist_ok=True)
target = recon / 'A-03-3.json'
try:
    with open(target, 'w', encoding='utf-8') as f:
        f.write('{\n  \"bin_id\": \"')
        f.write('A-03-3')
        f.flush()
        raise RuntimeError('the process was killed here, mid-write')
except RuntimeError as e:
    print('crashed:', e)
"
```


**Line by line:**

- `target exists: True` — **a file is there.** Nothing about its presence tells a reader whether
  it is finished.
- `'{\n  "bin_id": "A-03-3'` — **exactly as far as the write got before the crash**, and not one
  byte more. This is what "straight to the target" means: the bytes land in the real file as they
  are produced, in whatever order the operating system feels like flushing them.
- `JSONDecodeError: Unterminated string` — **the next reader's problem, not the writer's**,
  surfacing three stack frames deep inside the standard library's own parser, nowhere near the
  code that made the mistake. Whatever ran `reconciliation("A-03-3")` after this crash gets a file
  that exists, is not empty, and cannot be parsed — the worst of the three states a read can land
  in, and the one furthest from the line actually at fault.

Now the same crash, in the same place, against `write_reconciliation` itself — simulated by making
`os.replace` fail right after the temporary file is complete, which is the closest a test can get
to a process dying between "content is safe on disk" and "the rename happened":

```bash
uv run python -c "
from unittest.mock import patch
from stock_desk.store import Store
s = Store()
target = s.reconciliations / 'A-03-3.json'
print('before, exists:', target.exists())
with patch('os.replace', side_effect=RuntimeError('the process was killed here, mid-write')):
    try:
        s.write_reconciliation('A-03-3', {'bin_id': 'A-03-3', 'outcome': 'explained'})
    except RuntimeError as e:
        print('crashed:', e)
print('after, exists:', target.exists())
print('reconciliation():', s.reconciliation('A-03-3'))
print('left behind:', list(s.reconciliations.glob('*')))
"
```

**Line by line:**

- `after, exists: False` — **the crash happened and the target was never touched.** The write
  never reached `os.replace` successfully, so the old state — no file at all — is exactly what a
  reader still finds.
- `left behind: []` — **the `except BaseException` cleanup did its job.** The temporary file that
  held the finished content is gone too; a crash here leaves nothing partial anywhere in the
  directory, which is the property the naive version does not have.

## In production

**What a senior writes instead.** The same atomic-write discipline, plus a checksum or a schema
version written into the record itself, so a reconciliation file that *did* complete its rename but
was produced by an older, buggy version of this code can still be told apart from one produced by
the current rules — day 4's argument is about two writers disagreeing at the same moment; this is
the same argument stretched across time instead of across processes.

**What degrades at scale.** One `Store`, one process, one file per bin: sixty possible writers a
night, sequentially, is nothing. A network of sites each running their own desk against a shared
warehouse-management system needs the atomic write *and* a lock or a queue in front of it, because
`os.replace` is atomic for one filesystem and says nothing about two processes on two machines
racing to write the same remote path at once — which is precisely the failure day 4 spends its
whole day on.

**The review comment.** *"`write_reconciliation` fsyncs the file but not the directory it was
written into. On some filesystems, a crash right after the rename can lose the directory entry
even though the file's own bytes are safe. If this write has to survive a hard power cut and not
just a killed process, that is the next thing to fix — and it is worth a comment saying it was
considered and skipped, not silently left out."*

**The interview question.** *"You need to write a file so that a reader never sees a half-written
version of it. Walk me through your approach, and tell me the one line that is actually doing the
atomic part — and on what filesystem that stops being true."*
