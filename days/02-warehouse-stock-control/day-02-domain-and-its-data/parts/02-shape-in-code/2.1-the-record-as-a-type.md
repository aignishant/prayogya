## One-line answer

Two frozen records, two enumerations and one function that decides a count from three facts — and
the order of its four checks is the design, because a variance that has been explained is finished
being interesting before anybody asks which direction the shelf disagreed.

## The idea

A dictionary loaded from JSON will let you ask for `record["recored_qty"]` — misspelled — and hand
you a `KeyError` on line two hundred of some other function, nowhere near the line that made the
mistake. It will let you compare a `Bin`'s quantity to a `Count`'s quantity and get `True` back
even when one of them was accidentally loaded from last week's file, because a dictionary has no
opinion about which dictionary it is.

A **type** is the fix, and it is a fix in the most literal sense: it fixes what a thing is allowed
to be. `stock_desk/domain.py` turns the two JSON shapes day 2 already printed into two Python
classes that cannot be typed incorrectly once, because the typo happens at the one place they are
built — `from_record` — and every other line in this project gets `bin.recorded_qty`, which either
exists or fails immediately, at the place the mistake actually is.

And then the rule the whole day has been pointing at. `reconcile` takes a bin, a count and a
*reason* — the one fact that requires reading a counter's sentence, which this module refuses to
do — and decides between four outcomes with four ordered checks. Decided first: is there even a
disagreement. Decided second, before the sign of the gap is asked about at all: has someone already
said why. Only once both of those are answered does the direction of the gap get to matter, because
a shortfall with no explanation and an overage with no explanation are different problems that both
start the same way — nobody has said why yet.

## The mechanism

The whole file, at `stock_desk/domain.py`:

```python
"""The two records this desk works with, and the rule that decides between four outcomes.

A count arrives from the floor; the ledger either agrees with it or it does not. Where it does
not, the desk decides whether a known cause covers the gap or whether stock has to be reordered.
Everything in this module is decided by reading fields — no model, no network, no guessing. The
model's job, from day 8, is to turn a counter's free-text note into the one fact this module
cannot read off the form: the reason.
"""

from __future__ import annotations

from dataclasses import dataclass
from enum import StrEnum


class Outcome(StrEnum):
    """What the desk decides about one bin's count."""

    MATCHED = "matched"
    EXPLAINED = "explained"
    REPLENISH = "replenish"
    OVER_COUNTED = "over_counted"


class Reason(StrEnum):
    """Why a count disagreed with the ledger, and the disagreement is not a problem.

    One value per way a variance is ordinary rather than alarming. An explained variance names
    exactly one of these, because a reconciliation that lists three possible causes is a
    reconciliation that makes the next reader guess which one actually happened.
    """

    RECEIPT_NOT_BOOKED = "receipt_not_booked"
    PICK_NOT_CONFIRMED = "pick_not_confirmed"
    KNOWN_BREAKAGE = "known_breakage"


@dataclass(frozen=True)
class Bin:
    """One bin, as the ledger holds it. Frozen: a bin is read, never edited by this desk."""

    bin_id: str
    sku: str
    description: str
    aisle: str
    unit: str
    recorded_qty: int
    reorder_at: int

    @classmethod
    def from_record(cls, record: dict) -> Bin:
        """Build a Bin from one entry of `data/ledger.json`."""
        return cls(
            bin_id=record["bin_id"],
            sku=record["sku"],
            description=record["description"],
            aisle=record["aisle"],
            unit=record["unit"],
            recorded_qty=int(record["recorded_qty"]),
            reorder_at=int(record["reorder_at"]),
        )


@dataclass(frozen=True)
class Count:
    """One cycle count, exactly as the counter submitted it.

    `note` is optional **because a matched count needs no explaining**. The desk's job is to
    notice when it disagrees with the ledger and, only then, to need the note at all.
    """

    bin_id: str
    counted_qty: int
    counted_by: str
    counted_at: str
    note: str = ""

    @classmethod
    def from_record(cls, record: dict) -> Count:
        """Build a Count from one entry of `data/counts.json`.

        The `expected` block is deliberately not read here: it is this project's declared correct
        answer, used by tests and evals, and the desk must never see it.
        """
        return cls(
            bin_id=record["bin_id"],
            counted_qty=int(record["counted_qty"]),
            counted_by=record["counted_by"],
            counted_at=record["counted_at"],
            note=record.get("note", ""),
        )


def reconcile(
    bin: Bin,
    count: Count,
    reason: Reason | None,
) -> tuple[Outcome, Reason | None, int]:
    """Decide one bin's count from three facts, and read no English while doing it.

    `reason` is **given**, not derived. It requires reading a sentence a counter wrote, which is
    the one thing this module refuses to guess at: day 8 puts a model behind it. Everything else
    here is a field comparison.

    The order of the checks is the whole design. A zero delta is decided first, because a reason
    attached to a matched count is not a stricter test — it is a reason for nothing. An explained
    variance is decided before the sign of the delta is asked about, because "we know why" ends
    the question whichever direction the shelf disagreed. Only once there is no explanation does
    the direction matter: a shortfall with no cover is a reason to reorder, and an overage with no
    cover is a reason to look again at the ledger, never at the supplier.
    """
    delta = count.counted_qty - bin.recorded_qty
    if delta == 0:
        return Outcome.MATCHED, None, 0
    if reason is not None:
        return Outcome.EXPLAINED, reason, delta
    if delta < 0:
        return Outcome.REPLENISH, None, delta
    return Outcome.OVER_COUNTED, None, delta


#: Words that appear near each of the three ordinary explanations. Not a reader and not used by
#: `reconcile`.
RECEIPT_WORDS = ("receiv", "goods-in", "booked in")
PICK_WORDS = ("pick", "outbound")
BREAKAGE_WORDS = ("break", "broke", "damag", "crush")


def guess_reason_from_note(note: str) -> Reason | None:
    """A STAND-IN for reading the note, kept so its failure can be demonstrated.

    Nothing in this desk decides anything with it. It scans for words that appear near each of the
    three ordinary explanations, which means it cannot tell a receipt that was never called a
    receipt from one that was — and one of this project's own nine variances says exactly that.
    Day 8 replaces it with a model that reads the note; `tests/test_domain.py` asserts that it is
    still wrong, so that nobody quietly promotes it to a decision.
    """
    lowered = note.lower()
    if any(word in lowered for word in RECEIPT_WORDS):
        return Reason.RECEIPT_NOT_BOOKED
    if any(word in lowered for word in PICK_WORDS):
        return Reason.PICK_NOT_CONFIRMED
    if any(word in lowered for word in BREAKAGE_WORDS):
        return Reason.KNOWN_BREAKAGE
    return None
```

**Line by line:**

- `from __future__ import annotations` — **every type hint in this file is a string until
  something asks**, which is what lets `Bin.from_record` say it returns `Bin` from inside the
  class body that is still being defined. Without it, `Bin` on that line would not exist yet.
- `class Outcome(StrEnum)` — **a string that can only be one of four values, and prints as
  itself.** `Outcome.MATCHED == "matched"` is `True`, which is what lets the fixture's
  `expected["outcome"]` — a plain string read out of JSON — be compared against this enum with no
  conversion at the call site.
- `class Reason(StrEnum)` — **three values, not four.** There is no `Reason.NONE`; the absence of
  a reason is spelled `None`, in Python, everywhere in this project, because a fourth enum member
  meaning "no reason" would be a second way to say the same thing the type system already says for
  free.
- `class Bin` and `class Count`, both `@dataclass(frozen=True)` — **read, never edited.** Nothing
  in this desk ever needs to change a bin's recorded quantity in memory and write it back; every
  change to the truth goes through the store, which is the next part, and a frozen dataclass makes
  the alternative a `TypeError` rather than a bug discovered later.
- `Bin.from_record` and `Count.from_record` — **the one place each JSON shape becomes a type.** A
  typo in a key name — `record["recored_qty"]` — fails here, on this line, the moment the fixture
  is loaded, rather than three functions later where the message would be about a missing
  attribute and not about a misspelling.
- `note: str = ""` — **a default, not an `Optional`.** A count with no note is not a count missing
  data; it is a count with nothing to say, and `""` is truthier to write and to test than `None`
  would be for a field that means "empty" far more often than it means "absent".
- `def reconcile(bin: Bin, count: Count, reason: Reason | None)` — **`bin` shadows a builtin, on
  purpose.** Python's `bin()` turns an integer into a binary string and nothing in a stock desk
  calls it; the warehouse's own word for the thing is worth more here than the rarely-used
  function it borrows a name from.
- `delta = count.counted_qty - bin.recorded_qty` — **counted minus recorded, always in that
  order.** A positive delta is more on the shelf than the ledger expected; a negative one is less.
  Every later day that reads a delta reads it this way, and the sign is never flipped anywhere else
  in this project.
- `if delta == 0: return Outcome.MATCHED, None, 0` — **checked first, and it settles fifty-one of
  tonight's sixty counts without asking about a reason at all.** A reason attached to a matched
  count would be a reason for nothing, and this line is what stops that question from being asked.
- `if reason is not None: return Outcome.EXPLAINED, reason, delta` — **checked before the sign of
  `delta`.** This is the ordering choice the whole part is about: whichever direction the shelf
  disagreed, an accepted cause ends the question. The three receipt notes are overages; the three
  pick notes and two breakage notes are shortfalls; all eight reach this line the same way.
- `if delta < 0: return Outcome.REPLENISH, None, delta` — **only reached with no reason at all.**
  A shortfall nobody can explain is the one outcome this project's brief names by itself: the
  eval on day 18 goes red the moment this branch stops being reachable in the right place.
- `return Outcome.OVER_COUNTED, None, delta` — **the fourth outcome, and this fixture set never
  reaches it.** An overage with no accepted cause is not this desk's job to fix by ordering more —
  it is a reason to check the ledger itself, and the honest thing for `reconcile` to do is name
  that state rather than silently folding it into one of the other three.
- `RECEIPT_WORDS`, `PICK_WORDS`, `BREAKAGE_WORDS` and `guess_reason_from_note` — **a function
  `reconcile` never calls.** It exists to be shown wrong in part 3.2, on the one note among the
  nine that describes a receipt without ever using a word this list recognises.

## When it breaks

Ask `reconcile` for an outcome using a dictionary instead of the type it declares, which is what
happens the day somebody "simplifies" a call site by skipping `Bin.from_record`:

```bash
uv run python -c "
from stock_desk.domain import reconcile
bin_like = {'bin_id': 'A-01-1', 'recorded_qty': 20}
count_like = {'counted_qty': 26}
reconcile(bin_like, count_like, None)
"
```


**Line by line:**

- `AttributeError: 'dict' object has no attribute 'counted_qty'` — **the type does its job by
  refusing to pretend.** `count` is evaluated first on this line, and a `dict` has a
  `counted_qty` *key*, not a `counted_qty` *attribute* — `reconcile` was written against `Count`,
  which has the attribute because `from_record` put it there under a name checked once, at load
  time, rather than trusted forever after.

## In production

**What a senior writes instead.** The same shape, validated at the boundary with a schema library
rather than by hand — day 14's structured output is where this project does exactly that for the
replenishment order it writes out — so a malformed record is refused with a message naming every
field wrong at once, not just the first one a hand-written `from_record` happens to touch.

**What degrades at scale.** Four `if` statements read in order is a design one person can hold in
their head, and it is also the shape that breaks first when a fifth outcome is needed: a variance
explained by two causes at once, say, once a real site's data stops being this tidy. The fix at
that point is not a fifth `if` bolted onto the end — it is a table of rules, checked in a declared
order, which is what day 11's workflow runtime is for.

**The review comment.** *"`reconcile` returns a three-tuple. Two call sites already destructure it
as `outcome, reason, delta` and a third destructures it as `outcome, delta, reason` because nobody
checked. A dataclass return type would make that mistake a type error instead of a silent field
swap."*

**The interview question.** *"You are asked to decide one thing from four ordered rules. Walk me
through how you would choose the order, and tell me what changes about the design the day a fifth
rule is added."*
