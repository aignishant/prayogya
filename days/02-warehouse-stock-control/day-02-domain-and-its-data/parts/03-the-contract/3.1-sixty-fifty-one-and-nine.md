## One-line answer

`PROJECT.md` says this desk reconciles sixty bins and explains every one of nine planted
variances, and `tests/test_domain.py` is where those two numbers — and the fifty-one, and the
eight, and the one — stop being a sentence in a brief and become seven assertions that can go red.

## The idea

A promise written in prose is easy to keep by accident and easy to break without noticing. "This
desk reconciles sixty bins and explains every one of nine planted variances" reads as a fact about
the project, and the day somebody deletes three fixtures while tidying up, it quietly becomes a
fact about fifty-seven bins and six variances, and nothing says so — the prose still reads the
same.

A test suite is that promise, counted. `test_the_ledger_is_sixty_bins` is not testing `Store`; it
is testing that the fixture set still says what the brief says it says. `test_nine_variances_are_
planted` is not testing `reconcile`; it is testing that the count of `MATCHED`, `EXPLAINED` and
`REPLENISH` entries in the declared answers is fifty-one, eight and one, which is the arithmetic
behind "nine planted variances" made checkable rather than trusted.

And one test that is not about the fixtures at all: `test_the_rules_reproduce_every_declared_
outcome` runs `reconcile` — the actual function, part 2.1's actual code — against every one of
tonight's sixty counts, handing it the declared reason as a given fact, and checks that what comes
back matches what was declared by hand. This is the test that would catch part 2.1's "When it
breaks" mistake before a human ever ran it by hand: reorder the checks in `reconcile`, and this is
the assertion that goes red, on the exact bin the reordering gets wrong.

## The mechanism

The whole file, at `tests/test_domain.py`:

```python
"""The fixture set, asserted as a contract.

`PROJECT.md` says this desk is done when a cold clone reconciles sixty bins and explains every
one of the nine planted variances. Those numbers are a promise, and this file is where the
promise becomes a thing that can go red.

Nothing here runs a model. Every assertion is about the fixtures and the rules that read them.
"""

from __future__ import annotations

import pytest

from stock_desk.domain import (
    Outcome,
    Reason,
    guess_reason_from_note,
    reconcile,
)
from stock_desk.store import Store


@pytest.fixture
def store() -> Store:
    return Store()


def test_the_ledger_is_sixty_bins(store: Store) -> None:
    assert len(list(store.bins())) == 60


def test_the_queue_is_sixty_counts_one_per_bin(store: Store) -> None:
    bin_ids = {b.bin_id for b in store.bins()}
    count_ids = {c.bin_id for c in store.counts()}
    assert len(list(store.counts())) == 60
    assert count_ids == bin_ids


def test_nine_variances_are_planted(store: Store) -> None:
    expected = store.expectations()
    outcomes = [entry["outcome"] for entry in expected.values()]
    assert outcomes.count(Outcome.MATCHED) == 51
    assert outcomes.count(Outcome.EXPLAINED) == 8
    assert outcomes.count(Outcome.REPLENISH) == 1
    assert outcomes.count(Outcome.OVER_COUNTED) == 0


def test_every_explained_variance_names_a_reason_the_desk_can_produce(store: Store) -> None:
    reasons = [
        entry["reason"]
        for entry in store.expectations().values()
        if entry["outcome"] == Outcome.EXPLAINED
    ]
    assert len(reasons) == 8
    for reason in reasons:
        assert reason in set(Reason), f"{reason} is not a Reason this desk can name"


def test_every_matched_count_has_no_reason_and_no_delta(store: Store) -> None:
    for entry in store.expectations().values():
        if entry["outcome"] == Outcome.MATCHED:
            assert entry["reason"] is None
            assert entry["delta"] == 0


def test_the_rules_reproduce_every_declared_outcome(store: Store) -> None:
    """The whole fixture set, decided by `reconcile`, compared with what was declared by hand.

    The reason is taken from the expectation rather than derived: reading a note is the model's
    job from day 8, and this test is about the rules.
    """
    expected = store.expectations()
    bins = {b.bin_id: b for b in store.bins()}
    for count in store.counts():
        declared = expected[count.bin_id]
        the_bin = bins[count.bin_id]
        reason = Reason(declared["reason"]) if declared["reason"] else None
        outcome, got_reason, delta = reconcile(the_bin, count, reason)
        assert outcome == declared["outcome"], count.bin_id
        assert (got_reason.value if got_reason else None) == declared["reason"], count.bin_id
        assert delta == declared["delta"], count.bin_id


def test_the_keyword_scan_is_still_wrong_about_a_real_variance(store: Store) -> None:
    """An inverted case: it asserts that the stand-in fails, so nobody promotes it to a decision.

    Bin A-10-2's note describes an unbooked delivery without ever using a word the scan
    recognises. If this test ever goes red, either the fixture changed or somebody taught the
    scan to read English — and the second one is day 8's job, with a model, not a longer word
    list.
    """
    declared = store.expectations()
    counts = {c.bin_id: c for c in store.counts()}
    wrong = [
        bin_id
        for bin_id, count in counts.items()
        if count.note
        and str(guess_reason_from_note(count.note) or "") != (declared[bin_id]["reason"] or "")
    ]
    assert "A-10-2" in wrong
```

**Line by line:**

- `@pytest.fixture def store() -> Store` — **one `Store`, built fresh for every test.** Nothing in
  `Store` caches anything, so this costs nothing, and it means no test can leak state into the
  next one by holding a `Store` from an earlier test.
- `test_the_ledger_is_sixty_bins` and `test_the_queue_is_sixty_counts_one_per_bin` — **the two
  numbers checked first, and checked against each other.** The second test does not just count the
  queue; it compares the *set* of bin ids in the ledger against the *set* of bin ids in the queue,
  so a count against a bin the ledger does not have — or a bin with no count at all — fails here
  rather than surfacing later as a `None` from `store.bin(...)` nobody expected.
- `test_nine_variances_are_planted` — **the arithmetic behind "nine" made explicit: fifty-one,
  eight, one and zero.** Reading `outcomes.count(Outcome.MATCHED)` against a plain Python list
  works because `Outcome` is a `StrEnum` and the declared `entry["outcome"]` is the matching plain
  string — no conversion needed at either end.
- `test_every_explained_variance_names_a_reason_the_desk_can_produce` — **every declared reason,
  checked against the enum that is supposed to be exhaustive.** `reason in set(Reason)` is `True`
  for a string that matches one of the three values and `False` for anything else, including a
  typo — which is exactly the kind of mistake a hand-written fixture can carry silently.
- `test_every_matched_count_has_no_reason_and_no_delta` — **the fixture's own internal
  consistency.** A matched entry with a nonzero declared delta, or a reason attached to it, would
  be a fixture that disagreed with itself before `reconcile` ever ran.
- `reason = Reason(declared["reason"]) if declared["reason"] else None` — **the declared string
  converted back into the enum `reconcile` expects.** `Reason("receipt_not_booked")` works because
  a `StrEnum`'s constructor accepts its own values; a bad string here raises `ValueError` before
  the assertion below it even runs, which is a second, implicit check that the fixture's reasons
  are real.
- `assert outcome == declared["outcome"], count.bin_id` — **the bin id as the failure message.**
  Sixty iterations of this loop with no identifying detail in the assertion would report only that
  *some* bin failed; the bin id is what turns a red test into a place to look.
- `str(guess_reason_from_note(count.note) or "")` — **the scan's answer, coerced to a plain
  string, compared against the declared reason coerced the same way.** `guess_reason_from_note`
  returns a `Reason` or `None`; `declared[bin_id]["reason"]` is a plain string or `None`; both
  sides go through `or ""` so `None` compares equal to `None` without a special case.
- `assert "A-10-2" in wrong` — **the inverted case.** This test does not assert the scan is right.
  It asserts the scan is wrong, on a specific bin, because a passing test here means the scan has
  started reading English — and the day that becomes true on purpose is day 8, with a model
  wired in, not with a longer tuple of words.

## When it breaks

Delete one of the nine planted variances from the fixture set — the way tidying up "unnecessary"
data by hand actually goes wrong — by turning C-18-2's genuinely unexplained shortfall back into a
match:

```bash
uv run python -c "
import json
p = 'data/counts.json'
d = json.load(open(p, encoding='utf-8'))
for c in d['counts']:
    if c['bin_id'] == 'C-18-2':
        c['counted_qty'] = 59
        c['note'] = ''
        c['expected'] = {'outcome': 'matched', 'reason': None, 'delta': 0}
json.dump(d, open(p, 'w', encoding='utf-8'), indent=2)
open(p, 'a', encoding='utf-8').write('\n')
"
uv run pytest -q tests/test_domain.py::test_nine_variances_are_planted
```

```bash
git checkout -- data/counts.json
uv run pytest -q tests/test_domain.py
```

- `assert 52 == 51` — **the count moved by exactly one**, because the fixture moved by exactly

  gone on reading the same; the number in the test is what would have caught the change.

## In production

**What a senior writes instead.** The same shape, with the fixture-contract tests run in the
pipeline against the fixture file's own checksum as well as its counts — so a fixture edit that
happens to keep the *count* of variances at nine while changing *which* nine still shows up as a
diff a reviewer has to approve, rather than a silent pass because the arithmetic still balanced.

**What degrades at scale.** Seven tests over sixty fixture rows run in eighty milliseconds. A real
evalset with three hundred cases and a live model behind `reconcile`'s missing half runs in
minutes and costs money per run — day 18 is where that tradeoff gets made explicitly, and the
fixture-contract tests in this file are what stay fast and free forever, because they never leave
the rules.

**The review comment.** *"`test_the_rules_reproduce_every_declared_outcome` loops over sixty
counts in one test function. When it fails, `pytest` stops at the first assertion — you get one
bin id, not a list of every bin the rules got wrong. Consider `pytest.mark.parametrize` over the
sixty bin ids instead, so a single broken rule shows you its whole blast radius in one run."*

**The interview question.** *"Your project's README makes a numeric promise — some count, some
percentage. Show me the line of code that would go red if that promise stopped being true, and
tell me who would notice if that line did not exist."*
