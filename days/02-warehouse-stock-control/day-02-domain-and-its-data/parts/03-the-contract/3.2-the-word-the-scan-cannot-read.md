## One-line answer

Widening `guess_reason_from_note`'s word list to catch the one note it misses breaks a note it
already had right — the scan cannot be patched into correctness with more words, which is why this
project needs a model at all, and it needed one before a line of agent code existed.

## The idea

A supervisor reviewing tonight's nine variance notes by eye would read bin A-10-2's — *"the
supplier's Wednesday drop hasn't made it onto the sheet yet"* — and know at once that this is a
receipt nobody booked. A machine built to look for the word "receiving" does not know that. It
knows the word "receiving", and this note does not contain it.

That is not a bug you fix by adding "drop" to the list of words that mean *receipt*. Watch what
happens when you try.

## The mechanism

`guess_reason_from_note`, printed whole in part 2.1, checked against every one of tonight's nine
variance notes:

```bash
uv run python -c "
from stock_desk.store import Store
from stock_desk.domain import guess_reason_from_note
s = Store()
expected = s.expectations()
for count in s.counts():
    if not count.note:
        continue
    declared = expected[count.bin_id]['reason']
    guessed = guess_reason_from_note(count.note)
    guessed_str = guessed.value if guessed else None
    flag = 'WRONG' if guessed_str != declared else 'ok'
    print(f'{count.bin_id:8} declared={declared!s:22} guessed={guessed_str!s:22} {flag}')
"
```

**Line by line:**

- **Eight right, one wrong — and the wrong one is A-10-2, exactly as `tests/test_domain.py`
  declares.** The other eight notes each contain a word the scan was built to recognise: "receiv"
  inside "receiving", "Goods-in", "picked", "outbound", "Picker", "damaged", "crushed". A-10-2's
  note contains none of them, on purpose — it says "the supplier's Wednesday *drop*", and *drop*
  is not on any list.

The obvious fix — teach the scan the word it is missing:

```diff
-RECEIPT_WORDS = ("receiv", "goods-in", "booked in")
+RECEIPT_WORDS = ("receiv", "goods-in", "booked in", "drop")
```

Run the same check against all nine notes again:

```
A-03-3   declared=receipt_not_booked     guessed=receipt_not_booked     ok
A-10-2   declared=receipt_not_booked     guessed=receipt_not_booked     ok
A-17-1   declared=receipt_not_booked     guessed=receipt_not_booked     ok
B-04-4   declared=pick_not_confirmed     guessed=pick_not_confirmed     ok
B-11-3   declared=pick_not_confirmed     guessed=pick_not_confirmed     ok
B-18-2   declared=pick_not_confirmed     guessed=pick_not_confirmed     ok
C-05-1   declared=known_breakage         guessed=receipt_not_booked     WRONG
C-12-4   declared=known_breakage         guessed=known_breakage         ok
C-18-2   declared=None                   guessed=None                   ok
```

**Line by line:**

- **A-10-2 is fixed. C-05-1 is now broken**, and it was not broken before. Its note reads "A pallet
  was *dropped* in transit and two units were too damaged to shelve" — a breakage, described using
  the word "dropped", which now also matches `"drop"`. `guess_reason_from_note` checks
  `RECEIPT_WORDS` before `BREAKAGE_WORDS`, so a note that matches both is classified by whichever
  list runs first, and the fix that widened the first list stole a case the second list already
  had right.
- **The count of wrong answers did not change. Which answer is wrong did.** Before the fix, one
  note out of nine was misread. After it, one note out of nine is still misread — a different one.
  A word list has no way to be *more correct*; it can only trade one blind spot for another,
  because a word does not know which sense of itself a sentence is using.

And the day's own test notices, on its own:

```bash
uv run pytest -q tests/test_domain.py::test_the_keyword_scan_is_still_wrong_about_a_real_variance
```

```
>       assert "A-10-2" in wrong
E       AssertionError: assert 'A-10-2' in ['C-05-1']
```

**Line by line:**

- `assert 'A-10-2' in ['C-05-1']` — **the inverted case does exactly its job.** It was written to
  go red the moment the scan stops being wrong about A-10-2 in particular, and it went red the
  instant that happened — even though the scan is, in a real sense, *still just as wrong as
  before*. A test that only checked "is the scan ever wrong" would have stayed green through this
  whole edit and told nobody that the failure had moved.

## When it breaks

This part *is* the failure, caused on purpose, and the fix above is the one everybody reaches for
first: read the false negative, find the word missing from the list, add the word. It compiles. It
passes ruff. Run only `test_the_keyword_scan_is_still_wrong_about_a_real_variance` in isolation and
watch it go red — but run the *rest* of the suite and every other test still passes, because
nothing else in this project's tests happens to read C-05-1's note through this function. A team
that fixed this and ran a narrower test — or no test at all, because "adding a word" does not feel
like it needs one — would ship a scan that is confidently wrong about a different bin than before,
with nothing on a dashboard to say so.

The lesson is not "write more keyword lists." It is that a function built to recognise *specific
words* cannot be made to understand *what a sentence means*, and every attempt to patch it one word
at a time moves the boundary of its ignorance without ever closing it. That boundary is exactly
what a model is for, and day 8 is where this project stops pretending otherwise.

## In production

**What a senior writes instead.** Nothing that reads free text with a word list, ever, past a
prototype. The question "does this note describe a receipt, a pick or a breakage" is a
classification task with three labels and a training signal sitting right there in nine years of a
real warehouse's own historical notes — exactly the kind of problem a small model is built for, and
exactly the kind of problem where a regex is a demo, not a design.

**What degrades at scale.** Nine notes, three categories, one blind spot: a human reviewing the
scan's output catches the mistake by lunchtime. Three hundred notes a night across a real
distribution centre, and a keyword scan silently misclassifying five per cent of them is fifteen
variances a night explained wrong — some receipts marked as unexplained shortfalls that trigger a
needless reorder, some genuine shortfalls marked "explained" and never looked at again, and nobody
notices either failure mode because both produce output that looks exactly as confident as the
95% the scan got right.

**The review comment.** *"This diff adds one word to `RECEIPT_WORDS` to fix bin A-10-2. Did you
run the full note set through the scan afterwards, not just the one bin you were fixing? Paste the
before-and-after table."*

**The interview question.** *"You have a rule-based classifier that is wrong on five per cent of
real inputs. Your teammate proposes adding more rules to cover the failures you've seen. What
question do you ask before agreeing, and what would make you recommend a model instead?"*
