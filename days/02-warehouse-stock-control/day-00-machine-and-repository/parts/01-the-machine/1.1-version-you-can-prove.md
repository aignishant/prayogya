## One-line answer

A version you remember is a guess, so the first file this stock desk gets is the one that writes
down what the machine actually said, with the date it said it — including three versions the desk
has not installed yet, because the day a project starts is the day its world is measured.

## The idea

A stock-take finds forty units of a part in bin C-07-2 and the ledger says fifty-two. The
warehouse manager's first question is not "where are the twelve". It is: **which version of the
ledger software was counting when the fifty-two was written?** Because if the answer is "whatever
was on the goods-in terminal that month", then the twelve might be real, or might be a rounding
rule that changed in a release nobody noted, and there is no way to tell the two apart after the
fact.

Nobody on the floor can answer. The terminal was set up by someone who has left. The version was
obvious at the time — it was whatever was installed — and nobody wrote it down, because nobody
writes down the obvious. That is the shape of this failure. It never arrives as an error. It
arrives as a question you cannot answer about a number you already acted on.

So the first thing this project builds is not code. It is a record.

Three words, defined here because everything after this leans on them:

- An **interpreter** is the program that runs your code — one `python` executable, at a real path
  on disk, of one exact version. Not a language, not a setting. A file.
- A **pin** is a written-down exact version, recorded in a file so that a machine and not a memory
  decides what gets used.
- An **observation** is a value you read off this machine today, together with the command that
  printed it and the date you ran it.

The record this part writes holds observations. `PACKAGES.md` is where every version this stock
desk depends on goes, and the rule that governs it is severe on purpose: **a value that was not
observed does not get written down.** If a lookup fails, the row says so and names the exact
command to run. A guess that happens to be right is still a guess, and the next reader — the
manager with the twelve missing units — cannot tell which kind they are holding.

This project adds one thing to the record that its first day would not otherwise have. A project
begins on a date, and on that date the world has a state: the framework it will install on day 1
has a latest version, the protocol its boundary will speak has a current revision, the SDK that
speaks it has a release. Those are facts about the day the project started, and they are cheapest
to write down now — before anything is installed and while the decision about what to install is
still open. So the record's last three rows are versions this desk has *observed and not
installed*, and each row says so. The day that installs one will read its own row first.

## The mechanism

Three commands. Run them in an empty folder; they read the machine and change nothing.

```bash
uv --version
git --version
python --version
```

```
uv 0.12.3 (507230998 2026-08-07 x86_64-pc-windows-msvc)
git version 2.54.0.windows.1
Python 3.12.10
```

**Line by line:**

- `uv --version` — `uv` is the one binary this project uses to get an interpreter and, from day 1,
  an environment. It answers with its own version and, in parentheses, the exact commit it was
  built from and the date of that build. The commit is why this line is worth keeping rather than
  rounding to "0.12": two machines can both say 0.12.3 and one of them can be a nightly.
- `git --version` — the history is this project's memory, so the tool that keeps it is a
  dependency like any other. On Windows the version carries a platform suffix
  (`2.54.0.windows.1`), and that suffix is part of the observation. Writing "2.54.0" would be
  rewriting what the machine said.
- `python --version` — the bare name, resolved by whatever this machine's search path finds first.
  Note the value: **3.12.10**. Hold on to it. The next part pins a different one, and the gap
  between those two numbers is the entire reason this project pins anything at all.
- All three are `--version` rather than `-V` or `version`. Every tool spells this differently and
  two of the three accept several spellings; the long form is the one that works everywhere and
  the one worth typing into a record.

Three more lookups, none of them on this machine — the state of the world on the day this project
began. Each is a page, opened today, and what it said:

| Where | What it said today |
| --- | --- |
| `https://pypi.org/pypi/google-adk/json` | version `2.9.0`, released 2026-09-10; `requires_python >=3.10`; the `mcp` extra requires `mcp<2,>=1.24` |
| `https://pypi.org/pypi/mcp/json` | version `2.2.0`; `requires_python >=3.10` |
| `https://modelcontextprotocol.io/docs/learn/versioning` | "The **current** protocol version is **2026-07-28**" |

Now the record itself. This is the whole file, at its real path in this project.

```markdown
# Packages and pins — Warehouse Stock Control

Append-only. Every version this project depends on gets a row here with the value **actually
observed on this machine**, the date it was observed, the day that added it, and the command that
printed it.

A version you remember is a guess. A guess that happens to be right is still a guess, and the next
reader cannot tell which kind they are holding. If a value could not be looked up, the row says
`TODO(<the exact command>)` and never a number.

A later row may supersede an earlier one. Say so in the last column; do not edit the old row.

| What | Value | Date observed | Day | How it was observed, and why it is here |
| ---- | ----- | ------------- | --- | --------------------------------------- |
| uv | 0.12.3 | 2026-09-12 | 0 | `uv --version`. The one binary that owns this project's interpreter and, from day 1, its environment. |
| git | 2.54.0.windows.1 | 2026-09-12 | 0 | `git --version`. The history is the record of how the desk was built; one day, one commit. |
| CPython (bare `python`) | 3.12.10 | 2026-09-12 | 0 | `python --version`. **Not what this project runs.** Recorded because it is what the bare name resolves to on this machine, and the gap between it and the row below is the reason day 0 pins anything at all. |
| CPython (pinned) | 3.12.13 | 2026-09-12 | 0 | `uv run python -V`, after `uv python pin 3.12.13` downloaded it. The newest 3.12 patch `uv python list` offered on the day; written into `.python-version` so a machine and not a memory decides. |
| google-adk (observed, not installed) | 2.9.0 | 2026-09-12 | 0 | `https://pypi.org/pypi/google-adk/json`, released 2026-09-10. Recorded at the start of the project so the day that installs it pins with the release notes read; its `mcp` extra still requires `mcp<2,>=1.24`. |
| mcp (observed, not installed) | 2.2.0 | 2026-09-12 | 0 | `https://pypi.org/pypi/mcp/json`. The Python SDK that speaks the current protocol revision. |
| MCP protocol revision | 2026-07-28 | 2026-09-12 | 0 | `https://modelcontextprotocol.io/docs/learn/versioning` — "The **current** protocol version is 2026-07-28." A fact about the world, recorded because every boundary day of this project depends on it. |
```

**Line by line:**

- `# Packages and pins — Warehouse Stock Control` — the file is named for what it holds, not for a
  tool. It is not a lockfile and it is not generated: a lockfile records what a resolver chose,
  and this records what a human observed, including things no resolver has an opinion about, like
  which git you have and which protocol revision the world was on.
- **"Append-only"** — stated in the second word of the file because it is the property that makes
  the record worth anything. If a row can be edited, a wrong pin can be quietly corrected, and the
  history of what this desk actually ran stops existing. Old rows stay. New rows supersede.
- **"actually observed on this machine"** — the standard the whole file exists to enforce. Every
  row has to be traceable to a command someone ran or a page someone opened, which is why the last
  column carries the command or the URL and not a description.
- **"`TODO(<the exact command>)` and never a number"** — the escape hatch, and it is deliberately
  more work than looking the value up. A row that carries the command to run is a row the next
  reader can finish. A row that carries a plausible number is a row nobody will ever question.
- **The `Date observed` column** — not "date added". A version is a fact about a day. `google-adk
  2.9.0` was the latest on 2026-09-12, and it had been for two days; a reader on a different day
  reads this row and knows exactly what it does and does not claim.
- **The two CPython rows, and why both are here** — this is the part people delete, and deleting
  it is the bug. The first row records what the bare word `python` means on this machine. The
  second records what this project actually runs. They are different files at different paths with
  different version numbers, and the *only* reason anybody knows that is that both were written
  down.
- **`3.12.13` in the pinned row, not `3.12.12`** — the newest patch the tool offered on the day.
  Part 1.2 is where it is chosen and downloaded; here it is recorded, with the fact that it *was*
  downloaded, because a pin that had to be fetched is a pin that was not lying around.
- **The three "observed, not installed" rows** — nothing in this project imports the framework or
  the SDK yet, and nothing will for a day. The rows are here anyway, because the decision about
  which version to install is made on the day of the install, and that decision should be made
  against what the world looked like when the project started — not against whatever PyPI says on
  a morning three days later. The label in the first column is the honesty: a reader must not
  mistake these for pins.
- **`mcp<2,>=1.24` in the framework's row** — a constraint on an *extra* this desk will not ask
  for, recorded because it is the one fact about these two packages that decides how the boundary
  days go. Whoever installs the framework reads it here first.

## When it breaks

Nothing errors here. That is the failure mode of this whole part, and it is worth seeing what the
*absence* of a record looks like when a version does move underneath you. On the machine this was
written on, asking `uv` for an interpreter version that does not exist does not fail either:

```bash
uv python pin 3.12.99
echo "exit=$?"
cat .python-version
```

```
warning: No interpreter found for Python 3.12.99 in managed installations, search path, or registry
Updated `.python-version` from `3.12.13` -> `3.12.99`
exit=0
3.12.99
```

That command **succeeded** — exit status 0 — on a warning nobody reads in a scroll-back, and wrote
a pin that cannot resolve. The damage surfaces later, somewhere else, as a different command's
error. Somebody typed a version from memory, got a warning instead of a refusal, and the desk was
broken from that moment while still looking fine. The smallest fix is the discipline in this part:
the number you write down is the number a command printed back to you, and after you write it you
run the command again and read it. `uv python pin 3.12.13` puts it back, and the next part is
where that number came from.

## In production

**What a senior writes instead.** Not a hand-kept table — a generated one, printed by the check
that runs in CI, so the record cannot drift from the machine. That is the right end state and the
wrong starting point: a generated record teaches you nothing about which values matter, and a
stock desk with four tools does not need a generator. The senior move at this size is narrower:
keep the file by hand, make the day's check refuse when a pinned value and the running value
disagree — day 1 does exactly that for the interpreter — and put a date on the freshness rows so
that "the world has moved" is a diff against a date rather than a feeling.

**What degrades at scale.** A warehouse's stock ledger is the number the business believes. A
three-aisle synthetic warehouse has sixty bins; a regional distribution centre has sixty
thousand, and a cycle count touches a few hundred of them every night. Every variance the desk
explains is a number somebody will act on — a replenishment raised, a supplier queried, a write-off
booked — and the day an auditor asks why a write-off was booked in March, the answer starts with
what was counting in March. A record with seven rows is cheap now and priceless once the number of
counts per night has three digits in it.

**The review comment.** *"This row says `google-adk 2.9`. Which 2.9? And was that installed, or
looked up? The column says observed; say where."* A version without its source is the same
guess wearing a URL.

**The interview question.** *"Your service booked a stock adjustment six months ago and the
auditor asks what it was running. What in your repository answers that, and what does it depend
on that you do not control?"*

## Check yourself

- **Run:** `uv --version && git --version && python --version` — expect three lines, and expect at
  least one of the three to differ from the values printed above. Write yours into `PACKAGES.md`;
  the rows in this document are observations from one machine on one date, not a target to match.
- **Run:** open the three URLs in the table and read the versions they say *today*. If any differs
  from the row, add a row that supersedes it — do not edit the old one.
- **Say out loud:** Your `PACKAGES.md` has a row saying `python --version` printed something. Which
  file on disk printed it, and what would you type to find out?
- **Say out loud:** why are there three rows for things that are not installed, and what would go
  wrong if they were added on the day of the install instead?
