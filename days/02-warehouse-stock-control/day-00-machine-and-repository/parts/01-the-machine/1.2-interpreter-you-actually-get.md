## One-line answer

The word `python` means a different program on every machine, so this project writes one exact
version into a file that a tool reads instead of a person — and chooses the newest patch the tool
offers on the day, downloads it, and reads it back, because a pin nobody watched resolve is a
number in a file.

## The idea

Two goods-in terminals stand six feet apart on the same dock. A pallet arrives, the same barcode is
scanned on each, and the two screens show different quantities for the same part. Not because the
pallet changed. Because each terminal runs "the scanner software", and "the scanner software" on
the left one is whatever was installed the day it was unboxed and on the right one is whatever was
installed the day it was replaced after a coffee spill, and those are two releases apart with a
different rounding rule for the inner-pack count. Nobody chose either version. Each terminal chose
for itself, by finding the first program that answered to the name.

That is what the bare word `python` does. When you type it, the operating system walks a list of
folders in order — the **search order** — and runs the first file it finds called `python`. Which
file that is depends on what was installed on this machine, in what order, by whom. Part 1.1
observed it: on this machine the bare name resolves to 3.12.10, and nothing about that number was
a decision. It was an accident of history that a version record can reproduce and nothing else can.

A pin is how a project stops choosing by accident. `uv python pin` writes one exact version into a
**pin file** — `.python-version`, whose entire contents are that version and a newline — and every
`uv run` from then on reads the file and uses that interpreter, downloading it if the machine does
not have it. The interpreter becomes a decision, written down, in a file that travels with the
repository. A second machine, a second person, a machine in six months: same file, same version.

Two things about *which* version make this project's pin different from a pin somebody copies.
First, it is the newest patch the tool offered on the day — `uv python list` was asked, it showed
3.12.13 as available for download, and that is what was pinned, because a project that starts today
starts on today's interpreter and not on the one that already happened to be installed. Second,
it was not on this machine: the pin caused a download, and the download is in the transcript,
which is how you know the pin was real rather than a name for something already there.

And one thing about *where* the file lives, which is this part's failure. The tool looks for a pin
file in the working directory and then in every folder above it. A folder with no pin of its own is
governed by whichever parent has one — silently — and the check this day ends with is what turns
that silence into a red line.

## The mechanism

Ask what is available, choose, pin, and read it back:

```bash
mkdir warehouse-stock-control
cd warehouse-stock-control
uv python list | head -8
```

```
cpython-3.15.0rc1-windows-x86_64-none                 <download available>
cpython-3.15.0rc1+freethreaded-windows-x86_64-none    <download available>
cpython-3.14.7-windows-x86_64-none                    <download available>
cpython-3.14.7+freethreaded-windows-x86_64-none       <download available>
cpython-3.13.15-windows-x86_64-none                   <download available>
cpython-3.13.15+freethreaded-windows-x86_64-none      <download available>
cpython-3.12.13-windows-x86_64-none                   <download available>
cpython-3.12.12-windows-x86_64-none                   C:\Users\nisha_gnzw\AppData\Roaming\uv\python\cpython-3.12.12-windows-x86_64-none\python.exe
```

**Line by line:**

- `uv python list` — **everything the tool knows about**, newest first: what it could download
  and what is already on this machine. The two are told apart by the last column, which is either
  `<download available>` or a path.
- `cpython-3.12.13-windows-x86_64-none   <download available>` — **the newest 3.12 patch, and not
  here yet.** This is the one this project pins. A 3.13 or a 3.14 is also on the list, and the
  reason this desk stays on 3.12 is the framework it will install on day 1: `requires_python
  >=3.10` was observed in part 1.1, and the newest patch of a minor version that has been stable
  for a year is the boring choice — chosen on purpose, and recorded as one.
- `cpython-3.12.12-windows-x86_64-none   C:\Users\...\python.exe` — **the one that was already
  here, with its path.** Something else on this machine had installed it. Pinning it would have
  been faster and would have been a choice made by what happened to be installed — the terminal
  choosing for itself, one step removed.

```bash
uv python pin 3.12.13
cat .python-version
uv run python -V
uv run python -c "import sys; print(sys.executable)"
```

```
Downloading cpython-3.12.13-windows-x86_64-none (download) (20.9MiB)
 Downloaded cpython-3.12.13-windows-x86_64-none (download)
Pinned `.python-version` to `3.12.13`
3.12.13
Python 3.12.13
C:\Users\nisha_gnzw\AppData\Roaming\uv\python\cpython-3.12.13-windows-x86_64-none\python.exe
```

**Line by line:**

- `uv python pin 3.12.13` — **writes the pin, and this time it downloads.** Twenty-one megabytes,
  once, into the tool's managed installations. The `Downloading` line is the evidence the previous
  part asked for: this interpreter was not on the machine before this command and is now.
- `Pinned .python-version to 3.12.13` — the tool's own confirmation. Part 1.1's failure showed the
  same command *succeeding* on a version that does not exist, with a warning instead of a download;
  the difference between that transcript and this one is the difference between a pin and a typo.
- `cat .python-version` → `3.12.13` — **the whole file.** One version and a newline. Nothing else
  goes in it, and nothing reads it but the tool.
- `uv run python -V` → `Python 3.12.13` — **read back.** Not `python -V`, which would print the
  bare name's answer from part 1.1. `uv run` is what makes the pin file matter: it reads the file,
  finds or fetches that interpreter, and runs the command with it.
- `sys.executable` — **the actual file.** A path ending in `cpython-3.12.13-windows-x86_64-none\python.exe`
  inside the tool's own folder. This is the interpreter. Not a language, not a setting; this file.
  Compare it with what `python -c "import sys; print(sys.executable)"` prints on your machine, and
  the two paths are the two terminals on the dock.

The whole file, at `.python-version`:

```text
3.12.13
```

**Line by line:**

- `3.12.13` — **exact.** Not `3.12`, which would let the tool choose the patch and choose
  differently on two machines; not `>=3.12`, which is a constraint, not a pin. Three numbers and a
  newline, and a machine reads them.

## When it breaks

The tool looks for a pin file in the working directory and then in each of its parents. Delete this
project's pin, put one in the folder above, and ask again:

```bash
rm .python-version
echo "3.12.12" > ../.python-version
uv run python -V
```

```
Python 3.12.12
```

No warning. No error. The project has no pin of its own, so the tool walked up one folder, found
somebody else's, and obeyed it — and `3.12.12` is a real interpreter on this machine, so the
command runs and prints a plausible number. Somebody who cloned this project into a folder under a
parent that already had a pin — a `projects/` directory with its own `.python-version`, say — would
run this desk on an interpreter this project never chose, every time, with nothing on the screen to
say so.

The check this day ends with catches it, because it reads *this folder's* pin file and refuses when
there is none:

```
RED  interpreter       no .python-version: nothing decides which interpreter runs this desk
```

Put the file back and remove the parent's:

```bash
rm ../.python-version
uv python pin 3.12.13
uv run python -V
```

```
Python 3.12.13
```

The smallest fix is the file in the folder. The habit is the second line of every transcript in
this part: after the pin, read it back, and read it back with `uv run` and not with the bare name.

## In production

**What a senior writes instead.** The same one-line file, plus the tool's own `uv python install`
in the setup listing and in the pipeline — so the download happens as a named step rather than as
a side effect of the first `uv run` — and a pin by *implementation and build* where the platform
matters: `cpython-3.12.13` rather than `3.12.13`, so a machine that happens to have a different
Python implementation of the same version cannot satisfy the pin by accident. Day 19 of this
project puts the same version into a container image, where the base image *is* the pin and the
tool is told not to download at all.

**What degrades at scale.** A warehouse's scanning terminals are the version problem at its
simplest, and a distribution centre has three hundred of them. Every one that "chooses for itself"
is a device whose behaviour depends on its own history, and the day two of them disagree about an
inner-pack count is the day somebody spends a shift with a clipboard finding out which is right.
Three hundred devices reading one pin file is three hundred devices that agree — and the cost is
that changing the pin is now a decision somebody has to make, on purpose, which is the point.

**The review comment.** *"`.python-version` says `3.12`. That resolves to a different patch on a
machine that already has 3.12.10 than on one that has nothing. Pin the patch, and paste the
`Downloading` line from the machine that had to fetch it."*

**The interview question.** *"Two developers type `python` and get different programs. Explain
exactly how that happens, and what a project does so that it cannot."*

## Check yourself

- **Run:** `uv python list | head -8` and say which line this project's pin came from, and whether
  it was on your machine before you pinned it.
- **Run:** `uv run python -c "import sys; print(sys.executable)"` and then the same without `uv
  run`. Two paths. Say which one the pin file chose.
- **Do it:** the parent-folder trap. Move the pin up one folder, run `uv run python -V`, run the
  check, read `no .python-version`. Put it back and run both again.
- **Say out loud:** why did this project pin 3.12.13 rather than the 3.12.12 that was already
  installed, and why not 3.14?
