## One-line answer

The first thing in this repository's history is not code, it is the one page that says what the
desk reconciles, who may write to the ledger, which twenty days build it and what has to be true
before it is done — because a system nobody can describe in a page is a system nobody can tell is
finished.

## The idea

A new supervisor takes over the night cycle count. The handover is a walk down aisle B with the
person leaving: count the bins on the sheet, key the numbers into the terminal, and if the number
is different from the ledger — well, it depends. Sometimes goods-in has not booked a receipt yet.
Sometimes a pick was confirmed late. Sometimes somebody dropped a case and did not say. You raise a
replenishment if it looks low. You will pick it up.

By Thursday the supervisor has picked up that "it depends" has nine cases, that two of them are
argued about, and that nobody agrees on which discrepancies mean *order more* and which mean *find
out what happened*. None of it is written down, because everyone who knows it is busy doing it.

That is a desk without a brief, and the cost is not confusion. The cost is that nobody can say what
"working" means, so nobody can say what "broken" means either.

This project is built doc-first for exactly that reason. Before any code exists, one page says what
this desk is: what arrives at it, what it decides, which tools it has, which agents do the
deciding, where its data lives, which twenty days build it in what order, and — the load-bearing
sentence — **what has to be true before it can be called done**. That page is `PROJECT.md`, and
writing it before the code is not ceremony. It is the only moment in the project when the shape of
the thing is still cheap to change.

Then that page becomes the first thing in the repository's history.

A **repository** is a folder plus a complete record of every change ever made inside it. Three
words for the three states a file can be in, and they are easy to confuse because git uses one
verb, `add`, for two of them:

- the **working tree** is the folder as it exists on disk right now;
- the **staging area** is the list of paths git is holding for the next commit — what `git add`
  writes into;
- a **commit** is a permanent, named snapshot of everything that was staged, with a message saying
  why.

A path git has been told to hold, from a `git add` onwards, is **tracked**. That word does almost
nothing in this part and it does everything in the next two, so it is defined here where it is
still calm.

One more thing this project's brief carries that a brief written from a template would not: its
own day map. Twenty days, of which two are this project's alone — one on what two writers do to a
stock ledger, one on the boundary under a second copy of itself — inserted after the boundary days
because the ledger is the thing this desk exists to protect, and the numbering of every later day
shifts by two to make room. The map is in the brief because the map is a decision about the
project, made on day 0, and a decision that lives only in someone's head is the handover on aisle B.

## The mechanism

The whole brief, at its real path at the root of the project:

````markdown
# P02 · Warehouse Stock Control

**Industry.** Logistics — warehouse management.

**What it is.** A desk for a synthetic three-aisle warehouse whose counted stock disagrees with
its recorded stock. Cycle counts arrive from the floor, one bin at a time. The desk reconciles each
count against the stock ledger, explains every discrepancy it can — a receipt not yet booked, a
pick not yet confirmed, a known breakage — and raises a replenishment only where no explanation
covers the gap. The ledger has exactly one writer, and the day the desk is allowed a second one is
the day its own eval goes red.

**Days.** 20 · **Deploy tier.** D3 · **Depends on nothing, and references nothing.**

real supplier appears anywhere in it.
````

**Line by line:**

- **`# P02 · Warehouse Stock Control`** — the project's own name and number, at the top of its own
  repository. This folder does not know about any other; everything it needs is inside it, and
  everything it teaches is taught in it.
- **`**Industry.** Logistics — warehouse management.`** — naming the industry in the second line
  is what stops this brief being a generic agent demo: every decision below inherits meaning from
  it. A "variance" means something specific on a warehouse floor, and so does "the ledger".
- **`**What it is.**`, in one paragraph** — the whole system in the order the work happens: a
  count arrives, it is reconciled, the gap is explained or it is not, and one of two things
  happens. If this paragraph needs a second one, the project is two projects.
- **"The ledger has exactly one writer"** — **the sentence the whole project is arranged around.**
  It is in the description, in the boundary row, in the done-when, and it is the subject of both
  inserted days. A stock ledger with two writers is a ledger whose number nobody can trust, and a
  desk that reconciles against an untrusted number is explaining noise.
- **`**Days.** 20 · **Deploy tier.** D3`** — the size of the commitment, up front. D3 is this
  project's deploy floor: a running container with a health endpoint, a compose file with the
  boundary beside it, and CI running the evalset. Written on day 0 because it changes what day 1
  builds.
- **"Depends on nothing, and references nothing."** — a promise about this repository, and the one
  a reader can check most easily: if any file in this folder needs something outside it, the
  sentence is false and the project is not finished.
- **The triad table — Tools, MCP boundary, Cast** — three rows because these are the three
  decisions that are expensive to change later. The tool signatures name their arguments, because
  a tool's arguments are its interface and an interface changed on day 7 is four days of rework.
  `record_count` and `raise_replenishment` are the two that write, and the boundary row says who
  owns the thing they write to.
- **The day map** — twenty rows, and the two that are not in every project's spine are days 4 and
  6. Their titles say what they are for. Every day from 7 onward carries a number two higher than
  the spine's; a reader of the plan's spine and a reader of this file are counting the same days
  with different numbers, and this file is the one that is right for this project.
- **The feature-set table** — twenty rows, one per day, and the third column is the reason each
  day exists *here*: not "sessions" but *yesterday's aisle leaking into today's reconciliation*.
  Every row is a failure this warehouse would actually have, and a row that could be pasted into
  another project's brief unchanged is a row that has not been written yet.
- **"Done when."** — sixty bins, nine planted variances, one eval that goes red on one specific
  change. Three numbers and a sentence, and every one of them is checkable by a stranger. This is
  the sentence day 18 of this project will be pointed at.
- **"All data in this project is synthetic."** — the last thing in the file, and the first thing a
  reader who finds part numbers and supplier names in `data/` needs to have been told.

Then the history. The brief goes in first and alone:

```bash
git init
git config user.name "your name"
git config user.email "you@example.com"
git rev-parse --show-toplevel
git add PROJECT.md
git commit -m "P02 day 0: the brief"
git log --oneline
```


**Line by line:**

- `git init` — **the folder becomes a repository.** Nothing visible changes except a `.git`
  directory, and from now on every file in the folder is in one of the three states above.
- `git rev-parse --show-toplevel` — **the one line this project's day-0 check asks for that its
  first version would not have.** It prints the folder git considers the root. If it prints this
  folder, the repository is this project's. If it prints a folder *above* this one, this project
  is inside somebody else's repository, and every `git add` from here would be adding to theirs.
  Part 3.1 turns that into a red line.
- `git add PROJECT.md` — **by name.** Every `git add` on this day names its path. `git add -A` is
  the enemy of part 3.2, and the habit that prevents it starts on the first commit.
- `1 file changed, 77 insertions(+)` — **the brief is seventy-seven lines and it is the whole first
  commit.** Nothing else is in it: no code, no pin, no rule. A reader walking the history from the
  start reads what the desk is before reading anything about how it is built.
- `61a365e` — **a name computed from the contents.** Your hash will differ, because your name and
  email and the second you pressed enter are in it. That is the property that makes a commit a
  record rather than a label: the same page committed twice is two different commits, and nobody
  can quietly swap one for another.

The pin and the record go in next, together, because they are one decision:

```bash
git add PACKAGES.md .python-version
git commit -m "P02 day 0: the pins, and the interpreter this desk runs on"
```

```
[main 800b067] P02 day 0: the pins, and the interpreter this desk runs on
 2 files changed, 22 insertions(+)
 create mode 100644 .python-version
 create mode 100644 PACKAGES.md
```

**Line by line:**

- **Two files, one commit** — the record that says which interpreter was chosen and the file that
  makes the choice. Separating them would let the history hold a pin with no record of why, or a
  record of a pin that was never written.

## When it breaks

Write the brief after the code, which is what every project does that does not decide otherwise
on day 0. There is no error. There is a day 6 on which the tools table says `record_count` takes a
quantity and the code takes a delta, and nobody can say which is the bug — because the brief was
written to describe the code and the code was written to describe whatever the author remembered
of the brief. A brief written first is the thing the code can be wrong *against*.

The nearer failure, and the one the transcript above guards, is `git init` inside a folder that
already sits under a repository. On this machine, a copy of this project placed inside another
repository's folder and asked the question:

```bash
git rev-parse --show-toplevel
```

```
C:/Users/nisha_gnzw/AppData/Local/Temp/p02/outer
```

That is not this folder. Every `git add` here would stage into `outer`'s history, the ignore rules
that apply are `outer`'s, and a `.env` written here is governed by whatever `outer` says about
`.env`, which is probably nothing. The smallest fix is `git init` *here*, which creates this
folder's own repository and makes it the nearest one — and the check in part 3.1 is what notices
before the first `git add` does.

## In production

**What a senior writes instead.** The same page, with two additions that cost nothing on day 0 and
a great deal later: a *non-goals* line under the description — the desk does not decide what to
order from whom, does not price anything, does not touch goods-in — and a *glossary* of the five
words the industry uses that a reader from outside it will misread: bin, SKU, cycle count,
variance, replenishment. A brief that defines its words is a brief two people can disagree about
precisely.

**What degrades at scale.** A three-aisle warehouse with sixty bins is a brief one person holds in
their head. A distribution centre with sixty thousand bins has a stock-control team, a goods-in
team, a picking team and a finance team, and each of them has a different answer to "what counts
as a variance" — a receipt booked late is a variance to finance and not to goods-in. The brief is
the document those four teams argue about *before* the desk is built, and a desk built without it
implements one team's answer and gets three complaints.

**The review comment.** *"The done-when says nine planted variances. The domain day has not been
written. Who plants them, and how does the eval know which nine?"* The right answer is a sentence
in this file, and the review comment is what makes somebody write it on day 2 rather than discover
it on day 18.

**The interview question.** *"You inherit a system with no design document. What is the first
page you write, what goes in it, and what does writing it change about the code you have not
touched yet?"*

## Check yourself

- **Run:** `git log --oneline` — expect the brief as the first commit, alone, and `git show
  --stat HEAD~1` to list `PROJECT.md` and nothing else.
- **Run:** `git rev-parse --show-toplevel` and confirm it prints this folder.
- **Say out loud:** `git add` puts a file into which of the three states, and which word describes
  it from then on?
- **Say out loud:** why does the day map live in the brief and not only in the curriculum that
  assigned it?
