## One-line answer

A clone learns which key it needs from a committed file that carries the name and never the value
— `.env.example` — and the real value goes into `.env`, which the rule in the previous part already
covers, so the secret exists on this machine and in no history anywhere.

## The idea

Every cage in every warehouse has a key, and every key has a tag. The tag says *cage C — stock
control — key 3 of 3*. It does not say the cut of the key. A new supervisor reads the tag, knows
which key they are missing, and asks the site manager for it in person; the tag is on the board
for anybody to read, and the key is in a pocket. If somebody wrote the cut on the tag, every person
who walked past the board would have the cage.

`.env.example` is the tag. It is committed, so it reaches every clone. It lists every name the desk
expects to find in its **process environment** — the set of name-to-string pairs the operating
system hands a program when it starts, which Python reads as `os.environ`, and which has never
heard of any file. Beside each name is nothing: an equals sign and a newline. A reader knows what
to set. Nobody learns what it was set to.

`.env` is the key. It is the same file with the value filled in, it lives only on this machine, and
the rule from part 2.2 means git will never mention it. Day 1 writes the code that reads it into
the process environment; today it is written by hand, and today's check is what confirms it was.

The one decision worth a paragraph is the *name*. This desk explains variances with a Gemini model
on an AI Studio key, and the provider's own documentation — opened today, quoted in the hub — reads
two variable names, `GEMINI_API_KEY` and `GOOGLE_API_KEY`, and says which wins when both are set:
`GOOGLE_API_KEY`. So this project sets that one and nothing else, because a project that sets both
has two places for the same secret to be wrong, and a project that sets the losing one has a key
that is silently overridden by whatever else on the machine set the winning one. One name, the
winning one, and a comment saying why.

## The mechanism

The whole file, at `.env.example`:

```text
# Warehouse Stock Control — the shape of .env, with no value in it.
#
# Copy this file to .env and fill the value in. .env is ignored and never leaves your machine;
# this file is committed, and it is the only place a new reader can learn which names the desk
# expects to find in its environment.

# The key the desk explains variances with. Get one at https://aistudio.google.com/apikey
# Setting this name alone is what selects the AI Studio path. Nothing else is needed here.
GOOGLE_API_KEY=
```

**Line by line:**

- **"the shape of .env, with no value in it"** — the file describes itself in its first line,
  because a reader who opens it expecting a secret needs to be told at once that there is none
  here and where the secret goes.
- **"Copy this file to .env"** — the instruction, in the file, so that it travels with the file.
  `SETUP.md` repeats it; a stranger who opens this file first should not need to have found
  `SETUP.md`.
- **"Get one at https://aistudio.google.com/apikey"** — the one URL, read from the provider's own
  page today. A key file that does not say where keys come from sends every new reader to a
  search engine, and the first result is not always the provider.
- **"Setting this name alone is what selects the AI Studio path"** — the reason there is one name
  and not two. The provider reads two and prefers this one; a comment that explained neither would
  leave the next person adding the other "to be safe", which is the opposite of safe.
- `GOOGLE_API_KEY=` — **the name, an equals sign, and nothing.** Not `GOOGLE_API_KEY=your-key-here`,
  which is a value — a wrong one, and one that part 3.1's check would accept as "set". The check
  reads names from this file and values from `.env`; a placeholder value here would be a value the
  check learns to expect.

Then the copy, and the one edit made by hand:

```bash
git add .env.example
git commit -m "P02 day 0: the names the desk expects, with no values"
cp .env.example .env
git status --short
```

```
[main 655dba8] P02 day 0: the names the desk expects, with no values
 1 file changed, 9 insertions(+)
 create mode 100644 .env.example
```

**Line by line:**

- **The example is committed before the copy is made** — the tag goes on the board before the key
  is cut. Nothing depends on this order today; it is the habit that part 2.2 is about, kept where
  it costs nothing.
- `cp .env.example .env` — **the same file, at the name the rule covers.** On PowerShell,
  `Copy-Item .env.example .env`.
- `git status --short` **prints nothing.** `.env` exists on disk, and git does not mention it — the
  rule from part 2.2, consulted at the moment git was about to speak, and answering no. This is the
  first time the rule has been asked about a file that is actually there.
- **The value is put in with an editor, not with a shell.** Open `.env`, put the key after the
  equals sign, save. Not `echo "GOOGLE_API_KEY=..." > .env`, because a shell keeps a history and
  a history is a file; the tag board is not the place to write the cut, and neither is the
  terminal's scroll-back.

## When it breaks

Put a value in the example — the thing everyone does once, to save a step:

```diff
-GOOGLE_API_KEY=
+GOOGLE_API_KEY=AIza-not-a-real-key-but-shaped-like-one
```

Nothing errors. `git status` shows `.env.example` modified, because it is tracked and meant to be;
the next commit carries it; every clone from then on has the value. It is a secret published on
purpose, by a file whose whole job is to hold no secrets, and the ignore rule cannot help because
the file is the one it was told to except. The check in part 3.1 does not catch this either — it
reads the example for names and never looks at what follows the equals sign — and the `TODO(me)`
in the hub is exactly that sixth check. The smallest fix today is the discipline: the example
carries names, and the one time a value belongs in it is never.

## In production

**What a senior writes instead.** The same example file, plus the values kept in a secrets manager
rather than in `.env` at all — injected into the process environment by whatever starts the
process, so that no file on any developer's disk holds a real key. `.env` survives as a local
convenience for a laptop, and day 19 of this project shows the container form of the same idea: a
file on the machine that runs the container, handed to the process at start-up, never in the
image. And a key per person, not a key per project, so that when one leaks the rotation is one
person's morning and not the whole team's.

**What degrades at scale.** One name in one file. A distribution centre's stock system talks to a
goods-in system, a carrier's tracking service, a label printer's API and a model provider, and each
has a credential with a different shape and a different owner. The example file scales — it is a
list of names with a comment each — and what does not scale is the `.env` on each of twelve
laptops holding all four, because the day one laptop is lost, four credentials are rotated and
four services notice. The example file's real job at that size is to be the *inventory* of what
must be rotated.

**The review comment.** *"`.env.example` has `GEMINI_API_KEY=` and `GOOGLE_API_KEY=`. The
provider's page says the second wins. Pick one, and say in the comment why it is that one."*

**The interview question.** *"A new developer clones your repository. Without asking anybody,
how do they find out which secrets they need, and how do you make sure they never find out what
yours were?"*

## Check yourself

- **Run:** `cat .env.example` — expect one name and no value; then `git status --short` after
  copying it to `.env` — expect nothing.
- **Run:** `git log --oneline -- .env.example` — one commit; `git log --oneline -- .env` — none,
  and say why the second is the important one.
- **Say out loud:** two variable names, one file. Which one, why, and where did you read it?
- **Say out loud:** where must the value never be typed, and what file would it end up in if it
  were?
