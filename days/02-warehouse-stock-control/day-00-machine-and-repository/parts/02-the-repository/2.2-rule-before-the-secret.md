## One-line answer

An ignore rule is git's answer to "should I mention this path?", and git only asks about paths it
is not already holding — so `.gitignore` is written and committed before `.env` exists, and the
proof is a command that answers about a file that is not there yet.

## The idea

A warehouse has a cage: a locked mesh enclosure at the end of aisle C where the high-value stock
sits — the items small enough to walk out in a pocket. The rule about the cage is written on the
door, and it is written *before* the first pallet goes in: what goes in the cage, who has the key,
and that nothing in the cage appears on the open-floor count sheet. Write the rule after the first
pallet is on the open floor and the rule has nothing to say about it — the stock is already out,
already counted, already on a sheet somebody photocopied.

`.gitignore` is the rule on the cage door, and the order matters for exactly the reason it matters
on the floor. Git's ignore machinery is a question-and-answer: when git is about to *mention* a
path — in `git status`, in `git add .`, in an editor's "stage all" button — it first asks the
ignore rules whether it should. The rules answer about paths **git is not already holding**. A
tracked path is never asked about. So an ignore rule for `.env` written *after* `.env` has been
staged is a rule that will never be consulted, and the file will be in the next commit and every
commit after it, and in the history for as long as the history exists.

That order — the rule before the file — is the whole content of this part, and the reason it gets
a part of its own is that it is invisible when done right. Nothing errors. Nothing prints. The only
evidence that it was done in the right order is a command that asks git about a path that does not
exist yet and gets an answer, which is the mechanism below.

Two more things about the rule file, both of which the later parts lean on. Git reads ignore
patterns from six places — the **ignore sources** — of which this file is one, and the only one a
reviewer sees; two of the six are per-machine and invisible, which is why the check in part 3.1
asks git which source a rule came from rather than assuming. And within one file the *last*
matching line decides, which is why a line that starts with `!` — a **negated pattern**, taking a
path back out of the ignore list — only works when it sits *below* the pattern it is excepting.
This project's rule has one such line, and it is placed where it is on purpose.

## The mechanism

The whole file, at `.gitignore`:

```gitignore
# Warehouse Stock Control — what git must never be told to hold.
#
# This file exists before a single file it names does. That order is the whole point: an ignore
# rule speaks only about paths git has never tracked, so a rule written after the first
# `git add` has nothing to say about the file it was written for.

# Secrets. Never committed — not once, not "just to see if the key works".
.env
.env.*
!.env.example
*.key
*.pem
service-account.json

# The environment. Rebuilt from the lockfile by uv, so it is never committed and never copied
# from one machine to another.
.venv/
__pycache__/
*.pyc

# Editors and operating systems, which have opinions about every folder they open.
.DS_Store
Thumbs.db
.idea/
.vscode/
*.swp
```

**Line by line:**

- **The comment at the top says when the file was written** — before any file it names — because
  that is a fact about the history that the file's contents cannot otherwise carry, and the next
  reader will not think to check the commit order.
- `.env` — **the secret, by its exact name.** Line 8, and part 3.1's check names the line.
- `.env.*` — **every variant.** `.env.local`, `.env.production`, `.env.bak` — the files people make
  when they have two keys, and the one they forget. The transcript below shows this line catching
  `.env.local`.
- `!.env.example` — **the one file with that prefix that must be committed**, taken back out of
  the previous line's reach. It sits *below* `.env.*`, and that is not tidiness: within one ignore
  file the last matching line wins, so a negation above the pattern it is excepting does nothing.
  Swap the two lines and `.env.example` silently never reaches a clone — a stranger's checkout
  would not know which key to set, and no command would say why.
- `*.key`, `*.pem`, `service-account.json` — **the other shapes a credential arrives in.** This
  desk uses one API key in one variable, and it will not on every machine forever; the day
  somebody downloads a service account file into the project folder, the rule is already there.
- `.venv/` — **the environment is rebuilt, never copied.** Day 1 creates it from a lockfile; a
  committed `.venv` is a hundred megabytes of one machine's binaries that are wrong on every other.
- `__pycache__/` and `*.pyc` — **compiled bytecode**, regenerated on every run and different per
  interpreter version, which after part 1.2 is a thing this project has an opinion about.
- **The editor block** — files that other people's tools create in your folder. None of them are
  this project's, and one of them — `.idea/` — can carry a path to a local copy of the key.

Now the proof that the order was right. `.gitignore` is written; `.env` is not. Ask git about the
file that does not exist:

```bash
git check-ignore -v .env
echo "exit=$?"
git add .gitignore
git commit -m "P02 day 0: the ignore rule, before any secret exists"
git check-ignore -v .env
echo "exit=$?"
```

```
.gitignore:8:.env	.env
exit=0
[main 872933b] P02 day 0: the ignore rule, before any secret exists
 1 file changed, 26 insertions(+)
 create mode 100644 .gitignore
.gitignore:8:.env	.env
exit=0
```

**Line by line:**

- `git check-ignore -v .env` — **asks the question git will ask itself later**: if a path called
  `.env` appeared, would it be mentioned? `-v` says which rule answered.
- `.gitignore:8:.env	.env` — **the source, the line, the pattern, and the path**, tab-separated.
  The file is `.gitignore`, the rule is on line 8, the pattern is `.env`, and it matched the path
  `.env`. This is the line part 3.1's check reads and prints back, so a rule that came from a
  per-machine ignore source — one a reviewer cannot see — would show up as a different file name
  here.
- `exit=0` — **the verdict.** Zero means ignored. The printed line is for a person; the exit
  status is for the check that runs this, and part 3.2 is about the case where the printed line is
  blank and the exit status is the only thing that speaks.
- **The answer is the same before and after the commit** — because `check-ignore` reads the rule
  file from the working tree. Committing it is what makes the rule part of the history a clone
  receives; the answer was already right on disk.
- **The file being asked about does not exist yet**, and git answered anyway. That is the whole
  proof: the rule was written first, and there is a command that can show it.

Two more questions, for the two lines whose behaviour is least obvious. The example file is
committed in the next part, and from that moment a tracked path is never asked about — so the
second question is put with `--no-index`, which asks the rules alone, ignores what git holds, and
gives the same answer before the commit and after it:

```bash
git check-ignore -v .env.local .env
git check-ignore -v --no-index .env.example
echo "exit=$?"
```

```
.gitignore:9:.env.*	.env.local
.gitignore:8:.env	.env
.gitignore:10:!.env.example	.env.example
exit=0
```

**Line by line:**

- `.gitignore:9:.env.*	.env.local` — **the variant line catches the variant.** A `.env.local`
  written by somebody with two keys is ignored by line 9, and the answer says so.
- `--no-index` — **ask the rules, not the index.** Without it, once `.env.example` is committed in
  part 2.3, `git check-ignore -v .env.example` prints nothing and exits 1 — the same silence part
  3.2 gets for a tracked `.env` — because a tracked path is outside the ignore machinery entirely.
  With it, git evaluates the patterns as if the path were new, today and every day after.
- `.gitignore:10:!.env.example	.env.example` — **the negation is the rule that decided.** Line 9
  matched, line 10 unmatched it, and with `-v` git reports the last pattern that had a say — the
  negated one — and exits 0 because a pattern matched. Read the `!` in the third column: that is
  the line saying *not ignored*, and it is below the line it overrides.

## When it breaks

Swap the two lines that must be in order:

```diff
 .env
-.env.*
 !.env.example
+.env.*
```

```bash
git check-ignore -v --no-index .env.example
echo "exit=$?"
```

```
.gitignore:10:.env.*	.env.example
exit=0
```

`.env.example` is now ignored, and the third column says which line did it: `.env.*`, on line 10,
after the negation on line 9 had already spoken. The last match decides — so the one file in this
block that must reach a clone never will, in any repository where it is not already tracked. There
is no error; `git status` in a fresh clone simply stops mentioning the file, and the failure is
discovered by a stranger on a different machine who cannot find out which key the desk needs. In
*this* repository nothing changes at all, because the file is already tracked and tracked paths
are never asked about — which is why the question has to be put with `--no-index`, and why part
3.1's check does not catch this one. The `TODO(me)` in the hub asks whether it should. The smallest
fix is the order, and the habit is the one this part is about: after writing a rule, ask git the
question — for the file it must ignore *and* for the one it must not, with `--no-index` for the
one that is already committed.

## In production

**What a senior writes instead.** The same file, plus a pre-commit hook that runs
`git check-ignore` on every staged path and refuses the commit if any secret-shaped file — by name
*or by content*, using a scanner that recognises what a key looks like — is about to be recorded.
The ignore file is the rule on the cage door; the hook is the person on the door checking pockets.
Both, because part 3.2 shows the rule alone can be walked past with one flag.

**What degrades at scale.** One `.env` in one folder is one rule. A distribution centre's stock
system has a goods-in service, a picking service, a finance export and a label printer, each with
its own credentials, on twelve developer machines and three build servers. The `.env.*` line is
what scales — it does not need to know the names — and the thing that does not scale is the
per-machine ignore source that one developer set up in 2024 and that the rest of the team's clones
do not have. That is the failure the `-v` flag exists for: a rule that lives on one machine shows
up as a different file name in the answer.

**The review comment.** *"`!.env.example` is above `.env.*` in this diff. That negation does
nothing there. Move it below and paste `git check-ignore -v .env.example` exiting 1."*

**The interview question.** *"You add `.env` to `.gitignore` and `git status` still shows it as
modified. Explain, and fix it without losing the rule."*

## Check yourself

- **Run:** `git check-ignore -v .env` before `.env` exists — expect the source, the line and the
  pattern, and exit 0.
- **Run:** `git check-ignore -v --no-index .env.example` — expect line 10's negation in the third
  column, and say why the question needs `--no-index` once the file is committed.
- **Do it:** swap lines 9 and 10, ask about `.env.example` again, read the wrong answer, swap them
  back.
- **Say out loud:** name the two states a path can be in from git's point of view, and which one
  the ignore rules are never asked about.
