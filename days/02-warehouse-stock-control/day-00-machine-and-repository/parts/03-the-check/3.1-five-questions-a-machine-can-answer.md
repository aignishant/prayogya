## One-line answer

Everything this day set up can stop being true without anything erroring, so the day ends with a
program that asks the machine five questions — the interpreter, the repository, the ignore rule,
the tracking, the key — and answers with an exit status, because a setup that is remembered is a
setup that has already drifted.

## The idea

The night shift's last job is the close-down walk. Cage locked, key on the board, count sheets in
the tray, terminals on the right software, ledger backed up. Everybody does it and everybody does it
from memory, and the morning that one item is missed is the morning nobody can say which one it
was — because the walk was never written down, so there is nothing to compare the morning against.

Then somebody writes it as a form. Five lines, five boxes, and the walk becomes something a person
can be *wrong* about in a specific place: box three is unticked, and box three is the cage. Better
still, the form goes on the terminal and the terminal fills it in — it can see whether the cage
sensor says locked, whether the backup job ran, which software version it is running — and a person
reads five lines and one verdict instead of remembering nineteen things.

`check.py` is that form, filled in by the machine. It asks five questions, each about one thing
this day set up, each answered by reading the machine rather than by trusting the reader:

1. **Is the interpreter the pinned one?** Read `.python-version`; compare it with the version of
   the interpreter actually running this script.
2. **Is there a repository here, and is it this folder's?** Ask git where its root is. This is
   the question the first version of this check would not have asked, and the reason it is here
   is part 2.1's failure: a folder inside somebody else's repository answers every other git
   question *about the wrong repository*, reassuringly.
3. **Is `.env` ignored, and by which rule?** Ask git the question from part 2.2, and print the
   source.
4. **Is `.env` tracked?** Ask git whether it is holding the path. Asked separately from question
   three because — part 3.2 — the two go wrong in different ways.
5. **Is every name in `.env.example` set in `.env`?** Read the names from one file and the values
   from the other, and never print a value.

Every answer has three parts: a verdict a program can read, a line a person can read, and — when
the verdict is red — the thing to do about it, in the line. And the program's own verdict is its
**exit status**: the single number a process hands back when it ends, zero for success, the only
channel through which one program tells another how it went. Everything printed is for you. The
number is for the next thing that runs this.

The reason this file exists on day 0, before any code it could check, is that a check nobody has
watched go red is not evidence of anything. This part writes it and makes it green. The next part
breaks it on purpose.

## The mechanism

The whole file, at `check.py`:

```python
"""The stock desk's day-zero check: is this machine ready to hold a stock ledger?

Five questions, asked of the machine rather than of the reader. It imports nothing that is not
in the standard library, because on day zero this project has no dependencies and no environment
to install them into.

Run it with the pinned interpreter:

    uv run python check.py

Exit status 0 means every question answered yes. Exit status 1 means at least one did not, and
the line that starts with RED says which.
"""

from __future__ import annotations

import platform
import subprocess
import sys
from pathlib import Path

ROOT = Path(__file__).resolve().parent


def git(*args: str) -> tuple[int, str]:
    """Run a git command in this project and return its exit status and its output.

    `text=True` so the output is a string. Errors are captured rather than printed, because the
    verdict this file prints is the only thing its caller should have to read.
    """
    done = subprocess.run(
        ["git", *args], cwd=ROOT, capture_output=True, text=True, check=False)
    return done.returncode, (done.stdout + done.stderr).strip()


def env_names(path: Path) -> list[str]:
    """The variable names declared in a .env-shaped file, in the order they appear."""
    names = []
    for line in path.read_text(encoding="utf-8").splitlines():
        line = line.strip()
        if line and not line.startswith("#") and "=" in line:
            names.append(line.split("=", 1)[0].strip())
    return names


def env_values(path: Path) -> dict[str, str]:
    """The name-to-value pairs in a .env-shaped file. Nothing here reads the process environment."""
    values = {}
    for line in path.read_text(encoding="utf-8").splitlines():
        line = line.strip()
        if line and not line.startswith("#") and "=" in line:
            name, value = line.split("=", 1)
            values[name.strip()] = value.strip()
    return values


def check_interpreter() -> tuple[bool, str]:
    pin_file = ROOT / ".python-version"
    if not pin_file.exists():
        return False, "no .python-version: nothing decides which interpreter runs this desk"
    pinned = pin_file.read_text(encoding="utf-8").strip()
    running = platform.python_version()
    if running != pinned:
        return False, f"pinned {pinned}, running {running}: run it with `uv run python check.py`"
    return True, f"interpreter {running}, as pinned in .python-version"


def check_repository() -> tuple[bool, str]:
    """Is there a repository here at all, and is it this folder's?

    Asked first among the git questions, so that the two below it can mean what they say. Without
    this, "git is not holding .env" and "there is no git here" print the same reassuring line, and
    only one of them is good news.
    """
    status, top = git("rev-parse", "--show-toplevel")
    if status != 0:
        return False, "no repository: `git init` here before anything else is written"
    if Path(top).resolve() != ROOT:
        return False, f"this folder is inside another repository rooted at {top}"
    return True, "a repository, rooted here"


def check_ignored() -> tuple[bool, str]:
    if not (ROOT / ".gitignore").exists():
        return False, "no .gitignore: write the rule before the secret exists, not after"
    status, output = git("check-ignore", "-v", ".env")
    if status != 0:
        return False, ".env is NOT ignored by git: one `git add -A` away from a leaked key"
    source = output.splitlines()[0].partition("\t")[0]
    return True, f"git ignores .env, by the rule at {source}"


def check_untracked() -> tuple[bool, str]:
    status, _ = git("ls-files", "--error-unmatch", ".env")
    if status == 0:
        return False, ".env is TRACKED: an ignore rule cannot reach a path git already holds"
    return True, ".env is not tracked by git"


def check_key() -> tuple[bool, str]:
    example, real = ROOT / ".env.example", ROOT / ".env"
    if not example.exists():
        return False, "no .env.example: nobody can learn which names this desk expects"
    if not real.exists():
        return False, "no .env: copy .env.example to .env and fill the value in"
    declared, filled = env_names(example), env_values(real)
    missing = [n for n in declared if not filled.get(n)]
    if missing:
        return False, f"empty in .env: {', '.join(missing)}"
    return True, f"{len(declared)} name(s) from .env.example set in .env, none printed here"


# TODO(me): a sixth check. A value left in .env.example is a secret published on purpose,
# and nothing above would notice.
# TODO(me): `check_key` accepts any non-empty value, including the words "your key here" typed
# straight from a tutorial. Decide what a value that is obviously not a key should do, and why
# this file must still never print it.
CHECKS = [
    ("interpreter", check_interpreter),
    ("repository", check_repository),
    ("ignore rule", check_ignored),
    ("secret untracked", check_untracked),
    ("key present", check_key),
]


def main() -> int:
    red = 0
    for name, run in CHECKS:
        ok, detail = run()
        red += not ok
        print(f"{'ok ' if ok else 'RED'}  {name:<17} {detail}")
    print("\nstock desk: ready" if not red else f"\nstock desk: {red} check(s) red")
    return 1 if red else 0


if __name__ == "__main__":
    sys.exit(main())
```

**Line by line:**

- `import platform, subprocess, sys` and `from pathlib import Path` — **the standard library and
  nothing else.** On day 0 there is no environment to install anything into, and a check that
  needed a package would need a check of its own. `platform.python_version()` is how a running
  interpreter says what version it is, from the inside.
- `ROOT = Path(__file__).resolve().parent` — **the folder this file is in**, not the folder the
  command was typed from. Every path below is relative to the project, so the check gives the same
  answer from any working directory.
- `git(*args)` — **one helper for every git question**, with `capture_output=True` so git's own
  chatter never reaches the screen, `text=True` so the answer is a string, and `check=False` so a
  non-zero exit is a *value* this file reads rather than an exception that ends it. The exit
  status is the answer to most of the questions below; the text is for the one that needs a
  source.
- `env_names` and `env_values` — **two readers for one file shape**, kept separate on purpose. The
  first is run on the committed example and returns names only. The second is run on the secret
  and returns values, which are compared and never printed. A single function returning both would
  be one refactor away from printing a key.
- `check_interpreter` — **the pin file's contents against the running interpreter.** Three
  outcomes and three sentences: no pin file at all — which is part 1.2's parent-folder trap
  arriving as a red line; a pin that does not match, with *both* versions in the message and the
  fix beside them; or a match. `running != pinned` is a string comparison, which is exactly right:
  `3.12.13` and `3.12.13` are the same interpreter and `3.12.13` and `3.12.12` are not.
- `check_repository` — **the question a first version of this file would not ask.** `git
  rev-parse --show-toplevel` prints the root of whatever repository governs this folder. A
  non-zero exit means there is none, and the message says the one command to run. A root that is
  not this folder means the nearest repository is somebody else's, and the message names it. Both
  of those states would let the next two checks print green while talking about the wrong
  repository, which is why this question is asked *before* them and not after.
- `Path(top).resolve() != ROOT` — **compared as paths, not as strings.** Git prints its answer
  with forward slashes on every operating system; `resolve()` normalises both sides, so the
  comparison is about the folder and not about how it was spelled.
- `check_ignored` and `output.splitlines()[0].partition("\t")[0]` — **the source of the rule,
  printed back.** Part 2.2's `-v` output is tab-separated; the first field is `file:line:pattern`,
  and that is what a person reads on the green line — `.gitignore:8:.env` — and what tells them
  if the rule came from a per-machine ignore source nobody else has.
- `check_untracked` and `--error-unmatch` — **the tracking question, exit status only.** Without
  the flag, `git ls-files .env` prints nothing and exits 0 whether or not the file is tracked; the
  flag makes "not tracked" a non-zero exit, which is what a check can read.
- `check_key` and `missing = [n for n in declared if not filled.get(n)]` — **names from the
  example, values from the secret, compared by presence.** The message on failure names the
  variable and not the value; the message on success says how many were set and *none printed
  here*, because the temptation to print the value "so you can see it worked" is the whole reason
  this line says that.
- **The two `TODO(me)` comments** — the check's own known gaps, written where the next reader will
  find them. The sixth check is part 2.3's failure; the second is a question about what "set"
  should mean, and it is deliberately a question, because the answer changes what this file must
  never do.
- `CHECKS` — **a list of pairs, in the order the questions should be read.** Interpreter first
  because everything else assumes it; repository before the two git questions that depend on it;
  the key last because it is the only one that depends on something the reader did by hand.
- `main()` and `red += not ok` — **count the red lines, print one verdict, return it.** `ok ` with
  a trailing space so the columns line up under `RED`; `{name:<17}` so the detail starts in the
  same column on every line. `sys.exit(main())` turns the count into the exit status, and that
  number is the only thing the next program that runs this will read.

- `1 name(s) from .env.example set in .env, none printed here` — **one name, present, unprinted.**

**Line by line:**

- `pinned 3.12.13, running 3.12.10` — **the bare name, from part 1.1, running the check.** Both
  numbers in the message, and the fix after the colon. This is the most common red line this
  check will ever print, and it is the one that costs nothing.
- **No repository: two red lines**, and the second one is the interesting one. With no repository,
  `git check-ignore` cannot answer, so `ignore rule` is red for a reason that has nothing to do
  with the rule — and `secret untracked` is *green*, because git is indeed not holding `.env`. Read
  without the `repository` line, that pair says "the rule is broken but the secret is safe", which
  is two wrong conclusions. The `repository` line above them is what says: none of the git answers
  below mean anything.
- `inside another repository rooted at .../outer` — **every git question here is being answered
  by `outer`**, and `outer` has this folder's `.gitignore` nowhere in its rules. The message names
  the root so the reader knows which repository would have received the first `git add`.

## When it breaks

Fold the two git questions about `.env` into one, which is what the first draft of every check
like this does:

```diff
-    ("ignore rule", check_ignored),
-    ("secret untracked", check_untracked),
+    ("secret safe", lambda: (check_ignored()[0] and check_untracked()[0], ".env is safe")),
```

It is green, and it is one line shorter. Then part 3.2 happens — `.env` force-added and committed —
and the line says `RED  secret safe  .env is safe`, or nothing useful at all, because the two
questions it merged fail *for different reasons with different fixes*: an ignore rule that never
applied, or a rule that applies to a path git already holds. One line and half the diagnosis. The
smallest fix is the two lines this file has, each with the sentence that says what to do, and the
rule is the one every check in this project keeps: **one question, one line, one fix in the
message.**

## In production

**What a senior writes instead.** The same five questions, run by the project's driver as its
first step on every `check` — which is exactly what day 1 of this project does — and a sixth and
seventh from the `TODO(me)` comments. Then the questions a warehouse system actually needs on
day 0 that this one cannot ask yet: that the ledger file has one writer, that a count has a
timestamp and an author, that the aisle map matches the bin list. Every one of those is a day of
this project, and every one arrives as a line in a check that can go red.

**What degrades at scale.** A close-down walk with five boxes takes a minute. A distribution
centre's close-down has two hundred, and the form that grew from five to two hundred by adding a
line each time something went wrong is a form nobody reads and everybody ticks. The check that
survives is the one where each line names a *fix*, not a fact — `run it with uv run`, `git init
here`, `copy .env.example to .env` — because a red line with a fix is an instruction and a red
line without one is a complaint.

**The review comment.** *"`check_key` says `1 name(s) set`. It would say that for
`GOOGLE_API_KEY=x`. Either that is fine and the docstring should say a non-empty value is all this
checks, or it is not and the second `TODO(me)` is the next change."*

**The interview question.** *"You have a setup document with nine steps. Turn it into something
that can fail. What do you check, what do you refuse to check, and how does the next program know
the answer?"*
