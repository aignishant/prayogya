## One-line answer

`SETUP.md` is every command from a bare machine to a green check, written as a listing rather than
a lesson, and it is only true once somebody has followed it in an empty folder and watched it go
green — which this part does, and which is the only reason the file can be committed.

## The idea

The company opens a second warehouse in another town. Same racking, same ledger, same close-down
walk — and nobody from the first site is going to be standing there on the Monday the doors open.
All that travels is a binder.

The first version of that binder is always written by someone who already knows. It says "set up
the goods-in terminal", which means seven things they do without thinking. It says "the usual
labels". It assumes a cage key that was cut years ago and lives on a hook the writer has never had
to describe. Every line is true and the binder does not work, and the way that is discovered is not
by reading it. It is by handing it to somebody who has never seen the first site and watching where
they stop.

`SETUP.md` is that binder for this project, and this part writes it and then does the handing-over.

The distinction that keeps it useful: **day 0 is the lesson and `SETUP.md` is the listing.** They
cover the same ground on purpose. The lesson explains why the ignore file is written before the
secret exists; the listing says write the ignore file, then the example, in that order. A reader
setting up this desk for the second time, on a new machine, does not want the reasoning again —
they want the commands, in order, with nothing missing. A reader setting it up for the first time
wants both, and the listing is what they will come back to.

One rule governs the whole file, and it is the one that is always broken first: **no step may be
"as you did before", and no step may assume a machine somebody else prepared.** Every command from
nothing. That is what makes it checkable, and being checkable is the only thing that keeps a setup
document from rotting. This project's listing has one line its author's first draft would not have
had — `git rev-parse --show-toplevel` after `git init` — because part 2.1's failure is a step a
stranger can get wrong without any error telling them, and a listing that does not ask the
question is a listing that assumes the answer.

## The mechanism

The whole file, at the root of the project:

````markdown
# Setup — bare machine to green check

Every command from a machine with nothing on it to `stock desk: ready`. Nothing here is assumed
and nothing here is optional. Day 0 is the lesson behind these commands; this file is the listing,
for a reader in a hurry or for the same reader on a new machine six months from now.

Commands are written for a POSIX shell (Git Bash on Windows, or any shell on macOS and Linux).
Where PowerShell differs, the PowerShell form is given underneath.

## 1 · The two tools this project needs

`uv` owns the interpreter and, from day 1, the environment. `git` owns the history.

```bash
uv --version
git --version
```

If `uv` is not installed, the install commands are at <https://docs.astral.sh/uv/getting-started/installation/>.
Whatever version you get, write it into `PACKAGES.md` with today's date. A version nobody wrote
down is a version nobody can reproduce.

## 2 · The folder, and the interpreter it runs on

```bash
mkdir warehouse-stock-control
cd warehouse-stock-control
uv python pin 3.12.13
cat .python-version
uv run python -V
```

Expect `.python-version` to hold `3.12.13`, and `uv run python -V` to print `Python 3.12.13`.
`uv` downloads that interpreter if the machine does not already have it — about twenty megabytes,
once.

`python -V` on its own may print something else entirely. That is not a problem to fix; it is the
reason this project pins.

## 3 · The repository

```bash
git init
git config user.name "your name"
git config user.email "you@example.com"
git rev-parse --show-toplevel
```

The last command must print this folder. If it prints a folder above it, you are inside somebody
else's repository, and `check.py` will say so.

If `git init` prints a hint about `master`, set the default once and re-run it in a fresh folder:

```bash
git config --global init.defaultBranch main
```

## 4 · The files day 0 writes, in this order

The full contents of each are printed by day 0. The order is not decoration — `.gitignore` is
written **before** `.env` exists, because an ignore rule speaks only about paths git has never
been told to hold.

| Order | File | What it is |
| --- | --- | --- |
| 1 | `PROJECT.md` | the brief: what this desk is, its tools, its cast, its boundary, its twenty days, and what "done" means |
| 2 | `PACKAGES.md` | every version this project depends on, with the date it was observed — including the three it has not installed yet |
| 3 | `.gitignore` | the paths git must never be told to hold, written before any of them exist |
| 4 | `.env.example` | the names the desk expects in its environment, with no values |
| 5 | `check.py` | the five questions this file's last section asks |

Commit as you go. One day, one commit is the habit; on day 0 the commits are smaller than that,
because `.gitignore` must land in the history before `.env` lands on disk.

## 5 · The key

The desk explains variances with a Gemini model on an AI Studio key.

1. Get a key at <https://aistudio.google.com/apikey>.
2. `cp .env.example .env` (PowerShell: `Copy-Item .env.example .env`).
3. Open `.env` and put the key after `GOOGLE_API_KEY=`.

Setting `GOOGLE_API_KEY` alone is what selects the AI Studio path. Nothing else goes in that file
yet. `.env` is ignored by `.gitignore`, has no place in any commit, and never leaves your machine.

What the free tier allows is not published as a number: AI Studio shows your own limits at
<https://aistudio.google.com/rate-limit>. Read them there rather than trusting a number written
down anywhere, including here.

## 6 · The green check

```bash
uv run python check.py
```

```text
ok   interpreter       interpreter 3.12.13, as pinned in .python-version
ok   repository        a repository, rooted here
ok   ignore rule       git ignores .env, by the rule at .gitignore:8:.env
ok   secret untracked  .env is not tracked by git
ok   key present       1 name(s) from .env.example set in .env, none printed here

stock desk: ready
```

Exit status 0 is the verdict; the lines are for you. If any line starts with `RED`, it names the
file or command to look at, and day 0 part 3.1 explains each of the five.
````

**Line by line:**

- **"Every command from a machine with nothing on it"** — the standard, in the first sentence, so
  that a reader who finds a step missing knows it is a bug in the file and not a thing they were
  supposed to know.
- **"Day 0 is the lesson behind these commands; this file is the listing"** — the relationship
  between the two documents, stated in the file, because a reader who has only this file needs to
  know where the reasoning is, and a reader who has only the lesson needs to know this exists.
- **Section 1 sends the reader to the tool's own install page and asks them to record the
  version** — not to install a particular version. The version that matters is the one they get,
  written down; the pin is on the interpreter, not on `uv`.
- **Section 2 pins `3.12.13` and says the download is expected** — a stranger who sees twenty
  megabytes downloading on a setup step will stop and wonder; the sentence saying it is once and
  it is normal is what keeps them going.
- **Section 3's `git rev-parse --show-toplevel`, and the sentence after it** — the one step this
  project's listing carries that a template listing would not. It costs a second, and it is the
  difference between a stranger who put the folder under their `projects/` repository finding out
  now and finding out when `check.py` says so — or, without that check, never.
- **Section 4's table, with an order column** — the order is the content. `.gitignore` is third,
  before `.env.example` and long before `.env`; a reader who does them alphabetically has done
  part 2.2 backwards, and the file says why that matters in one sentence.
- **"Commit as you go"** — with the reason: the ignore rule must be in the history before the
  secret is on disk. A listing that said "commit at the end" would be describing part 3.2.
- **Section 5, the key** — three numbered steps, the provider's own URL, the one variable name,
  and the sentence about limits not being published as a number, which is there so that nobody
  adds one later. `.env` "never leaves your machine" is the promise the rest of the day made good.
- **Section 6, the expected output** — five lines, verbatim from the run below, so a reader can
  diff their screen against the file. The last sentence points at the part that explains a red
  line, which is the one thing a listing may point to without becoming a lesson.

Now the handing-over. In a folder that has never held this project, with the file open and
nothing else:

```bash
cd /tmp && rm -rf stranger && mkdir stranger && cd stranger
```

Then sections 1 to 6, typed from the file. What they printed, on this machine, on the day:

```

```

ok   secret untracked  .env is not tracked by git

**Line by line:**

- `Pinned .python-version to 3.12.13` **without a `Downloading` line** — this machine already had
  the interpreter, from part 1.2's download an hour earlier. A stranger's machine would show the
  download here, and section 2 told them to expect it.
- `Initialized empty Git repository in .../stranger/warehouse-stock-control/.git/` and the
  toplevel line beneath it — **the same folder, twice.** The listing's new step answered, and the
  answer was the right one.
- **Five green lines, identical to section 6.** The listing was followed from nothing and reached
  the line it promised. That is the only test a setup document has, and this is the transcript
  that lets the file be committed: it was true on this date, on this machine, in an empty folder.
- **What this does not prove** is the production note: the machine had `uv` and `git` already,
  and it had the interpreter cached. A stranger with none of those would exercise section 1's link
  and section 2's download, which this run did not.

## When it breaks

Write the listing from memory instead of from the run — which is how the first draft of this file
was written, and how the step `git rev-parse --show-toplevel` came to be missing from it. Nothing
errors. The listing reads well. A stranger who happened to `mkdir warehouse-stock-control` inside a
folder that was already a repository follows every step, sees every command succeed, and reaches:

```
RED  repository        this folder is inside another repository rooted at C:/Users/nisha_gnzw/AppData/Local/Temp/p02/outer
stock desk: 1 check(s) red
```

— at step 6, with no idea which of the five preceding sections was wrong, because none of them
was. The listing was incomplete, and the check said so on the reader's machine rather than the
author's. The smallest fix is the line the file now has in section 3, and the discipline is this
part's: **a listing is written from a run, and a run in an empty folder, and the transcript of that
run is what gets pasted under section 6.** A setup document that has never been followed cold is a
guess about what a stranger needs.

## In production

**What a senior writes instead.** The same six sections, executed by a machine on every change:
the listing's commands extracted and run in a container with nothing in it, its output diffed
against section 6. That is day 19 of this project — the cold clone, run for real — and the reason
it can be automated then is that the listing was written as commands and not as advice now. The
other senior move is the one this file already makes and most do not: the *expected output* is in
the document, so "it worked" is a diff and not a feeling.

**What degrades at scale.** One warehouse, one binder. A company opening its fifth site has a
binder that was correct for the first, patched for the second, and read by nobody since — and the
fifth site's setup takes a week because the binder says "the usual labels" and the label printer
was replaced two sites ago. A listing rots at exactly the rate nobody follows it from nothing; the
cure is not a better writer but a rule that every site opens from the binder alone, and that
whoever finds the missing step fixes the binder before they fix the site.

**The review comment.** *"Section 6 shows five green lines. Paste the command that produced them
*and the folder it ran in*. A listing verified in the author's working copy has verified that the
author's working copy works."*

**The interview question.** *"You write setup instructions for a project you know well. How do
you find out what you left out, and what is the one thing you can do so that the next person does
not have to?"*
