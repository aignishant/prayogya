## One-line answer

Track `.env` once and the ignore rule stops applying to it entirely — two checks go red for two
different reasons, the fix is one command, and the key in the history stays readable forever, so
the real fix is to rotate it.

## The idea

The stock ledger is a bound book. Every count goes in as a line — bin, part, quantity, who counted,
when — and the pages are sewn in, on purpose: a ledger you can tear a page out of is not evidence of
anything, and a warehouse's ledger is the number the auditors, the insurers and the finance team all
believe.

One night a counter writes the cage's combination into the notes column, because the supervisor
read it out while they were writing and they wrote down everything the supervisor said. The mistake
is noticed at once. And the ledger does what it was built to do: nothing can be removed. The line is
struck through, a note is added beneath it, and the combination is still there, still legible under
one horizontal line, for as long as the book exists — and in the photocopy finance took that
morning.

A git history is that ledger. This is a feature: a repository whose past can be quietly edited
would be useless for the audit question this project answers on day 14, and for the far simpler
one — *what was the ledger software running in March* — from part 1.1. But it means a secret
committed once is a secret committed permanently, in every clone anyone ever made, and the correct
response is not to try to erase it. It is to make the secret worthless.

This part causes that on purpose, watches the check catch it, and then does both halves of the fix
— the one that stops it recurring, and the one that actually protects the key.

There is one mechanism here worth arriving at slowly, because almost everybody gets it wrong the
first time. **Ignore rules and tracking are not two names for the same thing.** An ignore rule is
git's answer to "should I mention this path to you?" — and it is only ever asked about paths git is
not already holding. Tracked wins, always, and silently. The rule text does not change, the
`.gitignore` file does not change, and yet the answer to "is `.env` ignored?" flips from yes to no
the moment the file is staged. Part 3.1 asked those as two questions for exactly this reason, and
this is the transcript where they answer differently.

## The mechanism

Force the file in, the way a hurried `git add -f` or an editor's "stage all" button would:

```bash
git add -f .env
git status --short
```

```
A  .env
```

**Line by line:**

- `git add -f .env` — `-f` is `--force`, and it exists precisely to override ignore rules. Without
  it, git refuses and tells you the path is ignored. With it, git does what you said. The rule was
  never a lock; it was an answer to a question, and `-f` stops asking.
- `A  .env` — staged as a new file. The path is now **tracked**: git is holding it for the next
  commit. Everything after this line follows from that one word.

Ask the two questions part 3.1 asks, by hand:

```bash
git check-ignore -v .env
echo "exit=$?"
git ls-files --error-unmatch .env
echo "exit=$?"
```

```
exit=1
.env
exit=0
```

**Line by line:**

- `git check-ignore -v .env` prints **nothing** and exits 1. In part 2.2 the same command on the
  same file in the same repository printed `.gitignore:8:.env	.env` and exited 0. Not one
  character of `.gitignore` has changed. The file is tracked, so git no longer considers it
  ignorable, and the ignore machinery has no opinion left to give.
- **Silence plus exit 1 is the answer.** In part 2.2 the same output — nothing, exit 1 — was the
  *right* answer for `.env.example`. Same two characters on the screen, opposite meaning, and the
  only way to tell them apart is to know which path was asked about. That is why the check reads
  the exit status and prints its own sentence, rather than showing you git's.
- `git ls-files --error-unmatch .env` prints the path and exits 0 — git is holding it.
  `--error-unmatch` is what makes the negative case a non-zero exit instead of empty output, which
  is the only reason `check_untracked` can be written in three lines.

Commit it, and run the check:

```bash
git commit -m "P02 day 0: add env"
uv run python check.py
echo "exit=$?"
```

```
[main af873e9] P02 day 0: add env
 1 file changed, 9 insertions(+)
 create mode 100644 .env

ok   interpreter       interpreter 3.12.13, as pinned in .python-version
ok   repository        a repository, rooted here
RED  ignore rule       .env is NOT ignored by git: one `git add -A` away from a leaked key
RED  secret untracked  .env is TRACKED: an ignore rule cannot reach a path git already holds
ok   key present       1 name(s) from .env.example set in .env, none printed here

stock desk: 2 check(s) red
exit=1
```

**Line by line:**

- `1 file changed, 9 insertions(+)` — nine lines, one of which is the key. The commit message says
  nothing about a secret, which is exactly how this survives review.
- **Two checks go red, and they are the two that ask about different things.** The `ignore rule`
  check is red because `check-ignore` now exits 1. The `secret untracked` check is red because
  `ls-files` now exits 0. Written as one check — part 3.1's failure — this would have produced one
  line and half the diagnosis.
- **The interpreter, repository and key checks are still green**, and that is the right behaviour:
  they were not affected, and a check that fails everything when one thing is wrong tells you
  nothing about where to look. The `repository` line in particular is green *and correct*: this is
  this folder's repository, holding a file it should not.

The first half of the fix — stop tracking, without deleting the file on disk:

```bash
git rm --cached .env
git status --short
git commit -m "P02 day 0: stop tracking .env"
uv run python check.py
echo "exit=$?"
```

```
rm '.env'
D  .env
[main effeb5d] P02 day 0: stop tracking .env
 1 file changed, 9 deletions(-)
 delete mode 100644 .env

ok   interpreter       interpreter 3.12.13, as pinned in .python-version
ok   repository        a repository, rooted here
ok   ignore rule       git ignores .env, by the rule at .gitignore:8:.env
ok   secret untracked  .env is not tracked by git
ok   key present       1 name(s) from .env.example set in .env, none printed here

stock desk: ready
exit=0
```

**Line by line:**

- `git rm --cached .env` — **`--cached` removes the path from the staging area and leaves the
  file on disk.** Without the flag, `git rm` deletes the file too, and the key with it. The
  printed `rm '.env'` is git describing what it did to the index, not to the folder; `.env` is
  still there, and `key present` is green to prove it.
- `D  .env` — staged as a deletion. The next commit records that git stopped holding the path.
- **Both red lines go green at once**, because both were consequences of one word — tracked — and
  that word is no longer true. The rule on line 8 is consulted again, and answers.
- `key present` **stayed green throughout** — the file never left the disk. That is the whole
  point of `--cached`.

And the second half, which no command in this project can do. The key is still in the history:

```bash
git show HEAD~1:.env | tail -1
git log --oneline | head -3
```

```
GOOGLE_API_KEY=not-a-real-key
effeb5d P02 day 0: stop tracking .env
af873e9 P02 day 0: add env
67ff3fb P02 day 0: the check, and the listing
```

**Line by line:**

- `git show HEAD~1:.env` — **the file as it was one commit ago**, printed in full from the history,
  with the value on its last line. The commit that stopped tracking it did not remove it from the
  commit that added it; a commit is a snapshot, and snapshots do not edit each other.
- **Every clone made between `af873e9` and `effeb5d` has this line**, and so does every clone made
  after, because the history travels whole. The value shown here is a placeholder this transcript
  used on purpose. Had it been real, the only fix left is the one outside the repository: **rotate
  the key** — revoke this one at the provider, issue a new one, put the new one in `.env`. The old
  one is in the ledger under a horizontal line, and the ledger is what it is for.

## When it breaks

This part *is* the failure, caused on purpose. The version of it nobody causes on purpose is the
one where the two red lines never appear, because the check was written as one line — part 3.1's
`When it breaks` — or because the check was never run before the push. Then the sequence is: an
editor's "stage all", a commit message about something else, a push, and a notification from the
provider three days later that a key was found in a public repository and has been revoked. The
smallest fix is the one this part practises: run the check, read two red lines, `git rm --cached`,
and then rotate — in that order, and the last step is not optional whatever the first three found.

## In production

**What a senior writes instead.** A pre-commit hook that refuses to stage anything the ignore
rules cover *and* anything whose contents look like a credential, so that `-f` and "stage all" are
stopped at the door rather than caught at the check; a secret scanner on the remote that rejects
the push; and a rotation runbook that is one command, because the moment this happens for real the
person holding the keyboard is not calm. History rewriting — `filter-repo` and its relatives — is
the tool people reach for and the senior refuses: it rewrites *this* copy, every other clone keeps
the line, and it teaches the team that a leak can be undone.

**What degrades at scale.** One key, one repository, one afternoon. A distribution centre's stock
system has four credentials, forty clones across the company, and a build server that keeps every
commit it ever built. A key that lands in the history is in forty-one places within the hour, and
the rotation is not one key but every credential the leaked one could reach — the carrier's API
that the goods-in key was also used for, because somebody reused it. The cage combination written
in the ledger is the cost of one cage; the cost of the master key is every cage.

**The review comment.** *"This pull request removes `.env` with `git rm --cached` and adds it to
`.gitignore`. Good. Which commit added it, what key was in it, and has that key been revoked? The
review is not done until the answer to the third is yes."*

**The interview question.** *"A secret was committed and pushed an hour ago. Walk me through what
you do, in order, and tell me which step people skip."*
