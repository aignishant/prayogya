## One-line answer

A folder of scripts is a folder; a package is a folder with a declared name that every import in
the project starts with — and the two lines that make `stock_desk` a package are the two files this
part prints, each of which is only a docstring saying what lives under that name.

## The idea

The kit bag has compartments, and the compartments are labelled. Scanner in the front pocket,
labels in the side, count sheets in the sleeve. A counter who has never used this bag can find the
radio because the label says radio, and a supervisor auditing forty bags can check each one the
same way. A bag with the same contents loose in the bottom is the same kit and a worse one.

A Python project is that bag. The compartments are **packages** — folders that Python treats as a
unit with a name — and the label on each is a file called `__init__.py`. Its presence is what turns
`stock_desk/` from a folder that happens to contain Python into the name `stock_desk`, which every
import in this project begins with: `from stock_desk.util import keys`, `from stock_desk import
models`. Nothing is imported by relative path, nothing by a bare file name, and so nothing depends
on which folder a command was typed in.

The file can be empty. In this project it is not, and the reason is the label: the docstring at
the top of each `__init__.py` says what lives under that name and what does not. `stock_desk` says
the ledger is not opened from here — it will sit behind a second package, `stock_mcp`, which is
named today and built on day 3, because the boundary between the desk and the ledger is the whole
project and the name of that boundary belongs in the first file a reader opens. `stock_desk.util`
says what the kit is: four modules, four promises, and no opinion about stock.

There is one thing a package does not do, and this part's failure is it. A package is findable by
name only from somewhere Python has been told to look. From the project root, under `uv run`, the
root is on the path and the name resolves. From anywhere else it does not, and the error names the
package as if it did not exist — which, from where you are standing, it does not.

## The mechanism

The whole file, at `stock_desk/__init__.py`:

```python
"""Warehouse Stock Control — the desk that reconciles counted stock against the ledger.

Everything the desk is lives under this name. `stock_desk.util` is the kit the rest is built with;
`stock_desk.models` is the only place a model is named. The ledger itself is never opened from
here: from day 3 it sits behind `stock_mcp`, which is the one writer.
"""
```

**Line by line:**

- **A docstring and nothing else.** The file's presence makes the folder a package; its contents
  are the label. Code that ran here would run on every `import stock_desk`, which is every test
  and every command, and a package whose import has side effects is a package nobody can import
  safely.
- **"Everything the desk is lives under this name"** — the promise the rest of the project keeps:
  no module outside `stock_desk` except the boundary and the tests.
- **"`stock_desk.models` is the only place a model is named"** — part 3.1's rule, stated where a
  reader looks first. A model ID anywhere else in the tree is a bug, and this sentence is what
  makes it one.
- **"from day 3 it sits behind `stock_mcp`, which is the one writer"** — the second package,
  named two days before it exists. The ledger has one writer; that sentence is the project's brief
  in six words, and it belongs on the label of the package that is *not* the writer.

The whole file, at `stock_desk/util/__init__.py`:

```python
"""The kit: four modules, four promises, no opinions about stock.

- `keys` — a secret reaches the desk from the environment and reaches a log only as a fingerprint.
- `logging` — one JSON object per line, with secret-looking fields replaced by name.
- `backoff` — a retry waits what it was told to wait, and escalates rather than inventing a count.
- `budget` — a ceiling on model calls that refuses instead of overspending.

Nothing here knows what a bin or a variance is. That is the point: a helper that knew would be
rewritten the day the domain moved, and the day the domain moves is every other day.
"""
```

**Line by line:**

- **Four lines, four modules, one promise each** — the index of section 2. A reader who opens
  this file knows what the kit holds before opening any of it, and a module added to `util/`
  without a line here is a compartment with no label.
- **"no opinions about stock"** — the rule that keeps the kit reusable across the desk. `backoff`
  does not know it is retrying a bin read; `budget` does not know the four names it will count.
  The day the domain changes, the kit does not.
- **`logging`, as a module name** — it shadows nothing, because it lives under `stock_desk.util`
  and is imported as `stock_desk.util.logging`, but a test that wants both this and the standard
  library's module of the same name imports this one under another name. Part 3.2 does exactly
  that.

Prove the name resolves, from the project root, under the pinned interpreter:

```bash
uv run python -c "import stock_desk, stock_desk.util; print(stock_desk.__file__); print(stock_desk.util.__doc__.splitlines()[0])"
```

**Line by line:**

- `stock_desk.__file__` — **the label's own path.** The package resolved to *this* folder's
  `__init__.py`, which is the fact the next part's driver depends on: every command it runs
  imports the desk by name, from the root, and gets this file.
- `stock_desk.util.__doc__.splitlines()[0]` — **the first line of the kit's label, read back
  through the import.** A docstring is data; this is the cheapest proof that the package Python
  found is the one on disk.

## When it breaks

Ask for the package from somewhere that is not the project root:

```bash
cd ..
uv run --project warehouse-stock-control python -c "import stock_desk"
```

```
Traceback (most recent call last):
  File "<string>", line 1, in <module>
ModuleNotFoundError: No module named 'stock_desk'
```

The environment is the right one — `--project` pointed the tool at it — and the interpreter is the
pinned one, and the package is not found, because the folder that contains `stock_desk/` is not on
the import path. Python looks in the current directory and in the environment's installed
packages, and this project is neither: `package = false` in part 1.1 means it is never installed,
and the current directory is one level up. Somebody who wrote a script in a `scripts/` folder, or
ran a test from inside `tests/`, meets exactly this line and reads it as a missing install.

The smallest fix is to run from the root, which is why every command in this project's driver
does — and why `pyproject.toml` carries `pythonpath = ["."]` for the test runner, which would
otherwise meet the same error from inside `tests/`. The rule is the one the label states: every
import starts with the package name, and the package name is found from one place.

## In production

**What a senior writes instead.** A `src/` layout with the package installed into the environment
in editable form, so that the name resolves from any directory and `pythonpath = ["."]` is not
needed — at the cost of `package = false` becoming a build system, a `[build-system]` table and a
wheel nobody ships. For a desk that runs from its own folder and ships as a container that copies
that folder, the flat layout is honest and the editable install is a second thing to explain.

**What degrades at scale.** A warehouse's software is one package until the day two teams share
the repository: stock control and goods-in both want a `util`, both want a `models`, and the
first collision is an import that silently picks the wrong one. Forty modules under one name is
fine; two top-level names that both contain a `util` is the day the labels stop helping. The
boundary package this project names today is that split done on purpose, on day 3, with a process
line between the two names rather than a shared folder.

**The review comment.** *"`from util import keys` — that works from the root and from nowhere
else, and it resolves to a different `util` the day another package has one. Import from
`stock_desk.util`, always."*

**The interview question.** *"What makes a folder a package, what does the file that makes it one
do at import time, and why does your project's test runner need a `pythonpath` setting?"*
