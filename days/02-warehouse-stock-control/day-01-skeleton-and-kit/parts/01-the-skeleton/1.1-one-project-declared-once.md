## One-line answer

`pyproject.toml` is where this desk states its name, the exact Python it runs on and the exact
versions of everything it installs — and `uv.lock` is the receipt for what that produced — so that
"it works here" becomes a fact a second machine can reproduce rather than a claim.

## The idea

Every counter on the night shift is handed the same kit at the goods-in desk: a scanner, a roll of
labels, a pad of count sheets, a radio. Standard issue, signed out against a name. That is not a
courtesy. It is what lets the supervisor say, when two counters report different quantities for
bin C-07-2, that the difference is about the shelf — because it cannot be about the scanner.

Now imagine the kit is not standard issue. Each counter brings whatever scanner was in the drawer,
with whatever firmware it had when it was last used. The counts still look like counts. They go
into the ledger with the same confidence, and somewhere down the line a replenishment is raised on
a number that was never comparable to anything.

Software has exactly this kit, and it is a file. `pyproject.toml` is where a project writes down
what it is and what it needs — its name, the interpreter it runs on, and every package it installs,
at an exact version. Day 0 pinned the interpreter in `.python-version`, which decides *which
Python*. This file decides everything else, and it does it for every machine that ever clones this
desk.

Two terms, because the difference between them is what this part is about:

- A **floor** is a requirement written as `>=`, which says what is too old and leaves the choice
  of what to install to whoever resolves it, on the day they resolve it.
- A **pin** is a requirement written as `==`, which leaves no choice. The version in the file is
  the version installed, everywhere, until the file changes.

A floor is a note in the drawer saying "any scanner newer than the grey ones". A pin is a serial
number on the sign-out sheet.

There is one more file in this part that nobody types: `uv.lock`. It is written by the tool when it
resolves the project — every package, every version, every hash of what it downloaded — and it is
committed, because it is the receipt for the kit that was actually issued. The pin says what was
asked for; the lock says what was got. The two agree today, and the failure at the end of this part
is what the tool does the morning they do not.

## The mechanism

The whole file, at `pyproject.toml`:

```toml
[project]
name = "warehouse-stock-control"
version = "0.1.0"
description = "A stock-control desk: reconcile cycle counts against the ledger, explain each variance, replenish only what no explanation covers."
requires-python = "==3.12.*"
dependencies = []

[dependency-groups]
dev = [
    "ruff==0.16.7",
    "pytest==9.1.1",
]

[tool.uv]
package = false

[tool.ruff]
line-length = 100
target-version = "py312"

[tool.ruff.lint]
select = ["E", "F", "I", "B", "UP", "SIM"]

[tool.pytest.ini_options]
testpaths = ["tests"]
pythonpath = ["."]
```

**Line by line:**

- `[project]` and `name = "warehouse-stock-control"` — **the project's own name, the same as its
  folder.** Nothing imports this name; it is what the tool calls the environment it builds, and
  what a lockfile says it was built for.
- `requires-python = "==3.12.*"` — **the interpreter, as a constraint on the whole 3.12 line.**
  Day 0's pin file says exactly `3.12.13`; this line says the project refuses anything that is not
  a 3.12. The two agree by design: the pin file chooses, and this line is what makes a resolver
  refuse a machine whose pin file was lost.
- `dependencies = []` — **nothing, today, on purpose.** The desk has no code yet that needs a
  package. The framework that will run its agents was observed at 2.9.0 on day 0 and recorded in
  `PACKAGES.md` as *observed, not installed*; it arrives the day the first agent needs it, with its
  release notes read that morning, and not before. An empty list here is a statement, not an
  omission.
- `[dependency-groups]` and `dev = [...]` — **the tools a developer runs, kept apart from what the
  desk needs to run.** A group is installed on this machine and in the pipeline, and left out of
  the image that ships. Two entries, both pins.
- `"ruff==0.16.7"` — **the linter, at the version the registry called latest on the day.** Not
  `>=0.16`, which would let two machines lint with two rulesets and disagree about the same line.
- `"pytest==9.1.1"` — **the test runner, pinned the same way.** The kit is standard issue or it is
  not.
- `[tool.uv]` and `package = false` — **this project is a folder of modules, not a distribution.**
  Nothing here is built into a wheel or installed under its own name; the tool creates the
  environment, and the code runs from the folder. The line stops the tool trying to build a
  package out of a project that has no build.
- `[tool.ruff]`, `line-length = 100`, `target-version = "py312"` — **the ruler and the language
  level.** A hundred columns because the code blocks in this project's own days are read on a
  screen; `py312` so the linter's suggestions match the interpreter that will actually run them.
- `select = ["E", "F", "I", "B", "UP", "SIM"]` — **six families of rules, named.** Errors and
  pyflakes for what will not run; import ordering so two files never disagree about it;
  bugbear for the mistakes that run and are wrong; pyupgrade so the code is written for the
  version it pins; simplify for the branches that do not need to exist. The list is short so
  that a rule firing is worth reading.
- `[tool.pytest.ini_options]`, `testpaths = ["tests"]`, `pythonpath = ["."]` — **where the tests
  are, and how they import the desk.** The second line puts the project root on the import path
  for the test runner, which is why `from stock_desk import ...` works inside a test without the
  project being installed. Part 1.2's failure is what happens without it.

Then the environment, built from the file. Everything below is run from the project root:

```bash
uv sync
uv run ruff --version
uv run pytest --version
```

```

         If the cache and target directories are on different filesystems, hardlinking may not be supported.

 + ruff==0.16.7

```

**Line by line:**

- `Using CPython 3.12.13` — **day 0's pin, read first.** The tool found the pin file and chose the
  interpreter before it resolved a single package.
- `Creating virtual environment at: .venv` — **the environment, in the folder, ignored by git.**
  Day 0's `.gitignore` has `.venv/` on line 17, written before this directory existed; it is
  rebuilt from the lockfile on every other machine and never copied.
- `Resolved 8 packages in 1ms` — **eight, from two pins.** Two named, five that those two need,
  and the project itself. The resolution is what `uv.lock` records, and it took a millisecond
  because nothing had to be decided.
- `warning: Failed to hardlink files; falling back to full copy.` — **the tool preferred to link
  files from its cache and this filesystem would not let it.** It says so, it says what to set to
  make the warning go away, and it carries on. Three lines of warning and no error; read them
  once so the next time you see `UV_LINK_MODE` you know it is about disk, not about the desk.
- `Installed 7 packages in 669ms` and the seven `+` lines — **the kit, itemised.** `ruff` and
  `pytest` are the two that were asked for; `colorama`, `iniconfig`, `packaging`, `pluggy` and
  `pygments` are what pytest brings with it. Every one is in the lockfile at exactly this version.
- `ruff 0.16.7` and `pytest 9.1.1` — **read back, through `uv run`.** The versions that will
  lint and test this desk on this machine, and — because the lockfile is committed — on every
  other.

And the record. **A marked diff against `PACKAGES.md` as printed on day 0 part 1.1**, two rows
appended:

```diff
 | MCP protocol revision | 2026-07-28 | 2026-09-12 | 0 | `https://modelcontextprotocol.io/docs/learn/versioning` — "The **current** protocol version is 2026-07-28." A fact about the world, recorded because every boundary day of this project depends on it. |
+| ruff | 0.16.7 | 2026-09-12 | 1 | `uv run ruff --version`, after `uv sync`. The linter in the `dev` group; 0.16.7 was the registry's latest on the day. |
+| pytest | 9.1.1 | 2026-09-12 | 1 | `uv run pytest --version`, after `uv sync`. The test runner in the `dev` group. |
```

**Line by line:**

- **Two rows, both observed through `uv run`** — the version the environment holds, not the
  version the file asked for. They agree today; a row that quoted the file would be a copy of a
  copy.
- **`ruff`'s row says why 0.16.7** — it was the newest on the registry when the project's day 1
  was written. A pin that was the latest on its date is a pin somebody can date.

## When it breaks

Move a pin without moving the lock, which is what happens the morning somebody edits
`pyproject.toml` by hand and forgets the tool has a receipt:

```bash
sed -i 's/"ruff==0.16.7"/"ruff==0.16.6"/' pyproject.toml
uv sync --locked
echo "exit=$?"
```

```
Resolved 8 packages in 12ms
error: The lockfile at `uv.lock` needs to be updated, but `--locked` was provided.

hint: To update the lockfile, run `uv lock`.
exit=1
```

The pin says one thing and the receipt says another, and `--locked` refuses to choose. That refusal
is the whole value of the flag: without it, `uv sync` quietly rewrites the lockfile to match the
new pin and installs whatever it resolved, and the environment on this machine stops matching the
one every other clone has. The fix the hint names — `uv lock` — is the right one for the person
who changed the pin on purpose:

```bash
uv lock
git diff --stat uv.lock
```

```
Resolved 8 packages in 7ms
Updated ruff v0.16.7 -> v0.16.6
 uv.lock | 40 ++++++++++++++++++++--------------------
 1 file changed, 20 insertions(+), 20 deletions(-)
```

Forty lines of receipt for one version number: the package's version, its download URL and its
hash, for two platforms. That diff is what gets committed *with* the pin change, in the same
commit, so the history never holds a `pyproject.toml` that asks for something the lockfile did not
get. The smallest fix is to run `uv lock` after every edit to a pin, and the habit is to run `uv
sync --locked` — never bare `uv sync` — in any place that must not decide for itself.

## In production

**What a senior writes instead.** The same file, with `uv sync --locked` as the only form of the
command anywhere a machine runs it — the pipeline, the image, the setup listing — and a bot that
opens a pull request when a pin's registry version moves, so that upgrading is a diff somebody
reviews rather than a `>=` somebody forgot they wrote. And a `[dependency-groups]` entry per
purpose — `dev` today, an `eval` group the day a judge is installed — so that the image ships only
what runs.

**What degrades at scale.** A stock-control system at a regional distribution centre has a scanner
firmware, a label-printer driver, a carrier's client library and a model SDK, each with its own
release cadence, on forty machines across three shifts. One floor in that list is a machine that
resolves differently on a Tuesday, and the count it reports is the one the ledger keeps. The lock
is what makes forty machines one machine; the pin is what makes the next version a decision.

**The review comment.** *"`ruff>=0.16` — which 0.16? Pin it, run `uv lock`, and commit both files
in this change so the lockfile diff is in the review."*

**The interview question.** *"What is the difference between a pin and a lockfile, and what goes
wrong if a project has only one of them?"*

## Check yourself

- **Run:** `uv sync --locked` in a clean state — expect `Resolved 8 packages` and no `Installed`
  line, because the environment already matches the receipt.
- **Run:** `git ls-files uv.lock` — the receipt is tracked, and say what a clone would do without
  it.
- **Say out loud:** which line of this file decides *which Python*, which decides *what else*, and
  which file decides what was actually got?
