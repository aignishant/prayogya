## One-line answer

`./run` is the one file that knows every command this project has and every command it will have
— each one run through the pinned interpreter and the locked environment — so that "how do I run
this" is answered by reading one file, and "what is not built yet" is answered by the same file
saying which day builds it.

## The idea

At the goods-in desk there is one sign-out sheet. Every kit goes out against it and comes back
against it. A counter who wants a scanner does not go to the drawer; they go to the sheet, and the
sheet says what is available, what is out, and — for the label printer that has been on order since
March — what does not exist yet and when it will. One sheet, one place to look, and a supervisor
who can see the whole floor's equipment by reading it.

`run` is that sheet. It is a Python script at the root of the project with two tables in it: the
commands that exist, each as the exact list of words to execute, and the commands that will exist,
each with the day of this project that builds it. Every command goes through `uv run`, which means
it runs on day 0's interpreter inside part 1.1's environment whatever `python` happens to mean in
the shell that typed it. And it is a Python script rather than a shell script because the machine
this desk was written on runs three shells and agrees with none of them about quoting.

Three things the sheet does that a `README` of commands cannot. It **fails on the first red step**
— `check` is lint, then tests, then day 0's five questions, and a red lint does not run the tests.
It **refuses a command that is not built yet by name** rather than by absence, so that `./run mcp`
today prints the day that builds it instead of `command not found`. And it **says when a program
is missing** in one line — the compose command on day 19 needs a tool this machine does not have,
and a driver that reports that as a traceback through the interpreter's own subprocess module is a
driver that sends the reader to the wrong file.

The one thing a Python driver needs that a shell script does not is permission to be run as
`./run`. That is a bit git stores, and on this machine it had to be set by hand.

## The mechanism

The whole file, at `run`:

```python
#!/usr/bin/env python3
"""The one door into the stock desk.

Every command this project has is here, so a command is found by reading one file rather than by
remembering. Each one runs through `uv run`, which means the work always happens on the
interpreter pinned in `.python-version` and in the environment locked in `uv.lock`, whatever
Python you happened to launch this script with.

    ./run check          lint, tests, and the setup check, in that order
    ./run lint           ruff, on everything
    ./run test           pytest
    ./run setup          the day-0 machine check

On Windows PowerShell, where `./run` is not executable, the same commands are
`python run check`, `python run lint`, and so on.
"""

from __future__ import annotations

import subprocess
import sys
from pathlib import Path

ROOT = Path(__file__).resolve().parent

#: Commands that exist. Each is a list of argv lists, run in order, stopping at the first failure.
COMMANDS: dict[str, list[list[str]]] = {
    "lint": [["uv", "run", "ruff", "check", "."]],
    "test": [["uv", "run", "pytest", "-q"]],
    "setup": [["uv", "run", "python", "check.py"]],
}
COMMANDS["check"] = COMMANDS["lint"] + COMMANDS["test"] + COMMANDS["setup"]

#: Commands the project will have, and the day of this project that builds each one. Naming them
#: here rather than leaving them absent means `./run` is the map of the whole desk from day 1.
PLANNED: dict[str, str] = {
    "mcp": "day 3, the boundary that owns the ledger",
    "count": "day 7, the desk over the whole cycle count",
    "eval": "day 18, the evalset and the gate that goes red",
    "serve": "day 19, the container and its health endpoint",
    "up": "day 19, compose, with the boundary beside the desk",
}


def run(argv: list[str]) -> int:
    """Run one command in the project root, letting its output through to the terminal."""
    print(f"--- {' '.join(argv)}", flush=True)
    try:
        return subprocess.call(argv, cwd=ROOT)
    except FileNotFoundError:
        # The command's first word is a program this machine does not have. Say which, in one
        # line, instead of a traceback that names a file inside Python's own subprocess module.
        print(f"{argv[0]} is not installed on this machine", file=sys.stderr)
        return 127


def usage() -> int:
    print(__doc__.strip().splitlines()[0])
    print("\ncommands:")
    for name in COMMANDS:
        print(f"  {name}")
    for name, when in PLANNED.items():
        print(f"  {name:<8} not built yet: {when}")
    return 2


def main(argv: list[str]) -> int:
    if not argv or argv[0] in {"-h", "--help", "help"}:
        return usage()
    command = argv[0]
    if command in PLANNED:
        print(f"'{command}' is not built yet: {PLANNED[command]}", file=sys.stderr)
        return 2
    if command not in COMMANDS:
        print(f"no such command: {command}", file=sys.stderr)
        return usage()
    for step in COMMANDS[command]:
        status = run(step)
        if status != 0:
            print(f"\nFAIL {command}: `{' '.join(step)}` exited {status}", file=sys.stderr)
            return status
    print(f"\nOK {command}")
    return 0


if __name__ == "__main__":
    sys.exit(main(sys.argv[1:]))
```

**Line by line:**

- `#!/usr/bin/env python3` — **the interpreter line for `./run`**, read by the shell and not by
  Python. It names whatever `python3` the machine finds first — which is exactly the accident day
  0 was about — and that is fine here, because this script's only job is to call `uv run`, which
  then chooses the pinned one. The driver may run on any Python; the desk runs on one.
- **The docstring's table** — the commands that exist, one line each, and the PowerShell form. It
  is the first thing `usage()` prints and the first thing a reader sees, so it is kept true by
  hand every time a command is added.
- `ROOT = Path(__file__).resolve().parent` and `cwd=ROOT` — **every command runs in the project
  root**, wherever the driver was invoked from. Part 1.2's failure is what a command run from the
  wrong folder meets; this line is why the driver never does.
- `COMMANDS` — **a dictionary of names to lists of argv lists.** Each command is one or more
  processes, each given as the exact words, never as a shell string. No shell means no quoting
  rules, and no quoting rules means the same file works under three shells.
- `["uv", "run", "ruff", "check", "."]` — **the linter, through `uv run`.** Every entry starts with
  those two words. That is the whole mechanism by which the driver keeps the desk on its pinned
  interpreter and its locked packages.
- `COMMANDS["check"] = COMMANDS["lint"] + COMMANDS["test"] + COMMANDS["setup"]` — **the gate, as a
  concatenation.** Lint first because it is fastest and fails on a typo; tests second; day 0's
  five questions last, so that a red machine check is not what stops the tests from running.
- `PLANNED` — **the sheet's second table.** Five names, five days. `count` is day 7, when the desk
  first runs over a whole cycle count; `mcp` is day 3, the boundary. Each entry is deleted on the
  day it becomes real, so this table shrinks to nothing by day 19.
- `run(argv)` and `print(f"--- {' '.join(argv)}")` — **every step announces itself** before
  running, so a red step in `check` is identifiable by the line above the error.
- `subprocess.call(argv, cwd=ROOT)` — **the child's exit status is the return value**, and it is
  what `main` reads. Output is not captured; it goes straight to the terminal, because the driver
  has nothing to add to what ruff or pytest print.
- `except FileNotFoundError:` and `return 127` — **a program this machine does not have.** The
  interpreter raises this from deep inside its own subprocess module, naming no program; the
  driver catches it, names the first word of the command, and returns the shell's own number for
  *command not found*. The transcript below is the difference.
- `usage()` returning `2` — **help is not success.** A script that prints its usage and exits 0
  is a script a pipeline reads as passing.
- `if command in PLANNED:` before `if command not in COMMANDS:` — **the planned table is checked
  first**, so a planned command gets its own sentence and not the generic one.
- `for step in COMMANDS[command]: ... if status != 0: ... return status` — **stop at the first
  red step and hand its status back.** `FAIL check` names the exact command that failed and its
  exit code; the reader looks at the lines above it.

**Line by line:**

- **The usage listing is the whole map** — four commands that exist, five that will, and the day
  each arrives. Exit status 2, because nothing was done. The planned command prints its day and
  exits 2 as well.
- `--- uv run ruff check .` — **each step announced**, then its own output. `All checks passed!`
  is ruff's; `17 passed` is pytest's; the five `ok` lines are day 0's check running under the
  driver for the first time.
- `OK check` — **the driver's one line.** Exit status 0, and only because all three steps
  returned it.

Then the program that is missing. On this machine there is no `docker`; add a command that needs
it and run it:

```bash
python run docker
```

```
--- docker --version
docker is not installed on this machine

FAIL docker: `docker --version` exited 127
```

**Line by line:**

- `docker is not installed on this machine` — **one line, naming the program.** The command was
  announced, the interpreter raised, the driver said which word could not be found.
- `exited 127` — **the number a shell uses for the same thing.** A script wrapping the driver reads
  this the way it reads any missing command.

And the bit. `run` has no extension, so nothing tells the shell it is a script except the first
line and a permission git has to be told to record:

```bash
git update-index --chmod=+x run
git ls-files -s run
```

```
100755 0d929d808811c9f457601e50200e6adb164ecb0f 0	run
```

**Line by line:**

- `--chmod=+x` — **sets the executable bit in git's index**, whatever the working copy's
  permissions say. On this machine the working copy already had it; the index is what a clone
  receives, and a clone that receives `100644` gets a `./run` that says *permission denied*.
- `100755` — **the mode git will hand to every clone.** The six digits after it are the blob's
  hash; the `0` is the stage. The mode is the only part of this line a person needs to read.

## When it breaks

Take the `try` out, which is what the first draft of every driver like this looks like:

```diff
     print(f"--- {' '.join(argv)}", flush=True)
-    try:
-        return subprocess.call(argv, cwd=ROOT)
-    except FileNotFoundError:
-        # The command's first word is a program this machine does not have. Say which, in one
-        # line, instead of a traceback that names a file inside Python's own subprocess module.
-        print(f"{argv[0]} is not installed on this machine", file=sys.stderr)
-        return 127
+    return subprocess.call(argv, cwd=ROOT)
```

```
    self._execute_child(args, executable, preexec_fn, close_fds,
  File "C:\Users\nisha_gnzw\AppData\Local\Programs\Python\Python312\Lib\subprocess.py", line 1538, in _execute_child
    hp, ht, pid, tid = _winapi.CreateProcess(executable, args,
                       ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
FileNotFoundError: [WinError 2] The system cannot find the file specified
```

The traceback names `subprocess.py` twice and `_winapi.CreateProcess` once, and never names
`docker`. A reader who has not seen this before opens the interpreter's own library looking for a
missing file, and the file that is missing is a program that was never installed. The smallest fix
is the seven lines above: catch the one exception the interpreter raises for this, print the first
word of the command, and return the number a shell would.

## In production

**What a senior writes instead.** The same file, with two more things the first version does not
need: a `--dry-run` that prints each step without running it, so the map can be read by a machine;
and every step's exit status and duration written as one JSON line to the same logger section 2
builds, so `./run check` in a pipeline leaves a record of which step went red and not only that
one did. The driver stays a script in the repository and not a task-runner installed on the
machine, because a task-runner is one more version to pin.

**What degrades at scale.** A warehouse's software has a handful of commands until the day it has
sixty: one per report, one per import, one per printer. A driver whose `COMMANDS` table is sixty
lines is still readable; sixty scripts in a `bin/` folder, half of which assume a folder somebody
had, are not. The table is what keeps the sixty findable, and the `PLANNED` table is what stops the
sixty-first from being written as "the usual way".

**The review comment.** *"`./run check` runs pytest before ruff. Swap them: the lint takes a
second and fails on a typo, and nobody wants to wait for the tests to find out their import order
was wrong."*

**The interview question.** *"Your project has a `run` script. What does it guarantee about the
interpreter, what happens when I ask it for something that does not exist yet, and how does a
clone on another operating system get to execute it?"*
