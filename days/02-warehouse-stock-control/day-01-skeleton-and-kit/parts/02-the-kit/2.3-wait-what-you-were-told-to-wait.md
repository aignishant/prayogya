## One-line answer

A retry that is told how long to wait waits exactly that long, a retry that is told nothing waits
one, two, four, and a retry that runs out of attempts raises the last failure to its caller —
because the one thing a stock desk must never do when the ledger is busy is make up a quantity.

## The idea

A counter scans a bin and the radio comes back: *ledger busy, try again in thirty seconds.* There
are three things the counter can do. Wait thirty seconds and scan again — right. Wait ten, because
thirty feels long, scan again, get told to wait again, and now the ledger is busier because of the
counter's own retries — wrong, and it is what everybody does the first time. Or write down what the
bin *probably* holds and move on — and that is the one that gets somebody sacked, because a number
on a count sheet that nobody counted is a replenishment that gets raised, a pallet that gets
ordered, and a write-off six weeks later when the real count is done.

This module is the radio discipline, and it has three rules.

**Wait what you were told to wait.** A failure worth retrying is a `Transient`, and a `Transient`
may carry `retry_after` — the interval the other side asked for, in seconds. When it does, that
interval is the wait. Not a shorter one because the desk is in a hurry; not a longer one because
the desk is being polite. The other side knows its own load, and its number beats our arithmetic
every time.

**When told nothing, back off.** A failure that carries no interval gets the desk's own schedule:
one second, then two, then four — doubling, so that a ledger that is down for a minute is asked
three times and not sixty. The schedule is one wait shorter than the number of attempts, because
the last attempt is not followed by a wait; it is followed by the exception reaching the caller.

**Escalate; never substitute.** When the attempts run out, the last failure is raised as it is.
Not caught and turned into `None`, not caught and turned into a default quantity, not caught and
logged and forgotten. Whoever called `retry` asked for a bin's contents, and the honest answer
after four tries is *I could not find out* — which a caller can act on, and which a made-up
fifty-two cannot be told apart from.

Two details make this testable rather than merely correct. The function that sleeps is a
**parameter**, so a test can hand in a list's `append` and read the schedule back in milliseconds
instead of living through it. And a hook called before each wait — `on_wait` — is where the caller
puts its log line, so the module logs nothing itself and knows nothing about the logger.

## The mechanism

The whole file, at `stock_desk/util/backoff.py`:

```python
"""Honest retry: wait what you were told to wait, and escalate when the attempts run out.

Nothing in here ever returns a substitute answer. A stock desk that invents a bin quantity because
the ledger was busy has not degraded gracefully; it has made a number up, and a made-up number in a
stock ledger is a replenishment nobody ordered or a write-off nobody approved.
"""

from __future__ import annotations

import time
from collections.abc import Callable, Iterator


class Transient(Exception):
    """A failure worth trying again.

    `retry_after` is the interval the other side asked for, in seconds, or `None` when it did not
    say. A provider's own instruction always wins over our arithmetic.
    """

    def __init__(self, message: str, retry_after: float | None = None) -> None:
        super().__init__(message)
        self.retry_after = retry_after


def delays(attempts: int = 4, base: float = 1.0) -> Iterator[float]:
    """The waits between attempts: base, 2x base, 4x base ...

    One fewer than `attempts`, because the last attempt is not followed by a wait — it is
    followed by the exception reaching the caller.
    """
    for step in range(max(attempts - 1, 0)):
        yield base * (2**step)


def retry[T](
    call: Callable[[], T],
    *,
    attempts: int = 4,
    base: float = 1.0,
    sleep: Callable[[float], None] = time.sleep,
    on_wait: Callable[[int, float, Transient], None] | None = None,
) -> T:
    """Call `call` until it returns, or re-raise its last `Transient` after `attempts` tries.

    `sleep` is a parameter so a test can watch the schedule without living through it. `on_wait`
    is called before each wait with the attempt number, the interval and the failure, which is
    where a caller puts its log line.
    """
    waits = list(delays(attempts, base))
    for attempt in range(1, attempts + 1):
        try:
            return call()
        except Transient as failure:
            if attempt == attempts:
                raise
            wait = failure.retry_after if failure.retry_after is not None else waits[attempt - 1]
            if on_wait is not None:
                on_wait(attempt, wait, failure)
            sleep(wait)
    raise AssertionError("unreachable: the loop above either returns or raises")
```

**Line by line:**

- `class Transient(Exception)` — **the one kind of failure this module retries.** Anything else —
  a `KeyError`, a bad argument, a bin that does not exist — passes straight through, because
  retrying a mistake three times gives the same mistake three times later. A caller decides what
  is transient by raising this; the module never guesses from a message.
- `self.retry_after = retry_after` — **the other side's instruction, carried on the exception.**
  `None` means it said nothing. The distinction between `None` and `0.0` is real: zero is an
  instruction to try again at once.
- `delays(attempts=4, base=1.0)` and `range(max(attempts - 1, 0))` — **one fewer wait than
  attempts**, and never a negative count. Four attempts, three waits: `1.0, 2.0, 4.0`. One attempt,
  no waits — the transcript in part 3.2 holds both.
- `base * (2**step)` — **doubling.** The first wait is the base; each one after is twice the
  last. A ledger that is down for ninety seconds sees this desk three times, not ninety.
- `def retry[T](...)` — **generic over the call's return type**, in the syntax this interpreter
  supports natively, so a caller that retries a function returning a dictionary gets a dictionary
  back as far as a type checker is concerned. No `TypeVar` import; the bracket is the declaration.
- `sleep: Callable[[float], None] = time.sleep` — **the default is real sleep, and it is a
  parameter.** The test hands in `waited.append` and reads `[7.5, 7.5]` back in a millisecond. A
  retry whose sleep is hard-wired is a retry whose schedule is tested by waiting for it, which
  means never.
- `waits = list(delays(attempts, base))` — **the schedule, computed once**, up front, before the
  first attempt. A generator consumed inside the loop would be harder to read and impossible to
  index by attempt.
- `if attempt == attempts: raise` — **the last attempt escalates.** A bare `raise` re-raises the
  `Transient` that was caught, with its message and its `retry_after` intact, so the caller sees
  exactly what the ledger said last.
- `wait = failure.retry_after if failure.retry_after is not None else waits[attempt - 1]` — **the
  rule in one line.** The other side's number if there is one; the schedule if there is not. This
  is the line the failure section deletes.
- `on_wait(attempt, wait, failure)` — **the hook, with everything a log line needs**: which
  attempt, how long, and what went wrong. Called before the sleep, so the line is on the page while
  the desk is waiting rather than after it wakes.
- `raise AssertionError("unreachable: ...")` — **a sentence for the type checker and the next
  reader.** Every path through the loop returns or raises; this line says so out loud rather than
  letting the function fall off its end with an implicit `None`, which is the substitute answer
  the whole module exists to refuse.

Run it. A ledger that is busy twice and answers the third time, asking for a short wait each time,
with the caller's log line on the hook:

```bash
uv run python -c "
from stock_desk.util.backoff import Transient, retry
from stock_desk.util.logging import log
calls = {'n': 0}
def read_bin():
    calls['n'] += 1
    if calls['n'] < 3:
        raise Transient('429 from the ledger', retry_after=0.01)
    return {'bin': 'C-07-2', 'qty': 52}
print(retry(read_bin, attempts=4, on_wait=lambda a, w, f: log('ledger.retrying', attempt=a, waiting=w, detail=str(f))))
"
```

```
{"ts": "2026-09-12T11:09:39.356+00:00", "event": "ledger.retrying", "attempt": 1, "waiting": 0.01, "detail": "429 from the ledger"}
{"ts": "2026-09-12T11:09:39.368+00:00", "event": "ledger.retrying", "attempt": 2, "waiting": 0.01, "detail": "429 from the ledger"}
{'bin': 'C-07-2', 'qty': 52}
```

**Line by line:**

- `"attempt": 1, "waiting": 0.01` — **the ledger's number, not ours.** The schedule would have said
  `1.0`; the exception said `0.01`, and `0.01` is what was waited. Twelve milliseconds between the
  two timestamps, which is the wait plus the call.
- **Two log lines and then the answer.** The third attempt returned, no line was written for it,
  and the dictionary came back through `retry` unchanged. The caller's `print` is the last line,
  on standard output; the two log lines were on standard error, which is why they could be told
  apart.
- `"detail": "429 from the ledger"` — **the failure's own message**, on the log line, so a reader
  knows *why* the desk waited and not only that it did.

And the ledger that never answers, with the sleep replaced by a print so the schedule is visible:

```bash
uv run python -c "
from stock_desk.util.backoff import Transient, retry
def busy():
    raise Transient('429 from the ledger')
try:
    retry(busy, attempts=3, sleep=lambda w: print('would wait', w))
except Transient as gone:
    print('escalated:', gone)
"
```

```
would wait 1.0
would wait 2.0
escalated: 429 from the ledger
```

**Line by line:**

- `would wait 1.0`, `would wait 2.0` — **the schedule, because the ledger said nothing.** Two
  waits for three attempts; the third attempt is followed by nothing.
- `escalated: 429 from the ledger` — **the last failure, raised, with its message.** No `None`, no
  default, no quantity. The caller now knows the bin could not be read, and on day 15 of this
  project that knowledge becomes a count marked *unread* rather than a number.

## When it breaks

Delete the rule. The version that always uses its own schedule — because the schedule is
"exponential backoff" and everybody knows that is correct:

```diff
             if attempt == attempts:
                 raise
-            wait = failure.retry_after if failure.retry_after is not None else waits[attempt - 1]
+            wait = waits[attempt - 1]
             if on_wait is not None:
```

```
>       assert waited == [7.5, 7.5]
E       assert [1.0, 2.0] == [7.5, 7.5]
E         
E         At index 0 diff: 1.0 != 7.5
E         Use -v to get more diff
FAILED tests/test_kit.py::test_retry_prefers_the_interval_the_provider_asked_for
1 failed, 16 passed in 0.08s
```

The ledger asked for seven and a half seconds, twice, and was asked again after one and then two.
Every retry succeeds eventually in this test, so nothing about the *answer* is wrong — the desk got
its bin — and that is why the version ships: it looks like an optimisation. What it does on a real
night is arrive early at a ledger that is busy because a receipt run is booking two thousand
lines, get refused again, and be one of three hundred terminals doing the same, so that the ledger
spends its recovery answering refusals. The provider's number was the ledger saying *I know when I
will be free*, and the schedule threw it away. The smallest fix is the one line back, and the
principle is the module's title: when you are told how long to wait, that is how long you wait.

## In production

**What a senior writes instead.** The same `retry` with two additions the desk will need by day
15: a **cap** on `retry_after`, because a ledger asking for an hour is telling you to stop, not to
wait, and a caller holding a count for an hour is a caller nobody can reason about; and
**jitter** on the schedule — a small random fraction added to each wait — so that three hundred
terminals refused at the same second do not all retry at the same second. Both are two lines, both
are deliberately absent today so that the rule they modify is learned first.

**What degrades at scale.** One terminal retrying a busy ledger is a nuisance. Three hundred
terminals on a distribution centre floor, each with its own retry loop, each ignoring the ledger's
`retry_after` in favour of one-two-four, is a synchronised wave: the ledger refuses them all at
once, they all wait one second, they all come back at once. That pattern has a name on every
platform team, and the cure is the two lines above plus this part's rule — honour the interval —
because a ledger that says *thirty seconds* is spreading its own load, and a client that listens is
part of the spreading.

**The review comment.** *"`retry` catches `Transient` and re-raises the last one. The caller in
this diff wraps `retry` in `try/except Exception: return {}`. That turns four honest failures into
an empty bin, which the reconciler will read as a variance of the full quantity and raise a
replenishment for. Let it raise."*

**The interview question.** *"A service you call returns 429 with a `Retry-After` header. Tell me
what your client does with that header, what it does when the header is absent, and what it does
after the last attempt — and what it must never do."*
