## One-line answer

One module turns the file day 0 wrote into a value in memory, and it is the only module that ever
does: the key enters the desk through `require`, which names the variable and never the value when
it is missing, and leaves the desk only as a twelve-character fingerprint that answers "is this the
same key as before?" and nothing else.

## The idea

Every counter on the night shift is issued the same kit at the goods-in desk: a scanner, a roll of
labels, a pad of count sheets, and a radio. The radio is the odd one out. It is the only item in
the kit that is worthless on its own and dangerous in the wrong hands — it is tuned to the site's
channel, and the channel code is what lets a voice on it move stock. So the code is never written
on the radio, never read out over it, and never on the count sheet. It is keyed in once, at the
desk, by the supervisor, and from then on the radio just works. If a counter's radio stops
working, the supervisor asks *which radio* — number seven — and never *what was the code*.

The desk's key is the radio's channel code, and this module is the goods-in desk. It does three
things and refuses to do a fourth.

It **reads the key from the environment**, once. The **process environment** is the set of
name-to-string pairs the operating system handed this program when it started — Python calls it
`os.environ` — and it is where every runtime this desk will ever have puts secrets: a shell, a
container, a pipeline runner. Day 0's `.env` file is a convenience for a laptop; `load_env` copies
its lines into the environment so that the rest of the desk only ever looks in one place. And it
copies them **without overwriting**: a name the environment already carries wins over the file,
because whatever started the process outranks a file on one developer's disk.

It **refuses with the name, not the value**. When `require` cannot find a key it raises an
exception whose message says which variable and what to do — and never what was there, because an
exception message ends up in a log, a terminal, a ticket and a screenshot, and a value that reaches
any of those has left the building.

It **fingerprints**. The one question that actually comes up about a key in operation is "is
terminal seven on the same key as terminal eight?", and it can be answered by a short hash of the
value without the value ever being compared in the open. Twelve hex characters of a SHA-256: enough
to tell two keys apart, useless to anybody who reads them.

What it refuses to do is print. Nothing in this file writes the value anywhere, and the test that
holds that is the one that checks the exception message.

## The mechanism

The whole file, at `stock_desk/util/keys.py`:

```python
"""The one place this desk turns a file on disk into a secret in memory.

Nothing else in this project opens `.env`, and nothing anywhere prints what it finds. A key
reaches the rest of the desk through `require`, and reaches a log only as a `fingerprint`.
"""

from __future__ import annotations

import hashlib
import os
from pathlib import Path

ROOT = Path(__file__).resolve().parents[2]
ENV_FILE = ROOT / ".env"


class MissingKey(RuntimeError):
    """A required variable is absent or empty. Carries the name and never the value."""


def load_env(path: Path = ENV_FILE) -> list[str]:
    """Copy `name=value` lines from a .env-shaped file into the process environment.

    Returns the names it set, in file order. A name already present in the environment is left
    alone: whatever started this process — a shell, a container runtime, a CI runner — outranks a
    file on one developer's disk.
    """
    if not path.exists():
        return []
    loaded = []
    for line in path.read_text(encoding="utf-8").splitlines():
        line = line.strip()
        if not line or line.startswith("#") or "=" not in line:
            continue
        name, value = line.split("=", 1)
        name, value = name.strip(), value.strip()
        if name and name not in os.environ:
            os.environ[name] = value
            loaded.append(name)
    return loaded


def require(name: str) -> str:
    """The value of `name` from the process environment, or `MissingKey` naming the variable.

    The message quotes the variable and never the value, because an exception message ends up in
    a log, a terminal, a ticket and a screenshot.
    """
    value = os.environ.get(name, "").strip()
    if not value:
        raise MissingKey(f"{name} is not set: copy .env.example to .env and fill the value in")
    return value


def fingerprint(secret: str) -> str:
    """Twelve hex characters of the SHA-256 of a secret: safe to log, useless to an attacker.

    It answers one question and only one — "is this the same key as before?" — which is the
    question that actually comes up when two terminals disagree.
    """
    return hashlib.sha256(secret.encode("utf-8")).hexdigest()[:12]
```

**Line by line:**

- `ROOT = Path(__file__).resolve().parents[2]` — **the project folder, found from this file.**
  `parents[0]` is `util/`, `parents[1]` is `stock_desk/`, `parents[2]` is the root that holds
  `.env`. Computed from the file's own location so `load_env()` finds the same file whatever
  directory the command was typed from — the driver runs from the root, a test does not.
- `class MissingKey(RuntimeError)` — **a named failure**, so a caller can catch exactly this and
  nothing else. The docstring is a promise about the message, and the test in part 3.2 holds it.
- `if not path.exists(): return []` — **no file is not an error.** A container has no `.env`; its
  runtime put the key straight into the environment. Returning an empty list says "I set nothing",
  and `require` is where the absence becomes a failure, if it is one.
- `line.startswith("#") or "=" not in line` — **the same three rules day 0's `check.py` reads the
  file by**: blank lines and comments are skipped, and a line is a setting only if it has an
  equals sign. Two readers of one file format agreeing on what a line is.
- `if name and name not in os.environ:` — **the platform wins.** A shell that exported the
  variable, a compose file that injected it, a pipeline that set it: all of those outrank the file.
  The transcript below shows it.
- `os.environ.get(name, "").strip()` and `if not value:` — **absent and empty are the same
  failure.** `.env.example` ships the name with nothing after the equals sign; a copy of it that
  was never filled in has the name set to an empty string, and that is the case day 0's fourth
  check exists for.
- `raise MissingKey(f"{name} is not set: copy .env.example to .env and fill the value in")` —
  **the variable, the fix, and nothing else.** No `{value!r}`, not even for a value that failed a
  shape check, and the failure below is what happens when somebody adds one.
- `hashlib.sha256(...).hexdigest()[:12]` — **a fingerprint, not an encryption.** Twelve characters
  is 48 bits, plenty to tell two keys apart and nowhere near enough to recover one. The docstring
  says the one question it answers so nobody extends it into a second.

Run it, from the project root, with the key day 0 put in `.env` — a placeholder, on this machine:

```bash
uv run python -c "
from stock_desk.util import keys
print(keys.load_env())
print(keys.fingerprint(keys.require('GOOGLE_API_KEY')))
"
```

```
['GOOGLE_API_KEY']
fa77d7bdb2ae
```

**Line by line:**

- `['GOOGLE_API_KEY']` — **one name set, from the file.** The list is the names, never the values;
  it is what a log line about start-up can carry.
- `fa77d7bdb2ae` — **the fingerprint of the placeholder `not-a-real-key`.** It is on this page
  because the value is not a secret. A real key's fingerprint would also be safe to print, and it
  would be the only form of the key that ever is.

And the precedence rule, with the same file on disk and the variable already in the environment:

```bash
GOOGLE_API_KEY=from-the-platform uv run python -c "
from stock_desk.util import keys
print(keys.load_env())
print(keys.fingerprint(keys.require('GOOGLE_API_KEY')))
"
```

```
[]
2dd4283a7f32
```

**Line by line:**

- `[]` — **the file set nothing**, because the name was already there. Same file, same line in it,
  no effect.
- `2dd4283a7f32` — **a different fingerprint**, which is the whole point of having one: without
  reading either value, a reader can see that the desk is on the platform's key and not the
  file's. Two terminals on different channels, told apart by the number on the radio.

## When it breaks

The variable unset and the file absent — a fresh clone, or a container whose runtime forgot to
inject it:

```bash
env -u GOOGLE_API_KEY uv run python -c "
from stock_desk.util import keys
try:
    keys.require('GOOGLE_API_KEY')
except keys.MissingKey as why:
    print(type(why).__name__ + ':', why)
"
```

```
MissingKey: GOOGLE_API_KEY is not set: copy .env.example to .env and fill the value in
```

That is the message doing its job: the name, the fix, and no value because there was none. The
failure this part exists to prevent is the improvement somebody makes to it. A key that is set but
wrong is a common case — a placeholder left in, a key from the wrong provider — so the helpful
version checks the shape and says what it found:

```diff
     value = os.environ.get(name, "").strip()
-    if not value:
-        raise MissingKey(f"{name} is not set: copy .env.example to .env and fill the value in")
+    if not value.startswith("AIza"):
+        raise MissingKey(f"{name}={value!r} does not look like an AI Studio key")
     return value
```

```
MissingKey: GOOGLE_API_KEY='not-a-real-key' does not look like an AI Studio key
```

On this machine the value it printed is a placeholder, which is the only reason it is on this page.
On a machine with a real key that was one character wrong — a paste that dropped the last
character — the message is the whole key but one, in the terminal, in the log the desk writes on
start-up, in the ticket somebody raises about it. The check is reasonable; the message is the
leak. The smallest fix is the one the file has: name the variable, describe the shape it failed if
you like, and never interpolate the value. The general rule is the module's docstring: **nothing
anywhere prints what it finds.**

## In production

**What a senior writes instead.** The same three functions, with `load_env` gone: on a laptop the
shell or a direnv-style tool exports the file, and everywhere else the runtime injects the value,
so the desk never reads a file at all and there is one fewer place a secret can be. `require` stays
exactly as it is, and `fingerprint` is logged once at start-up — `key=fa77d7bdb2ae` — so that "is
the region-two desk on the rotated key yet?" is a `grep` and not a call.

**What degrades at scale.** A three-aisle warehouse has one desk and one key. A distribution
centre runs a desk per zone on three hundred terminals, and a key rotation is three hundred
environments to update. Without the fingerprint, the morning after a rotation is spent finding
which terminals still carry the old key by watching them fail; with it, one log query lists them by
fingerprint before the first count is keyed. And without the precedence rule — the platform wins —
a `.env` left on a terminal from a test in March silently overrides the rotated key the runtime
injected, and the terminal fails in a way that looks like the rotation was wrong.

**The review comment.** *"`require` raises `MissingKey` with the value's length in the message
'to help debugging'. The length of a key is a fact about the key. Take it out; the name and the
fix are the whole message."*

**The interview question.** *"Your service needs a secret. Walk me through where it comes from on
a laptop, in a container and in CI, which of those wins if two are set, and every place the value
is allowed to appear."*
