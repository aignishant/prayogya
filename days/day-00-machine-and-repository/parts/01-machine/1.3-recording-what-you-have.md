## One-line answer

`docs/PINS.md` records the version of every tool *as observed on the machine, on a date* — and
when the observation disagrees with the plan, you append the observation and leave the plan
alone.

## The story

Still the rented house, still the handover. The owner's sheet says the electricity meter reads
4,120 units. You walk to the meter box and look. The dial says 4,187.

You do not cross out the owner's number and write yours over it. You do not quietly accept 4,120
because it is on the printed sheet. You write, underneath, *"meter read 4,187 on the day of
handover, in front of both of us"*, with the date, and you both initial it. The sheet now holds
two facts: what the owner believed, and what the dial said. When the first bill arrives, that
second line is the one that settles the argument — and the fact that the two lines differ is
itself information. Somebody used sixty-seven units between the printing and the handover, and
now everyone knows it.

The person who overwrites the number saves one line of paper and loses the only evidence of the
gap.

## The idea in plain language

The plan's §5 pins this project to a list of tool versions, and every one of those numbers was
read from a public record on a stated date. A **pin** is a version written down with the date it
was observed and the place it was read from. It is not a wish and not a rule; it is an
observation.

The list of pins lives in `docs/PINS.md`, the **pin ledger**. A ledger is a table you only ever
*add* to. Rows are never edited and never deleted. When a later observation differs from an
earlier one, a new row is appended, dated, and its `Why` column says which row it supersedes.
The old row stays, because the old row is the record that the earlier reader was told something
different — and a reader who finds a bug on day 60 needs to know what the machine looked like on
day 0, not what it was corrected to on day 61.

Today the ledger meets its first disagreement. The plan's §5 says `uv 0.12.16`, read from the
package index on 2026-09-18. The development machine, on the same date, answers `uv --version`
with `0.12.3`. Both are true. The index holds the newest published release; the machine holds
whichever release was installed on it. Neither number is wrong, and the difference is exactly
the kind of fact the ledger exists to hold.

What you do with the difference is a decision, not a correction. You may upgrade the tool to
match the plan, or keep the installed one and record it. Either way, the ledger gets a row saying
what was *observed*, and the plan's table is not touched — the plan changes only through
`docs/CHANGELOG_PLAN.md` (Principle 8), and a newer patch of the same tool is not an amendment.

## Why Prahari needs it

The plan's §9 freshness check re-reads every pin at every phase gate. It can only compare "what
we have" with "what we had" if "what we had" was written down honestly at the time. Day 26 records
the per-model rate limits of the default provider — a limit is a version in this project, and a
limit that was guessed instead of read becomes a retry loop that never fires or fires forever.
Day 46 re-reads the `mcp` package before its first install; the ledger row from the plan says
`2.2.0` and warns that the record describes a major rework, and day 46 will either confirm that
number or append the one it finds. Without the habit built today, every one of those days starts
by asking "where did this number come from?" and finding no answer.

## The mechanism

Read the values live, then write them down. Nothing here is typed from memory.

```powershell
uv --version
uv python list 3.12 --only-installed
git --version
```

**Line by line:**

- `uv --version` — the installed tool's version, straight from the binary. On the development
  machine, today: `uv 0.12.3 (507230998 2026-08-07 x86_64-pc-windows-msvc)`. The hash and the
  date after the version are the build's identity; the ledger row records the version and notes
  the date.
- `uv python list 3.12 --only-installed` — every Python 3.12 the tool can see, with paths. This
  is the source for the "which exact patch of 3.12 runs here" row; the first line on this machine
  was `cpython-3.12.13-windows-x86_64-none`, a build the tool downloaded and manages itself. The
  plan's row says `3.12.10 observed`, which is the interpreter under `Programs\Python\Python312`;
  the managed one is newer and is the one `uv run` chose in [the previous part](1.2-uv-project-and-lockfile.md).
- `git --version` — the version-control tool the next section is about. Today:
  `git version 2.54.0.windows.1`. It is not in the plan's §5 at all, and that is the third kind
  of ledger row: a tool the project depends on that nobody thought to pin.

Then append. The ledger's columns are `What`, `Value`, `Date observed`, `Day`, and `Why, and how
it was observed`. The rows this day appends are written out verbatim in the hub's §11, so that
what gets pasted is what was observed and not a retyping of it.

The rule for the `Why` column: it names *how* the value was read — the command or the URL — and,
if the row supersedes an earlier one, it says so and says why the two differ. "Newer than the
plan's row because the plan read the package index and this row read the machine" is a complete
sentence and a complete explanation.

## When it breaks

The ledger breaks in silence, which is why it needs a rule rather than a reminder. There is no
error message for "someone edited a row". The nearest thing to a real failure is the one this
repository's own tooling produces when a day claims something the plan does not say — here, a
hub that lists a concept ID the plan did not assign to it:

```text
FAIL  day  0  7 parts
        days/day-00-machine-and-repository/LESSON.md: claims FND-01, which the plan does not assign to this day

1 of 1 day(s) fail the depth contract.
```

That is `python granth.py depth 0` refusing a hub whose frontmatter disagrees with the plan's §8.
The same instinct — *the plan is right and the day is a bug* — applies to the ledger: a ledger
row that disagrees with the plan is not a reason to change the plan, and a plan that disagrees
with the machine is not a reason to change the ledger. You record both and let the difference
stand.

The second silent failure: a `TODO` left in the value column and never returned to. The plan's
own ledger has one today — the Gemini free-tier limits row says
`TODO(open https://aistudio.google.com/rate-limit while signed in ...)`. That is *correct*: a
lookup that could not be completed leaves the exact command, never a guess. The failure is not
the `TODO`; it is a `TODO` that is still there on the day the number is needed. Day 25 owns that
one.

## In production

A professional team keeps this ledger under a different name — a *bill of materials* for
software, or a dependency manifest with provenance — and the rule is the same: every version in
production is one that somebody observed, on a date, from a named source. When a security
advisory names a library version, the first question is "do we run that?", and a team with a
ledger answers it by reading a table, while a team without one answers it by logging into every
machine.

At scale, the disagreement this part is built around becomes routine: the newest published
release, the release in the lockfile, and the release actually installed on a given host are
three different numbers more often than they are the same one. Systems that assume they match are
the ones that produce "but it works in staging". The lockfile from [the previous
part](1.2-uv-project-and-lockfile.md) pins the second; this ledger pins the first and the third.

The failure that only shows under real traffic is the *retired* version: a provider announces
that a model or an endpoint version is being withdrawn, and a team whose ledger says which
version every service uses can grep for it, while a team whose knowledge lives in someone's head
finds out from the 404. In this project that is the phase-gate freshness check, run on purpose
before the 404 runs it for you.

The review comment on the teaching version: *"You changed the version in the table. Where is the
row saying what it was before, and why it changed? I cannot tell whether the old value was a typo
or a downgrade."*

The interview question: *"A dependency you run has a published vulnerability in versions below X.
How long does it take you to say, with evidence, whether you are affected?"* The honest answer
is either "one query against our manifest" or "I would have to check every deployment", and the
interviewer knows which one they want to hear.

## Check yourself

- **Run:** `uv --version` — then open `docs/PINS.md` and find the plan's `uv` row. If the two
  numbers differ, that is the observation this day's ledger row exists to record. Do not edit the
  existing row.
- **Say out loud:** why does the ledger keep a row you know to be out of date, and what would be
  lost if you deleted it?
