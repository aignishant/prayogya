## One-line answer

A version pin is a written promise that every command in this repository runs on the same
Python, and a file called `.python-version` is where the promise lives.

## The story

You are moving into a rented house. At the handover the owner walks you through it with a
printed sheet: the geyser is this model, the fridge is that model, the stove has four burners.
You both sign it. Nobody enjoys this. It feels like paperwork for a house you can plainly see.

Six months later the geyser stops working. You call the owner and say "the geyser is broken".
The owner says "which geyser? The old one was replaced last year, wasn't it?" Now you are
arguing about what the house *was*, when the only thing you wanted to fix was what the house
*is*. If you had both signed the sheet, there would be nothing to argue about. You would open the
sheet, read the model number, and call the right repair line.

The sheet was never for the day you moved in. It was for the day something broke and two people
needed to agree on what they were looking at.

## The idea in plain language

Python is not one thing. It is a program, called an **interpreter**, that reads your `.py` files
and runs them, and there are many versions of that program. Version 3.12 and version 3.13 behave
almost the same — but *almost* is the word that costs you an evening. A library that works on one
may refuse to install on the other. An error message may be worded differently. A behaviour you
relied on may have quietly changed.

On this machine, right now, there are three copies of Python 3.12 installed and the system could
easily pick up a fourth. Which one runs when you type `python`? Whichever one your shell finds
first. That answer changes when you install something, when you open a different terminal, or
when you come back to this repository in three weeks on a different laptop.

A **version pin** is a small file that says, in writing, *this project runs on Python 3.12*. The
tool that manages this project (introduced in the next part) reads that file and uses that
version every time, no matter what your shell would have found. The file is called
`.python-version`, it lives at the root of the repository, and it is committed like any other
file — because a promise that only lives on your laptop is a promise only you can read.

The pin does two jobs. It stops today's you and future you from running different Pythons
without noticing. And when something breaks, it turns "which Python was that?" from an argument
into a lookup.

## Why Prahari needs it

Day 12 installs `torch`, and day 10 installs `numpy` 2.5.3, which the pin ledger records as
requiring Python 3.12 or newer. Without the pin, a shell that happens to find an older Python
fails the install with an error about the Python version, and the reader spends the evening on
the machine instead of on attention. Day 1 builds the toolchain gate, `python granth.py check`,
and that gate runs `mypy` against a declared Python version; a pin that is missing or drifting
makes the gate green on one terminal and red on another, which is worse than red everywhere.

## The mechanism

The pin is written by `uv`, the project tool this repository uses. The part after this one
explains `uv` properly; here you only need to know that `uv python pin` exists.

```powershell
uv python list 3.12 --only-installed
uv python pin 3.12
Get-Content .python-version
```

**Line by line:**

- `uv python list 3.12 --only-installed` — shows every Python 3.12 the tool can see on this
  machine, with the full path to each. Run this first so that the pin is a fact about your
  machine, not a hope. On the development machine it listed three: two managed by `uv` under
  `AppData\Roaming\uv\python\` and one installed from the official installer under
  `AppData\Local\Programs\Python\Python312\`.
- `uv python pin 3.12` — writes the request `3.12` into `.python-version` in the current
  folder. It pins the *minor* version, not `3.12.13`, on purpose: a patch release fixes bugs
  without changing behaviour, and a pin that names a patch forces every reader to have that exact
  build. The tool prints `Pinned .python-version to 3.12`.
- `Get-Content .python-version` — reads the file back. It contains one line: `3.12`. That is the
  whole file. (Under a POSIX shell, `cat .python-version`.)

The pin is *read* every time the tool runs a command for this project: it looks for
`.python-version` in the working directory and each parent, and uses the first one it finds. If
the requested version is not installed, `uv` downloads a managed build of it by default — which is
why the `3.12.13` build appeared on this machine without anyone installing it by hand.

There is a second, looser statement of the same fact in `pyproject.toml`:

```toml
requires-python = ">=3.12"
```

That line says what the *project* tolerates. `.python-version` says what *you* will actually use.
They must agree, and the tool checks that they do — the next section shows what happens when they
do not.

## When it breaks

The pin and the project requirement disagreeing is the common one. Here `requires-python` had
been edited to `>=3.13` while `.python-version` still said `3.12`:

```text
Using CPython 3.12.13
error: The Python request from `.python-version` resolved to Python 3.12.13, which is incompatible with the project's Python requirement: `>=3.13` (from `project.requires-python`)
Use `uv python pin` to update the `.python-version` file to a compatible version
```

The tool refuses to guess which of the two files is right. The smallest fix is to make them
agree — and in this project the answer is always `3.12`, because the plan's §4 pins it.

Trying to pin a version the project has already ruled out is refused up front:

```text
error: The requested Python version `3.11` is incompatible with the project `requires-python` value of `>=3.12`.
```

And pinning a version that does not exist anywhere is *not* refused — the pin is written with a
warning, and the failure moves to the next command that tries to use it:

```text
warning: No interpreter found for Python 3.99 in managed installations, search path, or registry
Updated `.python-version` from `3.12` -> `3.99`
```

```text
error: No interpreter found for Python 3.99 in managed installations, search path, or registry
```

Read that pair carefully. The pin file is a *request*, and writing a request is cheap. The check
that the request can be honoured happens when something actually needs an interpreter. A wrong
pin therefore fails one step later than where it was made, which is exactly the kind of gap that
makes a reader blame the wrong command.

## In production

A professional pins in two places, deliberately, and knows why they differ. `.python-version`
is for the people and machines that *run* the project: developers, the CI runner, the container
build. `requires-python` is for anyone who *installs* the project as a dependency, and it is
what the resolver uses when deciding which versions of other libraries are even allowed. A team
that pins only one of them ships a project that works on every laptop and fails in CI, or the
other way round.

At scale, the pin is what makes "works on my machine" a checkable claim. A CI job reads
`.python-version`, installs exactly that, and runs the same commands you ran. When a test is
green locally and red in CI, the first thing a senior engineer checks is whether the two
interpreters match — and with a committed pin, that check is one line in the CI log.

The failure that only shows with real traffic is the *silent drift*: a developer upgrades their
machine's Python, the project still runs because nothing in it was version-sensitive yet, and six
weeks later a library release drops support for the older version that the pin still names. The
pin did not fail; it did its job by making the drift visible the moment someone reads it. The
plan's §9 freshness check re-reads these pins at every phase gate for exactly this reason.

The review comment on the teaching version: *"You pinned `3.12` in `.python-version` but
`requires-python` says `>=3.10`. Which one is true? If we support 3.10, the CI matrix needs a
3.10 job. If we do not, tighten the requirement."*

The interview question: *"Your project's `requires-python` says `>=3.9`. What actually happens
when someone installs it on 3.9?"* The honest answer, for most projects, is *nobody knows,
because nobody ran it there* — and that is the point of the question.

## Check yourself

- **Run:** `uv python find` — expect a path ending in `python.exe` whose folder name contains
  `cpython-3.12`. If it points at a different version, the pin is not being read from where you
  stand; check which folder you are in.
- **Say out loud:** why does the pin name `3.12` and not `3.12.13`, and what would change for
  the next reader if it did?
