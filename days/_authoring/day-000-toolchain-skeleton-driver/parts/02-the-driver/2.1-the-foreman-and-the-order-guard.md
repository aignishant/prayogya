## One-line answer

`./p` reads the plan and nothing else, so the plan is the single thing that decides what a day must
cover and whether that day is allowed yet — and the marker comments are what stop a person editing
the plan and a script reading it from ever drifting apart.

## The idea

The foreman in the workshop does not turn a spanner. They hold the job-card book: which job is
next, what it needs, whether the one before it was signed off. If you ask for a card out of order
they say no, and the reason they can say no is that the book, not their memory, has the order in
it. A foreman who reconstructs the order from memory is just a colleague with an opinion.

A curriculum of 297 sittings has the same problem in a worse form, because there is no colleague to
disagree with you. You sit down, you feel like writing the retrieval day, and nothing on earth
stops you — except that the retrieval day builds on a boundary that day 129 prints and a kit that
day 128 prints, and writing it early produces a document that quietly assumes files nobody has.

So this repository has a driver whose whole job is holding the book. Two things follow from that,
and the second is the one people get wrong.

**First: the driver is authoring only.** `./p` briefs a day, checks the depth contract, regenerates
the indexes and refuses to close a day whose checklist is unticked. It never builds, serves, tests
or deploys anything. Each of the forty projects carries its own `./run` for that, and `./run` never
reads the plan. The plan's §13 says this explicitly, and the reason is the one from part 1.2: the
moment a project needs the root driver, the project is no longer independent.

**Second: the plan is read by a machine, and the machine reads markers rather than headings.** A
heading is prose. Someone will improve "The day map" into "The day map, and how to read it" on a
Tuesday, and every tool that looked for the old wording will silently find nothing — silently,
because "no rows" and "no table" look identical to something scanning for a heading. A **marker
block** is an HTML comment pair that fences a table, invisible when the document is rendered, and
impossible to reword by accident:

```text
<!-- granth:day-map:start -->
...the table...
<!-- granth:day-map:end -->
```

The plan carries three of them — `tracks`, `phases` and `day-map` — and `p.py` reads what is
between them and ignores the other 1,300 lines. That is the join between a document written for
people and a program that has to agree with it.

## The mechanism

Everything `./p` cannot learn from the plan lives in one file. Here is the part of `granth.toml`
that carries decisions, at its real path:

```toml
# granth.toml
[project]
name         = "Prayoga"
slug         = "prayoga"
plan_version = "v3.1.0"
driver       = "python p.py"

[paths]
plan = "docs/00_MASTER_PLAN.md"
docs = "docs"
days = "days"

[contract]
require_failure_part = true
require_sources      = true

part_sections = [
  "one-line answer", "the idea", "the mechanism", "line by line",
  "when it breaks", "in production", "check yourself",
]

[toolchain]
lint         = ""
format_check = ""
test         = ""
```

The division of labour is the point: the plan holds *what the curriculum is*, and this file holds
only what the plan cannot express — where things live, and the shell commands of the local
toolchain.

Now the two functions that do the reading. Both are in `p.py`, at the real path, whole:

```python
# p.py
def marked_block(text: str, marker: str) -> str:
    """Text between `<!-- granth:<marker>:start -->` and its `:end`.

    Markers rather than heading names: a heading can be reworded freely, a marker cannot be
    reworded by accident.
    """
    name = re.escape(marker)
    hit = re.search(rf"<!--\s*granth:{name}:start\s*-->(.*?)<!--\s*granth:{name}:end\s*-->",
                    text, re.S)
    return hit.group(1) if hit else ""


def plan_days(cfg: Config) -> dict[int, PlanDay]:
    block = marked_block(read_plan(cfg), "day-map")
    if not block:
        sys.exit("granth: the plan carries no <!-- granth:day-map:start --> block.\n"
                 "        Every day document is checked against it — add the markers and re-run.")
    days: dict[int, PlanDay] = {}
    for cells in table_rows(block):
        if len(cells) < 2 or not re.fullmatch(r"\d{1,3}", cells[0]):
            continue
        days[int(cells[0])] = PlanDay(int(cells[0]), cells[1],
                                      ids_in(cells[2]) if len(cells) > 2 else [])
    return days
```

**Line by line:**

- `re.escape(marker)` — the marker name is interpolated into a pattern, so it is escaped before it
  gets there. Today the names are `tracks`, `phases` and `day-map` and none of them contain a regex
  metacharacter, which is exactly the situation in which people skip the escape and leave a trap
  for whoever adds a marker with a dot in it.
- `(.*?)` with `re.S` — non-greedy, and dot-matches-newline. Greedy would run from the first
  `:start` to the *last* `:end` in the file and swallow two other blocks whole; without `re.S` the
  dot would stop at the first line ending and match nothing useful.
- `return hit.group(1) if hit else ""` — a missing block returns empty rather than raising. The
  caller decides what a missing block means, and it means something different for `doctor`
  (report it) than for `plan_days` (stop everything).
- `sys.exit(...)` in `plan_days` — this is the one place a missing marker is fatal, because every
  day document is checked against the day map. Continuing with an empty map would report every day
  as unplanned, which looks like 297 bugs instead of one.
- `re.fullmatch(r"\d{1,3}", cells[0])` — a row counts as a day only if its first cell is nothing
  but one to three digits. This is what lets the block contain per-phase sub-headings, header rows
  and separator rows without any of them being mistaken for day 12.
- `ids_in(cells[2]) if len(cells) > 2 else []` — a day with no ID column is legal and closes
  nothing. Day 0 does close IDs, but the capstone's final day and any future parked day may not,
  and a parser that required the column would have made that a syntax error rather than a decision.

With those two functions, the guard is simply a comparison against the ledger. Here is it saying
yes, and here is it saying no:

```console
$ python p.py brief 0
# Prayoga — brief for day 0

## The assignment

**Title (from the plan):** Day zero — the toolchain, the skeleton, and the `./p` driver

**Close exactly these IDs — no more, no fewer:** RB-01, RB-02, RB-03

**Phase 0 — The authoring repository — the plan, the ledgers and `./p`**

- Days in the phase: 0
- The gate this day feeds: `python p.py doctor` and `python p.py check` both green on a repository with one day in it
...
**Day 0 is next. Go.**
```

**Line by line:**

- `python p.py brief 0` — the first command of every sitting, before reading anything. It replaces
  reading the plan §17, `docs/PROGRESS.md` and `docs/TRACEABILITY.md` by hand when all you need is
  what today must cover.
- **Close exactly these IDs — no more, no fewer** — not advice. `python p.py depth` compares the
  hub's frontmatter against this list and fails on an ID the plan did not assign *and* on an
  assigned ID the hub omits. A day that wants a different ID is asking for a plan amendment.
- **Day 0 is next. Go.** — printed only when the requested day is the one the ledger says is next.
  Its absence is the signal, and the exit code carries the same information for anything scripted.

## When it breaks

Ask for a day out of order. This is real output, and the exit code is the part that matters:

```console
$ python p.py brief 5
# Prayoga — brief for day 5

**STOP.** Day 5 is out of order — day **0** is next.

Not yet in the ledger: 0, 1, 2, 3, 4.
Never skip a day, merge two days, or reorder days without an ADR.

---

## The assignment
...
## Open IDs from earlier days

An open ID from a day already behind you is a bug, not a backlog item.

- `RB-01` was assigned to day 0 and is not closed.
- `RB-02` was assigned to day 0 and is not closed.
- `RB-03` was assigned to day 0 and is not closed.
- `FN-01` was assigned to day 1 and is not closed.
...
$ echo $?
1
```

Two things worth noticing. It still prints the brief — refusing to tell you what day 5 covers would
be pointless, since you can read the plan — but it leads with the stop and it exits `1`, so a hook
or a script gets an unambiguous answer while a human gets a useful one.

And the second half is the part that earns its place: it lists every ID assigned to an earlier day
and not yet closed. An open ID from a day already behind you is not a backlog item, it is a bug,
and this is the only place in the repository where that fact surfaces without being looked for.

The other failure here is quieter. Break the config the driver depends on and every command dies at
the same place:

```console
$ python p.py status
  File "...\Python312\Lib\tomllib\_parser.py", line 649, in parse_value
    raise suffixed_err(src, pos, "Invalid value")
tomllib.TOMLDecodeError: Invalid value (at line 79, column 10)
```

A traceback rather than a message, because `load_config` does not guard the parse. That is a real
rough edge in this driver and worth knowing before it happens to you: the line and column are
accurate, and the fix is always in `granth.toml` and never in the plan.

## In production

A senior engineer does not put the order guard in a document that asks people to be careful. They
put it where the work happens: an exit code, in a pre-commit hook or a pipeline step, so that
"never reorder days without an ADR" is enforced by something that cannot be talked round at 11pm.
The rule and the check are the same object or the rule is decoration.

What degrades is the cost of an unenforced ordering, and it does not degrade linearly. With
**ten** days, a person can hold the order in their head and a mistake costs one re-read. With
**297** across **forty** repositories, nobody holds it, and a day written early produces documents
that assume files no reader has — which is not caught by reading the day, only by building it,
which happens weeks later.

The same shape shows up everywhere in real systems: database migrations that must apply in order,
deploy steps with a dependency, a release checklist. The mechanism is always the one here — a
persisted record of what is done, compared against what is being asked for, refusing rather than
warning. The version people regret is the one that logs a warning and continues.

The review comment: *"This day closes `MC-33`, but the plan assigns `MC-33` to day 129. Which one
is wrong — the day or the plan?"* Exactly one of them is, and the question forces someone to say
which, rather than letting both stand.

The interview question: **"Your pipeline has steps that must run in order and sometimes they do
not. How do you stop that, and how do you tell the difference between a step that is out of order
and a step that has genuinely already run?"** The answer needs a ledger, and it needs the ledger to
be the thing that decides — not a timestamp, not a filename, and not the operator.

## Check yourself

- **Run:** `python p.py brief 0; echo "exit $?"` then `python p.py brief 5; echo "exit $?"` — expect
  `0` and `1`, and expect the second to name every ID still open from an earlier day.
- **Say out loud:** why does the plan carry marker comments instead of the driver simply looking
  for a heading called "The day map"?
