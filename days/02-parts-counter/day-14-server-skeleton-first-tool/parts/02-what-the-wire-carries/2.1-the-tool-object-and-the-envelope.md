## One-line answer

A tool crosses the hatch as two structures and neither is your Python: going out it is a `Tool`
object — a name, a description and two JSON Schemas, every field of it derived from your function —
and coming back it is an envelope with three compartments, the dictionary you returned serialised
into text in one, the same dictionary as structured data in another, and a flag saying whether it
went wrong.

## The idea

Ask the storeman for a rear brake pad set. They do not hand you a loose part. It comes back on a
tray: the part itself, a docket beside it saying what it is and where it came from, and a stamp on
the docket that says either *issued* or *refused*. The tray is the same tray every time, whatever
you asked for. That is not bureaucracy for its own sake — it is what lets the person collecting for
somebody else, who has no idea what a brake pad looks like, carry it back to the workshop and know
they have the right thing and that it went through.

The sign above the hatch works the same way. It is not four sentences somebody chalked up; it is a
printed docket, one per service, with fixed boxes on it: *what it is called* · *what it does, in
words* · *what you must give me* · *what you will get back*. Fixed boxes are the point. Somebody who
has never been to this shop can walk up, read four dockets they have never seen, and know how to
ask, because the boxes are the same boxes at every hatch in the trade.

This part is about those two printed things — the docket that goes out and the tray that comes back
— and it is deliberately not about the conversation that gets you to the counter in the first place.
Whether you have to announce yourself before you may ask anything, and what the two sides agree
about which edition of the rulebook they are both using, is **day 15's subject**, and day 15 has the
whole handshake. Today: what one tool's declaration actually contains, and what shape its answer
comes back in.

Two names, so that the rest of the day can use them. A **Tool object** is the specification's
structure for one declared tool — the docket. A **tool result envelope** is the structure a tool's
answer arrives in — the tray. Neither is something you write. Both are built from the function you
already wrote, which is why part 1.2 spent its time on the docstrings and the type hints: those are
the only inputs the derivation has.

## The mechanism

Ask the server for its tool list and print one entry in full. This is `find_part`'s `Tool` object,
exactly as the SDK emits it, with the fields it left empty dropped:

```console
$ uv run --frozen python -c "
import asyncio, json, warnings; warnings.filterwarnings('ignore')
from parts_mcp.server import mcp
async def main():
    tools = await mcp.list_tools()
    print([t.name for t in tools])
    t = [x for x in tools if x.name == 'find_part'][0]
    print(json.dumps(t.model_dump(exclude_none=True), indent=2))
asyncio.run(main())
"
['find_part', 'stock_level', 'bin_location', 'adjust_stock']
{
  "name": "find_part",
  "description": "Find parts whose number or name matches a query. An empty list is a valid answer.",
  "inputSchema": {
    "properties": {
      "query": {
        "title": "Query",
        "type": "string"
      }
    },
    "required": [
      "query"
    ],
    "title": "find_partArguments",
    "type": "object"
  },
  "outputSchema": {
    "additionalProperties": true,
    "title": "find_partDictOutput",
    "type": "object"
  }
}
```

**Line by line:**

- `"name": "find_part"` — the function's `__name__`, unchanged. This is the string a client stores,
  a model emits, and `tools/call` carries. Part 1.2's *When it breaks* is about what a rename does
  to it.
- `"description"` is the docstring's first line, in full, and it is the **only** prose the model
  gets. *An empty list is a valid answer* is in the model's context because it is in the docstring;
  there is no other channel.
- `"inputSchema"` is a JSON Schema built from the signature. `query: str` produced
  `{"title": "Query", "type": "string"}` and an entry in `"required"`, because the parameter has no
  default. Give it a default and it leaves `required` — which is how a schema says *optional*, since
  JSON Schema has no separate optional flag.
- `"title": "Query"` on the property is generated from the parameter name, capitalised. It is
  cosmetic and it is not a description: there is **no** `description` key on that property, and
  there is nowhere for one to come from, which is exactly the limitation of a derived declaration
  that part 1.2's recap named.
- `"title": "find_partArguments"` on the schema itself is the name of the model the SDK built behind
  the scenes for the argument bag. Harmless, and worth recognising so that you do not go looking in
  your own code for where you named it.
- `"outputSchema"` exists because the function is annotated `-> dict[str, Any]`, and it is
  `{"type": "object", "additionalProperties": true}` — *an object, any keys*. That is the honest
  derivation of `dict[str, Any]`: the return type says "a dictionary of anything", so the schema
  says so too. Annotate a precise return type and you get a precise schema; annotate a loose one and
  the schema is loose, and the client can check nothing.
- The list order — `find_part`, `stock_level`, `bin_location`, `adjust_stock` — is declaration
  order, and the same four names came back over a real stdio connection, which is how you know the
  transport is not reordering or filtering anything.

### Which boxes the docket has, and which this SDK fills in

The specification's server tools page, revision `2026-07-28`, lists a `Tool`'s fields. Verbatim,
fetched 2026-09-10 from `https://modelcontextprotocol.io/specification/2026-07-28/server/tools`:

> `name` […] `title`: Optional human-readable name […] `description` […] `icons`: Optional array
> […] `inputSchema`: JSON Schema defining expected parameters […] `outputSchema`: Optional JSON
> Schema defining expected output structure […] `annotations`: Optional properties describing tool
> behavior

Now the same object with nothing dropped, so the empty boxes are visible:

```console

import asyncio, json, warnings; warnings.filterwarnings('ignore')
from parts_mcp.server import mcp
import mcp.types as t
async def main():

    print('declared fields:', list(t.Tool.model_fields))
```

**Line by line:**

- The SDK's `Tool` type carries all seven fields the specification lists, plus `meta` and
  `execution`. **Four of them are filled in from your function** — `name`, `description`,
  `inputSchema`, `outputSchema` — and `title`, `icons` and `annotations` come back `null`, because
  nothing in a Python function expresses a human-readable display name, an icon or a behavioural
  hint. They are not missing; they are unfilled, and they stay unfilled until somebody passes them
  to the decorator on purpose.
- `annotations` being `null` is the one worth caring about. That is where a server says *this tool
  only reads* or *this tool is destructive*, and it is what a client uses to decide whether to
  confirm with a human before running something. Three of this project's four tools read and one
  writes, and the declaration does not distinguish them **at all**. Part 1.2's review comment asked
  for exactly this.
- `description` carries the **entire** docstring, not the first line — the blank line, the second
  paragraph and the trailing indentation are all in there as literal `\n` and spaces. The listing in
  part 1.2 printed the first fifty-two characters because a terminal is narrow; the model gets all
  of it. So the second paragraph of `adjust_stock`'s docstring — *Only call this when the person has
  clearly asked* — really does reach the model, and the leading indentation really is sent along
  with it.
- `part_no: str` and `delta: int` became `"type": "string"` and `"type": "integer"`, both in
  `required`, in signature order. A model given this cannot be told, by the schema, that a negative
  `delta` means issuing stock; that sentence lives in the description because it has nowhere else to
  go.
- `meta` and `execution` are SDK-level fields that this server does not use. Do not build anything
  on them because they appear in a dump: the specification's list above is the interoperable set.

### What comes back on the tray

The declaration is half of it. This is what a call's answer looks like after it has crossed a real
process boundary — three tools called through this project's own client over stdio, with a write in
the middle and its reverse after it, so the fixture ends where it started:

```console
$ uv run --frozen python -c "
import asyncio, json, warnings; warnings.filterwarnings('ignore')
from parts_counter.util import mcp as client
async def main():
    ts = client.over_stdio()
    tools = {t.name: t for t in await ts.get_tools()}
    for name, args in [('stock_level', {'part_no':'BRK-0143'}),
                       ('adjust_stock', {'part_no':'BLT-0310','delta':2}),
                       ('adjust_stock', {'part_no':'BLT-0310','delta':-2})]:
        r = await tools[name].run_async(args=args, tool_context=None)
        print(name, '->', json.dumps(r)[:130])
    await ts.close()
asyncio.run(main())
"
stock_level -> {"content": [{"type": "text", "text": "{\n  \"part_no\": \"BRK-0143\",\n  \"on_hand\": 4,\n  \"unit\": \"set\",\n  \"reorder_at\": 6
adjust_stock -> {"content": [{"type": "text", "text": "{\n  \"part_no\": \"BLT-0310\",\n  \"before\": 0,\n  \"after\": 2,\n  \"unit\": \"kit\"\n}"}]
adjust_stock -> {"content": [{"type": "text", "text": "{\n  \"part_no\": \"BLT-0310\",\n  \"before\": 2,\n  \"after\": 0,\n  \"unit\": \"kit\"\n}"}]
```

*The client half of this — `parts_counter/util/mcp.py`, and `over_stdio()` in particular — is day
17's subject and is printed whole there. It appears here only as the thing holding the other end of
the wire.*

**Line by line:**

- **The envelope is the lesson.** Your function returned a Python `dict`. What came back is
  `{"content": [...], "structuredContent": {...}, "isError": false}` — the return value was
  serialised, wrapped and labelled on the way out, and nothing you wrote asked for any of that.
- `"content"` is a **list** of typed blocks, and here it holds one block of `"type": "text"`. A list,
  because a tool may return several pieces, and typed, because one of them could be an image or an
  embedded resource rather than words. The list is the general case; one text block is the common
  one.
- `"text"` holds your dictionary **as a JSON string** — look at the escaped quotes and the `\n`s.
  That is the readable form, for a model that consumes text. It is not a nested object; it is a
  string that happens to contain JSON.
- `"structuredContent"` holds the same dictionary as actual structured data, and it exists because
  the tool declared an `outputSchema`. Text for the model to read, structure for code to use, both
  from one `return`.
- `"isError": false` is the stamp on the docket, and it is a field of the **result**, not a
  transport-level failure. A tool that returns an error dictionary still comes back with a result
  and a flag, not with the connection reporting a problem. Part 2.2 is about why the specification
  insists on that difference.
- The two `adjust_stock` calls are `+2` then `-2` on the belt kit, so `before: 0, after: 2` and then
  `before: 2, after: 0`. The fixture is exactly where it started, and the write went through the
  lock in part 1.1 on its way.

## When it breaks

The `outputSchema` is derived from the return annotation, and it is a promise the server enforces on
your behalf. Annotate a function `-> dict[str, Any]` and the promise is vacuous, which is safe.
Tighten it and forget one branch, and the tool starts failing in exactly that branch. Here is
`stock_level` with its annotation changed to a five-key `TypedDict` — the good part still answers,
and the not-found branch does not:

```traceback
good part: {'part_no': 'BRK-0143', 'on_hand': 4, 'unit': 'set', 'reorder_at': 6, 'below_reorder': True}
```

*Caused deliberately on this machine on 2026-09-10 by annotating `stock_level` with a `TypedDict`
and calling it with `NOPE-0000`, then restoring the file. Two of the five identical validation
errors are shown and the pydantic documentation links are cut; nothing else is edited.*

Somebody tightens that annotation on a Friday because a reviewer asked for a real `outputSchema`,
forgets that the not-found branch returns `{"error": ..., "known": [...]}` instead, and ships a tool
that works for every part number in the fixture and fails for every one that is not — which is to
say, only in the branch nobody tested. Notice where the failure landed: the tool *ran*, the store
was fine, and the SDK rejected the answer on the way out. The smallest fix is to make the error
shape part of the declared return type. The general rule: a derived schema is a promise you did not
read, so read it once, in a transcript, before you ship it.

## In production

**What a senior writes instead.** They pass the fields the derivation cannot invent — `title` for
the display name, `annotations` marking the three readers as non-destructive so a client can decide
what needs a human's confirmation — and they give the write a precise return type so its
`outputSchema` says something. They also stop treating `content` as "the answer": code reads
`structuredContent`, and the text block is for the model. Reaching into `content[0]["text"]` and
parsing the JSON out of it works, right up to the day a tool returns two blocks.

**What degrades at scale.** Every tool's whole declaration goes to the model on every turn. The
`adjust_stock` dump above is a little over four hundred characters of description and schema for
**one** tool, and this server has four. At forty tools — a plausible size for a shared internal
server — that is a fixed cost of thousands of tokens paid on every turn of every conversation before
the user's question is read, and it is paid whether the model uses any of them or not.

**The review comment.** "Print the `Tool` object for each of these and put it in the pull request.
Three things I want to see: `outputSchema` is `additionalProperties: true` for all four, which means
we are promising nothing about what comes back; `annotations` is null on the one tool that writes;
and the full docstring including the indentation is going to the model, so the second paragraph of
`adjust_stock` is doing real work and should not be reflowed casually."

**The interview question.** "A model calls one of your MCP tools and your function returns a Python
dictionary. Describe precisely what the client receives, field by field. Then tell me the difference
between `content` and `structuredContent`, which of them your own code should read, and what decides
whether `structuredContent` is present at all."
