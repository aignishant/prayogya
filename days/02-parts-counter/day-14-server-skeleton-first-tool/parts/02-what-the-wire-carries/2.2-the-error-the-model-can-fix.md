## One-line answer

The specification splits refusals into two kinds — the request itself was wrong, which a model
cannot usually repair, and the tool ran and had bad news, which a model very often can — and it
tells clients to hand the second kind straight to the model; this server's four tools are written
on the second side of that line, and the boundary's two regression tests are what stop day 12's
failures from coming back the next time somebody touches the lock.

## The idea

Stand at the hatch and listen to the storeman say no. It happens in two completely different ways
and it is worth learning to hear the difference, because what you do next is different.

The first way: you hand a docket through and the storeman hands it straight back without turning
round. There is no such service at this hatch. Or the docket is for a different shop. Or the boxes on
it are blank. Nothing was fetched, nothing was looked up, and there is nothing you can do standing
there except go and find out what the right docket is. That refusal is about the **asking**.

The second way: the storeman turns round, goes to the shelf, comes back, and says *there's no part
with that number — here are the six we carry, one of them is probably the one you mean.* The service
exists, your docket was fine, the storeman did the work, and the answer is bad news with a way
forward in it. That refusal is about the **answer**, and you can act on it without leaving the
counter.

That is the distinction the protocol makes, and it makes it for a very specific reason: on the other
side of a lot of these hatches there is a language model, and one of those two refusals is something
it can recover from on its own. Told *no part numbered NOPE-0000, here are the six we have*, a model
picks the right one and asks again. Told *malformed request*, it usually just tries the same broken
thing more slowly.

Two names for the two ways. A **protocol error** is a failure of the request itself — an unknown
tool, a request the server cannot parse — reported as a JSON-RPC `error` rather than as a result. A
**tool execution error** is a tool that ran and failed, reported *inside* a normal result with
`isError: true`. The tray comes back either way; only one of them has anything on it.

And then the second half of this part, which is the day's deliberate failure. Part 1.1 fixed day
12's two races. Nothing about a fix is worth anything if the next person can undo it without being
told, so the fixes get pinned: day 12's lost update and day 12's torn read are now two tests, and you
are going to break the lock on purpose and watch one of them go red with the exact number day 12
printed.

## The mechanism

The specification's server tools page, revision `2026-07-28`, draws the line first. Verbatim, fetched
2026-09-10 from `https://modelcontextprotocol.io/specification/2026-07-28/server/tools`:

> 1. **Protocol Errors** indicate issues with the request structure itself that models are less
>    likely to be able to fix: Unknown tool · Malformed requests · Server errors […]
> 2. **Tool Execution Errors** contain actionable feedback that language models can use to
>    self-correct and retry with adjusted parameters […] They are reported in tool results with
>    `isError: true`

And what a client is told to do with each, from the same page, verbatim:

> Clients **MAY** provide protocol errors to language models, though these are less likely to result
> in successful recovery. Clients **SHOULD** provide tool execution errors to language models to
> enable self-correction.

Read the modal verbs — they are the whole of it. `MAY` for the first, `SHOULD` for the second. The
specification is not saying one is serious and the other is not; it is sorting failures by **whether
telling the model helps.**

### Where this server sits on that line

The unknown-tool case is the specification's own first example, and it is what the SDK raises when
a name does not resolve:

```console
$ uv run --frozen python -c "
import asyncio, warnings; warnings.filterwarnings('ignore')
from parts_mcp.server import mcp
async def main():
    await mcp.call_tool('stock_levl', {'part_no': 'BRK-0143'})
asyncio.run(main())
"
mcp.server.fastmcp.exceptions.ToolError: Unknown tool: stock_levl
```

The arguments case is one step further in, and it is where day 12's worst little failure quietly
died. Day 12 handed `adjust_stock` the string `"-1"` and watched it travel three frames into
`store.adjust` before the arithmetic raised `TypeError`. Behind the boundary the argument bag is
validated against the derived `inputSchema` **before the function runs**:

```console
$ uv run --frozen python -c "
import asyncio, warnings; warnings.filterwarnings('ignore')
from parts_mcp.server import mcp
async def main():
    for args in [{'part_no':'BLT-0310','delta':'two'}, {'part_no':'BLT-0310'}]:
        try:
            await mcp.call_tool('adjust_stock', args)
        except Exception as e:
            print('---'); print(type(e).__module__+'.'+type(e).__name__+':', str(e)[:400])
asyncio.run(main())
"
---
mcp.server.fastmcp.exceptions.ToolError: Error executing tool adjust_stock: 1 validation error for adjust_stockArguments
delta
  Input should be a valid integer, unable to parse string as an integer [type=int_parsing, input_value='two', input_type=str]
    For further information visit https://errors.pydantic.dev/2.13/v/int_parsing
---
mcp.server.fastmcp.exceptions.ToolError: Error executing tool adjust_stock: 1 validation error for adjust_stockArguments
delta
  Field required [type=missing, input_value={'part_no': 'BLT-0310'}, input_type=dict]
    For further information visit https://errors.pydantic.dev/2.13/v/missing
```

**Line by line:**

- `delta: 'two'` never reaches the function. The schema part 2.1 printed says `{"type": "integer"}`,
  and something now enforces it — so the type hint that was *only* a description on day 12 has
  become a guard, without anybody adding an `isinstance` check. That is the boundary paying for
  itself: the validation is a property of the protocol layer, not of your function.
- The message names the argument, the expected type, the value it got and the type it got. A model
  handed that can fix it in one turn. This is the shape the specification means by *actionable
  feedback*.
- A **missing required argument** fails the same way, with `Field required`. `delta` is in
  `required` because the parameter has no default — which is a decision made in the `def` line and
  enforced at the far end of a wire.
- Be exact about one thing: `'2'` — a string that *is* a number — is **coerced** to `2` and the
  adjustment goes through. Validation here is pydantic's, and pydantic coerces where it safely can.
  Do not read this transcript as "strings are rejected"; read it as "the argument bag is checked
  against the declared schema, and the check is lenient in the ways pydantic is lenient."

Now the tools' own bad news. All three of the tools that take a part number handle an unknown one by
**returning** a dictionary rather than raising:

```console
$ uv run --frozen python -c "
import asyncio, json, warnings; warnings.filterwarnings('ignore')
from parts_mcp.server import mcp
async def main():
    r = await mcp.call_tool('stock_level', {'part_no': 'NOPE-0000'})
    print('structured:', json.dumps(r[1], indent=2))
asyncio.run(main())
"
structured: {
  "error": "no part numbered 'NOPE-0000'",
  "known": [
    "BRK-0142",
    "BRK-0143",
    "FLT-0071",
    "FLT-0072",
    "BLT-0310",
    "SPK-0055"
  ]
}
```

**Line by line:**

- The tool **ran**. It reached the store, the store raised `PartNotFound`, the tool caught it and
  turned it into an answer. Nothing failed at the protocol layer, so this comes back as an ordinary
  result on an ordinary tray.
- `"known"` carries the six part numbers, which is the difference between a refusal a model can act
  on and one it can only repeat. *Not found* invites a second guess; *not found, here are the six*
  invites a choice.
- **And now the honest caveat, because it is a real gap.** The specification's mechanism for this
  class is `isError: true` on the result. This server does not set that flag: it returns a normal
  result whose payload happens to have an `error` key, so the envelope says `isError: false` and the
  bad news is inside the content. The *intent* matches the specification — recoverable feedback,
  handed to the model — and the *mechanism* does not. A client that branches on `isError` learns
  nothing here; a model reading the text does. Which of those two you were relying on is a question
  worth asking before you copy this pattern, and it is the first item in this part's review comment.
- The alternative shape — let `PartNotFound` escape and be reported as `isError: true` — is
  available and is what a stricter server does. This project chose the returned dictionary on day
  12, for tools with no boundary in front of them, and the move did not revisit that choice. Naming
  an inherited decision as inherited is more useful than pretending it was made today.

### The fixes, pinned

`projects/02-parts-counter/tests/test_boundary.py`, whole file:

```python
# tests/test_boundary.py
"""What the boundary's store promises, asserted. These run in `python run.py check`."""

from __future__ import annotations

import json
import threading

import pytest

from parts_mcp import store


@pytest.fixture
def inventory():
    """Restore the synthetic inventory after any test that writes to it."""
    before = store.PARTS_FILE.read_text(encoding="utf-8")
    yield
    store.PARTS_FILE.write_text(before, encoding="utf-8")


def test_get_refuses_an_unknown_part() -> None:
    with pytest.raises(store.PartNotFound):
        store.get("NOPE-0000")


def test_find_is_case_insensitive_on_number_and_name() -> None:
    assert [p["part_no"] for p in store.find("brk")] == ["BRK-0142", "BRK-0143"]
    assert [p["part_no"] for p in store.find("TIMING BELT")] == ["BLT-0310"]


def test_adjust_changes_the_count_and_persists_it(inventory) -> None:
    before = store.get("FLT-0071")["on_hand"]
    store.adjust("FLT-0071", -3)
    assert store.get("FLT-0071")["on_hand"] == before - 3
    assert json.loads(store.PARTS_FILE.read_text(encoding="utf-8"))


def test_two_writers_lose_nothing(inventory) -> None:
    """Day 2's failure, as a test. Twenty issues from two threads; twenty come off the count."""
    part = "SPK-0055"
    start = store.get(part)["on_hand"]
    errors: list[str] = []

    def issue() -> None:
        for _ in range(10):
            try:
                store.adjust(part, -1)
            except Exception as exc:  # noqa: BLE001 - the assertion is that there are none
                errors.append(type(exc).__name__)

    left, right = threading.Thread(target=issue), threading.Thread(target=issue)
    left.start(); right.start(); left.join(); right.join()

    assert errors == []
    assert store.get(part)["on_hand"] == start - 20


def test_a_reader_never_sees_a_half_written_file(inventory) -> None:
    """The torn read from day 2. Readers run while a writer rewrites the whole document."""
    part = "SPK-0055"
    failures: list[str] = []
    stop = threading.Event()

    def write() -> None:
        for _ in range(30):
            store.adjust(part, 1)
            store.adjust(part, -1)
        stop.set()

    def read() -> None:
        while not stop.is_set():
            try:
                store.all_parts()
            except Exception as exc:  # noqa: BLE001
                failures.append(type(exc).__name__)

    writer, reader = threading.Thread(target=write), threading.Thread(target=read)
    writer.start(); reader.start(); writer.join(); reader.join()

    assert failures == []
```

**Line by line:**

- The module docstring says where these run: `python run.py check`. A test file nobody can find the
  runner for is a test file that stops being run, and the driver day 11 printed has a `tests` check
  that shells out to pytest.
- `from parts_mcp import store` — the tests import the **boundary's** store, not the agent's. There
  is no `parts_counter.store` any more to import by accident; part 1.1 deleted it. If this line
  still said `parts_counter`, the whole file would be asserting things about a module that does not
  exist, and the error would be an `ImportError` rather than a wrong pass.
- `@pytest.fixture def inventory()` reads the file's text **before** the test and writes it back
  after. Text, not a parsed document: restoring the bytes restores the formatting, the `_comment`
  key and the trailing newline, so `git status` is clean afterwards whatever the test did. Parsing
  and re-dumping would restore the data and quietly rewrite the file.
- The restore is after `yield`, so it runs whether the test passed or failed. That matters most
  precisely when you are about to break the lock on purpose: a failing test still puts the fixture
  back.
- It uses `store.PARTS_FILE.write_text` directly rather than `store.adjust`, because a restore is
  not a business operation. It is putting the world back, and going through the module under test to
  undo the module under test is how a broken restore hides a broken test.
- **Only the three tests that write take `inventory`.** `test_get_refuses_an_unknown_part` and
  `test_find_is_case_insensitive...` do not, because a fixture on a read-only test is noise that
  teaches the next reader to add it everywhere.
- `test_get_refuses_an_unknown_part` uses `pytest.raises(store.PartNotFound)` and asserts the
  **named** exception. `KeyError` would also pass and would also pass for a genuine typo inside the
  store — the named class is what makes this test about the policy (*never guess at a near match*)
  rather than about Python.
- `test_find_is_case_insensitive_on_number_and_name` asserts an exact **list**, in order, twice:
  once matching on the part number in lower case and once matching on the name in upper case. Two
  assertions in one test because they are one behaviour — the normalisation in `find` — checked from
  its two sides. Asserting the list rather than its length is what makes a wrong-but-same-sized
  answer fail.
- `test_adjust_changes_the_count_and_persists_it` checks two separate claims: the count moved by the
  delta, and the file on disk still parses. The second is not redundant. `store.get` reads through
  the same code path that wrote, so it would happily agree with itself about a file that is
  unreadable to anybody else; `json.loads(...read_text())` is the independent look.
- `assert json.loads(...)` without comparing it to anything is asserting *this parsed and was not
  empty*, which is the whole claim. An empty document would be falsy and fail.
- `test_two_writers_lose_nothing` is **day 12's `run.py race`, as an assertion.** Same part, same
  two threads, same ten issues each. The differences from the demonstration are deliberate: there is
  no `time.sleep(0.001)` between adjustments, because a test should not be slower than it has to be,
  and no restoring adjustment at the end, because the fixture does that.
- `left.start(); right.start(); left.join(); right.join()` — both threads started before either is
  joined, exactly as day 12 insisted. Start-then-join one at a time runs them in sequence and the
  test passes against a completely unlocked store, which is the standard way this test is written
  wrongly and the reason it is worth reading this line twice.
- `assert errors == []` comes **before** the count assertion, and the order is the diagnosis. If a
  thread crashed, you want to be told that rather than told about a count that is wrong *because* a
  thread crashed. Two failure modes, reported in the order that makes the second one interpretable.
- `assert store.get(part)["on_hand"] == start - 20` is the lost-update assertion, written as
  arithmetic rather than as a literal `220`. `start` is read at the top, so the test does not depend
  on the fixture's current value and does not silently start passing for the wrong reason if
  somebody edits `parts.json`.
- `except Exception as exc:  # noqa: BLE001` with the comment *the assertion is that there are
  none* — a blanket catch, on purpose, for the same reason day 12 gave: narrowing it would be
  asserting in advance which failures the race can produce.
- `test_a_reader_never_sees_a_half_written_file` is day 12's **other** failure, and it is a different
  shape because the failure is. One writer doing thirty paired adjustments, one reader looping as
  fast as it can, and the claim is that the reader never once caught the file mid-write.
- `stop = threading.Event()` and `stop.set()` at the end of `write()` — the reader loops until the
  writer says stop, rather than for a fixed number of iterations. A count would make the test's
  coverage depend on how fast the machine is; an event makes the reader run for exactly as long as
  there is a writer to catch out.
- `store.adjust(part, 1)` then `store.adjust(part, -1)`, thirty times: sixty whole-file writes, and
  the count ends where it began. The test never asserts the count, because that is the other test's
  job; this one only asserts that no read failed.
- `assert failures == []` is the whole assertion, and on day 12 this list filled up with
  `JSONDecodeError` every single run. It is empty now because of `_write_atomically`, and it stays
  empty because of the lock — **both** fixes are load-bearing here, which is why breaking either one
  is visible from this file.
- One property of this test worth knowing before you break things: if the writer thread dies from an
  exception, `stop.set()` never runs and the reader loops for ever. It does not go red — it **hangs**.
  That is a real weakness in the test and it is the reason the break below is aimed at the other one.

- `assert 230 == (240 - 20)` — **ten spark plugs lost**, which is the exact number day 12's first

- pytest prints the arithmetic unevaluated — `(240 - 20)` rather than `220` — because the assertion
  was written as arithmetic. That is the payoff for not hard-coding `220`: the failure line tells you
  where the expected number came from.
- `errors == []` passed. No thread crashed; the atomic write is still in place and still doing its
  job, so the torn read did not come back. **One fix removed, one failure returned.** Day 12's claim
  that these are two separate races with two separate windows is now something the test suite
  demonstrates rather than something a document asserts.

  failure. Check it: `git status --porcelain parts_mcp/` is empty afterwards.
- Two things that do **not** work as a break, both checked on this machine rather than assumed.
  Changing `_LOCK = threading.RLock()` to `threading.Lock()` leaves all five tests green, for the
  reason part 1.1 gave: nothing in the module re-enters the lock today. And removing the lock from
  `all_parts()` instead makes the *reader* test **hang** rather than fail — the writer dies on a
  `PermissionError`, `stop.set()` is never reached, and the reader loops for ever. A break that
  hangs teaches nothing at a terminal, which is why the instruction above is specific about which
  line to remove.

Put the `with _LOCK:` back, re-indent, and run the whole suite. Fourteen green, or you are not done.

## When it breaks

That failure is the one you caused. The one that arrives uninvited is the same test, red, in
somebody else's pull request:

```text
E       assert 230 == (240 - 20)
tests\test_boundary.py:56: AssertionError
```

Somebody refactors the store on a Friday to hold the lock for a shorter time — a reasonable
instinct, since a lock around a `fsync` is a lock held across a disk write — moves the read outside
it, and this test goes red on a number that means nothing to them. The message is a lost update and
the test's docstring says so in one line: *Day 2's failure, as a test.* The smallest fix is to put
the read back inside the critical section, because the read is not incidental to the write, it is
the value the write is computed from. If the lock really is held too long, the answer is a different
data store, not a shorter critical section.

## In production

**What a senior writes instead.** They set `isError: true` rather than smuggling an `error` key
through a successful result, because a client that has to parse the payload to find out whether the
call worked is a client that will get it wrong. Concretely: raise a specific exception from the tool
and let the protocol layer label the result, keeping the helpful `known` list in the message. And
they never write a concurrency test whose failure mode is a hang — the reader loop above gets a
deadline, so a dead writer produces a red rather than a build that runs until somebody cancels it.

**What degrades at scale.** These two tests take a fraction of a second and they are a **sampling**
argument, not a proof. Twenty adjustments and roughly sixty reads is enough to catch a lock that is
missing entirely, every time; it is nowhere near enough to catch a window that opens on one call in
ten thousand. A suite like this one goes green on a store that is wrong once a day at production
volume, and the honest way to say that is out loud in the pull request, not by adding a zero to the
loop count and calling it rigour.

**The review comment.** "Three things. `stock_level` returns `{"error": ...}` inside a result with
`isError: false` — pick one story: either raise and let the protocol flag it, or document that this
server signals tool failures in the payload, because right now a client branching on `isError` sees
every call as a success. `test_a_reader_never_sees_a_half_written_file` hangs instead of failing if
the writer thread dies; give the reader a deadline. And add a test that asserts the four **tool
names**, because part 1.2's rename risk is the one thing in this project a test could catch and
currently does not."

**The interview question.** "Your MCP tool is asked for a record that does not exist. Walk me
through the two ways the protocol lets you report that, say what the specification tells a client to
do with each, and tell me which one you would pick for this tool and why. Then: you have just fixed
a lost-update race with a lock. Write me the test that stops it coming back, and tell me what your
test does **not** prove."
