## One-line answer

On stdio the client launches the server as a child process and the protocol *is* that process's
standard input and output — one JSON message per line, no exceptions — so a single `print()` anywhere
in your server, in a library it imports, or in a debugging line you forgot, is not noise on the
channel: it **is** a message, and the client will try to parse it as one.

## The idea

The dumbwaiter shaft between the kitchen and the first floor has one car in it and no other way in
or out. That is its whole charm: nothing has to be addressed, nothing can be misrouted, and if a
tray is in the car then it came from the kitchen, because there is nowhere else it could have come
from. Two hatches, one rope, no ambiguity.

It is also its whole danger. A shaft that will accept a tray will accept a tea towel. Drop one in
because your hands were full and it is now *in the car*, riding up with the food, and the person at
the top has no way of knowing that one of the things in front of them was never meant to be sent.
There is no separate slot for things-that-are-not-orders. The shaft does not have opinions. It has a
car.

That is stdio, and the specification says it in almost those words. On this binding the client starts
your server as a **child process** — it runs the command itself — and then writes to that child's
**standard input** and reads from its **standard output**. Standard input and standard output are the
two channels every program on the machine already has: the first is where a program's input arrives,
the second is where whatever it prints goes. On this transport those two channels have been
requisitioned. They are the protocol now. From the stdio transport page of the `2026-07-28` revision,
verbatim:

> The server reads JSON-RPC messages from `stdin` and writes JSON-RPC messages to `stdout`. · Each
> message is a single JSON-RPC request, notification, or response. · Messages are delimited by
> newlines, and **MUST NOT** contain embedded newlines.

Newline-delimited: one message, one line. A reader on the far end can therefore find where a message
ends by looking for the next `\n` and nothing more — no length prefix, no framing header, no parser
that has to buffer until the braces balance. It is the cheapest framing there is, and the price of it
is that a newline in the wrong place ends a message early and a newline in the right place starts one
that nobody meant to send.

There *is* a channel left for the things that are not messages, and it is the third one every
program has: **standard error**. Same page, same revision:

> The server **MAY** write UTF-8 strings to `stderr` for any logging purposes […] The client **MAY**
> capture, forward, or ignore the server's `stderr` output and **SHOULD NOT** assume `stderr` output
> indicates error conditions.

That second sentence is the one people get wrong. `stderr` here is not the error channel; it is the
**everything-else** channel. A client that treats a line on `stderr` as evidence of a failure will
report a healthy server as broken the first time it logs anything, and this project's server logs on
every request — you will see it do so a few lines from here.

And then the rule that the rest of this part exists to serve. Same page, same revision, and it is one
sentence:

> The server **MUST NOT** write anything to its `stdout` that is not a valid MCP message.

Not *should not*. Not *avoid*. **MUST NOT**, because there is no mechanism by which a client could
survive it. The tea towel is in the car. You will cause that failure before this part is over, and
the thing worth watching is not the error — it is how quietly the same bug can hide.

One last consequence, and it is the one that makes stdio bearable in a world of crashes. Same page,
same revision:

> If the server process exits unexpectedly, the client **SHOULD** restart it. Because the protocol is
> stateless, any in-flight requests are simply lost and the client can retry them against the fresh
> process.

Note who is being described there. At the `2026-07-28` revision the protocol carries no session and
no opening handshake, so a fresh process is immediately as useful as the one that died: relaunch,
resend, done. The stack **this** project runs is a revision behind that — it opens every connection
with an `initialize` exchange, which day 15 owns — so a restart here costs one extra round trip
before the retry can go out. The shape of the advice survives the era gap; the cost of it does not.
`docs/adr/ADR-0005-mcp-era-gap-and-the-1x-pin.md` is where that gap is written down.

## The mechanism

Day 11 printed `run.py` whole, in part 2.2. Today it grows the two subcommands that start the
boundary, and this is the marked diff that adds them. Two other differences exist between day 11's
file and the finished one and **neither belongs to this part**: day 14 repointed `parts` and `race`
at `parts_mcp`, and day 17 adds `probe`. This part adds these hunks and nothing else.

`projects/02-parts-counter/run.py` — the module docstring, against the version day 11 printed:

```diff
 """This project's own driver. It depends on nothing above this folder.

     python run.py check          the gate: config, pins, the registry, and the tests
     python run.py parts <query>  find parts, straight through the tools
     python run.py race           the concurrent-write demonstration from day 2
+    python run.py mcp            run the boundary server on stdio
+    python run.py mcp --http     run the same server on Streamable HTTP at :8090/mcp
 """
```

`projects/02-parts-counter/run.py` — the new function, and the two new arms of `main`:

```diff
 # ── unchanged from day 11 part 2.2: check_keys through race ──


+def serve_mcp(http: bool = False) -> int:
+    """Run the boundary server. Same server, same tools; only the transport differs."""
+    from parts_mcp.server import mcp
+
+    if http:
+        mcp.settings.host, mcp.settings.port = "127.0.0.1", 8090
+        mcp.run(transport="streamable-http")
+    else:
+        mcp.run(transport="stdio")
+    return 0
+
+
 def main(argv: list[str]) -> int:
     match argv[1:]:
         case ["check"]:
             return check()
         case ["parts", query]:
             return parts(query)
         case ["race"]:
             return race()
+        case ["mcp"]:
+            return serve_mcp()
+        case ["mcp", "--http"]:
+            return serve_mcp(http=True)
         case _:
             print(__doc__, file=sys.stderr)
             return 2


 if __name__ == "__main__":
     sys.exit(main(sys.argv))
```

**Line by line:**

- `def serve_mcp(http: bool = False)` — one function owns the transport decision, which is part 1.1's
  production note written as code. There is exactly one occurrence of the string
  `"streamable-http"` in this project and exactly one of `"stdio"`, and both are in this function. A
  typo has one place to live and a rename has one place to happen.
- `from parts_mcp.server import mcp` **inside the function**, not at the top of the file. This is the
  same rule day 11 established for the whole driver: `run.py check` must not import the boundary, the
  MCP SDK or anything else it is not checking. A module-scope import here would mean that a broken
  server file makes the *gate* fail to start, and the gate is the thing you run to find out what is
  broken.
- `http: bool = False` — the default is stdio, matching both the SDK's default and the shape a local
  client expects. The flag is the exception; the shaft is the normal case.
- `mcp.settings.host, mcp.settings.port = "127.0.0.1", 8090` — written before `run`, because `run`
  reads the settings object rather than taking a host and port. `127.0.0.1` and not `0.0.0.0`: the
  loopback address is reachable only from this machine, so a development server started on a laptop
  on a shared network is not quietly serving your inventory to it. Day 18 is where that address
  changes, and it changes because a container's port mapping requires it to.
- No host or port is set on the stdio branch, and there is nothing to set. That asymmetry is the
  whole difference between the two bindings in one line of code: one of them has an address and the
  other one *is* a process.
- `return 0` after `mcp.run(...)` — unreachable until the server stops, and correct when it does. A
  server that is stopped deliberately has exited successfully, and the driver reports that the way
  everything else in this project reports a verdict: as an exit status, which is P00 day 3's subject
  and `PRIMER.md` §2's recap.
- `case ["mcp"]` and `case ["mcp", "--http"]` as two separate arms rather than one arm with a flag
  parsed inside it. The `match` statement is matching the argument list by shape, so an unknown
  spelling — `mcp --https`, `mcp -http` — falls to `case _`, prints the docstring and exits `2`. That
  is the "I never ran" exit status day 11 walked, and it is what stops a mistyped flag from silently
  starting the wrong transport.
- The docstring lines are not decoration: `case _` prints `__doc__`, so those two `+` lines in the
  first hunk are the program's usage message. A subcommand added without its docstring line is a
  subcommand nobody can discover.

### The protocol, by hand, down the shaft

You do not need a client to talk to a stdio server. You need three lines of JSON and a pipe. This is
the handshake day 15 walks in full; here it is a way to *see the framing*:

```console
$ cd projects/02-parts-counter
$ printf '%s\n%s\n%s\n' \
 '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"by-hand","version":"0"}}}' \
 '{"jsonrpc":"2.0","method":"notifications/initialized"}' \
 '{"jsonrpc":"2.0","id":2,"method":"tools/list"}' \
 | uv run --frozen python run.py mcp 2>/dev/null | cut -c1-110
{"jsonrpc":"2.0","id":1,"result":{"protocolVersion":"2025-06-18","capabilities":{"experimental":{},"prompts":{
{"jsonrpc":"2.0","id":2,"result":{"tools":[{"name":"find_part","description":"Find parts whose number or name
```

And the same run with the two channels swapped, so that `stdout` is discarded and only `stderr`
reaches the terminal:

```console
$ printf '%s\n%s\n%s\n' \
 '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"by-hand","version":"0"}}}' \
 '{"jsonrpc":"2.0","method":"notifications/initialized"}' \
 '{"jsonrpc":"2.0","id":2,"method":"tools/list"}' \
 | uv run --frozen python -m parts_mcp.server 2>&1 >/dev/null
Processing request of type ListToolsRequest
```

**Line by line:**

- Three messages went in and **two** came out, and that is not a lost reply. The middle line is
  `notifications/initialized` — a notification, which by definition has no `id` and gets no answer.
  Counting lines out against lines in and expecting them to match is a client bug waiting to happen.
- `cut -c1-110` is truncating for the page. Each of those two lines is one complete JSON object on
  one line with no interior newline, exactly as the framing rule requires, and you can prove it to
  yourself by dropping the `cut` and piping to `wc -l`: two.
- `2>/dev/null` in the first transcript is not tidying up. It is the demonstration: the protocol
  survives having `stderr` thrown in the bin, because nothing on `stderr` is part of the protocol.
- `2>&1 >/dev/null` in the second is the same trick backwards, and the order matters —
  `2>&1` first points `stderr` at wherever `stdout` currently goes, *then* `stdout` is redirected
  away. Write them the other way round and you discard both.
- `Processing request of type ListToolsRequest` is the SDK's own log line, on `stderr`, on a run in
  which nothing went wrong. This is the specification's "**SHOULD NOT** assume `stderr` output
  indicates error conditions" arriving as a fact about your own server: a client that treated that
  line as a failure would mark this healthy boundary as broken on its very first tool listing.
- The first pipeline runs `run.py mcp`; the second runs `python -m parts_mcp.server`. Both start the
  identical server — `parts_mcp/server.py` ends in `mcp.run(transport="stdio")` — which is worth
  seeing once, because it means the module is directly runnable and the driver is a convenience
  rather than a dependency.

### Now put a tea towel in the shaft

Add one line to a tool body in `parts_mcp/server.py` — day 13 printed that file whole; this is a
temporary edit you will undo:

```diff
 @mcp.tool()
 def stock_level(part_no: str) -> dict[str, Any]:
     """Return how many of one part are on hand, and whether that is below its reorder point."""
+    print("hello")
     try:
```

Run the handshake again, this time asking for that tool:

```console
$ printf '%s\n%s\n%s\n' \
 '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"by-hand","version":"0"}}}' \
 '{"jsonrpc":"2.0","method":"notifications/initialized"}' \
 '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"stock_level","arguments":{"part_no":"BRK-0143"}}}' \
 | uv run --frozen python -m parts_mcp.server 2>/dev/null | cut -c1-130
{"jsonrpc":"2.0","id":1,"result":{"protocolVersion":"2025-06-18","capabilities":{"experimental":{},"prompts":{"listChanged":false}
{"jsonrpc":"2.0","id":2,"result":{"content":[{"type":"text","text":"{\n  \"part_no\": \"BRK-0143\",\n  \"on_hand\": 4,\n  \"unit\"
```

**Line by line:**

- **`hello` is not there.** Two clean protocol lines, no junk, no error. The rule you were just told
  is a **MUST NOT** was broken and the run looks perfect.
- It is not there because of buffering. When a program's output goes into a pipe rather than to a
  terminal, Python holds it in a block buffer and writes it out in chunks; five characters do not
  fill a chunk, so `hello\n` was still sitting in memory. Meanwhile the SDK is not writing through
  that buffer at all — it builds a **second** wrapper around the same underlying file:

```console
$ grep -n "TextIOWrapper(sys.std" .venv/Lib/site-packages/mcp/server/stdio.py
47:        stdin = anyio.wrap_file(TextIOWrapper(sys.stdin.buffer, encoding="utf-8", errors="replace"))
49:        stdout = anyio.wrap_file(TextIOWrapper(sys.stdout.buffer, encoding="utf-8"))
```

**Line by line:**

- `sys.stdout.buffer` is the raw binary file underneath Python's text-mode `sys.stdout`. The SDK
  wraps *that*, with an encoding it chooses, and writes every protocol line through the new wrapper —
  which is correct of it, because the framing rule requires UTF-8 and the platform default is not
  guaranteed to be UTF-8 on Windows.
- The consequence for you is that there are now **two** text wrappers on one file. Your `print` goes
  into the original; the protocol goes through the new one. Whatever is in the original's buffer when
  the process ends is at the mercy of which wrapper is finalised first, and in this run it was
  discarded.
- So the bug did not fail. It **hid**, and it hid for a reason that has nothing to do with your code
  and everything to do with how the output happened to be connected. Change nothing except that, and
  it stops hiding.

Change exactly that. `PYTHONUNBUFFERED=1` is a single environment variable, set by container images,
process supervisors and launch configurations all over the industry, precisely so that logs appear
promptly:

```console
$ printf '%s\n%s\n%s\n' \
 '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"by-hand","version":"0"}}}' \
 '{"jsonrpc":"2.0","method":"notifications/initialized"}' \
 '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"stock_level","arguments":{"part_no":"BRK-0143"}}}' \
 | PYTHONUNBUFFERED=1 uv run --frozen python -m parts_mcp.server 2>/dev/null | cut -c1-130
{"jsonrpc":"2.0","id":1,"result":{"protocolVersion":"2025-06-18","capabilities":{"experimental":{},"prompts":{"listChanged":false}
hello
{"jsonrpc":"2.0","id":2,"result":{"content":[{"type":"text","text":"{\n  \"part_no\": \"BRK-0143\",\n  \"on_hand\": 4,\n  \"unit\"
```

**Line by line:**

- There is the tea towel, riding up in the car: `hello` on its own line, between two protocol
  messages, in the stream a client is parsing one line at a time.
- Nothing about the server changed. One environment variable did, and the same source file went from
  compliant-by-accident to non-compliant. That is what a **MUST NOT** is protecting you from: not the
  failure you can see, but the one that is already present and waiting for an unrelated change to
  reveal it.
- The same line appears if you write `print("hello", flush=True)`, which is what people write the
  moment they notice their debugging output vanishing — the fix for the symptom is the trigger for
  the bug.

## When it breaks

A real client meets that line. This is `parts_counter/util/mcp.py`'s stdio toolset — day 17's file —
calling `stock_level` on a server carrying one stray `print`, and it is the mild version, because the
`print` ended in a newline:

```console
Failed to parse JSONRPC message from server
Traceback (most recent call last):
  File "...\.venv\Lib\site-packages\mcp\client\stdio\__init__.py", line 155, in stdout_reader
    message = types.JSONRPCMessage.model_validate_json(line)
  File "...\.venv\Lib\site-packages\pydantic\main.py", line 782, in model_validate_json
    return cls.__pydantic_validator__.validate_json(
pydantic_core._pydantic_core.ValidationError: 1 validation error for JSONRPCMessage
  Invalid JSON: expected value at line 1 column 1 [type=json_invalid, input_value='hello\r', input_type=str]
```

Now drop the newline — `print("hello", end="", flush=True)`, which is exactly what a progress
indicator or a partially written log line does — and the junk stops being its own line and becomes a
prefix on the next real one:

```console
Invalid JSON: expected value at line 1 column 1 [type=json_invalid, input_value='hello{"jsonrpc":"2.0","i...ue},"isError":false}}\r', input_type=str]
MCP tool execution failed with McpError: Timed out while waiting for response to ClientRequest. Waited 20.0 seconds.
result: {'error': 'MCP tool execution failed: Timed out while waiting for response to ClientRequest. Waited 20.0 seconds.'}
```

Read the second block twice. The first case cost a log line: the client threw the junk away and the
answer still arrived. The second case **ate the answer** — five characters with no newline swallowed a
complete tool result, the request that was waiting for it never completed, and the caller sat on a
timeout and then reported a failure that names neither `print` nor `stdout`. Somebody debugged that
for an evening because the tool "worked when I ran it by hand" — it did, on a terminal, where the
buffering is different. The smallest fix is to delete the `print`. The fix that lasts is
`print(..., file=sys.stderr)`, or a logger configured to write there, everywhere in the server
process and everywhere in anything it imports.

## In production

**What a senior writes instead.** Nothing in a stdio server writes to `stdout` — ever — and that is
enforced rather than remembered. Logging is configured once at server start-up with `stderr` as its
destination, third-party libraries that print are pinned or wrapped, and the belt-and-braces version
is three lines at the top of the entry point that reassign `sys.stdout` to `sys.stderr` after the
transport has taken the real handle, so that a stray `print` in a dependency lands somewhere harmless
instead of on the wire. They also stop reaching for `print` as a debugger on this code path at all,
because the channel is spoken for.

**What degrades at scale.** The number is **one line**. One line of non-protocol output on `stdout`
is enough to corrupt a session, and if it lands mid-message it costs a full client timeout — twenty
seconds on this project's toolset, which is the value `parts_counter/util/mcp.py` sets — during which
the calling agent is blocked and its turn is burning wall-clock it will never get back. At one stray
`print` per hundred tool calls, a thousand-call batch stops ten times for twenty seconds each and
finishes with ten fabricated-looking failures that no traceback explains.

**The review comment.** "This adds `print(f'looking up {part_no}')` inside a tool on a server that
runs over stdio. That is a protocol violation, not a debug line — the spec says the server MUST NOT
write anything to stdout that is not a valid MCP message. Please send it to `stderr` via the logger.
Note it will appear to work locally: under a pipe the buffering usually swallows it, and it starts
corrupting the stream the moment anything sets `PYTHONUNBUFFERED`."

**The interview question.** "An MCP server works when you pipe JSON into it by hand and fails
intermittently under a real client, with the client reporting request timeouts and no error on the
server side. Give me three candidate causes ranked by how likely they are, and say what single
command you would run first to tell them apart."
