## One-line answer

Streamable HTTP puts the whole protocol behind **one URL that accepts POST**, one message per
request, and the server answers each one either as a plain JSON object or as an event stream — which
is why the client has to declare it can read a stream in the `Accept` header *before* the server will
look at the body at all.

## The idea

The kitchen's second outlet is a loading bay: a numbered roller door onto the yard. Nothing about it
resembles the shaft. There is no car and no rope; there is a doorway, and vans come to it. Each
consignment goes out on its own trip, with its own paperwork, and the bay has no memory of the van
that was here before. If two vans arrive together, two consignments go out together, because a
doorway is not a queue of one.

The bay does one thing before it loads anything, and it looks like bureaucracy until you have watched
it go wrong. It asks what the van can take. Some vans can carry a sealed box and nothing else; some
have a tail lift and can take an open pallet that keeps being added to while the driver waits. The
bay has to know *which* before it decides how to send the order out, because the two are packed
differently and there is no undoing it once the door is shut. A van that turns up without saying is
turned away at the gate — not because the order is wrong, but because the bay cannot begin.

That is the whole of this part. On this binding the server is not a process somebody launched; it is
**an address**. The specification calls that address the MCP endpoint, and it is precise about the
shape. From the Streamable HTTP transport page of the `2026-07-28` revision, verbatim:

> The server exposes a single HTTP endpoint (the **MCP endpoint**) that accepts POST. · The client
> sends every JSON-RPC request or notification as its own HTTP POST. · The server answers each
> request with either a single JSON object or a Server-Sent Events (SSE) stream scoped to that
> request

Three sentences, three things worth holding on to. **One endpoint** — not one per method, not a REST
surface where `tools/list` is a `GET /tools`; every message in the protocol goes to the same URL and
the method name lives in the body. **One POST per message** — the framing problem stdio solved with
newlines is solved here by HTTP itself, because a request body has a length and an ending and
somebody else's code already knows how to find them. And **two possible answer shapes**, which is
the part that surprises people: a single JSON object, or a **Server-Sent Events** stream.

Server-Sent Events, usually written SSE, is an ordinary HTTP response whose body never ends on
purpose. Instead of one document it carries a sequence of small blocks, each a line naming the event
and a line carrying its data, separated by blank lines. It exists so that a server can keep sending
after it has started answering. Here it gives the server the option of streaming progress or logs
alongside a result rather than going silent until the whole thing is ready.

The consequence is the header. If the answer might be a stream, the client must be able to read a
stream, and there is no way to find that out afterwards — the response line and its content type go
out before the body does. So the client says up front, in `Accept`, that it will take either shape,
and a client that does not say so is refused before its body is parsed. That refusal is the first
thing most people meet on this transport, and it reads like a bug in your JSON when it is nothing of
the kind.

## The mechanism

Nothing new is written here. `run.py mcp --http` — part 1.2's diff — starts the same
`parts_mcp/server.py` day 13 printed, and this part is what you can see on the wire once it is up.
Start it in one terminal and leave it running:

```console
$ cd projects/02-parts-counter
$ uv run --frozen python run.py mcp --http
```

The paths it serves are not guesses; they are settings on the server object, and they can be read:

```console
$ uv run --frozen python -c "
import warnings; warnings.filterwarnings('ignore')
from parts_mcp.server import mcp
print('streamable_http_path =', mcp.settings.streamable_http_path)
print('json_response        =', mcp.settings.json_response)
"
streamable_http_path = /mcp
json_response        = False
```

**Line by line:**

- `streamable_http_path = /mcp` — the MCP endpoint is `/mcp`, and it is a default, not a law. A
  client that assumes it gets a `404` on a server mounted elsewhere, and a `404` says nothing about
  what was being looked for. `parts_counter/util/mcp.py` writes the whole URL out for exactly this
  reason, and day 17 is where that file is printed.
- `json_response = False` — this is the server choosing, once and for every request, which of the
  specification's two answer shapes it uses. `False` means *always the stream*. Set it to `True` and
  the same server answers with a bare JSON object and no event framing. Both are conformant; the
  stream is the default because it is the shape that can still carry something after the answer has
  begun.
- Reading settings off the object rather than off the documentation is the habit worth stealing here.
  These two values decide whether every `curl` you are about to type hits the endpoint or a `404`,
  and the object in front of you is the only thing that actually knows.

### The refusal that comes before the body

Send a well-formed request with no `Accept` header worth the name:

```console
$ curl -s -D - -X POST http://127.0.0.1:8090/mcp \
   -H 'Content-Type: application/json' \
   -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'
HTTP/1.1 406 Not Acceptable
date: Wed, 09 Sep 2026 19:52:25 GMT
server: uvicorn
content-type: application/json
content-length: 152

{"jsonrpc":"2.0","id":"server-error","error":{"code":-32600,"message":"Not Acceptable: Client must accept both application/json and text/event-stream"}}
```

**Line by line:**

- `406 Not Acceptable` is HTTP's own status for "I cannot produce anything you said you would take".
  It is not an authentication problem, not a validation problem and not a routing problem, and it
  arrives before the body is examined at all — the JSON in that request was perfectly good.
- The message says **both**: `application/json` *and* `text/event-stream`. Not either. The server is
  reserving its right to choose the shape per request, and it will only do that if the client has
  committed to handling both. This is the loading bay asking about the tail lift before it loads.
- The error body is still JSON-RPC — `"jsonrpc":"2.0"` and an `error` object with code `-32600`,
  which is JSON-RPC's "Invalid Request". Two error systems are stacked here and they do not always
  agree: the HTTP status carries one verdict for proxies, load balancers and metrics, and the body
  carries another for the client's own error handling. A client that reads only one of the two will
  eventually report the wrong thing.
- `"id":"server-error"` rather than the `1` you sent. The server never got as far as parsing your id,
  so it invented a placeholder. If your client matches replies to requests by id — and it must — this
  reply matches nothing, which is another reason a transport-level refusal has to be handled at the
  transport level and not in the code that waits for answers.

### What a served message actually looks like

Now with the header the transport requires:

```console
$ curl -s -D - -X POST http://127.0.0.1:8090/mcp \
   -H 'Content-Type: application/json' \
   -H 'Accept: application/json, text/event-stream' \
   -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"curl","version":"0"}}}'
HTTP/1.1 200 OK
date: Wed, 09 Sep 2026 19:52:56 GMT
server: uvicorn
cache-control: no-cache, no-transform
connection: keep-alive
content-type: text/event-stream
x-accel-buffering: no
Transfer-Encoding: chunked

event: message
data: {"jsonrpc":"2.0","id":1,"result":{"protocolVersion":"2025-06-18","capabilities":{"experimental":{},"prompts":{"listChanged":false},"resources":{"subscribe":false,"listChanged":false},"tools":{"listChanged":false}},"serverInfo":{"name":"parts-mcp","version":"1.30.0"}}}
```

**Line by line:**

- `content-type: text/event-stream` — the server took the second of its two options, as
  `json_response = False` promised it would. Everything after the blank line is SSE framing, and the
  framing is two lines: `event:` names the kind of thing, `data:` carries it.
- `event: message` and then `data: {...}` — and inside the `data:` line is an **ordinary JSON-RPC
  result**, byte for byte the thing that came down the pipe on stdio in part 1.2. That is part 1.1's
  claim made visible: the binding wrapped the message, it did not change it. Strip the two SSE lines
  and you have the stdio transcript.
- `Transfer-Encoding: chunked` and no `content-length`. The server does not know how long the answer
  will be when it starts writing, because a stream is allowed to keep going. This is what makes the
  `Accept` demand unavoidable rather than fussy.
- `x-accel-buffering: no` and `cache-control: no-cache, no-transform` are aimed past the client at the
  proxies in between. A reverse proxy that buffers a response to make it efficient will hold a stream
  until it ends, which for a stream means holding it forever; these headers ask it not to. Day 18 is
  where a proxy first exists in front of this server, and this is the header that makes it behave.
- **There is no `mcp-session-id` header in that response.** Look for it and it is not there — not on
  the `initialize` reply, not on any reply. That absence is the point of the next transcript, and
  *why* this server is built that way is day 13's subject, not this part's.

### No session, therefore no continuity to lose

These two calls were made against that same running server, on separate connections, and **neither
of them performed an `initialize` first**:

```console
$ curl -s -X POST http://127.0.0.1:8090/mcp \
   -H 'Content-Type: application/json' \
   -H 'Accept: application/json, text/event-stream' \
   -d '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"stock_level","arguments":{"part_no":"BRK-0143"}}}'
event: message
data: {"jsonrpc":"2.0","id":2,"result":{"content":[{"type":"text","text":"{\n  \"part_no\": \"BRK-0143\",\n  \"on_hand\": 4,\n  \"unit\": \"set\",\n  \"reorder_at\": 6,\n  \"below_reorder\": true\n}"}],"structuredContent":{"part_no":"BRK-0143","on_hand":4,"unit":"set","reorder_at":6,"below_reorder":true},"isError":false}}

$ curl -s -X POST http://127.0.0.1:8090/mcp \
   -H 'Content-Type: application/json' \
   -H 'Accept: application/json, text/event-stream' \
   -d '{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"bin_location","arguments":{"part_no":"BLT-0310"}}}'
event: message
data: {"jsonrpc":"2.0","id":3,"result":{"content":[{"type":"text","text":"{\n  \"part_no\": \"BLT-0310\",\n  \"bin\": \"C-07-2\",\n  \"name\": \"Timing belt kit\"\n}"}],"structuredContent":{"part_no":"BLT-0310","bin":"C-07-2","name":"Timing belt kit"},"isError":false}}
```

**Line by line:**

- Each request carried everything needed to answer it — the method, the tool name, the arguments —
  and the server had never seen the connection before. Two separate `curl` invocations means two
  separate TCP connections; nothing was reused and nothing was remembered.
- Compare that with what part 1.2 required on stdio, where the three messages had to go down **one**
  pipe to **one** process in order. Here there is no "the connection" to speak of. That is the
  difference between a shaft and a doorway, and it is the whole reason this transport can be put
  behind a load balancer with more than one server behind it.
- The result envelope is identical to stdio's: `content` with a text block, `structuredContent` with
  the same data as an object, `isError: false`. Day 17 is where that envelope is taken apart. Today
  it is evidence: same server, same tools, same answers, different carrying.
- The `id` in each reply is the `id` you sent. On stdio that mattering was invisible because there
  was one pipe and one order; here it is load-bearing, because two POSTs can be in flight at once and
  the only thing tying an answer to its question is that number.

## When it breaks

The `406` is the one you will actually hit, and its message is unusually good, which is why it is
worth reading rather than skimming:

```text
{"jsonrpc":"2.0","id":"server-error","error":{"code":-32600,"message":"Not Acceptable: Client must accept both application/json and text/event-stream"}}
```

Somebody had a working script that talked to the server over stdio, moved it to HTTP because the
server had been containerised, kept the JSON exactly as it was, and got this. They spent the evening
on the request body — reformatting it, validating it, checking the method name — because a `-32600`
"Invalid Request" is the code JSON-RPC uses for a malformed message, and every instinct says the
problem is in the thing you just changed. The body was never read. The smallest fix is one header:
`Accept: application/json, text/event-stream`, with **both** values, comma-separated.

## In production

**What a senior writes instead.** They do not hand-write these requests. A real client library sets
`Accept` correctly, matches replies to requests by id, and handles a stream that ends mid-answer —
this project's is `parts_counter/util/mcp.py`, printed on day 17. `curl` comes out when you need to
know whether the server or the client is lying, and the discipline that makes it useful is `-D -`:
always dump the response headers, because on this transport the headers carry decisions the body
never mentions.

**What degrades at scale.** The number is **one connection per in-flight request**. Every POST holds
a connection open for as long as its answer takes, and the answers are streams that a proxy will not
release early — so a boundary serving 200 concurrent tool calls is holding 200 open connections, and
the first limit you meet is not CPU or memory but a proxy's or a load balancer's per-backend
connection cap. That is the cost of the shape that bought you replicas, and it is a cost you can
count in advance rather than discover.

**The review comment.** "This client sends `Accept: application/json` only. It works today because
our server happens to answer small results quickly, but the transport requires both media types and
the server is entitled to refuse — please send `application/json, text/event-stream` and add a test
that asserts a 406 is surfaced as a configuration error rather than retried."

**The interview question.** "Your MCP server is behind a load balancer with three replicas and
clients report that roughly one call in three fails. The server logs show nothing unusual. Walk me
through what you would check, and say what it would mean if the failures stopped when you pinned
every client to one replica."
