## One-line answer

`parts_mcp/server.py` is this project's boundary and it fits on one screen, and the single most
consequential thing in it is a keyword argument on line 30: `stateless_http=True` makes the server
answer a stranger on a connection it has never seen before, while `stateless_http=False` — which is
the SDK's default, so it is what you get by not deciding — mints a session identifier, hands it back
in a header, and answers the next call without it with `Bad Request: Missing session ID` and an HTTP
400.

## The idea

Two counters, in two buildings, with the same four clerks behind each and the same shelf of parts
behind them. At the first counter you walk up, say what you want, and are answered. Come back an
hour later, or send a colleague instead, or walk in through the other entrance — same answer, no
preamble, nobody asks whether you have been in before. At the second counter you walk up and are
handed a small numbered ticket first, and from then on nothing happens unless you are holding it.
Lose the ticket and they are not being difficult; they genuinely cannot help you, because everything
they know about you is filed under that number.

The staff are identical. The shelf is identical. The questions and the answers are identical. The
difference is entirely in whether there is a ticket, and it is invisible from the outside until the
moment you turn up without one.

That is what this part is: **the same file, served twice, one keyword apart.** The four things this
boundary can do are exactly the four functions day 12 printed, in the same order, with the same
docstrings and the same dictionaries coming back — and this day is not about them. It is about the
object those four functions are attached to, what it is for, and the one argument on its constructor
that decides which of the two counters you have built. The tool bodies get their own sitting
tomorrow, where the four are taken one at a time and the wire format of a call is opened up. Today,
look past them at the shape.

Two words before the code, because both are used loosely everywhere else. A **transport** is how
bytes get from client to server — a subprocess's pipes, or HTTP requests to a URL. A **protocol
revision** is what those bytes mean, named by a date like `2025-06-18`. They vary independently: the
same revision runs over either transport, and one transport can carry several revisions. Line 85 of
the file below picks a transport and says nothing about a revision, and that separation is the point
of both this part and day 16.

## The mechanism

`projects/02-parts-counter/parts_mcp/server.py`, whole file — new to the curriculum today, and taught
at full depth here because this is where it first appears:

```python
# parts_mcp/server.py
"""This project's data boundary. It owns the inventory; nothing else opens the file.

Four tools, three of which read and one of which writes, and the write is the reason this process
exists as a separate thing at all.

`stateless_http=True` is the shape this curriculum builds towards and the reason day 3 spends a
sitting on the reframe. It means every request carries everything needed to answer it, so a second
replica can answer a call the first one never saw, and a container can be killed between two calls
without losing anything. The alternative — a session established once and referred to afterwards —
is the phone call, and it is what makes a server a thing you cannot scale by adding another.

The tool docstrings are written for a model, because they are what a model is shown: the MCP tool
declaration takes its `description` from the docstring and its `inputSchema` from the type hints,
the same derivation P01 day 4 taught for ADK's own `FunctionTool`.

All data is synthetic.

Verified against mcp 1.30.0 on 2026-09-10.
"""

from __future__ import annotations

from typing import Any

from mcp.server.fastmcp import FastMCP

from parts_mcp import store

mcp = FastMCP("parts-mcp", stateless_http=True)


@mcp.tool()
def find_part(query: str) -> dict[str, Any]:
    """Find parts whose number or name matches a query. An empty list is a valid answer."""
    hits = store.find(query)
    return {"query": query, "count": len(hits),
            "hits": [{"part_no": p["part_no"], "name": p["name"]} for p in hits]}


@mcp.tool()
def stock_level(part_no: str) -> dict[str, Any]:
    """Return how many of one part are on hand, and whether that is below its reorder point."""
    try:
        part = store.get(part_no)
    except store.PartNotFound:
        return {"error": f"no part numbered {part_no!r}",
                "known": [p["part_no"] for p in store.all_parts()]}
    return {"part_no": part["part_no"], "on_hand": part["on_hand"], "unit": part["unit"],
            "reorder_at": part["reorder_at"], "below_reorder": part["on_hand"] <= part["reorder_at"]}


@mcp.tool()
def bin_location(part_no: str) -> dict[str, Any]:
    """Return the bin a part is stored in, so somebody can walk to it."""
    try:
        part = store.get(part_no)
    except store.PartNotFound:
        return {"error": f"no part numbered {part_no!r}",
                "known": [p["part_no"] for p in store.all_parts()]}
    return {"part_no": part["part_no"], "bin": part["bin"], "name": part["name"]}


@mcp.tool()
def adjust_stock(part_no: str, delta: int) -> dict[str, Any]:
    """Change the on-hand count of a part by delta. Use a negative delta to issue stock.

    Only call this when the person has clearly asked for the count to change. Reading a level is
    stock_level; this is the tool that alters the record.
    """
    try:
        before = store.get(part_no)["on_hand"]
        part = store.adjust(part_no, delta)
    except store.PartNotFound:
        return {"error": f"no part numbered {part_no!r}",
                "known": [p["part_no"] for p in store.all_parts()]}
    return {"part_no": part["part_no"], "before": before, "after": part["on_hand"],
            "unit": part["unit"]}


if __name__ == "__main__":
    # stdio is the default and the one a local client launches as a subprocess. Day 6 runs the
    # same server over Streamable HTTP without changing a line above this one, which is the
    # argument for transports being a property of how you serve rather than of what you wrote.
    mcp.run(transport="stdio")
```

**Line by line:** full depth, and deliberately **only on the shape** — the server object, the
registration, and the serve call. The four tool bodies are tomorrow's whole subject and are not
explained here; what you need from them today is that they exist, they take strings and integers,
and they return plain dictionaries.

- **The module docstring** is for people and is the only text in this file that is. Every other
  docstring below it is read by a machine and shown to a model, which is why the tone changes so
  sharply between them: this one argues, and theirs instruct. Do not put project rationale in a tool
  docstring for the same reason you do not put it in an API response.

- `from __future__ import annotations` — makes every annotation in this module a *string* rather
  than an evaluated object. It is here for the ordinary reason it is in every modern module (it lets
  a hint name a type that does not exist yet, and costs nothing at import), and it is worth being
  explicit that it does **not** break the tool schemas: `FastMCP` resolves the annotations properly
  rather than reading the raw strings, and the proof is not an assertion, it is day 14's `tools/list`
  output, where `find_part`'s `inputSchema` comes back with a real `"type": "string"` in it. Written
  without this import the file behaves the same; written with it and a naive schema builder, every
  parameter would silently lose its type — which is the failure mode worth knowing about, because a
  schema with no `type` constrains nothing and the model finds that out before you do.

- `from typing import Any` — imported solely for the `dict[str, Any]` return annotations. `Any` is
  the honest choice here rather than a lazy one: these four return dictionaries whose values are
  genuinely of mixed type — strings, integers, booleans, a list — and pretending otherwise with
  `dict[str, str]` would be a hint that lies. A hint that lies is worse than `Any`, because tooling
  believes it.

- `from mcp.server.fastmcp import FastMCP` — **the single most version-sensitive line in this
  project.** This module path exists in `mcp` 1.x and does not exist in 2.x, where the class was
  renamed. Part 2.2 is about that break and the error it produces; note for now that the import is
  the thing that fails, which means the failure arrives at import time and not at request time, and
  that is the good version of this bug.

- `from parts_mcp import store` — the boundary imports the store, and **nothing outside the
  `parts_mcp` package imports either.** That sentence is the whole of day 12's argument turned into
  a package layout. The store reaches the disk; the server is the only thing that reaches the store;
  everything else in the world reaches the server, over a protocol, or does not reach it at all.

- `mcp = FastMCP("parts-mcp", stateless_http=True)` — four separate decisions on one line.

  - **It is at module level, not inside a function.** The server object is built once, when the
    module is imported, because the `@mcp.tool()` decorators below need it to exist while the module
    body is running. A consequence worth holding on to: *importing this module is what builds the
    tool table*. Nothing has to be started for `mcp` to know its four tools, which is why day 14 can
    list them without a server running at all.
  - **`"parts-mcp"` is the server's name on the wire**, and you can see it come back in the
    `initialize` result below as `"serverInfo":{"name":"parts-mcp","version":"1.30.0"}`. Read that
    `version` twice: it is **the SDK's version, not this project's**. `1.30.0` is `mcp`'s. Nothing in
    this file sets a version, and a client that reads that field as *the parts server's release* will
    be wrong in a way that is very hard to argue with later.
  - **`stateless_http=True` is the day.** With it, the server keeps nothing between requests: no
    session is created, no identifier is minted, no header comes back, and any request that arrives
    complete is answered by whichever process receives it.
  - **And the default is `False`.** Read from `FastMCP.__init__` on this machine today:
    `stateless_http: bool = False`. So the postcard is the opt-in and the switchboard is what you get
    by not deciding — which is exactly backwards from what the current specification revision now
    requires, and is the clearest single piece of evidence that this SDK belongs to the older era.
    Section 2 is about that gap.

- `@mcp.tool()` — **with the parentheses.** The decorator is a factory: calling it returns the actual
  decorator, which registers the function on `mcp` and then hands the function back unchanged. Two
  consequences. First, `find_part` is still an ordinary Python function after registration, so it can
  be imported and called and unit-tested with no server anywhere — which is what day 14's tests do.
  Second, registration is a **side effect of import**, so the order the four appear in this file is
  the order they will appear in a tool listing, and deleting the import of this module anywhere is
  enough to make its tools quietly not exist.

- **The four bodies — day 14, in full.** They are printed above because the completeness rule does
  not allow a file to appear with a hole in it, and they are not explained here because tomorrow's
  entire sitting is the four of them one at a time: the read-versus-write asymmetry on the wire, the
  `structuredContent` field, and what `isError: true` is for. What today needs from them is only
  their shape: a string in, a dictionary out.

- `if __name__ == "__main__":` and `mcp.run(transport="stdio")` — **the transport is chosen at serve
  time, not at write time.** Not one line above this changes when the same file is served over HTTP
  instead, which is the argument the comment in the file is making and which day 16 makes properly.
  One subtlety to file away now, because it is the commonest confusion in this SDK: `stateless_http`
  is a property of the **HTTP** transport and is inert under stdio. A stdio server is one process per
  client, launched by that client and dying with it, so there is nothing for a session to be sticky
  *to* — the process boundary already is the session.

### Stateless: `initialize` hands back no session

```console
$ curl -s -D - -X POST http://127.0.0.1:8090/mcp \
   -H 'Content-Type: application/json' \
   -H 'Accept: application/json, text/event-stream' \
   -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"curl","version":"0"}}}'
HTTP 200
content-type: text/event-stream

event: message
data: {"jsonrpc":"2.0","id":1,"result":{"protocolVersion":"2025-06-18","capabilities":{"experimental":{},"prompts":{"listChanged":false},"resources":{"subscribe":false,"listChanged":false},"tools":{"listChanged":false}},"serverInfo":{"name":"parts-mcp","version":"1.30.0"}}}
```

`-D -` dumps the response headers, and the thing to look for is the one that **is not there**: no
`mcp-session-id`. The server was asked to introduce itself, did so, and handed back nothing to quote
later, because there is nothing to quote.

### Stateless: a tool call with no session, on a fresh connection, works

```console
$ curl -s -X POST http://127.0.0.1:8090/mcp \
   -H 'Content-Type: application/json' \
   -H 'Accept: application/json, text/event-stream' \
   -d '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"stock_level","arguments":{"part_no":"BRK-0143"}}}'
event: message
data: {"jsonrpc":"2.0","id":2,"result":{"content":[{"type":"text","text":"{\n  \"part_no\": \"BRK-0143\",\n  \"on_hand\": 4,\n  \"unit\": \"set\",\n  \"reorder_at\": 6,\n  \"below_reorder\": true\n}"}],"structuredContent":{"part_no":"BRK-0143","on_hand":4,"unit":"set","reorder_at":6,"below_reorder":true},"isError":false}}
```

And a **second, brand-new connection**, still carrying no session:

```console
$ curl -s -X POST http://127.0.0.1:8090/mcp \
   -H 'Content-Type: application/json' \
   -H 'Accept: application/json, text/event-stream' \
   -d '{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"bin_location","arguments":{"part_no":"BLT-0310"}}}'
event: message
data: {"jsonrpc":"2.0","id":3,"result":{"content":[{"type":"text","text":"{\n  \"part_no\": \"BLT-0310\",\n  \"bin\": \"C-07-2\",\n  \"name\": \"Timing belt kit\"\n}"}],"structuredContent":{"part_no":"BLT-0310","bin":"C-07-2","name":"Timing belt kit"},"isError":false}}
```

Neither call performed an `initialize` first. Each request carried everything needed to answer it, and
was answered by a process that had never heard of the caller. **That is the postcard.** Stop and
notice how unremarkable it looks, because that is the whole win: there is nothing to see.

### Stateful: the same file, one flag flipped — it mints a session and then demands it

```console
$ curl -s -D - -X POST http://127.0.0.1:8091/mcp \
   -H 'Content-Type: application/json' \
   -H 'Accept: application/json, text/event-stream' \
   -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"curl","version":"0"}}}'
HTTP 200
mcp-session-id: 8afe8ea126254dab906853bdfe33751b
```

```console
$ curl -s -X POST http://127.0.0.1:8091/mcp \
   -H 'Content-Type: application/json' \
   -H 'Accept: application/json, text/event-stream' \
   -d '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"stock_level","arguments":{"part_no":"BRK-0143"}}}'
{"jsonrpc":"2.0","id":"server-error","error":{"code":-32600,"message":"Bad Request: Missing session ID"}}
HTTP 400
```

**That pair is the phone call set against the postcard, with nothing else changed.** One flag; one
server answers a stranger, the other refuses anyone who has not rung first. The identifier is minted
per connection and not per server, which is easy to say and easier to disbelieve until you watch it:
a second `initialize` against that same running process on the same day returned
`mcp-session-id: 2a4c870a3a9740cb9e5c400bfe0d66bd`. Nothing about the ticket is derivable. It is
handed out, and holding it is the only way to be served.

One last observation, and it is the tidiest evidence in the day that the two shapes are genuinely
different protocols rather than two settings: hand the **stateless** server a session identifier and
it does not object, does not look it up, and does not care — the answer comes back exactly as if the
header were absent. Which is, word for word, what the `2026-07-28` specification requires a modern
server to do with one:

```text
An `Mcp-Session-Id` header on a request: ignore it, and do not mint or echo session IDs.
```

## When it breaks

The first failure everybody hits with this transport has nothing to do with sessions, and the message
is unusually clear once you know to read the whole of it. Drop the `Accept` header — which is what
every HTTP client that has not been told otherwise does — and the request is refused before it is
parsed:

```console
$ curl -s -i -X POST http://127.0.0.1:8090/mcp \
   -H 'Content-Type: application/json' \
   -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'
HTTP/1.1 406 Not Acceptable
content-type: application/json
content-length: 152

{"jsonrpc":"2.0","id":"server-error","error":{"code":-32600,"message":"Not Acceptable: Client must accept both application/json and text/event-stream"}}
```

Somebody wires a health check at the boundary on a Friday, points it at `/mcp`, and it is red all
weekend while the server is perfectly well and answering the agent normally. The `406` is not about
the body, the method or the tool; it is about one request header, and it happens because the
transport may answer either with a single JSON object or with an event stream and will not guess
which you can accept. The smallest fix is the one header:
`Accept: application/json, text/event-stream`. The wider lesson is that this endpoint is not a
REST endpoint that happens to speak JSON, and treating it as one fails at the first hop.

## In production

**What a senior writes instead.** They do not leave `stateless_http` unwritten. The default is
`False`, so omitting it is not neutrality — it is choosing the switchboard silently, and the choice
becomes visible for the first time on the day somebody scales the deployment to two replicas. The
line they write is the explicit one with a comment beside it saying which of the two shapes was
intended and why, so that the next person changing it has to argue with a sentence rather than notice
an absence.

**What degrades at scale.** The stateful side's failure is not gradual and that is what makes it
dangerous. Take a boundary serving clients that hold sessions and replace the process — a deploy, a
crash, an autoscaler reclaiming a quiet replica — and **every** one of them gets a `400` or a `404`
on its very next call, not some proportion of them. Meanwhile the ceiling that decides how many can
be held at once is not yours: this SDK's own defaults are `max_sessions=10000` and
`session_idle_timeout=1800` seconds, read from the constructor on this machine today, so one process
carries up to ten thousand pieces of invisible per-client state and silently discards any that has
been quiet. The stateless side holds zero, has no ceiling and has nothing to expire.

**The review comment.** "This is the boundary, so I want the transport decision on the page rather
than in the defaults. Write `stateless_http=` explicitly whichever way you mean it. And if you mean
`False`, then the deployment description in this pull request needs to say how requests are pinned to
a replica and what happens to an in-flight client during a deploy — because right now the answer is
`Bad Request: Missing session ID`, and we would find that out from a customer."

**The interview question.** "You have an MCP server behind a load balancer with two replicas and
clients are intermittently getting HTTP 400 with `Missing session ID`. Walk me through your
diagnosis. Then tell me the two ways to fix it, which one you would choose, and what each one costs
you on every request for the rest of the system's life."
