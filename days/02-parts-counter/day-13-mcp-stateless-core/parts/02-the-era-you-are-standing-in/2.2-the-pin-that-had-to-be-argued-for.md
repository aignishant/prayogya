## One-line answer

This project depends on `google-adk[mcp]==2.8.0` rather than plain `google-adk==2.8.0`, and the
square brackets are the whole point: `google-adk`'s `mcp<2` bound is declared only under its extras,
so `uv add "mcp==2.2.0"` beside a bare `google-adk` resolves cleanly, installs a version nothing can
use, and the failure arrives at import — once with an excellent message and once with an almost
invisible one.

## The idea

The works finally ordered a replacement for the board. The catalogue entry was clear about the thing
it was clear about: same wall bracket, same four bolt holes, same height. It arrived, it went up, the
bolts went in, and the fitter went home. Nothing in the delivery, the invoice or the catalogue was
wrong. Nobody had lied to anybody.

The first call came in the next morning, and the plug on the end of every one of three hundred
handsets did not fit the new jacks. The catalogue had said *bracket*, because the catalogue was about
brackets. What it should have said, in the one sentence that would have saved the week, is which
handsets the board accepts — and it did say that, further down, in the section describing the version
of the board that ships **with the handset kit**. The works had ordered the board on its own.

That is precisely, and not loosely, what happened here. The check that would have caught the problem
existed and was published. It simply did not apply to the thing that was ordered, and the ordering
tool — which is very good at finding contradictions, and finds them for a living — had no
contradiction in front of it to find. **This is the day's deliberate failure**, it is a real one that
cost real time on this machine before this day was written, and the reason it belongs at
`production` level is that nothing about it is a beginner's mistake: the resolver was right, the
metadata was right, the install was right, and the program was broken.

## The mechanism

`projects/02-parts-counter/pyproject.toml` — a marked diff against the version **day 11 printed
whole** in its hub §3. Two lines change and that is the entire file's difference:

```diff
 [project]
 name = "parts-counter"
 version = "0.1.0"
 requires-python = ">=3.12"
 dependencies = [
-    "google-adk==2.8.0",
+    "google-adk[mcp]==2.8.0",
+    "mcp==1.30.0",
 ]

 [dependency-groups]
 dev = [
     "pytest==9.1.1",
 ]
```

**Line by line:**

| Line | What it does, and the failure it prevents |
| --- | --- |
| `google-adk[mcp]` — the `[mcp]` **extra** | Turns on the optional dependency set in which `google-adk` declares `mcp>=1.24,<2`. Without the brackets that bound is not applied to this project at all, and an incompatible `mcp` installs silently. This is the line that makes the conflict findable. |
| `mcp==1.30.0` — named directly, and exactly | The extra would install *some* 1.x; naming the version makes it the same 1.x on every machine and every March. A floor here would reintroduce exactly the drift `PRIMER.md` §1 is about. |
| `==` on both, not `>=` | An application is deployed, not imported. A range hands the choice of what runs in production to whichever machine resolved it last, on whichever day. |
| `pytest==9.1.1` in `[dependency-groups]`, unchanged | Day 11's line, reprinted only so the diff has its surrounding context. A dev tool is not a dependency of the thing being shipped. |

> **Recap — a floor is not a pin.** `>=4.11.8` and `>=3.12` say what is *too old* and hand the actual
> choice to whichever machine resolves them, on whichever day. Three files answer three different
> questions: `pyproject.toml` records what you **asked for** and may be a range, `uv.lock` records
> what the asking **produced** — exact versions and hashes, including packages you never named — and
> `.python-version` records **which interpreter**. The test of whether you have pinned anything is to
> hand the folder to somebody next March and ask whether they get what you have.
> Self-contained version: `PRIMER.md` §1.
> Deep version, if you have the full plan:
> `days/00-foundry/day-03-keys-pinning-refusing-check/parts/02-the-pin-and-the-refusal/2.1-a-floor-is-not-a-pin.md`

Today adds a fourth question to that list, and it is the one P00 day 3 could not have asked because
P00 had no framework in it: **a pin you never applied is not a pin either.** `mcp<2` was published,
correct and public the entire time. It was simply attached to something this project had not asked
for.

### The bound, read out of the installed package

```console
$ uv run --frozen python -c "
from importlib.metadata import requires
for r in requires('google-adk'):
    if r.lower().startswith('mcp'): print(r)
"
mcp>=1.24,<2 ; extra == "all"
mcp>=1.24,<2 ; extra == "mcp"
mcp>=1.24,<2 ; extra == "test"
```

Three declarations, and the thing to notice is what follows every semicolon. `extra == "all"`,
`extra == "mcp"`, `extra == "test"` are **environment markers**: conditions under which the
requirement applies. All three conditions are false for a project that depends on plain
`google-adk`. So the number of times `google-adk` constrains `mcp` for such a project is not three.
It is **zero** — and asking for the pair therefore succeeds, quickly and quietly, with nothing to
report, because there is genuinely no conflict. Run in a throwaway project on this machine on
2026-09-10:

```console
$ uv add "google-adk==2.8.0" "mcp==2.2.0"
Resolved 67 packages in 1.27s
```

Sixty-seven packages, no warning, no conflict, no question. The environment that comes out of it
cannot run a line of this project.

### The loud half of the failure

With `mcp` 2.2.0 installed, the server from part 1.2 does not start, and the message is one of the
best pieces of error text in this whole curriculum:

```console
$ uv run --frozen python -c "from mcp.server.fastmcp import FastMCP"
Traceback (most recent call last):
  File "<string>", line 1, in <module>
  File ".../site-packages/mcp/server/fastmcp.py", line 16, in <module>
    raise ModuleNotFoundError(_MESSAGE, name=__name__)
ModuleNotFoundError: No module named 'mcp.server.fastmcp'. This is mcp 2.x, where FastMCP was renamed to MCPServer (from mcp.server.mcpserver import MCPServer) and other APIs changed; see the migration guide at https://py.sdk.modelcontextprotocol.io/v2/migration/#fastmcp-renamed-to-mcpserver or pin 'mcp<2' to keep running v1 code.
```

Look at the third frame before you read the message: `mcp/server/fastmcp.py` **exists** in 2.x, and
all it does is raise. Somebody kept the file solely so that the failure would land in the right
place with something useful to say. That is a deliberate act of hospitality towards people who have
not migrated yet.

Read what that message does, because it is worth copying the next time you rename anything. It names
the old symbol, names the new one, gives the exact import line to write instead, links the migration
page, and then — the part almost nobody does — tells you how to **not** migrate, by naming the pin
that keeps your existing code working. Somebody sat down and wrote that on purpose. A reader who
meets it is never confused for more than a moment.

### The quiet half

Now the same broken environment, on the client side. This is `google-adk`'s own MCP client, imported
by its real module path so the failure is visible:

```console
$ uv run --frozen python -c "from google.adk.tools.mcp_tool.mcp_toolset import McpToolset"
Traceback (most recent call last):
  File "<string>", line 1, in <module>
  File ".../site-packages/google/adk/tools/mcp_tool/mcp_toolset.py", line 39, in <module>
    from mcp.shared.session import ProgressFnT
ModuleNotFoundError: No module named 'mcp.shared.session'
```

That is clear enough — but it is not the import anybody writes. The import people write goes through
the package, and the package has this in it, verbatim, from the installed
`google/adk/tools/mcp_tool/__init__.py` in this project's environment:

```python
__all__ = []

try:
  from ._agent_to_mcp import to_mcp_server
  from .conversion_utils import adk_to_mcp_tool_type
  from .conversion_utils import gemini_to_json_schema
  from .mcp_session_manager import SseConnectionParams
  from .mcp_session_manager import StdioConnectionParams
  from .mcp_session_manager import StreamableHTTPConnectionParams
  from .mcp_tool import MCPTool
  from .mcp_tool import McpTool
  from .mcp_toolset import MCPToolset
  from .mcp_toolset import McpToolset

  __all__.extend([
      'adk_to_mcp_tool_type',
      'gemini_to_json_schema',
      'McpTool',
      'MCPTool',
      'McpToolset',
      'MCPToolset',
      'SseConnectionParams',
      'StdioConnectionParams',
      'StreamableHTTPConnectionParams',
      'to_mcp_server',
  ])

except ImportError as e:
  import logging

  logger = logging.getLogger('google_adk.' + __name__)
  logger.debug('MCP Tool is not installed')
  logger.debug(e)
```

**Line by line:** this is not this project's code — it is a dependency's, printed as evidence — and
four lines of it decide how the failure reaches you.

- `__all__ = []` **before the `try`** — so the module always imports successfully and always has a
  name list. When the block fails, that list stays empty and the module is a valid, importable,
  completely empty package. Nothing anywhere raises.
- `try:` around **ten imports at once** — any one of them failing loses all ten. `ProgressFnT` is the
  one that is missing under `mcp` 2.x, and it takes `McpToolset`, `StdioConnectionParams` and seven
  others down with it, none of which have anything wrong with them.
- `except ImportError as e:` — `ModuleNotFoundError` is a subclass of `ImportError`, so the missing
  module is caught here. This is the line that turns a precise diagnosis into a silence.
- `logger.debug('MCP Tool is not installed')` and `logger.debug(e)` — the real cause **is** recorded,
  and at `DEBUG`, which is not shown by default. So the true error exists, on this machine, in a log
  record nobody will see. The message it does show, incidentally, is also wrong about the situation:
  `mcp` is installed. It is the wrong major version, and the handler cannot tell those two apart.

The result is that `from google.adk.tools.mcp_tool import McpToolset` fails saying it cannot find
`McpToolset` — a name, in a package that exists, that you can see in the source with your own eyes —
and nothing in the failure mentions `mcp`, a version, or a bound. The good half of the day's failure
tells you exactly what to do. The quiet half sends you looking for a typo.

### Why the brackets are the fix

Because of what they change about **when** the mistake is caught.

| Without `[mcp]` | With `[mcp]` |
| --- | --- |
| `uv add "mcp==2.2.0"` succeeds | the resolver has two contradictory requirements and refuses |
| the environment is built and looks healthy | no environment is built |
| the failure appears at import, in two different places, one of them silent | the failure appears in a resolver, naming both packages and both bounds |
| the person debugging is reading their own code | the person debugging is reading the message |

Here is the right-hand column, run in the same throwaway project on the same day — the identical
request, with the brackets added:

```console
$ uv add "google-adk[mcp]==2.8.0" "mcp==2.2.0"
  × No solution found when resolving dependencies for split (markers:
  │ python_full_version >= '3.14'):
  ╰─▶ Because google-adk[mcp]>=2.8.0 depends on mcp>=1.24,<2 and your project
      depends on google-adk[mcp]==2.8.0, we can conclude that your project
      depends on mcp>=1.24,<2.
      And because your project depends on mcp==2.2.0, we can conclude that
      your project's requirements are unsatisfiable.
```

Every fact needed to fix it is in five lines: both packages, both bounds, and the chain of reasoning
that puts them in contradiction. Nothing was installed, so nothing has to be uninstalled, and nobody
spends an afternoon reading their own code.

That is the whole argument for the two characters. It does not make anything possible that was
impossible before; it moves a failure from run time to resolve time, and from a package's internals
to a message about packages. Blast radius before capability, as always: this is containment for a
dependency, which is a place people rarely think to put it.

## When it breaks

The pull request that caused this said `uv add mcp` and nothing else, and it went green, because at
the point it was written nothing in the project imported `McpToolset` yet. Here is what the next
person saw, days later, on the first line of code that did:

```console
$ uv run --frozen python -c "from google.adk.tools.mcp_tool import McpToolset"
Traceback (most recent call last):
  File "<string>", line 1, in <module>
ImportError: cannot import name 'McpToolset' from 'google.adk.tools.mcp_tool' (.../site-packages/google/adk/tools/mcp_tool/__init__.py)
```

The parenthesis even names the file that swallowed the cause — and opening
that file shows `McpToolset` imported on a line you can point at, which sends the reader off in
precisely the wrong direction. They read it as a name removed in an ADK upgrade, went to the release
notes, found `McpToolset` present and documented, and lost the rest of the afternoon before anybody thought to ask
what version of `mcp` was installed — a package that appears nowhere in the error, nowhere in the
traceback, and nowhere in the code they were reading. The smallest fix is
`uv add "google-adk[mcp]==2.8.0"`, which makes the resolver refuse to build that environment ever
again. The smallest *diagnosis*, if you are ever in that afternoon, is to import the failing module
by its full path — `google.adk.tools.mcp_tool.mcp_toolset` — which walks straight past the `except`
and shows you the real cause.

## In production

**What a senior writes instead.** They never depend on a framework's optional integration without
naming the extra that carries it. The habit is one question asked at `add` time: *does this package
have an opinion about the thing I am installing beside it, and is that opinion switched on for me?*
It takes one command to answer — read the requirements out of the installed distribution and look at
what follows the semicolons — and it is the difference between a resolver error and an afternoon.

**What degrades at scale.** The number here is small and it is the point: `google-adk` 2.8.0 declares
its `mcp` bound **three** times and applies it **zero** times to a project that has not asked for an
extra. Multiply that by a dependency tree of a few hundred distributions, each with its own extras,
and the amount of published, correct, entirely inert constraint in a typical environment is large
enough that "it resolved" means considerably less than people think it does. `mcp` 2.2.0 and 1.30.0
were released on the same day, 2026-09-07, so this was not a stale-index problem either: the newest
thing was simply the wrong thing.

**The review comment.** "This adds `mcp` as a direct dependency but leaves `google-adk` bare, which
means adk's `mcp<2` bound is not applied to us — it lives under an extra. Please change the
requirement to `google-adk[mcp]==2.8.0` so the resolver can actually refuse a bad pair, and add a
paragraph to `PACKAGES.md` saying why the pin is where it is. Right now a future `uv add mcp@latest`
goes green and breaks at import, and the ADK half of that break does not mention `mcp` at all."

**The interview question.** "A dependency of yours declares an upper bound on a package you are also
installing directly, your resolver reports no conflict, and the program fails at import. Explain how
that is possible, tell me the command you would run to confirm it, and tell me what you would change
so the resolver catches it next time."
