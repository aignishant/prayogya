## One-line answer

Everything parts 1.1 to 2.1 taught — `initialize`, `notifications/initialized`, capabilities agreed
once, a version countered rather than refused — was removed by the current specification revision
`2026-07-28`, and the fastest way to understand what it was *for* is to skip it against the server
you can still run and read what comes back.

## The idea

One year the site replaces the book with a badge.

You are handed a card at the main office, and printed on it are the things the desk used to tell
you: who you are, what trade, which permits you hold. Now every door reads the card. The hut by the
gate is not merely quieter — it is **gone**, and the sign that used to point at it now points at the
badge office. Nobody signs in, because nothing on the far side of any door depends on a record of
your having arrived. Each door decides, on its own, from what you are holding.

That is the current MCP revision, `2026-07-28`, and it did not soften the handshake or deprecate it.
It deleted it. From the revision's own changelog, verbatim:

> Make MCP stateless: remove the `initialize`/`notifications/initialized` handshake. Every request
> now carries its protocol version and client capabilities in `_meta`
> (`io.modelcontextprotocol/protocolVersion`, `io.modelcontextprotocol/clientCapabilities`). Clients
> SHOULD identify themselves on each request (`io.modelcontextprotocol/clientInfo`), and servers
> SHOULD identify themselves in each result's `_meta` (`io.modelcontextprotocol/serverInfo`). Version
> mismatches return `UnsupportedProtocolVersionError`
>
> — MCP specification, revision **`2026-07-28`**, *Key Changes*, major change 2

And the page that replaced the lifecycle page opens with six words that are the whole of this part:

> **There is no negotiation handshake.** Every request carries its protocol version, and the server
> accepts or rejects each request independently:
>
> — MCP specification, revision **`2026-07-28`**, `basic/versioning`

That page also gives the two words this curriculum will use for the rest of the boundary track, and
they are the specification's own, verbatim:

> * **Modern**: protocol versions that convey version, identity, and capabilities as per-request
>   metadata (revision `2026-07-28` and later).
> * **Legacy**: protocol versions that establish a session with an `initialize` handshake
>   (`2025-11-25` and earlier).
> * **Dual-era**: an implementation that supports both modern and legacy versions.
>
> — MCP specification, revision **`2026-07-28`**, `basic/versioning`, *Terminology*

Read the second bullet slowly. `2025-11-25` is the string part 2.1 watched this server hand back as
its latest. **By the current specification's own definition, everything this day has run is
legacy.**

And the hut really is gone. The path `.../specification/2026-07-28/basic/lifecycle` — the same path
that serves the three-phase lifecycle under `2025-06-18` — resolves at this revision to
`.../specification/2026-07-28/basic/versioning`. Fetched on 2026-09-10, it returns a page titled
*Versioning and Compatibility*. There is no lifecycle page at this revision, because there is no
lifecycle left to describe.

So why did you just spend a day learning it? Two reasons, and the second is the better one. First,
because `google-adk` 2.8.0 requires `mcp<2` and the 1.x SDK is a legacy-era implementation, so the
handshake is not history *in this project* — it is what runs when you type `./run probe`. Second,
because you cannot feel what a mechanism was for until you take it away, and taking it away is
something you can do right now, with one line.

## The mechanism

**The deliberate failure: skip the handshake.** One message, straight to work — no `initialize`, no
notification, exactly the way a modern client would open:

```console
$ cd projects/02-parts-counter
$ printf '%s\n' '{"jsonrpc":"2.0","id":1,"method":"tools/list"}' \
  | uv run --frozen python -m parts_mcp.server
Failed to validate request: Received request before initialization was complete
{"jsonrpc":"2.0","id":1,"error":{"code":-32602,"message":"Invalid request parameters","data":""}}
```

And with the two streams separated, because which stream carried which sentence is the whole lesson:

```console
$ printf '%s\n' '{"jsonrpc":"2.0","id":1,"method":"tools/list"}' \
  | uv run --frozen python -m parts_mcp.server 2>/dev/null
{"jsonrpc":"2.0","id":1,"error":{"code":-32602,"message":"Invalid request parameters","data":""}}
$ echo $?
0
$ printf '%s\n' '{"jsonrpc":"2.0","id":1,"method":"tools/list"}' \
  | uv run --frozen python -m parts_mcp.server 2>&1 1>/dev/null
Failed to validate request: Received request before initialization was complete
```

**Line by line:**

- **The request was refused, and that refusal is the answer to "what was the handshake for?"** The
  tools exist. The store is readable. Nothing is broken. The server declined because a rule about
  *order* was not satisfied, and order is the only thing a handshake has ever enforced.
- `"code": -32602, "message": "Invalid request parameters"` — and the parameters were **fine**. There
  were no parameters. The wire error names the wrong thing entirely, because `-32602` is the closest
  code the SDK has for "I would not accept this", and "you have not initialised" is not a category
  JSON-RPC has.
- `"data": ""` — an empty string where the useful half would go. Compare that with the example
  initialization error printed on the `2025-06-18` lifecycle page itself, which uses the same
  `-32602` and fills `data` with `{"supported": [...], "requested": ...}`. The code is identical; the
  diagnosis is absent.
- **The accurate sentence exists and went to the wrong audience.** `Received request before
  initialization was complete` is exactly what a developer needs, and it was written to standard
  error — the stream the stdio transport explicitly tells clients they may ignore. Day 16 takes
  standard error's role properly; here it is enough to notice that the good message and the message
  the client receives are two different messages.
- `echo $?` is `0`. The server did not fail; it answered. From the operating system's point of view
  nothing went wrong, which means no supervisor, no wrapper and no exit-status check anywhere will
  ever see this. Day 3's rule holds here too: the status is the verdict, and the verdict is "fine".
- **Now compare it with a completely different mistake.** Part 1.1 left `protocolVersion` out of a
  perfectly well-ordered `initialize`. Part 2.1 sent `null` in it. All three — a skipped handshake, a
  missing field, a wrong type — hand the client the identical line: `-32602`, `Invalid request
  parameters`, `data: ""`. Three unrelated bugs, one indistinguishable wire error, and the sentence
  that tells them apart on a stream nobody is required to read.

*Run on this machine on 2026-09-10: uv 0.12.3, CPython 3.12.12, `mcp` 1.30.0.*

### One honest correction to part 1.1

While causing the failure above, a second thing turned up, and it is recorded here rather than
tidied away. **Omitting `notifications/initialized` does not fail on this server.** Send
`initialize`, skip the notification, send `tools/list`, and the tool list comes back. The
specification does not require it to fail, and it says why — the constraint it writes is on the
*server*, not the client:

> * The client **SHOULD NOT** send requests other than pings before the server has responded to the
>   `initialize` request.
> * The server **SHOULD NOT** send requests other than pings and logging before receiving the
>   `initialized` notification.
>
> — MCP specification, revision **`2025-06-18`**, `basic/lifecycle`, *Initialization*

So the notification gates what the **server** may start doing, and this server — which initiates
nothing — has nothing to gate. Two of the three messages are enforced here; the third is a promise
that only matters to a server that talks first. That is a real property of a real implementation,
and a document that had asserted "all three are required" would have been tidier and wrong.

### What the modern answer looks like, and why you will not see it here

At `2026-07-28` a version the server cannot serve is not countered, ignored or reported as bad
parameters. It is a named error carrying the answer:

> If the server does not implement the requested version (whether the version is unknown to the
> server, or is a known version the server has chosen not to support), it **MUST** respond with an
> `UnsupportedProtocolVersionError` listing the versions it does support:
>
> — MCP specification, revision **`2026-07-28`**, `basic/versioning`

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "error": {
    "code": -32022,
    "message": "Unsupported protocol version",
    "data": {
      "supported": ["2026-07-28", "2025-11-25"],
      "requested": "1900-01-01"
    }
  }
}
```

That block is **quoted from the specification, not produced by this project**, and nothing in this
repository can produce it. `-32022` was allocated by the same revision, which partitioned the
JSON-RPC server-error range and renumbered `UnsupportedProtocolVersion` from `-32004` to `-32022`.
The pinned `mcp` 1.30.0 has no such error: its ceiling is `2025-11-25`, and part 2.1 watched it
counter rather than refuse. Everything in this repository is legacy-era, and the specification is
blunt about what that means when the two eras meet — from the compatibility matrix, verbatim, the row
that describes a client like ours against a server like the ones being written now:

> **Legacy** client, **Modern** server: Fails. stdio: the server rejects `initialize` with a JSON-RPC
> error; the exact code is implementation-defined (`initialize` is an unknown method and the request
> also lacks the required `_meta` fields). […] Legacy clients have no fall-forward mechanism.
>
> — MCP specification, revision **`2026-07-28`**, `basic/versioning`, *Compatibility Matrix*

**"Legacy clients have no fall-forward mechanism."** A modern client meeting an old server can probe
and step down. An old client meeting a new server can only fail, because nothing in the edition it
speaks describes the edition it met. That is the position this project's client is in, and knowing it
is worth more than pretending otherwise.

### The honest close

This project performs a handshake, and it will keep performing one, for a reason that has nothing to
do with the protocol being right: **`google-adk` 2.8.0 declares `mcp>=1.24,<2`**, so the newest MCP
SDK this project may install is the 1.x line, and the 1.x line is legacy-era. The full reasoning,
including why that bound sits behind an extra and fails silently when it is dodged, is in
`projects/02-parts-counter/PACKAGES.md`, and the structural decision is
`docs/adr/ADR-0005-mcp-era-gap-and-the-1x-pin.md`.

`PACKAGES.md` also carries the `TODO(me)` for the day this changes — re-check at the start of P03,
and when the bound widens, the move is named there. When that day comes, this part is the one that
gets deleted, and parts 1.1 and 1.2 get rewritten around `_meta`. **Write days you are willing to
delete.** A curriculum that never has to delete a page is one that stopped checking.

## When it breaks

This is what it looks like when a modern client meets this server, and it is worth causing once so
you recognise it later. Two streams, and the client only reads one:

```text
Failed to validate request: Received request before initialization was complete
{"jsonrpc":"2.0","id":1,"error":{"code":-32602,"message":"Invalid request parameters","data":""}}
```

Somebody upgraded a client library over a weekend, pointed it at an unchanged server, and got
`Invalid request parameters` on a request that has no parameters. They spent the evening checking
argument names, because the error told them to. The sentence naming the real cause was on the
server's standard error the whole time, in a subprocess whose output their client discarded. The
smallest fix is to capture and surface the server's standard error in the client's own logs; the real
fix is the era check the `2026-07-28` versioning page specifies, and neither the SDK nor this project
can do it yet.

## In production

**What a senior writes instead.** They pin the protocol revision in the same place they pin the
package, and they treat the pair as one decision. Concretely: `mcp==1.30.0` in `pyproject.toml` and a
row in `PACKAGES.md` recording that the revision on the wire is `2025-11-25` while the published
current revision is `2026-07-28` — so the gap is a written-down fact with a date on it rather than
something a new joiner discovers by reading the specification and getting confused. A dependency pin
without the revision it implies is half a pin.

**What degrades at scale.** The handshake is **three messages per connection**, and its cost is a
function of how you connect rather than of how much work you do. A client that opens one stdio
process and asks a thousand questions pays three; a client that opens a fresh process per question
pays three thousand, plus a thousand interpreter start-ups, to do identical work. That ratio —
**three per connection against three thousand** — is the entire argument the `2026-07-28` reframe
makes, one revision before anybody had to make it by hand.

**The review comment.** "This client hard-codes `2025-06-18` in the `initialize` params and never
reads the returned version, and our `PACKAGES.md` says the SDK's ceiling is `2025-11-25` while the
current spec revision is `2026-07-28`. Three different dates in one system and none of them checked
against another. Please put the supported set in one constant, assert on the negotiated result, and
link ADR-0005 from the module docstring so the next person knows this is deliberate."

**The interview question.** "A protocol you depend on removes its connection handshake and moves
per-connection state onto every request. Your framework pins you to a client that cannot speak the
new revision. Walk me through what you do on Monday — and say specifically what you would write down,
where, and what would have to become true before you migrate."
