## One-line answer

The `capabilities` object each side sends during the handshake is a declaration made **before**
anybody asks for anything, so that neither side ever has to probe, guess or discover by failure —
and because it is declared once, it is a fact about a *connection*, which is precisely the thing a
stateless protocol cannot have.

## The idea

Back at the site hut. The board on the wall behind the desk is not a list of what happened today; it
is a list of what is *in force* today. Hot work suspended. East stair closed. Scaffold on the north
face tagged. You read it on the way in, and from then on you plan your work around it without
asking anybody anything.

The board is doing something subtle and worth naming. It is not preventing you from striking an arc
— nothing physically stops you. It is making it **your fault** if you do, and, more usefully, it is
removing every reason for you to walk to the desk and ask. The alternative to a board is a hundred
people a day asking the same three questions, or, worse, a hundred people finding out by trying.

That exchange has a name in this protocol: **capability negotiation**. Each side, in the handshake,
sends an object describing the optional features it supports. The server's goes in its `initialize`
result; the client's goes in the `initialize` request's `params`. Neither side asked. Both sides now
know, for the life of the connection, and no message afterwards has to carry the question again.

The revision this project runs, labelled `2025-06-18`, states the effect of that plainly:

> Client and server capabilities establish which optional protocol features will be available during
> the session.
>
> — MCP specification, revision **`2025-06-18`**, `basic/lifecycle`, *Capability Negotiation*

Two words in that sentence carry the whole idea, and they are the two that part 2.2 comes back to.
**"Optional"** — capabilities exist because not every server does everything, and a protocol whose
features were all mandatory would need no negotiation at all. And **"the session"** — the scope of
the promise. The board is up for today. Not for this question; for today.

Hold on to that second word. Everything in this part is true of a connection, and day 13 has already
argued that a connection is exactly what a stateless boundary refuses to have.

## The mechanism

This is what the server day 14 built admits to, taken from the `initialize` result part 1.1 printed
— reproduced here as a table rather than as JSON, because the flags matter and the punctuation does
not:

| Key | Value here | What the server has promised by saying it |
| --- | --- | --- |
| `experimental` | `{}` | No non-standard features. A client that special-cases a vendor extension will find nothing here and must fall back to the standard path. |
| `prompts.listChanged` | `false` | The server offers prompts, and will **never** send `notifications/prompts/list_changed`. A client that waits for one waits forever; if it wants a fresh list it must ask again. |
| `resources.listChanged` | `false` | Same promise for resources: the list can change and you will not be told. |
| `resources.subscribe` | `false` | The server will not let a client subscribe to one resource's changes. This is the strongest flag on the board, because it is the one that turns a whole method off. |
| `tools.listChanged` | `false` | The server offers tools, and will never announce that its tool list changed. Day 17's client fetches the list once. |

**Line by line — what "false" is actually saying.** Every one of those flags is a **negative
promise**, and a negative promise is more useful than it looks: it tells the client which code path
it may delete. `listChanged: false` does not mean *the list never changes*. It means *you will not be
told when it does*, which is a statement about the server's notifications and not about its
inventory. The correct client response is to decide, once, whether staleness matters — and if it
does, to poll, because the alternative has just been withdrawn.

`subscribe: false` is the one you can watch. Ignore it and call the method anyway:

```console
$ cd projects/02-parts-counter
$ printf '%s\n%s\n%s\n%s\n' \
 '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"by-hand","version":"0"}}}' \
 '{"jsonrpc":"2.0","method":"notifications/initialized"}' \
 '{"jsonrpc":"2.0","id":4,"method":"resources/subscribe","params":{"uri":"file:///nothing"}}' \
 '{"jsonrpc":"2.0","id":5,"method":"prompts/list"}' \
 | uv run --frozen python -m parts_mcp.server 2>/dev/null
{"jsonrpc":"2.0","id":1,"result":{"protocolVersion":"2025-06-18","capabilities":{"experimental":{},"prompts":{"listChanged":false},"resources":{"subscribe":false,"listChanged":false},"tools":{"listChanged":false}},"serverInfo":{"name":"parts-mcp","version":"1.30.0"}}}
{"jsonrpc":"2.0","id":4,"error":{"code":-32601,"message":"Method not found"}}
{"jsonrpc":"2.0","id":5,"result":{"prompts":[]}}
```

**Line by line:**

- `"id": 4` came back as an **error**, and the error is `-32601 Method not found` — the JSON-RPC code
  for a method the server does not implement. The board said `subscribe: false`; the method is
  genuinely not there. The capability flag and the runtime behaviour agree, which is the entire
  reason a client can trust the board rather than probing.
- `"id": 5` was answered **normally, immediately afterwards**. That matters: the failed subscribe did
  not poison the connection. This is a per-request error, not a connection error, and the fourth line
  proves it rather than asserting it.
- `{"prompts":[]}` — an empty list, not an error. The server declared a `prompts` capability and has
  no prompts registered, and those are different statements. *I can do this and have none* is a valid
  answer; *I cannot do this* is `-32601`. A client that treats both as failure will refuse to work
  with a perfectly good server that simply has nothing in one drawer.
- The client's own capabilities were `{}` — the empty object in message one. That declares **no**
  roots, **no** sampling, **no** elicitation. The consequence is not visible in this transcript,
  because the server does not echo what the client said; it is visible in what the server may never
  do afterwards. A server that wanted this client to run a model call on its behalf has been told,
  before it could ask, that this client will not.

That last point is the one worth sitting with. **The client's half of the board is the half you
cannot see from outside**, and it is the half that constrains the server. It was sent once, in one
field, at the start, and every later message in the connection is interpreted against it.

*Run on this machine on 2026-09-10: uv 0.12.3, CPython 3.12.12, `mcp` 1.30.0.*

### And this is exactly the part that did not survive

A capability declared once, at the start, is a fact about a **connection**. It is stored on one side,
remembered by the other, and consulted by messages that do not carry it. Day 13's whole argument was
that a stateless boundary keeps nothing between one request and the next — so a stateless boundary
cannot hold a board on a wall, because there is no wall.

The current specification revision, **`2026-07-28`**, resolved that by moving the board onto every
request. From its changelog, verbatim and labelled:

> Make MCP stateless: remove the `initialize`/`notifications/initialized` handshake. Every request
> now carries its protocol version and client capabilities in `_meta`
> (`io.modelcontextprotocol/protocolVersion`, `io.modelcontextprotocol/clientCapabilities`).
>
> — MCP specification, revision **`2026-07-28`**, *Key Changes*, major change 2

And its front page describes the base protocol as, verbatim:

> JSON-RPC message format · **Stateless, self-contained requests** · **Per-request capability
> negotiation**
>
> — MCP specification, revision **`2026-07-28`**, front page

Day 13 taught that reframe and owns it; this part only notes where its consequence lands. Every
worker now carries a badge that states the permits, and it is read at every door instead of once at
the gate. Nothing is negotiated less — it is negotiated more often, and by messages that can be
answered by any replica, in any order, with nothing remembered in between.

**Do not go looking for `_meta` in this project.** The stack here is `mcp` 1.30.0, pinned because
`google-adk` 2.8.0 requires `mcp<2`, and it cannot speak that revision. Part 2.2 is where that gap is
faced squarely instead of in a paragraph.

## When it breaks

A client that ignores the board and probes instead is the failure this part exists to prevent, and
the wire tells you nothing helpful when it happens:

```text
{"jsonrpc":"2.0","id":4,"error":{"code":-32601,"message":"Method not found"}}
```

Two words, no `data`, no hint that a flag in the handshake already said this. Somebody wired a
resource watcher on a Friday, tested it against a server with `subscribe: true`, shipped it against
one with `subscribe: false`, and spent the evening reading `Method not found` and checking their
method spelling. The smallest fix costs one line: read `capabilities.resources.subscribe` out of the
`initialize` result you already received, and refuse to start the watcher when it is false — with an
error that says *this server does not support subscriptions*, which is the sentence the wire will
never say for you.

## In production

**What a senior writes instead.** They store the `initialize` result on the client object and branch
on it, rather than calling methods hopefully and catching `-32601`. Concretely: one field on the
client holding the server's capabilities, and every optional feature guarded by a read of it at
start-up — so an unsupported feature is a clear refusal at connect time and never an error in the
middle of a user's request. The rule underneath: **a capability check belongs where the connection is
made, not where the feature is used.**

**What degrades at scale.** `listChanged: false` moves the cost of freshness onto the client, and it
multiplies by client count. One client that must not serve a stale tool list has to call `tools/list`
once per poll cycle; **a hundred connected clients make a hundred of those calls per cycle**, all of
them returning the identical unchanged list, where a `listChanged: true` server would have sent zero
messages until something actually changed. The flag is one boolean and it is the difference between
traffic proportional to the number of clients and traffic proportional to the number of changes.

**The review comment.** "We call `resources/subscribe` unconditionally and catch the error. That
turns a documented capability check into an exception handler, so a genuine transport failure and a
server that simply doesn't do subscriptions land in the same `except` — please read
`capabilities.resources.subscribe` from the handshake result and fail fast at connect time."

**The interview question.** "A protocol declares optional features once, at connection set-up. Name
two things that becomes impossible to do afterwards, and explain what a stateless redesign has to do
with those declarations to keep them meaningful."
