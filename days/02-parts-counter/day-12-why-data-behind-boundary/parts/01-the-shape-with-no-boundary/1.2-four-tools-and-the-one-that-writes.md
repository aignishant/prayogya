## One-line answer

Three of this project's four tools answer questions and one of them changes the inventory, and the
difference is not a matter of degree: a wrong answer is corrected by the next question, while a wrong
adjustment outlives the conversation and leaves behind exactly one JSON line on this process's
standard error and nothing else.

## The idea

Stand in the stockroom doorway and watch what people actually do in there. Three of the four things
are questions. *Do we carry an air filter for this?* *How many rear pads are on the shelf?* *Which
shelf is the belt kit on?* Every one of those can be got wrong and it costs nothing much, because the
person who got a wrong answer is standing right there and asks again, or walks to the shelf and
looks. The room forgives being misread. Nothing about the room changed while they were reading it.

The fourth thing is not a question. Somebody takes a belt kit off the shelf and crosses out the
number on the card. That act has a property none of the questions have: **it is still true
tomorrow.** If they took the wrong thing, or crossed out the wrong card, or took two and wrote down
one, the room now disagrees with the world and it will keep disagreeing until somebody counts. The
person who did it has gone back to the workshop. There is no note saying it was them, no second pair
of eyes, and — this is the part that matters most — nobody who was not standing in that doorway has
any way of finding out that the number moved at all.

That asymmetry is the shape of this file. `parts_counter/tools.py` holds four functions. Three read
and one writes, and the three that read are the easy ones: their worst failure is a wrong answer,
and the next question corrects it. The one that writes can be wrong in a way that survives the
conversation that caused it, and there is nothing in the file to catch it — **no record of who
asked, no second opinion, and no way for anything outside this process to learn it happened.**

Nothing here is a mistake, and it is worth being exact about that, because the temptation on reading
a day like this one is to go looking for the bad line. Every function is short. Every one is typed.
Every one returns a plain dictionary that turns into JSON without ceremony. Three of them handle a
part number that does not exist and say so usefully. The file would pass review. Today's subject is
what is **missing** rather than what is wrong, and the missing things are all the same kind of thing:
they are all things that live outside a single Python process.

One more thing to notice before the code, because it changes how you read the docstrings. These
functions are going to be handed to a model, and the model never sees the code. It sees a
declaration built by reading the function — the name, the parameter types, and the docstring as the
description. So the docstrings below are not written for us. They are written for the model, and
sentences like *An empty list is a valid answer* and *Only call this when the person has clearly
asked for the count to change* are in there because they are the only place that guidance can live.

> **Recap — a tool declaration is derived, not written.** The model is given a name, a description
> and a JSON Schema for the arguments; ADK builds all three from the function object itself — name
> from `__name__`, schema from the type hints and defaults, description from the docstring. A
> parameter with no type hint produces a property with no `type`, which constrains nothing, and a
> per-argument description has nowhere to live in a derived declaration, so guidance about an
> argument belongs in the docstring. Self-contained version: `PRIMER.md` §4.

## The mechanism

`projects/02-parts-counter/parts_counter/tools.py`, whole file:

```python
# parts_counter/tools.py
"""The four things the counter can do — and one of them writes.

Three reads and a write, and the write is why this project has a boundary day. A tool that only
answers questions is a tool whose worst failure is a wrong answer. A tool that changes the
inventory can be wrong in a way that outlives the conversation, and there is nothing in this file
to stop it: no record of who asked, no second opinion, and no way for anything outside this process
to know it happened.

Nothing here is a mistake. Every function is short, typed and documented, and the whole file would
pass review. Day 2 is about what is missing rather than what is wrong.

ADK derives each declaration from the signature and the docstring (P01 day 4), so the docstrings
below are written for the model and not for us.

All data is synthetic.
"""

from __future__ import annotations

from typing import Any

from parts_counter import store
from parts_counter.util.logging import log


def find_part(query: str) -> dict[str, Any]:
    """Find parts whose number or name matches a query. An empty list is a valid answer."""
    hits = store.find(query)
    return {"query": query, "count": len(hits),
            "hits": [{"part_no": p["part_no"], "name": p["name"]} for p in hits]}


def stock_level(part_no: str) -> dict[str, Any]:
    """Return how many of one part are on hand, and whether that is below its reorder point."""
    try:
        part = store.get(part_no)
    except store.PartNotFound:
        return {"error": f"no part numbered {part_no!r}",
                "known": [p["part_no"] for p in store.all_parts()]}
    return {"part_no": part["part_no"], "on_hand": part["on_hand"], "unit": part["unit"],
            "reorder_at": part["reorder_at"], "below_reorder": part["on_hand"] <= part["reorder_at"]}


def bin_location(part_no: str) -> dict[str, Any]:
    """Return the bin a part is stored in, so somebody can walk to it."""
    try:
        part = store.get(part_no)
    except store.PartNotFound:
        return {"error": f"no part numbered {part_no!r}",
                "known": [p["part_no"] for p in store.all_parts()]}
    return {"part_no": part["part_no"], "bin": part["bin"], "name": part["name"]}


def adjust_stock(part_no: str, delta: int) -> dict[str, Any]:
    """Change the on-hand count of a part by delta. Use a negative delta to issue stock.

    Only call this when the person has clearly asked for the count to change. Reading a level is
    stock_level; this is the tool that alters the record.
    """
    try:
        before = store.get(part_no)["on_hand"]
        part = store.adjust(part_no, delta)
    except store.PartNotFound:
        return {"error": f"no part numbered {part_no!r}",
                "known": [p["part_no"] for p in store.all_parts()]}
    # The only trace this write leaves anywhere, and it goes to this process's stderr. Day 2 is
    # about who else needed to know and had no way of finding out.
    log("stock.adjusted", part_no=part["part_no"], delta=delta,
        before=before, after=part["on_hand"])
    return {"part_no": part["part_no"], "before": before, "after": part["on_hand"],
            "unit": part["unit"]}


REGISTRY = {f.__name__: f for f in (find_part, stock_level, bin_location, adjust_stock)}
```

**Line by line:**

- `from parts_counter import store` and `from parts_counter.util.logging import log` — two imports,
  both inside this project. `logging.py` was printed whole, at full depth, by **day 11**; it is not
  reprinted here. Nothing in this file reaches outside `projects/02-parts-counter/`, which is the
  rule that makes this project runnable on its own.
- Every function returns `dict[str, Any]` and never a bare string or a custom object. The return
  value is going into a tool-result turn and from there into JSON, so a dictionary is the shape that
  survives the trip without anybody writing a serialiser. It also means a caller who is not a model
  — the driver, a test, you at a prompt — gets something they can index rather than something they
  have to parse.
- **Every function takes flat, primitive arguments** — a `str`, or a `str` and an `int`. Nothing
  takes a nested object, a list or a dataclass. That is not laziness: the declaration the model gets
  is a JSON Schema derived from these hints, and the flatter the schema the smaller the number of
  ways the model can fill it in wrongly. Complexity in an argument is complexity a model has to get
  right on the first attempt with no feedback.
- `find_part` returns `count` **beside** `hits`, which is redundant — the list has a length. It is
  there because the model reads the result as text and a stated count is far harder to misread than
  a list it has to measure. Cheap redundancy aimed at the actual consumer.
- `find_part` returns `part_no` and `name` for each hit and **not** the whole part record. The
  bin and the on-hand count are two other tools' answers. A search tool that returns everything
  teaches the model that it never needs the other tools, and then the model stops calling them, and
  then a change to what "in stock" means has to be made in two places.
- `find_part` **echoes `query` back** in the result. When the transcript is read later — by you, by
  an eval, by whoever is working out what went wrong — the result carries the question it answered
  instead of being a floating answer that has to be paired up with a call three lines above it.
- The docstring's *An empty list is a valid answer* exists because of what a model does with an
  empty result otherwise. Handed `{"count": 0, "hits": []}` with no guidance, the pull towards
  producing a helpful-sounding answer anyway is real, and this sentence is the cheapest available
  counterweight. It is a line of documentation doing the job of a guardrail, which is exactly what a
  derived declaration forces you into.
- `stock_level` and `bin_location` **catch `store.PartNotFound` and return an error dictionary**
  rather than letting the exception escape. Both choices are defensible and this one is right for a
  tool: an exception crossing back into the framework becomes a failed turn, whereas a returned
  error is a fact the model can read and act on — usually by trying a different part number.
- The error dictionary carries `known`, the list of every part number this project has. That is the
  difference between "no" and "no, and here is what there is": the model's next call has a chance of
  being right rather than being another guess. It is affordable because the inventory is six parts,
  and it is the first thing that has to change when it is ten thousand.
- `{part_no!r}` uses `repr`, so the message quotes the value. `no part numbered 'SPK-9999 '` shows
  the trailing space that `no part numbered SPK-9999` would hide, and a trailing space is exactly
  the kind of thing a model's argument arrives with.
- `below_reorder` is **computed in the tool**, not left to the caller. `on_hand <= reorder_at` is a
  business rule, and the moment the model is asked to apply it from two raw numbers it will
  eventually apply it as `<`. A rule that has one home has one behaviour.
- `stock_level` returns `unit` alongside the count so the answer can be "four sets" rather than "4".
  The tool's job is to make the correct sentence easy to say.
- **`adjust_stock` is the write, and everything about it is different.** Its docstring is two
  paragraphs where the others get one line, and the second paragraph — *Only call this when the
  person has clearly asked for the count to change* — is a policy sentence aimed squarely at the
  model. There is nowhere else to put it. There is no confirmation step, no approval gate and no
  second opinion in this project; the entire defence against an unwanted write is a sentence in a
  docstring, and naming that out loud is the honest version of describing this file.
- `before = store.get(part_no)["on_hand"]` reads the count first so the result can report both
  `before` and `after`. Notice the cost: this is a **second whole-file read**, so one adjustment is
  read, read, write. Notice also the gap it opens — `get` and `adjust` are two separate reads of the
  same file, and nothing holds it still between them. Part 2.1 is about what fits in that gap.
- Both calls sit inside **one** `try`, and only `store.PartNotFound` is caught. Anything else — a
  corrupt file, a bad type, a full disk — propagates. That is the correct instinct and it is worth
  saying why: a tool that catches everything reports every failure as a normal, expected result, and
  the model then reasons about a disk error as though it were a business outcome.
- The comment above `log(...)` is the most important comment in this project, because it names a
  gap rather than explaining a line: **this is the only trace the write leaves anywhere.** One JSON
  object, on this process's standard error, gone when the terminal scrolls.
- `log("stock.adjusted", ...)` is called with `part_no`, `delta`, `before` and `after` — the four
  values you would need to reconstruct what happened. Look at what is **not** there: who asked. Not
  because somebody forgot, but because this process does not know. There is no user, no session and
  no request identifier reaching this function, so the record cannot carry one.
- The event name is `stock.adjusted` — dotted, past tense, naming a thing that happened rather than
  a thing being done. Past tense because the write has already succeeded by the time this line runs;
  a log line saying `adjusting` that appears after the fact is a small lie that costs somebody an
  hour when they are reading records at speed.
- `REGISTRY = {f.__name__: f for f in (...)}` builds the name-to-function map **from the function
  objects**, so a rename cannot leave a stale string behind. The alternative — a hand-written dict
  with quoted keys — is two places to change and one of them is not checked by anything.

**Line by line:**

- `find_part('filter')` matched on the **name**, not the number: neither `FLT-0071` nor `FLT-0072`
  contains the word "filter" in its part number. That is `store.find` checking both fields, and it
  is what makes the tool usable by somebody who knows what the thing is called and not what it is
  numbered.
- `"below_reorder": true` on the rear brake pads — four on hand against a reorder point of six. The
  tool answered the question that was asked and the one that follows from it in the same breath.
- Three calls, three results, and **nothing about the inventory changed**. Run any of them again and
  you get the same answer. That is the property the write does not have.

Now the write, and everything it leaves behind. The two adjustments cancel each other out, so the
inventory ends where it started:

```console
$ uv run --frozen python -c "
import json
from parts_counter import tools
print(json.dumps(tools.adjust_stock('BLT-0310', 2)))
print(json.dumps(tools.adjust_stock('BLT-0310', -2)))
"
{"at": "2026-09-09T18:47:14.534+00:00", "event": "stock.adjusted", "part_no": "BLT-0310", "delta": 2, "before": 0, "after": 2}
{"at": "2026-09-09T18:47:14.536+00:00", "event": "stock.adjusted", "part_no": "BLT-0310", "delta": -2, "before": 2, "after": 0}
{"part_no": "BLT-0310", "before": 0, "after": 2, "unit": "kit"}
{"part_no": "BLT-0310", "before": 2, "after": 0, "unit": "kit"}
```

**Line by line:**

- **The four lines are not in the order they were produced.** The two `stock.adjusted` records came
  first, one from each call, and the two `print` lines came after — because the records go to
  **standard error** and the prints go to **standard output**, and the two streams are buffered
  differently. What you are looking at is the shape of the whole problem in a terminal: the record
  of the write and the answer to the caller travel by different roads and arrive out of order.
- Each record carries `at`, an explicit UTC timestamp with an offset, from `util/logging.py`. It is
  the only thing in the whole system that would let two of these be ordered against each other, and
  it only works because the writer refused to use a naive local time.
- `before: 0, after: 2` then `before: 2, after: 0`. Read together, the two records tell the entire
  story of what happened to the belt kit. **That is the audit trail, in full.** An **audit trail** is
  a durable, ordered record of every change, kept somewhere a reader other than the writer can get
  at it — and what this system has instead is two lines on one process's standard error, which is
  gone when the terminal scrolls and was never visible to anybody who was not attached to it.
- Nothing in either record says **who asked**. Not a user, not a session, not a request. That field
  is absent because there is no value to put in it: nothing upstream of `adjust_stock` passes an
  identity down, and a function cannot log what it was never told.
- The returned dictionary carries `before` and `after` too, so the caller's own answer is
  self-explaining — "the belt kit went from zero to two" — rather than the bare new number, which is
  useless to anybody who did not know the old one.

## When it breaks

`delta: int` is a type hint, and the schema the model is given is derived from it — but the hint is
a description of the argument, not a guard on it. Nothing between the model and the function checks
that what arrived is actually an integer. Hand it the string `"-1"`, which is what a model produces
perfectly often, and it gets as far as the arithmetic before anything notices:

```traceback
  File "C:\...\parts_counter\tools.py", line 63, in adjust_stock
    part = store.adjust(part_no, delta)
           ^^^^^^^^^^^^^^^^^^^^^^^^^^^^
  File "C:\...\parts_counter\store.py", line 70, in adjust
    part["on_hand"] = part["on_hand"] + delta
                      ~~~~~~~~~~~~~~~~^~~~~~~
TypeError: unsupported operand type(s) for +: 'int' and 'str'
```

Somebody sees that in a log on a Friday and reads it as a bug in the store, because the store is
where the traceback ends — and spends an hour there before noticing that the value came in from
outside and was never checked at any point on the way. The fix is not in `store.adjust`. It is one
`isinstance` check at the top of `adjust_stock`, in the function that sits at the edge, which is the
general shape of the answer: **validate where the untrusted value arrives, not where it finally
explodes.** Notice what saved the file here: the exception was raised before `_write` was reached, so
the inventory was untouched. That was luck of ordering rather than a design that protects it.

## In production

**What a senior writes instead.** They separate the four tools by what they can do, and they say so
in the code rather than in a docstring: the three reads go to one agent or one permission set, and
the write goes behind something that can refuse — an allowlist, an approval step, or at minimum a
distinct credential. They also add the `isinstance` check and an idempotency key, so that the same
adjustment applied twice does not move the count twice. And the write's record goes somewhere a
second process can read it, because a record on standard error is a record that exists only for
whoever is watching.

**What degrades at scale.** The number is **one**. Exactly one process can see that a write
happened: the one that made it. Every additional consumer of this inventory — a dashboard, a nightly
report, a second agent, the finance system that wants to know why the count moved — sees zero of the
adjustments, for ever, no matter how many there are. That number does not get worse gradually; it is
already as bad as it goes, and it stays there until something outside this process can read the
record.

**The review comment.** "Three of these are safe to retry and one of them is not, and nothing in the
file distinguishes them. `adjust_stock` needs, in order: a type check on `delta` before it reaches
the store, an identity on the record so we can answer 'who moved this', and somewhere for that
record to go other than stderr. Right now the only thing standing between a misread question and a
changed inventory is a sentence in a docstring, and I would like that written in the pull request
description so that we are all agreeing to it on purpose."

**The interview question.** "You are exposing four functions to a model as tools. Three read and one
writes. Describe, concretely, what you would do differently for the write — in its declaration, in
its implementation, in what it logs, and in what stands in front of it — and say which of those you
would insist on before the first deployment and which can wait."
