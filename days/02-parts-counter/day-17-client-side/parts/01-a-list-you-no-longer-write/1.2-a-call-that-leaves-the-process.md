## One-line answer

`await toolset.get_tools()` is not a lookup — it launches the server, completes whatever that server
expects before it will talk, asks it `tools/list`, and hands back objects; and when one of those
objects is called, what comes back is not the tool's return value but an **envelope** around it,
because the value was serialised on the way out of the other process and this side is what unwraps
it.

## The idea

You have rung the number. Somebody picks up, and the first thing you hear is not their voice — it is
the room. A trolley going past. Somebody two desks away saying a part number out loud. That noise is
not information you asked for and it is not a problem; it is proof you are talking to somewhere else.
If you were reading a list off your own desk there would be no room behind it.

Then you ask what they stock, and they read you four things. You did not choose those four, you did
not maintain them, and you would not have known if there had been five. You write them down as you
hear them, and the list you now hold is a copy of an answer, not a copy of a file.

Then you ask for one of them by name — how many timing belt kits are on the shelf — and here is the
bit that is easy to miss on a phone call and impossible to miss over a protocol. **You do not receive
the shelf.** You receive somebody's account of the shelf: a sentence, spoken, that you then have to
turn back into a number. If the answer had been a whole page of detail, they would still have had to
read it to you one word at a time, and you would still have had to write it down and make sense of it
at your end. Nothing crossed that line except text.

That is the entire content of this part, and it holds exactly for a tool call across a process
boundary. The tool on the other side returns a Python `dict`. A `dict` cannot cross a pipe. What
crosses is bytes, and what arrives here is a structure with the tool's answer **inside** it —
serialised on the way out, labelled with whether it went well, and unwrapped on this side. The
protocol calls that structure the tool result; day 14 is where its fields were taken apart, in
`days/02-parts-counter/day-14-server-skeleton-first-tool/`. This part is about *where the unwrapping
happens*, which is here, on the client, in your process, in the object your agent is holding.

One more thing to notice while the receiver is still against your ear: the noise from the room and
the answer to your question come down two different channels, and only one of them is the answer.
Confusing the two is a real and common bug, and the specification is explicit about it. That comes
back at the end of the mechanism.

## The mechanism

The driver gets one new subcommand. This is a marked diff against `projects/02-parts-counter/run.py`
as **day 11 part 2.2** printed it whole — with the docstring rows and the `serve_mcp` cases that
**days 14 and 16** added shown as unchanged context, because this project already printed those and
a file printed twice is a bug:

```diff
--- projects/02-parts-counter/run.py    as day 11 part 2.2 printed it, plus the rows days 14 and 16 added
+++ projects/02-parts-counter/run.py    after today
 """This project's own driver. It depends on nothing above this folder.

     python run.py check          the gate: config, pins, the registry, and the tests
     python run.py parts <query>  find parts, through the boundary's own tool
     python run.py race           day 2's concurrent-write demonstration, re-run against the
                                  store the boundary owns
     python run.py mcp            run the boundary server on stdio
     python run.py mcp --http     run the same server on Streamable HTTP at :8090/mcp
+    python run.py probe          list and call the boundary's tools across a real process line
 """

 # ── unchanged from day 11 part 2.2: the six check_* functions, CHECKS, check(), parts(), race() ──
 # ── unchanged from day 14 and day 16: serve_mcp() ──

+def probe() -> int:
+    """List and call the boundary's tools over stdio. Proves the line is real, needs no key."""
+    import asyncio
+    import json
+
+    from parts_counter.util import mcp as client
+
+    async def go() -> None:
+        toolset = client.over_stdio()
+        try:
+            tools = await toolset.get_tools()
+            print(f"{len(tools)} tool(s) fetched from the server:")
+            for tool in sorted(tools, key=lambda t: t.name):
+                print(f"  {tool.name}")
+            print()
+            result = await tools[0].run_async(
+                args={"part_no": "BRK-0143"} if tools[0].name == "stock_level" else {},
+                tool_context=None)
+            print("one call, returned across the boundary:")
+            print(" ", json.dumps(result)[:200])
+        finally:
+            await toolset.close()
+
+    asyncio.run(go())
+    return 0
+

     match argv[1:]:
         case ["check"]:
             return check()

         case ["race"]:

         case ["mcp"]:

         case ["mcp", "--http"]:

+        case ["probe"]:
```

**Line by line:**

- `import asyncio`, `import json` and `from parts_counter.util import mcp as client` are **inside the
  function**, not at the top of the file. That is the same decision day 11 made for `parts()` and
  `race()` and it is load-bearing here for a new reason: `run.py check` must be able to report that
  the framework is missing, and a module-level `from parts_counter.util import mcp` would make
  `run.py check` fail at import with a traceback about `google.adk` instead of a `RED` line about
  what is wrong. **A gate that cannot start cannot report.**
- `as client` — the alias exists because `parts_counter.util.mcp` and the third-party package `mcp`
  would otherwise be the same name in this file. Naming it `client` also says which half of the
  protocol this is: the boundary is the server, this is the client.
- `async def go()` nested inside a synchronous `probe()`, with one `asyncio.run(go())` at the bottom
  — one event loop, at the edge, in the function the CLI calls. Async is contagious upwards and the
  cure is a single entry point rather than an `async def main`.
- `toolset = client.over_stdio()` — no `await`. Part 1.1's point, arriving as syntax: construction is
  free and contacts nothing, which is why the next line is where everything actually happens.
- `tools = await toolset.get_tools()` — **the whole subject of this part, in one call.** Four things
  happen behind it, in order: the client launches `parts_mcp.server` as a subprocess with the command
  and working directory part 1.1 pinned; it completes the exchange the server requires before it will
  answer anything, which for this stack is the `initialize` / `notifications/initialized` handshake
  taught in `days/02-parts-counter/day-15-lifecycle-handshake-history/`; it sends `tools/list`, whose
  request and response shape are `days/02-parts-counter/day-14-server-skeleton-first-tool/`; and it
  turns each `Tool` in the reply into an object with a `name`, a schema and a `run_async`. **Not one
  of those four is visible in this line.** That is the trade the toolset makes.
- `try: ... finally: await toolset.close()` — the `finally` is not tidiness. `over_stdio` launched a
  process; if the demo call raises and nothing closes the toolset, the interpreter it started is
  still there. On Windows an orphaned child holding the store's file is exactly the `PermissionError:
  [WinError 5]` day 14 chased.
- `sorted(tools, key=lambda t: t.name)` — the *printing* is sorted so the output is comparable
  between runs. Note what is **not** sorted: the very next statement indexes `tools[0]`, the
  unsorted list. Hold that thought; it is a rep in the hub §5 and it is why the demo call in the
  transcript below is the one it is.
- `run_async(args={...}, tool_context=None)` — the ADK-side call. `args` is a plain dict, matching the
  `inputSchema` the server declared; `tool_context` is `None` because there is no agent run in
  progress, and passing `None` is how you call a tool from a script rather than from a turn.
- `json.dumps(result)[:200]` — `result` is already a plain Python structure by the time it reaches
  here, which is the fact the rest of this part is about, and the slice is there so a long answer does
  not fill the terminal. The slice is also why the transcript below ends mid-string.
- `case ["probe"]: return probe()` — one line in the `match`, exactly as day 11's shape intended.
  Adding a subcommand touches the docstring, the function and one case, and nothing else.

*(Run on this machine on 2026-09-10 from `projects/02-parts-counter`. `-W ignore` is not decoration:
without it, ADK prints three `UserWarning: [EXPERIMENTAL] feature ...` lines over the top of the
output — hub §8 has them.)*

Three things in that, and they are not equally obvious.

**One: a different process answered.** `Processing request of type ListToolsRequest` is not printed by
`run.py`. Search this project for that string and you will not find it; search the installed SDK and
you will — `mcp/server/lowlevel/server.py` line 733, `logger.info("Processing request of type %s",
type(req).__name__)`, read on this machine on 2026-09-10. It is the server's own logging, running
**inside the child process**, and it reached your terminal because the child's standard error is
inherited by the parent. It is the trolley going past behind the person on the phone. The
stdio transport is explicit that this channel is for exactly that, and equally explicit that it is not
a failure signal. From the specification's stdio transport page, revision `2026-07-28`, fetched
2026-09-10, verbatim:

> The server **MAY** write UTF-8 strings to `stderr` for any logging purposes […] The client **MAY**
> capture, forward, or ignore the server's `stderr` output and **SHOULD NOT** assume `stderr` output
> indicates error conditions.

That rule is day 16's — `days/02-parts-counter/day-16-transports-stdio-http/` — and the reason it is
repeated here is that this is the first day where you *see* it happen and could mistake it for
something being wrong. Two lines on stderr, a successful run, exit `0`.

**Two: four tools, and this project never listed them.** Nothing in `parts_counter/` names
`find_part`, `stock_level`, `bin_location` or `adjust_stock`. The four names came down the wire. Add a
fifth tool to `parts_mcp/server.py` and this output has five rows with no edit on this side, which is
what part 1.1 promised and what you have now watched happen.

**Three: the demo call errored, and nothing raised.** `tools[0]` is `adjust_stock` — the toolset
returns the four in alphabetical order — so the ternary took its `else` branch and called it with no
arguments at all. The server refused, and *the refusal came back as a value*: `run.py probe` exited
`0`, no exception crossed the boundary, and the text of a pydantic validation error from another
process is now sitting in a Python string in yours. Protocol errors and tool-execution errors are two
different things with two different destinations, and day 14 owns that distinction; what today adds is
that from the client's side **both of them arrive as data**.

*(Run on this machine on 2026-09-10. `before` and `after` are the store's own report of the change;
the third call restores the count, which is why running this twice is safe.)* A write comes home in
the same envelope as a read. There is no second shape for "this changed something" — which is exactly
why the *instruction* in part 2.1 has to carry that rule instead, and why P27 spends a week on
approval gates.

**Read the `text` field twice.** `stock_level` is an ordinary Python function on the server that
returns a `dict`. What came back is a string **containing JSON** — the braces are escaped, the
newlines are `\n`, and if you `json.loads` it you get the dict again. Beside it, `structuredContent`
carries the same value as a real object, because the tool declared an `outputSchema` and the server
could therefore promise a shape. And `isError: false` is a third, separate statement: not "the call
succeeded" in the transport sense — the transport already said that — but "the tool's own answer is an
answer and not a complaint".

That triple is the fact this part exists to plant. **The value was serialised on the way out, and the
client is what unwraps it.** Nothing on this side received a `dict`; this side received bytes and
built one. Everything that follows from that — a `datetime` that arrives as a string, a `Decimal` that
arrives as a float, a custom class that does not arrive at all — is a consequence you now know the
shape of, and P07's schema-driven tools are where it gets its own week.

- `types: ['MCPTool']` — one more name to have met. The objects the toolset hands back are `MCPTool`
  instances, not the `FunctionTool` objects P01's agent held. Same `name`, same `run_async`, entirely
  different provenance: a `FunctionTool` was built by reading a function in this process, an `MCPTool`
  was built by reading a `Tool` declaration that arrived over a pipe.

## When it breaks

The first version of `probe()` written on this machine had `import asyncio` and no `import json`, and
the second `print` is the only line in the function that uses it. Everything worked — the process
launched, the handshake completed, the tool list came back, the call crossed the boundary and
returned — and then the whole run died on the last statement, four levels down inside `asyncio.run`,
with the traceback pointing at the framework's file paths on the way:

*(Observed on this machine on 2026-09-10, with the home-directory prefix elided.)* Somebody shipped
that on a Friday and spent an hour on the coroutine, because the traceback opens with `asyncio` and
`run_until_complete` and every instinct says the async is wrong. It is not: read the **last** frame,
not the first. The smallest fix is `import json` beside `import asyncio` — and the general lesson is
that a function-local import block is a list you have to keep in step by hand, which is the price of
keeping `run.py check` able to start.

## In production

**What a senior writes instead.** They do not index `tools[0]`. A probe that means "call `stock_level`"
says so — `by_name = {t.name: t for t in tools}` and then `by_name["stock_level"]` — because indexing
a list whose order is decided by another process is a test that passes for a reason you did not
choose. They also assert the list rather than print it: a probe that prints four names is a thing a
human reads, and a probe that fails when a name is missing is a thing a pipeline reads.

**What degrades at scale.** Every `get_tools()` on an `over_stdio` toolset launches a fresh
interpreter, and the measurement in part 1.1 puts that at **1.07 to 1.34 seconds** per call on this
machine, against **0.0001 seconds** to construct the object. Put a probe like this in a readiness
check that a container platform polls every 5 seconds and you have a boundary that spends roughly a
quarter of its life being started by its own health check. The `over_http` shape exists so that the
process is started once and probed cheaply.

**The review comment.** "Two on `probe`. `tools[0]` depends on the server's ordering — use the name.
And `json.dumps(result)[:200]` truncating mid-escape means the one time this output matters, during
an incident, it is unparseable; print `result['isError']` and the `structuredContent`, and keep the
full text behind a flag."

**The interview question.** "Your tool returns a `dict` with a `datetime` in it. It works in unit
tests and fails the moment the tool moves behind an MCP boundary. What has changed, what is the error
you would expect to see, and at which side of the line would you fix it?"
