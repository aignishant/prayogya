## One-line answer

A toolset that cannot reach its server fails at `get_tools()` and not at import, with the same
`ConnectionError` whether the server was never started or was started and died — and the agent
built on it constructs perfectly, so nothing goes wrong until a question arrives and is answered by
a model with nothing to look anything up in.

## The idea

The parts desk has a number, and the number is the whole of your relationship with the stockroom
now. You do not know what is on the shelves. You know how to ask.

Which is better every single day until the phone is engaged — and the thing worth noticing is what
"engaged" does to *you*, rather than to the phone. When you walked the aisles, an empty shelf was a
fact you tripped over: you went to fetch a brake pad set and there was nowhere to fetch it from, and
you knew immediately. Now the shelves are somebody else's and your only symptom is silence on a
line. You are not told the stockroom burned down. You get a ring tone that never stops.

Part 1.1 said this out loud when the toolset was first printed: what you buy is a boundary whose
tools can change without this project being edited, and what you pay is **a failure mode a list of
imported functions cannot have.** `from parts_counter.tools import find_part` either works when
Python reads the file or raises there and then, loudly, before anything else happens. There is no
state of the world in which that import succeeds and the function is absent. A toolset has exactly
that state, and it is the normal one: the object exists, it is well-formed, it has been handed to an
agent, and there is nothing behind it.

So the question this part is about is not *what is the error* — you will see it in a moment and it
is unremarkable. It is **when**, and **who finds out**. Three moments, and they are further apart
than they look: the module is imported, the toolset is constructed, and the tools are actually
fetched. Only the third one talks to anything. Everything before it succeeds on a machine where the
server does not exist, has never existed, and could not be started if you asked.

And then the part that makes this worth a `failure: true` rather than a paragraph. An agent is not a
program that stops when its tools are missing. It is a model with an instruction, and a model with
an instruction and no tools **still answers**. It has been told it is a parts counter. It will
count parts. The stock level it reports will be a number, it will look like every other number this
system has ever produced, and it will have come from nowhere at all.

## The mechanism

Three probes, and the first two are the same failure arriving by two different routes. Nothing here
is a trick: the first points the stdio launcher at a module that does not exist, the second points
the HTTP client at a port nothing is listening on.

**One — the server cannot start.** The command is right, the interpreter is right, the module is not
there:

```console
$ uv run --frozen python -c "
import asyncio, warnings, sys; warnings.filterwarnings('ignore')
from google.adk.tools.mcp_tool import McpToolset, StdioConnectionParams
from mcp import StdioServerParameters
from parts_counter.util import mcp as client

print('import  : fine')
ts = McpToolset(connection_params=StdioConnectionParams(
    server_params=StdioServerParameters(command=sys.executable,
        args=['-m','parts_mcp.no_such_module'], cwd=str(client.PROJECT_ROOT)), timeout=10))
print('construct: fine  ->', type(ts).__name__)

async def main():
    try:
        print('get_tools:', len(await ts.get_tools()), 'tools')
    except BaseException as e:
        print('get_tools: RAISED', type(e).__module__ + '.' + type(e).__name__)
        print('           ', str(e)[:180])
    finally:
        await ts.close()

asyncio.run(main())
"
...\.venv\Scripts\python.exe: No module named parts_mcp.no_such_module
Error on session runner task: unhandled errors in a TaskGroup (1 sub-exception)
...\.venv\Scripts\python.exe: No module named parts_mcp.no_such_module
Error on session runner task: unhandled errors in a TaskGroup (1 sub-exception)
import  : fine
construct: fine  -> McpToolset
get_tools: RAISED builtins.ConnectionError
            Failed to create MCP session: Failed to create MCP session: Connection closed
```

**Line by line:**

- `import  : fine` and `construct: fine` — the two lines that matter most, and they are the boring
  ones. `McpToolset(...)` built an object against a server that cannot exist. It validated the
  connection parameters, which are valid, and stopped. Nothing was launched and nothing was asked.
- `get_tools: RAISED builtins.ConnectionError` — the third moment, and the first one that touches
  the world. This is where a missing server becomes a program's problem, and by then the toolset has
  been passed to an agent and the agent has been handed to a runner.
- `Failed to create MCP session: Failed to create MCP session: Connection closed` — read the
  repetition. The message is nested inside itself because an inner failure was wrapped and re-raised
  with the same prefix. It is cosmetic and it is worth noticing, because the doubled phrase is the
  fastest way to recognise this exact failure in a log a year from now.
- **`Connection closed` is what the client saw, and it is not what happened.** The pipe closed
  because the subprocess exited; the subprocess exited because the module was not there. The client
  is reporting the last thing that happened to it, which is one causal step removed from the thing
  that went wrong.
- The truth is in the two lines *above* the output, and they came from the **subprocess's stderr**:
  `No module named parts_mcp.no_such_module`. Day 16 quoted the stdio transport telling clients they
  "**SHOULD NOT** assume `stderr` output indicates error conditions" — and here is the other edge of
  that rule. The stream you were told not to treat as errors is the only stream carrying the reason.
  A client that discards it, which is the easy thing to do, converts a one-line diagnosis into an
  afternoon.
- `Error on session runner task` appears **twice**, and so does the subprocess's complaint. The
  connection was attempted more than once before the failure was surfaced. That is a reasonable
  thing for a client to do and it means a log with one bad server in it has two of every line.

**Two — the server is not running.** Same client, HTTP instead of stdio, nothing listening on the
port:

```console
$ uv run --frozen python -c "
import asyncio, warnings; warnings.filterwarnings('ignore')
from parts_counter.util import mcp as client
ts = client.over_http('http://127.0.0.1:8099/mcp')
print('construct: fine ->', type(ts).__name__)

async def main():
    try:
        print('get_tools:', len(await ts.get_tools()), 'tools')
    except BaseException as e:
        print('get_tools: RAISED', type(e).__module__ + '.' + type(e).__name__)
        print('           ', str(e)[:200])
    finally:
        await ts.close()

asyncio.run(main())
"
construct: fine -> McpToolset
get_tools: RAISED builtins.ConnectionError
            Failed to create MCP session: Failed to create MCP session: All connection attempts failed
```

**Line by line:**

- **The same exception type, from a completely different cause.** `ConnectionError` covers *the
  server exited on startup* and *there is no server*, and a caller that catches it learns only that
  the boundary is unreachable. If your handling of the two differs — and it should, because one is a
  deployment that is down and the other is a deployment that never came up — the type will not tell
  you which.
- `All connection attempts failed` rather than `Connection closed`. That phrase is the only
  distinguishing signal, it is inside a message string rather than in a field, and matching on it
  means matching on prose that a library may reword in a patch release.
- There is **no stderr rescue here.** Nothing was launched, so nothing wrote a reason anywhere. The
  stdio failure was more confusing and better instrumented; this one is cleaner and tells you less.
- `construct: fine` again, from a helper that names a URL. `over_http` does not check the URL, and
  nothing in this project checks it either — a typo in the port lives happily until the first
  `get_tools()`.

**Three — and this is the one to sit with.** What does building the *agent* do?

```console
$ uv run --frozen python -c "
import warnings; warnings.filterwarnings('ignore')
from parts_counter.agent import build_counter
a = build_counter()
print('build_counter(): returned', a.name, '- nothing was contacted')
print('tools declared  :', [type(t).__name__ for t in a.tools])
"
build_counter(): returned parts_counter - nothing was contacted
tools declared  : ['McpToolset']
```

**Line by line:**

- `build_counter()` succeeds on a machine with no server, no port and no boundary. It constructs a
  toolset, hands it to an `Agent`, and returns. Part 2.1 printed that function and this is the
  consequence of the shape it has: **the agent's tool list is a promise to ask later.**
- `tools declared : ['McpToolset']` — one object, not four functions. The count is right and the
  contents are unknown, to us and to the agent, until something calls `get_tools()`.
- So every check that constructs an agent passes. `run.py check` builds no agent and would not catch
  this either. There is no green-to-red transition anywhere in this project for "the boundary is
  gone", which is the gap this part exists to name.

*Observed on this machine on 2026-09-10: google-adk 2.8.0, mcp 1.30.0, CPython 3.12.12.*

## When it breaks

It breaks in the only way that costs anything, which is when nobody sees any of the above. The
deployment brings the agent up and the boundary up as two containers; the boundary crashes on a bad
config; the agent starts perfectly, because starting is all it does. Then a question arrives.

The `ConnectionError` fires inside the run, and what happens next is a decision this project has not
made yet. If it propagates, the request fails and somebody is paged — which is the good outcome,
and the one day 9 argued for. If anything upstream catches broadly and carries on, the model answers
from its instruction alone: it has been told it is a workshop parts counter, so it produces a stock
figure, and that figure is indistinguishable in shape and tone from every correct one this system
has ever returned.

That is precisely the failure P01's evalset was built to catch, and it caught it by asserting on the
**trajectory** rather than the prose — *did the desk call the tool, or did it merely sound right?*
See `days/01-ask-desk/day-10-ship-d1-healthz-eval/parts/02-the-check-that-can-go-red/2.1-the-first-eval-that-can-fail.md`.
**This project has no such eval.** `run.py check` has six checks and not one of them would go red
with the boundary switched off. That is a debt, it is owed by day 8 of this project, and
`CODEMAP.md` records `evals/` as owed by that day. The smallest honest thing to do today is to
write it down rather than to feel covered by a check that is checking something else.

## In production

**What a senior writes instead.** They do not let "can I reach my dependencies?" be answered for the
first time by a user's request. The toolset is exercised once at start-up — fetch the tool list,
assert it is non-empty, assert the names are the ones this agent was built for — and the process
refuses to become ready if that fails. That is the readiness half of the distinction P01 day 10 drew
about `/healthz`: liveness asks whether restarting would help, readiness asks whether this process
should receive traffic, and a boundary that is down is exactly a readiness problem. They also pin the
expected tool names, because a boundary that answers with *different* tools is a worse failure than
one that does not answer at all, and `get_tools()` succeeding is not the same claim as
`get_tools()` returning what you were expecting.

**What degrades at scale.** The number is **four**: the four tool names this agent's instruction
assumes exist. Nothing checks them. A boundary deployed at the wrong version can return three, or
five, or four with `adjust_stock` renamed, and every one of those cases leaves `get_tools()`
succeeding and the agent quietly less capable than its instruction claims. The failure surface is
not "the server is down", which is loud; it is "the server is subtly not the one you wrote against",
which is silent and grows with every tool you add.

**The review comment.** "This wires the agent to `over_stdio()` at construction, so a broken
boundary is discovered on the first user question rather than at deploy. Please add a start-up probe
that calls `get_tools()` and fails readiness if it returns an empty list or is missing any of the
four names we depend on — and log the tool names it *did* get, because the version-skew case is the
one we will actually hit."

**The interview question.** "Your agent gets its tools from a server over MCP. Someone deploys a
version of that server with one tool renamed. Nothing errors. Walk me through every place that could
have caught it, say which of them you would build first, and tell me what your agent does in the
meantime."
