## One-line answer

A check nobody has watched fail has verified nothing, so the last act of building a checker is to
break something on purpose and confirm it goes red — which is how this very part was found to be
broken while it was being written.

## The idea

Every job card in the workshop has an inspection box, and the box gets a stamp. A shop can run for
years like this and be proud of it. Then one day a job comes back from a customer with a fault that
the inspection would obviously have caught, and someone goes and looks at the stamp, and discovers
what the stamp actually means: it means somebody stamped it.

The inspection was never wrong. It was never *anything*. Nobody had ever seen it reject a job, so
nobody had ever learned whether it could.

This is the failure the plan's Principle 9 exists to prevent — *every day ends with a check that
can go RED* — and it is worth being precise about why a green check is weak evidence. A green check
is consistent with two very different worlds: the work is correct, or the check is not looking. You
cannot tell those apart from the green. You can only tell them apart by having seen red.

Two commands close this out, and they check different things.

`python p.py depth N` reads a day's documents against the contract in the plan §5: are the seven
sections present, in order, is there a walkthrough after every code block that carries logic, does
the hub claim exactly the IDs the plan assigns, does some part declare `failure: true`, has a clock
crept in anywhere. It checks the half of the standard a script can check, and it is loud about the
half it cannot.

`python p.py index` regenerates the derived documents — the traceability table, the curriculum
index, the tracker, the wiki. A **generated document** is one rebuilt from the days themselves;
editing one by hand only means the next run silently overwrites you. `index --check` asserts they
are current rather than rewriting them, which is what makes staleness a failure rather than a
surprise.

The distinction that matters: `depth` checks the days against the contract, `index --check` checks
the indexes against the days, and `check` runs both. Nothing in that chain checks the *quality* of
a document, and it is important to be honest about that. The checker is a floor. It cannot tell
whether a scene is one the reader has lived, whether the explanation is any good, or whether *In
production* is true. Those are checked by reading, and a repository that argues with its own
checker will not survive the reading either.

## The mechanism

Here is the function that decides whether a code block has been explained. It is the check that
caught this day, at its real path, whole:

```python
# p.py
def unexplained_code_blocks(cfg: Config, text: str) -> list[int]:
    """Fences no walkthrough follows. An unexplained line is a bug in the document: the reader
    can copy it but cannot change it."""
    lines, out = text.splitlines(), []
    for start, lang, heading, after in _fences(cfg, text):
        if not _needs_walkthrough(cfg, lang, heading):
            continue
        j, explained = after, False
        while j < len(lines):
            if re.search(r"line by line", lines[j], re.I):
                explained = True
                break
            if re.match(r"^`{3,}[\w+-]", lines[j]) or lines[j].startswith("## "):
                break
            j += 1
        if not explained:
            out.append(start + 1)
    return out
```

**Line by line:**

- `_needs_walkthrough(cfg, lang, heading)` — two escapes, both deliberate. A fence whose language
  is in `no_walkthrough_langs` carries output, a diagram or a config dump rather than logic, so
  demanding a walkthrough after it would only teach padding. A fence under an exempt heading —
  *When it breaks*, *Setup*, *Ledger* — is evidence rather than teaching. Everything else must be
  explained.
- `j, explained = after, False` then the `while` — the search starts at the line *after* the
  closing fence and walks forward. It is a forward scan rather than a fixed lookahead because the
  walkthrough may be separated from the block by a blank line or a sentence.
- `if re.match(r"^`{3,}[\w+-]", lines[j]) ... break` — **this is the line that caught this day.**
  The scan gives up as soon as it meets another opening fence. A `bash` block followed immediately
  by a `console` block of its output, with the walkthrough after both, reads perfectly well to a
  human and fails here — because by the time the walkthrough arrives, a second block has started
  and the first one's claim to it has lapsed. That is strict, and the strictness is the point: it
  is what makes "which block does this explanation belong to?" have exactly one answer.
- `lines[j].startswith("## ")` — the scan also stops at the next section. A walkthrough in a later
  section does not retroactively explain an earlier block.
- `out.append(start + 1)` — the *line number* of the offending fence, not just its existence,
  because a part with three code blocks and one complaint needs to say which.

Now the two commands, run on this repository:

```console
$ python p.py depth 0
OK    day  0  4 parts

OK all 1 day(s) meet the depth contract.

$ python p.py index
OK wrote 6 generated document(s) under docs/.

$ python p.py index --check
OK 6 generated document(s) are current.
```

**Line by line:**

- `depth 0` with no other argument — checks one day. With no day at all it checks every written
  day, which is what `check` calls.
- `index` writes; `index --check` compares and returns non-zero if anything differs. The two share
  all their logic and differ only in what they do with the result, so the check can never drift
  from what the writer would have produced.
- The count is `6` because the tracker, the traceability table, the curriculum index, the wiki
  summary, this day's wiki page and the entity index are all derived. None of them is written by
  hand, and every line in them is copied from a day document.

## When it breaks

This is not a hypothetical. Here is `depth 0` on the day you are reading, partway through writing
it — real output, pasted:

```console
$ python p.py depth 0
FAIL  day  0  3 parts
        days/day-000-toolchain-skeleton-driver/parts/01-the-workbench/1.1-one-tool-owns-the-environment.md: code block at line 58 has no 'Line by line' walkthrough after it
        days/day-000-toolchain-skeleton-driver/parts/01-the-workbench/1.1-one-tool-owns-the-environment.md: code block at line 92 has no 'Line by line' walkthrough after it
        days/day-000-toolchain-skeleton-driver/parts/02-the-driver/2.1-the-foreman-and-the-order-guard.md: code block at line 139 has no 'Line by line' walkthrough after it
        days/day-000-toolchain-skeleton-driver: no part declares 'failure: true' — every day carries at least one part whose subject is a deliberate failure
        days/day-000-toolchain-skeleton-driver: no LESSON.md — the hub is what assembles the day

1 of 1 day(s) fail the depth contract.
```

Five complaints, and they are three different kinds of wrong.

The three `line 58` / `line 92` / `line 139` failures were a real mistake, made while writing this
day: a `bash` block showing a command, then a `console` block showing its output, then the
walkthrough. It looks right. It is not — the scan in the mechanism above stops at the second fence,
so the first block was never explained by anything the checker could see. The fix was to merge each
pair into one `console` block carrying both the command and its real output, which is also the
better document: the reader sees what was typed and what came back in one place.

The fourth is a missing deliberate-failure part, and the file you are reading is what fixed it.
Note the shape of that: the day could not be finished without a part whose subject is a failure,
and the check would not let it be finished by asserting one had been considered. It had to be
declared, in frontmatter, in a file.

The fifth is the hub, which had not been written yet. Its wording is worth reading twice — *the hub
is what assembles the day*. Four parts on disk are four documents; without the hub they are not a
day, and the checker refuses to call them one.

Now cause it deliberately, which is the rep. Take any part, delete its `## In production` heading,
and run the check:

```console
$ python p.py depth 0
FAIL  day  0  4 parts
        days/day-000-toolchain-skeleton-driver/parts/02-the-driver/2.2-the-inspection-that-inspected-nothing.md: missing section 'in production'

1 of 1 day(s) fail the depth contract.

$ echo $?
1
```

Put it back and it goes green — `OK all 1 day(s) meet the depth contract.` That round trip — red, fix, green — is the only thing that turns a
green check from a decoration into evidence, and it is the reason this part exists.

## In production

A senior engineer does not add a check and move on. They add the check, then break the thing it
guards and confirm the pipeline goes red, and only then do they trust it. In a test suite the
discipline has a name — write the failing test first — and the reason is identical: a test that has
never failed has not been shown to be connected to anything.

What degrades is confidence in checks that are never exercised, and it degrades silently in
proportion to how many you have. **Six** generated documents and **one** written day is a system
small enough to eyeball. At **297** days and **310** IDs, nobody eyeballs anything: the traceability
table is the only statement of what is closed, and if `index --check` ever stops being run, the
table keeps rendering, keeps looking authoritative, and keeps describing a repository that no longer
exists. A stale index is worse than no index, because no index makes you go and look.

The industrial version of this failure is coverage theatre: a suite with a high coverage number
where the assertions are weak, so the tests execute the code without ever disagreeing with it. The
tool that exists precisely to catch it — mutation testing — works by deliberately introducing bugs
and reporting which ones the suite failed to notice. That is the same move as this part, automated:
break it on purpose and see whether anything objects.

The review comment: *"Have you seen this check fail? Paste the red."* It sounds rude and it is the
single most useful question in a review of anything that guards.

The interview question: **"Your CI has been green for three months. What would make you suspicious
of it, and how would you find out whether it is actually checking anything?"** A weak answer talks
about coverage. A strong one says: introduce a defect the check claims to catch, and watch.
