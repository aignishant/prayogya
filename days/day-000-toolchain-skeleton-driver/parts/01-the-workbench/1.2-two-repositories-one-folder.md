## One-line answer

This folder holds two different kinds of repository — one that writes the curriculum and forty that
are the curriculum — and the rule that keeps them apart is that nothing under `projects/` may ever
import from the root.

## The idea

The workshop has an office and it has benches. The office holds the job-card book, the wall chart
and the shop's own set of rules. Each bench belongs to one job: its own vice, its own drawer of
parts, its own drawing pinned above it. A bench is finished when the thing on it works, and it
works whether or not the office is open.

The mistake that ruins a shop like this is small and reasonable: someone keeps the good torque
wrench in the office because everyone needs it, and now no bench can finish a job without walking
to the office. The bench is no longer self-contained. You do not find out on the day it happens —
you find out the day someone tries to take a bench somewhere else.

That is precisely what the plan's §0 describes happening to v2 of this curriculum. Shared code
lived in one place, later projects imported it, and a reader who took one project folder to a
different machine got an import error for a module they had never been given. v3 deleted the shared
folder, and this folder now holds two kinds of thing that must not lean on each other.

An **authoring repository** is the root you are standing in: the plan, the ledgers, the day
documents, and `p.py`. Its job is to write and check the curriculum. A **project repository** is
any folder under `projects/` — one of the forty systems. Its job is to be a running agentic system,
complete alone.

The rule between them runs one way only, and it is the plan's §1 and §7:

> Nothing under `projects/` may import from the repository root. `./p` is authoring only; every
> project carries its own `./run`, and `./run` never reads the plan.

So the root's driver and a project's driver are different programs with different jobs, and the day
that one starts doing the other's work is the day the forty projects stop being independent.

The second idea in this part is smaller and has a strict order attached to it. A repository that
will one day hold API keys needs its ignore file **before** it holds them — not because the rule is
different later, but because git remembers. A secret committed once is in the history, and removing
it from the working tree does not remove it from the repository you already pushed. The ignore file
is cheap on day 0 and expensive on day 40.

## The mechanism

The skeleton, as it stands after this day:

```text
agentic-projects/
├── CLAUDE.md              the standing contract every session reads first
├── README.md
├── granth.toml            identity, and the knobs the depth contract exposes
├── p.py                   the whole authoring toolchain, one file, stdlib only
├── .gitignore             written before the first secret exists
├── .python-version        the pin from part 1.1
├── docs/
│   ├── 00_MASTER_PLAN.md  THE CONTRACT
│   ├── PROGRESS.md  PINS.md  SOURCES.md  GLOSSARY.md  PROVENANCE.md  CHANGELOG_PLAN.md
│   ├── adr/               one file per structural decision, never rewritten
│   ├── archive/           the plan as it was before adoption
│   └── wiki/              generated; never edited by hand
├── days/
│   ├── _TEMPLATES/        LESSON.md · CHECKLIST.md · PART.md
│   └── day-000-toolchain-skeleton-driver/
└── projects/              the forty. Each one a repository. Empty until day 1.
```

**Line by line:**

- `granth.toml` and `p.py` sit at the root and **only** at the root. A project that needed either
  of them would be a project that cannot be taken anywhere, which is the one thing v3 exists to
  prevent.
- `docs/` splits into three kinds of file that behave differently: the plan, which is the contract;
  the six append-only ledgers, which are history; and `wiki/`, which is output. Editing something
  in `wiki/` only means the next `python p.py index` silently overwrites you.
- `docs/archive/` holds the plan exactly as it was before it was adopted, so the claim "sections 0
  to 13 are unchanged" is checkable rather than trusted.
- `days/_TEMPLATES/` is not a day. It has no number and no tool treats it as one; it is what
  `python p.py new N` copies from.
- `projects/` is empty today and stays empty until day 1. It is in the skeleton anyway, because a
  folder that exists is a decision recorded and a folder that does not is a decision deferred.

Now the ignore file, printed whole, at its real path:

```gitignore
# .gitignore
# Secrets never touch git. This file exists before the first secret does.
.env
.env.*
!.env.example
*.key
*.pem
credentials.json
secrets.*

# The learner's own work. The teaching lives in parts/; lab/ is where you make mistakes.
days/*/lab/

# Generated locally, never committed
__pycache__/
*.pyc
.pytest_cache/
.ruff_cache/
.mypy_cache/
.venv/
venv/
node_modules/
dist/
build/
*.egg-info/

# Editors and operating systems
.DS_Store
Thumbs.db
.idea/
*.swp
```

**Line by line:**

- `.env` then `.env.*` then `!.env.example` — the third line is the one that carries a decision.
  The first two hide every environment file; the `!` un-hides the example. Without it the one file
  that documents *which* keys a project needs would be invisible, and a stranger cloning a project
  would have to guess. Order matters: a later negation re-includes, so the `!` line must come after
  the patterns it is undoing.
- `*.key` and `*.pem` — private keys by extension rather than by name, because the name is whatever
  the person who downloaded it happened to call it.
- `days/*/lab/` — the learner's own work is deliberately not committed. The teaching lives in
  `parts/`; `lab/` is where you are allowed to make a mess, and a mess in the history is a mess
  forever.
- `.venv/` and `venv/` — both, because part 1.1's point was that you cannot rely on everyone
  choosing the same name.
- `__pycache__/` before there is any Python to cache. Same reasoning as the secrets block: the
  ignore file is written for the repository this becomes, not the repository it is.

## When it breaks

The failure this file prevents, caused on purpose. A key is written to `.env`, and then git is
asked whether it can see it:

```console
$ printf 'GOOGLE_API_KEY=AIza-not-a-real-key\n' > .env

$ git check-ignore -v .env
.gitignore:2:.env	.env

$ git status --porcelain .env

```

The middle command is the interesting one. `git check-ignore -v` answers *which rule* hid the file
and *which line* it is on: `.gitignore`, line 2, pattern `.env`. The last command prints nothing at
all, and nothing is the correct answer — git cannot see the file, so there is no state to report.

Now run the same thing in the order people actually do it. Create `.env` first, commit, *then* add
the ignore rule, and `git status --porcelain .env` prints a modification rather than nothing,
because git tracks what it has already been told about. The ignore file only ever governs files git
has not seen yet. That is the whole reason for the order, and it is why the smallest fix — writing
`.gitignore` before anything else — has to happen on day 0 rather than on the day it first matters.

## In production

A senior engineer does not trust the ignore file on its own. They add a secret scanner to the
pre-commit hook and to CI, because `.gitignore` prevents an accident and does nothing about a
deliberate `git add -f`, a key pasted into a test fixture, or a key in a file whose name nobody
predicted. The ignore file is the floor, not the standard.

What degrades is history, and it degrades permanently rather than gradually. There is no scale at
which a committed and pushed secret becomes cheaper to fix: the rotation cost is the same on a
repository with **one** contributor and with **fifty**, and every fork, clone and CI cache that
pulled it before the rotation is another copy you do not control. This is the one failure in the
whole curriculum that a later day cannot undo, which is why it is taught on the first one.

The review comment: *"This adds `.env.local` to the ignore file — was anything already committed
under that name? Check the history, not the working tree."* The distinction between the two is
exactly what people get wrong.

The interview question: **"You have just found an API key in your repository's history. Walk me
through what you do, in order."** The answer that gets it right starts with *rotate the key* and
only then talks about rewriting history — because the secret is already out, and scrubbing the
history of a repository other people have cloned protects nothing you have not already lost.

## Check yourself

- **Run:** `printf 'X=1\n' > .env && git check-ignore -v .env && git status --porcelain .env && rm .env`
  — expect the rule and its line number, then silence.
- **Say out loud:** why does `.gitignore` have to exist before the first secret, given that the
  rule it contains would be identical if you added it tomorrow?
