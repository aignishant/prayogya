## One-line answer

Streaming is one field on `RunConfig` — `streaming_mode`, whose enum has exactly three values —
and turning it on changes the **number and the shape** of the events, from three to nineteen for the
same question, while changing the answer not at all: sixteen of the new events are single words
carrying `partial=True`, and every one of them is `is_final_response() == False`.

## The idea

The line is still open and the arrangement changes. Up to now your commentator waited until there
was something to say and then said it: one message, complete, when the result existed. You asked
them to talk instead — to keep speaking while it is happening, so that you are not sitting in
silence.

Nothing about the race changed. The finishing order is the finishing order. What changed is the
shape of what comes down the line: instead of one sentence you now get a word at a time, each one a
fragment that means very little on its own and everything in sequence. You cannot act on any single
fragment. You cannot write "known" in the results book. But you can put each one on the screen as it
arrives, and the person watching stops asking whether the line has gone dead.

And there is a bookkeeping cost that arrives with it, which is the honest reason this is a decision
rather than an obviously good idea. Every fragment is a message. If you were counting messages —
logging them, storing them, charging for them, testing against them — your counts have just changed
by a large factor for a race that is exactly the same race. Anybody downstream who wrote "there will
be a handful of messages per question" wrote that down against the arrangement you have just
replaced, and nothing told them.

So: streaming is a switch you throw on the run, not a property of the agent and not a property of
the model. This part is what the switch is called, what the three positions are, and what happens to
the stream when you move it. The word for a fragment is a **partial** event: one marked as a piece
of something still arriving rather than as a thing you may act on.

**Line by line:**

- `from google.adk.agents.run_config import RunConfig, StreamingMode` — the full path, because
  `RunConfig` is not exported from `google.adk.agents` itself. Day 07 part 2.2 already imported
  `RunConfig` this way in a probe; this is the first time it is in this project's own code.
- **`run_config()` has two jobs, and they arrived on two different days.** The bound —
  `max_llm_calls=loop.MAX_CALLS_PER_QUESTION` — is the rep day 07's hub §5 asked for, after day 07
  part 2.2 found that `RunConfig.max_llm_calls` exists, defaults to **500**, and had been governing
  every ADK run in this project since day 6 without anybody choosing it. The streaming switch is
  today's. Two jobs in one function is normally a smell; here it is the correct shape, because both
  are answers to the same question — *what settings does a run of this desk use?* — and splitting
  them would let a caller pick one and forget the other.
- **The docstring's "Day 4" is this project's day 4, which is curriculum day 7.** The `6` itself is
  older than that: `loop.MAX_CALLS_PER_QUESTION = 6` was written on this project's day 2, curriculum
  day 5. What day 4 of this project decided is the thing the docstring is really about — that the
  six, and not the framework's five hundred, governs the ADK path too. The constant is not
  redefined here and is not copied here; it is read from `loop`, so there is one number and one
  place to change it.
- `*` before `stream` — keyword-only. `run_config(True)` will not compile, so every call site reads
  `run_config(stream=True)` and a boolean argument at a distance never has to be guessed at.
- `stream: bool = False` defaults to **off**, which is why `ask()` gets three events and not
  nineteen, and why adding this function changed nothing about the behaviour day 6 shipped. A new
  configuration object whose defaults change existing behaviour is a configuration object that
  arrives as a bug report.
- `StreamingMode.SSE if stream else StreamingMode.NONE` — a conditional expression rather than two
  branches, because both arms set the same field and there is nothing else to decide. The enum's
  three values, read from `google.adk.agents.run_config.StreamingMode` in google-adk 2.8.0, are:

  | Name | Value |
  | --- | --- |
  | `NONE` | `None` |
  | `SSE` | `'sse'` |
  | `BIDI` | `'bidi'` |

  `NONE`'s value is the Python `None`, not the string `'none'` — so the "off" position of this
  switch is the absence of a mode rather than a mode called off, and a comparison written as
  `mode == "none"` is false in every case including the one it was aimed at. `SSE` is the position
  this project uses. `BIDI` is the third, this project has not run it, and nothing in this document
  claims what it does beyond its name — see *When it breaks*.
- `ask()` gains `run_config=run_config()`, on its own line, with the trailing comma. It is the
  single place a person's question enters the framework in this project, so it is the place the
  bound has to be attached: a run started anywhere without a `run_config` silently gets 500.
- `ask()` calls `run_config()` **with no arguments**, so the desk's own answer path is
  non-streaming. That is a real decision and not an oversight: `ask` returns a string, and a
  function that returns a string has nowhere to put a fragment. Streaming without a consumer for the
  fragments is nineteen events of extra bookkeeping in exchange for nothing.

**Line by line:**

- **Nineteen events, and `2 model call(s)`.** The right-hand number did not move. The same two model
  calls happened, the same tool ran once, the same sentence came back. Everything that changed is
  the packaging, which is the single most important sentence in this part: **streaming changes the
  number and shape of the events, not the answer.**
- Rows 1 and 2 are byte-for-byte what part 1.2 printed. The tool call and the tool result are not
  fragmented, because there is nothing to fragment: a function call arrives complete or not at all.
  So the empty-text problem from part 1.2 is entirely unaffected by streaming — a client that
  switched on streaming to fix a blank screen still has a blank screen for exactly as long as
  before.
- Rows 3 to 18 are the sixteen words of the sentence, one per event, each with its trailing space
  except the last. Sixteen words plus two tool events plus one final event is nineteen, and the
  arithmetic is worth doing once so that the number stops being a surprise: a stream's length is a
  function of how long the answer is, and nothing else bounds it.
- **`partial=True` on every fragment**, and this is what the flag means: the event is a piece of
  something still arriving. The framework's events reference draws exactly this line — an event
  whose text is present with `partial` set is a *streaming text chunk*, and one whose text is
  present without it is a *complete text message*. A fragment is not a short answer. It is not an
  answer at all.
- **`final=False` on all sixteen**, and it follows from the rule part 1.2 read out rather than from
  a separate mechanism: the documented condition includes *not a partial stream chunk*, so
  `partial=True` alone disqualifies an event from being final. You do not have to remember this —
  you have to call the helper.
- Row 19 is `partial=None` and `final=True`. It is the only row in nineteen that a client may act
  on, and the only one `agent.ask` would have kept.
- **And row 19 carries the whole sentence again.** Look at its text against row 18's `'up.'`: the
  final event is not the last fragment, it is a repeat of everything. The transcript truncates at
  48 characters, so what you can see is that it starts the same way row 3 did. Part 2.2 is that
  observation taken seriously, and it is the day's deliberate failure.
- `partial=None` on row 19, not `False` — the third state from part 1.2 again, in the one row where
  a naive `if event.partial == False` would have been written by somebody trying to find the answer
  without the helper. `None == False` is `False`, so that condition rejects the answer and accepts
  nothing.

## When it breaks

It breaks for whoever is downstream of the count, and it breaks silently, because the only visible
difference is a number in a summary line. Here are the two tails, from the two runs above, one flag
apart:

```console
3 events, 2 model call(s)
19 events, 2 model call(s)
```

Somebody turns streaming on to improve how the page feels, and a log pipeline that writes one row
per event goes from three rows a question to nineteen — a storage bill and an ingest rate that
moved by more than six times with no code change anyone would flag in review, on a diff that reads
`stream=True`. The smallest fix is not to turn streaming off; it is to write the log at the point
where a turn ends rather than at the point where an event arrives, so that the log's unit is the
thing you actually wanted to count.

The third streaming mode is genuinely unexamined here, and it is left as a `TODO(me)` rather than
described, because this project has never run it and a sentence about it would be invention:

## In production

**What a senior writes instead.** They make streaming a property of the *transport*, decided at the
edge, and never of the agent. One `run_config(stream=...)` call, wired to whether the caller asked
for a streaming response, so that the HTTP endpoint and the batch job share one agent and one
configuration function and differ in one boolean. And they never let `run_config()` be optional at a
call site: a helper that returns the project's settings is only worth having if forgetting it is
impossible, which means no `runner.run_async` anywhere in the codebase without it.

**What degrades at scale.** The number is **19 against 3** — the same question, the same answer, the
same **2** model calls, six and a third times the events. Nothing about the model's cost changed;
everything about the event-handling cost did. At a thousand questions a day that is 19,000 events
instead of 3,000 through every consumer you have: the logger, the session store, the trace exporter,
the websocket. The failure mode is not the model bill, which is identical. It is the piece of
infrastructure that was sized against three.

**The review comment.** "This turns on `StreamingMode.SSE` for all traffic, including the nightly
batch that has no screen to render to. Please pass `stream=` from the request path only. Also, the
event count per question goes from 3 to 19 on our own sample question — check with whoever owns the
log ingest before this merges, because their alert threshold was set against the old number."

**The interview question.** "You switch your agent to streaming and the answers are unchanged but
your observability bill triples. Explain what actually changed in the run, and where you would put
the boundary so that the user-facing improvement does not have to be paid for by every consumer of
the event stream."
