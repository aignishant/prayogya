## One-line answer

Day 7 found `RunConfig.max_llm_calls`, read its default and could not make it fire; the scripted
double can, and when it does it raises `LlmCallsLimitExceededError` after **7 events for 3 model
calls** — which is the thing to take away, because the bound counts model calls and the stream you
are watching counts events, and the gap between those two numbers is where people size the limit
wrongly.

## The idea

The line is open and the commentator has got stuck. They say they are going to check the timing
board. They check it. They say they are going to check the timing board. They check it. There is no
malice in it and no error message, and from where you are sitting it sounds like diligence: somebody
being thorough about a race that has not resolved yet.

Nothing at the track will stop this, because nothing at the track knows it is happening. The only
person who can stop it is the operator at the exchange, and the operator's rule is not "listen for
repetition" — the operator cannot hear the call. The rule is a count. After three connections to the
track, the line comes down, whatever is being said on it.

And now the part that catches people. You have been listening to messages, and you have heard rather
more than three of them: a "checking the board" and a "the board says" for each connection, and one
more "checking the board" that had just started when the plug came out. Seven things reached your
ear. The operator counted three. Both counts are correct, they are counts of different things, and
the number the operator was given was a number of *connections*. Somebody who sets that number by
thinking about how many messages a normal race produces will set it far too low or far too high, and
will not find out which until a live one.

This part is short because it closes something rather than opening it. Day 7 of this curriculum
established what the bound is, where it lives, what it defaults to and what disables it, and ended by
saying it could not be watched firing on a machine with no key. Part 1.1 of today built the thing
that removes that obstacle. So: watch it fire, read the real message, and take away the one fact the
earlier day could not show you — which of the two counts is the one being bounded.

## The mechanism

`scripted.NEVER_STOPS`, from the file part 1.1 printed whole, is a script of one step: ask for
`check_service_status`, for ever. It never produces an answer, and the clamp in
`generate_content_async` means the step repeats rather than the script running out. Nothing in the
run stops on its own; the bound has to.

The limit is overridden to `3` here rather than using `run_config()`'s six, purely to keep the
transcript short — this project's own number is unchanged, and the last row of the table below is
where it is discussed. Observed on this machine on 2026-09-10:

```console
$ uv run --frozen python -c "
import asyncio, warnings
warnings.filterwarnings('ignore')
from google.adk.agents.run_config import RunConfig
from google.adk.sessions import InMemorySessionService
from google.genai import types
from ask_desk import agent, scripted

async def main():
    model = scripted.ScriptedModel(scripted.NEVER_STOPS, name='never-stops')
    desk = agent.build_desk(model)
    ss = InMemorySessionService()
    await ss.create_session(app_name=agent.APP_NAME, user_id='u', session_id='s')
    r = agent.build_runner(ss, desk)
    msg = types.Content(role='user', parts=[types.Part(text='Is the VPN down?')])
    n = 0
    try:
        async for e in r.run_async(user_id='u', session_id='s', new_message=msg,
                                   run_config=RunConfig(max_llm_calls=3)):
            n += 1
    except Exception as ex:
        print(f'raised after {n} events')
        print(f'{type(ex).__module__}.{type(ex).__name__}: {ex}')
asyncio.run(main())
"
raised after 7 events
google.adk.agents.invocation_context.LlmCallsLimitExceededError: Max number of llm calls limit of `3` exceeded
```

**Line by line — recap depth.** The bound is taught in full by **day 07 part 2.2**, which found the
field, read its default, read the source of its enforcement and named what disables it. Nothing in
that is repeated here; what is new is that it can now be watched. What each line of the probe
contributes, and the failure each prevents:

| Line | What it does, and the failure it prevents |
| --- | --- |
| `scripted.NEVER_STOPS` as the script | Produces a runaway on demand, with no key and no quota. Prevents the situation day 7 was in: a bound documented but never seen firing, which is a bound nobody has tested. |
| `RunConfig(max_llm_calls=3)` | A small, explicit limit for the transcript. Prevents a demonstration that scrolls for six calls and teaches nothing extra on the last three. |
| `n += 1` inside the loop, before any check | Counts **events**, which is the number this day has been reading all along. Without it, the transcript would show the exception and hide the fact that seven things had already been yielded. |
| `try` / `except Exception` around the whole `async for` | The bound arrives as a raised exception out of `run_async`, not as a return value or a final event. Code that only handles events never sees it, and a caller that does not catch it gets a traceback where it expected an answer. |
| `type(ex).__module__` in the print | Names where the exception is defined, so the reader can find it. Prevents a bare class name that could belong to anything. |
| `RunConfig(...)` here rather than `agent.run_config()` | Keeps this project's own six untouched while the transcript uses three. Prevents the reader concluding that the demonstration changed the desk's real budget. |

**And the two numbers.** `raised after 7 events`, and a message naming a limit of three, from one
run. The run
had already produced three call-and-result pairs — six events — and the seventh event was the fourth
call being asked for when the count went past three and the enforcement raised. So:

- the bound counts **model calls**: connections to the provider, one per turn the model is asked for;
- the stream counts **events**: everything the runner emits, which includes every tool result your
  own process produced and, with streaming on, every word.

Part 1.2 already showed these are different — `3 events, 2 model call(s)` — and part 2.1 widened the
gap to `19 events, 2 model call(s)` with a flag. Here the ratio is seven to three. There is no fixed
conversion between them, which is the practical point: **you cannot size `max_llm_calls` by looking
at how many events a normal run produces**, and the event count is the one that is easy to observe.

> **Recap — the bound this project sets, and the one it inherits.** `RunConfig.max_llm_calls` is
> ADK's own ceiling on model calls for a single run. It is **on by default at 500**, a value sized to
> stop an infinite loop rather than to budget a question; a value of zero or less **disables it
> entirely**, because the enforcement is guarded by `max_llm_calls > 0`; and it can be moved from
> outside your repository by the `ADK_MAX_LLM_CALLS` environment variable. This project passes its
> own `loop.MAX_CALLS_PER_QUESTION`, which is `6`, through `agent.run_config()` so that the number
> deciding what one question may cost is one somebody here chose.

> override:

## When it breaks

It breaks where day 7 predicted it would and could not show: in a run nobody is watching. The real
message, verbatim, from the run above:

```console
raised after 7 events
google.adk.agents.invocation_context.LlmCallsLimitExceededError: Max number of llm calls limit of `3` exceeded
```

Somebody deploys a desk whose `max_llm_calls` was left to inherit the default, and one question with
a tool the model keeps re-asking for runs to **500** calls before this line appears. The message is
clear and it arrives far too late to be useful: the cost is already spent, and the only thing the
exception tells you is the number you did not choose. The smallest fix is the one line
`agent.run_config()` already contains — pass your own constant — and the second-smallest is to log
the model-call count on every completed run, so that a question drifting from two calls to five is
visible before it is a question that reaches five hundred.

## In production

**What a senior writes instead.** They set the bound from a named constant, they alert on the
*distribution* rather than on the ceiling, and they treat `LlmCallsLimitExceededError` as a signal
rather than as an error to swallow: caught at the request boundary, returned to the caller as a
distinct failure, and counted, because a run that hits the ceiling is nearly always a prompt or a
tool problem rather than a legitimately long job. They also never pin the bound at zero to "turn it
off for a debugging session", because zero is the value that removes the ceiling altogether.

**What degrades at scale.** The numbers are **6 against 500**. One runaway question under this
project's bound costs six model calls; the same question under the inherited default costs up to
five hundred — eighty-three times more — and the event stream it emits is larger again, because
every model call in a tool loop brings a result event with it. At the ratio observed here, seven
events for three calls, five hundred calls is well over a thousand events through every consumer of
the stream. The failure is not that nothing stops it. It is that the thing which stops it was sized
to catch an infinite loop, not to bound a question, and the difference is two orders of magnitude of
somebody's quota.

**The review comment.** "This `run_async` call does not pass `run_config=`, so it inherits
`max_llm_calls=500`. Every other call path goes through `agent.run_config()`. Please use it here
too — and while you are in the file, catch `LlmCallsLimitExceededError` at the handler and return a
distinct status, because right now a bounded run and a provider outage look identical to the
caller."

**The interview question.** "Your agent framework bounds a run by the number of model calls, and
your observability counts events. Given one run, explain why those two numbers differ, describe what
changes the ratio between them, and tell me how you would choose the bound without looking at the
event count at all."
