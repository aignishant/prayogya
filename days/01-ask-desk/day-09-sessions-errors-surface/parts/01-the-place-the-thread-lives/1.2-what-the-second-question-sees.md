## One-line answer

The thread is still being carried on every request — the runner does it now instead of you — and the
`session_id` you pass is the entire input that decides which thread that is: an id that names no slot
fails loudly, and an id that names the **wrong** slot fails silently, as a confident answer to a
conversation the person in front of you never had.

## The idea

A doctor picks up the notes from the slot at the foot of a bed and reads them. Everything in them is
true. The dates are right, the observations are careful, the drug chart is legible. They are the
notes of the patient in the next bed, because the trolley was pushed one place along at some point
this morning and nobody noticed.

Nothing about that goes wrong loudly. There is no alarm, because every part of the system did exactly
what it was asked: the slot held notes, the notes were complete, they were handed over on request.
The only broken thing is the join between the number and the bed, and no one on the ward can see a
join. What they see is a clinician being confidently wrong about a person, in a way that reads as
carelessness rather than as a filing error.

That is what a wrong `session_id` looks like, and it is why this part exists at the level it does.
Day 4 part 2.2 caused a very similar symptom by a completely different route: the model's reply was
never appended to the list, so every request went out with a hole in it and the answers came back
repetitive and mildly incoherent. The model there was being shown a thread that was **missing
things**. Here the model is being shown a thread that is **complete and belongs to someone else**.
Both produce an answer that arrives on time, in the right format, with no exception anywhere — and
the two need telling apart, because the fix for one is nowhere near the fix for the other.

There is a third case, and it is the good one. If you pass an id that names no session at all, the
runner refuses. That refusal is loud, it happens on the first call, and it is the case people worry
about. It is not the case that costs anything.

So the shape to hold on to: **the thread did not stop being carried when the framework arrived — it
stopped being carried by you.** On day 4 you could see the thread, because it was a list you could
print. Now the only thing you can see at the call site is three strings, and one of them is doing all
the work.

## The mechanism

No new code. The mechanism is the subcommand part 1.1 printed, run in full, and read as two
experiments rather than one:

```console
$ cd projects/01-ask-desk
$ uv run --frozen python run.py session
--- one session, two questions ---
  after question 1: session 's-1' holds 4 event(s)
  after question 2: session 's-1' holds 8 event(s)

--- two sessions, one question each ---
  after question 1: session 's-1' holds 4 event(s)
  after question 2: session 's-2' holds 4 event(s)
```

**Line by line:**

- The first block is accumulation, and it is the whole claim of the day in two lines. Four, then
  eight. Nothing in `run.py session` appends anything, resends anything or holds a list. The second
  question was asked in exactly the same way as the first, and the slot had grown.
- Both questions in that block passed `session_id="s-1"`, and that is the only reason they landed in
  the same slot. Not the runner, not the agent, not the process — the string.
- The second block is the same two questions with the second one addressed to `s-2`. Both slots hold
  **four**. Not eight and zero, not an error: two complete, correct, four-event conversations that
  have never heard of each other.
- Read those two blocks together and you have the whole control surface. Identical code, identical
  model, identical questions; one character different in one argument; a conversation or two
  strangers. There is no third input.
- `holds 4 event(s)` is `len(session.events)` read back from the service. Part 1.1 established that
  the fourth event is your own question, so "four" is one exchange, not four exchanges.

### Three ids, three outcomes — and only one of them is loud

```console
$ uv run --frozen python -c "
import asyncio, warnings
warnings.filterwarnings('ignore')
from google.adk.sessions import InMemorySessionService
from google.genai import types
from ask_desk import agent, scripted

async def main():
    ss = InMemorySessionService()
    await ss.create_session(app_name=agent.APP_NAME, user_id='u', session_id='s-1')
    model = scripted.ScriptedModel(scripted.LOOKS_IT_UP, name='looks-it-up')
    runner = agent.build_runner(ss, agent.build_desk(model))
    msg = types.Content(role='user', parts=[types.Part(text='Is the VPN down?')])
    try:
        async for _ in runner.run_async(user_id='u', session_id='s-2', new_message=msg,
                                        run_config=agent.run_config()):
            pass
    except Exception as ex:
        print(f'{type(ex).__module__}.{type(ex).__name__}: {ex}')
    print('get_session on a wrong id returns:', await ss.get_session(app_name=agent.APP_NAME, user_id='u', session_id='s-2'))
asyncio.run(main())
"
google.adk.errors.session_not_found_error.SessionNotFoundError: Session not found: s-2
get_session on a wrong id returns: None
```

**Line by line:**

- `SessionNotFoundError: Session not found: s-2` — an id that names **no** slot is a hard failure on
  the first call, before any model call is made. Good. This is the case that costs nothing, because
  nobody ships past it.
- `get_session` on the same id returns `None` rather than raising. Two different answers to two
  different questions: *run this conversation* is an assertion that the conversation exists, so it
  raises; *is there a conversation here?* is a question, so it answers.
- What this probe **cannot** show is the third case, and its absence is the lesson. If `s-2` had been
  created — one line earlier in this same file, or by another request an hour ago — there would be no
  exception here and no `None`. The run would go through, the model would be shown four events
  belonging to somebody else, and the output would be an answer.
- So the failure mode is not "wrong id crashes" and it is not "wrong id is empty". It is: **wrong id
  that happens to exist is indistinguishable, from inside the process, from right id.**

### Which of the two amnesias is it?

Day 4 part 2.2's failure and this one arrive looking the same to whoever reports it — "it forgot what
I just said". The two are separated by where you look, not by what the user says:

| | Day 4 part 2.2 — the reply that was never filed | Today — the wrong slot |
| --- | --- | --- |
| What the model is shown | the thread with the model's own turns missing: two `user` turns in a row | a complete, well-formed thread that belongs to another conversation |
| What the store says | on day 4 there was no store; the list in your process was short by half | the session holds the right number of events — four per question — and they are the wrong ones |
| The first thing to check | count the turns in the outgoing request, and look for two consecutive `user` roles | print `session.id`, `user_id` and `app_name` beside the id the caller asked for, and read the first event's text |
| What it looks like on one question | perfect. Turn one has nothing to file yet, so a single-question smoke test passes | perfect, if the wrong slot is empty. A fresh id looks exactly like a fresh conversation |
| The fix | append the model's reply to the thread — one line | fix the join between the caller and the id; the storage was never wrong |

**Line by line:**

- The row that does the work is the second one. On day 4 the evidence was in the request; today the
  evidence is in the store, and the request is beyond reproach. Looking in the wrong one of those two
  places is how this costs a week.
- The last row is the reason to keep them apart. Day 4's was a bug in this project's code. Today's is
  a bug in whatever decides the id — a route, a cookie, a queue key — and no amount of reading
  `agent.py` will find it.

### And the one this project has right now

`ask_desk/agent.py`'s `ask`, printed whole by **day 06 part 1.1**, builds a brand-new
`InMemorySessionService()` inside the function and creates `session_id="s-1"` in it every time. That
is deliberate for a one-shot command — `run.py adk "..."` asks one question and exits — and it is
worth naming out loud rather than leaving as an accident:

| Line, from the file day 06 part 1.1 printed | What it does, and the failure it prevents or causes |
| --- | --- |
| `session_service = InMemorySessionService()` inside `ask` | A fresh, empty store per call. Prevents one command's conversation leaking into the next; **causes** every `run.py adk` invocation to start from nothing, however many times you run it. |
| `session_id: str = "s-1"` as a default parameter | A fixed, guessable id. Harmless here because the store is new each time; the same default in a long-running server would put every user in one slot. |
| `await session_service.create_session(...)` before the runner | Creates the slot, so `run_async` cannot hit the `SessionNotFoundError` above. This is the line that makes an unknown id impossible rather than merely unlikely. |

So the honest statement about this project today: it has a session and it does not yet have a
conversation. Day 10 puts the desk behind HTTP, where the store outlives the request and the id
starts arriving from outside — and that is the first point at which everything in this part can
actually go wrong.

## When it breaks

The loud one arrives first, usually from a queue worker or a retry that reconstructs a request from a
stored payload:

```console
google.adk.errors.session_not_found_error.SessionNotFoundError: Session not found: s-2
```

Somebody sees that at three in the morning, adds a `create_session` call before the run so it cannot
happen again, and goes back to bed. That is the wrong fix and it is worse than the error: the missing
session was evidence that the id was being derived incorrectly, and creating one on demand converts
every future occurrence into a silent empty conversation. The smallest honest fix is to log the id
alongside where it came from, then find out why it names nothing; if new conversations really are
allowed here, they get their own explicit branch, so that "start fresh" is a decision in the code and
not a fallback.

## In production

**What a senior writes instead.** The `session_id` is never taken from the client. The server mints
it, stores it against the authenticated user, and looks it up on each request; `user_id` comes from
the token, never from the body. And they include all three parts of the address in every structured
log line for a turn, because the difference between the two amnesias in the table above is one
`grep` away when the id is logged and a week's work when it is not.

**What degrades at scale.** The number is **zero**: the number of exceptions raised, and the number
of log lines produced, by a run against a valid-but-wrong session. It costs the same as a correct
run, takes the same path, and returns an answer of the same shape. Nothing in your error rate moves,
so no alert fires and no dashboard changes colour — the whole cost lands on users noticing that the
desk is confidently talking about something else, and on however long it takes for enough of them to
say so.

**The review comment.** "This takes `session_id` from the request body and passes it straight to
`run_async`. Any caller can then read any other caller's conversation by guessing an id, and there is
no error when they do — the run succeeds and returns an answer. Please derive the session from the
authenticated user, and add a test that a session belonging to user A cannot be run as user B."

**The interview question.** "A user says your assistant 'forgot the last thing they told it'. Give me
two mechanisms that produce exactly that report, one in how the conversation is assembled and one in
which conversation was fetched, and say which single piece of evidence would tell you which of the
two you are looking at."
