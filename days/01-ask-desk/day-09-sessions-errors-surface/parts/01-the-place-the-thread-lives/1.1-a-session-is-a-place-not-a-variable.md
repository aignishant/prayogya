## One-line answer

The conversation you carried by hand on day 4 now lives in a **session** — a stored thing addressed
by the triple `(app_name, user_id, session_id)` and held by a session service, not by any variable
in your code — and one question puts **four** events into it, because the question itself is stored
alongside the work it caused.

## The idea

Walk onto a ward at handover. The nurse going off shift does not tell the nurse coming on what
happened to the patient in the third bed; there would be no way to check it later and no way to
correct it. What happens instead is that everything is already written, and it is in a numbered slot
on the trolley at the foot of that bed. The slot is the address. The notes are in it. Anyone on any
shift who can read the number at the foot of the bed can pick up exactly what was written, in order,
and add the next line to it.

That is the change from day 4. On day 4 the thread was `Conversation.contents`, an ordinary Python
list living in your process, and you attached the whole of it to every request yourself. It was
correct, and it had the property that everything on a trolley-less ward has: it existed only for as
long as the person holding it stayed on shift. Close the process and the conversation was gone,
because a list is a thing in memory and nothing else.

A **Session** — `docs/GLOSSARY.md`, introduced in day 6 part 2.1, and deliberately not redefined
here — is that list moved into a numbered slot. Two words matter about the move. The first is that the slot has
an **address made of three parts**, not one: which application, which person, and which conversation.
`session_id` alone would collide the moment two applications, or two people, each opened a
conversation they both called `s-1`. The second is that the slot belongs to a **session service** —
the object that owns the storage and hands sessions out. Your code does not hold the conversation any
more. It holds the address, and asks.

That second word is the one that changes how you debug. When the conversation was a list, the
question "what does the model know?" was answered by printing a variable. Now it is answered by
asking a service for a session, and the only thing that decides which conversation you get is the
address you typed. There is no other input. Nothing about the address is validated against your
intent, because nothing knows your intent — which is the whole of the next part.

And one detail that catches everyone, because it makes a count come out wrong. What goes into the
slot is not just what the desk did. **Your question goes in too.** The patient's own words are part
of the notes, written down before anything was done about them, because a record of the treatment
with no record of the complaint is not a record. So a question that produces three things the desk
did leaves **four** entries behind, and a count that expected three will be off by one for every
question, for ever.

**Line by line:**

- `sessions = InMemorySessionService()` is created **inside `turns`**, not at module level and not
  once for the whole subcommand. That is what makes the second experiment honest: the two-session run
  starts from an empty store, so the counts it prints cannot be inherited from the first run. A store
  shared across both would have made `s-1` start the second experiment already holding four events,
  and the output would have looked like a bug in the framework rather than in this file.
- `scripted.LOOKS_IT_UP + scripted.LOOKS_IT_UP` — the script is doubled because this subcommand asks
  two questions and each one costs two model calls. `ScriptedModel` repeats its last step for ever
  once the script runs out, so a single copy would still have produced output; it would have produced
  the *wrong* output, with the second question answered by a step written for the first. Doubling the
  list is the cheapest way to make each question get its own two steps. The double itself is printed
  whole by day 08, in `days/01-ask-desk/day-08-events-streaming/`.
- `agent.build_desk(model)` and `agent.run_config()` are this project's own helpers, printed with the
  event walkthrough in `days/01-ask-desk/day-08-events-streaming/`. They are what keep a scripted
  model out of anything user-facing and keep the bound at this project's own `MAX_CALLS_PER_QUESTION`
  rather than at ADK's default.
- The `if await sessions.get_session(...) is None:` guard is the interesting line, and the comment
  above it is the reason. `create_session` does not return the existing session when you call it
  twice with one id — it **raises**. So a loop that creates before every question crashes on the
  second one, and the fix is not a `try`/`except`: it is to ask whether the slot is occupied, and to
  create only when it is not. *When it breaks*, below, is that crash.
- `session_id=sid` is passed to `run_async`, and `user_id` and `app_name` come from the same three
  places every time. Those three values are the whole address; there is no fourth input and no hidden
  default that would rescue a wrong one.
- `len(stored.events)` is read back **from the service**, after the run, rather than counted as the
  events go past. Counting them as they go past would count what `run_async` yielded, which is a
  different number — that is the point the transcript below lands, and it only lands if the count
  comes from the store.
- `import asyncio` and the two `from` lines sit **inside** `session`, matching the arrangement day 06
  part 2.1 established for `adk`: `run.py check` must not import the framework, because the gate has
  to be runnable on a machine where the framework is the thing that is broken.
- `case ["session"]:` is added to `main`'s `match`, above `["eval"]`. The order of cases here is the
  order of the docstring, which is the order somebody reads them in.

**Line by line:**

- `s.id`, `s.app_name`, `s.user_id` are the three parts of the address, and the session hands all
  three back. That is worth seeing once: the triple is not a convention you keep in your head at the
  call site — it is stored on the thing, so a session you fetched can always say what it is.
- **Four events for the first question, four for the second.** Day 08's walkthrough of the same
  script shows `run_async` yielding **three** — a tool call, a tool result, and the final answer. The
  fourth is `author=user`, first in the list, and it is your question. The runner stored it before it
  did any work.
- So the two counts answer two different questions. *How many events did I have to handle?* is three.
  *How many events are in the session?* is four. A dashboard that renders `len(session.events)` and a
  test that counts what the loop saw will disagree by exactly one per question, and neither of them
  is wrong.
- `author` is a name, not a role: `user` for the question and `ask_desk` — the agent's own name — for
  everything the desk produced. In this project there is one agent, so that column is dull. From P03
  onward there are several, and this is the field that says which of them spoke.
- **Two invocation ids across eight events, four apiece.** An *invocation* is one call to
  `run_async` for one user message, and every event it produces carries the same
  `invocation_id`. That is the grouping to reach for when a session has hundreds of events and you
  want the four that belong to the question somebody is complaining about.
- The ids differ between the two questions in one session, which is the point: a session is the
  thread, an invocation is one exchange inside it. The session is what the model sees; the invocation
  is what you debug.

The signature that fixes the address, quoted verbatim from
`https://adk.dev/api-reference/python/google-adk.html`, read 2026-09-09:

> `abstractmethod async create_session(*, app_name, user_id, state=None, session_id=...)`

**Line by line:**

- `abstractmethod` — `create_session` is declared on the base class and implemented by each service.
  `InMemorySessionService` is one implementation and the only one this project uses; a database-backed
  one answers the same call, which is why the address is three parts rather than a Python object
  reference. An address can be written down and sent; a reference cannot.
- Everything is **keyword-only**, after the bare `*`. There is no positional order to get wrong, so
  the failure mode where `app_name` and `user_id` are swapped cannot happen silently.
- `session_id=...` has a default. Omit it and the service invents one, which is right for a web
  front end handing out a new conversation per visitor and wrong for this project, where
  `run.py session` needs to name the same slot twice.
- `state=None` is the fourth thing a session can hold and this project never uses it. It is named
  here so its absence is a decision rather than an oversight; P06 is where a tool writes into it.

*Observed on this machine on 2026-09-10: google-adk 2.8.0, CPython 3.12.12, uv 0.12.3.*

Somebody hits this on the second turn of the first real conversation, reads it as the framework being
awkward, and wraps it in `try: ... except AlreadyExistsError: pass`. That works and it hides the
question worth asking, which is *why did my code think this was a new conversation?* The refusal is
the good behaviour: if `create_session` silently returned the existing session, then a caller who
meant to start fresh — a "new chat" button, a test that wanted a clean slate — would get somebody
else's history back with no signal at all, and every symptom in part 1.2 would arrive with no error
anywhere near it. The smallest fix is the one in the file above: ask `get_session` first, and create
only when the slot is empty.

## In production

**What a senior writes instead.** They do not let the three parts of the address be typed at the call
site. `app_name` comes from one constant — this project has `APP_NAME` in `ask_desk/agent.py` for
exactly that reason — `user_id` comes from whatever authenticated the request and is never accepted
from a request body, and `session_id` is minted by the server and handed to the client, not chosen by
it. A client that picks its own `session_id` can pick somebody else's, and there is no error for
that; part 1.2 is what it looks like when they do.

**What degrades at scale.** The number is **four events per question, held for ever**. Every count in
this part came out of `InMemorySessionService`, which is a dictionary in your process: nothing is
written to disk, nothing expires, and nothing is evicted. A desk in one process that answers a
thousand questions is holding four thousand events, all of them resent to the model as the thread
grows, and all of them lost the moment the process restarts. Both halves of that are bad and they
fail in opposite directions — cost that grows without bound until an availability event that discards
the lot. P16 Recall Desk is where sessions move to a database and the difference between a session
and a memory gets its own project.

**The review comment.** "`create_session` is being called on every turn and the `AlreadyExistsError`
is swallowed. That means we can no longer tell a genuinely new conversation from a repeated one, and
a 'new chat' that silently resumes an old thread will look like a model bug. Please call
`get_session` first and create only on `None` — and please move `user_id` off the request body: right
now any caller can read any other caller's session by guessing the id."

**The interview question.** "Your agent stores conversations in a session service keyed by
`(app_name, user_id, session_id)`. A user reports that their chat history disappeared after a deploy,
and a second user reports seeing a conversation that was not theirs. Which part of that triple is
implicated in each report, and what would you look at first to tell the two apart?"
