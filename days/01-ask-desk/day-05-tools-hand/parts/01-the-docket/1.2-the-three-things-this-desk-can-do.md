## One-line answer

A tool is two objects — the Python function that does the work and the JSON declaration that
describes it — kept in one file because nothing in the language, the provider or your editor will
ever tell you they have stopped agreeing.

## The idea

Behind the wall there is a menu pinned up on the kitchen side, and it is not the same object as the
menu on the table. The one in the dining room is the one the waiter reads from. The one by the pass
is the one the cooks work to. Every kitchen that has ever run has a story about the night those two
went out of step: a dish was taken off, the printed menus went out, and the board by the pass still
had it — or the other way round, and orders came through for something nobody had prepped.

Nothing catches that. There is no machine at the slot in the wall that compares the two menus.
Somebody notices, eventually, because a plate went out wrong or a docket came through for a dish
that does not exist. The only reliable defence any real kitchen uses is embarrassingly simple:
**keep both menus in one place, so changing one without the other is something you have to do on
purpose rather than something you can do by forgetting.**

That is why this desk's three tools and the three JSON objects that describe them live in one file,
next to each other, in the order they are named. It is not tidiness. It is the only mechanism
available. Python will not complain if a declaration names a parameter the function does not have;
the provider will not complain, because the provider has never seen the function; your type checker
will not complain, because a dictionary of strings is a valid dictionary of strings whatever is in
it. The drift is invisible until the day a call arrives that cannot be served, and part 2.2 is that
day.

Two more things are settled in this file, and they are worth naming before you read it.

The first is **what a tool returns**. Every one of these three returns a plain dictionary, and every
value in it is something JSON can carry — strings, numbers, lists, dictionaries. That is not an
aesthetic choice: the result is going back to the model as JSON, so a value that cannot be
serialised is a value that cannot be returned. A tool that returns one of your own objects works
perfectly in a test and fails at the moment the result crosses the wall.

The second is that **the data is synthetic**. Every note, every service, every timestamp in this
project's knowledge base was written for this curriculum. That is a standing rule here rather than a
convenience: real support tickets carry real names and real incidents, and a curriculum that trains
you on them teaches you to be careless with them.

## The mechanism

`projects/01-ask-desk/ask_desk/tools.py`, whole file — the kitchen and the menu by the pass, in one
place:

```python
# ask_desk/tools.py
"""The three things this desk can do, and the JSON that describes them to a model.

A tool is two objects that must not drift apart: a Python function that does the work, and a
declaration that tells the model the function exists, what it is for, and what arguments it takes.
The model never sees your code. It sees the declaration and nothing else, so the declaration is the
entire interface — a wrong description is a wrong tool, and it fails by being called at the wrong
moment rather than by raising.

Day 2 writes both halves by hand. Day 4 replaces the right-hand half with `FunctionTool`, which
derives it from the function itself, and the comparison is the point of that day.

All data here is synthetic.

Declaration shape verified against https://ai.google.dev/api/generate-content on 2026-09-09.
"""

from __future__ import annotations

import json
from pathlib import Path
from typing import Any

DATA_FILE = Path(__file__).with_name("data") / "notes.json"


def _load() -> dict[str, Any]:
    """Read the synthetic store. Small enough to read per call; a cache would hide staleness."""
    return json.loads(DATA_FILE.read_text(encoding="utf-8"))


class UnknownTool(RuntimeError):
    """The model asked for a tool that does not exist. Never guess which one it meant."""


def search_notes(query: str, limit: int = 3) -> dict[str, Any]:
    """Find knowledge-base notes matching a query. An empty list is a valid answer."""
    words = [w for w in query.lower().split() if len(w) > 2]
    scored = []
    for note in _load()["notes"]:
        haystack = f"{note['title']} {note['body']} {' '.join(note['tags'])}".lower()
        score = sum(1 for w in words if w in haystack)
        if score:
            scored.append((score, note))
    scored.sort(key=lambda pair: (-pair[0], pair[1]["id"]))
    hits = [{"id": n["id"], "title": n["title"], "service": n["service"]}
            for _, n in scored[:limit]]
    return {"query": query, "count": len(hits), "hits": hits}


def fetch_note(note_id: str) -> dict[str, Any]:
    """Return one note in full by its id, or an error saying it does not exist."""
    for note in _load()["notes"]:
        if note["id"].lower() == note_id.lower():
            return note
    return {"error": f"no note with id {note_id!r}",
            "known_ids": [n["id"] for n in _load()["notes"]]}


def check_service_status(service: str) -> dict[str, Any]:
    """Return the current status of one service: operational, degraded or maintenance."""
    services = _load()["services"]
    if service.lower() not in services:
        return {"error": f"no service named {service!r}", "known": sorted(services)}
    return {"service": service.lower(), **services[service.lower()]}


#: The functions, by the name the model will use. `dispatch` looks up here and nowhere else.
REGISTRY = {
    "search_notes": search_notes,
    "fetch_note": fetch_note,
    "check_service_status": check_service_status,
}

#: What the model is told. Hand-written on day 2; every field here is a promise about the function
#: above it, and nothing checks that the two agree.
DECLARATIONS: list[dict[str, Any]] = [
    {
        "name": "search_notes",
        "description": (
            "Search the internal knowledge base for notes matching a query. "
            "Returns ids and titles only. An empty list means nothing matched, which is a "
            "valid answer and must not be reported as an error."
        ),
        "parameters": {
            "type": "object",
            "properties": {
                "query": {
                    "type": "string",
                    "description": "Words to search for, e.g. 'vpn file share'.",
                },
                "limit": {
                    "type": "integer",
                    "description": "Maximum notes to return. Defaults to 3.",
                },
            },
            "required": ["query"],
        },
    },
    {
        "name": "fetch_note",
        "description": (
            "Return the full text of one knowledge-base note by its id. "
            "Use search_notes first to find an id; do not guess one."
        ),
        "parameters": {
            "type": "object",
            "properties": {
                "note_id": {
                    "type": "string",
                    "description": "The note id, e.g. 'KB-101'.",
                },
            },
            "required": ["note_id"],
        },
    },
    {
        "name": "check_service_status",
        "description": (
            "Return the current operational status of one service. "
            "Known services are: vpn, printing, mail, identity."
        ),
        "parameters": {
            "type": "object",
            "properties": {
                "service": {
                    "type": "string",
                    "description": "One of: vpn, printing, mail, identity.",
                },
            },
            "required": ["service"],
        },
    },
]


def dispatch(name: str, args: dict[str, Any]) -> dict[str, Any]:
    """Run the tool the model asked for, and return a dict the model can be shown.

    Two rules, and both are about honesty rather than convenience. An unknown name raises rather
    than guessing at a near match, because a model that misremembers a tool name needs to be told,
    not accommodated. And an exception inside a tool is returned to the model as an `error` key
    rather than being allowed to kill the run — the model can then say what went wrong, which is
    more useful than a traceback, and the run's own error is still visible in the turn log.
    """
    if name not in REGISTRY:
        raise UnknownTool(
            f"the model asked for {name!r}, which this desk does not have. Known tools: "
            f"{', '.join(sorted(REGISTRY))}. A tool the model invents is a sign the declarations "
            f"and the registry have drifted apart."
        )
    try:
        return REGISTRY[name](**args)
    except TypeError as exc:
        # The model sent arguments that do not fit the signature: a missing required field, or a
        # name that is not a parameter. The declaration promised something the function does not
        # accept, and this is where that promise is broken.
        return {"error": f"{name} rejected these arguments: {exc}", "arguments_received": args}
```

**Line by line:**

- The module docstring says **"Day 2 writes both halves by hand. Day 4 replaces the right-hand
  half"** — and those are the *project's* days, not the curriculum's. This project has seven days of
  its own, numbered 1 to 7, and they are curriculum days 4 to 10. So the project's day 2 is the day
  you are reading, and its day 4 is curriculum day 7. Every file in this project counts its own
  days, because a project that has been copied to another machine has no idea what day 5 of a
  curriculum was.
- `DATA_FILE = Path(__file__).with_name("data") / "notes.json"` — anchored to **this file**, never
  to the working directory. `Path("data/notes.json")` would resolve against wherever the shell
  happened to be, so the same code would find the notes when run from the project folder and raise
  `FileNotFoundError` when run from anywhere else. `with_name` swaps the filename and keeps the
  directory, which is the sibling relationship these two paths actually have on disk.
- `_load()` re-reads and re-parses the file **on every call**, and the docstring says why out loud:
  a cache is the correct optimisation and it is also the thing that makes a data change invisible
  until the process restarts. At this size the read costs nothing, and the honest default at
  teaching scale is the one with no hidden state. The production section below says what to write
  instead and when.
- The leading underscore on `_load` is the module saying *this is not part of the interface*. The
  three tool functions and `dispatch` are; `_load` is plumbing, and a reader deciding what to import
  needs that distinction more than the interpreter does.
- `class UnknownTool(RuntimeError)` — a named exception, defined here beside the code that raises
  it, so that a caller can catch **this** failure without catching every other runtime error. Part
  2.2 is entirely about why this one raises rather than returning.
- `search_notes(query: str, limit: int = 3)` — the type hints are not decoration even though nothing
  here reads them. They are the specification that the declaration below has to match by hand today,
  and that the framework will read automatically on day 7. Writing them now means day 7 changes one
  thing rather than two.
- `[w for w in query.lower().split() if len(w) > 2]` — lower-case, split on whitespace, drop words
  of two characters or fewer. That last filter is what stops `is`, `my`, `to` and `on` from matching
  half the corpus and flattening every score to the same number. It is crude, it is stated as crude,
  and its consequences are visible in the transcript below.
- `haystack = f"{title} {body} {' '.join(tags)}".lower()` — one flat string per note, so a match may
  come from anywhere in it. That is generous on purpose: a searcher that only looked at titles would
  miss KB-101 for the word "mount", which appears only in the body.
- `score = sum(1 for w in words if w in haystack)` — **substring containment, one point per distinct
  query word.** Not word-boundary matching, not stemming, not vectors. This is the line that makes
  the third hit in the transcript below wrong, and naming that here rather than discovering it later
  is the difference between a teaching example and a toy.
- `if score:` — notes scoring zero are dropped rather than returned with a score of nothing. An
  empty result is a real answer, which is precisely what the declaration's description tells the
  model.
- `scored.sort(key=lambda pair: (-pair[0], pair[1]["id"]))` — descending by score, then **ascending
  by id**. The second key is the important one and it is easy to leave out: without it, two notes on
  the same score come back in whatever order the file happened to list them, and the same query
  returns different results after somebody reorders the JSON. A tie-break on a stable value is what
  makes this function testable at all.
- The `hits` comprehension returns **`id`, `title` and `service` only** — never `body`. That is the
  decision the declaration's description reports as "Returns ids and titles only", and it is a real
  economy: five bodies is far more text than five titles, and the model only needs one of them. The
  cost is a second round trip through `fetch_note`, which is what the description tells the model to
  expect.
- `return {"query": query, "count": len(hits), "hits": hits}` — the query is echoed back in the
  result. The model already knows what it asked, so this is for the human reading the turn log
  later, and it costs a handful of tokens to make a transcript readable without cross-referencing.
- `fetch_note` compares `note["id"].lower() == note_id.lower()` — case-insensitively, because
  `kb-101` is what a model produces about as often as `KB-101` and refusing one of them teaches
  nothing. The lookup is a linear scan over five notes; a dictionary would be faster and would need
  building on every `_load`, and at this size the scan is the simpler thing to read.
- `fetch_note` **returns** an error dictionary for an unknown id rather than raising, and includes
  `known_ids`. This is the single most useful line in the file for the model's behaviour: handed
  `{"error": ..., "known_ids": [...]}`, the model can pick a real id and try again inside the same
  question. Handed an exception, the run stops and a person has to restart it.
- `check_service_status` returns `{"service": service.lower(), **services[...]}` — the normalised
  service name plus everything the store holds. The dictionary unpacking means adding a field to the
  JSON automatically reaches the model, which is convenient and is also how a field you did not
  intend to expose gets exposed. At this size that is the right trade; behind a real status API it
  is not.
- `REGISTRY` maps the **model-facing name** to the function object, and the comment says `dispatch`
  looks here and nowhere else. That is a deliberate refusal of the obvious alternative — reaching
  into `globals()` or `getattr(module, name)` — which would let a model call any function in this
  file, imported ones included, by naming it. The registry is a list of what is reachable, and a
  list of what is reachable is a security boundary even when nothing about it looks like one.
- `DECLARATIONS` is a `list`, and its order is the order the model sees. That order is not neutral:
  `search_notes` first, `fetch_note` second is the sequence the desk wants used, and the
  `fetch_note` description reinforces it in words.
- The `#:` comments above `REGISTRY` and `DECLARATIONS` say what each **is for**, and the second one
  states the whole problem of this part in one sentence: *every field here is a promise about the
  function above it, and nothing checks that the two agree.* That sentence is in the file rather
  than in this document because the person who breaks it will be reading the file.
- The three declarations sit **below** the three functions in the same module. That placement is the
  mechanism from *The idea*: a rename shows up in one diff, and a reviewer looking at a changed
  signature has the description on the screen.
- `dispatch(name, args)` takes the name and an argument dictionary, which is exactly the shape the
  model's `functionCall` part carries. No unpacking is done by the caller, so the mapping from wire
  format to Python call happens in one place.
- `if name not in REGISTRY: raise UnknownTool(...)` — **raises**, and does not guess. There is an
  obvious and tempting alternative here: fuzzy-match `lookup_ticket` to the nearest known name and
  run that. Part 2.2 is about why that is the worst available choice.
- The error message interpolates `', '.join(sorted(REGISTRY))` — the actual list of tools, sorted so
  the message is stable between runs. An error that names the alternatives is an error somebody can
  act on without opening the source.
- `return REGISTRY[name](**args)` — the argument dictionary is splatted as **keyword** arguments, so
  the keys in the schema's `properties` must equal the parameter names in the signature. This is the
  single line where the declaration and the function are forced to agree, and it is also the line
  that raises when they do not.
- `except TypeError as exc: return {"error": ...}` — an exception from calling the function is
  converted into a result the model can read. `TypeError` and nothing wider: a `KeyError` from
  inside `search_notes` is a bug in this project and must not be dressed up as a message to the
  model. The comment above it says exactly which two cases it covers, and part 2.2 causes both.
- `"arguments_received": args` echoes what actually arrived. Without it the model is told its
  arguments were wrong and not what they were, and it will frequently send the same ones again.

**Line by line:**

- Two top-level keys, `notes` and `services`, because the three tools ask two different questions.
  `search_notes` and `fetch_note` read the first; `check_service_status` reads the second. One file
  rather than two, because it is one store and splitting it would mean two paths, two reads and two
  chances for them to disagree about what exists.
- `notes` is a **list** and `services` is an **object**. That is not inconsistency: a note is looked
  up by scanning, and a service is looked up by name, so the shape of each matches the access. Making
  `services` a list would put a linear scan in `check_service_status` for no gain.
- Every note carries `id`, `title`, `service`, `tags` and `body` — five fields, and `search_notes`
  returns three of them. The store deliberately holds more than the search returns, which is what
  makes the two-call pattern real rather than decorative.
- `tags` exists alongside `title` and `body` even though the scorer flattens all three into one
  string. It earns its place the moment scoring stops being flat: a tag match is a much stronger
  signal than a body match, and P18 is where that weighting is taught.
- **`KB-311` is the note that breaks the search**, and it is in this file on purpose. Its title
  contains "Shared mailbox", so the query word `share` is a substring of `shared` and it scores on a
  VPN question. The transcript below shows it happening. A corpus with no such collision would let
  the flat scorer look correct.
- The `since` values are UTC instants with a `Z` suffix, in the format the rest of this curriculum
  uses. They are strings rather than dates because JSON has no date type — every date that crosses a
  wire is a string somebody agreed on, and this file is a small reminder of that.
- `"status": "degraded"` on `vpn`, with a `note` saying the gateway itself is up. That distinction —
  degraded but not down — is the reason `check_service_status` exists as a separate tool from
  `search_notes`: the knowledge base says what is *known*, the status says what is *true right now*,
  and answering "is the VPN down?" well needs both.
- `"note": ""` on the two healthy services. An empty string, not a missing key, so the model always
  receives the same shape and never has to reason about whether a field being absent means anything.
- `identity` is in `maintenance` with a note saying sign-in is unaffected. Three distinct statuses
  across four services means every branch of a status answer has a fixture behind it, which is what
  makes this file usable as an eval corpus in P18 rather than only as a demo.
- Every incident described here is invented. No real ticket, no real person, no real network. The
  addresses are from the private ranges, the ids follow a made-up scheme, and the failures are
  plausible because they were written to be plausible.

**Line by line:**

- `"count": 3` and three hits, because `limit` defaulted to `3`. Nothing passed it, the Python
  default applied, and the model would have got the same result — which is why the declaration
  mentions the default in prose.
- KB-101 is right and it is right for the right reason: `vpn`, `file` and `share` all appear in it,
  so it scores three and sorts first.
- KB-102 scores one, on `vpn`. Reasonable, and correctly below KB-101.
- **KB-311 is wrong, and it is a `mail` note answering a VPN question.** It scored because `share`
  is a substring of `shared`, in "Shared mailbox". Not a typo, not a bad fixture: this is
  `if w in haystack` doing exactly what it says, and there is no word-boundary check anywhere in
  this file to stop it.
- The `service` field in each hit is what makes the error visible at a glance — `"service": "mail"`
  in a list of VPN answers is a mismatch you can see without reading the title. A search result that
  omitted it would have hidden this.
- What this costs in practice: the model is handed a plausible-looking third result and may fetch
  it, spend a round trip on it, and mention a mailbox in an answer about a VPN. Nothing raised.
  Nothing logged. **The only thing that catches this class of failure is a retrieval eval** — a set
  of queries with known-correct answers, scored on every change — and building one is P18. Naming
  the gap here is the honest version; calling the scorer good enough would not be.

## When it breaks

The failure that reaches a user does not look like a failure. It looks like the transcript above,
and the wrong line in it is the one that reads best:

```console
    {
      "id": "KB-311",
      "title": "Shared mailbox stops receiving after a licence change",
      "service": "mail"
    }
```

Somebody asks why file shares keep dropping on the VPN, and the desk's answer mentions a shared
mailbox and a licence change. Nothing errored — the search ran, the model read three titles, and one
of them was about sharing. The smallest fix is to score on word boundaries rather than substrings,
which turns `share in "shared"` from a match into a miss; the fix that actually holds is a set of
queries with known-correct answers, run on every change to the scorer, and that is P18.

## In production

**What a senior writes instead.** They do not hand-write `DECLARATIONS`, and day 7 shows what
replaces it. They also do not write `search_notes` — substring scoring over a JSON file is replaced
by a real index the first time the corpus outgrows a screen, and the tool keeps its signature while
its body changes. The habit worth copying from this file is the placement: whatever generates the
declaration lives in the same module as the function, so drift is a diff rather than a discovery.

**What degrades at scale.** `_load()` re-reads and re-parses the entire JSON on **every** call, and
`fetch_note` calls it **twice** on the miss path — once to scan, once to build `known_ids`. At five
notes that is nothing. At a corpus of ten thousand notes it is two full parses per failed lookup,
inside a loop that may run six times for one question, so a single question can parse a file of
many megabytes a dozen times over. The fix is to load once at import and expose an explicit
reload; the reason it is not here is that a cache added before the read is understood is a cache
nobody can reason about.

**The review comment.** "`fetch_note` calls `_load()` twice on the miss path — hoist it. And
`search_notes` scores with `w in haystack`, so `share` matches `shared` and a mail note ranks
against a VPN query; there is a fixture in `notes.json` that does exactly this. Either match on word
boundaries or open a ticket for the retrieval eval, but do not ship this scorer with no test that
would notice it regressing."

**The interview question.** "You have a tool whose JSON declaration and whose Python signature are
maintained by hand. Describe three ways they can drift apart, say which of the three produces an
exception and which two produce a wrong answer with no error, and say what you would put in CI to
catch all three."
