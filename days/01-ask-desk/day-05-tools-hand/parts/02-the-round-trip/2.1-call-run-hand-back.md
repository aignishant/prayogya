## One-line answer

A model cannot run anything, so a tool call is a **request** it makes of you: it returns a
`functionCall` part instead of an answer, you run the function, you append a `functionResponse` turn
carrying the result, and you send the whole conversation again — which is why one question with
tools costs at least two provider calls and never exactly one.

## The idea

Watch what the waiter actually does after they take the order, because it is not one journey. They
write the docket and put it through the slot. Then they leave. The kitchen has the docket and the
waiter has nothing — no plate, no answer, nothing to bring you. Some time later a plate appears on
the pass and the waiter picks it up and carries it to your table, and only then does anything arrive
in front of you.

Two trips through the same doorway, in opposite directions, for one order. That is not inefficiency
and there is no arrangement that removes it: the waiter cannot cook and the kitchen cannot see your
table, so somebody has to walk both ways. A restaurant where the order and the plate are one motion
is a restaurant where the waiter is also the cook.

Your model is in exactly that position and it is worth being precise about the limitation, because
it is easy to describe it as something more magical than it is. **The model cannot execute
anything.** It has no interpreter, no file system, no network. When it decides that a tool is
needed, all it can do is produce a message that says so — a **tool call**, which is a part of its
reply carrying the tool's name and an object of arguments, in place of the text it would otherwise
have written. That message comes back to you over the same wire as any other reply.

So the sequence for one question, when a tool is involved, is: you send the conversation and the
declarations; the model replies with a tool call; **you** run the function, in your process, with
your credentials, against your data; you append a **tool-result turn** carrying what the function
returned; and you send the whole conversation again. Now the model has the result and can answer —
or ask for another tool, in which case you go round again.

Three things follow from that, and each one is a decision this project has to make in code.

First, **the number of provider calls per question is now variable and at least two.** Day 4 could
say "one question, one request" and mean it. Today a question costs one call to be asked for a tool,
and a second to be answered afterwards — and if the model wants `search_notes` and then `fetch_note`
and then `check_service_status`, it costs four. The hub's budget section says two as the floor and
names the ceiling, and the ceiling is the third point below.

Second, **the model's tool-call turn is part of the conversation and must be filed like any other.**
It is tempting to treat it as plumbing — a signal you consume and discard — and if you do, the
conversation ends up containing a tool result with nothing in front of it explaining why it is
there. The provider is stateless, so the whole thread is resent every time; a result with no request
above it reads to the model exactly as strangely as it would to you.

Third, **a loop that ends when the model stops asking for tools ends when the model chooses to.**
That is a control-flow decision handed to a system that is not obliged to make it. The bound has to
live in your code, where the model cannot reach it, and it has to be a hard refusal rather than a
warning. This is the day that stops being theoretical, because today is the first day the loop can
go round more than once.

`projects/01-ask-desk/ask_desk/provider.py` — appended below `text_of`, which day 4 printed. The
marker comment is in the file, not in this document:

```python
# ask_desk/provider.py
# ── everything above this line is unchanged from the file day 4 printed whole ──

# ── added on day 2, for tools ──────────────────────────────────────────────────────────────────

def function_calls(candidate: dict[str, Any]) -> list[dict[str, Any]]:
    """Every `functionCall` part in a candidate, in the order the model produced them.

    A list, not an optional single call: one turn may ask for several tools at once, and code that
    reads `parts[0]` runs the first and silently discards the rest.
    """
    parts = candidate.get("content", {}).get("parts", [])
    return [part["functionCall"] for part in parts if "functionCall" in part]


def function_response_message(calls_and_results: list[tuple[dict[str, Any], dict[str, Any]]],
                              ) -> dict[str, Any]:
    """Build the turn that hands tool results back to the model.

    One message carrying one part per call, in the order they were requested. The provider matches
    a result to its call by `name`, and by `id` when the call carried one, so both are echoed back
    exactly as received rather than reconstructed.
    """
    parts = []
    for call, result in calls_and_results:
        response_part: dict[str, Any] = {"name": call["name"], "response": result}
        if "id" in call:
            response_part["id"] = call["id"]
        parts.append({"functionResponse": response_part})
    return {"role": "user", "parts": parts}
```

**Line by line:**

- The comment `# ── added on day 2, for tools ──` is a real line in the real file, and it says
  *this project's* day 2 — which is the day you are reading. Every file in this project dates its
  own additions in the project's numbering, because a project copied to another machine has no idea
  what curriculum day it was written on.
- `function_calls` returns a **list**, and the docstring gives the reason in one sentence. A turn may
  carry several `functionCall` parts, and the natural mistake is to write `parts[0]` and treat the
  call as singular. That version works for months, because most turns ask for one tool, and then
  silently drops the second call the day the model asks for two — the first tool runs, the second
  never does, and the model is handed one result where it expected two.
- `candidate.get("content", {}).get("parts", [])` — two defaulted lookups rather than
  `candidate["content"]["parts"]`. A candidate that was blocked, or that finished on a safety stop,
  can arrive with no `content` at all, and the subscript version meets that with a `KeyError` that
  names nothing useful. Defaulting to an empty list means "no calls", which is exactly the truth in
  that situation.
- `if "functionCall" in part` — a filter on **key presence**, not a type check and not a
  `try`/`except`. A part in this API is a dictionary with exactly one interesting key: `text`,
  `functionCall`, `functionResponse` and so on. Asking which key it has is asking what kind of part
  it is, and it composes with `text_of`, which day 4 printed and which filters on `"text" in part`
  in the same way. Both functions can run over the same parts list and neither trips over the
  other's parts.
- Note that the key on the wire is `functionCall` in camel case, while the request this project
  builds uses `function_declarations` in snake case. That is not our inconsistency to fix — the
  request and response schemas of this API differ in exactly that way, and matching the wire is the
  only correct behaviour. Normalising one of them "for tidiness" produces a key the provider does
  not recognise.
- `function_response_message` takes a list of **(call, result) pairs**, not two parallel lists and
  not a dictionary keyed by name. Pairs keep a result attached to the call it came from, which
  matters the moment a turn asks for the same tool twice with different arguments — a dictionary
  keyed by name would collapse those two into one.
- `{"name": call["name"], "response": result}` — the name is copied **from the call**, not from the
  registry and not from a variable you happen to have in scope. The model matches a response to its
  request by that string, and reconstructing it means the two can differ.
- `if "id" in call: response_part["id"] = call["id"]` — the id is echoed **when present and never
  invented**. Some calls carry one and some do not, and a fabricated id is worse than a missing one:
  the provider has no way to tell that the id you sent back is not the id it issued.
- `parts.append(...)` in the loop's order — the results go back in the order the calls arrived. That
  is what makes the pairing readable to a human reading the log later, and it costs nothing to
  preserve.
- `return {"role": "user", "parts": parts}` — **one message carrying every result**, not one message
  per tool. And the role is `"user"`, which is the single most contested line in this file. The
  documentation says two different things about it, and the next block is where that is dealt with
  rather than glossed.

**Line by line:**

- `from ask_desk import provider, tools` — `loop.py` now imports `tools`, which is what makes the

  project**; nothing in this file reaches outside the `ask_desk` package, which is the rule that

- `MAX_CALLS_PER_QUESTION = 6` is a **module constant**, not a parameter with a default and not a
  field on `Conversation`. That placement is a decision: a caller who can pass `max_calls=200` can
  remove the bound at a call site, in a file nobody reviewing this one will read. Changing it here
  is a diff on the file that documents why it exists.
- Six, and not three or sixty. Three is below the natural depth of this desk's own tools —
  `search_notes` then `fetch_note` then an answer is three calls on a perfectly ordinary question —
  so a bound of three would refuse correct work. Sixty is not a bound, it is a delay before the same
  failure. Six leaves room for a search, a fetch, a status check and an answer, with slack for one
  wrong turn.
- The comment says **"a count of provider calls, not a timeout and not a token budget"**, and the
  distinction earns its two lines. A timeout bounds how long you wait and not how much you spend; a
  token budget bounds one call's size and not the number of calls. The thing that runs away here is
  the *count*, so the count is what is bounded.
- `class LoopExhausted(RuntimeError)` — its own class, so a caller can catch this and nothing else.
  Part 2.2 is about what it is for.
- The docstring's second paragraph is the design decision, written where the person tempted to
  change it will read it: **raised, never swallowed.** The obvious alternative is to return the last
  text the model produced, which turns a run that hit its limit into a run that looks like it
  answered. There is no field on the return value that would say otherwise, so the caller cannot
  tell, and neither can the log.

- `None` and not `[]`, because `build_request` tests `if tools:` and both are falsy — but `None`

And `ask`, which is **replaced rather than extended**. Day 4's version made exactly one provider
call and returned its text, because with no tools there was nothing to act on. This is the whole
method as it now stands:

```python
# ask_desk/loop.py — inside class Conversation, replacing the single-call version day 4 printed

    def ask(self, question: str) -> str:
        """Answer one question, running whatever tools the model asks for along the way.

        One question may take several provider calls: the model asks for a tool, we run it, hand
        the result back, and it asks again or answers. Every one of those calls resends the entire
        conversation, because the provider still remembers nothing.
        """
        self.contents.append(user_message(question))

        for _ in range(MAX_CALLS_PER_QUESTION):
            # THINK — the whole thread, plus the tools it is allowed to reach for.
            url, body = provider.build_request(
                self.contents,
                model=self.model,
                system_instruction=self.system_instruction,
                tools=tools.DECLARATIONS if self.use_tools else None,
            )
            response = provider.send(url, body)

            candidate = provider.first_candidate(response)
            text = provider.text_of(candidate)
            self.turns.append(Turn(
                number=len(self.turns) + 1,
                request=body,
                response=response,
                finish_reason=candidate.get("finishReason"),
                text=text,
            ))

            # OBSERVE — file the model's turn, whatever it was. A turn asking for a tool is part
            # of the conversation exactly as an answer is, and omitting it leaves the tool results
            # in the thread with nothing explaining why they are there.
            reply = candidate.get("content")
            if self.remember and reply is not None:
                self.contents.append(reply)

            # ACT — run every tool this turn asked for, then hand the results back and go round.
            calls = provider.function_calls(candidate)
            if not calls:
                return text
            results = [(call, tools.dispatch(call["name"], dict(call.get("args") or {})))
                       for call in calls]
            self.contents.append(provider.function_response_message(results))

        raise LoopExhausted(
            f"reached {MAX_CALLS_PER_QUESTION} provider calls for one question without a final "
            f"answer. The full conversation is in `contents` and every turn is in `turns`; the "
            f"bound stopped this, and nothing else was going to."
        )
```

**Line by line:**

- `self.contents.append(user_message(question))` happens **once, before the loop**. The question is
  asked once however many times the conversation goes round; putting it inside would resend the
  question after every tool result and the model would answer it repeatedly.
- `for _ in range(MAX_CALLS_PER_QUESTION):` — the bound is the loop's own structure, not a counter
  checked inside a `while True`. There is no path through this method that runs the body a seventh
  time, and there is no variable anybody can fail to increment. A `while` with a manual counter is
  the same logic with one more thing to get wrong.
- The three comments — **THINK, ACT, OBSERVE** — are day 4's vocabulary made visible in the code. On
  day 4 the ACT step had nothing to do and the loop did not exist; the three words were a shape
  waiting for today. They are in the file because a reader six months from now needs to see which of
  the three stages a line belongs to.
- `provider.build_request(self.contents, ...)` sends **`self.contents`**, not a copy and not the
  tail. The endpoint is stateless: it holds nothing between calls, so every single trip round this
  loop resends the entire conversation including every tool call and every tool result so far. That
  is the cost of statelessness and it is also what makes the loop yours.
- `provider.first_candidate(response)` — day 4 printed it, and it exists so that a response carrying
  no candidates raises something that names the problem rather than an `IndexError` from
  `["candidates"][0]`. It matters more today than it did yesterday, because today the loop can be on
  its fourth call when it happens.
- `self.turns.append(Turn(...))` records the request **and** the response, before anything is
  decided about them. That ordering is the point: the turn is filed whether it turns out to be a
  tool call or an answer, so a run that ends in `LoopExhausted` still has every request and every
  response available for reading. A log written only on the success path is a log that is absent
  exactly when you need it.
- `finish_reason=candidate.get("finishReason")` — recorded with `.get`, so an absent field is `None`
  rather than an exception. **This project does not branch on it**, and that is deliberate: the
  provider's `FinishReason` enum documents `MALFORMED_FUNCTION_CALL`, `UNEXPECTED_TOOL_CALL` and
  `TOO_MANY_TOOL_CALLS`, and documents no value for the ordinary case of a successful function call.
  Code that decided "this is a tool call" by testing the finish reason would be guessing at an
  unpublished contract. The presence of a `functionCall` part is the fact; the finish reason is
  recorded and not trusted.
- `reply = candidate.get("content")` then `if self.remember and reply is not None` — the model's
  turn is appended to the conversation **before** any tool runs. The comment says why in the file: a
  tool-result turn with no tool-call turn above it is a result nothing asked for, and the model
  reads the thread you send exactly as literally as it looks.
- `calls = provider.function_calls(candidate)` and `if not calls: return text` — **the only exit
  that returns an answer.** No tool calls means the model has said what it wants to say, and the
  loop is over. Everything else in the body leads back round.
- `tools.dispatch(call["name"], dict(call.get("args") or {}))` — three defensive spellings in one
  line, each earning its place. `.get("args")` because a call with no arguments may omit the key
  entirely. `or {}` because it may also be present and `null`. `dict(...)` because the value that
  arrives is parsed from the response and passing it straight through would hand a caller's
  structure to `**` unpacking; a fresh dictionary is cheap and cannot be mutated by anything else.
- The list comprehension runs **every** call this turn asked for, in order, and pairs each result
  with its call. That pairing is what `function_response_message` needs, and building it here means
  the provider module never has to know how a tool is run.
- `self.contents.append(provider.function_response_message(results))` — **one message for all the
  results**, appended to the same conversation, and then the loop goes round and sends the lot
  again. That single line is the second half of the round trip from *The idea*.
- The `raise LoopExhausted(...)` is outside the loop, so it is reached only by falling off the end —
  which happens exactly when the bound was hit without a text answer. The message names the number,
  says where the evidence is, and says the bound is the only thing that stopped it. That last clause
  is there because the person reading this error at eleven at night needs to know it is a limit and
  not a crash.

**Line by line:**

- `"role": "user"` — the tool result is sent as a **user turn**. See the paragraphs below; this is
  the line the documentation contradicts itself about.
- `"parts"` is a list with one entry because one tool was called. Two calls in a turn would give two
  entries in this same list, in the order they were requested, and still one message.
- `"functionResponse"` is the part's only key, in camel case to match the wire, and its sibling in a
  model turn would be `functionCall`. A part is one kind of thing.
- `"name": "check_service_status"` is copied from the call, and it is how the provider knows which
  request this answers. There is no positional matching and no implicit ordering to rely on.
- No `"id"` appears, because the stand-in call carried none. Had it carried one, it would be echoed
  here beside the name.
- `"response"` holds **the tool's return value verbatim** — the whole dictionary
  `check_service_status` produced, keys and all. It is not stringified, not wrapped in a `"result"`
  envelope of ours, and not summarised. The model reads these keys directly, which is why the
  field names a tool returns are part of its interface as surely as its parameters are.

### The role of a tool-result turn: the documentation disagrees with itself

This is not a detail to smooth over, so it is stated plainly. Both of the following are on
`https://ai.google.dev/api/generate-content`, both read on 2026-09-09.

The `Content` type's own `role` field:

> The producer of the content. Must be either 'user' or 'model'.

And the prose beside `Tool.functionDeclarations`, about the turn that carries a result back:

> The next conversation turn may contain a FunctionResponse with the `Content.role` "function"
> generation context for the next model turn.

Those cannot both be complete. The first says two values are permitted and names them; the second
uses a third value the first excludes. **We send `"user"`**, for two reasons. It is the value the
normative field description permits, and a request whose role is outside the documented enumeration
is a request that may be rejected outright rather than interpreted generously. And the request
already carries the information: a part whose key is `functionResponse` is unambiguous about what it
is, whatever the message it rides in claims about its producer.

What we have **not** done is verify which the provider actually accepts, and it would be dishonest
to imply otherwise. There is no working key on this machine, so the round trip has never completed
here.

## When it breaks

The round trip is two calls, and the first of them can fail exactly as day 4's single call could —
except that today you have written more code between you and the wire, so the temptation to blame
the new code is stronger. This is the hand-rolled path meeting a key the provider will not accept:

```console
$ uv run --frozen python run.py ask "Is the VPN down?"
the provider refused this request: HTTP 400: 'API key not valid. Please pass a valid API key.'
$ echo $?
1
```

Somebody adds tools on a Friday, runs this, sees a failure that did not happen yesterday, and spends
the evening reading `function_response_message`. The request was built correctly and sent; the key
in `.env` is the synthetic one this project has carried since it was created. Note also what the
status is — **400, not 401** — so a retry policy branching on `401` to mean "bad credentials" will
not recognise this and will retry a request that can never succeed. The smallest fix is to read the
message before the diff: the provider is describing the key, and nothing in that sentence is about
tools.

## In production

**What a senior writes instead.** They do not write this loop; they let a framework hold it, which
is day 6 and day 7 of this project. What they keep is the two things a framework does not decide for
them: a bound on the number of calls per question, and a rule about what happens when the bound is
hit. Frameworks default those generously or not at all, and the review comment below is the one that
gets written about somebody's first agent.

**What degrades at scale.** Every trip round the loop resends the **entire** conversation, so the
request grows monotonically within a single question. A question that goes search, fetch, status,
answer sends four requests, and the fourth carries the question, three tool-call turns, three tool
results and three declarations — several times the payload of the first. At the bound of six calls
the last request can be five or six times the size of the first, and every one of those bytes is
billed and counted against a context window. That is the cost of a stateless endpoint, and it is
precisely what the provider's newer stateful API removes; this project uses the stateless one on
purpose, and `PROJECT.md` says why.

**The review comment.** "This loop has no upper bound — it is `while True` with a `break` when the
model stops asking for tools, which means the model decides when your program stops. Add a hard cap
in code the prompt cannot reach, and raise when you hit it rather than returning the last partial
text, otherwise a run that failed is indistinguishable from one that worked."

**The interview question.** "Your agent answers one user question by calling three tools. How many
requests reach the model provider, what does each one contain, and what is the largest thing you
send? Then say what changes about all three answers if the provider holds the conversation for you."
