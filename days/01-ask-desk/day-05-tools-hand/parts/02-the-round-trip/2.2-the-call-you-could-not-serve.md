## One-line answer

A tool call can arrive naming a tool you do not have or carrying arguments your function will not
take, and those two need opposite treatments — an unknown **name** raises, because guessing at a
near match runs the wrong code, while bad **arguments** come back as an `error` result the model can
read and correct — and neither of them is the failure that empties a quota, which is a loop whose
end condition the model controls.

## The idea

The dockets that ruin a service are not the illegible ones. An illegible docket gets sent back
across the pass within seconds, because nobody can pretend to read it. The dockets that cause damage
are the ones that are perfectly clear and wrong.

Here is the first kind. A docket comes through for a dish that is not on the menu — near enough to
one that is, mind, one word off. There is a cook who will look at it, decide what was meant, and
cook that. They are trying to help, they are usually right, and the one time they are wrong nobody
finds out until the plate is on the table, because a plate was produced and everything downstream
assumed it was the ordered plate. The kitchen that sends that docket **back** looks less helpful and
is the one you want, because the fault gets named at the pass, next to the person who wrote it, and
not in the dining room ten minutes later.

Here is the second kind, and it needs the opposite response. A docket comes through for a real dish
with something missing — no table number, or a quantity nobody wrote down. Sending that back is
correct and it is also not the end of it: what the kitchen writes on the returned docket decides
whether the waiter fixes it in one trip or three. *"No"* means another lap. *"No — this needs a
table number, and you gave me a seat number"* means the corrected docket comes back right the first
time.

That is the whole distinction this part is about, and both halves of it live in one function.
A name that does not exist is **not recoverable by the model** — there is no argument it could send
that would make `lookup_ticket` exist, so telling it is pointless and running something else is
worse. A bad argument **is** recoverable by the model — it can read what went wrong and send the
call again — so refusing to tell it is refusing free repair.

And then the third thing, which is not a bad docket at all. Nothing above bounds how many dockets
one order can generate. A waiter who keeps sending clarifications through the slot, each one
answered, each answer prompting another, will keep the kitchen busy all night without a single plate
going out and without anybody doing anything wrong. Every docket in that stack is well-formed. What
is missing is a rule, held by the restaurant and not by the waiter, that says an order gets a fixed
number of trips through the slot and then somebody comes out and says so. Today is the first day
your loop can go round more than once, so today is the day that rule has to exist.

## The mechanism

`dispatch` was printed whole in [part 1.2](../01-the-docket/1.2-the-three-things-this-desk-can-do.md)
and is not reprinted here. What follows is the three ways a call goes wrong, caused on purpose, with
no model and no key involved — because all three are decided in your process, by your code, from the
name and the arguments alone.

```console
$ uv run --frozen python -c "
import json
from ask_desk import tools
try:
    tools.dispatch('lookup_ticket', {'id': 'T-1'})
except tools.UnknownTool as e:
    print('UnknownTool:', e)
print(json.dumps(tools.dispatch('fetch_note', {})))
print(json.dumps(tools.dispatch('search_notes', {'q': 'vpn'})))
"
UnknownTool: the model asked for 'lookup_ticket', which this desk does not have. Known tools: check_service_status, fetch_note, search_notes. A tool the model invents is a sign the declarations and the registry have drifted apart.
{"error": "fetch_note rejected these arguments: fetch_note() missing 1 required positional argument: 'note_id'", "arguments_received": {}}
{"error": "search_notes rejected these arguments: search_notes() got an unexpected keyword argument 'q'", "arguments_received": {"q": "vpn"}}
```

**Line by line:**

- **The first call raises and the other two return.** That is the whole design in one transcript,
  and it is worth pausing on, because the instinct is to make them consistent. They are treated
  differently because the model's ability to recover is different, and consistency here would mean
  being wrong about one of them.
- `tools.dispatch('lookup_ticket', ...)` — a tool this desk has never declared and does not have.
  The name is one the model produced, and there is no argument it could add that would bring
  `lookup_ticket` into existence. So `UnknownTool` is **raised**, and the run stops.
- Consider what the tempting alternative does. `lookup_ticket` is one edit-distance from nothing here
  but it is close in *meaning* to `fetch_note`, and a fuzzy match would find it. That code would run
  `fetch_note` with `{'id': 'T-1'}`, which is not even its parameter name — and on a day when the
  argument names happened to line up, it would run the wrong tool successfully and hand the model a
  result labelled with a tool it never asked for. **Silently running something other than what was
  asked for is the failure mode with no error and no log line.** Refusing is louder and cheaper.
- The message names `', '.join(sorted(REGISTRY))` — the three real tools, alphabetically, so the
  message is stable between runs and a diff of two logs is about what changed rather than about
  dictionary ordering.
- The message's last sentence — *"A tool the model invents is a sign the declarations and the
  registry have drifted apart"* — is a diagnosis, not decoration. In practice the model is rarely
  being creative. Somebody renamed a function and left the declaration, or added a declaration for a
  function still on a branch, and the model is dutifully calling exactly what it was told exists.
- `tools.dispatch('fetch_note', {})` — a real tool, called with **nothing**. The declaration says
  `"required": ["note_id"]`, so a model that sends no arguments has ignored the schema. Python's own
  `TypeError` text is carried through verbatim into the `error` string:
  `fetch_note() missing 1 required positional argument: 'note_id'`. It names the function, the
  count, and the parameter — better than anything this project would write by hand, and it stays
  correct when the signature changes.
- `tools.dispatch('search_notes', {'q': 'vpn'})` — a real tool with a **plausible but wrong argument
  name**. `q` is what a hundred search APIs call that parameter; this one calls it `query`, and the
  declaration says `query`. `got an unexpected keyword argument 'q'` is what `**args` unpacking does
  with a key the signature has never heard of, and it is caught by the same `except TypeError`.
- Both argument failures return `{"error": ..., "arguments_received": ...}` — a dictionary, from a
  function that completed normally. The run does not stop. The result goes back to the model exactly
  as a successful result would, and the model gets to read it.
- `"arguments_received"` echoes what actually arrived. Without it the model is told its arguments
  were wrong and not what they were, and the commonest thing it then does is send the same ones
  again — which costs another two provider calls to learn nothing.
- Note what is **not** caught: only `TypeError`, and only from the call itself. A `KeyError` raised
  inside `search_notes` because `notes.json` lost a field is a bug in this project, and dressing it
  up as a message to the model would hide a broken deployment behind a chatty answer. It propagates,
  and it should.

### Why an `error` key is a legitimate answer and not a hack

Returning a dictionary with an `error` key is not this project inventing a convention. The provider
documents the response field as the caller's to shape, and names this case specifically. Verbatim,
from `https://ai.google.dev/api/generate-content`, read on 2026-09-09:

> Callers can use any keys of their choice that fit the function's syntax to return the function
> output, e.g. "output", "result", etc. In particular, if the function call failed to execute, the
> response can have an "error" key to return error details to the model.

So the shape `function_response_message` sends is the documented one, and the model is expected to
receive tool failures this way. That is what makes the raise-versus-return split defensible rather
than merely opinionated: one of the two cases has a documented channel back to the model, and the
other does not.

Note also that this is the same shape `fetch_note` already returns for an id that does not exist —
`{"error": ..., "known_ids": [...]}` from part 1.2. A tool's *expected* failures and its *argument*
failures reach the model through one mechanism, so the model has one thing to learn rather than two.

### The second failure, and the one that empties a quota

Everything above is a single call going wrong. The failure with no error message at all is the loop
that does not stop.

`ask` runs `for _ in range(MAX_CALLS_PER_QUESTION)` — printed in
[part 2.1](2.1-call-run-hand-back.md) — and the constant is `6`. Take that away and the natural
alternative is `while True`, with the loop ending when the model stops asking for tools. Read that
sentence again with the emphasis where it belongs: **the loop ends when the model chooses to end
it.** The end condition of your program has been delegated to a system that has no obligation to
meet it, is not deterministic, and is being steered by whatever text arrives in the conversation —
including text that came out of your own tools.

Nothing about that failure looks like a failure while it is happening. Every request is well-formed.
Every tool call is valid. Every result goes back correctly. The turns are filed. The only signal is
that no answer ever arrives, and the only thing consuming anything is your quota — which, per the
plan's budget policy, has a ceiling nobody outside your account can read.

The bound has three properties, and each of them is a decision:

- **It counts provider calls, not time and not tokens.** A timeout bounds how long you wait; a
  token budget bounds one call's size. The quantity that runs away here is the *number of calls*, so
  that is what is counted.
- **It lives in code the model cannot reach.** Not in the system instruction, not in a tool
  description. Anything expressed in the conversation is a request to a model, and a request is not
  a limit.
- **It raises.** `LoopExhausted` stops the run rather than returning the last text the model
  produced. Returning that text would turn a question that failed into a question that looks
  answered, with no field on the return value saying otherwise — the caller cannot tell, and neither
  can the log. The exception's message names the count and says the conversation and every turn are
  still on the object, so the run can be read back.

Watching that bound refuse needs a model that will keep asking, and therefore a working key. There
is none on this machine, so the transcript is not here:

```text
TODO(me): with a working GOOGLE_API_KEY, set MAX_CALLS_PER_QUESTION = 1 in ask_desk/loop.py and run
  uv run --frozen python run.py ask "Is the VPN down?"
Record the LoopExhausted message verbatim, and record how many entries Conversation.turns holds when
it is raised. Then restore the constant to 6 and run the same question again.
```

*The three failures above were observed on this machine on 2026-09-09, uv 0.12.3, CPython 3.12.12,
with no key and no network.*

## When it breaks

The error that reaches somebody at eleven at night is not the raise. It is the one that came back
wrapped in a perfectly successful answer:

```text
{"error": "fetch_note rejected these arguments: fetch_note() missing 1 required positional argument: 'note_id'", "arguments_received": {}}
```

A desk went out with a declaration whose `required` list had been trimmed while somebody was tidying
the JSON. The model, reading a schema that said nothing was compulsory, called `fetch_note` with no
arguments; the tool returned that dictionary; the model read it, apologised in fluent prose, and
told the user it could not find the note. Nothing raised, nothing was logged as an error, and the
first sign was a support complaint about an unhelpful desk. The smallest fix is the `required` line
in the declaration. The fix that would have caught it is a test that dispatches every declared tool
with exactly its declared-required arguments and asserts no `error` key comes back — the check that
the two halves in `tools.py` still agree, which nothing in this project has yet.

## In production

**What a senior writes instead.** They validate the arguments against the declaration's schema
*before* calling the function, with a real JSON Schema validator, so the error handed back to the
model says "expected string, got integer at `note_id`" rather than repeating whatever Python's
argument binding happened to say. They keep the raise on an unknown name exactly as it is. And they
log every tool call and its outcome with the conversation identifier attached, because the second
question anybody asks about a bad answer is "which tools ran".

**What degrades at scale.** The bound is the number. With `MAX_CALLS_PER_QUESTION = 6`, a thousand
questions cost at most six thousand provider calls and you can say that sentence to whoever pays for
them. Remove it and the sentence has no ending: a **single** question can consume every call the
account has left, at a rate limited only by the provider, and the run that does it looks identical
to a healthy one until the quota is gone. Note also that each of those six calls is larger than the
last, because the stateless endpoint means the whole conversation is resent every time — so the cost
is not six times the first call, it is more.

**The review comment.** "Two things in `dispatch`. The unknown-name path raising is right — please
do not 'improve' it into a nearest-match, because that runs a tool nobody asked for and there is no
log line that would show it. But the `except TypeError` is catching argument-binding errors and
anything else in the call stack that happens to raise `TypeError`; if a tool has a genuine bug that
raises one, we will hand the model a friendly error and never see it. Bind the arguments explicitly
before the call, or narrow the catch."

**The interview question.** "Your agent loop calls tools until the model stops asking for them.
Describe what happens when it does not stop, say who is in control of that decision as the code is
written, and say where you would put the bound so that no prompt change can move it."
