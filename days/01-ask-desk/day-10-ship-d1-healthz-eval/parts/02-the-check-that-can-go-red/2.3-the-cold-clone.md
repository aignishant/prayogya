## One-line answer

A project is finished when somebody who has only its folder can reach a green check on a machine that
has never seen it — so the last day of every project is the day the folder is copied out alone and
made to prove it, and a cold clone that was never run is not a claim you are allowed to make.

## The idea

Every ship carries the certificate. The boats are surveyed, the davits are greased, the falls are in
date, and the paperwork in the drawer says all of it. And then there are ships where the boat has
never once left the chocks — not because anybody lied, but because the drill kept being the day the
tug was late, or the weather was wrong, or the port call was short. The certificate is honest about
what was inspected. It is silent about the one thing that was never done, and the silence reads
exactly like a pass.

Everything in this project is currently a certificate. Ten days of documents say the folder is
self-contained. The import lines look right. Nobody has typed `from adk_kit import anything`. But the
claim being made is not about the imports; it is about a **stranger on a bare machine**, and the only
instrument that measures it is a stranger on a bare machine. Here is the plan's own sentence, and it
is deliberately blunt:

> Every project's last day is the cold-clone day: wipe the working copy, clone the folder alone,
> follow the README, and record the output. That output is pasted into the day document. **A project
> whose cold clone was never run is not finished.**

The word doing the work is **alone**. Copying `projects/01-ask-desk/` and nothing else is what turns
a claim into a measurement, because everything the folder secretly depended on stops existing at the
moment of the copy. Not the repository root, not `p.py`, not the authoring `docs/`, not the other
projects, not your shell history, not the environment variable you exported last Tuesday and have
forgotten about. The failures a cold clone finds are almost never dramatic: a `SETUP.md` step that
says "as before", a file no day ever printed, a version that was in your environment and in nobody's
document. Each of them is invisible from inside, because from inside, the missing thing is present.

And the second half of the drill is the half that gets skipped, which is why this document ends by
being unusually specific about what was and was not done here. A cold clone run on the machine that
built the project is not a cold clone. It is the ship lowering the boat while still tied to the
quay — worth doing, genuinely informative about the davits, and silent about everything that only
open water tests. Both halves get recorded below, and the half that was not run is marked as owed
rather than described as done.

## The mechanism

### The gate, as it stands on this machine

Everything a cold clone can be asked to prove **without a provider key** was run today. This is
`run.py check` — six checks, the last of which runs the whole evalset against the scripted double:

```console
$ uv run --frozen python run.py check
green  keys
green  interpreter
green  pins
green  lock
green  model
green  grounded-status-question  tools=['check_service_status']
green  ungrounded-answer-is-caught (inverted)  tools=[]
       failed as intended: expected the desk to call 'check_service_status' and it did not. It answered anyway, which means the answer was not grounded in anything this system knows.

2/2 case(s) passed
$ echo $?
0
```

*Observed on this machine on 2026-09-10 — uv 0.12.3, CPython 3.12.12, google-adk 2.8.0,
fastapi 0.141.1, uvicorn 0.52.4. No provider call was made by any of it.*

Three things in that transcript are worth naming, because they are the parts a certificate cannot
carry. The evalset's own rows appear **inside** the gate's output, which is what makes `check` a gate
rather than a config linter — the sixth check's subject is behaviour. The inverted case is green and
still prints its reason, so the gate says out loud what it just caught. And `echo $?` was typed,
because a screen full of `green` is decoration until the status agrees with it.

### What was and was not run — the honest half

A true cold clone means copying **only** `projects/01-ask-desk/` to a machine that has never seen
this repository, following that folder's own `SETUP.md` from the first line, and running its own
checks. That is not what happened here, and the difference matters enough to be written down rather
than implied.

**Run on this machine on 2026-09-10, in place, with no working provider key:**

| What | Evidence |
| --- | --- |
| The gate, all six checks | the transcript above — `0 problem(s)`, exit `0` |
| The evalset, standalone | part 2.1's transcript — `2/2 case(s) passed`, exit `0` |
| The evalset going red on purpose | part 2.2's transcript — `1/2`, exit `1`, caught by the inverted case |
| `/healthz` over real HTTP, served by `run.py serve` | part 1.1's transcript — the body, and `200` |
| `/ask` refusing honestly | part 1.2's transcript — `HTTP 502`, and `422 string_too_short` |
| Every tracked file maps to a day | the table above, walked against the folder |

**Not run, and therefore not claimed:**

- The folder was **not** copied to a clean machine. Everything above was run in place, inside the
  repository that authored it. That is the boat lowered alongside the quay: it proves the davits
  turn and it proves nothing about open water.
- `uv sync --frozen` was **not** run from a bare state, so `SETUP.md` step 2 is untested against an
  empty `.venv`.
- There is **no working `GOOGLE_API_KEY` on this machine.** Every path that reaches the provider was
  observed being refused, never succeeding. So `run.py ask`, `run.py adk`, and `POST /ask` returning
  `200` with a real answer are all owed, and no transcript of any of them appears anywhere in this
  project's days.

Two things the walk turned up that a cold clone would trip over, both real and both found today by
reading the folder's own documents against the folder:

- `SETUP.md` step 4 says *"Five checks, all of which must be green: `keys`, `interpreter`, `pins`,
  `lock`, `model`."* There are now six. A stranger following that document counts the rows, finds an
  extra one, and has to decide whether their clone is broken.
- `README.md` offers *"The four commands"*. The driver now answers eight subcommands: `check`,
  `plan`, `ask`, `adk`, `events`, `session`, `eval`, `serve`.

Neither is a bug in the code and both are exactly what the cold-clone day exists to catch: documents
that were true when they were written and are now quietly wrong, in the two files a stranger reads
first. Fixing them is in the hub's build brief, unsolved.

## When it breaks

The classic cold-clone failure is not a missing line of code — the days print those. It is a file
that stopped agreeing with another file while everybody's machine went on working anyway, and the
error arrives from a tool rather than from your project. This is the real text, observed on this
machine on 2026-09-09 from the same `uv lock --check` that `run.py check`'s `lock` check runs, with
`pyproject.toml` naming a version the lockfile did not hold:

```console
error: The lockfile at `uv.lock` needs to be updated, but `--check` was provided.
```

Somebody hand-edited a pin in `pyproject.toml` on a Friday and never re-locked. Nothing went wrong
for them: their `.venv` already had the package, so every command kept working, and the drift was
invisible from inside. The colleague who received the folder hit it on their first command, before
they had run a single line of the project. It reads as a lockfile problem and it is a *nobody-cloned-
this* problem: the disagreement existed for days and the only instrument that could see it was a
machine with no `.venv`. The smallest fix is `uv lock` — and the fix that stops it recurring is
running the cold clone often enough that "works here" and "works" are the same sentence.

## In production

**What a senior writes instead.** They do not do this by hand once at the end. The cold clone becomes
a CI job that checks out the repository into a clean container, copies exactly one subdirectory into
an empty image, and runs that folder's own `./run check` — so the claim is re-measured on every push
rather than asserted once on the day somebody remembered. Two habits go with it: build the image
`FROM` a base that has nothing preinstalled, and never mount the source repository, because a bind
mount silently restores every file the copy was supposed to leave behind.

**What degrades at scale.** With one project it is a chore. This curriculum has forty, and the
duplication is deliberate: forty `PACKAGES.md`, forty drivers, forty copies of the same idea living
separate lives. If the cold clone is a manual step, it will be run on project one and skipped by
project six, and the failure it catches is not one broken project — it is a class of breakage that
gets copied forward into every project scaffolded from the last one. **Twenty-six files here, and one
of them unmapped is enough to make the folder unbuildable by a stranger; twenty-five of twenty-six is
not a score, it is a failure.**

**The review comment.** "The README says this runs standalone, and I can see four imports that would
resolve from the repository root. Please add a CI job that copies only this directory into a clean
container and runs `./run check` there — if it passes we can keep the sentence, and if it does not,
the sentence is the bug."

**The interview question.** "A colleague clones your service's repository and cannot get it running.
It works on every machine on your team. Walk me through how you would find what the repository is
depending on that nobody wrote down — and then tell me what you would put in CI so that the next
colleague does not have to ask."
