## One-line answer

A status code is the one word your service gets to say about *why* a request failed, and the three
this desk can produce — 502 for a provider refusal, 503 for a missing key, 422 for a malformed
request — are three different instructions to three different people, all of which are destroyed the
moment somebody wraps the handler in a bare `except` and returns 500.

## The idea

The drill card on the bulkhead does not have one bell on it. It has three signals, and they are not
three volumes of the same alarm — they are three different sets of instructions. Seven short and one
long: abandon ship, go to your muster station with a lifejacket. Three long: man overboard, get to
the rail and keep your eyes on the water. Continuous ringing: fire, and where you go depends on which
compartment. Every hand aboard knows which one is sounding before they know anything else about the
emergency, and that knowledge is what makes the first thirty seconds useful instead of frantic.

Now fit one bell to the ship and ring it for everything. Nothing is hidden, exactly — the alarm is
sounding, and it is sounding honestly. But every person aboard now has to find out what is happening
before they can do anything about it, and the finding out is the expensive part. The bell has stopped
being information and become an interruption.

That is the whole argument for status codes, and it is worth being precise about who is listening.
When your desk fails, there is a person who has to decide, quickly, **which half of the system to
open**: the code, or the environment it was deployed into. A **status code** is the number in the
first line of an HTTP response, and its job is to answer that question before anybody reads the body.
The families do most of the work: `4xx` means *the caller sent something wrong*, `5xx` means *the
server failed*. Within `5xx` the distinctions are the ones that decide who gets woken up.

This desk can fail exactly three ways from outside, and each one has a different owner.

A **provider refusal** — the model service was reached and said no. That is `502 Bad Gateway`: this
server acted as a gateway to another one, and the other one is the problem. Nothing in your code is
broken. Somebody should read the provider's message, which is why part 1.1 puts it in the body
verbatim.

A **missing key** — the process is running perfectly and was deployed without the secret it needs.
That is `503 Service Unavailable`: the service cannot serve, right now, for a reason that is about
configuration rather than about the request. It is the code that says *look at the deployment*. And
it is exactly the failure `/healthz` deliberately does not report, for the reason part 1.1 gave: a
restart cannot produce a secret. The two decisions are the same decision seen from two ends — the
probe is told nothing it can act on, and the caller is told precisely what is wrong.

A **malformed request** — an empty question, or one longer than the bound. That is `422
Unprocessable Content`: the request was well-formed HTTP and its content was not usable. Nothing
failed. Nobody should be woken. The caller has a bug and the response body says which field.

Collapse those three into `500 Internal Server Error` and you have not lost detail; you have lost the
**routing**. Two of the three are not code failures at all, so an on-call rota that pages on `5xx`
now pages the wrong team for two of the three things that can go wrong here, and a dashboard counting
500s shows an application in trouble when the truth is that somebody forgot a secret and somebody
else sent an empty string. This is day 9's rule — the failure surfaces rather than being swallowed —
carried one step further. Day 9 established that an error must not be turned into a cheerful answer.
Today's addition: **surfacing an error is only half the job if every error surfaces as the same
error.**

## The mechanism

The three status codes live in `ask_desk/api.py`, printed whole in part 1.1 and not reprinted here.
What is new is the way to start it. The driver gains one subcommand.

`projects/01-ask-desk/run.py`, as a marked diff — day 4 printed this file whole, day 6 added the
`adk` subcommand, and days 8 and 9 added `events` and `session`. Everything not shown is unchanged
from those days:

```diff
--- projects/01-ask-desk/run.py    as days 4 to 9 left it
+++ projects/01-ask-desk/run.py    with the `serve` subcommand
@@ the last line of the module docstring @@
+    python run.py serve               the D1 API on :8080
 """
@@ immediately above `def main(argv: list[str]) -> int:` @@
+def serve() -> int:
+    """The D1 surface: the agent behind HTTP, with a health endpoint that means something."""
+    import uvicorn
+
+    from ask_desk import api
+
+    uvicorn.run(api.app, host="127.0.0.1", port=8080, log_level="warning")
+    return 0
+
+
 def main(argv: list[str]) -> int:
@@ in `main`, the last case before the fallback @@
+        case ["serve"]:
+            return serve()
         case _:
             print(__doc__, file=sys.stderr)
             return 2
```

**Line by line:**

- `import uvicorn` and `from ask_desk import api` are **inside the function**, not at the top of the
  file. This is the same move day 6 made for `adk`, and the reason is `check`: `run.py check` must be
  runnable on a machine that has just cloned the folder, and every import at module scope is a
  package that must already be installed before the gate can tell you anything. Pushing the server
  imports down means `check` needs neither the web framework nor the server, and a broken install
  reports as a red check rather than as an import error before any check runs.
- `uvicorn.run(api.app, ...)` takes the **application object**, not the string `"ask_desk.api:app"`.
  The string form is what enables uvicorn's reloader, and this project does not want it: the reloader
  spawns a second process, which means two agents, two sessions and two of everything else in a
  project whose whole subject is knowing exactly how many model calls a question costs.
- `host="127.0.0.1"` — the loopback address, and it is a deliberate refusal. Bound to `127.0.0.1`
  this server is reachable only from this machine. `0.0.0.0` would bind every interface, which is
  what a container needs and what a laptop on a café network absolutely does not. D1 is *run
  locally*, and the address says so. Changing it is a decision that belongs to P02's Dockerfile,
  where the container boundary is the thing that makes it safe.
- `port=8080` — an unprivileged port, chosen once and written into the driver rather than passed on
  the command line, so that every transcript in this project and every `curl` in every checklist is
  talking about the same place.
- `log_level="warning"` — uvicorn's default is `info`, which prints a line per request. That is
  correct for a service and wrong for a teaching transcript, where a line of access log between every
  command turns a readable session into noise. The trade is real and it is stated here so that the
  first thing you do in P02 is put it back.
- `return 0` after `uvicorn.run(...)` — that call blocks until the server stops, so this line is
  reached on a clean shutdown, and `main` hands the zero to `sys.exit`. A server that was stopped on
  purpose exited successfully; that is what the exit status is for, and day 3 part 2.2 is the deep
  version.
- `case ["serve"]:` placed **before** `case _:` — the fallback prints the docstring and returns `2`.
  Day 3's distinction survives here: `1` means the thing ran and failed, `2` means you typed the
  command wrong, and a pipeline that treats those the same reports a typo as a code failure.

And an empty question is rejected before any of that:

```console
POST /ask ---> empty question: 422 string_too_short
```

*Observed on this machine on 2026-09-10. The body in the first block is cut where the capture cut
it; the provider's full message is the one day 9's transcripts print in full.*

**Line by line:**

- `HTTP 502`, not 500. The request reached the provider and the provider refused it. An operator who
  sees this needs to read the body and then go and look at the key — and the body already tells them
  which, because the provider's own words are in it.
- `the provider refused this request:` is the prefix `api.py` adds. Without it, a body beginning
  `400 INVALID_ARGUMENT` inside a `502` response reads as two contradictory status codes and the
  first question anybody asks is "400 or 502?". The prefix names whose 400 it is.
- The 422 line names the **pydantic validation rule that fired** — `string_too_short` — not a generic
  "bad request". That string comes from `Field(min_length=1)` in part 1.1, and it means the caller
  can fix their bug without asking you anything.
- The 422 also proves what did *not* happen: `agent.ask` was never entered, no session was created,
  and no provider call was made. The bound was enforced at the boundary, which is the only place
  where enforcing it is free.
- The third answer, **503 for a missing key**, is the one this machine cannot produce alongside the
  others, because a missing key and a rejected key are different states and this machine is in the
  second. `TODO(me)` in `Check yourself` is how you see it.

## When it breaks

The failure this section exists to prevent looks responsible when it is written. Somebody wraps the
handler body in `except Exception` so that "the API never crashes", and every one of the three
answers above becomes the same one. This is the text that stops arriving the moment they do:

```console
{"detail":"the provider refused this request: 400 INVALID_ARGUMENT. {'error': {'code': 400, 'message': 'API key not valid. Please pass a valid API key.', 'statu...
```

Somebody shipped that wrapper on a Friday. At 11pm the desk started returning 500s, the application
team was paged because 500 means the application, and they read code for an hour before anybody
thought to check the deployment's secret. The information was never missing — the provider had said
`API key not valid` in the very first response — it had been flattened into a status code that means
*something went wrong inside this program*, which was the one thing that had not. The smallest fix is
the file in part 1.1: catch the two exception types you can actually diagnose, name a status for
each, and let anything you did not anticipate be a genuine 500, which is then true.

## In production

**What a senior writes instead.** They add an exception handler at the application level —
`@app.exception_handler(...)` — rather than a `try/except` in every route, so the mapping from
exception type to status code is written once, in one place, and cannot drift between endpoints. And
they add a request ID: a header echoed into every response and every log line, so that "the 502 I got
at 11:04" is a thing you can grep for rather than a thing you have to reconstruct from timestamps.

**What degrades at scale.** Two of the three failures this surface can produce — the missing key and
the malformed request — are not application failures. Collapse them into 500 and 100% of the alerts
from those two point at the wrong team, and the number that matters is not the alert count but the
time between the first alert and the first person looking in the right place. Once the desk is behind
a load balancer, it gets worse in a specific way: most load balancers treat 502 and 503 as *this
backend is sick* and will take the instance out of rotation, and treat 500 as a normal response and
leave it in. Getting the code wrong therefore changes routing, not just reporting.

**The review comment.** "This catches `Exception` and returns 500 for everything. A missing key is a
deployment problem and should be 503; a provider refusal is an upstream problem and should be 502
with the provider's message in the detail; validation is already handled by pydantic and should stay
422. As written, the on-call runbook for this service can only say 'read the logs', which is the
runbook we were trying to delete."

**The interview question.** "Your service returns 500 for every failure. Describe three distinct
failure modes it has, say which status code each should have and why, and then tell me what a load
balancer in front of it does differently for each of those codes."
