## One-line answer

"The assistant remembers the conversation" is a sentence about a Python list on an object in your
own process — the provider keeps no copy and offers no identifier to quote back — so every turn
attaches the entire correspondence, and the loop that does it is thirty lines you can read.

## The idea

Your correspondent is thorough, quick and completely without memory. Every letter is read carefully
and answered well, and then the desk is cleared: the letter, your previous letters, the replies,
everything. Next time you write, they begin from nothing.

You can still hold a conversation with such a person. You keep the file yourself — your letters and
their replies, in order — and each time you write you attach the whole file. They read the file, see
where the exchange had got to, and answer the new page at the end of it. It works perfectly. It also
means that the envelope gets thicker every time, that the file is the *only* copy, and that if your
desk burns down there is no correspondence anywhere in the world.

That is the endpoint this project uses. **Stateless** means the server keeps nothing between calls:
no session, no identifier, no thread to attach to. Every request carries everything the answer
depends on. This is not a limitation being worked around — it is the reason the loop is code you can
read, and it is the whole difference between this project and a stateful API where the conversation
is a thing on somebody else's machine.

Three words for the three objects, because they get used loosely and then confused.

A **turn** is one piece of the conversation with its producer attached: a `role` of `user` or
`model`, and the parts that make it up. Your question is a turn. The reply is a turn.

A **conversation**, or thread, is the ordered list of turns. In this project it is
`Conversation.contents`, a plain Python list, and its position in memory is the entire answer to
"where is the memory?".

A **system instruction** is the standing orders — what the desk is for, what it may answer from,
what to do when it does not know. It is not a turn, because nobody said it in the exchange, and it
rides beside `contents` rather than inside it. But it is resent on every single request, for the
same reason the conversation is: an instruction given once, to something that remembers nothing, is
an instruction given never.

Two consequences follow immediately, and they are the reason to hold this picture rather than the
comfortable one.

The first is cost, and it is arithmetic. Turn one sends one turn. Turn two sends three. Turn ten
sends nineteen. The text of your first question has by then been paid for ten times, and it will be
paid for again on turn eleven. Nothing here is wasteful — it is what statelessness *is* — but a
system built on the belief that "the model remembers" will be surprised by its bill and will have no
idea where it came from.

The second is fragility, and it is the one this day was chosen for. If the list is where the memory
is, then dropping something from the list is losing the memory, and there is no error and no warning
because nothing is broken. The `Conversation` you are about to read carries a flag called `remember`
for exactly this reason: it is a switch rather than an edit you make and undo, so part 2.2 can run
the broken behaviour beside the working one and print the difference.

## The mechanism

`projects/01-ask-desk/ask_desk/loop.py` as day 4 leaves it — whole file. Day 5 adds a bound and a
tool branch to `ask`; today there is no branch, because with nothing to reach for the model's first
reply is the answer:

```python
# ask_desk/loop.py
"""Think, act, observe — the loop, written out, with nothing hidden.

The provider is stateless. It remembers nothing between calls, so the conversation is a list that
lives here, in this process, and every turn resends all of it. There is no session on the server to
attach to and no identifier to quote back. If this list is dropped, the model meets the next
question with no idea that the previous one happened.

That is the entire mechanism a framework will later perform for you, and on day 1 it is about
thirty lines and one list.

Day 1 has no tools, so `act` has nothing to do and the model's first reply is the answer. Day 2
puts the tool branch inside `Conversation.ask`, and that is where a bound on the number of provider
calls per question becomes necessary — a loop that stops when the model says it is finished is a
loop the model can decline to end.
"""

from __future__ import annotations

from dataclasses import dataclass, field
from typing import Any

from ask_desk import provider
from ask_desk.util import models

# The desk's standing orders. Sent on every single turn, because the provider is stateless and an
# instruction given once is an instruction forgotten immediately.
SYSTEM_INSTRUCTION = (
    "You are an internal IT ask desk. Answer from the notes you are given and nothing else. "
    "If the notes do not cover the question, say so plainly and do not guess."
)


@dataclass
class Turn:
    """One exchange, kept so that a run can be read back after it has finished."""

    number: int
    request: dict[str, Any]
    response: dict[str, Any]
    finish_reason: str | None
    text: str


def user_message(text: str) -> dict[str, Any]:
    """A `Content` with the `user` role. The provider accepts only 'user' and 'model' here."""
    return {"role": "user", "parts": [{"text": text}]}


@dataclass
class Conversation:
    """The thread, and the only place it exists.

    `contents` is the memory. It is an ordinary Python list on an ordinary Python object, and the
    provider has no copy of it.
    """

    model: str = models.ANSWERING
    system_instruction: str = SYSTEM_INSTRUCTION
    contents: list[dict[str, Any]] = field(default_factory=list)
    turns: list[Turn] = field(default_factory=list)

    #: When False, the model's replies are never appended to `contents`. That is the deliberate
    #: failure of day 1: every turn then arrives as if it were the first. It is a flag here rather
    #: than an edit you make and undo, so the broken behaviour can be run beside the working one.
    remember: bool = True

    @property
    def request_count(self) -> int:
        """Provider calls this conversation has made. The number the hub's budget section states."""
        return len(self.turns)

    def next_request(self, question: str) -> tuple[str, dict[str, Any]]:
        """Build the request this question would send, without sending it.

        Separated from `ask` so the shape of a turn can be read, diffed and asserted on with no
        key, no network and no cost — which is also how the day's failure is shown.
        """
        pending = self.contents + [user_message(question)]
        return provider.build_request(
            pending,
            model=self.model,
            system_instruction=self.system_instruction,
        )

    def ask(self, question: str) -> str:
        """Answer one question. With no tools on offer, one provider call is the whole turn.

        That call resends the entire conversation, because the provider remembers none of it.
        """
        self.contents.append(user_message(question))

        # THINK — the whole thread, and the standing orders, in one request.
        url, body = provider.build_request(
            self.contents,
            model=self.model,
            system_instruction=self.system_instruction,
        )
        response = provider.send(url, body)

        candidate = provider.first_candidate(response)
        text = provider.text_of(candidate)
        self.turns.append(Turn(
            number=len(self.turns) + 1,
            request=body,
            response=response,
            finish_reason=candidate.get("finishReason"),
            text=text,
        ))

        # OBSERVE — file the model's turn so that the next question arrives after it rather than
        # instead of it. ACT has nothing to do today: with no tools on offer the first reply is the
        # answer, and day 2 is where this straight line becomes a loop.
        reply = candidate.get("content")
        if self.remember and reply is not None:
            self.contents.append(reply)

        return text


def ask_once(question: str, *, model: str = models.ANSWERING) -> str:
    """The whole desk, for a single question with no follow-up."""
    return Conversation(model=model).ask(question)
```

**Line by line:**

- The module docstring says the thing the rest of the file is a consequence of: *there is no session
  on the server to attach to and no identifier to quote back.* Everything below — the list, the
  resend, the flag — follows from that one sentence, and a reader who skips it will read the resend
  as inefficiency instead of as the protocol.
- `from ask_desk import provider` and `from ask_desk.util import models` — both inside this project.
  There is no third-party import in this file at all, which is what makes "the loop is thirty lines"
  a checkable claim rather than a slogan.
- `SYSTEM_INSTRUCTION` is a **module-level constant**, not a string built inside `ask`. It is a
  behavioural specification for the whole desk, so it belongs where somebody can find it, review it
  and change it in one place — and where the difference between two runs cannot be a prompt that
  quietly varied.
- The instruction's last clause — *"say so plainly and do not guess"* — is doing real work. Without
  a sentence like it, a model asked something the notes do not cover produces a fluent, plausible,
  invented answer, which is the single most expensive failure mode a desk like this has. The
  instruction is the cheapest guard against it and it is nowhere near sufficient; evals are what
  make it checkable, and they are a later project.
- `@dataclass class Turn` records the request, the response, the finish reason and the text of one
  exchange — the *whole* request and the *whole* response, not a summary. This is the audit trail:
  after a run has finished and gone wrong you can read back exactly what was sent, which is a
  question that is otherwise unanswerable, because the request was assembled and discarded inside a
  function call.
- `finish_reason: str | None` is typed optional because the field genuinely may not be there.
  Typing it `str` would be a claim about the provider's response that the provider does not make.
- `Turn.number` is stored rather than derived from a list index, so a turn that gets logged, pickled
  or handed around on its own still knows where it came from. An index is a fact about a list; a
  number is a fact about the turn.
- `user_message` is a **function and not a literal typed at each call site**. There are two places
  in this file that need a user turn and there will be more; one function means the role string and
  the nesting are written once, and the docstring is where the constraint lives — the provider
  accepts only `user` and `model`.
- `@dataclass class Conversation` — a dataclass rather than a hand-written `__init__` because every
  field has a sensible default and the generated `__repr__` prints the whole thread when you are
  debugging one. It is a container with behaviour, which is exactly the shape dataclasses are for.
- `model: str = models.ANSWERING` — the default comes from the registry, so a `Conversation()` with
  no arguments is still pinned. There is no path through this class that reaches an unpinned model,
  which is part 1.1's rule made structural rather than remembered.
- `contents: list[...] = field(default_factory=list)` and the same for `turns`. `= []` as a
  dataclass default is an error Python raises outright, and the reason it does is the bug it would
  otherwise cause: one list shared by every instance ever created, so two conversations would end up
  in each other's memory. `default_factory` builds a fresh list per instance.
- `contents` and `turns` are **two lists, not one**. `contents` is what goes on the wire, in exactly
  the shape the provider wants; `turns` is what you keep for yourself. Merging them would mean
  either sending your bookkeeping to the provider or filtering it out on every request, and the
  second option is a filter that eventually gets a case wrong.
- `remember: bool = True` — the day's failure as a switch. It defaults to correct, so nothing is
  broken by accident, and it is a field rather than an edit so that part 2.2 can hold a working
  conversation and a broken one side by side in one command and print the difference between them.
  A failure you have to introduce by editing a file is a failure you demonstrate once and never
  regression-test.
- `request_count` is a `@property` over `len(self.turns)` rather than a counter incremented by hand.
  A counter and a list are two facts that can disagree; a property cannot. This is the number the
  hub's budget section reports, and it is derived from what actually happened rather than from what
  the code intended.
- `next_request` builds `pending = self.contents + [user_message(question)]` — the `+` makes a **new
  list**. Nothing is appended, so calling `next_request` leaves the conversation exactly as it was
  and you can call it as often as you like. `self.contents.append(...)` here would mean that
  inspecting a request changed the state you were inspecting.
- `next_request` returns what `build_request` returns and sends nothing. It exists so the shape of a
  turn is inspectable without a key, a network or a charge — which is how `run.py plan` works, how
  part 1.3's transcript was produced, and how part 2.2 demonstrates a failure without making a
  single request.
- `next_request` passes no `tools` argument. `build_request` accepts one; today nothing has any to
  give it, and the request that goes out has no `tools` key. Day 5 changes this one call and that is
  most of what adding tools means.
- `ask` starts with `self.contents.append(user_message(question))` — the question joins the thread
  **before** the request is built, and then `build_request(self.contents, ...)` sends the thread
  itself. There is no separate "current question" parameter travelling alongside the history,
  because there is no such thing at the protocol level: the question is the last turn.
- The `# THINK` comment sits above the request and the `# OBSERVE` comment above the append, with
  `ACT` named as having nothing to do. Naming the three beats in a file where one of them is absent
  is deliberate: day 5 fills the empty one, and you will read the diff as a gap being filled rather
  than as a rewrite.
- `provider.send(url, body)` is called with what `build_request` returned, unmodified. Anything
  added between those two lines would be in the request and not in the printed plan, and `run.py
  plan` would stop being a truthful preview of `run.py ask`.
- `first_candidate` then `text_of`, in that order, both from `provider`. The loop never indexes into
  the response itself; the two functions that know the response's shape live in the module that
  owns the protocol, and this file stays about the conversation.
- The `Turn` is appended **before** the reply is filed into `contents`. That order matters on the
  failure path: if the append below is skipped — deliberately, by `remember=False`, or by a bug —
  `turns` still holds the complete record of what happened, so the evidence survives the failure
  that destroyed the memory.
- `reply = candidate.get("content")` — `.get`, not `["content"]`. A candidate that stopped for a
  safety reason can arrive without content at all, and indexing meets that with a `KeyError` from
  inside your loop rather than a `None` you can test.
- `if self.remember and reply is not None` — two conditions, and the second is not the first's
  business. `remember` is the switch; `reply is not None` is the protocol reality that a candidate
  may carry nothing. Collapsing them would make the demonstration in part 2.2 look like defensive
  coding.
- The appended object is `candidate["content"]` **exactly as it arrived**, not something
  reconstructed from `text`. It already carries `"role": "model"` and its own parts, in the shape
  the next request needs. Rebuilding it from the text would drop everything that is not text — which
  on day 5 is the model's request to call a tool, and dropping that breaks the tool loop in a way
  that is very hard to see.
- `ask` returns `text` — the answer, as a string, for a caller that wants an answer. The full record
  is on the object for the caller that wants the record. One return value, two audiences, and
  neither is forced to unpack the other's.
- `ask_once` constructs a `Conversation`, asks, and drops it. It is the honest spelling of "a
  question with no follow-up": the conversation existed, it was one turn long, and it was garbage
  collected. Nothing was cleaned up on a server, because there was nothing there.

And the driver, `projects/01-ask-desk/run.py`, whole file. Day 3 built P00's version of this and the
five checks are its direct descendants; what is new is the fifth check and the two subcommands that
drive the desk:

```python
# run.py
"""This project's own driver. It depends on nothing above this folder.

    python run.py check          the gate: config, pins, and the registry
    python run.py plan "..."     print the request a question would send, and send nothing
    python run.py ask "..."      ask the desk one question, hand-rolled (needs a working key)
"""

from __future__ import annotations

import json
import subprocess
import sys
import tomllib
from pathlib import Path

from ask_desk import loop, provider
from ask_desk.util import keys, models

HERE = Path(__file__).parent


def check_keys() -> list[str]:
    """Every name `.env.example` declares must be wired. Wired is all this can prove."""
    problems = []
    names = keys.names_this_project_reads()
    if not names:
        return [".env.example declares no key names: the committed file is the list of names"]
    for name in names:
        try:
            keys.require(name)
        except keys.MissingKey as exc:
            problems.append(str(exc))
    return problems


def check_interpreter() -> list[str]:
    """The interpreter actually running must be the one `.python-version` pins."""
    pin_file = HERE / ".python-version"
    if not pin_file.exists():
        return [".python-version is missing: requires-python is a floor, not a pin"]
    pinned = pin_file.read_text(encoding="utf-8").strip()
    running = ".".join(str(n) for n in sys.version_info[:3])
    if running != pinned:
        return [f".python-version pins {pinned}; this interpreter is {running}"]
    return []


def check_pins_are_pins() -> list[str]:
    """A dependency written with `>=` is a floor. Two machines can honour it differently."""
    data = tomllib.loads((HERE / "pyproject.toml").read_text(encoding="utf-8"))
    return [f"{d!r} is a floor, not a pin: one machine gets a version another never saw"
            for d in data["project"]["dependencies"] if "==" not in d]


def check_lock_is_obeyed() -> list[str]:
    """`uv lock --check` proves the lockfile still answers pyproject, and writes nothing."""
    result = subprocess.run(["uv", "lock", "--check"], cwd=HERE, capture_output=True, text=True)
    if result.returncode != 0:
        lines = [ln.strip() for ln in result.stderr.splitlines() if ln.startswith("error:")]
        return [f"uv lock --check exited {result.returncode}: "
                f"{lines[0] if lines else 'uv printed no error line'}"]
    return []


def check_model_is_registered() -> list[str]:
    """The model every call will name must be an exact ID this project wrote down."""
    try:
        models.require_pinned(models.ANSWERING)
    except models.UnpinnedModel as exc:
        return [str(exc)]
    return []


CHECKS = {
    "keys": check_keys,
    "interpreter": check_interpreter,
    "pins": check_pins_are_pins,
    "lock": check_lock_is_obeyed,
    "model": check_model_is_registered,
}


def check() -> int:
    failures = 0
    for name, run_check in CHECKS.items():
        problems = run_check()
        failures += len(problems)
        for problem in problems:
            print(f"RED    {name}: {problem}")
        if not problems:
            print(f"green  {name}")
    print(f"\n{failures} problem(s)")
    return 1 if failures else 0


def plan(question: str) -> int:
    """Print the exact JSON a question would send. Contacts nothing and needs no key."""
    url, body = loop.Conversation().next_request(question)
    print(f"POST {url}\n")
    print(json.dumps(body, indent=2))
    return 0


def ask(question: str) -> int:
    try:
        print(loop.ask_once(question))
    except provider.ProviderError as exc:
        print(f"the provider refused this request: {exc}", file=sys.stderr)
        return 1
    except keys.MissingKey as exc:
        print(f"{exc}", file=sys.stderr)
        return 1
    return 0


def main(argv: list[str]) -> int:
    match argv[1:]:
        case ["check"]:
            return check()
        case ["plan", question]:
            return plan(question)
        case ["ask", question]:
            return ask(question)
        case _:
            print(__doc__, file=sys.stderr)
            return 2


if __name__ == "__main__":
    sys.exit(main(sys.argv))
```

**Line by line:**

- The module docstring is the **usage message**. `print(__doc__)` at the bottom means the help text
  and the documentation are one string, so they cannot disagree — the commonest small lie in a CLI
  is a usage line describing a flag that was renamed.
- `from ask_desk import loop, provider` and `from ask_desk.util import keys, models` — four imports,
  all inside this folder, plus four from the standard library. This file is the entry point a
  stranger runs, and it is also the proof that the project needs nothing above itself.
- `HERE = Path(__file__).parent`, and every check that touches a file goes through it. Run this
  driver from any directory and it inspects the same project; without it, `check_interpreter` would
  quietly report on whatever `.python-version` happened to be beside the shell.
- The first four checks are day 3's, carried into this project as its own code rather than imported
  — the independence rule from part 1.2 applied to a file rather than to an idea. They are unchanged
  in shape: every `check_*` returns `list[str]`, none of them raises, so one run reports every
  problem instead of only the first.
- `check_pins_are_pins` is green today over an **empty list**, and that is worth naming rather than
  enjoying. This project has no third-party dependency at all on day 4 — every file it prints
  imports the standard library and its own modules, which is what "no framework" in the day's title
  means literally. So the check passes because there is nothing to object to, not because something
  was pinned well. A green check over an empty collection is one of the commonest ways a suite tells
  you nothing while looking healthy, and the way to find out is to give it something to refuse: the
  hub §6 has the edit.
- `check_model_is_registered` is the new one, and it is three lines because part 1.1 did the work.
  It asserts that the ID every call in this project is about to name is in the registry. This is the
  cheapest possible check — no key, no network — and it catches a class of failure that otherwise
  surfaces as a `404` in production.
- `check_keys` calls `keys.require(name)` and **discards the value**. It needs to know whether the
  call raises, not what it returns, and never holding the secret in a local means there is nothing
  for a later `print` or a traceback to leak.
- `CHECKS` is a dict from name to function, so adding a sixth check is one line and the loop is
  untouched. The order is insertion order — a language guarantee since 3.7 — and it is the order the
  output appears in, which is why the cheapest checks are listed first.
- `check()` returns `1 if failures else 0` and does not exit. A function that exits cannot be called
  from anything else, cannot be tested, and cannot be composed into a larger driver later. Day 3
  spent a whole document on the one line that turns this integer into a verdict.
- `plan` builds `loop.Conversation().next_request(question)` — a fresh, empty conversation, so what
  it prints is the *first* turn. It needs no key and touches nothing, which is what makes it the
  right first command when a request is misbehaving.
- `json.dumps(body, indent=2)` prints the body as the provider will receive it, formatting aside.
  Printing the Python `repr` instead would show single quotes and `True`, neither of which is JSON,
  and the difference is exactly the kind of thing you are looking at this output to find.
- `ask` catches `provider.ProviderError` and `keys.MissingKey` **separately**, because they are two
  different problems with two different fixes: one means the provider said no, the other means this
  machine is not wired. Both print to `stderr` and return `1`.
- Both handlers print a message and return a status; neither returns a plausible-looking answer.
  That is the honest-failure rule in four lines — a driver that swallowed the error and printed
  something reassuring would be indistinguishable, on screen, from a working desk.
- Any exception that is *not* one of those two propagates and prints a traceback. That is
  deliberate: an unexpected exception is a bug in this project, and a bug should arrive with its
  stack rather than as a tidy message that hides where it came from.
- `match argv[1:]` with `case ["plan", question]` — structural pattern matching binds the argument
  and checks the count in one line, so `run.py plan` with no question falls through to the usage
  case rather than raising an `IndexError`.
- `case _: print(__doc__, file=sys.stderr); return 2` — a **2**, not a 1. Exit `1` means the checks
  ran and failed; exit `2` means they never ran. A pipeline that treats those the same reports a
  typo in a command as a code failure.
- `sys.exit(main(sys.argv))` — the line day 3 removed on purpose to watch a check print `RED` and
  exit `0`. It is here, and the whole of the day-3 argument is why.

## When it breaks

Now the same project with a question put to it. The request was built correctly — part 1.3 printed
it — and it was sent, and the value in `.env` is the synthetic one. This is the whole path, from the
command line through `ask_once`, into `provider.send`, and back out of the driver:

```console
$ uv run --frozen python run.py ask "Is the VPN down?"
the provider refused this request: HTTP 400: 'API key not valid. Please pass a valid API key.'
$ echo $?
1
```

Part 1.3 met this rejection at the socket, where it is a status code with a documented value that
turns out to be wrong; here it is out of the driver, and what matters is the second line. The desk
printed **nothing that looks like an answer** and handed back `1`. A driver that caught
`ProviderError` and printed *"Sorry, I could not reach the knowledge base"* would have exited `0`,
and every pipeline, hook and eval downstream would have recorded a successful run of a system that
answered nothing. The smallest fix here is not to the code at all — it is a working key in `.env` —
and the code's job was to say so instead of covering for it.

## In production

**What a senior writes instead.** The conversation is not a list on an object that dies with the
process. It is a session behind an interface — a store with an identifier the caller quotes, so a
second request can land on a second replica and still find the thread; and behind that interface,
something that decides what to *keep*, because an unbounded transcript eventually exceeds the
model's context and then fails at the worst moment rather than the cheapest one. Trimming to the
last N turns, summarising the older ones, and keeping the system instruction pinned at the front are
the three usual moves. The framework this project adopts on day 6 has a session service for exactly
this, and the memory track is where what-to-keep gets taught properly.

**What degrades at scale.** The number is **nineteen**. On turn ten a correctly-kept thread carries
nineteen contents — ten of yours and nine replies — and every one of them is uploaded and read
again on turn eleven, and again on turn twelve. Input grows linearly with the number of turns and
the total input paid for across a conversation grows with the square of it, which is why a chat that
felt free in testing at three turns is a surprise at thirty. Nothing is wrong; it is what stateless
means, and a system that never says so out loud is a system whose bill nobody can explain.

**The review comment.** "`Conversation` is fine, but it is process-local and unbounded. Two things
before this can serve more than one user: put the thread behind a store keyed by a session id so a
second request does not have to hit the same worker, and put a cap on `contents` with a documented
policy for what gets dropped. Right now a long-running chat fails when it exceeds the context
window, and the failure arrives as a provider error in the middle of a user's sentence."

**The interview question.** "Your assistant holds multi-turn conversations. Where does the
conversation physically live, what happens to it when the process restarts, and what happens when it
grows past the model's context window? Answer for the system you last worked on, not in general."
