## One-line answer

Skip the one line that appends the model's reply to `contents` and the second question goes out as
two consecutive `user` turns with nothing from the model in between — a well-formed request, no
exception, no warning, and an assistant that has never once been shown a word it said.

## The idea

You have been keeping the file, as part 2.1 said you must: your letters and their replies, in order,
attached to everything you send. Then one week you are in a hurry. The reply comes, you read it, you
act on it, and you put it in the bin instead of the folder. Nothing happens. Nothing *can* happen —
the folder is a folder.

The next letter goes out with the file attached. Your correspondent opens it and finds two letters
from you, one after the other, and no answer between them. From where they sit, this is a person who
wrote, was ignored, and wrote again. And here is the part worth stopping on: **they will still
reply.** They are helpful and they have no memory, so they have nothing to compare this against.
They will answer your second letter reasonably, probably repeat some of what they already told you
last week, and post it back. The envelope will look exactly like every other envelope.

That is the failure, and it is the day's deliberate one because of the shape rather than the size.
There is no exception. There is no warning. The request is well formed. The reply arrives, on time,
in the right format, and reads like an answer — because it is an answer, to a question asked by
somebody the model has never been allowed to see itself answering.

Be precise about what is and is not legal here, because the temptation is to assume the provider
will catch it. The reference for `Content.role` says, verbatim, on 2026-09-09:

> The producer of the content. Must be either 'user' or 'model'.

That constrains the **value** of the field. Both turns in the broken request carry `user`, which is
one of the two permitted values, so nothing about the field is wrong. The page does not say that
turns must alternate, and this project has not established what the provider does with a sequence
that does not — so the honest position is that the request is documented-legal and its treatment is
unknown here, which is a strictly worse situation than an error.

Two more things make this failure hard to catch by eye.

The first is that **the first turn of every conversation is identical either way.** Turn one has
nothing to file yet. So a demonstration, a smoke test or a screenshot that asks one question passes
perfectly, and only the second question is wrong. Anything that tests your desk one question at a
time will never see it.

The second is that the symptom is not silence, it is *repetition and mild incoherence* — a
follow-up answered as though it were an opening, a fact restated that was given a moment ago,
advice that ignores the constraint the previous answer established. Those read like model quality.
People retune the system instruction, or swap the model, or write a longer prompt, and the bug is a
missing `append`.

## The mechanism

There is no new code in this part. The mechanism is one line that part 2.1 already printed, and the
switch that lets it be turned off without editing anything:

The line, in `Conversation.ask`:

> `if self.remember and reply is not None:` &nbsp;→&nbsp; `self.contents.append(reply)`

The switch, in the dataclass: `remember: bool = True`.

That flag exists for this document. A failure you demonstrate by editing a file is a failure you see
once; a failure that is a constructor argument can be run **beside** the working version, in one
command, with both results printed together — and it can be asserted on by a test later.

Now the comparison. Read the command as carefully as the output, because one thing in it is not
real, and it says so:

```console
$ uv run --frozen python -c "
import json
from ask_desk.loop import Conversation

# A stand-in for what turn 1 returned. Synthetic, written here, not a recorded provider response.
reply = {'role': 'model', 'parts': [{'text': 'The VPN gateway is up. There is a known issue with split tunnelling.'}]}

kept = Conversation()
kept.contents.append({'role':'user','parts':[{'text':'Is the VPN down?'}]})
kept.contents.append(reply)                      # what ask() does when remember is True

dropped = Conversation(remember=False)
dropped.contents.append({'role':'user','parts':[{'text':'Is the VPN down?'}]})
                                                 # what ask() does when remember is False

for label, convo in [('reply filed', kept), ('reply dropped', dropped)]:
    _, body = convo.next_request('What should I try first?')
    roles = [c['role'] for c in body['contents']]
    print(f'{label:14} -> {len(body[\"contents\"])} contents, roles {roles}')
"
reply filed    -> 3 contents, roles ['user', 'model', 'user']
reply dropped  -> 2 contents, roles ['user', 'user']
```

**Line by line:**

- **The `reply` dictionary is a stand-in, written in the command itself.** It is not a recorded
  provider response, and this document does not claim it is one. There is no working key on this
  machine, so no real reply could be captured; what is being demonstrated is the *shape of the next
  request*, and that half is real, produced by this project's own `next_request` from this
  project's own `Conversation`. The text inside it could have been any sentence at all without
  changing a single number in the output.
- `kept` performs by hand exactly what `ask` does when `remember` is `True`: append the user turn,
  then append the model's turn. `dropped` performs what `ask` does when `remember` is `False`:
  append the user turn and stop. The comments in the command say which is which, so the transcript
  is readable without the source beside it.
- `next_request` is used rather than `ask`, so **nothing is sent**. No key, no network, no quota,
  and the difference between correct and broken is visible anyway. This is the payoff of part 1.3's
  decision to separate building a request from performing one.
- `reply filed -> 3 contents, roles ['user', 'model', 'user']`. The exchange reads as an exchange:
  a question, an answer, a follow-up. The model's second turn begins with its own previous answer in
  view, which is the only reason "what should I try first?" refers to anything.
- `reply dropped -> 2 contents, roles ['user', 'user']`. Two turns, both `user`, adjacent. One
  content is missing and it happens to be the entire memory of the exchange. The `parts` are
  well-formed, the roles are legal values, `json.dumps` will serialise it, and `build_request` had
  no objection — it does not audit the thread it is handed, and a function that guessed at what a
  well-shaped conversation looks like would be wrong the first time somebody had a legitimate reason
  for something unusual.
- The difference between the two runs is **one integer** — 3 against 2 — and that is the whole
  observable, on this machine, of a bug that removes the assistant's memory.

And this is what the second request actually carries when the reply was dropped — the `contents`
array, in full:

```json
[
  {
    "role": "user",
    "parts": [
      {
        "text": "Is the VPN down?"
      }
    ]
  },
  {
    "role": "user",
    "parts": [
      {
        "text": "What should I try first?"
      }
    ]
  }
]
```

**Line by line:**

- Read it as the model receives it: somebody asked whether the VPN is down, was told nothing, and
  then asked what to try first. Every reasonable reading of that is a person who was ignored.
- `"What should I try first?"` has no antecedent. The word *first* refers to a sequence that was
  never established, and the model must invent one — which it will do, fluently, because that is
  what it is for.
- There is nothing in this JSON to fail on. No missing field, no wrong type, no illegal role value.
  A schema validator would pass it. A test asserting `response.status == 200` would pass it. This is
  why the check that catches this failure has to be about the **thread**, not about the request.
- What the model returns when handed this is **`TODO(me)`: run
  `uv run --frozen python run.py ask "Is the VPN down?"` followed by a second question in one
  process, with a working key in `.env`, and record both answers.** No answer is written here,
  because none was observed, and a plausible one invented for a document is exactly the kind of
  thing this curriculum treats as a fabricated result.

*The role sequences above were observed on this machine on 2026-09-09, uv 0.12.3, CPython 3.12.12.
The model reply inside the command is synthetic and is labelled as such in the command itself.*

## When it breaks

It does not break. That is the finding, and it is why this is the day's deliberate failure rather
than one of its traps: there is no error text to paste, because no error is produced. The request is
valid, the transport succeeds, the reply parses, `text_of` returns a string, and `run.py ask` exits
`0`.

The only error this path can be made to print on this machine is the one that has nothing to do with
it — the synthetic credential being refused, which part 2.1 showed end to end:

```text
the provider refused this request: HTTP 400: 'API key not valid. Please pass a valid API key.'
```

Note what that means honestly: the *user-visible* symptom of the forgetting bug — an assistant that
answers a follow-up as if it were an opening — cannot be reproduced here, because reproducing it
needs a working key and there is not one on this machine. `TODO(me)`: with a real key in `.env`, ask
two questions in one process against a `Conversation()` and then against a
`Conversation(remember=False)`, and write down what differs in the two second answers. What *is*
reproducible offline, and what you should trust, is the shape of the request
above: two `user` turns, adjacent, with the model's own words nowhere in them. Somebody shipped
this, watched a demonstration of one question go perfectly, and spent the following week improving
a prompt.

## In production

**What a senior writes instead.** They make the append impossible to forget rather than easy to
remember. `contents` becomes private to the conversation object and the only way to add to it is a
method that adds *both* halves of an exchange, so a code path cannot record one and drop the other.
Above that, the thread lives in a session service — the framework this project adopts on day 6 has
one — where appending the model's turn is the framework's job and not a line in your loop. And
underneath both, they write the assertion: a test that runs two turns and checks that the roles in
the second request alternate. It is three lines, it goes red on this bug, and it is the only thing
in the list that would have caught it.

**What degrades at scale.** The numbers are **19 and 10**. By the tenth question a thread that files
its replies carries nineteen contents; the broken one carries ten, and every one of the ten is
yours. So you pay to upload ten of your own questions, you receive an answer built on none of the
nine that were given, and the model has been shown its own words **zero** times in the entire
conversation. The cost does not show up as an error rate — it shows up as an assistant that is
subtly, consistently worse than the model you are paying for, in a way that no dashboard has a
column for.

**The review comment.** "This appends the user message and returns the text, and never appends
`candidate['content']`. Turn two therefore sends two `user` roles in a row and the model has no view
of its own previous answer — nothing will raise, and the symptom looks like a quality problem.
Please append the model turn inside `ask`, make `contents` private so no caller can half-update it,
and add a test asserting the roles alternate across two turns."

**The interview question.** "A stateless chat API. Name three bugs that produce a well-formed
request the server accepts, no exception anywhere in your code, and a measurably worse assistant —
and for each one, say what you would assert in a test to catch it, given that you cannot assert on
the model's answer."
