## One-line answer

The parameter schema the model is shown is derived from the function's signature — annotations become
`type`, defaults become `default`, and a parameter without a default becomes `required` — which
means ADK writes down one thing day 5's hand-written declaration only said in English, and stops
constraining a parameter entirely the moment you leave its annotation off.

## The idea

The clerk works down your old paperwork box by box. Where you wrote a date, they copy a date into the
date box. Where you wrote nothing, they copy nothing, and the box on the new form stays empty. They
do not stop and ask what you meant to put there. An empty box is not an error to a clerk; it is
simply a box with nothing in it, and the form goes into the pile looking exactly as complete as
every other form in the pile.

The old paperwork here is the function signature. `search_notes(query: str, limit: int = 3)` carries
four separate facts, and every one of them is written in a place a program can read: there is a
parameter called `query`, it is annotated `str`, there is a parameter called `limit`, and `limit`
has a default of `3`. Day 5's declaration restated three of those by hand in JSON and turned the
fourth — the default — into a sentence: `"Maximum notes to return. Defaults to 3."` A sentence is
for a reader. It sits inside a `description` field, in English, and the model has to *read* it and
believe it in order to act on it.

`FunctionTool` copies the signature into a **JSON Schema** — the same shape day 5 typed by hand: an
object with a `properties` map, one entry per parameter, and a `required` list naming the ones with
no default. Annotations become the `type` of each property. Defaults become a `default` key. And
this is where ADK gets something the hand-written version did not have: `"default": 3` is a *field*,
not a sentence. It is in the schema, at the parameter, in a place a machine reads before a model
does.

Which brings us to the empty box. Leave the annotation off — write `limit=3` instead of
`limit: int = 3` — and the derived property has no `type` key at all. Not `"type": "any"`, not
`"type": null`. The key is absent, and a JSON Schema property with no `type` constrains nothing: a
string satisfies it, a number satisfies it, an object satisfies it. Nothing raises when the tool is
wrapped, nothing warns when the agent is built, and the declaration that goes out is well-formed and
complete-looking. The box is simply empty, and the form goes into the pile.

The word for the missing thing is worth saying plainly, because it is not obvious: an annotation you
wrote for your editor and your type checker is, in this file, load-bearing at runtime, for a reader
that is not Python.

## The mechanism

The signature `FunctionTool` reads, from the file **day 05 part 1.2** printed whole:

```python
# ask_desk/tools.py — the signature, from the file day 05 part 1.2 printed whole

def search_notes(query: str, limit: int = 3) -> dict[str, Any]:
    """Find knowledge-base notes matching a query. An empty list is a valid answer."""
    # ── body unchanged from day 05 part 1.2 ──
```

**Line by line — recap depth.** The function is taught in full by day 05 part 1.2, in
`days/01-ask-desk/day-05-tools-hand/`. Only the four facts the derivation reads matter here:

| Token | What it becomes, and the failure it prevents |
| --- | --- |
| `query` | A property named `query` in the schema. The model sends this key or the call does not fit the function. |
| `: str` | `"type": "string"` on that property. Without it the schema permits any JSON value at all — see the second transcript below. |
| `limit` | A second property. Optional, because of what follows it. |
| `= 3` | Two things at once: `"default": 3` in the schema, and `limit` left *out* of `required`. The model may omit it and get the same behaviour the function would have chosen. |
| `-> dict[str, Any]` | Not read into the parameter schema. The return type is expressed to the model by the value it is handed at the tool-result turn, which day 5 built. |

And the declaration derived from it. This is the day's centrepiece:

```console
$ uv run --frozen python -c "
import json, warnings
warnings.filterwarnings('ignore')
from google.adk.tools import FunctionTool
from ask_desk import tools

d = FunctionTool(tools.search_notes)._get_declaration()
print('name       ', d.name)
print('description', repr(d.description))
print(json.dumps(d.parameters_json_schema, indent=2))
"
name        search_notes
description 'Find knowledge-base notes matching a query. An empty list is a valid answer.'
{
  "properties": {
    "query": {
      "title": "Query",
      "type": "string"
    },
    "limit": {
      "default": 3,
      "title": "Limit",
      "type": "integer"
    }
  },
  "required": [
    "query"
  ],
  "title": "search_notesParams",
  "type": "object"
}
```

**Line by line:**

- `"type": "string"` and `"type": "integer"` came from `: str` and `: int`. Day 5 typed those two
  strings into JSON by hand and they were correct; here nobody typed them, so nobody can mistype them
  or forget to change one when the signature changes. That is the same argument as the name in part
  1.1, applied to a second field.
- `"required": ["query"]` came from the *absence of a default*, not from anything you declared.
  `limit` has `= 3` and so is optional; `query` has nothing and so is required. Day 5 maintained that
  list by hand, which means day 5 could have listed `limit` as required and shipped a declaration
  that contradicted its own function.
- **`"default": 3` is the thing ADK has that the hand-written version does not.** Day 5's
  declaration carried the same fact as prose — `"Maximum notes to return. Defaults to 3."` — inside
  the parameter's `description`. Compare the two honestly: one is a field a schema validator reads,
  the other is a sentence a language model has to parse and trust. When they disagree, only one of
  them is checkable.
- `"title": "Query"` and `"title": "Limit"` are the parameter names with the first letter
  capitalised. Note what they are not: they are not guidance. `"Query"` tells the model nothing that
  `query` did not already tell it. Part 2.2 is where that costs something.
- `parameters_json_schema` is reached through `_get_declaration()`, whose leading underscore says
  plainly that it is not a supported interface. It is used here to *look*, in a probe, and nowhere in
  `ask_desk/`. A private method is a fine window and a terrible door.
- Nothing in this command contacts a provider. Deriving a declaration reads the function object,
  builds a schema and stops.

Now the same signature with the two annotations removed, and nothing else changed:

```console
$ uv run --frozen python -c "
import json, warnings
warnings.filterwarnings('ignore')
from google.adk.tools import FunctionTool

def search_notes_untyped(query, limit=3):
    '''Find knowledge-base notes matching a query. An empty list is a valid answer.'''
    return {}

d = FunctionTool(search_notes_untyped)._get_declaration()
print(json.dumps(d.parameters_json_schema, indent=2))
"
{
  "properties": {
    "query": {
      "title": "Query"
    },
    "limit": {
      "default": 3,
      "title": "Limit"
    }
  },
  "required": [
    "query"
  ],
  "title": "search_notes_untypedParams",
  "type": "object"
}
```

**Line by line:**

- Both `"type"` keys are **gone**. Not empty, not null — absent. A JSON Schema property carrying only
  a `title` places no constraint on the value: `"vpn"`, `3`, `true` and `{"a": 1}` all satisfy it
  equally.
- Everything else survived. `"default": 3` is still there, `"required": ["query"]` is still correct,
  the property names are still right. The declaration is well-formed and it is *nearly* the same
  document, which is exactly why nobody spots this in review: the diff is two absent lines in a block
  of twelve.
- No exception, no warning, no log line. The wrapper does not consider a missing annotation to be a
  problem, because it has no way to know whether you meant to leave it off.
- This function is a probe, defined in the command. Nothing in `ask_desk/tools.py` looks like this
  and part 2.1's rep is the only place this day touches that file.

*Observed on this machine on 2026-09-09: google-adk 2.8.0, CPython 3.12.12, uv 0.12.3.*

## When it breaks

The unconstrained parameter does not fail where it was written. It fails later, inside the tool,
when the model sends the value the schema permitted. Here is `search_notes` receiving `3` where it
expected words — the path leading in is elided to keep the trace readable, and the two frames shown
are verbatim:

```console
$ uv run --frozen python -c "
from ask_desk import tools
print(tools.dispatch('search_notes', {'query': 3}))
"
Traceback (most recent call last):
  File "<string>", line 3, in <module>
  File "...\projects\01-ask-desk\ask_desk\tools.py", line 153, in dispatch
    return REGISTRY[name](**args)
           ^^^^^^^^^^^^^^^^^^^^^^
  File "...\projects\01-ask-desk\ask_desk\tools.py", line 38, in search_notes
    words = [w for w in query.lower().split() if len(w) > 2]
                        ^^^^^^^^^^^
AttributeError: 'int' object has no attribute 'lower'
```

Read the last two frames together, because the pairing is the lesson. `dispatch` is day 5's
guard rail and it catches `TypeError` — arguments that do not *fit* the signature — turning them into
an `error` dict the model can be shown. An `AttributeError` from inside the function body is not a
`TypeError`, so it goes straight past, out of the dispatcher, and kills the turn. Somebody's Friday
evening: a well-formed request, a well-formed declaration, and a traceback whose top frame is a list
comprehension nobody has edited in a month. The smallest fix is one word — `query: str` — and the
lasting one is a check that refuses to ship a schema property with no `type`.

## In production

**What a senior writes instead.** They annotate every parameter of every tool, including the obvious
ones, and they put a test in the suite that walks the agent's tools and asserts that every property
of every derived schema has a `type`. That test is four lines and it is the only thing standing
between a signature edit and an unconstrained interface, because no linter, formatter or type checker
in a default configuration treats a missing annotation as an error.

**What degrades at scale.** The number is **four out of four**. This desk has three tools and four
parameters between them, and dropping the annotations removes the `type` from every one — a hundred
per cent of the schema's constraints, from an edit that shows up in review as two deleted words. The
same arithmetic at thirty tools is thirty declarations that look complete and constrain nothing, and
the symptom is not an outage. It is a model that starts sending plausible garbage at a rate nobody
can attribute to anything.

**The review comment.** "`limit=3` lost its annotation in this diff. That is not a style change —
the annotation is the `type` in the tool's JSON Schema, so this ships a parameter the model may send
a string for. Please restore `limit: int = 3`, and let us add the schema assertion to the tool tests
so the next one goes red instead of shipping."

**The interview question.** "Your framework derives tool schemas from Python signatures. Somebody
removes a type annotation. Walk me through everything that does *not* fail — the import, the linter,
the type checker, the agent construction, the request — and tell me at which point the mistake first
becomes observable, and what you would put in place to make it observable earlier."
