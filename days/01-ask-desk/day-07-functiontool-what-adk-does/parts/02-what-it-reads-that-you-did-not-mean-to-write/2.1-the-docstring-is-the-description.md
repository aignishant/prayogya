## One-line answer

The entire docstring — every line of it, including the warning you wrote for your colleagues — is
the description the model reads on every turn, and a function with **no** docstring is described to
the model as `'Call self as a function.'`, which nothing raises, nothing warns about, no linter in a
default configuration objects to, and no check in this project can see.

## The idea

The clerk copies the note you scribbled in the margin. You wrote it for yourself, years ago, in
pencil, meaning nothing by it — *ask about the deposit* — and now it is on the new form, in the
clerk's neat hand, in a box that says Additional Information. Nobody transcribed your intent, because
nobody asked for it. They transcribed what was on the paper, and what was on the paper included the
note.

And when you left a box empty, the clerk did not leave it empty. The form does not permit an empty
box, so they reached for the office's own rubber stamp — the standard wording, the one that fits any
form and describes nothing about you — and stamped it. The finished form now says something in every
box. One of the things it says is about the office.

Those are the two halves of this document, and they are the same mechanism seen from either side.

The first half. Day 5 established that the **description** is the whole interface: the model never
sees your code, only the declaration, so the description is not documentation *about* the tool — it
is the instruction the model acts on when it decides whether to call it. Part 1.1 showed the name
coming from `__name__`. The description comes from `__doc__`, which is the docstring, whole. Not the
summary line. Not the first paragraph. The whole string, blank lines and all.

That changes what a docstring *is* in a file like `ask_desk/tools.py`. Everywhere else in Python, a
docstring is a note to the next human. Here it is being said to the model, in full, on every single
turn, as the tool's operating instructions. A line you added for a colleague — *don't use this one,
it's slow* — is now advice the model is weighing. That is not a hazard. Used deliberately it is the
best property of this whole arrangement, because the guidance and the code sit in one place and
cannot drift: the caution and the function it guards are the same edit.

The second half is the failure, and it is the quietest one in this project. Delete the docstring —
not a word of code, just the string — and `FunctionTool` has nothing to copy into the description. It
does not leave the description empty and it does not complain. A function with no docstring has
`__doc__` set to `None`, but `__call__.__doc__` — the documentation of the method that makes any
object callable — is always there, and it reads `'Call self as a function.'` That sentence leaks off
the object and travels out as the model's only description of your tool. The model is told, in the
one field that says what the tool is *for*, that its purpose is to call itself.

Sit with how little that costs to cause. It is one line removed. It is not a syntax error, not a
type error, not a test failure. Most linters treat a missing docstring as a style preference and
most projects have that rule off. It survives review, because reviewers read diffs and a deleted
docstring reads as tidying. It survives CI. It survives this project's own `run.py check`, and part
2.2's ledger is where that stops being a surprise and becomes an entry: nothing in `ask_desk/`
inspects a derived declaration, so there is nothing here that *could* go red.

What the model then does about being told a tool's purpose is to call itself is a question this
document does not get to answer. There is no working key on this machine, and inventing a model's
behaviour would be the same offence as inventing a transcript. The rep at the end names the exact
command that settles it.

## The mechanism

Start with the good half, on a function written to show it. The docstring below is what a careful
author writes: a summary line, a blank line, and two sentences of caution meant for whoever reads
the file next.

```python
# a probe, defined in the command below — nothing in ask_desk/ looks like this

def restart_service(service: str) -> dict:
    """Restart one service.

    Only ever call this after check_service_status shows the service is degraded.
    Restarting an operational service drops every session on it.
    """
    return {}
```

**Line by line:**

- The summary line, `Restart one service.`, is the part every Python convention agrees is the
  docstring's job: one sentence, imperative, on the first line.
- The two sentences after the blank line are the part every Python convention treats as being for a
  *reader of the source*. They are a caution about when the tool is safe to use, and the author of
  this function plainly wrote them for a colleague.
- `service: str` gives the parameter a `type` in the schema, per part 1.2, and `-> dict` is not read
  into the schema at all.
- The body is `return {}` because the body is irrelevant to the derivation. Nothing about what a tool
  *does* reaches the model; only what the declaration *says*.

Now what the wrapper makes of that docstring, together with what it makes of a function that has
none:

```console
$ uv run --frozen python -c "
import json, warnings
warnings.filterwarnings('ignore')
from google.adk.tools import FunctionTool

def restart_service(service: str) -> dict:
    '''Restart one service.

    Only ever call this after check_service_status shows the service is degraded.
    Restarting an operational service drops every session on it.
    '''
    return {}
print('A:', repr(FunctionTool(restart_service).description))

def restart_service_2(service: str) -> dict:
    return {}
print('B:', repr(FunctionTool(restart_service_2).description))

def restart_service_3(service) -> dict:
    '''Restart one service.'''
    return {}
print('C:', json.dumps(FunctionTool(restart_service_3)._get_declaration().parameters_json_schema))
"
A: 'Restart one service.\n\nOnly ever call this after check_service_status shows the service is degraded.\nRestarting an operational service drops every session on it.'
B: 'Call self as a function.'
C: {"properties": {"service": {"title": "Service"}}, "required": ["service"], "title": "restart_service_3Params", "type": "object"}
```

**Line by line:**

- **A** is the *whole* docstring. Read the escapes: `\n\n` is the blank line, and the two warning
  sentences follow it, intact. The description the model receives is not the summary line — it is
  every character between the triple quotes. The colleague-facing caution about dropping sessions is
  now part of the tool's operating instructions, which is exactly where it belongs and almost
  certainly not where its author thought it was going.
- The corollary is uncomfortable and worth stating flatly: anything you write in a tool's docstring
  is being said to the model. A stale note, a joke, a `TODO` left in, a sentence describing behaviour
  the function no longer has — all of it goes out, every turn, as instructions.
- **B** is the failure. `restart_service_2` differs from `restart_service` by nothing except the
  absent docstring — same name, same signature, same body — and its description is
  `'Call self as a function.'` For any plain function `f`, `f.__doc__` is `None` when the docstring is
  gone but `f.__call__.__doc__` is that sentence — the documentation of the method that makes an
  object callable — and it is what the wrapper ends up copying. The rubber stamp.
- Nothing was raised, nothing was warned, nothing was logged. The `print` on the previous line and
  the `print` on this line ran identically. If you were not comparing the two strings side by side you
  would have no reason to look.
- **C** is part 1.2's subject and it is in this transcript because the three cases were captured in
  one command: `restart_service_3` has a docstring but no annotation on `service`, and the property
  carries a `title` and no `type`.

### The break, on this project's own tools

The probe above is a probe. Here is the same failure on `ask_desk/tools.py`, which day 05 part 1.2
printed whole. Delete the one-line docstring from `check_service_status`, leaving the function
otherwise untouched, and derive all three descriptions together:

```console
$ uv run --frozen python -c "
import warnings; warnings.filterwarnings('ignore')
from google.adk.tools import FunctionTool
from ask_desk import tools
for f in (tools.search_notes, tools.fetch_note, tools.check_service_status):
    print(f'  {f.__name__:22} {FunctionTool(f).description!r}')
"
  search_notes           'Find knowledge-base notes matching a query. An empty list is a valid answer.'
  fetch_note             'Return one note in full by its id, or an error saying it does not exist.'
  check_service_status   'Call self as a function.'
```

**Line by line:**

- Three rows, two correct, one meaningless — and **nothing in the output is an error**. It is a
  well-formed list in which one entry quietly means something else. That is the shape this failure
  has in a real project: not a stack trace, not a red line, a column of plausible rows with one that
  has stopped saying anything.
- The broken row is the *status check* — the tool whose entire job is to tell the desk whether a
  service is up. Its description is now a sentence about function objects.
- The edit that caused it was the deletion of a single line, from a file whose other two functions
  are untouched and correct. There is no diff hunk here that looks dangerous.
- Restoring is the same edit in reverse. The description comes straight back, from the file, with
  nothing else changed:

```console
$ uv run --frozen python -c "
import warnings; warnings.filterwarnings('ignore')
from google.adk.tools import FunctionTool
from ask_desk import tools
print('  ', repr(FunctionTool(tools.check_service_status).description))
"
   'Return the current status of one service: operational, degraded or maintenance.'
```

**Line by line:**

- Same command, same file, one line put back, and the tool means something again. The whole distance
  between a described tool and an undescribed one is one string literal in one file.
- Note what this proves about ownership: the description is not stored anywhere, cached anywhere, or
  registered anywhere. It is read off the function each time a declaration is built, which is why the
  fix is instant and why the breakage is equally instant.

*Observed on this machine on 2026-09-09: google-adk 2.8.0, CPython 3.12.12, uv 0.12.3.*

## When it breaks

This section usually carries a traceback. This time the point is that there is not one, so what it
carries instead is the project's own gate, run with the break still in place — the docstring deleted
from `check_service_status`, one of the three tools describing itself as `'Call self as a function.'`:

```console
$ uv run --frozen python run.py check
green  keys
green  interpreter
green  pins
green  lock
green  model

0 problem(s)
$ echo $?
0
```

Five green and `0 problem(s)`, honestly reported, on a desk whose status tool no longer tells the
model what it is for. Nothing lied: the keys are wired, the interpreter matches, the pins are pins,
the lock answers, the model is registered — and not one of those five checks has ever looked at a
derived declaration. Somebody deletes a docstring on a Friday while tidying, the review passes
because the diff is one removed line, CI passes because CI runs this command, and the only thing
that changed is what the model believes one of its three tools is for. The smallest fix is to put the
line back. The lasting fix is a sixth check, and that is this day's rep.

## In production

**What a senior writes instead.** They treat a tool's docstring as an interface and review it as one:
the summary line says what the tool returns, and any line that is really a note to a colleague either
goes above the `def` as a `#` comment — which `__doc__` never sees — or is deliberately kept in the
docstring because the model *should* be told. And they add the check that this project does not have:
walk the agent's tools, derive each declaration, and refuse any description that is empty or equal to
`'Call self as a function.'`. It is a handful of lines, it goes in the same suite as the schema
assertion from part 1.2, and it is the only mechanism in the whole stack that can see this.

**What degrades at scale.** The number is **zero** — the number of checks in this project, in its
linter, in its type checker and in its CI that go red when a tool's description is destroyed. That is
not a small number that grows worse with scale; it is the number that makes scale dangerous. One
tool in three here, and you would still not have known without deriving the declarations by hand. At
twenty tools across four agents, a description silently replaced by a sentence about callable objects
is indistinguishable, in every artefact anyone looks at, from a description that is fine.

**The review comment.** "This removes the docstring from `check_service_status`. That docstring is
the tool's description in the model-facing declaration — with it gone the model is told the tool's
purpose is `'Call self as a function.'`, and nothing in our checks catches it. Please restore it, and
let us add a test that asserts every derived description is non-empty and not that string."

**The interview question.** "In a framework that derives a tool's description from its docstring,
describe the full blast radius of deleting one — what changes, what does not change, which of your
existing quality gates would notice, and how you would find out whether it had already happened in a
service you inherited."
