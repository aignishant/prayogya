## One-line answer

The agent is a brief and does nothing; the `Runner` is what works a question through it, it needs a
`SessionService` because the conversation list you carried by hand on day 4 now lives in a session
somebody else keeps, and every entrance to it is a coroutine — so the code that calls it is `async`
all the way up to one `asyncio.run` at the edge.

## The idea

The brief is written and it is sitting on a desk at the agency, where it does exactly nothing. A
brief is not a person. Somebody has to pick up your question, take it to whoever the brief describes,
and stay with the job until there is an answer to hand back — and that somebody is the second half of
what you bought.

Watch what the coordinator actually does with a job, because all three of this part's ideas are in it.
First they open a **file** for you, and everything about this job goes in it: your question, what came
back, what was looked up on the way. Next time you ring, they do not ask you to repeat the whole
conversation — they pull the file. That file is the thing you were carrying yourself last week in a
list, and handing it over is the single largest change in this project so far, because it is the first
time the thread is somewhere you cannot see.

Second, they do not hand you one finished answer and nothing else. If you stand there you can watch it
happen: a note that they are looking something up, a drawer opening, a result coming back, another
question, and eventually the sentence you actually wanted. Today you are only listening for the last
one. That the rest of it is available at all, and what you can do with it, is the subject of a later
day.

Third — and this is the one that shows up in the shape of your code rather than in its behaviour —
nobody at the agency sits with a phone pressed to their ear waiting. Everything in this job is
waiting: waiting for a model to answer, waiting for a lookup to come back. A coordinator who blocked
on each wait could run one job at a time. So the work is written to be *suspendable*: it hands control
back at every wait and picks up where it left off when something arrives.

The terms, as they arrive. A **runner** is the object that executes one turn for an agent: it holds
the agent, it holds the thing that stores conversations, and it produces the turn's events as they
happen. A **session** is one stored conversation, identified by a user and an id, and a
**session service** is what stores and retrieves them. The one this project uses keeps them in the
memory of the running process and nowhere else, which is fine for a desk you are building and is a
property with consequences — those belong to day 9, *Sessions, runs, and errors that surface instead
of hiding*, and not to this part.

## The mechanism

The driver gains one subcommand. `projects/01-ask-desk/run.py`, as a marked diff against the whole
file day 4 printed — four changes, and everything not shown is unchanged from that day:

```diff
--- projects/01-ask-desk/run.py    as day 4 printed it
+++ projects/01-ask-desk/run.py    with the `adk` subcommand
@@ the module docstring @@
     python run.py check          the gate: config, pins, and the registry
     python run.py plan "..."     print the request a question would send, and send nothing
     python run.py ask "..."      ask the desk one question, hand-rolled (needs a working key)
+    python run.py adk "..."      the same question through the ADK agent (needs a working key)
 """

 from __future__ import annotations

+import asyncio
 import json
 import subprocess
 import sys
 import tomllib
@@ below `def ask(question: str) -> int:`, which is unchanged from day 4 @@
+def adk(question: str) -> int:
+    """The same desk, driven by ADK's Agent and Runner instead of by loop.py."""
+    from ask_desk import agent  # imported here so `check` needs no framework import
+
+    try:
+        print(asyncio.run(agent.ask(question)))
+    except keys.MissingKey as exc:
+        print(f"{exc}", file=sys.stderr)
+        return 1
+    return 0
+
+
 def main(argv: list[str]) -> int:
     match argv[1:]:
         case ["check"]:
             return check()
         case ["plan", question]:
             return plan(question)
         case ["ask", question]:
             return ask(question)
+        case ["adk", question]:
+            return adk(question)
         case _:
             print(__doc__, file=sys.stderr)
             return 2
```

**Line by line:**

- The docstring line is part of the change and not an afterthought. `main`'s fallthrough case prints
  `__doc__` to `stderr` and returns `2`, so this docstring is the driver's only usage message: a
  subcommand that works and is not listed there is a subcommand nobody but its author can find.
- `import asyncio` at the top, and it is the **only** new import in this file. That is the shape of
  the boundary being drawn here: `run.py` knows that something inside is asynchronous, and it does not
  know what a `Runner` is.
- `from ask_desk import agent` **inside** the function, with the comment saying why. Importing it at
  the top would mean `python run.py check` imports the framework — and worse, builds `desk` at import
  time, since part 1.1's agent is constructed at module scope. The gate would then depend on the
  registry resolving, on the model field validating, and on `google.adk` being installed at all. A
  check that cannot run until the thing it checks is working is not a gate. This one line keeps
  `check` answerable on a machine where the install went wrong.
- `asyncio.run(agent.ask(question))` — the single place in this project where the asynchronous world
  is entered. `agent.ask(question)` does not run anything; it produces a coroutine, and `asyncio.run`
  starts an event loop, drives that coroutine to completion, returns its value and shuts the loop
  down. One per process, at the edge, in the synchronous function that the `match` statement calls.
- `except keys.MissingKey` and nothing else. Compare `ask` two functions above, which also catches
  `provider.ProviderError` — the hand-rolled path raises this project's own error type, which day 4
  wrote, because day 4's code is what sends the request. Nothing in the ADK path raises
  `ProviderError`, because nothing in the ADK path is this project's request code. What it raises
  instead is part 2.2's subject, and the fact that this `try` block does not catch it is deliberate:
  an error you have not decided how to handle should reach the terminal in full, not be flattened
  into a one-line message that loses the stack.
- `case ["adk", question]` sits below `case ["ask", question]` and above `case _`. Match statements
  try patterns in order, so a new case must go before the catch-all — and putting the two paths next
  to each other is the point of the whole subcommand: the same question, two implementations, one
  keystroke apart.

### What a runner needs, in the framework's own words

Three signatures, quoted verbatim from `https://adk.dev/api-reference/python/google-adk.html`,
checked 2026-09-09:

> `Runner(*, app=None, app_name=None, agent=None, node=None, plugins=None, artifact_service=None,
> session_service, memory_service=None, ...)`

> `async run_async(*, user_id, session_id, invocation_id=None, new_message=None, state_delta=None,
> run_config=None, yield_user_message=False)`

> `abstractmethod async create_session(*, app_name, user_id, state=None, session_id=...)`

**Line by line:**

- Every one of them begins with a bare `*`, so **every argument is keyword-only**. You cannot pass a
  runner's agent positionally and you cannot get the order wrong, which removes an entire class of
  mistake and replaces it with a different one: a misspelt keyword is not a wrong argument, it is a
  missing argument, and an argument with a default going missing is silent.
- In `Runner`, count the defaults: `app`, `app_name`, `agent`, `node`, `plugins`,
  `artifact_service`, `memory_service` — all `None`. **`session_service` has no default.** It is the
  only thing in that list the framework refuses to invent for you, and part 2.2 is why.
- `run_async` is `async` and takes `user_id` and `session_id` — and **not** `app_name`. The runner
  already holds the app name; the session was created under one; nothing reconciles them for you. That
  is why `agent.py` has `APP_NAME` as a module constant used in both calls, and why two string
  literals would have been a bug waiting for a typo.
- `new_message` defaults to `None`, which reads oddly until you notice what it means: you can drive a
  turn without adding a message, because the conversation the turn works from is the session's, not
  the argument's. The message is an *addition* to a thread that already exists.
- `create_session` is declared `abstractmethod async`. Two facts in two words. **Abstract**: this is
  the interface, and `InMemorySessionService` is one implementation of it, so the code in `agent.py`
  is written against a contract rather than against a store. **Async**: it is a coroutine, and calling
  it without `await` runs none of it.

### Where the conversation went

`ask_desk/agent.py` was printed whole in part 1.1 and is not reprinted here. Four of its lines carry
this part, and they are worth reading in this order:

- `session_service = InMemorySessionService()` — the store. This is the object that now holds what
  `loop.Conversation.contents` held on day 4: the list of turns, in order, with the model's replies
  filed alongside your questions. Day 4's deliberate failure was dropping the model's reply before it
  reached that list, and the resulting request went out with two `user` turns and no `model` turn in
  between. You cannot make that mistake here, because the append is no longer yours to forget.
- `await session_service.create_session(app_name=APP_NAME, user_id=user_id, session_id=session_id)` —
  the file is opened before the job starts. The `await` is doing real work: without it, the expression
  produces a coroutine object, the session is never created, and nothing raises at that line.
- `runner = build_runner(session_service)` — the runner is handed **that** service, not a fresh one.
  The session it will look up under `s-1` has to be in the store it was told about, and this is the
  line that connects the two halves.
- `message = types.Content(role="user", parts=[types.Part(text=question)])` — the same shape day 4
  built as a dictionary, now as typed objects from the provider SDK. `role="user"` is the same
  constraint day 4 met head-on and the same two values are legal.

And then the loop that is not a loop:

- `async for event in runner.run_async(...)` — `run_async` yields **events** as the turn happens, so
  this is a stream, not a call that returns once at the end. Everything day 4 wrote as an explicit
  think-act-observe cycle happens inside it: the request, the model's reply, a tool being asked for,
  the tool being run, the result going back. You are standing at the counter watching, and today you
  are watching for exactly one thing.
- `if event.is_final_response()` — from `https://adk.dev/tutorials/agent-team/`, checked 2026-09-09,
  verbatim:

  > Key Concept: `is_final_response()` marks the concluding message for the turn.

  Every other event is the middle of the work. Discarding them is a decision this file makes on
  purpose and comments on, and day 8 — *Events and streaming* — is where they stop being
  discarded. A day that reads only the last event and never says the others existed teaches a
  framework as a black box.
- `answer = "".join(...)` rather than `answer +=` — the final response is assembled from that one
  event's parts, and each new final response replaces rather than appends. If you had accumulated
  across events instead, a turn that produced text in the middle would arrive glued to the front of
  the answer.

Why any of it is asynchronous at all, from the same page, verbatim:

> Interactions with LLMs and potentially tools (like external APIs) are I/O-bound operations. Using
> asyncio allows the program to handle these operations efficiently without blocking execution.

**Line by line:**

- **I/O-bound** is the whole argument. A turn spends its life waiting on a network reply, not
  computing; the CPU is idle for effectively all of it. Asynchronous code lets the process do
  something else during those waits.
- For this project, with one agent and one question at a time, the practical benefit today is **zero**
  — and it is still the correct shape, because the alternative is a synchronous API that cannot be
  made concurrent later without changing every caller. The cost is paid once, at the edge, in
  `asyncio.run`.
- The rule that falls out of it, and the one people learn the hard way: **async is contagious
  upwards.** `create_session` being a coroutine is why `ask` is a coroutine, which is why `adk` needs
  `asyncio.run`. You do not get to await something in the middle of a synchronous function.

## When it breaks

Take the `await` off `create_session` — it reads perfectly well without one, and the line does not
look like it does anything — and the failure does not arrive at that line. Nothing is created, the
statement completes, and the runner then goes looking for a session that was never opened. The
transcript of that is a rep, not a recording: it has not been run on this machine, and the plan
forbids writing an error message from memory as firmly as it forbids inventing a version.

```text
TODO(me): in `ask_desk/agent.py`, delete the `await` before `session_service.create_session(...)`,
then run: uv run --frozen python run.py adk "Is the VPN down?"
Paste the real output here, including whatever Python says about the coroutine.
```

Two things to have in mind before you run it, because predicting first is what makes the rep worth
anything. The signature above says `create_session` is `async`, so the un-awaited call evaluates to a
coroutine object and the store stays empty. And the failure that follows arrives from `run_async`,
somewhere else entirely, about a session id — which is the general shape of this bug and the reason it
costs an evening: **the error is never raised where the mistake is.**

## In production

**What a senior writes instead.** They do not build a session service inside the function that answers
one question. `ask()` calls `InMemorySessionService()` on every invocation, so every question gets its
own empty store, and the session id `s-1` is reused across all of them — three questions produce three
different stores that each believe they are holding the first conversation. A service and a runner are
process-level objects, built once at startup and injected; the session id comes from the caller, keyed
to a real user and a real conversation. This file is written the way it is because today's subject is
the machinery and not the lifetime, and the lifetime is day 9's subject.

**What degrades at scale.** Two numbers, and the second is the one that bites. The store is in
process memory, so **10,000** conversations are 10,000 conversations in RAM, and a restart is
10,000 conversations gone — no error, no log line, just users whose desk has forgotten them. And the
bound from day 4 is not enforced on this path at all: `MAX_CALLS_PER_QUESTION = 6` guards
`loop.Conversation.ask` and nothing else, so where the hand-rolled desk stopped at six provider calls
for one question, the ADK desk stops when the model stops asking for tools. One question, an unbounded
number of requests, against a ceiling nobody has printed.

**The review comment.** "`ask()` constructs a new `InMemorySessionService` per call and then hardcodes
`session_id='s-1'`, so sessions never persist between questions and two concurrent callers would
collide on the same id if they ever shared a store. Hoist the service and the runner to module scope
or a factory, take the session id from the caller, and put the day-4 call bound back on this path
before it ships — the runner does not have one."

**The interview question.** "You port a synchronous agent loop to an async framework and one function
in the chain forgets an `await`. The program does not crash there. Describe what actually happens at
runtime, why the eventual error names a completely different line, and what you would add — in code
or in CI — so that a missing `await` cannot reach production."
