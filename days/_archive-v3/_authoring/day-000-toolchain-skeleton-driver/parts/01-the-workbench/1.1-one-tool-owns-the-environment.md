## One-line answer

One program installs the interpreter, resolves the dependencies and builds the environment, so
that "it works on my machine" stops being a claim about your machine and becomes a claim about a
file anyone can read.

## The idea

A shared workshop has a tool board on the wall. Every spanner hangs on a painted outline, and the
outline has the size written under it. Nobody keeps spanners in their pocket. The reason is not
tidiness — it is that a 13mm spanner that is actually a worn 12.7mm will round off a nut, and the
person who rounds it off will not be the person who owns the bad spanner. The board makes the tool
a fact about the shop instead of a fact about whoever happened to be holding it.

A machine that builds software has the same problem and hides it better. Ask a computer which
Python it has and it will answer confidently, and the answer will depend on which name you used to
ask. Here is this machine, today:

```console
$ python --version
Python 3.12.10

$ python3 --version
Python 3.11.9
```

Two names, two different interpreters, on one machine, right now. Neither is broken. One came from
an installer, one from somewhere else, and a document that says "run `python3`" and a document that
says "run `python`" are describing two different worlds. That is the trap the plan calls **the four
Pythons that ruin a Monday** — a system Python, a store Python, one a data-science installer left,
and one inside a virtual environment you forgot you had activated. You do not notice until a
package installs into one and your program runs in another.

Three words before going further, and each one gets a row in `docs/GLOSSARY.md` the first time it
is used.

An **interpreter** is the program that runs your code — the `python` executable itself, of a
specific version. An **environment** is an interpreter plus a particular set of installed packages;
two environments on one machine can hold the same package at different versions and never see each
other. A **pin** is a written-down exact version — `3.12`, not "whatever is newest" — recorded in a
file so that a machine, and not a memory, decides what gets used.

**uv** is the tool board. It is one binary that installs interpreters, creates environments,
resolves dependencies and writes the lockfile that records what it resolved. The alternative is
four tools that each solve a quarter of the problem and disagree at the seams, which is where a
Monday goes.

This day, and this repository, need less of it than any other day will: the authoring driver you
build later imports nothing but the standard library. That is deliberate. The tool board goes up
before the first job, not after the first rounded nut.

## The mechanism

Three commands, run on this machine today. Their output is pasted exactly as it came back.

```console
$ python --version
Python 3.12.10

$ uv --version
uv 0.12.3 (507230998 2026-08-07 x86_64-pc-windows-msvc)

$ git --version
git version 2.54.0.windows.1
```

**Line by line:**

- `python --version` — asks the interpreter that this shell resolves under the bare name `python`.
  It is deliberately the bare name and not `python3` or an absolute path, because the bare name is
  what every later command in this curriculum will use, so the bare name is the one that has to be
  right. On this machine it answers 3.12.10, and `python3` answers 3.11.9 — which is exactly why
  the check is worth running rather than assuming.
- `uv --version` — prints the version, the build hash and the target triple. The triple
  (`x86_64-pc-windows-msvc`) matters more than it looks: uv ships per-platform, and a lockfile
  resolved on one platform can resolve differently on another. Recording the triple in the pin
  ledger means a future disagreement has somewhere to start.
- `git --version` — the plan's second rule is *one day, one commit*, so git is not optional
  tooling here; it is where the memory of the curriculum lives. A repository that cannot record
  itself is a repository you cannot return to after three weeks away.

Now the pin. This repository fixes its interpreter in a file rather than in a habit:

```console
$ uv python pin 3.12
Pinned `.python-version` to `3.12`

$ cat .python-version
3.12
```

**Line by line:**

- `uv python pin 3.12` — writes the requested version into `.python-version` in the current
  directory. `3.12` and not `3.12.10`: the minor version is the compatibility promise, and pinning
  the patch would mean editing this file every time a security release lands, for no benefit the
  curriculum can name.
- `.python-version` — a one-line file, and the reason it is a file rather than a setting is that a
  setting lives on one machine and a file travels with the repository. Every uv command run from
  this directory reads it, so a second person cloning this folder gets the same interpreter without
  being told to.
- `cat .python-version` — the check, not the ceremony. The pin is only real if the file says what
  you think it says, and part 1.2 will show a case where it does not.

## When it breaks

Someone pins a version the machine does not have. Watch what uv actually does:

```console
$ uv python pin 3.13.99
warning: No interpreter found for Python 3.13.99 in managed installations, search path, or registry
Pinned `.python-version` to `3.13.99`
```

Read those two lines in order, because they disagree. The first says the interpreter does not
exist. The second says the pin was written anyway. `uv python pin` records an intention; it does
not verify one, and it exits successfully either way — so a script that only checks the exit code
learns nothing. The file now names an interpreter that is not there, and the failure surfaces
later, in whatever command first tries to use it, on whoever runs that command next.

That is the whole shape of the trap: the warning went past on a Friday, the pin got committed, and
the person who hits it on Monday sees a resolution error rather than the pin that caused it. The
smallest fix is to read the file after writing it — `cat .python-version` — and to treat the
warning as the error it actually is.

## In production

A senior engineer does not write `uv python pin` in a runbook step. They write the pin file into
the repository, and then they make the build fail without it: a first line in CI that reads
`.python-version` and compares it against the interpreter the runner actually resolved. The pin is
worthless as a suggestion and load-bearing as an assertion, and the difference is one comparison.

What degrades is the number of environments. One person on one machine can hold the four Pythons
in their head. This machine has **two interpreters answering to two names right now**, and that is
a quiet workstation with nothing exotic on it. A team of six, each with their own installers,
produces a matrix nobody has ever enumerated, and the first symptom is not an error — it is one
person's tests passing and another's failing on identical code.

The review comment you will get, and should give: *"This says `python3`. Which one is that on the
CI runner?"* It reads pedantic until the day the two disagree, and then it is the only question
that mattered.

The interview question underneath it: **"How does your project decide which Python it runs on, and
what happens if that decision is wrong?"** A weak answer names a tool. A strong answer names the
file, says who reads it, and says what fails — loudly, early — when the file and the machine
disagree.

## Check yourself

- **Run:** `python --version && python3 --version && uv --version && cat .python-version` — expect
  four lines, and expect to be able to say why the first two may differ on your machine.
- **Say out loud:** what is the difference between an interpreter, an environment and a pin, and
  which of the three does `.python-version` actually record?
