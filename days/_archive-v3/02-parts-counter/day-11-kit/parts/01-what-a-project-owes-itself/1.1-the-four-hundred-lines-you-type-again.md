## One-line answer

This project retypes utility files that P01 already has, because the plan's first rule is that every
line a project needs is printed inside that project's own documents — and the plan states the bill
for that rule in the open: roughly four hundred lines of near-identical scaffolding typed forty
times, forty extra sittings, and copies that will drift apart and never be reconciled.

## The idea

A fitter takes the lease on a unit at the end of a row. The unit is empty: a bench, a bare wall,
power. Across the road is a shop that has been open for twenty years, and its wall is covered in
tools — every spanner in every size, a torque wrench, three sets of feeler gauges, all of it hanging
on a board with the outline of each tool painted behind it, so that a gap on the wall is a tool
somebody has not put back. The owner over there is friendly, and would lend you anything you asked
for. You buy your own set anyway, and it costs you most of what you had.

You buy your own because a spanner you have to walk across the road to borrow is not a spanner you
have. It is a spanner you have *access to*, on the days that shop is open, while that owner still
likes you, as long as the tool is not already in somebody else's hand. At two in the morning, with a
gearbox in pieces on your bench, the difference between owning a 17mm and being able to borrow one is
the difference between a finished job and a car on blocks until Tuesday. And the painted board is the
second half of the same decision: a wall with outlines on it tells you what is missing without your
having to remember what you own.

That is the shape of this whole curriculum, and today is the sitting where you pay for it. This
project needs code that reads a key out of a file, and code that says which model may be called. Both
were written already — carefully, and well — one sitting ago, in a different folder. The obvious move
is to import them. The obvious move is the one that turns thirty-nine of these forty projects into a
note reading *the spanners are across the road*.

So the plan states the rule and it is short. This is the first of the three rules in the plan's §0,
and it is quoted here rather than paraphrased because a paraphrase of a rule is where the rule starts
to soften:

> **The Completeness Rule — code is never referenced, only printed.** Every line of code a project
> needs appears **in full, at its real path, inside that project's own day documents**. No import
> from another project. No "copy this from P03". No `...` and no "the rest is unchanged" unless the
> unchanged region was printed earlier **in this same project** and the day says which day printed
> it.

Now the honest part, because a rule with a hidden price is a rule that gets quietly dropped the first
time somebody notices the price. The plan does not hide it. An earlier version of this curriculum put
the shared code in a `_shared/adk_kit/` folder and had every project import it. That version was
cheaper to write and it made every project after the third one **unbuildable on its own**: a reader
who took one folder to a different machine got `ModuleNotFoundError`, and the day document that told
them to write `from adk_kit.cast import Orchestrator` had not printed code at all — it had printed a
pointer to a file the reader did not have, and they found that out only after they had believed it.

The current version deletes the shared folder outright, and here is what that costs, in the plan's
own words:

> Removing `_shared/` adds one day to every project from P04 — the kit day — and it means roughly
> **400 lines of near-identical scaffolding get typed forty times**. v2 was 256 sittings; v3 is
> **296**. That is the bill for four people being able to build four projects on four machines with
> nothing in common. I think it is worth paying, and you should know the number.

Forty sittings. Four hundred lines, forty times over. That is what independence costs, and what it
buys is one sentence long: four people take four folders to four different machines, and each of them
builds a complete, running system with nothing in common.

And there is a consequence the plan admits rather than argues away, which is the part most people
would leave out. **The copies will drift.** By the thirtieth project your `backoff.py` will be better
than the one in the sixth — you will have watched a real quota run out by then, and you will have
learned something the earlier file does not know. The sixth project will never get that improvement.
Nothing will tell it. Nothing will tell *you*, either, when you next open it. That is not a bug in
the arrangement; it is the arrangement, seen honestly. The plan's own suggestion is to turn the drift
into a record — each project's last day carrying a short note on what you would change if you wrote
it again — which costs nothing and makes forty divergent copies into a log of your own progress
rather than forty pieces of unfinished business.

One last thing before the code, because it is the working method for the rest of today and for every
kit day after it. The plan's second rule says a concept is taught deeply in **exactly one place**, and
everywhere else the same code is printed in full and explained at *recap depth*. So a walkthrough in
this curriculum comes in two shapes, and you will see both today:

| Depth | When it is used | What it looks like |
| --- | --- | --- |
| **Full** | the code is being taught here for the first time in the whole plan | prose bullets under the block: every non-obvious token, and why *that* line and not the obvious alternative |
| **Recap** | the code is borrowed — printed whole, taught deeply somewhere else | a table, one row per line that carries a decision, each row naming **the failure that line prevents**, then a pointer pair |

Part 1.2 is recap depth, twice over. Parts 2.1 and 2.2 are full depth, because the two files they
print are new here and no earlier day owns them. A pointer is never allowed to stand on its own,
either: every one of them is a **pair** — this project's own `PRIMER.md` section first, which is
self-contained and is what makes the project independent, and only then the deep document outside
this folder, which is optional reading for somebody who happens to have the whole plan.

## The mechanism

There is no new code in this part. What there is instead is the evidence for the claim, because
"near-identical" is the kind of word that should be checked rather than accepted.

P01 has a key reader at `ask_desk/util/keys.py`. This project has one at
`parts_counter/util/keys.py`. Count them, then ask what actually differs:

```console

$ wc -l projects/01-ask-desk/ask_desk/util/keys.py projects/02-parts-counter/parts_counter/util/keys.py

  70 projects/02-parts-counter/parts_counter/util/keys.py

$ diff -u projects/01-ask-desk/ask_desk/util/keys.py projects/02-parts-counter/parts_counter/util/keys.py | grep -c "^[+-][^+-]"
6
```

**Line by line:**

- Seventy lines each. Six lines differ, which is three removed and three added. The other sixty-seven
  lines are the same file typed twice, and this is one of the two smallest files in the kit.
- That is the four hundred lines, in miniature and made concrete. Multiply the shape by the number of
  files a kit holds, and then by forty projects, and you have the plan's figure — arrived at rather
  than quoted.
- `grep -c "^[+-][^+-]"` counts changed lines and skips the `---` and `+++` headers, which begin with
  the same characters and are not content. Counting them would have said eight, which is the kind of
  wrong number that survives review because nobody re-derives it.

**Line by line:**

- **Not one of the three changed lines carries logic.** A path in a header comment, a sentence in a
  docstring, and a path in another comment. Every branch, every message, every decision about what
  counts as a missing key is byte-for-byte the same file.
- That is exactly what makes the duplication tolerable *here* and intolerable somewhere else. This
  file is small, finished, and rarely changes. The moment a duplicated file starts changing every
  week, the trade has flipped and the honest move is to say so rather than to keep copying.
- Look at the second changed line, though, and read what it says: it points the reader at
  `PRIMER.md` §1. In P01's primer, the key sections **were** §1. In this project's primer, §1 is *A

  cross-reference rather than a stale algorithm, which is the mild version, and which is precisely
  how the severe version starts. Part 1.2 prints the file exactly as it sits on disk, with the wrong
  number in it, because a document that quietly corrects the code it is printing is a document you
  cannot check anything against.
- The build brief in the hub §5 carries the rep for it. Do not skip that one: the interesting question
  is not what the number should be, it is *what mechanism in this repository was supposed to catch
  this and did not*.

## When it breaks

The failure the Completeness Rule exists to prevent has exactly one error message, and it costs one
command to see. Type the import a copied snippet would have carried — P01's package name — from
inside this project:

```console
$ cd projects/02-parts-counter
$ uv run --frozen python -c "from ask_desk.util import keys"
Traceback (most recent call last):
  File "<string>", line 1, in <module>
ModuleNotFoundError: No module named 'ask_desk'
```

Somebody shipped a kit day with that line in it, and the reader who had only this one folder got this
at the first command they typed — not a wrong answer, not a bad key, just a package that is not there
and never was. The smallest fix is the one this project already makes: the reader lives at
`parts_counter/util/keys.py`, inside this project's own package, and is imported as
`from parts_counter.util import keys`. The general fix is the rule itself.

## In production

**What a senior writes instead.** For a real fleet they do the opposite of this, and they are right
to: one internal library, versioned, released, imported by everything, because the cost being
optimised there is *maintenance across thirty services* and not *portability of one folder*. What
they do not do is either extreme. They do not vendor a copy of a package that ships security fixes,
and they do not put a `utils` package on the shared path and let forty repositories import whatever
happens to be on `main` that afternoon. The question is always the same one this part is about: what
is this folder allowed to assume exists outside it, and what happens to somebody who assumed wrong.

**What degrades at scale.** The number is **thirty-nine**. A bug found in this file is fixed in one
project and left standing in thirty-nine others, and nothing in any of those thirty-nine will ever
mention that a fix exists. Multiply the plan's four hundred lines by forty and the curriculum carries
roughly **sixteen thousand lines** of code that is duplicated on purpose. That figure is the whole
argument for keeping the kit small: every line you add to `util/` you have agreed to type forty times
and to fix forty times.

**The review comment.** "This project imports `keys` from the sibling project's package. It works in
CI because CI checks out the whole monorepo, and it will fail for anybody who clones this directory
alone — which is the one promise on the front page of the README. Vendor the file, and add a check
that every import in this project resolves inside this project, so the next person cannot do it by
accident."

**The interview question.** "You have a shared internal library used by thirty services. A security
fix lands in it. Walk me through everything that has to happen before all thirty are actually running
the fixed version. Then tell me what would have had to happen instead if each service had vendored
its own copy — and say which of the two you would rather be responsible for, and why the answer
changes depending on how often the library changes."
