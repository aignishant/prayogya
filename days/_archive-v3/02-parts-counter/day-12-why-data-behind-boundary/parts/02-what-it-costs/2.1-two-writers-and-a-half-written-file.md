## One-line answer

Two writers against a read-modify-write store produce three separate failures at once — parts that
vanish because one side's change is overwritten, readers that crash on a file caught mid-write, and a
different wrong number on every single run — and the third is what keeps the first two alive for
months.

## The idea

Friday afternoon, and two people need spark plugs off the same shelf. One of them is fitting a
service; the other is making up a kit for Monday. They arrive within a few seconds of each other.
Both read the card: two hundred and forty. Both take ten. Both cross out the number and write down
what they worked out — two hundred and thirty — and both are telling the truth about what they did,
because each of them started from two hundred and forty and each of them took ten.

The card says two hundred and thirty. The shelf holds two hundred and twenty. Ten spark plugs are
gone from the room and present in the book, and nobody did anything wrong. There was no theft, no
carelessness and no misread number. The second person's write simply landed on top of the first
person's, and the card has no way of holding two truths at once.

Now make it worse in the way real rooms get worse. A third person walks past while somebody is
halfway through crossing out the old number and writing the new one, glances at the card, and sees
a scribble that is neither. In the room, that person shrugs and waits. In the program, that person
is a reader that gets a file with nothing in it yet and **crashes.**

And here is the thing that makes this bug survive: **the number is different every time.** Ten
missing on one afternoon, eight on the next, nine on the one after that. Nobody can reproduce it, so
nobody can file a useful report about it, so it becomes "the count drifts a bit" and lives in the
building for years. A bug that fails the same way every time gets fixed the week it is found. A bug
that fails differently every time gets a name and a shrug.

Two terms, and both are worth having by name.

A **lost update** is what happened to the first person's change: two callers read the same starting
value, both compute a new value from it, both write, and the second write erases the first. Nothing
errors. Nothing logs. The only evidence is that the total is wrong, and you can only see that if you
already know what it should have been.

A **torn read** is what happened to the third person: a read that lands while a write is in
progress and gets a file that is neither the old contents nor the new. `PARTS_FILE.write_text(...)`
opens the file for writing, which truncates it to nothing, and then writes the bytes. Between those
two moments the file on disk is **empty**, and a reader that arrives in that window gets an empty
string and hands it to `json.loads`.

This is the day's deliberate failure, and it is deliberate in a stronger sense than usual: the
demonstration ships in the project. `run.py race` exists so that you can watch parts disappear on
your own machine, as many times as you like, and get a different answer every time.

## The mechanism

This project's driver was printed whole by **day 11**. Only the subcommand this part is about is
reproduced here, as a marked diff against that file:

```diff
# projects/02-parts-counter/run.py — the `race` subcommand, unchanged since day 11
 # ── unchanged from day 11: the check functions, CHECKS, check() and parts() ──

 def race(part_no: str = "SPK-0055", each: int = 10) -> int:
     """Two threads issuing stock at once, against a store with no boundary in front of it.

     This is day 2's demonstration and it is deliberately runnable. The numbers differ every time,
     which is the point: a bug that produces a different wrong answer on each run is one nobody can
     reproduce from a bug report.
     """
     from parts_counter import store

     start = store.get(part_no)["on_hand"]
     errors: list[str] = []

     def issue() -> None:
         for _ in range(each):
             try:
                 store.adjust(part_no, -1)
             except Exception as exc:  # noqa: BLE001 - the point is that anything can happen
                 errors.append(type(exc).__name__)
             time.sleep(0.001)

     left, right = threading.Thread(target=issue), threading.Thread(target=issue)
     left.start(); right.start(); left.join(); right.join()

     end = store.get(part_no)["on_hand"]
     print(f"start on hand      : {start}")
     print(f"issued by two staff: {each * 2}")
     print(f"expected on hand   : {start - each * 2}")
     print(f"actual on hand     : {end}")
     print(f"parts unaccounted  : {end - (start - each * 2)}")
     print(f"reads that crashed : {errors}")
     store.adjust(part_no, start - end)
     print(f"restored to        : {store.get(part_no)['on_hand']}")
     return 0

 # ── unchanged from day 11: main() and the __main__ block ──
```

**Line by line:**

- `part_no: str = "SPK-0055"` and `each: int = 10` are defaults rather than required arguments, so
  the demonstration is one word to run. `SPK-0055` is the part with two hundred and forty on hand —
  chosen because twenty issued out of two hundred and forty never reaches zero, so the run cannot
  accidentally demonstrate something else.
- `from parts_counter import store` is **inside** the function, matching the `parts` subcommand from
  part 1.2 and for the same reason: `python run.py check` must not import the thing it is not
  checking.
- `start = store.get(part_no)["on_hand"]` records the truth before anything runs. Without a recorded
  starting point there is no way to say what the answer should have been, and "the number looks
  wrong" is not a finding.
- `errors: list[str]` collects **type names**, not exception objects and not tracebacks. A list of
  names is what makes the summary line readable at a glance; the full traceback for the interesting
  one is below, caused separately.
- `issue()` calls `store.adjust(part_no, -1)` ten times. One at a time, a single part per call —
  because a person taking one spark plug is the smallest honest unit of work, and because ten small
  writes give the race far more chances to happen than one large one would.
- `except Exception as exc:  # noqa: BLE001` — a blanket catch, which is normally a mistake, and the
  comment says why it is not one here: **the point is that anything can happen.** Narrowing this to
  `JSONDecodeError` would be asserting in advance which failures the race can produce, which is
  precisely the thing being investigated. The `noqa` is there because the linter is right in general
  and wrong in this one function, and silencing it with a code and a reason is how you say that.
- `time.sleep(0.001)` between adjustments is not padding. Without it, one thread's ten adjustments
  can finish before the other thread is scheduled at all, and the run comes out correct — which
  would be the worst possible outcome for a demonstration, because it would teach that the code is
  fine. The pause hands control back so that the two threads actually interleave.
- Two threads and not two processes, and that choice is worth stating plainly: **threads make the
  demonstration easy to run and make the failure look easier to fix than it is.** Everything you are
  about to watch happens inside one Python process, so a `threading.Lock` around `adjust` would stop
  all of it. Part 2.2 is about the version where that is not available.
- `left.start(); right.start(); left.join(); right.join()` — both started before either is joined.
  Starting and joining one at a time would run them in sequence and produce a perfectly correct
  count, which is the standard way this demonstration is written wrongly.
- The output prints `expected` and `actual` as separate lines and then their difference. Three lines
  where one would do, because the reader needs to see the arithmetic rather than be told its result.
- `store.adjust(part_no, start - end)` **restores the fixture** before the command exits, so the
  demonstration can be run repeatedly and leaves the repository as it found it. It is a single-writer
  correction applied after both threads have finished, which is the only moment in this whole
  function when a read-modify-write is actually safe.

### What actually happens

```console
$ uv run --frozen python run.py race
start on hand      : 240
issued by two staff: 20
expected on hand   : 220
actual on hand     : 230
parts unaccounted  : 10
reads that crashed : ['JSONDecodeError', 'JSONDecodeError']
restored to        : 240
```

**Line by line:**

- Twenty spark plugs were issued and the count moved by ten. **Ten parts left the room without
  leaving the book.** No exception was raised for those ten, nothing was logged, and no check
  anywhere in this project goes red because of them.
- That is ten lost updates: ten times, both threads read `n`, both wrote `n - 1`, and the shelf lost
  two while the card lost one.
- `reads that crashed : ['JSONDecodeError', 'JSONDecodeError']` — two of the twenty calls did not
  merely produce a wrong answer, they **failed outright**, on the read at the top of `adjust`. Those
  two adjustments never happened at all, which is a third distinct outcome sitting inside the same
  twenty calls: some succeeded, some were overwritten, some never ran.
- `restored to : 240` — the fixture is back. Verified afterwards: `parts.json` is byte-identical to
  the committed version, all six parts present.

**Line by line:**

- Ten lost, then eight, then nine, then nine. Two crashed reads, then two, then one, then three.
  **Nothing was changed between those runs.** Same code, same file, same machine, same command.
- Run it yourself and you will get a fifth number. That is not a hedge in the writing; it is the
  property being demonstrated, and any document that quotes one number as *the* answer here is
  describing a run rather than the bug.
- This is what makes the failure survive contact with a bug tracker. "Sometimes the count is off by
  a bit" cannot be reproduced on demand, cannot be attached to a test, and cannot be argued for
  against a feature. It gets closed as *cannot reproduce* and comes back next quarter under a
  different title.

### The two failures are not the same failure

One more experiment, because it is tempting to think of "lost parts" and "crashed reads" as one
problem with two symptoms. Widen the gap between the read and the write — a `time.sleep(0.002)`
inserted into `store.adjust` immediately after `payload = _read()`, and taken out again afterwards —
and run twice:

```console
$ uv run --frozen python run.py race
start on hand      : 240
issued by two staff: 20
expected on hand   : 220
actual on hand     : 229
parts unaccounted  : 9
reads that crashed : []
restored to        : 240
$ uv run --frozen python run.py race
start on hand      : 240
issued by two staff: 20
expected on hand   : 220
actual on hand     : 229
parts unaccounted  : 9
reads that crashed : []
restored to        : 240
```

**Line by line:**

- Nine lost, both times, and **no crashed reads at all** in either run. One line of sleep in one
  function changed which failure showed up.
- Nothing was fixed. Nine parts still went missing on both runs; the torn reads simply stopped
  landing in the window that produces them, because moving the sleep moved when the writes happen
  relative to the reads.
- This is exactly how a timing bug gets "fixed" in the wild: somebody makes an unrelated change, one
  of the two symptoms disappears, the ticket is closed, and the other symptom is now the only one
  anybody is looking for. What the experiment proves is that the lost update and the torn read are
  **two separate races with two separate windows**, and that a change which quiets one of them tells
  you nothing about the other.
- Say what this does not prove, too: two runs is two runs. It is enough to show that the two
  failures move independently, and it is not enough to claim anything about how often either
  happens.

### What a lock does and does not buy

The obvious fix is a `threading.Lock` around the body of `adjust`. It would work — completely — for
everything on this page, because everything on this page happens in one Python process. That is worth
sitting with rather than skipping past, because it is the shape of the whole argument:

- **One process, many threads.** A lock in the process solves it. This demonstration goes green.
- **Two processes.** A lock in one process is invisible to the other, and both of them still hold the
  file open. The count starts drifting again and the demonstration you just ran will not show it,
  because the demonstration is threads.
- **Two containers, or one container restarted while the other is running.** There is no shared
  memory at all to put a lock in.

An operating-system file lock covers more of that than a `threading.Lock` does, and it brings its own
list: it behaves differently on Windows and POSIX, it is advisory on some filesystems, it does not
survive the process being killed in an obvious way, and it turns every reader into somebody who must
also participate in the locking scheme or see nothing. None of that is an argument against locks. It
is an argument that **the question "who is allowed to write this?" has to be answered by something
that outlives any one process** — and that is the thread part 2.2 pulls.

## When it breaks

This is the crash, in full, from a read that landed while the other thread's `write_text` had
truncated the file and not yet written the bytes:

```traceback
  File ".../parts_counter/store.py", line 67, in adjust
    payload = _read()
              ^^^^^^^
  File ".../parts_counter/store.py", line 33, in _read
    return json.loads(PARTS_FILE.read_text(encoding="utf-8"))
           ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
json.decoder.JSONDecodeError: Expecting value: line 1 column 1 (char 0)
```

Read the message closely, because it is the most misleading part of it: *Expecting value: line 1
column 1 (char 0)* means the file was **empty**. Not corrupt, not truncated halfway through a
string — empty, because `write_text` had opened it for writing and truncation is the first thing
that happens. Somebody gets this at eleven at night, opens `parts.json`, finds a perfectly valid
document with all six parts in it, and concludes the error is impossible. It is not impossible; it
is a photograph of a moment that lasted a fraction of a millisecond and is gone by the time anybody
looks. The smallest fix for this one failure alone is to write to a temporary file in the same
directory and `os.replace` it onto the target, which is atomic — a reader then sees either the whole
old file or the whole new one and never the gap. That fixes the torn read. It does not return a
single lost part.

## In production

**What a senior writes instead.** Nobody ships a counter that edits a JSON file from two writers. The
smallest real answer is SQLite with a transaction, because the read and the write become one
indivisible act and the database refuses the second writer rather than losing its change; the next
answer up is a database with a row-level `UPDATE parts SET on_hand = on_hand - 1 WHERE part_no = ?`,
which never reads the value into your program at all and so has no window to lose. The move that
generalises past both — and the one this project makes — is to stop asking every caller to be careful
and instead put **one owner** in front of the data, so that the question of who may write is answered
once, in one place, by something that outlives any single process.

**What degrades at scale.** Two writers issuing ten each lost between eight and ten parts out of
twenty — call it half. That ratio is not a constant and it does not need to be: it says the failure
rate is on the order of *the fraction of the time two writers overlap*, which rises with the number
of writers and with how long each holds its window open. On six parts and two threads it is a
demonstration. On ten thousand parts, four workers and a file that takes longer to read and write,
the window is wider on every single call, and the count is wrong by an amount nobody can predict
before somebody does a physical stock take and finds out.

**The review comment.** "This adjusts a shared file with a read-modify-write and there is nothing
holding it still between the two. I ran `run.py race` four times and got 10, 8, 9 and 9 parts lost,
plus one to three crashed reads per run. Please do not fix this with a `threading.Lock` and call it
done — that covers this process only, and the deployment plan has two replicas. The write needs one
owner, and every reader needs to go through it."

**The interview question.** "A service keeps a counter in a JSON file, reads it, decrements it and
writes it back. Users report that the total drifts downward and occasionally a request fails with a
JSON parse error on a file that is valid when anyone looks at it. Walk me through both failures,
tell me which one an atomic file replace fixes and which it does not, and then tell me what you would
do differently if the service runs as two replicas behind a load balancer."
