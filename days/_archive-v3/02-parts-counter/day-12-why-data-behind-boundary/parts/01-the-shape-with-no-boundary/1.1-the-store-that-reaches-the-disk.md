## One-line answer

The inventory is one JSON file that any code in this process can open, and every change to it is the
same three-step sequence — read the whole file, change one number, write the whole file — which is
exactly right for one writer and has no answer at all for two.

## The idea

There is a stockroom at the back of the workshop and the door has been propped open since before
anybody now working there was hired. It is not carelessness. It is a small shop, everybody knows
everybody, and walking to the shelf yourself is faster than finding someone to fetch for you. On the
edge of each shelf is a card with a number written on it: how many are there. You take two brake pad
sets, you cross out the number, you write the new one. That is the whole system, and for years it has
been correct every single day.

Then one Friday the count is wrong. Not by much — nine spark plugs. Nobody stole them and nobody
lied. Two people were at the same shelf within the same few seconds, each read the card, each took
what they needed, and each wrote down what they believed the new total to be. Both numbers were
honest. Only one of them ended up on the card. The shop's problem is not its people; it is that the
card is written by whoever gets to it, and nothing in the room can tell that two hands reached for it
at once.

This part is about the code that is shaped exactly like that room, and the first thing to say about
it is that **it is not bad code.** Every function in `parts_counter/store.py` is short. Every one is
typed. Every one has a docstring saying what it does and what it raises. It would pass review at any
shop you would want to work at, and if you sent it to a reviewer with the instruction "find the bug",
they would come back and say there isn't one. They would be right. The problems the rest of today
finds are not defects in the lines. They are **consequences of the shape** — of an agent's tools
reaching a file on disk directly — and that is precisely why the shape is worth a whole day. A bug
you can point at gets fixed by the person who finds it. A shape gets fixed by an argument.

Two words before the code, both of which get used for the rest of the project.

The **store** is the layer that knows where the data physically is and how to turn it into Python
objects. It is the only part of this project that has heard of a file. Everything above it — the
tools, and later the agent — asks the store for parts and never for bytes. That separation is good
design and it is already here; it is what will make day 14's move survivable, because the shape of
the calls does not have to change when what is underneath them does.

**Read-modify-write** is the name for the sequence `adjust` performs: load the whole document into
memory, change one value in the loaded copy, and write the whole document back out. It is the natural
way to edit a JSON file and it is what almost every small program does. It carries one assumption,
never written down anywhere, and today is about paying for that assumption: **between the read and
the write, nothing else may touch the file.** One process, one thread, one writer. The moment that
stops being true, the read is describing a world that no longer exists by the time the write lands —
and the write does not know, because a write to a file does not ask what the file said a moment ago.

Hold the stockroom in your head as you read: the card on the shelf edge is `parts.json`, reading the
card is `_read`, and crossing out the number and writing a new one is `_write`. Nothing in the room
records who took what, and nobody outside the room can see that the number moved at all.

## The mechanism

The data first, because everything else in this project is a way of reaching it.

**Line by line:**

- The whole document is **one object with one key**, `parts`, holding a list. Not a bare top-level
  list. A JSON file whose root is a list has nowhere to grow: the day you need a schema version, a
  last-updated stamp or a second collection, you are changing the root type and every reader at once.
  An object at the root costs one line now and buys a place to put things later.
- `_comment` is a real key with a leading underscore, not a comment, because **JSON has no comments**
  and the alternative is a note in a README that nobody reads next to the file they are looking at.
  The underscore is the widely used convention for "this key is for humans". `store.py` never reads
  it, and it survives a read-modify-write cycle untouched precisely because `_write` writes the whole
  loaded document back rather than reconstructing it from the parts list.
- `part_no` is the identity and it is a **string**, not a number. `BRK-0142` has a prefix and leading
  zeros; the moment an identifier becomes an integer, `0142` becomes `142` and two parts collide. A
  general rule worth carrying: if you would never do arithmetic on it, it is not a number.
- `on_hand` and `reorder_at` **are** numbers, because both are counted and compared. `unit` is the
  word you would say out loud beside the count — `set`, `each`, `kit` — and it exists so that an
  answer can be "four sets" rather than the bare "4" that a person then has to interpret.
- `bin` is the physical location, and it is in this file rather than in a second one because the
  whole point of a part record is that one lookup tells somebody everything they need in order to
  walk to the shelf.
- `BLT-0310` sits at `on_hand: 0` and `BRK-0143` at `4` against a `reorder_at` of `6`. Both are
  deliberate: the fixture contains a part that is out of stock and a part that is below its reorder
  point, so that "below reorder" and "none left" are two different, testable states from the first
  day rather than states somebody has to construct by hand later.
- Six parts, and the smallness matters. Everything today does — every read, every write, every one of
  the twenty concurrent adjustments in part 2.1 — moves this entire file. A fixture this size makes
  the shape visible; it is not what makes the shape work.

Now the code that reaches it.

`projects/02-parts-counter/parts_counter/store.py`, whole file:

```python
# parts_counter/store.py
"""The parts inventory, read and written straight off the filesystem.

**This file is the version of the data layer that has no boundary, and it is written this way on
purpose.** Day 2 of this project is the argument for putting a boundary in front of it; you cannot
follow that argument without first having the thing the argument is about.

Everything here works. That is what makes it worth studying: the problems are not bugs, they are
consequences of an agent's tools reaching a filesystem directly, and every one of them survives
code review because each individual line is fine.

Day 3 onward moves this behind `parts_mcp/`, and this module keeps its shape while losing its
direct reach.

All data is synthetic.
"""

from __future__ import annotations

import json
from pathlib import Path
from typing import Any

DATA_DIR = Path(__file__).with_name("data")
PARTS_FILE = DATA_DIR / "parts.json"


class PartNotFound(KeyError):
    """No part with that number. Never guess at a near match on an inventory."""


def _read() -> dict[str, Any]:
    return json.loads(PARTS_FILE.read_text(encoding="utf-8"))


def _write(payload: dict[str, Any]) -> None:
    PARTS_FILE.write_text(json.dumps(payload, indent=2) + "\n", encoding="utf-8")


def all_parts() -> list[dict[str, Any]]:
    """Every part in the inventory."""
    return _read()["parts"]


def find(query: str) -> list[dict[str, Any]]:
    """Parts whose number or name contains `query`, case-insensitively."""
    needle = query.strip().lower()
    return [p for p in all_parts()
            if needle in p["part_no"].lower() or needle in p["name"].lower()]


def get(part_no: str) -> dict[str, Any]:
    """One part by its exact number, or `PartNotFound`."""
    for part in all_parts():
        if part["part_no"].lower() == part_no.strip().lower():
            return part
    raise PartNotFound(part_no)


def adjust(part_no: str, delta: int) -> dict[str, Any]:
    """Add `delta` to a part's on-hand count and write the file back.

    This is the write, and it is the reason day 2 exists. Read the sequence: read the whole file,
    change one number, write the whole file. Nothing here records who asked, nothing prevents two
    callers doing it at once, and nothing outside this process can see that it happened.
    """
    payload = _read()
    for part in payload["parts"]:
        if part["part_no"].lower() == part_no.strip().lower():
            part["on_hand"] = part["on_hand"] + delta
            _write(payload)
            return part
    raise PartNotFound(part_no)
```

**Line by line:**

- The module docstring says the file is written this way **on purpose**. That sentence is doing real
  work: without it, the next person to open this file assumes it is unfinished and improves it,
  which is how a deliberate teaching artefact quietly becomes an accident. A file whose shape is a
  decision should say so at the top, where the decision is.
- `from __future__ import annotations` makes every annotation in the module a string that is never
  evaluated at import. Two consequences here: `dict[str, Any]` costs nothing at runtime, and a
  future annotation that refers to a class defined further down the file cannot raise `NameError`.
- `DATA_DIR = Path(__file__).with_name("data")` — the path is resolved against **this source file**,
  not against the working directory. `__file__` is the absolute path of `store.py`; `with_name`
  swaps the last component, so the result is the `data/` folder that sits beside the module. This is
  the one line here that would be a bug if written the obvious way, and "When it breaks" is entirely
  about it.
- `PARTS_FILE` is a module-level constant rather than something computed inside `_read`. That is
  what lets a test — or the instrumentation two blocks below — say `if path == store.PARTS_FILE`
  and mean it, and it gives the whole module exactly one answer to "which file are we talking
  about?"
- `class PartNotFound(KeyError)` — a **named** exception, subclassing the one a caller would
  naturally expect from a lookup. The name is what lets `tools.py` catch this and only this; a bare
  `KeyError` would also catch a genuine typo in `part["on_hand"]` inside the store and report a
  programming mistake to the user as "no such part". The docstring carries the policy — never guess
  at a near match on an inventory — because that is a rule about the domain, not about Python, and
  the domain rule is the one people are tempted to break.
- `_read` and `_write` are underscore-prefixed: they are the two places, and the only two places,
  where this module touches a filesystem. Everything public goes through them. That is what makes
  day 14's move a change to two functions rather than a change to six.
- `_read` returns the whole document, not the parts list, so that `_write` has something complete to
  write back. If `_read` returned `payload["parts"]`, `adjust` would have to rebuild the surrounding
  object to save it, and `_comment` — anything the code does not know about — would be silently
  dropped on every write.
- `encoding="utf-8"` is passed **explicitly on both**, and it has to be. Python's default text
  encoding is the platform's, which on Windows is still not UTF-8; a part name with an accent in it
  written on one machine and read on another is `UnicodeDecodeError` at three in the morning. Naming
  the encoding is one keyword argument and it removes the entire class of problem.
- `json.dumps(payload, indent=2) + "\n"` — indented, and with a trailing newline. Both are for the
  humans and the tools downstream: an indented file produces a readable `git diff` instead of one
  enormous changed line, and a file that ends in a newline is a file that `diff`, `cat` and every
  POSIX tool consider well-formed. Neither affects the data.
- `all_parts()` calls `_read()` **every time**. There is no cache, and that is the right call for
  this file: a cache is a second copy of the truth, and the day you add one you have to decide when
  it is stale — which is a harder question than the one the cache was answering. The cost is
  measured in the transcript below.
- `find` lowercases and strips the query once, into `needle`, before the loop rather than inside it.
  `query.strip().lower()` inside the comprehension would run once per part, and more importantly the
  intent — *this is a normalised needle* — would be buried in a condition.
- `find` returns `[]` for no matches rather than raising. An empty result is a **valid answer** to a
  search, and the tool that wraps it says so to the model in as many words (part 1.2). `get`, by
  contrast, raises, because "the exact part number you named" has no honest empty answer.
- `get` compares `part["part_no"].lower() == part_no.strip().lower()`. The stripping is on the
  caller's argument only: the file's own values are trusted because this project wrote them, and the
  caller's are not because a model produced them. That asymmetry is deliberate and it is the right
  default at any boundary — normalise what comes in, trust what you control.
- **`adjust` is the whole of today in six lines.** Read the sequence in order: `payload = _read()`
  loads the entire document; the loop finds one dictionary inside the loaded copy;
  `part["on_hand"] = part["on_hand"] + delta` changes it **in memory**; `_write(payload)` writes the
  entire document back. Three things are assumed by that sequence and none of them is written down.
  **One writer** — nobody else may change the file between the read and the write, because this
  write carries the whole document and will flatten anything it does not know about. **One process**
  — the assumption is not enforceable from inside this one, since another process would have its own
  copy of `payload` and its own idea of the truth. **Nobody who needs to know** — the function
  returns the changed part to its caller and tells nothing else, so a change to the inventory is
  visible only to whoever happened to make the call.
- `_write(payload)` is **inside** the loop, immediately after the mutation, and `return` follows it.
  Writing after the loop instead would be a behaviour change: an unknown part number would then
  write the file back unchanged rather than raising, and a no-op write is a real event to anything
  watching the file's timestamp.
- `raise PartNotFound(part_no)` at the very end, after the loop has finished without returning. The
  ordering is deliberate: the function never writes and then discovers the part was wrong, so a
  failed adjustment leaves the file exactly as it found it. That is the one concurrency-adjacent
  property this file does have, and it is worth noticing that it comes from the control flow rather
  than from anything protecting the file.

What the store does when you ask it questions — every command in this document runs the store and
the tools **directly, with no model anywhere in it**:

```console
$ uv run --frozen python -c "
from parts_counter import store
print(store.PARTS_FILE.name)
print(store.get('SPK-0055'))
print([p['part_no'] for p in store.all_parts()])
"
parts.json
{'part_no': 'SPK-0055', 'name': 'Spark plug, iridium', 'bin': 'B-11-5', 'on_hand': 240, 'reorder_at': 48, 'unit': 'each'}
['BRK-0142', 'BRK-0143', 'FLT-0071', 'FLT-0072', 'BLT-0310', 'SPK-0055']
```

Now count what a change actually costs. `Path.read_text` and `Path.write_text` are wrapped so that
every touch of `parts.json` is recorded, and then the belt kit is adjusted up by one and back down
by one — a pair of changes that leaves the file exactly as it started:

```console
$ uv run --frozen python -c "
from pathlib import Path
from parts_counter import store
ops = []
rt, wt = Path.read_text, Path.write_text
Path.read_text = lambda self, *a, **k: (ops.append('read') if self == store.PARTS_FILE else None, rt(self, *a, **k))[1]
Path.write_text = lambda self, d, *a, **k: (ops.append('write') if self == store.PARTS_FILE else None, wt(self, d, *a, **k))[1]
store.adjust('BLT-0310', 1)
store.adjust('BLT-0310', -1)
print('whole-file operations for two adjustments:', ops)
print('bytes rewritten each time:', store.PARTS_FILE.stat().st_size)
"
whole-file operations for two adjustments: ['read', 'write', 'read', 'write']
bytes rewritten each time: 1161
```

**Line by line:**

- `read`, `write`, `read`, `write` — the sequence is visible, and the gap between the first `read`
  and the first `write` is the window this day is about. Nothing occupies that gap here because
  nothing else is running. Part 2.1 puts something in it.
- **1161 bytes rewritten to change one integer.** Every adjustment rewrites the entire inventory,
  including the five parts nobody asked about. With six parts that is nothing; the number is here so
  that it can be multiplied later.
- The instrumentation replaces `Path.read_text` on the class, which reaches `store._read` without
  `store` knowing. That is only reasonable because it is throwaway measurement in a one-line
  command — it is a fine way to answer a question and a terrible thing to leave in a codebase, since
  the next person to read `store.py` has no way of learning that `read_text` is not `read_text` any
  more.
- The pair of adjustments is `+1` then `-1` on purpose, so the fixture ends where it began. Every
  transcript in this day leaves `parts.json` byte-identical to how it found it, and that was checked
  rather than assumed.

## When it breaks

`DATA_DIR = Path(__file__).with_name("data")` is one of two lines that could have been written, and
the other one — the shorter, more obvious one — works perfectly on the machine of whoever wrote it.
Here is what a relative path does when the program is started from one folder up, which is what
happens the first time this runs from a repository root, a scheduler or a container with a different
working directory:

```traceback
  File "C:\...\Python312\Lib\pathlib.py", line 1013, in open
    return io.open(self, mode, buffering, encoding, errors, newline)
           ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
FileNotFoundError: [Errno 2] No such file or directory: 'parts_counter\\data\\parts.json'
```

*Observed on this machine on 2026-09-10. Wherever a traceback appears in this day the absolute path
prefix is elided — as `C:\...` here, as `...` in part 2.1 — and that elision is the only edit made
to any transcript in these documents.*

Somebody adds a nightly stock report on a Friday, wires it to a scheduler that starts programs from
the user's home directory, and gets that at eleven at night from a store that has worked all week.
The error is honest and completely unhelpful: the file is right there, and the message names the
path the program invented rather than the one it wanted. The smallest fix is the line that is in the
file — resolve the path against `__file__`, which is the module's own location and does not care
where anybody was standing when they typed the command.

## In production

**What a senior writes instead.** Not this. For anything with more than one writer they reach for
SQLite before they reach for JSON — it ships with Python, it needs no server, and it gives you the
one thing a JSON file cannot: a transaction, so that a read and a write either both happen or
neither does. If the file format is fixed for some other reason, the write becomes **write to a
temporary file in the same directory, then `os.replace` onto the target**, which is atomic on POSIX
and on Windows, so a reader never sees a half-written file. Both of those are real fixes and this
project takes neither, because both fix one process and today's argument is about the second one.

**What degrades at scale.** 1161 bytes rewritten to change one integer — and the whole document
re-parsed on every question, because `all_parts()` calls `_read()` and there is no cache anywhere in
the module. Multiply by a real workshop: at ten thousand parts the file is on the order of two
megabytes, every stock check parses two megabytes to answer a question about forty bytes, and every
adjustment rewrites two megabytes to change one of them. Nothing breaks. It just gets slower in a way that no single change
caused, which is the hardest kind of slowness to argue for fixing.

**The review comment.** "The store is clean and I have no complaints about any function in it. My
comment is about the shape: `adjust` is a read-modify-write against a file with no lock and no
atomic replace, and there is nothing in the module that stops a second caller from landing in the
gap. That is fine while there is exactly one of us. Please write down, in the module docstring, that
one writer is a requirement and not an accident — because the next person to add a worker thread
will not be able to see that assumption anywhere in the code."

**The interview question.** "You are handed a service that keeps its state in a JSON file and edits
it by loading it, changing a field and writing it back. Describe every way that goes wrong once a
second writer exists, say which of them a lock in the process would fix and which it would not, and
tell me what you would look for in the data to find out whether it has been happening already."
