## One-line answer

A transport decides only how the bytes are framed and delivered, never what they mean — which is
why the server day 13 printed has **not one line** that differs between stdio and Streamable HTTP,
and the entire change is the string you hand to `mcp.run(...)`.

## The idea

A restaurant on two floors has a dumbwaiter: a shaft with a small car in it, a rope, and a hatch at
each end. The kitchen loads a tray, pulls the rope, and the tray arrives upstairs. Later the same
kitchen starts sending food to the unit next door, and there is no shaft — there is a roller door
onto the yard and a numbered bay, and each order goes out through it as its own consignment.

Nothing about the cooking changed. The same dish, plated the same way, garnished the same way, with
the same note tucked under the rim saying which table it belongs to. What changed is the *carrying*:
who can be at the other end, how you know a tray has arrived, what happens to a tray that is halfway
there when the power goes off. The kitchen has one job and the shaft has another, and confusing them
is how a restaurant ends up with a recipe that only works on the first floor.

That split is exactly what this day is about. Your boundary server speaks a protocol: a set of
messages with names like `tools/list` and `tools/call`, each carrying an id so an answer can be
matched to its question. A **transport** is the arrangement that gets those messages from one process
to another. The specification is unusually blunt about the division of labour. From the transports
page of the `2026-07-28` revision, verbatim:

> Protocol semantics are identical on every transport. A transport is a **binding**: it defines how
> messages are framed and delivered, how request metadata is carried, and how cancellation and
> termination are signaled.

Read that word **binding** carefully, because it is doing real work. A binding is not a translation
and not a variant of the protocol. It is a mapping from one fixed set of messages onto one particular
way of moving bytes. Change the binding and every message keeps its name, its shape and its meaning;
what changes is the *envelope* — where a message starts and stops, how the far end learns there was
an error, and what "the connection ended" is even supposed to mean.

The practical consequence is the one this part is here to make you feel. If a transport is only a
binding, then the code that answers `tools/call` cannot possibly need to know which one is in use.
And in this project it does not: day 13 printed `parts_mcp/server.py` whole, and today runs that same
file two ways without editing it. The shaft or the bay; the tray is the tray.

The trap hiding underneath is that this is only true **from the protocol's side**. Your *code* can
still break a transport without saying a word to the protocol — because one of these two bindings
uses a channel your programming language also treats as a place to print things, and the other does
not. That is part 1.2's whole subject, and it is the reason this part exists first: you cannot see
why a stray `print()` is fatal until you believe that the transport is not part of the message.

## The mechanism

Nothing new is written today at this level, so there is no file to print here. There are two
commands, and one library function that decides what they may say.

The two commands are the ones day 11's driver grew for this day; part 1.2 prints the diff that adds
them:

```console
$ cd projects/02-parts-counter
$ uv run --frozen python run.py mcp          # the dumbwaiter: a subprocess and two pipes
$ uv run --frozen python run.py mcp --http   # the loading bay: one URL, one POST per message
```

Both start `parts_mcp/server.py`. Neither edits it. The file that decides which of the two strings is
legal lives in this project's own virtual environment, and you can read it rather than believe it:

```console
$ uv run --frozen python -c "
import inspect
from mcp.server.fastmcp import FastMCP
print(inspect.getsource(FastMCP.run))
"
    def run(
        self,
        transport: Literal["stdio", "sse", "streamable-http"] = "stdio",
        mount_path: str | None = None,
    ) -> None:
        """Run the FastMCP server. Note this is a synchronous function.

        Args:
            transport: Transport protocol to use ("stdio", "sse", or "streamable-http")
            mount_path: Optional mount path for SSE transport
        """
        TRANSPORTS = Literal["stdio", "sse", "streamable-http"]
        if transport not in TRANSPORTS.__args__:  # type: ignore  # pragma: no cover
            raise ValueError(f"Unknown transport: {transport}")

        match transport:
            case "stdio":
                anyio.run(self.run_stdio_async)
            case "sse":  # pragma: no cover
                anyio.run(lambda: self.run_sse_async(mount_path))
            case "streamable-http":  # pragma: no cover
                anyio.run(self.run_streamable_http_async)
```

*Read on this machine on 2026-09-10, out of `mcp` 1.30.0 — the version this project pins, and why it
is pinned there is in `PACKAGES.md` and in `docs/adr/ADR-0005-mcp-era-gap-and-the-1x-pin.md`.*

**Line by line:**

- `transport: Literal["stdio", "sse", "streamable-http"] = "stdio"` — **three** accepted values, and
  the default is `stdio`. That default is why `parts_mcp/server.py`'s last line could have been a
  bare `mcp.run()` and still worked; it says `transport="stdio"` explicitly instead, so that the
  choice is visible to a reader rather than inherited from a library's opinion. The one string that
  is not a transport in this curriculum's sense is `"sse"`, and part 2.2 is about why it is still in
  that list.
- `mount_path: str | None = None`, documented as "Optional mount path for **SSE** transport" — the
  second parameter serves only the deprecated binding. A signature carries its history; this one has
  a spare seat for a passenger who should have got off.
- `TRANSPORTS = Literal[...]` re-declared inside the body, then `TRANSPORTS.__args__` — the type hint
  is being used at run time as data. The annotation on the parameter is erased as far as the
  interpreter is concerned; nothing checks it. If the author wanted a wrong string to be refused, the
  check had to be written by hand, and this is that check written by hand.
- `raise ValueError(f"Unknown transport: {transport}")` — the refusal is a plain `ValueError` with
  the offending string in it. That is the whole safety net: pass a string that is nearly right and
  you get an exception naming what you passed, at the moment you start the server, and not a server
  that starts and answers nothing.
- `match transport:` with one `case` per value, each calling a differently named `run_*_async`. Three
  separate implementations behind one name. Everything above this line in the file — the tools, their
  schemas, the dispatch of `tools/call` — is shared by all three, and that shared part is the
  protocol. These three lines are the whole of what a transport is in this SDK.
- The `# pragma: no cover` comments on two of the three cases are worth noticing rather than skipping.
  They are the library's own admission that its tests do not exercise those branches. That is not a
  scandal — you cannot easily unit-test "binds a socket and serves forever" — but it does tell you
  which paths were proved by a test suite and which were proved by people running them.

## When it breaks

`streamable-http` is a mouthful and `http` is what everybody says out loud, so `http` is what
everybody types. The refusal is immediate and it names the string:

```console
$ uv run --frozen python -c "
import warnings; warnings.filterwarnings('ignore')
from parts_mcp.server import mcp
mcp.run(transport='http')
"
Traceback (most recent call last):
  File "<string>", line 4, in <module>
  File "...\projects\02-parts-counter\.venv\Lib\site-packages\mcp\server\fastmcp\server.py", line 308, in run
    raise ValueError(f"Unknown transport: {transport}")
ValueError: Unknown transport: http
```

Somebody wired that string into a container's start command, and the container went into a restart
loop with this traceback in its logs while a dashboard reported "unhealthy" and nothing else. The
smallest fix is the string `streamable-http`. The lasting fix is not writing the transport name at a
call site at all: it belongs in one function — the one part 1.2 adds to `run.py` — so that there is
exactly one place in the project where a typo of this kind can live.

## In production

**What a senior writes instead.** They do not let the transport be a literal scattered through the
code. One function owns the decision, the flag that selects it comes from the process's own
environment or its command line, and the value is validated at start-up rather than at first use —
because a server that refuses to start is an incident of a few characters, and a server that starts
and then cannot be reached is an incident of an afternoon. The habit generalises: any string that
selects between implementations gets exactly one home.

**What degrades at scale.** The number is **one**. One process is the entire capacity of the stdio
binding, forever, no matter what machine you put it on — because the client *is* the parent process
and the pipes go nowhere else. Choosing it is choosing a ceiling of one concurrent client per server
process, and a system that has grown to a hundred agent workers finds that out as a hundred
subprocesses, each with its own copy of whatever the server loads at import.

**The review comment.** "This hard-codes `transport='streamable-http'` in three places and
`'stdio'` in a fourth. Please move the choice into a single `serve()` and pass a validated value in.
Right now a rename in the SDK is a four-file change and a typo in any one of them is a runtime
failure in whichever environment happens to use that path."

**The interview question.** "A colleague says their MCP server 'supports stdio but not HTTP'. What
would you actually go and look at in their code to check whether that is true, and what would it mean
about their design if it turned out to be?"
