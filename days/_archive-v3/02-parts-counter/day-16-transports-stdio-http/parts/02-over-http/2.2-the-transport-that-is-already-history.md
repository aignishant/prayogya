## One-line answer

`transport="sse"` is a deprecated binding that the SDK still accepts and still runs — so nothing
stops you choosing it, the server starts cleanly, and the failure arrives later and somewhere else,
as a client that cannot find the endpoint it was built for.

## The idea

At the far end of the yard there is an older goods lift, from before the loading bay was put in. It
still works. You call it from a panel by the wall, wait for the doors, and then load through a
*different* hatch round the corner — the panel gives you a numbered ticket and the hatch will not
accept anything without one. Two openings, one job, and they only function as a pair. Nobody would
build it that way now, which is exactly why the bay was built. But the lift was never ripped out.
There is a laminated sign on it that says do not use, and the sign has been there long enough that
people walk past without reading it.

This is the shape of every deprecation you will ever meet, and it is worth naming plainly because the
word does not mean what it sounds like. **Deprecated** does not mean removed, broken, or refused. It
means: still here, still working, and no longer the thing you should be choosing — usually with a
date attached, and always with a successor. The failure mode of a deprecation is not an error. It is
*success*, for a while, followed by a cost nobody attributed to the decision that caused it.

MCP has exactly one of these in its transports, and you have already seen its name. Part 1.1 read the
accepted values straight out of the SDK — `"stdio"`, `"sse"`, `"streamable-http"` — and `"sse"` is the
old goods lift. It is the HTTP transport MCP shipped first, in which the client opens a long-lived
`GET` to one endpoint to receive messages and posts every request to a *second*, different endpoint,
with a session identifier tying the two together. From the Streamable HTTP transport page of the
`2026-07-28` revision, verbatim:

> Streamable HTTP was introduced in protocol version 2025-03-26 as a replacement for the HTTP+SSE
> transport from protocol version 2024-11-05.

And, on the same page and at the same revision, in a block that exists specifically so that nobody
can claim they were not told:

> **Deprecated**: The HTTP+SSE transport from protocol version 2024-11-05 has been deprecated since
> protocol version `2025-03-26` […] New implementations **SHOULD NOT** adopt it

Read the dates in that sentence. The transport was superseded by the revision that came *after* the
one that introduced it, and the specification has said so ever since. And still: the SDK you have
installed will run it, today, without a warning, if you ask. That gap between what the specification
says and what your toolchain permits is the subject of this part, and it is a general skill. A
library's accepted-values list is not a recommendation. It is a compatibility promise to code that
was written before the recommendation changed, and reading it as advice is how a system acquires a
dependency on something everyone else stopped building for.

## The mechanism

Nothing in this project selects `"sse"`. `run.py`'s `serve_mcp` — part 1.2's diff — offers exactly
two transports and neither of them is this one, which is deliberate: the way to choose the deprecated
binding here is to go around the driver on purpose. That is what the experiment below does, and it is
the only place in this curriculum that does it.

### It starts. That is the problem.

```console
$ cd projects/02-parts-counter
$ uv run --frozen python -c "
import warnings; warnings.filterwarnings('ignore')
from parts_mcp.server import mcp
mcp.settings.host, mcp.settings.port = '127.0.0.1', 8092
mcp.run(transport='sse')
"
INFO:     Started server process [15944]
INFO:     Waiting for application startup.
INFO:     Application startup complete.
INFO:     Uvicorn running on http://127.0.0.1:8092 (Press CTRL+C to quit)
```

**Line by line:**

- No warning. No deprecation notice. No mention anywhere in that output that the string just passed
  in has been superseded for two protocol revisions. The library's contract is "these three values
  work", and it is keeping it.
- `Application startup complete` and a listening address are, to every automated observer you are
  likely to have, a healthy server. A container orchestrator's readiness probe would pass here. A
  deployment would go green here.
- The same `parts_mcp/server.py` is behind it — the file day 13 printed, unedited, exactly as part
  1.1 said. The server is fine. The binding is the choice, and the choice was made in one string.

And the two endpoints it *does* serve, probed for their status alone:

```console
$ curl -s -o /dev/null -w "POST /messages/ -> %{http_code}\n" -X POST http://127.0.0.1:8092/messages/ \
   -H 'Content-Type: application/json' -d '{}'
POST /messages/ -> 400
$ curl -s -o /dev/null -w "GET /sse (2s cap) -> %{http_code}\n" -m 2 http://127.0.0.1:8092/sse
GET /sse (2s cap) -> 200
```

**Line by line:**

- `404 Not Found`, in `text/plain`, nine bytes long. Compare it with the `406` in part 2.1: that one
  was JSON-RPC, with a code and a sentence naming the exact header that was missing. This one is the
  web server's generic reply to a URL that does not exist. **The MCP endpoint is not there**, and
  nothing in the answer suggests what is.
- `POST /messages/ -> 400` and `GET /sse -> 200` are the old goods lift's two openings: a stream you
  open and hold, and a separate URL you post into. The `400` is the hatch refusing an unticketed
  consignment — the server's own log line for it is below.
- The `GET /sse` request had to be capped at two seconds by hand, and that is not an inconvenience,
  it is the transport. That response never ends; holding it open *is* how the client receives
  messages. Every connected client costs one held connection for the whole of its life, whether it is
  asking anything or not.

The server's log, from the same run, is the clearest single artefact this part produces:

```console
INFO:     127.0.0.1:58180 - "GET /mcp HTTP/1.1" 404 Not Found
INFO:     127.0.0.1:58232 - "POST /mcp HTTP/1.1" 404 Not Found
Received request without session_id
INFO:     127.0.0.1:58233 - "POST /messages/ HTTP/1.1" 400 Bad Request
INFO:     127.0.0.1:58234 - "GET /sse HTTP/1.1" 200 OK
INFO:     127.0.0.1:58350 - "POST /mcp HTTP/1.1" 404 Not Found
```

**Line by line:**

- Every failed attempt is recorded as a `404` on a path the server does not serve. From the server's
  side **nothing is wrong**: it is answering correctly, promptly and by the book. The system is
  broken and no component in it is misbehaving, which is the hardest class of outage to walk into.
- `Received request without session_id` is the sentence that names the era. This transport is
  session-bound by construction: the `GET /sse` stream hands out an identifier and `POST /messages/`
  demands it, so the two openings are a pair and a client that has only one of them has nothing. That
  is precisely the property the `2026-07-28` revision removed from HTTP transport altogether.
- Nothing in this log ever says the word "deprecated", "sse" or "transport". Whoever is on call is
  reading `404`s against a server that reports itself healthy, and the cause is a five-character
  string in a start-up command they cannot see from here.

### And through this project's own client

`parts_counter/util/mcp.py`'s `over_http` — day 17's file — pointed at that same server:

```console
$ uv run --frozen python -c "

    finally:
        await ts.close()
asyncio.run(main())
"
  File "...\.venv\Lib\site-packages\google\adk\tools\mcp_tool\mcp_session_manager.py", line 1331, in create_session
    raise ConnectionError(f'Failed to create MCP session: {e}') from e
ConnectionError: Failed to create MCP session: Failed to create MCP session: Session terminated
```

**Line by line:**

- `Session terminated` — for a server that is running, healthy, and has never terminated anything.
  The client asked for a stream at a URL that returned `404`, its stream ended immediately, and
  "ended" is the only vocabulary this layer has for that. The doubled message is the framework
  wrapping its own error text and is worth noticing: two layers each added the same sentence.
- The word `404` does not appear anywhere in this traceback. The one piece of information that would
  have solved it in seconds was thrown away one layer down.
- This is the day's deliberate failure, and its shape is the lesson rather than its text: **a wrong
  choice made at start-up, in a place with no error, surfacing later as a message that describes
  neither the choice nor the place.**

### What the current revision does with this traffic

For contrast, and quoted rather than run, here is how a server built to the `2026-07-28` revision is
told to treat the leftovers of the old transport. From the Streamable HTTP transport page of that
revision, verbatim:

> An `Mcp-Session-Id` header on a request: ignore it, and do not mint or echo session IDs.

and, for the two HTTP methods the old transport needed:

> HTTP GET or DELETE → `405 Method Not Allowed`

and, for the header the old transport used to resume a dropped stream:

> `Last-Event-ID` → ignore, streams are not resumable.

**Line by line:**

- The instruction is *ignore*, not *reject*. A modern server does not error on a legacy header; it
  reads past it. That is what lets an old client fail on its own terms rather than on the server's,
  and it is a deliberate design choice about where a mismatch should surface.
- `405` rather than `404` for `GET` and `DELETE`: the endpoint exists, the method does not apply. The
  distinction matters to whoever is debugging — `404` says "wrong address", `405` says "right address,
  wrong verb", and only one of those points at the real problem.
- "streams are not resumable" is a whole architecture in five words. A resumable stream requires the
  server to remember what it has already sent to whom, which is server-side state, which is the thing
  that revision removed.

**This project cannot run that revision** — `google-adk` 2.8.0 pins `mcp<2` and the 1.x line is a
legacy-era implementation, which is written up in `docs/adr/ADR-0005-mcp-era-gap-and-the-1x-pin.md`
and in `PACKAGES.md`. So the three rules above are quoted as what comes next and are not printed as
runnable code anywhere in P02. What your own stateless Streamable HTTP server from part 2.1 does with
the same probes, run today, is a partial rehearsal of them:

```console
$ curl -s -D - -m 3 -X DELETE http://127.0.0.1:8090/mcp -H 'Accept: application/json, text/event-stream'
HTTP/1.1 405 Method Not Allowed
{"jsonrpc":"2.0","id":"server-error","error":{"code":-32600,"message":"Method Not Allowed: Session termination not supported"}}

$ curl -s -D - -m 3 -X GET http://127.0.0.1:8090/mcp -H 'Accept: text/event-stream'
HTTP/1.1 200 OK
content-type: text/event-stream
Transfer-Encoding: chunked

$ curl -s -X POST http://127.0.0.1:8090/mcp \
   -H 'Content-Type: application/json' -H 'Accept: application/json, text/event-stream' \
   -H 'Mcp-Session-Id: 00000000000000000000000000000000' \
   -d '{"jsonrpc":"2.0","id":9,"method":"tools/call","params":{"name":"bin_location","arguments":{"part_no":"BLT-0310"}}}'
event: message
data: {"jsonrpc":"2.0","id":9,"result":{"content":[{"type":"text","text":"{\n  \"part_no\": \"BLT-0310\",\n  \"bin\": \"C-07-2\",\n  \"name\": \"Timing belt kit\"\n}"}],"structuredContent":{"part_no":"BLT-0310","bin":"C-07-2","name":"Timing belt kit"},"isError":false}}
```

**Line by line:**

- `DELETE` already behaves the modern way, and it says why: `Session termination not supported`.
  There is no session to end, so the verb has nothing to act on. The revision that removed sessions
  turned this server's local choice into everybody's rule.
- `GET` does **not**. It returns `200` and an open stream, where the current revision says `405`.
  That is the era gap, visible in one status code on your own machine: a legacy-era SDK still offers
  the standalone listening stream that the modern transport deleted.
- The made-up `Mcp-Session-Id` was ignored, the call was answered, and no session id came back in the
  response headers — which is the first of the three rules, arrived at from the other direction. This
  server ignores session ids because it was built with no sessions; a modern one ignores them because
  the protocol has none. Same behaviour, two different reasons, and only one of them is a promise.

## When it breaks

```text
ConnectionError: Failed to create MCP session: Failed to create MCP session: Session terminated
```

Somebody moved a working boundary into a container, copied the start command from an older project's
notes, and shipped it. The image built, the container started, the readiness probe passed and the
deployment went green. The first report came from a user, not a monitor: the agent had stopped being
able to look anything up and was answering from nothing. The traceback above is the whole of what the
client had to say, and it is a lie in the only way that matters — no session was terminated, because
none was ever created, because the URL it asked for does not exist on that server. The smallest fix
is one word in one string, `sse` to `streamable-http`. The fix that stops it recurring is that the
start command names a transport the project's own driver understands, so that a wrong one fails at
argument parsing with exit `2` instead of starting a server nobody can reach.

## In production

**What a senior writes instead.** They pick the current transport, and then they make the choice
unrepeatable: the transport is not spelled at a start command at all, it comes from one function, and
a check asserts that the served endpoint answers before anything is called healthy. The general rule
is stronger than this one case — **a deprecated feature that still works is a scheduled outage with
no date on it**, so it gets a ticket the day it is discovered, not the day it stops working. And a
readiness probe that only proves a socket is open proves nothing; the probe has to speak the protocol,
which for this server means a `tools/list` that comes back with four tools.

**What degrades at scale.** The number is **one held connection per client, indefinitely**. The old
transport requires every client to keep a `GET` stream open for its entire life whether it is asking
anything or not, so a hundred idle agents cost a hundred open connections and the same again in
per-connection state on whatever proxy sits in front. The replacement holds a connection only while a
request is being answered. That is the difference the deprecation exists to buy, and it is the reason
"it still works" is not an argument.

**The review comment.** "The Dockerfile's `CMD` passes `transport=sse`. That transport has been
deprecated since protocol revision `2025-03-26` and the spec says new implementations should not
adopt it — and more immediately, our own client speaks Streamable HTTP, so this container will start
healthy and serve `404` to every request. Please use the project's `run.py mcp --http` and add a
readiness check that actually lists tools."

**The interview question.** "A dependency you rely on marks a feature deprecated but keeps it
working, with no removal date announced. Your service uses it and there is no incident. Make the case
for scheduling the migration now, in terms your manager will accept, and tell me what evidence you
would gather first."
