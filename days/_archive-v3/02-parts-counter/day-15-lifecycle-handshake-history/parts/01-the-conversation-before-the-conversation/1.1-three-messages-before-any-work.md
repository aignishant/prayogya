## One-line answer

Before a legacy-era MCP client may ask this server for anything, three messages cross the pipe —
`initialize`, the server's reply, and `notifications/initialized` — and you can type all three by
hand into the server's standard input and read the answer with your own eyes.

## The idea

There is a hut by the gate of every building site, and you do not walk past it. You give your name,
you say what trade you are, and the person behind the desk tells you what is in force today: hot
work suspended until three, the east stair closed, the scaffold on the north face tagged and not to
be climbed. Then you sign the book and go to work.

Nothing was built during that exchange. No brick moved. And yet the exchange is the reason the rest
of the day works, because afterwards neither of you has to guess. The desk knows a welder is on
site. You know not to strike an arc. If either of you had skipped it and started work on
assumptions, the first thing anybody would learn about the mismatch is when something went wrong.

That is the shape of what happens at the start of every connection to the server day 14 built. The
specification calls it the **lifecycle**, and the revision this project runs — labelled
`2025-06-18`, and *not* the current one — divides it into three phases, verbatim:

> 1. **Initialization**: Capability negotiation and protocol version agreement
> 2. **Operation**: Normal protocol communication
> 3. **Shutdown**: Graceful termination of the connection
>
> — MCP specification, revision **`2025-06-18`**, `basic/lifecycle`

Read that first line again, because it names the two things today is about. **Capability
negotiation** is the permits board: each side says what it can do before either asks for anything.
**Protocol version agreement** is both parties confirming they are reading the same edition of the
site rules. Part 1.2 takes the first; part 2.1 takes the second.

Three terms, defined here because the rest of the day leans on them.

A **handshake** is an exchange of messages that carries no work and exists only so that the messages
which follow can assume something. It is a cost you pay once per connection to avoid paying a
smaller cost on every message afterwards — and, as part 2.2 will show, the current revision decided
that trade was the wrong way round.

A **request** in this protocol is a JSON object carrying `jsonrpc`, an `id`, a `method` and usually
`params`. The `id` is the whole point of it: the answer comes back carrying the same `id`, so a
client with several questions outstanding knows which reply belongs to which question.

A **notification** is the same thing **without an `id`**, and that single missing field changes its
meaning completely. No `id` means no reply is possible, because a reply would have nothing to
address itself to. So a notification is a statement, not a question: the sender says it and moves
on, and nothing in the protocol can tell the sender whether it was acted on. The third message of the
handshake, `notifications/initialized`, is exactly that. It is the client saying *I have read your
reply and I am ready*, and it is the one message of the three that expects silence back.

The person at the desk does not sign your book back at you. They just start letting you through.

## The mechanism

The whole handshake, driven by hand. Three newline-delimited JSON-RPC messages piped into the
server's standard input, one per line, in order — no client library anywhere in the picture:

```console
$ cd projects/02-parts-counter
$ printf '%s\n%s\n%s\n' \
 '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"by-hand","version":"0"}}}' \
 '{"jsonrpc":"2.0","method":"notifications/initialized"}' \
 '{"jsonrpc":"2.0","id":2,"method":"tools/list"}' \
 | uv run --frozen python -m parts_mcp.server
```

That runs the server `parts_mcp/server.py` — printed whole by day 13, at
`days/02-parts-counter/day-13-mcp-stateless-core/`, and its tool bodies walked by day 14 at
`days/02-parts-counter/day-14-server-skeleton-first-tool/`. Nothing in it is reprinted here, and
nothing in it changes today. Today's subject is the conversation that happens **before** any of
those tools is reachable.

Here is the first line of the server's standard output — the answer to message one — pretty-printed:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "protocolVersion": "2025-06-18",
    "capabilities": {
      "experimental": {},
      "prompts": {
        "listChanged": false
      },
      "resources": {
        "subscribe": false,
        "listChanged": false
      },
      "tools": {
        "listChanged": false
      }
    },
    "serverInfo": {
      "name": "parts-mcp",
      "version": "1.30.0"
    }
  }
}
```

**Line by line:**

- `"id": 1` — the same `id` the request carried. That is the only thing tying this object to that
  question. Change the request's `id` to `"abc"` and this comes back as `"abc"`; the protocol does
  not care what an id is, only that it matches.
- `"protocolVersion": "2025-06-18"` — the version **agreed**, not the version requested. Here they
  are the same string because the server supports what was offered. Part 2.1 offers versions it does
  not support and watches this field become something else entirely.
- `"capabilities"` — the permits board. Four keys, and every one of them is the server describing
  itself before being asked anything. `experimental` is the escape hatch for non-standard features
  and is empty. `prompts`, `resources` and `tools` each say the server has that feature at all, and
  each carries sub-flags saying **how much** of it. Part 1.2 is entirely about what those flags
  promise.
- `"listChanged": false`, three times — the server is telling you it will never volunteer that one
  of its lists has changed. `resources` additionally says `"subscribe": false`.
- `"serverInfo": {"name": "parts-mcp", ...}` — `name` is the string `parts_mcp/server.py` passed to
  its server constructor, and it is the server naming itself for logs and for a human picking
  between several.
- `"version": "1.30.0"` — **read this one twice.** That is not this project's version. This project
  has never declared a version to the SDK, so the SDK filled the field in with **its own**: `mcp`
  1.30.0, the pinned SDK recorded in `projects/02-parts-counter/PACKAGES.md`. Anyone reading a log
  and concluding the parts server is on release 1.30.0 has read the SDK's version number and
  believed it was ours. The failure is silent because the field is always populated and always
  plausible.

Now the second message — and the point is what does *not* happen. Send only `initialize` and the
notification, and count the lines that come back on standard output:

```console
$ printf '%s\n%s\n' \
 '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"by-hand","version":"0"}}}' \
 '{"jsonrpc":"2.0","method":"notifications/initialized"}' \
 | uv run --frozen python -m parts_mcp.server 2>/dev/null | wc -l
1
```

**Line by line:**

- **One line, for two messages sent.** The `initialize` request was answered; the notification was
  not, and that is correct rather than a fault. It carried no `id`, so there is no address to reply
  to.
- This is the cheapest possible demonstration of what a notification is. If you take one thing from
  this part into every other protocol you meet: **a message with no correlation id cannot be
  acknowledged, so anything that must be acknowledged cannot be a notification.**
- `2>/dev/null` discards the server's standard error. The server logs there — you will have seen a
  `Processing request of type ListToolsRequest` line in the first transcript — and day 16 is where
  standard error's role in the stdio transport is taken properly. Here it is only noise in a line
  count.

And the third message, `tools/list`, is answered normally once the handshake is done. Its response
body — the `Tool` objects, their `inputSchema` and `outputSchema` — belongs to day 14 and is walked
there; it is not reprinted here. What matters for this part is only that it was answered at all,
which is the claim part 2.2 breaks on purpose.

*Every transcript above was run on this machine on 2026-09-10: uv 0.12.3, CPython 3.12.12,
`mcp` 1.30.0.*

## When it breaks

The commonest way this goes wrong by hand has nothing to do with the protocol. Leave the
`protocolVersion` field out of `params` — a plausible slip, since the other two fields are there —
and the server does not say "you left out the version". It says this, on standard error, and the
extract is the top of it:

```text
Failed to validate request: 28 validation errors for ClientRequest
PingRequest.method
  Input should be 'ping' [type=literal_error, input_value='initialize', input_type=str]
    For further information visit https://errors.pydantic.dev/2.13/v/literal_error
InitializeRequest.params.protocolVersion
  Field required [type=missing, input_value={'capabilities': {}, 'cli...-hand', 'version': '0'}}, input_type=dict]
    For further information visit https://errors.pydantic.dev/2.13/v/missing
```

Twenty-eight errors for one missing field, because the incoming object is checked against a union of
every request type the protocol has and each one objects in its own way. The line that actually
matters is the second pair — `InitializeRequest.params.protocolVersion`, `Field required` — and it
is buried at position two out of twenty-eight. Someone debugging this at eleven at night reads the
first four lines, sees `PingRequest`, and starts wondering why the server thinks they sent a ping.
The smallest fix is to search the wall of text for `Field required` and ignore every `literal_error`
in it: those are the alternatives being ruled out, not the problem.

## In production

**What a senior writes instead.** Nobody types this handshake into a shell to get work done — a
client library sends it, and in this project that is day 17's job. What a senior does keep is
exactly the command above, in the project's own troubleshooting notes, because when a client
library reports "failed to connect to server" the fastest way to find out whether the *server* is
healthy is to hand it three lines on standard input and see whether an `initialize` result comes
back. A boundary you can drive with `printf` is a boundary you can debug without a debugger.

**What degrades at scale.** The handshake is per connection, not per request, and that is the number
that bites. A client that opens a fresh stdio process for each question pays **three messages and a
Python interpreter start-up** for every one of them; a client that opens once and keeps the process
pays them **once**, however many thousands of calls follow. Same server, same tools: the difference
is entirely in how often you sign in at the gate. Day 17 wires a client that opens once.

**The review comment.** "This log line prints `serverInfo.version` and labels it 'parts-mcp
version'. That field is `1.30.0` — it is the MCP SDK's version, because we never passed one. Either
pass this project's version to the server constructor or relabel the log line; right now every
incident report will quote a version number that has nothing to do with our deployment."

**The interview question.** "In JSON-RPC, what is the difference between a request and a
notification, and what does that difference make impossible? Give an example of something that
looks like it should be a notification but must not be."
