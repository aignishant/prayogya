## One-line answer

Offer this server a protocol version it knows and it echoes it back; offer it one it does not and it
does **not** refuse — it answers with its own latest, `2025-11-25`, and carries on, which quietly
makes checking the answer the client's job and nobody else's.

## The idea

The board in the site hut has a date on it, and the date is not decoration. Rules get reissued. The
edition you were inducted on in spring is not the edition pinned up in autumn, and a person working
from the wrong edition is not being careless — they are being careful about the wrong document.

So the desk asks which edition you signed. And here is the interesting part: when you name an
edition the desk has never heard of, the desk does not throw you off site. It hands you the edition
it has, says "this is what we work to", and lets you through the gate. Whether you can actually read
that edition is now entirely your problem, and nobody at the desk will ever check.

That is **version negotiation**, and it is the second half of what part 1.1 quoted from the
`2025-06-18` lifecycle. A **protocol revision** in MCP is a dated string — `2025-06-18`,
`2025-11-25` — naming one published edition of the rules. The client names the one it wants in the
`initialize` request; the server names the one that will actually govern the connection in its
result. Those two strings are allowed to differ, and the rule for when they may differ is written
down, verbatim:

> In the `initialize` request, the client **MUST** send a protocol version it supports. This
> **SHOULD** be the *latest* version supported by the client.
>
> If the server supports the requested protocol version, it **MUST** respond with the same version.
> Otherwise, the server **MUST** respond with another protocol version it supports. This **SHOULD**
> be the *latest* version supported by the server.
>
> If the client does not support the version in the server's response, it **SHOULD** disconnect.
>
> — MCP specification, revision **`2025-06-18`**, `basic/lifecycle`, *Version Negotiation*

Three sentences, and the design lives in the shape of them rather than in any one. The server's
obligations are both **MUST**: it must echo, or it must counter. There is no "MUST refuse" anywhere,
because refusal was never one of the options. And then the only sentence that protects the client is
a **SHOULD**, and it is addressed to the client. **The party that can detect the mismatch is not the
party that has to act on it.**

That is a load-bearing asymmetry and it is worth naming before you see it happen: negotiation that
counters rather than refuses moves the entire burden of correctness onto whoever wrote the client,
and it does so silently, in a field most people read once while getting something else working.

## The mechanism

Three handshakes, differing in one string. Each sends a single `initialize` and prints the
`protocolVersion` that came back:

```console
$ cd projects/02-parts-counter
$ for v in 2025-06-18 2024-01-01 9999-12-31; do
    printf '%s\n' "{\"jsonrpc\":\"2.0\",\"id\":1,\"method\":\"initialize\",\"params\":{\"protocolVersion\":\"$v\",\"capabilities\":{},\"clientInfo\":{\"name\":\"by-hand\",\"version\":\"0\"}}}" \
    | uv run --frozen python -m parts_mcp.server 2>/dev/null \
    | python -c "import sys,json; print('offered $v -> replied', json.loads(sys.stdin.readline())['result']['protocolVersion'])"
  done
offered 2025-06-18 -> replied 2025-06-18
offered 2024-01-01 -> replied 2025-11-25
offered 9999-12-31 -> replied 2025-11-25
```

**Line by line:**

- **Row one is the echo.** `2025-06-18` is a revision this SDK supports, so the rule's first
  **MUST** applies and the same string comes back. That agreement is why every other transcript in
  this day carries `2025-06-18`: it is a version both ends really speak.
- **Row two is the counter-offer.** `2024-01-01` is not a revision of anything — it is a date that
  never named an edition — and the server does not say so. It answers `2025-11-25` and the
  connection continues. Nothing in this transcript is an error. Nothing anywhere is logged as one.
- **Row three is the same counter-offer from the opposite direction.** `9999-12-31` is a version
  from the future, which is the more realistic case: a newer client meeting an older server. The
  answer is identical, and the identical answer is the point — **the server's reply does not
  distinguish "too old" from "too new" from "never existed".** It says only: here is mine.
- `2>/dev/null` again drops the server's log lines on standard error so the loop prints one clean
  line per run.

Where does `2025-11-25` come from? Not from this project's code, and not from the specification's
current revision. It is a constant in the pinned SDK:

```console
$ uv run --frozen python -c "
import mcp.types as t
print('LATEST_PROTOCOL_VERSION    =', t.LATEST_PROTOCOL_VERSION)
print('DEFAULT_NEGOTIATED_VERSION =', t.DEFAULT_NEGOTIATED_VERSION)
"
LATEST_PROTOCOL_VERSION    = 2025-11-25
DEFAULT_NEGOTIATED_VERSION = 2025-03-26
```

**Line by line:**

- `LATEST_PROTOCOL_VERSION = 2025-11-25` — the newest revision **this SDK implements**, and the
  string it hands back when it cannot honour what was asked. That is what row two and row three
  printed, arrived at by reading a constant rather than by any reasoning about the offered value.
- `DEFAULT_NEGOTIATED_VERSION = 2025-03-26` — a second, older constant, used when nothing was
  negotiated at all. Two version constants in one package is itself worth noticing: the SDK
  distinguishes *the best I can do* from *what I assume when nobody said*.
- **Be exact about what `2025-11-25` is and is not.** It is the latest revision the pinned `mcp`
  1.30.0 speaks. It is **not** the current specification revision — that is `2026-07-28`, recorded in
  `projects/02-parts-counter/PACKAGES.md` and in
  `docs/adr/ADR-0005-mcp-era-gap-and-the-1x-pin.md`. A reader who takes `2025-11-25` off this
  transcript as "the current MCP version" has read an SDK's ceiling and called it the protocol's.
  Part 2.2 is about the distance between those two dates.

Now the consequence the specification only ever wrote as a **SHOULD**. Offer a version the server
does not know, ignore the counter-offer entirely, and go straight to work:

```console
$ printf '%s\n%s\n%s\n' \
 '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2024-01-01","capabilities":{},"clientInfo":{"name":"by-hand","version":"0"}}}' \
 '{"jsonrpc":"2.0","method":"notifications/initialized"}' \
 '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"stock_level","arguments":{"part_no":"BRK-0143"}}}' \
 | uv run --frozen python -m parts_mcp.server 2>/dev/null
{"jsonrpc":"2.0","id":1,"result":{"protocolVersion":"2025-11-25","capabilities":{"experimental":{},"prompts":{"listChanged":false},"resources":{"subscribe":false,"listChanged":false},"tools":{"listChanged":false}},"serverInfo":{"name":"parts-mcp","version":"1.30.0"}}}
{"jsonrpc":"2.0","id":2,"result":{"content":[{"type":"text","text":"{\n  \"part_no\": \"BRK-0143\",\n  \"on_hand\": 4,\n  \"unit\": \"set\",\n  \"reorder_at\": 6,\n  \"below_reorder\": true\n}"}],"structuredContent":{"part_no":"BRK-0143","on_hand":4,"unit":"set","reorder_at":6,"below_reorder":true},"isError":false}}
```

**Line by line:**

- The client asked for `2024-01-01`, was handed `2025-11-25`, **did not look**, and got a correct
  answer to a real question. The system works. That is the problem.
- Nothing warned. No log line on standard error mentions a version, no field on the result flags a
  downgrade, and the tool result is byte-for-byte what a properly negotiated client would receive.
  The two situations are indistinguishable from inside the client.
- The result envelope — `content`, `structuredContent`, `isError` — is day 14's subject and is walked
  at `days/02-parts-counter/day-14-server-skeleton-first-tool/`. It appears here only as proof that
  the call went all the way through. The stock figures are synthetic, like all data in this
  curriculum.
- So the whole protection is one `if` in code nobody has written yet: compare the `protocolVersion`
  in the result against the set of revisions your client actually implements, and disconnect when it
  is not in the set. The specification says **SHOULD**. The SDK will not do it for you. If it is not
  in your client, it does not happen.

*Every transcript above was run on this machine on 2026-09-10: uv 0.12.3, CPython 3.12.12,
`mcp` 1.30.0.*

## When it breaks

The version field is typed more loosely than anybody expects, and you find that out from the wrong
end. Send `null` and the server logs a validation failure whose two halves name the reason:

```text
InitializeRequest.params.protocolVersion.str
  Input should be a valid string [type=string_type, input_value=None, input_type=NoneType]
    For further information visit https://errors.pydantic.dev/2.13/v/string_type
InitializeRequest.params.protocolVersion.int
  Input should be a valid integer [type=int_type, input_value=None, input_type=NoneType]
    For further information visit https://errors.pydantic.dev/2.13/v/int_type
```

Two complaints for one field, because the field accepts **a string or an integer**. So the version
written unquoted — `"protocolVersion": 20250618`, a natural slip when a template builds JSON by hand
— is not rejected at all: it validates as an integer, matches no known revision, and is answered
with the usual `2025-11-25` counter-offer while everything appears to work. Someone shipped that on
a Friday and spent the evening reading a handshake transcript in which every field was present and
the connection was silently on the wrong edition. The smallest fix is to quote the value, and the
fix that stops it recurring is the one the previous section named: assert on the version that came
*back*.

## In production

**What a senior writes instead.** They never let the negotiated version be implicit. The client holds
an explicit set of revisions it implements, offers the newest of them, and — the line that matters —
compares the returned string against that set and closes the connection with a named error when it is
absent. And they log the agreed version once per connection, at connect time, because the first
question in every protocol incident is "which revision were we actually on?" and the transcripts
above show that nothing else in the exchange will answer it.

**What degrades at scale.** The check costs **one string comparison, once per connection**. Skipping
it costs every request that follows: a long-lived stdio client that answers a thousand questions over
one server process performs that comparison once and a thousand calls inherit the result, or performs
it never and a thousand calls run against an edition the client does not implement. The asymmetry is
the argument — one comparison against an unbounded number of requests — and it is why "we'll add the
version check later" is never worth the trade.

**The review comment.** "We send `protocolVersion` and never read the one that comes back. Per the
`2025-06-18` lifecycle the server is allowed to counter with its own latest instead of refusing, so
this connects successfully against a server we cannot actually talk to. Please compare the result's
`protocolVersion` against our supported set and disconnect on a miss — and log the agreed version."

**The interview question.** "A protocol lets a server answer a version request with a different
version rather than an error. Who is responsible for detecting the mismatch, what happens if they
do not, and what would you change about the protocol so the failure could not be silent?"
