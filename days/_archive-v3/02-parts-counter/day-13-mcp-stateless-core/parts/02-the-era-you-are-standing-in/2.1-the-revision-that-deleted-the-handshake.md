## One-line answer

The current MCP specification revision, `2026-07-28`, deleted the `initialize` handshake and the
`Mcp-Session-Id` header outright — and this project performs a handshake anyway, because
`google-adk` 2.8.0 pins `mcp<2` and the 1.x SDK is a legacy-era implementation whose
`LATEST_PROTOCOL_VERSION` is `2025-11-25`, which is what this stack **speaks** and is emphatically
not what the specification currently **says**.

## The idea

The town's exchange went automatic last year. Everybody's home telephone dials straight through now;
nobody says *number please* to anyone any more, and most people under thirty have never spoken to an
operator in their lives. But walk into the works on the industrial estate and there is still a board
on the wall of the front office with a woman plugging cords into jacks, because every handset in that
building is wired to that board, and replacing the board means replacing three hundred handsets, and
nobody has three hundred handsets.

There is nothing shameful about the board. It works. Calls go through. The one thing that would be
shameful is not telling the new starter on her first morning, and letting her spend six months
believing that this is how telephones work — because the day she leaves for a job somewhere else, or
the day the works finally rewires, everything she knows about *number please* becomes not just
useless but actively misleading.

This part is that first morning, and this whole page exists for one sentence: **the protocol you are
about to spend four more sittings learning is not the protocol as it currently stands.** Everything
you run in this project is real, works, and is the era the toolchain can execute. It is also, as of
the revision that is current while this is written, history.

Two words are needed and the specification supplies both. A **protocol revision** is a dated version
of the rules — `2025-06-18`, `2025-11-25`, `2026-07-28` — and the current one is the one the
maintainers say is current, not the newest one you have heard of. And the specification itself now
names two **eras**, which is unusual and tells you how large the change was. Here is that definition
verbatim, from `https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning`, fetched
2026-09-10:

```text
* Modern: protocol versions that convey version, identity, and capabilities as per-request metadata
  (revision `2026-07-28` and later).
* Legacy: protocol versions that establish a session with an `initialize` handshake (`2025-11-25`
  and earlier).
```

Read the second bullet again and then look back at what part 1.2 ran. Every transcript in this day
begins with `initialize`. By the specification's own definition, this project is legacy, and it is
legacy by exactly one revision — `2025-11-25` is the last date on the wrong side of the line.

## The mechanism

There is no code in this part. Three facts, each read live, and then the honest paragraph.

### 1 · What the specification now says

The revision that is current, from `https://modelcontextprotocol.io/docs/learn/versioning`, fetched
2026-09-10:

```text
The current protocol version is 2026-07-28.
```

What it did, from that revision's changelog, verbatim:

```text
Make MCP stateless: remove the `initialize`/`notifications/initialized` handshake. Every request now
carries its protocol version and client capabilities in `_meta` […] Version mismatches return
UnsupportedProtocolVersionError
```

```text
Remove protocol-level sessions and the `Mcp-Session-Id` header from the Streamable HTTP transport.
List endpoints (`tools/list`, `resources/list`, `prompts/list`) no longer vary per-connection.
```

And how versions are settled now, from the versioning page, verbatim:

```text
There is no negotiation handshake. Every request carries its protocol version, and the server accepts
or rejects each request independently:
```

There is one more piece of evidence for how complete the removal was, and it is an absence rather
than a quote: **the lifecycle page is gone.** The URL `…/2026-07-28/basic/lifecycle` resolves to
`…/2026-07-28/basic/versioning`. A protocol whose specification no longer has a page called
*lifecycle* is a protocol that no longer has one.

### 2 · What this stack speaks

```console
$ uv run --frozen python -c "
import mcp.types as t
print('LATEST_PROTOCOL_VERSION    =', t.LATEST_PROTOCOL_VERSION)
print('DEFAULT_NEGOTIATED_VERSION =', t.DEFAULT_NEGOTIATED_VERSION)
"
LATEST_PROTOCOL_VERSION    = 2025-11-25
DEFAULT_NEGOTIATED_VERSION = 2025-03-26
```

Be exact about what those two constants are, because the names invite a misreading. `2025-11-25` is
**the newest revision this installed SDK implements**. It is not the newest revision of MCP, it is
not what the specification says today, and it is not a claim about anything outside this virtual
environment. It is a fact about a wheel on this disk, read from it on 2026-09-10. The current
revision is `2026-07-28`, four months and one era ahead of it, and no amount of upgrading `mcp`
inside the 1.x line will close that gap, because the gap is the line.

### 3 · Why the pin cannot simply be raised

`google-adk` 2.8.0 declares `mcp>=1.24,<2`, so the newest MCP SDK this project may install is a 1.x
release, and every 1.x release is legacy-era. That is the entire mechanism of the gap: it is not a
choice this curriculum made about pedagogy, it is a bound in a dependency's metadata. **Part 2.2 is
about that bound** — how it is stated, how it can be evaded by accident, and what it looks like when
it is.

### The two eras, side by side

Legacy is what this project runs. Modern is quoted, labelled, and **never pasted into this project's
code**, because none of it can be produced by anything installed here.

| | Legacy — what runs here (`2025-11-25` and earlier) | Modern — the current revision (`2026-07-28`) |
| --- | --- | --- |
| Opening a conversation | `initialize`, then `notifications/initialized` | nothing — there is no handshake |
| Where the protocol version lives | agreed once, in the `initialize` exchange | on every request, in `_meta` |
| Where capabilities live | agreed once, in the same exchange | on every request |
| Session identity over HTTP | `Mcp-Session-Id`, minted by the server, quoted by the client | removed; a server ignores the header if it sees one |
| A version the server cannot speak | the server counters with one it can — **day 15's subject** | the request is rejected, `UnsupportedProtocolVersionError` |
| Does `tools/list` vary per connection? | it may | no — list endpoints no longer vary per-connection |

The right-hand column is a reading list, not an instruction. Nothing named in it —
`UnsupportedProtocolVersionError`, `_meta`, per-request capabilities — exists in `mcp` 1.30.0, and
writing any of it into this project would produce code that cannot run and a transcript that could
only be invented.

### The honest paragraph

So: this project performs a handshake that the current specification revision deleted, and it will go
on doing so for the rest of the phase. The reason is not that the handshake is better, and it is not
that the reframe in part 1.1 is disputed — the reframe is the specification's own, quoted from its
own front page. The reason is that a day whose commands cannot be run is worth less than a day that
runs the previous era honestly. Every transcript in days 13 to 17 is real because this stack really
speaks that. The alternative was a phase of diagrams.

What you get out of the arrangement is worth more than the tidiness you lose. You are going to watch
a protocol move underneath a working system, with the old shape still executing in front of you and
the changelog entry that deleted it quoted on the same page. That is the single most useful thing
this phase can teach about depending on a specification that is still moving, and you cannot get it
from a stack that is already current.

**What day 15 does with this.** Day 15 is *Lifecycle, stateless-first: the old handshake as history*,
and it is where the handshake gets run by hand — three newline-delimited messages piped into the
server over stdio, `initialize`, `notifications/initialized`, `tools/list` — and where version
negotiation is observed rather than described, including what this server does when a client offers a
revision it has never heard of. It will then quote the changelog line above again, in its own body,
and put the handshake away. Today's job is only to make sure that when you see it, you already know
which era you are looking at.

**And what is owed if the bound moves.** `PACKAGES.md` in this project carries a `TODO(me)` naming
the exact moves: `FastMCP` becomes `MCPServer`, `mcp.server.fastmcp` becomes `mcp.server.mcpserver`,
and `stateless_http` leaves the constructor. `docs/adr/ADR-0005-mcp-era-gap-and-the-1x-pin.md` is the
record of why this day was written this way, so that whoever undoes it knows what they are undoing.

## When it breaks

Here is the era gap as an HTTP status code. This is a client that has read the current specification
and is doing exactly what it says — announcing `2026-07-28` — talking to the boundary from part 1.2:

```console
$ curl -s -w "\nHTTP %{http_code}\n" -X POST http://127.0.0.1:8090/mcp \
   -H 'Content-Type: application/json' \
   -H 'Accept: application/json, text/event-stream' \
   -H 'MCP-Protocol-Version: 2026-07-28' \
   -d '{"jsonrpc":"2.0","id":8,"method":"tools/list"}'
{"jsonrpc":"2.0","id":"server-error","error":{"code":-32600,"message":"Bad Request: Unsupported protocol version: 2026-07-28. Supported versions: 2024-11-05, 2025-03-26, 2025-06-18, 2025-11-25"}}
HTTP 400
```

That is the whole of this part in one line, and it is a much better error than it had to be: it names
the version it was given and then lists, in order, every version it does know. Somebody meets this
after upgrading a client library and reads it as a bug in their request, because the request is
correct — it is correct *for the current specification*, and this server has never heard of that
specification. The smallest fix is to send a revision from the right-hand end of that list. The real
fix is not available, because it is a dependency bound in somebody else's package.

## In production

**What a senior writes instead.** They write down the revision, not the library version, and they
write it where a person deploying the thing will see it. `mcp==1.30.0` tells you nothing about what
goes over the wire; `2025-11-25` is the fact that matters to whoever is integrating. And they check
it the way this project did — by reading the constant out of the installed package rather than out of
a changelog — because the wheel on the disk is the only thing that can be wrong in a way that
matters.

**What degrades at scale.** Count the revisions this boundary will accept: **four** —
`2024-11-05`, `2025-03-26`, `2025-06-18`, `2025-11-25` — and the one the specification calls current
is not among them. So a client fleet that follows the specification gets a `400` from this boundary on
**every single request**, not a degraded experience on some of them. And the gap is not local to this
project: `google-adk` 2.8.0's `mcp>=1.24,<2` applies to every project in this curriculum that reaches
a boundary through `McpToolset`, which from here is all of them, until that bound moves.

**The review comment.** "The pin in `pyproject.toml` is fine, but the pull request description says
'MCP support' and that is not a claim anybody can check. Which revision? Put the date in the
description and in `PACKAGES.md`, say where you read it from — the installed package, not the docs —
and say plainly whether it is the current one. If it is not, one sentence on why, and a `TODO`
carrying the exact upgrade moves."

**The interview question.** "You are integrating with a protocol whose specification has moved a
whole era ahead of the SDK your framework allows you to install. Walk me through how you would
establish that, what you would write down, what you would tell the team that consumes your service,
and how you would decide whether to wait for the framework or work around it."
