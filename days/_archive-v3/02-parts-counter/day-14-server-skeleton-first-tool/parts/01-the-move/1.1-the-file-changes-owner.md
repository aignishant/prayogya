## One-line answer

The inventory file has changed owner: it now lives beside the boundary rather than beside the
agent's tools, and the move bought two things that could not have been bought before it — one lock
that genuinely serialises every reader and every writer, because there is now only one process that
opens the file at all, and a write that lands whole or not at all.

## The idea

The stockroom door is bricked up. Where it used to stand there is a hatch about chest high, a shelf
under it wide enough to rest a box on, and a counter on the far side with one person behind it. You
do not walk in any more. You come to the hatch, say what you want, and the storeman turns round,
takes it off the shelf, writes the movement in the book at their elbow, and hands it through.

Everything about that is worse for you personally. You wait. There is a queue at half past eight
when three people arrive at once. On a good day, reaching past somebody for a box was faster than
any of this and you knew exactly where the box was. What you get in exchange is one thing and it is
the thing the shop was losing: **the book is right.** Not right most of the time, not right except
on Fridays — right, because exactly one pair of hands writes in it, and that pair of hands is never
writing two entries at once.

Two other things changed with the hatch, and they are worth saying plainly because they are the
whole of this part.

The first is that the storeman is the **only** person who touches the book. Before, when the door
was open, you could have agreed a rule — *shout before you write* — and everybody could have kept
it honestly, and it would still have failed the moment a delivery driver who had never heard the
rule walked in. A rule only binds the people who know it. A hatch binds everybody, including the
people who have never heard of it, because there is no other way in.

The second is how the storeman writes. They do not scribble over the old number in the book while
you watch. They write the new page out on a fresh sheet at their elbow, check it, and then swap the
sheet into the book in one movement. If you glance at the book at any moment you see either the old
page or the new page, complete. There is no instant at which you see a page halfway through being
rewritten, because such a page never exists where anybody can look at it.

Two words for those two things. **Serialising** access means putting every read and every write into
a single queue so that no two of them overlap; that is the storeman, and in code it is a lock. An
**atomic replace** means making a change visible in one indivisible step, so no reader can catch it
part-done; that is the fresh sheet, and in code it is writing a temporary file and then moving it
over the target. Day 12 lost parts to the missing first one and crashed readers on the missing
second one, and it was careful to show you that these are **two separate failures with two separate
windows** — quieting one tells you nothing about the other. Today both are fixed, separately, in one
file, and the file says which fix is which.

One last thing before the code, because it is the reason this is a move and not a patch. Day 12
ended by asking what a `threading.Lock` around `adjust` would actually buy, and answered: everything
on that page, and almost nothing in the world, because a lock lives inside one process and the
problem does not. Nothing about that argument has changed. What changed is the **shape**: there is
now exactly one process in this system that opens `parts.json`, so a lock inside that process is not
a partial answer any more. It is the whole answer. The lock did not get better; it got a building to
be the only door of.

## The mechanism

The move first, stated as paths, because the paths are the argument.

| Before — day 12 | After — today |
| --- | --- |
| `parts_counter/data/parts.json` | `parts_mcp/data/parts.json` |
| `parts_counter/store.py` | `parts_mcp/store.py` |
| `parts_counter/tools.py` | gone; the same four tools are declared on the server |

`parts_counter/store.py` and `parts_counter/tools.py` are **deleted**, not kept alongside. Both of
those deletions and the data file's new path are recorded in this project's `CODEMAP.md`, which is
the completeness proof: every file in the finished project names the day that printed it, and a file
that stopped existing says so rather than quietly falling off the list. Keeping the old store around
"in case" would leave a second door into the stockroom with nobody at it, which is precisely the
thing the day is removing.

The data file itself is unchanged — the same six synthetic parts day 12 printed whole, at a new
path. It is not reprinted here, because a file printed twice in one project is a bug.

Now the file, whole:

`projects/02-parts-counter/parts_mcp/store.py`:

```python
# parts_mcp/store.py
"""The inventory, and the only code in this system that touches the file.

This is `parts_counter/store.py` moved behind the boundary, and two things changed on the way. Both
are fixes for failures day 2 caused on purpose, and neither was available before the move — that is
the point of the move.

**One writer.** A lock serialises every read-modify-write, so two callers issuing stock cannot each
read `240` and each write `239`. Day 2 lost ten parts out of twenty to exactly that, and a lock in
`parts_counter/` would have fixed it only for callers inside that one process. Here there is only
one process that opens the file at all, so the lock is the whole answer rather than half of it.

**Whole-file writes, or nothing.** The old version truncated the file and wrote into it, so a
reader arriving mid-write got an empty file and a `JSONDecodeError`. Here the new contents go to a
temporary file in the same directory and are then moved over the old one. `os.replace` is atomic:
a reader sees the old file or the new one, and there is no instant at which it sees neither.

All data is synthetic.
"""

from __future__ import annotations

import json
import os
import tempfile
import threading
import time
from pathlib import Path
from typing import Any

DATA_DIR = Path(__file__).with_name("data")
PARTS_FILE = DATA_DIR / "parts.json"

#: How many times to retry the final rename, and how long to wait between attempts.
#:
#: `os.replace` is atomic, and on Windows it can still be *refused*: if any other process holds a
#: handle on the destination — a sync client, an antivirus scanner, a file indexer — the call
#: raises `PermissionError: [WinError 5] Access is denied`. That is not a bug in this code and not
#: a race between our own threads; the lock above already excludes those. It is somebody else's
#: handle, it is transient, and the correct response is to wait a moment and try again rather than
#: to fail a write that was going to succeed.
_RENAME_ATTEMPTS = 8
_RENAME_BACKOFF_SECONDS = 0.02

#: One lock for **all** file access, reads included, because every write rewrites the whole file.
#: A per-part lock would be finer-grained and wrong: two writers to two different parts still write
#: the same document. And readers have to hold it too — on Windows, replacing a file another handle
#: has open raises `PermissionError`, so an unguarded read does not merely see stale data, it makes
#: the writer fail. `RLock`, not `Lock`, because `adjust` reads while already holding it.
_LOCK = threading.RLock()


class PartNotFound(KeyError):
    """No part with that number. Never guess at a near match on an inventory."""


def _read() -> dict[str, Any]:
    """Read the whole document. Always called with `_LOCK` held."""
    return json.loads(PARTS_FILE.read_text(encoding="utf-8"))


def _write_atomically(payload: dict[str, Any]) -> None:
    """Write to a temporary file in the same directory, then move it over the target.

    Same directory matters: `os.replace` is only atomic within one filesystem, and a temporary file
    in the system temp directory can easily be on another one.
    """
    fd, temp_path = tempfile.mkstemp(dir=DATA_DIR, prefix=".parts-", suffix=".tmp")
    try:
        with os.fdopen(fd, "w", encoding="utf-8") as handle:
            json.dump(payload, handle, indent=2)
            handle.write("\n")
            handle.flush()
            # Force the bytes to disk before the rename. Without this the rename can be durable
            # while the contents behind it are not, and a crash leaves a valid name over an empty
            # file — the same torn read, arriving after a power cut instead of during a write.
            os.fsync(handle.fileno())
        _replace_with_retry(temp_path, PARTS_FILE)
    except BaseException:
        Path(temp_path).unlink(missing_ok=True)
        raise


def _replace_with_retry(source: str, destination: Path) -> None:
    """`os.replace`, retried while Windows says another process holds the destination."""
    for attempt in range(1, _RENAME_ATTEMPTS + 1):
        try:
            os.replace(source, destination)
            return
        except PermissionError:
            if attempt == _RENAME_ATTEMPTS:
                # Give up loudly. A write that silently did not happen is the failure mode this
                # whole module exists to prevent.
                raise
            time.sleep(_RENAME_BACKOFF_SECONDS * attempt)


def all_parts() -> list[dict[str, Any]]:
    """Every part in the inventory."""
    with _LOCK:
        return _read()["parts"]


def find(query: str) -> list[dict[str, Any]]:
    """Parts whose number or name contains `query`, case-insensitively."""
    needle = query.strip().lower()
    return [p for p in all_parts()
            if needle in p["part_no"].lower() or needle in p["name"].lower()]


def get(part_no: str) -> dict[str, Any]:
    """One part by its exact number, or `PartNotFound`."""
    for part in all_parts():
        if part["part_no"].lower() == part_no.strip().lower():
            return part
    raise PartNotFound(part_no)


def adjust(part_no: str, delta: int) -> dict[str, Any]:
    """Add `delta` to a part's on-hand count. Serialised, and durable or not at all."""
    with _LOCK:
        payload = _read()
        for part in payload["parts"]:
            if part["part_no"].lower() == part_no.strip().lower():
                part["on_hand"] = part["on_hand"] + delta
                _write_atomically(payload)
                return dict(part)
        raise PartNotFound(part_no)
```

**Line by line:**

- The module docstring is the diff. Read it as one: *this is the old file, moved, with two changes,
  and here is the failure each change answers.* A file that arrived by moving should say where it
  came from, because otherwise the next reader has to reconstruct the history from a repository log
  that nobody opens. Day 12's version carried a docstring saying it was deliberately unfixed; this
  one carries the correction, and the pair of them is the argument in the code rather than only in
  the documents.
- `DATA_DIR = Path(__file__).with_name("data")` is **unchanged** from day 12, and it is unchanged
  for exactly the reason day 12 gave: the path resolves against this source file, not against
  whoever's working directory. It matters more now, not less, because this module is about to be
  launched as a subprocess by a client that has no idea where it lives.
- `import os`, `import tempfile`, `import threading`, `import time` are the four new imports and
  they map one-to-one onto the two fixes: `threading` is the lock, and `os` + `tempfile` + `time`
  are the atomic write and its retry. Nothing else in the file is new.
- `_RENAME_ATTEMPTS = 8` and `_RENAME_BACKOFF_SECONDS = 0.02` are module constants with a `#:`
  comment above them rather than magic numbers inside the loop. Two reasons: a number you can find
  by searching is a number somebody can change during an incident, and a comment above a constant
  is the only place in a Python module where a paragraph of *why* fits without interrupting a
  function.
- **The retry is not a second lock, and the comment says so in as many words.** This is the
  distinction most worth carrying out of the file. The lock excludes **our own threads**; the retry
  survives **somebody else's process** — a sync client, a backup agent, a file indexer, anything
  with a handle open on `parts.json` that has never heard of us and never will. On Windows,
  `os.replace` onto a destination another process holds open does not merely lose a race, it
  refuses outright with `PermissionError`. No lock of ours can exclude that process, because it did
  not ask our permission to open the file. So the two fixes are aimed at two different populations
  of interferers, and neither substitutes for the other.
- `_LOCK = threading.RLock()`, and the `#:` comment above it carries three decisions. **One lock
  for the whole module**, not one per part: two writers touching two different parts still rewrite
  the same document, so a per-part lock would be finer-grained and simply wrong. **Readers hold it
  too**, which looks like over-locking until you remember the previous bullet — on Windows an
  unguarded reader with the file open makes the *writer* fail, so a read is not a passive act here.
  And **`RLock` rather than `Lock`**, so that a public function which takes the lock and then calls
  another public function that takes it cannot deadlock against itself.
- On that last point, be exact, because the file's own comment is slightly ahead of the file. As
  written, `adjust` takes `_LOCK` and then calls the **private** `_read`, which does not take it —
  so nothing in the module re-enters the lock today, and swapping `RLock` for `Lock` leaves all
  five of this project's boundary tests green. It was checked rather than assumed; the transcript is
  in the hub §9. What `RLock` buys is the next edit: the moment somebody reasonably changes
  `adjust`'s `_read()` to the public `all_parts()`, or has `adjust` call `get`, a plain `Lock`
  deadlocks the process silently and an `RLock` does not. It is insurance against a change that has
  not happened, which is a defensible thing to pay one word for and a bad thing to claim as a fix
  for something happening now.
- `_read` keeps its one-line body and gains a docstring that states its contract: **always called
  with `_LOCK` held.** It does not acquire the lock itself, and that is deliberate — if it did,
  `adjust`'s single critical section would become two, with a gap between them exactly where day
  12's lost update lived. A function whose safety depends on its caller must say so, in the only
  place the caller will look.
- `_write` is gone and `_write_atomically` has taken its name-shaped place. The name is the review
  comment: nobody reading a call to `_write_atomically(payload)` can think it is an ordinary write.
- `tempfile.mkstemp(dir=DATA_DIR, prefix=".parts-", suffix=".tmp")` — **`dir=DATA_DIR` is the load-
  bearing argument.** `os.replace` is atomic only within one filesystem, and the default temporary
  directory is very often on another one; a rename across filesystems is a copy followed by a
  delete, which has a middle, and a middle is exactly what we are paying to remove. The `prefix`
  starts with a dot so the working file sorts out of the way and reads as debris rather than data,
  and `mkstemp` — not `NamedTemporaryFile` — because it returns an open file descriptor and a path
  and lets this function decide when the file is closed and where it goes.
- `os.fdopen(fd, "w", encoding="utf-8")` wraps the raw descriptor `mkstemp` handed back rather than
  opening the path a second time. Opening by path would leave the descriptor leaked and would race
  with anything that noticed the new filename in between. `encoding="utf-8"` is explicit for the
  same reason it was on day 12: Python's default text encoding is the platform's, and on Windows
  that is still not UTF-8.
- `json.dump(payload, handle, indent=2)` then `handle.write("\n")` — the same indented, newline-
  terminated shape day 12 wrote, so the file's bytes are unchanged by the move and `git diff` shows
  the move and nothing else. `json.dump` to a handle rather than `json.dumps` to a string, because
  the string version builds the whole document in memory a second time for no benefit.
- `handle.flush()` then `os.fsync(handle.fileno())`, in that order, **before** the `with` block
  closes. `flush` pushes Python's buffer into the operating system; `fsync` pushes the operating
  system's buffer onto the disk. Only the second one survives a power cut, and the comment names the
  failure precisely: without it the rename can be durable while the contents behind it are not, so
  a crash at the wrong instant leaves a perfectly valid filename over an empty file. That is day
  12's torn read again, arriving after a power cut instead of during a write — the same symptom
  from a different direction, which is why the same file has to answer both.
- `except BaseException:` — deliberately wider than `Exception`, so that a `KeyboardInterrupt` or a
  `SystemExit` between `mkstemp` and the rename still removes the temporary file. Then
  `Path(temp_path).unlink(missing_ok=True)` and a bare `raise`: clean up, change nothing about the
  error, let it out. `missing_ok=True` because the failure may have been the rename itself, in which
  case the temporary file is already gone under its new name. A wide catch that re-raises is a
  different animal from a wide catch that swallows, and this is the one place the wide version is
  right.
- `_replace_with_retry` is its own function rather than four lines inside `_write_atomically`,
  because it is the only part of the write that is about **other people's processes** and it reads
  as a unit: try, catch the one error Windows raises for this, wait a little longer each time, and
  on the last attempt let it out. `for attempt in range(1, _RENAME_ATTEMPTS + 1)` counts from one so
  that `attempt` reads as "which try is this" in both the sleep and the comparison.
- `except PermissionError:` and nothing wider. A missing directory, a full disk, a bad descriptor —
  every one of those is a real failure that retrying makes slower and no better, so they go straight
  out. Retry exactly the error you have a story for.
- `time.sleep(_RENAME_BACKOFF_SECONDS * attempt)` is linear backoff: a longer wait each time round.
  A fixed delay retried eight times is one delay tried eight times, which helps only if the
  interference is always the same length; growing the wait covers a short scan and a long one with
  the same eight attempts.
- `if attempt == _RENAME_ATTEMPTS: raise` — **give up loudly.** The comment carries the reason and
  it is the module's whole thesis: a write that silently did not happen is the failure this file
  exists to prevent. Retrying forever would convert an outage into a hang, and swallowing the error
  would convert it into day 12.
- `all_parts()` gains `with _LOCK:` and nothing else. Every public read in the module goes through
  it — `find` calls it, `get` calls it — so one lock statement in one function covers all three
  reads. That is the reward for day 12's `_read`/`_write` discipline: the move touched two functions
  rather than six.
- `adjust` gains `with _LOCK:` around its **entire** body, read included. The critical section
  starts before `payload = _read()` and ends after `_write_atomically(payload)`, which is exactly
  the window day 12 named — the gap between the read and the write, with nothing in it. There is
  now something in it.
- `return dict(part)` rather than `return part`, and this one is new since day 12. `part` is a
  dictionary **inside** the payload the function loaded; handing it out lets a caller mutate the
  store's loaded document after the lock has been released, from outside the lock, which is a
  brand-new race introduced by the very fix that removed the old one. A shallow copy at the
  boundary of the critical section costs one word and closes it.
- `raise PartNotFound(part_no)` stays **inside** the `with` block, after the loop. It could sit
  outside and behave identically; keeping it in means the whole function is one critical section
  with one exit story, and nobody reading it has to work out whether the failure path holds the lock.

### What it does now

Day 12 shipped `run.py race` so that you could watch parts disappear. The same subcommand is still
there, against the same fixture, with the same two threads — only the module it imports changed.
Run it and read every line:

**Line by line:**

- `parts unaccounted  : 0`. Twenty spark plugs were issued and the count moved by twenty. Day 12's
  four runs of this exact command reported 10, 8, 9 and 9 parts lost; this is the same command, the
  same threads and the same file, so the difference is the lock and nothing else.
- `reads that crashed : []`. Empty, where day 12 collected one to three `JSONDecodeError`s every
  single run. That is the second fix reporting separately from the first: no reader saw a

- `restored to : 240` — the demonstration still puts the fixture back, so it can be run as often as
  you like. Confirm rather than assume it: `git status --porcelain parts_mcp/` afterwards.
- **Run it three times.** The number that mattered on day 12 was not "ten lost", it was "a different

  consecutive runs on this machine reported `0` and `[]` each time, and three more at double the
  contention — forty issues per thread — reported `expected 160, actual 160, lost 0, errors []`.

And what the two fixes cost, measured rather than guessed: fifty reads and one hundred writes
through the boundary's own store, timed on this machine.

```console
$ uv run --frozen python -c "
import time, warnings; warnings.filterwarnings('ignore')
from parts_mcp import store
n = 50
t0 = time.perf_counter()
for _ in range(n):
    store.all_parts()
t1 = time.perf_counter()
for _ in range(n):
    store.adjust('BLT-0310', 1); store.adjust('BLT-0310', -1)
t2 = time.perf_counter()
print(f'{n} reads under the lock      : {(t1-t0)*1000/n:.2f} ms each')
print(f'{n*2} writes, temp+fsync+replace: {(t2-t1)*1000/(n*2):.2f} ms each')
print('bytes rewritten per write   :', store.PARTS_FILE.stat().st_size)
print('belt kit back to            :', store.get('BLT-0310')['on_hand'])
"
50 reads under the lock      : 0.10 ms each
100 writes, temp+fsync+replace: 2.48 ms each
bytes rewritten per write   : 1161
belt kit back to            : 0
```

**Line by line:**

- A read costs a tenth of a millisecond and a write costs about two and a half. **A write is roughly
  twenty-five times a read**, and almost all of that gap is `os.fsync` waiting for the disk to
  admit it really has the bytes. That is the price of durability and it is not a bug to be tuned
  away; it is what "or not at all" costs.
- `1161` bytes rewritten per write — the identical number day 12 measured, because the document is
  the same document. The move changed who may write it and how the write lands, and changed nothing
  about how much of it gets written.
- The adjustments are paired `+1` then `-1` on the belt kit, so the fixture ends where it started,
  and the last line proves it rather than asserting it. Every transcript in this day leaves
  `parts.json` byte-identical.
- Multiply the two numbers together and you have the boundary's ceiling: **one lock, and about two
  and a half milliseconds per write, is roughly four hundred writes per second for the whole
  system** — every replica, every agent, every caller, because they all queue at one hatch. That is
  the number "In production" is about.

## When it breaks

The lock covers our own threads and nothing else, and this is what the outside world looks like when
it arrives. Observed on this machine while building this store, with reads left **outside** the lock:

```traceback
  File ".../parts_mcp/store.py", line 66, in _write_atomically
    os.replace(temp_path, PARTS_FILE)
PermissionError: [WinError 5] Access is denied: '...\parts_mcp\data\.parts-8ympgtow.tmp' -> '...\parts_mcp\data\parts.json'
```

Read the message carefully, because it is lying about the direction of the problem. *Access is
denied* sounds like a permissions bug — a file marked read-only, a service account without rights —
and people spend an evening on `icacls` before finding out that on Windows `os.replace` fails if
**any** handle is open on the destination. Two entirely different things cause it here. One is our
own readers, which is why reads went under the same lock; the other is a process we do not own,
because this repository sits inside a folder a sync client watches and that client opens
`parts.json` on nobody's schedule but its own. The first is fixed by the lock. The second cannot be,
and is fixed by the bounded retry — which is why the file carries both and says which is which.

## In production

**What a senior writes instead.** SQLite, in write-ahead-logging mode, and they reach for it before
they write the first line of `_write_atomically`. It is in the standard library, it needs no server,
and it gives you the two things this file spent forty lines hand-rolling — a transaction, so a read
and a write are one indivisible act, and readers that do not block writers. The hand-rolled version
here exists because you cannot judge what a database is buying you until you have paid for it
yourself once; that is this curriculum's build-first rule, not a recommendation to ship this.

**What degrades at scale.** One lock and a whole-file rewrite means **about four hundred writes per
second, total, for every caller in the system** — measured above at 2.48 ms per write on six parts
and 1161 bytes. That number does not stay still as the shop grows: at ten thousand parts the
document is on the order of two megabytes, so every adjustment serialises two megabytes of encode,
`fsync` and rename while every read in the process waits behind it. The reads themselves are a tenth
of a millisecond and they will not be, because they are queued behind the writes. The failure is
not an error; it is a stock check that used to be instant and now is not, with no single change to
blame.

**The review comment.** "Good — the lock is on the reads too and the temp file is in the same
directory, which is the pair people usually get half right. Three things. The docstring on `_LOCK`
says `RLock` is needed because `adjust` reads while holding it, but `adjust` calls `_read`, not
`all_parts`, so nothing re-enters today; keep the `RLock` and reword the comment to say it is
guarding the next edit. `_RENAME_ATTEMPTS = 8` with linear backoff gives up after a bounded wait —
please log the retries, because right now a slow sync client is invisible until the day it exceeds
eight. And write down the write ceiling this design has, in `PROJECT.md`, before somebody discovers
it during an incident."

**The interview question.** "You have a service that keeps state in a file and you have just put a
`threading.Lock` around every read and write of it. Tell me exactly which failures that fixes and
which it does not. Then tell me why the temporary file has to be in the same directory as the
target, what `os.fsync` buys you that closing the file does not, and what you would do about a
`PermissionError` from the rename on Windows."
