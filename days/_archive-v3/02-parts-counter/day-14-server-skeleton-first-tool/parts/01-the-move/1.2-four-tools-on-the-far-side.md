## One-line answer

The four things this boundary will do are declared by writing four ordinary Python functions and
decorating them: the name comes from the function, the argument schema from the type hints and the
description from the docstring — the same derivation ADK performs for a plain function — and the
one new thing to get wrong is that the decorator must be **called**, or the SDK refuses at import
with a message that tells you exactly which key you left off.

## The idea

There is a sign screwed to the wall above the hatch. It lists what you may ask for and how to ask:
*give me a part number and I will tell you how many are on the shelf* · *give me a part number and
I will tell you which bin it is in* · *give me a word and I will tell you what matches* · *tell me a
part number and a number to add or take away, and I will change the book.* Four lines. Nobody
standing at the hatch has ever seen the storeman work, and nobody needs to: the sign is the entire
interface between the two sides of the wall.

Now the thing worth noticing about that sign. Nobody wrote it separately. Somebody watched the
storeman, wrote down what they actually do, and screwed that to the wall — so the sign cannot
describe a service the storeman does not provide, and it cannot quietly go out of date while the
storeman changes their habits. The cost of getting it that way is that the sign can only say things
the storeman's own behaviour already contains. If the storeman has a rule in their head — *I only
change the book when somebody has clearly asked me to* — and they have never said it out loud, it
is not on the sign, and the person at the hatch will never learn it.

That is exactly the arrangement on the far side of this project's boundary. Four Python functions
sit in `parts_mcp/server.py`, which **day 13 printed whole** — the file, its `FastMCP` construction,
its `stateless_http=True`, and its `__main__` block are all there, at
`days/02-parts-counter/day-13-mcp-stateless-core/`, and this part does not reprint any of it. What
this part is about is the four function bodies and the four lines above them, because those four
lines are how a plain Python function becomes something a model on the other side of a process
boundary can ask for.

The mechanism is one you have already met. In P01 a plain function was handed to an ADK agent and a
declaration appeared: a name, a description, a JSON Schema for the arguments, all read off the
function object itself. Nothing was written twice, so nothing could drift, and the price was that
anything a declaration can carry but a function cannot express had nowhere to live. MCP's server
SDK does the same job with the same trade, one process further away.

> **Recap — a tool declaration is derived, not written.** The model never sees your code. It sees a
> name, a prose description and a JSON Schema for the arguments, and the framework builds all three
> by reading the function: the name from `__name__`, the schema from the type hints and defaults,
> the description from the docstring. A parameter with no type hint produces a property with no
> `type`, which constrains nothing; and a per-parameter description, which a hand-written
> declaration can carry, has nowhere to live in a derived one — so guidance about an argument
> belongs in the docstring, where the derivation will read it.
> Self-contained version: `PRIMER.md` §4.
> Deep version, if you have the full plan:
> `days/01-ask-desk/day-07-functiontool-what-adk-does/parts/01-what-the-wrapper-reads/1.2-the-type-hints-are-the-schema.md`

The new thing today is small and it stops the process from starting, which is the best kind of new
thing: `@mcp.tool` and `@mcp.tool()` are not the same, and only one of them is a decorator.

## The mechanism

The whole of `parts_mcp/server.py` was printed by **day 13**, at
`days/02-parts-counter/day-13-mcp-stateless-core/`. Only the four tool regions are reproduced here,
as marked regions of that file:

```python
# projects/02-parts-counter/parts_mcp/server.py — the four tool declarations
# ── unchanged from day 13: the module docstring, the imports, and
#    mcp = FastMCP("parts-mcp", stateless_http=True) ──


@mcp.tool()
def find_part(query: str) -> dict[str, Any]:
    """Find parts whose number or name matches a query. An empty list is a valid answer."""
    hits = store.find(query)
    return {"query": query, "count": len(hits),
            "hits": [{"part_no": p["part_no"], "name": p["name"]} for p in hits]}


@mcp.tool()
def stock_level(part_no: str) -> dict[str, Any]:
    """Return how many of one part are on hand, and whether that is below its reorder point."""
    try:
        part = store.get(part_no)
    except store.PartNotFound:
        return {"error": f"no part numbered {part_no!r}",
                "known": [p["part_no"] for p in store.all_parts()]}
    return {"part_no": part["part_no"], "on_hand": part["on_hand"], "unit": part["unit"],
            "reorder_at": part["reorder_at"], "below_reorder": part["on_hand"] <= part["reorder_at"]}


@mcp.tool()
def bin_location(part_no: str) -> dict[str, Any]:
    """Return the bin a part is stored in, so somebody can walk to it."""
    try:
        part = store.get(part_no)
    except store.PartNotFound:
        return {"error": f"no part numbered {part_no!r}",
                "known": [p["part_no"] for p in store.all_parts()]}
    return {"part_no": part["part_no"], "bin": part["bin"], "name": part["name"]}


@mcp.tool()
def adjust_stock(part_no: str, delta: int) -> dict[str, Any]:
    """Change the on-hand count of a part by delta. Use a negative delta to issue stock.

    Only call this when the person has clearly asked for the count to change. Reading a level is
    stock_level; this is the tool that alters the record.
    """
    try:
        before = store.get(part_no)["on_hand"]
        part = store.adjust(part_no, delta)
    except store.PartNotFound:
        return {"error": f"no part numbered {part_no!r}",
                "known": [p["part_no"] for p in store.all_parts()]}
    return {"part_no": part["part_no"], "before": before, "after": part["on_hand"],
            "unit": part["unit"]}


# ── unchanged from day 13: the __main__ block that calls mcp.run(transport="stdio") ──
```

**Line by line — recap depth for the derivation, which P01 day 7 owns.** What each line is
declaring, and the failure it prevents:

| Line | What it declares, and the failure it prevents |
| --- | --- |
| `@mcp.tool()` | Registers the function with the server's tool manager, which is what makes it appear in `tools/list`. Without it the function is ordinary Python: importable, callable, and invisible to every client. |
| `def find_part(...)` | The function's `__name__` **is** the tool name on the wire. Rename the function and every client's saved tool name breaks, silently, at the next call rather than at the rename. |
| `query: str` | The hint becomes `{"type": "string"}` in the `inputSchema`. Drop the hint and the property has no `type` at all, which constrains nothing and lets a model send a list where a word belongs. |
| `delta: int` | Becomes `{"type": "integer"}`. It shapes what the model is asked for and checks **nothing** at runtime — day 12 watched a string `"-1"` reach the arithmetic three frames away. |
| `-> dict[str, Any]` | Becomes an `outputSchema` — an open object. It is a promise about the answer's shape, and it is what lets a client hand back `structuredContent` as well as text. Part 2.1 reads the emitted schema. |
| `"""...An empty list is a valid answer."""` | The docstring **is** the description the model reads. Without that sentence a model given zero hits invents a plausible part number rather than reporting nothing found. |
| `"""...Only call this when the person has clearly asked..."""` | The one place guidance about *when* to call a tool can live in a derived declaration. There is no per-parameter or per-tool policy field to put it in; the docstring is it. |
| `except store.PartNotFound: return {"error": ...}` | An unknown part comes back as an answer, not an exception, so the model can read it and correct itself. Part 2.2 is entirely about why that distinction is in the specification. |
| `"known": [p["part_no"] for p in store.all_parts()]` | The error carries the six valid part numbers. An error that says only "not found" makes the model guess again; an error that lists the alternatives makes it choose. |
| `store.find` / `store.get` / `store.adjust` | Every tool goes through the store printed in part 1.1, so every read and write is inside the lock. A tool that opened `parts.json` itself would be a second door with nobody at it. |

The tools as the server itself reports them, listed through the SDK with no client and no model
anywhere in the path:

**Line by line:**

- Four tools, in **declaration order** — `find_part`, `stock_level`, `bin_location`,
  `adjust_stock` — not alphabetical. The order is the order the decorators ran at import, which is
  the order the lines appear in the file. Nothing in the protocol promises that, so nothing you
  write should depend on it; it is worth knowing only so that a reordered listing does not look like
  a bug.
- The `description` on each is the first line of that function's docstring, character for character,
  truncated here to fit the terminal. Nobody typed those descriptions into a declaration. They are
  the docstrings, read off `__doc__`.
- `mcp.list_tools()` is awaited — the whole MCP server API is asynchronous, because on the far side
  of it there is a transport. That is worth meeting now, in one line at a terminal, rather than for
  the first time inside a client.
- **No model was involved, and no key was needed.** This is the server answering a question about
  itself, in this process. Everything in this day runs that way.

### The one new thing to get wrong

`mcp.tool` is a method that **returns** a decorator. `@mcp.tool()` calls it and decorates the
function below with what came back. `@mcp.tool` — no parentheses — hands the function itself to
`mcp.tool` as its first positional argument, which is a completely different thing and, in this SDK,
a hard error at import:

```traceback
Traceback (most recent call last):
  File "<string>", line 1, in <module>
  File "C:\...\projects\02-parts-counter\parts_mcp\server.py", line 33, in <module>
    @mcp.tool
     ^^^^^^^^
  File "C:\...\.venv\Lib\site-packages\mcp\server\fastmcp\server.py", line 505, in tool
    raise TypeError(
TypeError: The @tool decorator was used incorrectly. Did you forget to call it? Use @tool() instead of @tool
```

*Caused deliberately on this machine on 2026-09-10 by removing the parentheses from `find_part`'s
decorator, then restoring the file. The absolute path prefixes are elided as `C:\...`; that elision
is the only edit made to any transcript in this day.*

**Line by line:**

- The error is raised **at import**, inside the module-level decorator line, before the server
  object has any tools and long before anything reaches a transport. That is the good case: a
  process that will not start is a process nobody deploys.
- `raise TypeError` inside `FastMCP.tool` means the SDK is checking for this on purpose. It could
  have let Python produce its own confusing failure later — the decorated name would have been bound
  to something that is not a function — and instead it inspects what it was handed and says what you
  meant.
- The message names the fix in the message: *Use `@tool()` instead of `@tool`*. Read the whole line
  before searching for it; the answer is usually in the sentence.
- Notice which line the traceback points at — `parts_mcp/server.py`, line 33, the decorator itself
  — and not the function below it. The decorator runs when the module is imported, not when the
  tool is called.

## When it breaks

The parentheses are the error you cause on purpose. The one you will actually hit is quieter, and it
comes from the same fact — the declaration is derived — pointing the other way:

```console
$ uv run --frozen python -c "
import asyncio, warnings; warnings.filterwarnings('ignore')
from parts_mcp.server import mcp
async def main():
    await mcp.call_tool('stock_levl', {'part_no': 'BRK-0143'})
asyncio.run(main())
"
mcp.server.fastmcp.exceptions.ToolError: Unknown tool: stock_levl
```

Somebody renames `stock_level` to `check_stock` because it reads better, ships it, and every client
that had the old name in a saved configuration starts failing with a message about a tool nobody
ever wrote. The name on the wire is `__name__`, and `__name__` is whatever the `def` line says, so a
rename is a public interface change wearing the clothes of a tidy-up. The smallest fix is to keep
the function name and change nothing else; the real fix is to treat tool names the way you treat URL
paths, and to notice at review time that a rename in this file is not local.

## In production

**What a senior writes instead.** The same four functions, and then two things this file does not
have. First, an explicit `title` and `annotations` on each declaration — the specification has fields
for a human-readable name and for behavioural hints such as whether a tool only reads, and a derived
declaration leaves both empty unless you pass them. Second, `adjust_stock` behind something that can
refuse: an idempotency key so the same adjustment applied twice does not move the count twice, and
an identity so the record can answer *who*. Three reads and one write in one undifferentiated list
is the shape day 12 already objected to, and moving it behind a boundary did not fix it.

**What degrades at scale.** Four tools is a list a model reads comfortably. The number worth knowing
is that **every tool's full declaration is sent to the model on every single turn** — name,
description and both schemas, for all of them. At four tools that is a few hundred tokens; a server
that grows to forty tools is sending forty declarations before the user's question is even read,
on every turn of every conversation, and the model's accuracy at choosing between them falls as the
list grows. The fix is not shorter docstrings — day 12 showed what the sentences are load-bearing
for — it is fewer tools per agent.

**The review comment.** "The docstrings here are the model-facing API and they read like it, which
is right. Two asks. Put `title` on all four and `annotations` marking the three reads as
non-destructive, because clients use those to decide what to show a user and what to confirm before
running. And add a test that asserts the four tool **names**, so that a rename fails in CI rather
than in whatever saved configuration somebody has on their laptop."

**The interview question.** "You are exposing Python functions as MCP tools. Walk me through
everything the model actually receives for one of them, and say where each piece came from in the
source. Then tell me what happens to a client that saved a tool name last month if I rename the
function this month, and what you would put in place so I find that out before the client does."
