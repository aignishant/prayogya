## One-line answer

P01 handed its agent four plain Python functions and the framework wrapped each one, so the tool list
was a decision made **when the file was written**; this project hands its agent a single **toolset**,
so the tool list is a question **answered when the agent runs** — which buys a boundary whose tools
can change without this project being edited, and costs a start-up failure that a list of imports
cannot have.

## The idea

There was a time when you knew the shelves. You wanted a timing belt kit, you walked down the far
aisle, you counted what was in the bin, and you came back. Then the stores were put in one person's
hands and you started going to the hatch instead — you no longer touched the shelves, but you were
still standing in the same building, watching the same person turn around and look.

Today you do not walk over at all. There is an extension number on a card by the phone. You ring it,
somebody picks up, and you ask. That is the whole change, and it is smaller than it sounds and larger
than it looks.

What it buys you is that **you no longer have to know what is on the shelves**. The parts desk can
move a bin, take on a new line, retire an old one, split "fasteners" into two categories — and
nothing about your morning changes, because your morning consists of ringing a number and asking. You
were never holding a list. You were holding a number, and the list was always theirs. The first thing
you say on the call is not "give me a timing belt kit"; it is closer to "what have you got?", and
that question is answered fresh every time you ask it.

What it costs you is that **the phone can ring out**. When you walked the aisles, the aisles were
there. When you went to the hatch, the hatch was in the building you were standing in. A number on a
card is a promise that somebody will pick up, and a promise is a different kind of thing from a
shelf. If nobody picks up, you do not get a shorter list — you get *no* list, and the difference
between "the desk stocks nothing" and "the desk did not answer" is not visible from where you are
standing with a receiver against your ear.

Hold that last sentence, because it is the failure this whole day is built around and it arrives in
part 2.2. An agent that was handed a list of four functions cannot end up with three. An agent that
was handed a number to ring can end up with none, and — this is the part that catches people — it can
end up with none *without anything raising*, and then answer your question anyway, out of its own
head, in a confident voice.

So the terms, as they arrive. A **toolset** is an object you give an agent in place of individual
tools, which the framework asks for a tool list at run time rather than reading at import. An **MCP
client** is the half of the protocol that lives on this side of the boundary: it opens the connection,
performs whatever the server expects, asks for the tool list, and forwards each call. **Connection
params** are the object that says *how to reach the server* — either a command to launch, or a URL to
post to — and they are the only thing that differs between the two ways this project can reach the
same four tools. This part is one file: the file that turns a number on a card into an object an
agent can be handed.

## The mechanism

`projects/02-parts-counter/parts_counter/util/mcp.py`, whole file — new today, and the only file in
this project that knows how to reach the boundary:

```python
# parts_counter/util/mcp.py
"""The client side: how this project reaches tools that now live in another process.

Days 1 and 2 had `parts_counter/tools.py` — plain Python functions the agent called in its own
process. Those functions are gone. The same four tools are now behind `parts_mcp/`, and what stands
in their place is a **toolset**: an object the agent is given that fetches the tool list from the
server at run time and forwards each call across the boundary.

The difference that matters is not the syntax. It is that this project no longer knows what tools
it has until it asks. `tools=[find_part, stock_level, ...]` was a list decided when the file was
written; `tools=[toolset]` is a question answered when the agent runs. That buys a boundary whose
tools can change without this project being edited, and it costs a startup failure mode that a
list of imported functions does not have — if the server is not there, there are no tools, and the
agent will answer from nothing rather than refuse.

Two connection shapes are offered because days 6 and 7 need both, and they are the same server:

  * **stdio** — the client launches the server as a subprocess and speaks over its pipes. One
    client, one server, same machine, no port and no network.
  * **Streamable HTTP** — the server is already running and reachable at a URL. Many clients, many
    replicas, and the shape a container is deployed in.

Verified against mcp 1.30.0 and google-adk 2.8.0 on 2026-09-10.
"""

from __future__ import annotations

import sys
from pathlib import Path

from google.adk.tools.mcp_tool import (
    McpToolset,
    StdioConnectionParams,
    StreamableHTTPConnectionParams,
)
from mcp import StdioServerParameters

PROJECT_ROOT = Path(__file__).resolve().parent.parent.parent

#: Where the server listens when it is run over HTTP. `/mcp` is the SDK's default path, and it is
#: written out here rather than assumed, because a client that guesses the path fails with a 404
#: that says nothing about what it was looking for.
DEFAULT_HTTP_URL = "http://127.0.0.1:8090/mcp"


def over_stdio() -> McpToolset:
    """A toolset that launches `parts_mcp` as a subprocess and speaks over its pipes.

    `sys.executable` rather than the string `"python"`: the interpreter running this code is the
    one with this project's dependencies installed, and the bare name resolves through PATH to
    whatever a shell happens to find — which is the P00 day 1 failure, arriving here as a server
    that starts and immediately cannot import `mcp`.
    """
    return McpToolset(
        connection_params=StdioConnectionParams(
            server_params=StdioServerParameters(
                command=sys.executable,
                args=["-m", "parts_mcp.server"],
                # The subprocess inherits neither the working directory nor the environment by
                # accident; both are stated, so the server starts the same way from anywhere.
                cwd=str(PROJECT_ROOT),
            ),
            timeout=20,
        ),
    )


def over_http(url: str = DEFAULT_HTTP_URL) -> McpToolset:
    """A toolset that connects to an already-running server at `url`.

    Nothing here launches anything. If the server is not up, this fails at the first tool listing
    rather than at import, which is why `run.py check` does not build one.
    """
    return McpToolset(
        connection_params=StreamableHTTPConnectionParams(url=url, timeout=20),
    )
```

**Line by line:**

- **The day numbers in that docstring are this project's own, not the curriculum's.** "Days 1 and 2"
  are `days/02-parts-counter/day-11-kit/` and `day-12-why-data-behind-boundary/`; "days 6 and 7" are
  `day-16-transports-stdio-http/` and today. The project folder has to be readable by somebody handed
  only `projects/02-parts-counter/`, and *P02 day 6* is a thing they can find in it. Translate when
  you read the file; do not translate when you read the repository.
- `from google.adk.tools.mcp_tool import (McpToolset, StdioConnectionParams,
  StreamableHTTPConnectionParams)` — three names from one module, and **that module is where the
  version wall of day 13 stands**. Under an `mcp` 2.x install this import does not fail with a
  version message; the package's `__init__.py` swallows the underlying `ModuleNotFoundError` and
  leaves `__all__` empty, so the error names `McpToolset` and never says why. That is day 13's
  subject — `days/02-parts-counter/day-13-mcp-stateless-core/` — and the reason this project depends
  on `google-adk[mcp]==2.8.0` with the extra spelled out.
- `from mcp import StdioServerParameters` — **the one import in this file that is not ADK.** It comes
  from the MCP Python SDK itself, and it is worth knowing why: the *command to launch a server* is
  not an ADK idea, it is a protocol-SDK idea, and ADK's `StdioConnectionParams` wraps it rather than
  reinventing it. Practically, this is the import people get wrong: `from google.adk.tools.mcp_tool
  import StdioServerParameters` is an `ImportError`, and the fix is not to hunt for a different ADK
  name but to notice which library owns the concept.
- `PROJECT_ROOT = Path(__file__).resolve().parent.parent.parent` — three `.parent`s, counted from
  `parts_counter/util/mcp.py`: `util/`, then `parts_counter/`, then the project folder. `.resolve()`
  first, so a symlinked checkout does not count a different number of levels. This is used for one
  thing only, and it is the `cwd=` below.
- `DEFAULT_HTTP_URL = "http://127.0.0.1:8090/mcp"` — the path is written out rather than assumed.
  `/mcp` is the SDK's default mount for the Streamable HTTP app, and a client that posts to `/`
  instead gets a 404 whose body says nothing about MCP at all. The port is the one day 16 used for
  the same server; `127.0.0.1` and not `0.0.0.0`, because a development server that binds every
  interface is a development server reachable from the coffee shop's wifi.
- `def over_stdio() -> McpToolset:` and `def over_http(...) -> McpToolset:` — **two functions, one
  return type, and no flag.** The temptation is one function with `http: bool = False`; the reason
  not to is that the two do genuinely different things — one *launches a process*, the other *dials
  an address* — and a boolean parameter hides that difference behind a word that reads like a
  formatting option. Day 18's container wants `over_http` and nothing else, and it should not have to
  pass `True` to say so.
- `McpToolset(connection_params=...)` — **`connection_params` is keyword-only.** Not a convention:
  the signature has a bare `*` before it, so `McpToolset(params)` is a `TypeError` and there is no
  positional form to fall back on. Read from the installed `google-adk` 2.8.0 source on this machine
  on 2026-09-10, verbatim:

```text
  def __init__(
      self,
      *,
      connection_params: (
          StdioServerParameters
          | StdioConnectionParams
          | SseConnectionParams
          | StreamableHTTPConnectionParams
      ),
```

  Four accepted types, and this project uses two of them. `SseConnectionParams` is the transport the
  protocol deprecated — day 16's subject, and marked 🅿️ in the plan. A bare `StdioServerParameters`
  is also accepted, without the `StdioConnectionParams` wrapper; it is not used here because the
  wrapper is the only place `timeout` can be set.
- `StdioConnectionParams(server_params=StdioServerParameters(...), timeout=20)` — **two objects, not
  one, and the nesting is the point.** The inner one is the MCP SDK's and describes *a process*:
  command, args, cwd, environment. The outer one is ADK's and describes *ADK's patience with that
  process*. Its `timeout` defaults to `5.0` seconds, read from the model fields on this machine, and
  five seconds is a fine number for a server that is already warm and a cruel one for a cold Python
  interpreter importing a framework on a laptop that is also running a sync client. `20` is this
  project's number, chosen for the machine the day was written on.
- `command=sys.executable` — **the single most important line in this file**, and the whole of P00
  day 1 arriving with a bill. `sys.executable` is an absolute path to *the interpreter currently
  executing this line*, which is by construction the one with `mcp` and `google-adk` installed. The
  string `"python"` is not a path; it is a name that is resolved by walking `PATH`, first match wins,
  and nothing announces that there was a choice. Under `uv run` the two happen to agree. Under a
  service manager, a scheduled task, an IDE's run button or a `Dockerfile`'s `CMD`, they do not, and
  *When it breaks* below is that disagreement, caused on purpose.

  > **Recap — a name is not a path.** `python` is resolved by search order: the machine walks a list
  > of directories and takes the first hit, so the same word means different programs in different
  > shells, and nothing tells you a choice was made. An absolute path skips the search entirely.
  > Self-contained version: `PRIMER.md` §1.
  > Deep version, if you have the full plan:
  > `days/00-foundry/day-01-machine-four-pythons/parts/02-the-project/2.2-the-two-commands-that-disagree.md`
- `args=["-m", "parts_mcp.server"]` — `-m` runs the module by *import path*, which means the import
  system finds it the same way `import parts_mcp.server` would, rather than a file path that is
  correct only relative to somewhere. Pair that with the next line.
- `cwd=str(PROJECT_ROOT)` — **stated, never inherited.** A subprocess started with no `cwd` inherits
  the parent's, so the server would start correctly when you ran `run.py` from the project folder and
  fail with `No module named parts_mcp` when you ran the same command from one directory up. That is
  a failure that depends on where your shell happened to be, which is the worst kind: it works on
  your machine every time, until the day it does not.
- `env=` is **not** passed, and the omission is deliberate rather than forgotten. `StdioServerParameters`
  defaults `env` to `None`, which means the child inherits this process's environment — including
  `GOOGLE_API_KEY`. That is fine today, because `parts_mcp` never reads it, and it is exactly the
  line day 18 will have to revisit when the boundary runs in its own container with its own secrets.
  Blast radius is not a thing you notice; it is a thing you go and look at.
- `StreamableHTTPConnectionParams(url=url, timeout=20)` — the whole of `over_http`. No command, no
  working directory, no process: **this function launches nothing**, and if the server is not already
  up there is no subprocess to blame. Its other defaults, read on this machine: `headers=None`,
  `sse_read_timeout=300.0`, `terminate_on_close=True`. The 300-second read timeout is a different
  number from the 20-second connect-and-call timeout and they are not interchangeable — one bounds
  *reaching* the server, the other bounds *waiting on a stream it has opened*.
- **Neither function contacts anything.** Both build an object and return it. Nothing is launched,
  nothing is dialled, and no error is possible here that is not a typo. That is why part 2.2's
  failure lands where it does, and it is worth predicting now: if construction is free, where does
  the cost of a dead server show up?

### The name in the documentation that is not the name in the library

ADK 2.8.0 ships **two** spellings of this class, and one of them is deprecated. From the installed
source on this machine, verbatim:

```text
class MCPToolset(McpToolset):
  """Deprecated name, use `McpToolset` instead."""

  def __init__(self, *args, **kwargs):
    warnings.warn(
        "MCPToolset class is deprecated, use `McpToolset` instead.",
        DeprecationWarning,
        stacklevel=2,
    )
    super().__init__(*args, **kwargs)
```

It is a subclass, not an alias — `MCPToolset is McpToolset` is `False` and `issubclass(MCPToolset,
McpToolset)` is `True` — so code written against the old name keeps working and says so once:

```console
$ uv run --frozen python -W default -c "
import warnings
from google.adk.tools.mcp_tool import MCPToolset, StreamableHTTPConnectionParams
with warnings.catch_warnings(record=True) as w:
    warnings.simplefilter('always')
    MCPToolset(connection_params=StreamableHTTPConnectionParams(url='http://127.0.0.1:8099/mcp'))
    for x in w:
        if issubclass(x.category, DeprecationWarning):
            print(x.category.__name__ + ':', x.message)
"
DeprecationWarning: MCPToolset class is deprecated, use `McpToolset` instead.
```

And here is the trap, because you will meet the capital spelling and conclude the library is wrong.
The framework's own documentation page, `https://adk.dev/tools-custom/mcp-tools/`, fetched
2026-09-10, carries examples in several languages, and the two spellings belong to two of them:
`from google.adk.tools.mcp_tool import McpToolset` is the Python one, and `import {LlmAgent,
MCPToolset} from "@google/adk";` is the TypeScript one. **`MCPToolset` in a code sample is a signal
about which language you are reading, not about which name to type in Python.** Note also that
`https://adk.dev/tools/mcp-tools/` redirects to `.../tools-custom/mcp-tools/`; a bookmark from a
tutorial written six months ago lands one hop away from the page you want.

## When it breaks

Somebody deploys the boundary behind a supervisor — a systemd unit, a scheduled task, an IDE run
configuration, anything that is not `uv run` — and writes `command="python"` because that is what the
tutorial had. Locally it worked, because inside `uv run` the bare name resolves to the project's own
interpreter. Outside it, on the same machine, in the same folder, it resolves somewhere else
entirely, and the server dies before it has said one word of protocol:

```console
$ python -c "import shutil; print('which python ->', shutil.which('python'))"
which python -> ...\AppData\Local\Programs\Python\Python312\python.EXE

$ python -c "
import subprocess
p = subprocess.run(['python','-c','import mcp; print(mcp.__file__)'], capture_output=True, text=True)
print('rc', p.returncode); print(p.stdout.strip() or p.stderr.strip())
"
rc 1
Traceback (most recent call last):
  File "<string>", line 1, in <module>
ModuleNotFoundError: No module named 'mcp'
```

*(Both run on this machine on 2026-09-10, from `projects/02-parts-counter`, with the home-directory
prefix elided. Inside `uv run --frozen`, `shutil.which("python")` on the same machine returns
`...\projects\02-parts-counter\.venv\Scripts\python.EXE` — which is why this never fails in the shell
where you tested it.)*

Somebody shipped that on a Friday. What they saw at eleven at night was not `ModuleNotFoundError`,
because the child's stderr goes to the client's error log and the client's own message is about a
connection — part 2.2 has the wording. The smallest fix is one word: `sys.executable`. The general
version of the fix is the habit: **anything that launches a program names the file, not the word.**

## In production

**What a senior writes instead.** They put the connection choice behind configuration rather than
behind a function name — `over_stdio()` in development, `over_http(os.environ["PARTS_MCP_URL"])` in a
container — and they add one thing this file does not have: a **tool filter**. `McpToolset` takes
`tool_filter`, a list of names or a predicate, and a senior narrows the boundary's four tools to the
two an agent is allowed to use rather than trusting the instruction text to hold the line. This
project deliberately does not, because the whole four are the subject, and P29 is where per-agent
tool sets get their own week.

**What degrades at scale.** `over_stdio` launches **one server process per toolset**, and the toolset
is built inside `build_counter()`, so it is one process per agent construction — and `McpToolset`'s
`tool_list_cache_ttl_seconds` defaults to `None`, meaning no cache, so every one of them pays for a
fresh `tools/list` round trip. Measured on this machine on 2026-09-10, three toolsets in one process:
constructing the object costs **0.0001 s**, and the launch-plus-handshake-plus-list behind the first
`get_tools()` costs **1.343 s, 1.114 s and 1.067 s**. So a hundred requests that each build their own
agent spend on the order of **two minutes** starting interpreters, before a single question reaches a
model. `over_http` is the answer — one already-warm server, no fork — and it is why day 18's container
runs the boundary as its own service.

**The review comment.** "`over_stdio` is fine for the CLI, but `build_counter()` calls it by default,
so every construction of the agent forks an interpreter and nothing ever reaps it. Please make the
toolset a parameter with no default on the server path, and give the HTTP one an env-var URL —
otherwise the first load test we run will be a load test of `subprocess`."

**The interview question.** "Your agent's tools come from a remote toolset rather than a list of
functions. Name one thing that gets easier and one class of bug that becomes possible, and say at
which point in the process's life each of them shows up."
