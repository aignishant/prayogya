## One-line answer

One question produces a *sequence* of events, not one reply — here three of them, of which exactly
one is the answer — and the two that are not carry an empty string where their text would be, so a
client that renders text and nothing else shows a blank screen for the entire period the desk is
doing the work.

## The idea

The line is open and the commentary has started. Three messages reach you.

The first is somebody saying they are going to check the timing board. The second is somebody
reading what the timing board said. The third is the sentence you actually rang up for. Only the
third one is the result, and the first two are not noise — they are the reason the third one is
right rather than invented. If the commentator had skipped straight to a result without going near
the board, you would want to know that too.

Now imagine you are not the one listening. You are running a screen in a betting shop, and your
screen shows the result. Your rule is simple: show whatever the commentary says. The first message
arrives — it contains no result, so your screen shows nothing. The second arrives — no result, so
nothing. The third arrives and the screen fills. From the outside, from the point of view of
someone watching your screen, the shop was dark for the whole of the work and then suddenly
finished. Nobody complains about the ending; they complain about the dark.

That is the entire subject of this part. What used to be a single reply is now a **sequence**, and
the sequence has structure worth reading. An **event** is one thing the runner produces while it is
working a question through the agent: a request to run a tool, a tool's answer coming back, a piece
of text, the finished text. Each one says who produced it, whether it is a fragment of something
still arriving, and — through a helper you do not have to write — whether it is the concluding
message of the turn.

Two terms this part uses are already defined in this curriculum and are linked rather than
restated. A **turn** — one piece of a conversation together with who produced it — was defined by
[day 4 part 1.3](../../../day-04-loop-hand/parts/01-what-a-turn-is-made-of/1.3-one-letter-one-reply.md)
and has a row in `docs/GLOSSARY.md`. A **session** — one stored conversation, held by a session
service rather than by your code — was defined by
[day 6 part 2.1](../../../day-06-first-adk-agent/parts/02-the-one-who-runs-it/2.1-the-runner-the-session-and-the-await.md)
and has a row of its own. An event is smaller than a turn: several of them make one.

## The mechanism

The driver gains one subcommand, and it is deliberately a subcommand rather than a script in a
document, because a stream you can re-run is a stream you can argue about.
`projects/01-ask-desk/run.py`, as a marked diff against the whole file **day 04 part 2.1** printed,
with **day 06 part 2.1**'s `adk` addition already applied. Everything not shown is unchanged from

**Line by line:**

- The docstring line is part of the change, for the reason day 06 part 2.1 gave: `main`'s
  fall-through prints `__doc__` to `stderr`, so this docstring is the driver's only usage message.
  `[--stream]` in square brackets says the flag is optional, and the two `case` arms below are what
  make that true.
- **`from google.adk.sessions import InMemorySessionService` is inside `events`, and the module
  scope is deliberately untouched.** This is the rule day 06 part 2.1 stated in this project: it put
  `from ask_desk import agent` *inside* the `adk` function so that `python run.py check` would not
  import the framework, because a gate that cannot run until the thing it checks is installed is not
  a gate. An editor's auto-import will put this line at the top of the file, it will work perfectly,
  and `run.py check` will quietly start loading `google.adk` before it checks anything. Nothing goes
  red. The only way to notice is to know the rule exists, which is why the hub lists it as a trap
  and why §5 asks you to move it to the top on purpose and find out what it costs.
- `import asyncio` **inside** `events`, when day 6 already added `import asyncio` at the top of this
  file. It is redundant and it is harmless, and it is the kind of thing that arrives when a function
  is written to be self-contained and then pasted in. Worth deleting; not worth a second thought
  beyond that.
- `from ask_desk import agent, scripted` inside the function, which is the day-6 pattern applied
  correctly: neither module is imported until somebody actually asks for events, so `check` never
  builds the module-level `desk` and never resolves the pinned model.
- `scripted.ScriptedModel(scripted.LOOKS_IT_UP, name="looks-it-up")` — the double from part 1.1,
  named. The name goes into the model string as `scripted/looks-it-up`, so anything this run emits
  identifies itself.
- `agent.build_desk(model)` and `agent.build_runner(sessions, desk)` — both seams from part 1.1,
  used exactly as they were built. Note the order of the two arguments to `build_runner`: the
  session service first, because that is the one the framework requires.
- `await sessions.create_session(...)` before the run, and not after. The runner does not create a
  session for you; it looks one up. Day 06 part 2.2 caused the failure that happens when it is
  missing, and this line is that lesson applied.
- `run_config=agent.run_config(stream=stream)` — one function, one flag, and the whole difference
  between this part's output and the next part's. `run_config` is section 2's subject and is not
  walked through here.
- `async for event in runner.run_async(...)` — the loop is `async for` because `run_async` is an
  asynchronous **generator**. It does not return a list of events when the work is over; it yields
  each one at the moment it happens. That is the difference between watching and being told
  afterwards, and it is the reason this whole subject exists.
- `event.get_function_calls()` and `event.get_function_responses()` — two helper methods, and using
  them rather than reaching into `event.content.parts` and testing each part for a `function_call`
  attribute. The framework's own documentation defines a final response partly in terms of these two
  being empty, so they are the supported way to ask the question, and code that hand-rolls the
  equivalent is code that has to be revisited when a part type is added.
- `text = "".join(p.text for p in event.content.parts if p.text)` guarded by
  `if event.content and event.content.parts` — three separate things can be absent. `event.content`
  may be `None`, `content.parts` may be `None`, and an individual part may carry a `function_call`
  and no text at all. Any one of them left unguarded is an `AttributeError` or a `TypeError` in the
  middle of a stream, which is the worst place to find one.
- The `if calls / elif responses / else "text"` ladder is a **classification**, and its order is a
  claim: an event carrying function calls is a call event even if it also carries text. That is the
  right way round for reading a stream, and it is not the only defensible order — which is exactly
  why it is three visible lines rather than a clever expression.
- `partial={str(event.partial):5}` — `str(...)` before formatting, because `event.partial` is not a
  plain `bool`. It is an optional one, and an unset optional prints as `None`, which is why the
  transcript below reads `partial=None` rather than `partial=False`. That distinction looks
  cosmetic and is not: the documentation defines the condition as *`partial` is not `True`*, and
  `None`, `False` and `True` are three states where you might have been expecting two.
- `text[:48]!r` — truncated, and `!r` so the quotes are visible. Both matter for the reading below.
  Without `!r` an empty string prints as nothing at all and you cannot tell an empty text from a
  missing column; with it, you get `''` and the point of this part is on the screen.
- `print(f"{n} events, {model.calls} model call(s)")` — two different counts, printed together on
  purpose. They are not the same number and part 2.3 is where the gap between them becomes a bug
  report.
- `case ["events"]` and `case ["events", "--stream"]` as **two arms** rather than one arm with a
  parsed flag. Structural pattern matching checks the argument count as part of the match, so
  `run.py events --strem` falls through to the usage case and exits `2` instead of being silently
  read as "no flag".

**Line by line:**

- **Three events for one question.** Day 6's `agent.ask` kept exactly one of them and dropped the
  other two on the floor, which is why the desk looked to that day like a thing that returns a
  string. It is not; it is a thing that emits a sequence, and returning a string is what you do with
  the sequence afterwards.
- Event 1 is the model asking for a tool. Event 2 is the tool's answer coming back. Event 3 is the
  answer to the question. That order is the loop days 4 and 5 wrote by hand, seen from outside: it
  is the *same* three steps, now emitted by the runner instead of printed by your own `for` loop.
- **Events 1 and 2 carry `''`.** Not a short text, not a placeholder — an empty string. The work
  that makes the answer trustworthy produces no words at all, and every one of those rows is a
  moment in real time when a person is looking at your interface. A client whose render step is
  "print `event.content.parts[].text`" shows a blank screen for the entire working period and then
  the whole answer at once. Nothing raises, nothing logs, and the bug report you eventually get says
  "it's slow", which sends somebody to look at the wrong thing.
- `final=True` on exactly one row, and it is the row with the text. `is_final_response()` is a
  method you call rather than a field you read, which is a hint that it is computed from several
  things rather than set by anybody. The framework's tutorial states the contract:

  > Key Concept: `is_final_response()` marks the concluding message for the turn.

  And the events reference gives the computation in a form you can hold against the three rows
  above: it is `True` when there are no function calls, no function responses, `partial` is not
  `True`, and the event does not end with a code execution result — plus two special cases this
  desk does not use, `skip_summarization` and a long-running tool.
- Read that rule against row 1: `get_function_calls()` is non-empty, so `final=False`. Against row
  2: `get_function_responses()` is non-empty, so `final=False`. Against row 3: neither, and
  `partial` is `None` rather than `True`, so `final=True`. Three rows, one rule, no special-casing —
  which is why you call the helper rather than writing `if "text" in kind`.
- `partial=None` on all three rows, because nothing here is streaming yet. Hold that column in your
  head: it is the only thing that changes in the next part, and nineteen rows appear.
- **`2 model call(s)` for three events.** The tool result was not a model call — your own process ran
  `check_service_status` and handed the answer back. So the two counts are already different on the
  simplest possible run, and this is where to notice it rather than in the middle of part 2.3.
- **There is a column this command does not print, and it is the one that matters most later:
  `author`.** The framework's events reference gives the field with its own comment —
  `author: str  # 'user' or agent name` — alongside `invocation_id`, an ID for the whole
  interaction run, and `id`, unique to the single event. With one agent, `author` is a constant and
  printing it would be three identical rows, which is why it is not in the format string above.
  With a cast of three, it is the only way to tell which of them said a thing, and a stream logged
  without it is a transcript of a meeting with no names against the lines. This desk has one agent
  today; the day it has two, that format string has a column missing.

## When it breaks

This is the failure with no error text, which is what makes it worth a section. There is no
traceback to paste, because nothing goes wrong in the program's own terms — the two rows that break
a client are these, exactly as printed above:

```console
  1. partial=None  final=False call:check_service_status          ''
  2. partial=None  final=False result:check_service_status        ''
```

Somebody wires a web front end to the desk on a Friday, renders `event.content.parts[].text` for
every event, and ships it. It works perfectly in their own testing, because they were testing the
answer. On Monday the support queue says the page hangs. It does not hang: it is showing two empty
strings, correctly, for the whole of the work. The smallest fix is to stop rendering the text and
start rendering the *classification* — the same `if calls / elif responses / else` ladder that is
already in the code above — so that "looking up `check_service_status`" appears on the screen while
it is true.

## In production

**What a senior writes instead.** They never render an event stream by its text. They render it by
its kind, exactly as `events` does above, and map each kind to something a person can read: a tool
call becomes a status line naming the tool, a tool result becomes that line ticking over, and the
final response replaces both. They also treat `is_final_response()` as the only permitted answer to
"is this the answer" — because the rule it computes has special cases for long-running tools and
summarisation that no hand-written condition in an application will remember to include.

**What degrades at scale.** The number is **3**, and it is the smallest this desk will ever produce.
One question, one tool, three events: two of them empty. Add a second tool call to the same question
and it is five, of which four are empty. A client that shows text only is therefore dark for
two-thirds of the simplest run and four-fifths of a slightly harder one, and the proportion gets
worse — not better — as the desk gets more capable. There is no threshold at which this starts being
a problem; it is already the majority of every run.

**The review comment.** "The front end renders `event.content.parts[0].text` and skips anything
falsy. That is every tool call and every tool result — `run.py events` shows two of three events
with `''` on the simplest question we have. Please switch on `get_function_calls()` /
`get_function_responses()` and show the tool name while it is running, and use
`is_final_response()` rather than 'the event that has text' to decide what replaces it."

**The interview question.** "Your agent emits an event stream and your UI shows a blank screen until
the answer appears. Walk me through what is actually in that stream, which fields you would branch
on, and why you would not just render whichever event has text in it."
