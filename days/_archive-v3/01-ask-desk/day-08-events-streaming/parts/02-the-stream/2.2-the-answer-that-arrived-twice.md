## One-line answer

Accumulate text from every event and you get **168** characters where the answer is **84** —
exactly doubled — because the final event repeats the entire sentence rather than carrying the last
fragment, and the four lines of code that do this are the four lines almost everybody writes first.

## The idea

You have been writing the commentary down as it comes, word by word, and it has gone well. The line
crackles and you keep up. The last word arrives and you underline it, satisfied.

Then the commentator, being a professional, does the thing a professional does at the end of a race:
they read the whole result back, from the top, cleanly, so that anybody who missed a word has it
complete. And you — head down, pen moving, writing down everything that comes down the line — write
it all again underneath.

Read your own page back now. The result is on it twice, with no gap between the two, because you
never stopped to ask whether the last thing you heard was new information or a repetition of what
you already had. Every single word you wrote was a word that was genuinely said. Nothing was
invented and nothing was misheard. The page is still wrong.

That is this part, and the reason it is the day's deliberate failure rather than an anecdote is the
shape of it. This is not a mistake you make by being careless. It is a mistake you make by writing
the most obvious possible loop — take each thing that arrives, add its text to what you have — and
it is the loop you write when you are trying to be simple rather than clever. It survives review
because a reviewer reads it and cannot point at a wrong line. It survives testing because with
streaming off there are no fragments, so the total is right by accident. And it survives your own
manual check, if the answer you happened to test with was short enough that reading it twice looks
like a formatting problem rather than a duplication.

The word for the last thing to arrive is worth pinning down before the code. A **final event** is not
"the end of the stream" in the sense of "the last bit". It is the concluding message *of the turn* —
a complete statement of the answer, standing on its own, produced after the fragments and containing
what they contained.

## The mechanism

Two accumulators over one stream, run side by side so the difference is a number rather than an
opinion. Observed on this machine on 2026-09-10:

```console
$ uv run --frozen python -c "
import asyncio, warnings
warnings.filterwarnings('ignore')
from google.adk.agents.run_config import RunConfig, StreamingMode
from google.adk.runners import Runner
from google.adk.sessions import InMemorySessionService
from google.genai import types
from ask_desk import agent, scripted

async def main():
    model = scripted.ScriptedModel(scripted.LOOKS_IT_UP, name='looks-it-up')
    desk = agent.build_desk(model)
    ss = InMemorySessionService()
    await ss.create_session(app_name=agent.APP_NAME, user_id='u', session_id='s')
    r = agent.build_runner(ss, desk)
    msg = types.Content(role='user', parts=[types.Part(text='Is the VPN down?')])
    naive = ''; partials = ''
    async for e in r.run_async(user_id='u', session_id='s', new_message=msg,
                               run_config=agent.run_config(stream=True)):
        t = ''.join(p.text for p in (e.content.parts or []) if p.text) if e.content else ''
        naive += t
        if e.partial: partials += t
    print('every event  :', len(naive), 'chars')
    print('partials only:', len(partials), 'chars')
    print('naive text   :', repr(naive[:110]))
asyncio.run(main())
"
every event  : 168 chars
partials only: 84 chars
naive text   : 'The VPN is degraded: there is a known split tunnelling issue, and the gateway is up.The VPN is degraded: there'
```

**Line by line:**

- Two accumulators, one stream, one run. `naive` takes the text of **every** event. `partials` takes
  the text only of events where `e.partial` is set. Running both in the same loop removes the
  objection that two runs differed — this is one run, and the double from part 1.1 guarantees that
  a second run would produce the same words anyway.
- `naive += t` **unconditionally**, before any test. That is the line under examination, and it is
  written this plainly on purpose: it is what the code looks like in the wild. Nothing about it is
  obviously wrong, which is the entire problem.
- `if e.partial: partials += t` — the same addition behind the flag part 2.1 explained. One extra
  clause is the whole fix, and the fact that the fix is this small is why the bug is so easy to
  ship.
- `''.join(p.text for p in (e.content.parts or []) if p.text) if e.content else ''` — the same
  triple guard `run.py events` uses, for the same three reasons: `e.content` may be `None`,
  `parts` may be `None`, and a part carrying a `function_call` has no text. Written inline here
  because the point of the probe is the two accumulators and not the guarding.
- `run_config=agent.run_config(stream=True)` — the switch from part 2.1, thrown deliberately. With
  it off, both accumulators produce the same number, which is exactly why this failure hides.
- **`every event : 168` against `partials only: 84`.** Not "a bit more". Exactly twice — 168 is 2 ×
  84 — and it is exactly twice because the final event contains a copy of every character the
  fragments contained and nothing else.
- `repr(naive[:110])` shows the join. Read the end of it: `...and the gateway is up.The VPN is
  degraded: there`. The sentence ends and restarts with **no separator at all**, because the
  fragments already carried their own spaces and there was no space to put between the last word of
  the answer and the first word of the repeat. In a log or a chat bubble it reads as a run-on
  typographical accident rather than as a duplicated answer, which is one more reason nobody
  reports it as a duplication.
- The 84 is the correct answer: `'The VPN is degraded: there is a known split tunnelling issue, and
  the gateway is up.'` is 84 characters. Both accumulators are *available*; only one of them is the
  answer.

### Where the extra copy comes from

It comes from a line printed in part 1.1, in this project's own `ask_desk/scripted.py`, in the
streaming branch of `generate_content_async`: the final `yield` carries `step.text` — the whole
sentence — and not the last word. Part 2.1's transcript is the same fact from the outside: row 18
is `'up.'` and row 19 starts `'The VPN is degraded: there is a known split tunn'`.

So the stream's contract is not "here are the pieces, then a marker". It is "here are the pieces,
then the finished thing". Both are defensible designs; a consumer that assumes the first when it is
given the second doubles every answer, and a consumer that assumes the second when it is given the
first loses everything except the last word. **You cannot write a correct accumulator without
knowing which one you have**, and the way you find out is to run the stream and look, which is what
this part just did.

Worth knowing that the framework's own documented pattern makes the same distinction and leaves the
same question open. From the events reference at `https://adk.dev/events/`, fetched 2026-09-09,
verbatim:

```python
# Pseudocode: Handling final responses in application (Python)
# full_response_text = ""
# async for event in runner.run_async(...):
#     # Accumulate streaming text if needed...
#     if event.partial and event.content and event.content.parts and event.content.parts[0].text:
#         full_response_text += event.content.parts[0].text
#
#     # Check if it's a final, displayable event
#     if event.is_final_response():
#         print("\n--- Final Output Detected ---")
#         if event.content and event.content.parts and event.content.parts[0].text:
#              # If it's the final part of a stream, use accumulated text
#              final_text = full_response_text + (event.content.parts[0].text if not event.partial else "")
#              print(f"Display to user: {final_text.strip()}")
#              full_response_text = "" # Reset accumulator
```

**Line by line:**

- `if event.partial and ...: full_response_text += ...` — the accumulation is **guarded by
  `partial`**, which is the fix this part is arguing for, written into the documentation. Copy this
  pattern and you do not have the bug.
- `final_text = full_response_text + (event.content.parts[0].text if not event.partial else "")` —
  and now read it against what this project's stream actually does. The final event has `partial`
  unset, so `not event.partial` is true, so its text is **appended to the accumulated fragments**.
  Against a stream whose final event carries only the remainder, that is correct. Against this
  project's stream, whose final event repeats the whole sentence, it is the doubling again. The
  documentation cannot decide this for you because the answer depends on the model and the mode,
  not on the framework.
- `full_response_text = ""` at the end — the accumulator is **reset** after a final response.
  Without it, a second question down the same session starts with the first question's answer
  already in the buffer, which is the same bug with a longer fuse.
- `event.content.parts[0].text` — index zero, no join. Fine for pseudocode; not fine in your code,
  because a real event may carry several parts and this reads the first one only. `run.py events`
  joins them for that reason.
- The comment `# If it's the final part of a stream, use accumulated text` is the sentence to keep.
  It says the accumulated text is the answer. Everything above is about not adding anything to it
  twice.

## When it breaks

It breaks in front of a user, and it breaks looking like a formatting bug. This is what came back
from the naive accumulator, verbatim, truncated at 110 characters by the probe:

```console
naive text   : 'The VPN is degraded: there is a known split tunnelling issue, and the gateway is up.The VPN is degraded: there'
```

Somebody ships a streaming chat panel on a Thursday. It is fine in review, fine in staging with
streaming off, and fine in the demo, where the answer was three words. Then a real question gets a
real paragraph and the panel prints it, then prints it again, joined by nothing — and the ticket
that arrives says "the assistant repeats itself", which sends everyone to look at the prompt. The
smallest fix is one clause: accumulate only when `event.partial` is set, and take the final event's
text as the answer rather than as an addition to it. The next-smallest fix, and the better one, is
to stop accumulating in the application at all and render the accumulated fragments for feel while
using the final event as the value.

## In production

**What a senior writes instead.** They keep two variables with two different jobs and never let one
do both: a display buffer, appended to on `partial` events only, which exists so the screen moves;
and the answer, assigned once from the final event, which is what gets stored, logged, evaluated and
returned. Assignment, not `+=`, for the second one — because the operator itself is the bug, and a
variable that is only ever assigned cannot be doubled. And they write the test that would have
caught it: one streamed question, asserting `len(answer) == len(the sentence)`, which is a test that
fails loudly the day the stream's contract changes under them.

**What degrades at scale.** The number is **exactly 2×**, and the thing about a doubling is that it
is invisible in every aggregate you would look at. Token counts, storage and latency percentiles all
move by a factor that looks like ordinary growth. On a 84-character answer it is 168 characters
stored per turn instead of 84; at a thousand turns a day that is a hundred thousand characters of
duplicated text a day, in the store, in the logs, and in the context of any later turn that quotes
the transcript back. The one place it is loud is an eval that compares against an expected answer —
which is why the day this project builds evals matters, and why this bug is being caught before
then.

**The review comment.** "`answer += text` runs for every event, including the final one. Our stream's
final event repeats the whole sentence — `run.py events --stream` shows row 18 as `'up.'` and row 19
as the full text — so this stores every answer twice. Please guard the accumulation with
`event.partial` and assign the answer from `is_final_response()`. Add a test asserting the stored
answer's length equals the sentence's, so this cannot come back."

**The interview question.** "You are consuming a streaming LLM event stream. Describe two possible
contracts for what the final event contains, say how you would find out which one you have, and
write the accumulator that is correct under the one you found — then say what happens to it if the
provider changes to the other."
