## One-line answer

A model cannot see your functions; it sees a small JSON object per function — a name, a description,
and a JSON Schema for the arguments — so that object is not documentation about the interface, it
**is** the interface, and a description that says the wrong thing produces a tool called at the
wrong moment rather than an error anyone can catch.

## The idea

A waiter takes your order and cannot cook. That is not a failing, it is the arrangement: they stand
where you are, they know what the kitchen can make, and they write a docket. The docket goes through
a slot in the wall. The kitchen never hears you speak. Nobody behind that wall knows you hesitated
over the fish, or that you said "not too spicy" while pointing at the menu, or that you are allergic
to something you mentioned on the way in. **Everything that crosses the wall crosses on the docket.**

So the docket format is the whole relationship between the two rooms. If a docket says *soup* and
the kitchen has three soups, the kitchen picks one and nobody has made a mistake. If the menu
describes a dish in a way that reads well and is wrong about what is in it, the docket will be
written correctly, the kitchen will cook exactly what was written, and the plate that arrives will
be wrong — and there is no moment in that chain where an error could have been raised. Everyone did
their job. The description was the bug.

That is exactly the arrangement between your program and a model, and it is worth being blunt about
which side of the wall each thing is on. Your Python functions are in the kitchen. The model is the
waiter: it is holding the conversation, it decides when a dish is wanted, and it has never seen your
code and never will. What it gets is a **function declaration** — one small JSON object per function
that names it, describes it in prose, and describes the shape of its arguments. That object is sent
with every request. It is the only thing about your tools the model ever receives.

Three consequences, and the third is the one that costs people afternoons.

First, the **name** is an identifier the model will type back at you, so it lives under a rule rather
than a preference. The provider documents the constraint on the name a model sends back — verbatim,
from `https://ai.google.dev/api/generate-content`, checked 2026-09-09:

> Must be a-z, A-Z, 0-9, or contain underscores and dashes, with a maximum length of 128.

Second, the **arguments** are described with a schema rather than prose: a type for each parameter,
a list of which ones are compulsory, and — because the model reads prose better than it reads
types — a description on each one as well. The vocabulary here is **JSON Schema**: a small standard
for saying "this is an object, it has these named properties, this one is a string, these ones are
required". It is the same vocabulary an HTTP API uses to describe a request body, and it is used
here for the same reason: it is machine-checkable and it is not English.

Third, and this is the part that has no equivalent in any interface you have written before: **the
description is executable, and nothing checks it.** A parameter's type can be wrong and something
will eventually complain. A description cannot be wrong in a way that complains. If your
`search_notes` description says "returns the full text of matching notes" and the function returns
titles only, no error is raised anywhere. The model reads the description, believes it, calls
`search_notes` once, gets titles, and writes an answer as though it had read the bodies. The
failure surfaces as a confidently wrong answer, days later, in something a person is reading.

So a function declaration is a promise about code that no compiler, linter or type checker will ever
compare against the code. It is the only interface in this project where the documentation and the
contract are the same object. Write it the way you would write the menu, not the way you would write
a docstring for a colleague — the reader is not going to open the file and check.

## The mechanism

The declarations do not sit in a request builder or in a prompt. They live beside the functions they
describe, in `ask_desk/tools.py`, which part 1.2 prints whole. This part is about the **shape** of
one of them, and the honest way to see that shape is to look at the bytes that actually leave —
because that is what the model receives.

`run.py plan` builds the exact request a question would send and sends nothing:

```console
$ uv run --frozen python run.py plan "Is the VPN down?"
POST https://generativelanguage.googleapis.com/v1beta/models/gemini-3.8-flash:generateContent

{
  "contents": [
    {
      "role": "user",
      "parts": [
        {
          "text": "Is the VPN down?"
        }
      ]
    }
  ],
  "system_instruction": {
    "parts": [
      {
        "text": "You are an internal IT ask desk. Answer from the notes you are given and nothing else. If the notes do not cover the question, say so plainly and do not guess."
      }
    ]
  },
  "tools": [
    {
      "function_declarations": [
        {
          "name": "search_notes",
          "description": "Search the internal knowledge base for notes matching a query. Returns ids and titles only. An empty list means nothing matched, which is a valid answer and must not be reported as an error.",
          "parameters": {
            "type": "object",
            "properties": {
              "query": {
                "type": "string",
                "description": "Words to search for, e.g. 'vpn file share'."
              },
              "limit": {
                "type": "integer",
                "description": "Maximum notes to return. Defaults to 3."
              }
            },
            "required": [
              "query"
            ]
          }
        },
        {
          "name": "fetch_note",
          "description": "Return the full text of one knowledge-base note by its id. Use search_notes first to find an id; do not guess one.",
          "parameters": {
            "type": "object",
            "properties": {
              "note_id": {
                "type": "string",
                "description": "The note id, e.g. 'KB-101'."
              }
            },
            "required": [
              "note_id"
            ]
          }
        }
      ]
    }
  ]
}
```

**This transcript is truncated, and the truncation is named.** The third declaration,
`check_service_status`, follows `fetch_note` in the same array and was cut here for length only.
Nothing else was edited. Part 1.2 prints `tools.py` whole, so all three declarations appear in full
in this same day, which is what the completeness rule asks for.

**Line by line:**

- `"tools"` is a **list of tool objects**, and each one carries a `function_declarations` array. Two
  levels of nesting for what looks like one list, and the reason is that `tools` is where every kind
  of tool goes — the provider's own search and code-execution tools are siblings of
  `function_declarations` in that object, not entries in it. Flattening it in your head is fine
  until the day you add a second kind of tool and cannot work out where it goes.
- `"name": "search_notes"` — lower case, an underscore, no dots and no spaces. It satisfies the
  constraint quoted above, and it satisfies it by looking like an ordinary Python function name,
  which is not a coincidence: this name is the string the model sends back, and the string your
  dispatcher looks up. Two things are agreeing on a spelling here, and part 1.2 is about the fact
  that nothing enforces the agreement.
- `"description"` is three sentences and every one of them is doing work. *What it searches* tells
  the model when this tool is the right one. *"Returns ids and titles only"* tells it that a second
  call will be needed to read a note, which is the difference between one round trip and a confident
  fabrication. *"An empty list means nothing matched, which is a valid answer and must not be
  reported as an error"* pre-empts the single most common behaviour of a model handed an empty
  result: apologising, or inventing something to fill the hole.
- `"parameters"` opens with `"type": "object"` and not with the parameter names. That is JSON Schema
  describing **the argument bag as a whole** — the thing the model must construct is a JSON object,
  and `properties` describes what may go in it. It reads like ceremony and it is the line that says
  what kind of value the model is being asked to build.
- `"properties"` names each parameter with the **exact spelling of the Python parameter**. `query`
  here is `query` in the function signature. The model sends back an object keyed by these names and
  the dispatcher passes it as keyword arguments, so a rename on one side without the other produces
  an argument the function has never heard of. That is one of the three failures part 2.2 causes on
  purpose.
- `"type": "string"` and `"type": "integer"` are the schema's whole opinion about the values. There
  is no `minimum` on `limit` and no pattern on `query`, and that is a deliberate floor rather than a
  finished job — the schema constrains what the model is *asked* for, and part 2.2 is about what
  happens when what arrives does not match.
- Each property carries its **own `description`**, and this is the field people skip. `"Words to
  search for, e.g. 'vpn file share'."` is worth more than the type is: the type says a string is
  wanted, the description says a *bag of words* is wanted rather than a sentence or a note id. Day 7
  compares this hand-written declaration with the one the framework derives automatically, and the
  per-parameter description is the thing the derived one does not have.
- `"required": ["query"]` lists **only** `query`. `limit` is absent from the list, which is how a
  schema spells optional — there is no `"optional": true`. The model is free to omit `limit`
  entirely, and the Python default of `3` then applies. Note what the schema does *not* say: the
  default is mentioned in the prose description and nowhere in the machine-readable part, so the
  model has to read English to learn it.
- Compare this request with the one day 4 printed for the same question. Everything above `"tools"`
  is byte-identical: the same contents, the same system instruction, the same endpoint. **The only
  change today is that the request now carries a `tools` key**, because `build_request` — which day
  4 printed, including its `tools` parameter — was being passed `None` and is now being passed
  something. Day 4 built the road; today is the first traffic on it.

*Observed on this machine on 2026-09-09, uv 0.12.3, CPython 3.12.12. No key was needed: `run.py
plan` builds the request and sends nothing.*

## When it breaks

The declaration and the function are two objects and nothing in Python, in the provider, or in your
editor compares them. So the failure arrives at the dispatcher, at the moment a name that was
promised turns out not to exist:

```console
$ uv run --frozen python -c "
from ask_desk import tools
try:
    tools.dispatch('lookup_ticket', {'id': 'T-1'})
except tools.UnknownTool as e:
    print('UnknownTool:', e)
"
UnknownTool: the model asked for 'lookup_ticket', which this desk does not have. Known tools: check_service_status, fetch_note, search_notes. A tool the model invents is a sign the declarations and the registry have drifted apart.
```

*This is the first statement of the transcript part 2.2 runs in full; the other two statements were
cut here and nothing was edited.* Read the last sentence of the message, because it was written to
be read at eleven at night by somebody who did not write this file: the usual cause is not an
inventive model, it is a rename. Somebody changed a function name and left the declaration alone, or
added a declaration for a function that is still on a branch. The smallest fix is the one part 1.2
argues for — put the declarations in the same file as the functions, where a rename is visible in
the same diff.

## In production

**What a senior writes instead.** They do not hand-write the JSON. They derive it from the function
signature and its docstring, so the two halves cannot drift by construction — that is what the
framework's `FunctionTool` does, and day 7 prints the comparison. What they keep from the hand
version is the *prose*: a derived schema gets types and required-ness for free and gets no
per-parameter guidance at all, so the docstring becomes the place where "a bag of words, not a
sentence" has to be said.

**What degrades at scale.** Every declaration is sent on **every** request, and with the loop this
day builds, one question costs at least two requests. Three declarations at roughly a hundred tokens
each is three hundred tokens of overhead per request, so a two-request question pays for them twice
and a six-request question pays six times. At thirty tools — an ordinary number for a desk that has
been alive a year — that is three thousand tokens on every single call before the conversation is
counted, and the model's accuracy at picking the right one falls at the same time as the bill rises.
The fix is not shorter descriptions; it is fewer tools per agent, which is what a cast is for, and
that is P03.

**The review comment.** "`search_notes`'s description says it returns matching notes. It returns ids
and titles. That is not a typo in a comment — it is the only specification the model has, and it
will call this once and then answer from the titles. Say 'ids and titles only' and say that
`fetch_note` is how you read one."

**The interview question.** "Your agent has a tool that deletes a record. Describe every place the
model's decision to call it comes from, and say which of them you can change without deploying
code."
