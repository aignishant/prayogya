## One-line answer

Wrap the event loop in `try/except Exception: return answer` and a run that failed comes back as the
empty string with the incident gone — and the version that returns a sentence instead of the empty
string is worse, because a fabricated result covering an error is the one thing this curriculum
forbids by name.

## The idea

An incident that is not written up did not stop happening. It stopped being findable. That is the
whole of this part, and it is worth sitting with for a moment before any code, because everyone
agrees with it in the abstract and almost nobody's error handling behaves as though they do.

Picture the end of a shift on the ward. Something went wrong — not catastrophically, it was caught,
the patient is fine — and writing it up means a form, and a conversation, and somebody senior asking
questions tomorrow. The alternative is to say nothing, and the alternative is *seductive*, because
nothing bad happens. The ward looks calmer at the end of a shift where nothing was written up than
one where something was. The absence of the record is indistinguishable, from outside, from the
absence of the event.

Then it happens again next month, to somebody else, on a different shift. Nobody connects the two,
because there is nothing to connect. The second write-up, if it happens, describes a one-off. This is
not a story about dishonesty; it is a story about a system that made silence cheaper than reporting
and then wondered why it had no data.

Software has a two-word version of not writing it up, and it is `except Exception:`. It is written
with good intentions almost every time — usually to stop one noisy failure from taking down a whole
batch — and it does exactly what the unwritten incident does. The failure still happened. The run
still failed. What changed is that nothing downstream can tell.

And there is a second, worse form, which is the one that gets people fired rather than merely
paged. The unwritten incident leaves a gap. The **invented** answer fills the gap in with something
plausible. A desk that returns `"I couldn't find anything"` when the provider dropped the connection
has not failed to report an error; it has *stated something false about the world* — that a search
happened and came back empty — and it has stated it in the calm, helpful voice that the correct
answers are also written in. Nobody downstream, human or machine, has any way to separate the two.

## The mechanism

The shape is already latent in `ask_desk/agent.py`'s `ask`, which **day 06 part 1.1** printed whole.
Two of its lines carry the whole failure, and they are both perfectly reasonable lines:

| Line, from the file day 06 part 1.1 printed | What it does, and what it sets up |
| --- | --- |
| `answer = ""` before the loop | The accumulator starts empty, which is the only sensible starting value. It is also a complete, valid, returnable `str` from the very first instruction. |
| `if event.is_final_response() and event.content and event.content.parts:` | The guard that keeps the code from crashing on an event with no content. Part 2.1 showed that the error event **is** final and **has** no content — so this guard steps neatly over it. |

Everything needed for the failure is therefore already present: a variable that is a valid answer
before anything has happened, and a guard that declines to write into it on exactly the event that
says the run went wrong. All that is missing is something to stop the exception, and one line does
that.

### The break: wrap the loop and return what you have

This is not an edit to `ask_desk/agent.py` — the file on disk stays as day 06 printed it. It is
`ask`'s own body, with one `try`/`except` around the loop, run as a probe so the working version and
the broken one can sit side by side:

```console
$ cd projects/01-ask-desk
$ uv run --frozen python -c "
import asyncio, warnings
warnings.filterwarnings('ignore')
from google.adk.sessions import InMemorySessionService
from google.genai import types
from ask_desk import agent, scripted

async def ask_swallowing(question):
    ss = InMemorySessionService()
    await ss.create_session(app_name=agent.APP_NAME, user_id='u', session_id='s')
    model = scripted.ScriptedModel(scripted.FAILS_AFTER_A_TOOL, name='fails-after-a-tool')
    runner = agent.build_runner(ss, agent.build_desk(model))
    message = types.Content(role='user', parts=[types.Part(text=question)])
    answer = ''
    try:
        async for event in runner.run_async(user_id='u', session_id='s', new_message=message,
                                            run_config=agent.run_config()):
            if event.is_final_response():
                print('final event: content is', event.content, '| error_code =', event.error_code)
            if event.is_final_response() and event.content and event.content.parts:
                answer = ''.join(p.text for p in event.content.parts if p.text)
    except Exception:
        return answer
    return answer

out = asyncio.run(ask_swallowing('Is the VPN down?'))
print('the caller received:', repr(out), '- length', len(out))
"
final event: content is None | error_code = RuntimeError
the caller received: '' - length 0
```

**Line by line:**

- `final event: content is None | error_code = RuntimeError` — the run knew. The event carried the
  class name of the exception, and the code printed it, and then threw it away because the next `if`
  is the one that decides what `answer` becomes.
- `event.content` is `None`, not an empty `Content` with empty `parts`. So the guard's second clause
  is false and the third is never evaluated. `answer` is never assigned, which means it is still the
  empty string it was initialised to.
- `except Exception: return answer` — this is the only line that differs from the working version,
  and it does two things at once, which is why it is so effective at hiding. It stops the exception,
  **and** it returns a value that was designed as a starting point rather than as a result.
- `the caller received: '' - length 0`. Not `None`. Not a sentinel. A `str`, of the type the
  signature promises, which every type checker approves of and every caller can concatenate.
- The function returned **normally**. There is no exception to catch upstream, no non-zero exit, no
  log line, nothing in a metric. A caller that checks `if answer:` finds nothing and might render an
  empty bubble; a caller that does not check writes `""` into a database as the desk's answer to that
  question, for ever.
- And note what did *not* happen: the tool ran. `check_service_status` was called and returned. Real
  work happened, it cost something, and the record of it is a zero-length string.

Compare with the honest version — the same probe with the `try`/`except` removed, which is
part 2.1's transcript:

```console
escaped after 3 events: builtins.RuntimeError: the provider closed the connection
```

**Line by line:**

- One line of output instead of a returned value, and everything anybody needs is in it: what
  happened, in the provider's own words, and where in the run it happened. The two versions differ by
  two lines of code and by the entire difference between a system you can operate and one you cannot.

### The worse version, and why it has its own name

Now the same swallow with a friendlier return value:

> `except Exception:` &nbsp;→&nbsp; `return "I couldn't find anything"`

This is the version people write on purpose, and they write it for a good reason: an empty bubble
looks broken to a user, and a sentence looks finished. It converts an operational problem into a
product one, which feels like an improvement right up until you ask what the sentence *claims*.

It claims a search was performed and returned nothing. That did not happen. The provider closed the
connection, and whether the VPN is degraded is a question this run never got an answer to. The
sentence is not a vaguer version of the truth; it is a different fact, asserted confidently, in the
same voice the correct answers use. And it is asserted to whoever asked — who now believes their
service is fine.

This is the one the plan names. `CLAUDE.md` and plan §9 carry it in the same breath as the
rate-limit rule: **never fabricate a result to cover an error.** Not "prefer not to". The reason it
gets its own rule rather than being left to judgement is that every individual instance is
defensible, and the aggregate is a system whose outputs cannot be trusted at all — because once one
answer might be a cover story, every answer might be.

The honest ways to be kind to the user are all still available, and none of them involve the desk
saying something untrue. Return the failure and let the layer that talks to humans phrase it. Say
*this failed, try again* rather than *I looked and found nothing*. Both are short sentences; only one
of them is a claim about the VPN.

### And no, retrying is not today's fix

The reflex on reading `the provider closed the connection` is to retry. Sometimes that is right, and
the provider's own troubleshooting page, read 2026-09-10, is specific about when:

> "Only retry on transient errors (like 429, 408, or 5xx). Do not retry on client errors (like 400 or
> 403)"

Two things follow, and both of them point away from writing a retry into `agent.py` today. The first
is that a retry needs to know **which** error it is looking at, and this run gave you
`error_code='RuntimeError'` — a Python class name, not a status. Retrying on that would retry a bad
request as eagerly as a timeout, which is the case the quoted line rules out. The second is that
honest backoff is a subject with its own gates — `Retry-After`, the delay schedule, the escalation
when the retries run out — and it is taught deeply in **P05 Bench Runner**, whose phase gate in the
plan §16 is *"four providers benchmarked, and no fabricated answer covers an error"*. Adding half of
it here would mean this project silently swallowing errors that a future day is going to have to
teach it to surface again.

What today's fix is: let it out, and make sure something writes it down. That is one line — the one
that is not there.

## When it breaks

The break above is the good version of the disaster, because it is running under a scripted model on
a machine with no provider key. The version that reaches production has the same two lines and a real
provider behind it, and this is what it looks like when it is finally caught — the same
`except Exception:` sitting above a real refusal instead of a scripted one:

```console
google.genai.errors.ClientError: 400 INVALID_ARGUMENT. {'error': {'code': 400, 'message': 'API key not valid. Please pass a valid API key.', 'status': 'INVALID_ARGUMENT', 'details': [{'@type': 'type.googleapis.com/google.rpc.ErrorInfo', 'reason': 'API_KEY_INVALID', 'domain': 'googleapis.com', 'metadata': {'service': 'generativelanguage.googleapis.com'}}, {'@type': 'type.googleapis.com/google.rpc.LocalizedMessage', 'locale': 'en-US', 'message': 'API key not valid. Please pass a valid API key.'}]}}
```

That is a rotated key, and it is an error every operator on earth can fix in a few keystrokes — but
only if they see it. Behind the swallow, a rotated key is not an outage; it is a desk that has quietly
started answering every single question with the empty string, at a hundred per cent failure rate,
while the health endpoint stays green and the error rate stays at nought. Somebody notices when a
user complains. The smallest fix is to delete the `except Exception:` and let the run fail; the next
smallest is to catch it exactly once, at the edge that talks HTTP, log `error_code`, `error_message`
and the invocation id, and answer with a status code that means *failed*.

## In production

**What a senior writes instead.** They never catch `Exception` in the middle of a run. Failures
travel to one place — the edge — where they are turned into a status code and a log line carrying the
invocation id from part 1.1, and the answer field is left **absent** rather than empty, because a
missing value and a zero-length one are different facts and only one of them means "we do not have
this". Where a bulk job genuinely must continue past a failure, they count the failures and fail the
job on the count, so continuing is a policy with a number attached rather than a `pass`.

**What degrades at scale.** The number is **100%**. On the rotated-key failure above, every question
fails and every question returns a valid empty string, so the observed error rate is zero and the
observed availability is a hundred per cent. Not degraded — *inverted*: the monitoring is at its most
confident exactly when the system is least working. Compare the honest version, where the same
rotation produces one exception per request, an alert inside a minute of traffic, and a fix before
anybody outside the team has typed a question.

**The review comment.** "This `except Exception: return answer` turns a failed run into a successful
empty one — `answer` is still the `''` it was initialised to, because the error event carries no
content and the guard above skips it. We would ship a rotated key to production and see a flat error
graph. Please let it propagate and handle it once at the API boundary, log `error_code` and
`error_message` from the final event, and add a test using `scripted.FAILS_AFTER_A_TOOL` that asserts
the call **raises** — so that anybody who adds this `except` back gets a red build."

**The interview question.** "A service returns an empty string instead of raising when its upstream
fails. Your dashboards show zero errors and full availability. Describe how you would find out that
this is happening, what you would change so that it cannot happen again, and what you would say to
the engineer who argues that returning a friendly message is better for users than returning an
error."
