## One-line answer

When a model call raises mid-run, ADK does **both** things and neither instead of the other: it emits
a final event carrying `error_code` and `error_message` and no content, **and** it lets the exception
propagate out of `run_async` — so a consumer that reads only events records a successful, empty
answer, and a caller that does not catch gets a traceback, from the same run.

## The idea

An incident on the ward gets recorded twice, on purpose, and the two recordings are for different
people. It goes in the notes in the slot, where it stays, timestamped, for whoever picks the notes up
next week. And it gets said out loud, immediately, to whoever is standing there — because notes are
read later and a person bleeding is a now problem. Nobody thinks of these as alternatives. A ward
that only wrote things down would be slow; a ward that only shouted would forget.

The framework does the same, and the trouble it causes is that most people expect it to have chosen.
The mental model people bring is *either* the error comes back as a value *or* it comes back as an
exception, and the first thing they do is decide which, and half of them decide wrong. Both channels
are live. If you read events and never catch, your code sees the incident and your process still
dies. If you catch and never read events, your code survives and has no idea what happened. Neither
is a bug in the framework; both are a bug in the reader.

There is a second thing about failure messages that this part is the right place for, because it has
the same shape and it costs more. An error message names the place where the error was raised. It
does not name the place you were looking. This project reads its key out of a file it owns; the
provider library builds its client out of the process environment; and until something copies the
value from one to the other, the library will tell you, correctly and unhelpfully, that no key was
provided — while the key sits on disk, in the file you are staring at, spelled right. Two true
statements about two different places, and a person in the middle who thinks there is only one place.

So one idea, in two halves: **a failure surfaces where the code that raised it lives, and finding it
means knowing which places there are.** The run has two. The key has two.

| Line | What it does, and the failure it prevents |
| --- | --- |
| `class Fail` as a script step, beside `Say` and `CallTool` | A failure is a **scripted outcome**, not an edit. It can be run beside the working script in one command and asserted on by a test — which is the difference between a failure you saw once and a failure you can regression-test. |
| `"""...Day 6 uses this..."""` in the docstring | Project-relative numbering: P01 runs from sitting 4 to sitting 10, so this project's own day 6 is **today**, global day 9. The file says it because a reader who has only `projects/01-ask-desk/` has no global numbering to read. |
| `message: str` | The text is chosen by this project, so when it appears in an event's `error_message` below there is no doubt about where it came from. A generic `RuntimeError()` would leave you guessing whether the framework or the double produced it. |

| The `#:` comment above it | Says the same thing in the file, so somebody reading `scripted.py` cold knows why this script exists and does not "simplify" it to a one-step failure. |

### What one failing run actually emits

```console
$ cd projects/01-ask-desk
$ uv run --frozen python -c "
import asyncio, warnings
warnings.filterwarnings('ignore')
from google.adk.sessions import InMemorySessionService
from google.genai import types
from ask_desk import agent, scripted

async def main():
    model = scripted.ScriptedModel(scripted.FAILS_AFTER_A_TOOL, name='fails-after-a-tool')
    desk = agent.build_desk(model)
    ss = InMemorySessionService()
    await ss.create_session(app_name=agent.APP_NAME, user_id='u', session_id='s')
    r = agent.build_runner(ss, desk)
    msg = types.Content(role='user', parts=[types.Part(text='Is the VPN down?')])
    n = 0
    try:
        async for e in r.run_async(user_id='u', session_id='s', new_message=msg,
                                   run_config=agent.run_config()):
            n += 1
            print(f'{n}. error_code={e.error_code!r} error_message={e.error_message!r} final={e.is_final_response()}')
    except Exception as ex:
        print(f'escaped after {n} events: {type(ex).__module__}.{type(ex).__name__}: {ex}')
asyncio.run(main())
"
1. error_code=None error_message=None final=False
2. error_code=None error_message=None final=False
3. error_code='RuntimeError' error_message='the provider closed the connection' final=True
escaped after 3 events: builtins.RuntimeError: the provider closed the connection
```

**Line by line:**

- Events 1 and 2 are the tool call and the tool result — the work that succeeded, and day 08 is where
  those two are read properly. `error_code` is `None` on both, which is what "nothing wrong here"
  looks like.
- Event 3 is the whole subject of this part. **`final=True`.** `is_final_response()` returns true for
  it, exactly as it does for a good answer. Anything downstream that branches on
  `if event.is_final_response():` will take the success branch on a run that failed.
- `error_code='RuntimeError'` and `error_message='the provider closed the connection'` — the
  exception's class name and its message, carried on the event as two strings. Both fields default to
  `None` and are `Optional[str]`; there is no error object, no traceback and no cause chain. What
  survives into the event is a label and a sentence.
- The message is the one `FAILS_AFTER_A_TOOL` chose, so there is no ambiguity about the path: this
  came out of the model call, through the runner, onto an event.
- **`escaped after 3 events`.** Read that line together with the one above it. The event was emitted,
  the loop received it, the loop finished the iteration — and *then* the exception came out of
  `run_async` anyway. Not instead of the event. After it.
- So there are two consumers of one failure and they see different things. An events consumer sees a
  final event with no content and two error fields. A caller that just awaits the run sees
  `RuntimeError`. Whichever one you wrote, the other one is also happening.
- The event has no `content`, which part 2.2 turns into its whole failure. A final event whose
  content is `None` cannot contribute any text, so any accumulator built the obvious way ends the run
  holding exactly what it held before — the empty string.

+
+    Days 1 and 2 built `util/keys.py`, and every hand-rolled call goes through it. The framework
+    does not: `google-genai` constructs its client from `os.environ` directly and has never heard

+    message so confusing.

**Line by line:**

- `import os` at the top of `agent.py`, and nothing else new. The bridge is four lines of standard
  library; it needs no dependency and no framework hook, and that is worth noticing before reaching
  for a settings library to solve it.
- `from ask_desk.util import keys, models` — `agent.py` now reads this project's own key module.
  Day 04 part 1.2 printed `util/keys.py` whole and it has not changed; what changed is who calls it.
- `os.environ.get("GOOGLE_API_KEY") is None` — the guard, and the direction of it is the decision.
  The **environment wins**. A container that had a real key injected keeps it; a stale `.env` in the
  image cannot overwrite it. Reverse this test and a deployment quietly runs on whatever a developer
  last committed.
- `is None` and not `if not os.environ.get(...)`. An empty string is a value, and the falsy test
  cannot tell an empty value from an absent one — that is P00 day 03 part 1.2's finding, and it is
  the reason `keys.get` documents "absent is `None`, never `''`".
- `value is not None` before the assignment, so a missing file leaves the environment untouched
  rather than writing `None` into it, which is a `TypeError` waiting for whoever runs this without a
  `.env`.
- `keys.require("GOOGLE_API_KEY")` **before** `export_key()`, and both before the session service and
  the runner are built. It raises `MissingKey` with a message naming the file and the line to add;
  the library's message names neither. Failing early with the better message is the entire reason
  this line exists, because both failures are about the same missing value and only one of them tells
  you where to put it.
- `export_key` is a named function rather than two lines inlined into `ask`. Day 10 puts the desk
  behind HTTP and the health endpoint needs to report whether the key is wired without asking a
  question; a named bridge can be called from both places.

## When it breaks

Before `export_key()` existed, this is what a correctly configured project got — observed on this
machine, with the key present in `.env` and spelled correctly:

```console
ValueError: No API key was provided. Please pass a valid API key. Learn how to create an API key at https://ai.google.dev/gemini-api/docs/api-key.
```

The sentence is true and it is about `os.environ`, which is empty; the person reading it is looking at
`.env`, which is not. So they check the file again, re-copy the key, restart the shell, and get the
same line — and the natural next move, exporting the variable by hand in that one terminal, works,
which "proves" the file is broken and sends the next hour in the wrong direction. The smallest fix is
the four-line bridge above. With it in place the same call reaches the provider and is refused for
the real reason:

```console
google.genai.errors.ClientError: 400 INVALID_ARGUMENT. {'error': {'code': 400, 'message': 'API key not valid. Please pass a valid API key.', 'status': 'INVALID_ARGUMENT', 'details': [{'@type': 'type.googleapis.com/google.rpc.ErrorInfo', 'reason': 'API_KEY_INVALID', 'domain': 'googleapis.com', 'metadata': {'service': 'generativelanguage.googleapis.com'}}, {'@type': 'type.googleapis.com/google.rpc.LocalizedMessage', 'locale': 'en-US', 'message': 'API key not valid. Please pass a valid API key.'}]}}
```

That is progress, not success: this machine has no working provider key, and the value in `.env` is
the synthetic one P00 day 02 wrote. The difference between the two messages is the whole point —
*no key was provided* became *this key is not valid*, which is a statement about the key rather than
about a place nobody was looking.

## In production

**What a senior writes instead.** They do not copy secrets between two stores at all. The process
environment is populated by the platform — a secret manager, a deployment manifest, an injected
file — and `.env` exists only on a developer's laptop, where a loader reads it at start-up and
nothing in the application knows it happened. And for the run itself they never rely on one channel:
the exception is caught at the edge and turned into a status code, *and* the error event is written
to structured logs with the invocation id, so the alert and the investigation are fed by different
paths and one of them failing does not blind the other.

**What degrades at scale.** The number is **zero recorded errors**. A consumer that reads only events
and never catches will treat `final=True` with no content as a completed turn — so at one failure in
every hundred questions, a desk answering a thousand questions a day files ten empty answers and
**zero** incidents, every day, and the failure rate you can measure is exactly nought however long you
look. The graph is flat because nothing is being written to it, and the only signal is users saying
the desk sent them a blank reply.

**The review comment.** "This wraps `run_async` in a `try/except` at the edge and turns it into a 502
— good. But the handler discards the events, so we never log `error_code` or `error_message`, and the
event stream is the only place the *invocation id* of the failed turn appears. Please log the final
event's error fields alongside the exception, so the alert and the session we need to look at are
joined up."

**The interview question.** "A framework reports a mid-run failure both by emitting an event that
carries the error and by re-raising out of the same call. Name one thing that breaks if you only
handle the event, one thing that breaks if you only catch the exception, and say which of the two you
would implement first in a service that has neither today."
