## One-line answer

An assertion that can no longer fail has silently withdrawn its protection from every case that
relied on it, and nothing in an ordinary green suite will ever say so — which is why this evalset
carries one **inverted case** whose whole job is to go red the moment the grounding assertion stops
objecting.

## The idea

The most useful person at a lifeboat drill is not the one holding the clipboard. It is the inspector
who, some time during the exercise, quietly pulls the fuse on the muster alarm and then stands back
to see how long it takes anybody to notice that the bell they are all relying on has gone silent.

That is a strange thing to do at first glance. The drill is about the boat. Nobody came to test the
bell. But think about what every other part of the exercise is resting on: the crew turn up at their
stations *because the alarm sounded*. If the alarm can fail without anybody knowing, then the boat
being sound, the davits turning and the falls running are all facts about a ship that will never be
told to use them. The bell is not one item on the list. It is the thing the rest of the list is
standing on.

Your evalset has one of those, and part 2.1 named it: `if tool not in tools_called:`. Every claim
this suite makes about grounding runs through that single line. The first case passes because the
desk called `check_service_status` and the line did not object. Add thirty more cases and they all
lean on the same line. Now imagine somebody refactoring — collecting tool names from a different
field, renaming something, adding an early `return` — and the line stops being reached. Nothing
breaks. Nothing raises. Every case still passes, because passing is what a case does when no
assertion objects, and an assertion that is never evaluated objects to nothing. The suite reports
green, faster than before, and it is now measuring nothing at all.

This is day 3's lesson arriving from a completely different direction. There, a check printed `RED`
and exited `0`: the verdict was discarded. Here nothing is discarded — the assertion simply has
nothing left to say. Both produce the same thing, which is a check that has quietly stopped being
one, and both are invisible in exactly the way that matters: **the broken version looks healthier
than the working one.** More green rows. Fewer complaints. Same screen.

So the general rule, stated once and then obeyed for the rest of the curriculum: **a check is worth
exactly what its red path is worth, and the red path is the one nobody runs.** Green is
self-testing — you see it every day, and it tells you nothing about whether red is reachable. Red
happens rarely, on somebody else's machine, usually under pressure. If you have never watched a
particular assertion fail, you have no evidence it can.

The answer this project adopts is an **inverted case**: a case whose declared expectation is its own
failure. `ungrounded-answer-is-caught` runs the `guesses` script — a scripted model that answers
without looking anything up — and the grounding assertion *must* object to it. If it objects, the
case is green: the detector works. If it stops objecting, the case goes red and says why, in a
sentence naming the consequence rather than the symptom. The evalset is no longer only checking the
desk. It is checking the instrument it checks the desk with, which is the only way a suite can make
a claim about its own red path without a human remembering to test it.

## The mechanism

Nothing new is written today. The mechanism is a two-word edit to `evals/harness.py`, printed whole
in part 2.1, and the point is what the evalset does about it.

The grounding assertion is weakened so that it can never object — the condition is replaced by
something permanently false, which is a fair stand-in for every real way a line stops being reached:

```diff
--- projects/01-ask-desk/evals/harness.py    as part 2.1 printed it
+++ projects/01-ask-desk/evals/harness.py    the break, inside `run_case`
     reasons = []
     for tool in case.get("expects_tools", []):
-        if tool not in tools_called:
+        if False:
             reasons.append(
                 f"expected the desk to call {tool!r} and it did not. It answered anyway, which "
                 f"means the answer was not grounded in anything this system knows."
             )
```

The whole of `expects_tools` is now decorative. Every case that names a tool still names it, the loop
still runs, the message is still written in the file — and no case can ever be failed by it again.
Run the suite:

```console
$ uv run --frozen python run.py eval
green  grounded-status-question  tools=['check_service_status']
RED    ungrounded-answer-is-caught (inverted)  tools=[]
       this case is supposed to fail and it passed. The desk answered without calling ['check_service_status'] and the grounding assertion did not object, so that assertion is no longer protecting any of the other cases.

1/2 case(s) passed
$ echo $?
1
```

*Observed on this machine on 2026-09-10, google-adk 2.8.0. No provider call was made.*

**Line by line:**

- Read the first row before the second, because the first row is the whole problem. `green
  grounded-status-question` — that case is now passing for no reason. Its `expects_tools` assertion
  cannot fail, so all that remains of it is the word *degraded* in the answer, which the scripted
  model would have said whether it looked anything up or not. Without the second row, this suite
  reports `1/1 case(s) passed` on a system whose grounding check has been deleted.
- `RED    ungrounded-answer-is-caught (inverted)` — the second row is the fuse-puller noticing. Not a
  human, not a code review: the suite, on the same run, with no extra command.
- The message names the **consequence**, not the symptom: *"that assertion is no longer protecting
  any of the other cases."* A message reading `AssertionError: expected failure` would have been true
  and useless. This one tells whoever is reading it, at whatever hour, what has actually been lost —
  and it is the sentence that stops somebody "fixing" the red row by deleting the strange case.
- `tools=[]` is the evidence sitting right beside the claim. The desk called nothing, and the
  assertion that exists to notice exactly that said nothing.
- `1/2 case(s) passed` and `echo $?` returning `1`. The count and the status agree, and you know they
  agree because the second command was typed. Day 3 part 2.2 is the deep version of why that habit
  exists.
- And note what the inverted case cost to run: it is one more entry in a JSON file and one branch in
  the scorer. This is the cheapest insurance in the project, and it is the only thing standing
  between a green suite and a suite that means nothing.

Put `if tool not in tools_called:` back, change nothing else, and the suite returns to the transcript
part 2.1 ends with: `2/2 case(s) passed`, exit `0`, with the inverted case explaining what it caught.

## When it breaks

The failure this document exists to prevent is not the weakened line. It is the response to the
weakened line, and it happens in a hurry. Somebody's refactor makes the suite go red on one strange
case that "is supposed to fail anyway", and the fastest way to a green pipeline is to delete it:

```console
RED    ungrounded-answer-is-caught (inverted)  tools=[]
       this case is supposed to fail and it passed. The desk answered without calling ['check_service_status'] and the grounding assertion did not object, so that assertion is no longer protecting any of the other cases.
```

Read as a bug report, that row is confusing — it says a case failed by passing, which sounds like a
harness problem rather than a code problem. Read as what it is, it is the only true thing on the
screen. The smallest fix is never to touch `cases.json`: restore the assertion. And the smallest
protection against the confusion is the one already in the file — the `_comment` on that case,
written so that whoever meets this row for the first time reads the reason before they reach for the
delete key.

## In production

**What a senior writes instead.** They do not hand-roll inverted cases for every assertion; they use
**mutation testing**, which does this systematically — it introduces small changes into the code
under test and reports which ones the suite failed to notice. Each surviving mutant is an assertion
that was not protecting anything. Where that is too heavy, they do the cheap version by hand, which
is this: for every assertion the suite leans on, one case that proves it can fail. And they treat a
suite's first red as an event worth recording — if an assertion has never once gone red in its life,
that is data about the assertion, not about the code.

**What degrades at scale.** Here the suite has two cases and one shared assertion, so the weakening
costs one green row that means nothing. Grow it to forty cases with thirty-eight leaning on that
line, and the same two-word edit leaves thirty-eight cases green and measuring nothing — and without
an inverted case the suite would print `40/40 case(s) passed` and exit `0`, which is a stronger claim
than it made before it broke. The damage scales with the size of the suite, and so does the
confidence, in the same direction.

**The review comment.** "This refactor moves the tool collection into the streaming branch, so on the
non-streaming path `tools_called` is always empty and `expects_tools` can no longer fail. The suite
is still green because nothing tests the assertion itself — please keep the inverted case and add one
for `forbids_text` too, since it has the same problem: it is a loop over an empty list in every
current case, so it has never once been executed."

**The interview question.** "You inherit a test suite that has been green for a year. Tell me
everything you would do to find out whether any of it is actually testing anything — and then tell me
which of those techniques you would put into CI so that the same question does not have to be asked
again next year."
