## One-line answer

An **eval** is a test whose subject is behaviour rather than a return value, and two decisions are
what make this one honest instead of decorative: it runs against a scripted stand-in so a red result
means *your code changed*, and it scores the **trajectory** — did the desk actually look the fact up
— rather than only the words, because a right answer nobody looked up is a right answer by accident.

## The idea

The boat goes into the water and comes back up, and the mate signs the drill card. That signature is
the part everybody stops thinking about, and it is the part that decides whether the drill was worth
anything, because there are two entirely different things the signature can mean.

It can mean *the officer watched the crew swing the davit out, run the falls, and get the boat to the
water*. Or it can mean *the boat is back in its chocks and the officer was on the bridge*. Both
produce the same signed card. The second is not fraud; it is the ordinary drift of a procedure that
is graded on its outcome instead of on what was done. Somewhere on that ship is a davit nobody has
turned in a year, and a card that says otherwise.

An **eval** is that card, written for a system whose behaviour is not fixed. Everything you have
tested up to now had one correct answer: `require_pinned` either raises or returns, `next_request`
either has three contents or two. A model does not work that way. Ask the same question twice and the
wording differs; ask it after the provider ships a new checkpoint and the reasoning may differ. So
you cannot assert on the string, and the temptation is to give up and assert on nothing — to check
that the desk *replied*, which is the signature-without-the-drill.

The way out is to notice what the two meanings of the signature actually differ about. Not the
outcome, which is identical. **What was done.** In an agent that difference is visible and it is
recorded: looking a fact up leaves a trace in the event stream, a tool call with a name on it. Day 8
made those events readable one by one; this part uses them as evidence. The sequence of what the
agent actually did during a run — which tools it called, in which order, before it answered — is
called the **trajectory**, and it is a thing you can assert on with the same confidence you assert
that a function returned `4`.

So this evalset asks the question that has exactly one defensible answer: *did the desk look it up,
or did it produce it?* A desk that says "the VPN is degraded" without ever having called
`check_service_status` was right by accident, and the accident is not repeatable. An eval that scored
only the prose would sign that card.

There is a second decision, and it is the one that keeps the whole thing from being muted within a
month. This evalset runs against `ask_desk/scripted.py` — the local stand-in day 8 printed, a **test
double**, which replays a fixed script and contacts nothing. Point an evalset at a live model and it
becomes a coin toss with a bill attached: it goes red on a Tuesday because a sampled token came out
differently, nobody can reproduce it, and after the third time somebody adds `continue-on-error` and
the check is gone. Against the double, the run is identical every time, so **a red result has exactly
one cause: this project's code changed.** That is what makes it a gate rather than a weather report.

The word for a collection of these cases is an **evalset**, and this one has two. The second is
strange enough to need its own document, which is part 2.2.

## The mechanism

Three new files, and one wiring change to the driver. First the cases, because the harness is easier
to read once you know what it is reading.

`projects/01-ask-desk/evals/cases.json`, whole file — synthetic, as all data in this curriculum is:

```json
{
  "_comment": "Synthetic evalset for P01 Ask Desk. Every case names the scripted behaviour it runs against, so a red result means this project's code changed and never that a model had an off day.",
  "cases": [
    {
      "name": "grounded-status-question",
      "question": "Is the VPN down?",
      "script": "looks_it_up",
      "expects_tools": [
        "check_service_status"
      ],
      "expects_text": [
        "degraded"
      ],
      "forbids_text": []
    },
    {
      "name": "ungrounded-answer-is-caught",
      "question": "Is the VPN down?",
      "script": "guesses",
      "expects_tools": [
        "check_service_status"
      ],
      "expects_text": [],
      "forbids_text": [],
      "expect_fail": true,
      "_comment": "Inverted: the scripted model answers without looking anything up. This case passes when the grounding assertion CATCHES it, and goes red if the assertion ever stops objecting."
    }
  ]
}
```

**Line by line:**

- The cases are **data, not code**. A case is a JSON object, so adding one is an edit to a file
  anybody can read and nobody can hide a bug in. The alternative — a Python file of test functions —
  works, and it lets a case do anything, which is precisely the freedom that turns an evalset into a
  program with its own bugs.
- `"name"` is used twice: it labels the row in the output, and the harness passes it as the
  `session_id`. Two cases therefore cannot see each other's conversation, and the name in a failure
  message is the same string you would use to find the session.
- `"script": "looks_it_up"` — the case names a *behaviour*, not a model. It cannot construct a model
  and it cannot reach the provider; the only models it can ask for are the ones the harness's
  `SCRIPTS` dictionary offers. The set of things this evalset can express is therefore visible in one
  place, which is a property worth more than the flexibility it costs.
- `"expects_tools": ["check_service_status"]` — the **load-bearing field**, and the reason this file
  is an eval rather than a string comparison. It asserts on the trajectory: this run must contain a
  call to that tool. Nothing about the wording of the answer can satisfy it.
- `"expects_text": ["degraded"]` — one word, not a sentence, and lower-cased by the harness before
  comparison. A single distinctive word from the source data is an assertion that survives rewording;
  a whole expected sentence is an assertion that breaks every time anything is rephrased, which is
  how prose assertions earn their reputation.
- `"forbids_text": []` — present and empty. An empty list is a statement: this case has no forbidden
  phrases, and the field is here so that adding one later is an edit rather than a schema change. It
  is the field where "never say the words *I think*" or a leaked identifier would go.
- `"expect_fail": true` on the second case, with its own `_comment` explaining the inversion. This is
  the field that makes the evalset check itself, and part 2.2 is entirely about it. Read the comment
  now and the code for it in a moment; the argument comes next door.
- `"_comment"` keys at both levels. JSON has no comment syntax, and an underscore-prefixed key that
  the reader ignores is the conventional way around it. The alternative — putting the explanation in
  a `README` beside the file — separates the reason from the thing, and the reason is what stops
  somebody deleting the strange-looking case in six months.

`projects/01-ask-desk/evals/harness.py`, whole file — the runner and the scorer:

```python
# evals/harness.py
"""The smallest eval that can go red, and the reason it can.

An eval is a test whose subject is a model's behaviour rather than a function's return value. This
one asks a question that has exactly one defensible answer — *did the desk look the fact up, or did
it produce one?* — and it can answer that without judging prose, because looking something up
leaves a trace: a tool call in the event stream.

Two decisions make this honest rather than decorative.

**It runs against a scripted model** (`ask_desk/scripted.py`), so the same input produces the same
events every time. An eval against a live model is a coin toss with a bill attached: it goes red on
a Tuesday for reasons nobody can reproduce, and a check that goes red at random gets muted. Here a
red result means the code changed.

**It asserts on the trajectory, not only on the text.** `expects_tools` is the load-bearing field.
A desk that answers "the VPN is degraded" without having called `check_service_status` produced the
right words by accident, and an eval that scored only the words would pass it — which is the
failure this file exists to catch.

All cases and all data are synthetic.
"""

from __future__ import annotations

import asyncio
import json
import sys
from dataclasses import dataclass
from pathlib import Path
from typing import Any

from google.genai import types

from ask_desk import agent, scripted
from google.adk.sessions import InMemorySessionService

CASES_FILE = Path(__file__).with_name("cases.json")

#: The scripts a case may name, by the key it uses. A case never constructs a model itself, so the
#: set of behaviours the evalset can express is visible in one place.
SCRIPTS = {
    "looks_it_up": scripted.LOOKS_IT_UP,
    "guesses": scripted.GUESSES,
}


@dataclass
class Result:
    """What one case produced, and why it passed or failed."""

    name: str
    passed: bool
    reasons: list[str]
    tools_called: list[str]
    answer: str
    inverted: bool = False


async def run_case(case: dict[str, Any]) -> Result:
    """Run one case and score it against what it declared it expects."""
    model = scripted.ScriptedModel(SCRIPTS[case["script"]], name=case["script"].replace("_", "-"))
    desk = agent.build_desk(model)
    sessions = InMemorySessionService()
    await sessions.create_session(app_name=agent.APP_NAME, user_id="eval", session_id=case["name"])
    runner = agent.build_runner(sessions, desk)

    message = types.Content(role="user", parts=[types.Part(text=case["question"])])
    tools_called: list[str] = []
    answer = ""
    async for event in runner.run_async(
        user_id="eval", session_id=case["name"], new_message=message,
        run_config=agent.run_config(),
    ):
        tools_called.extend(call.name for call in event.get_function_calls())
        if event.is_final_response() and event.content and event.content.parts:
            answer = "".join(part.text for part in event.content.parts if part.text)

    reasons = []
    for tool in case.get("expects_tools", []):
        if tool not in tools_called:
            reasons.append(
                f"expected the desk to call {tool!r} and it did not. It answered anyway, which "
                f"means the answer was not grounded in anything this system knows."
            )
    for phrase in case.get("expects_text", []):
        if phrase.lower() not in answer.lower():
            reasons.append(f"expected {phrase!r} in the answer; got {answer!r}")
    for phrase in case.get("forbids_text", []):
        if phrase.lower() in answer.lower():
            reasons.append(f"{phrase!r} must not appear in the answer; got {answer!r}")

    # An `expect_fail` case is the evalset checking itself. Its subject is not the desk but the
    # assertion above it: the scripted model deliberately answers without looking anything up, so
    # the case *must* produce a reason. If it stops producing one, the grounding check has been
    # weakened and every other case built on it is now worth less than it looks.
    if case.get("expect_fail"):
        if reasons:
            return Result(case["name"], True,
                          [f"failed as intended: {reasons[0]}"], tools_called, answer, True)
        return Result(case["name"], False, [
            "this case is supposed to fail and it passed. The desk answered without calling "
            f"{case.get('expects_tools')} and the grounding assertion did not object, so that "
            "assertion is no longer protecting any of the other cases."], tools_called, answer, True)

    return Result(case["name"], not reasons, reasons, tools_called, answer)


def main() -> int:
    """Run every case. Exit non-zero if any failed — the status is the verdict, as day 3 said."""
    cases = json.loads(CASES_FILE.read_text(encoding="utf-8"))["cases"]
    results = [asyncio.run(run_case(case)) for case in cases]

    for result in results:
        label = "green" if result.passed else "RED  "
        note = " (inverted)" if result.inverted else ""
        print(f"{label}  {result.name}{note}  tools={result.tools_called or '[]'}")
        if not result.passed or result.inverted:
            for reason in result.reasons:
                print(f"       {reason}")

    failed = [r for r in results if not r.passed]
    print(f"\n{len(results) - len(failed)}/{len(results)} case(s) passed")
    return 1 if failed else 0


if __name__ == "__main__":
    sys.exit(main())
```

**Line by line:**

- `CASES_FILE = Path(__file__).with_name("cases.json")` — resolved against **this file**, not against
  the working directory. `Path("evals/cases.json")` would find the file when you run from the project
  root and silently find nothing from anywhere else, and "silently" is the operative word: the
  evalset would report zero cases, print `0/0 case(s) passed`, and exit `0`. This is the same trap
  day 4 hit with `.env`, and it has the same one-line answer.
- `SCRIPTS` as a module-level dictionary is a **whitelist**, and its value is negative: a case that
  names a script not in it raises `KeyError` immediately, rather than being skipped or defaulting to
  something. A test framework that silently skips is worse than one that crashes, because a skipped
  case reports green.
- `@dataclass class Result` with `passed`, `reasons`, `tools_called` and `answer` — the result carries
  the **evidence**, not only the verdict. When a case goes red at three in the morning, `tools_called`
  and `answer` are on the screen already and nobody has to re-run anything to find out what happened.
  `reasons` is a list because one case can fail several assertions and you want all of them in one
  run, exactly as day 3's checks collect problems instead of raising on the first.
- `inverted: bool = False` defaulted last, because a dataclass cannot have a field without a default
  after one with a default. It is a display flag: it puts `(inverted)` in the output so that nobody
  reading the transcript mistakes the strange case for a broken one.
- `scripted.ScriptedModel(SCRIPTS[case["script"]], name=...)` — a fresh model per case. Sharing one
  across cases would share its call counter and its position in the script, and case two would start
  wherever case one stopped. Test isolation is not a principle here; it is arithmetic.
- `name=case["script"].replace("_", "-")` — the double labels itself, and day 8's file explains the
  rule it is obeying: a scripted model's identity appears in any log or event it produces, so nothing
  it emits can be mistaken for a provider response.
- `agent.build_desk(model)` and not the module-level `agent.desk` — `desk` is pinned to the real
  model, and this is the seam day 8 added for exactly this purpose. The agent under test is the same
  configuration, the same instruction and the same three tools; only the brain is swapped. Everything
  the eval scores is therefore this project's code.
- A fresh `InMemorySessionService()` per case, with `session_id=case["name"]` — two isolations, one
  belt and one braces. Different service objects mean nothing is shared even in principle; distinct
  session ids mean that if somebody later hoists the service out of the loop, the cases still do not
  see each other's history.
- `tools_called.extend(call.name for call in event.get_function_calls())` — this line **is** the
  trajectory. `get_function_calls()` returns the tool calls carried by one event, and day 8's
  transcripts show them arriving as their own events with no text attached. Accumulating the names
  across the run turns the event stream into a list you can assert on.
- `if event.is_final_response() and event.content and event.content.parts:` — the same guard
  `agent.ask` uses, and the same reason: the concluding message of the turn is the one with the
  answer in it, and the two `and` clauses are not defensive noise. An event can carry no content at
  all — the tool-call and tool-result events in day 8's transcript carry `''` — and indexing into
  `None` is how a scorer crashes on a run that was fine.
- `answer = "".join(...)` **assigns** rather than appending. Under the non-streaming run config the
  final event carries the whole answer, so assignment is correct; day 8's deliberate failure was
  precisely what happens when you accumulate text from every event and the final one repeats what the
  partials already delivered. Assignment here is that lesson written as one character.
- The three assertion loops are `for tool in case.get("expects_tools", [])` and its two siblings, all
  using `.get(..., [])`. A case that omits a field asserts nothing about it, which means a new field
  can be added to the harness without editing every existing case.
- `if tool not in tools_called:` — **the grounding assertion**, and the single most important line in
  the file. It is what says the answer had to come from somewhere. Part 2.2 weakens exactly this line
  and watches what the evalset does about it.
- The failure message says more than "assertion failed": *"It answered anyway, which means the answer
  was not grounded in anything this system knows."* A failure message is read by whoever is least
  familiar with the code, usually under pressure, and its job is to explain why the check exists.
- `phrase.lower() not in answer.lower()` — case-insensitive substring, on both sides. Not a regular
  expression, not an exact match. This is the weakest useful prose assertion and that is deliberate:
  strong prose assertions break on rewording and get deleted, and a deleted assertion protects
  nothing.
- `forbids_text` mirrors `expects_text` with the condition inverted, in a separate loop rather than a
  flag on the first. Two loops of three lines are easier to read than one loop with a boolean in it,
  and the failure messages can then say different things.
- The `expect_fail` block returns **early**, and it returns `passed=True` when `reasons` is
  non-empty. That inversion is the subject of part 2.2 and is not argued here; what belongs here is
  its shape — it is written as a branch over the *same* `reasons` list every other case is scored
  from, so it cannot drift away from what it is protecting.
- `return Result(case["name"], not reasons, ...)` — `not reasons` is the ordinary verdict: an empty
  list of reasons is a pass. Same convention as day 3's checks, one repository over.
- `results = [asyncio.run(run_case(case)) for case in cases]` — `asyncio.run` per case, so each case
  gets its own event loop and one case's stray task cannot outlive it into the next. It also means
  the cases run strictly in order, one at a time, which is what you want from something whose output
  you are going to read as a transcript.
- `label = "green" if result.passed else "RED  "` with the trailing spaces — the columns line up, and
  aligned columns are how you scan twenty rows for the one that is different. `RED` is upper case for
  the same reason.
- `if not result.passed or result.inverted:` — reasons are printed for failures **and** for inverted
  cases even when they pass. The inverted case's reason is the interesting output of a green run: it
  is the evalset saying, in words, what it just caught.
- `print(f"\n{len(results) - len(failed)}/{len(results)} case(s) passed")` — a count, and both halves
  of it. `2/2` and `2 passed` are different sentences: only the first tells you nothing was skipped.
- `return 1 if failed else 0` from `main`, and `sys.exit(main())` under `__main__`. Day 3 part 2.2 is
  the deep version and the reason it is repeated here rather than assumed: the exit status is the
  verdict, and a scorer that prints RED and exits `0` is a scorer that has been switched off.

**Line by line:**

- `check_evals_go_green` is the sixth entry in `CHECKS` and the only one whose subject is
  **behaviour**. The other five ask whether the project is configured correctly; this one asks whether
  it still does what it did. That is the line between a config linter and a gate, and it is one
  dictionary entry wide.
- It is last in the dictionary on purpose. The dictionary is iterated in insertion order — a language
  guarantee since 3.7 — so the cheap questions are answered first and the slowest check runs after
  everything that could have made it pointless. A red `model` check above it explains a red `evals`
  check below it.
- `import evals` **inside the function**, in both places. `check` must run on a machine where a
  half-finished evalset does not import; pushing the import down means the failure is a red check with
  a name on it rather than a traceback before any check has run.
- `if evals.main() != 0:` — the check calls `main` and reads its **exit status**, not its output. The
  harness already printed its own rows to the screen by the time this line runs, which is why the
  returned problem string says "see the output above" instead of trying to summarise what the reader
  can already read.
- The problem string is deliberately vague, and that is the one place in this project where vague is
  right: the harness's own message is specific, it is above, and repeating it here would give the

- `case ["eval"]` before `case ["serve"]` — order among literal patterns is irrelevant to matching
  and relevant to reading. The match block is the file's table of contents.

  screen and the status underneath must agree, and you do not know that they do until you have typed
  the second command.

## When it breaks

The way this file gets built wrong is to skip the double and point the evalset at the real model,
because that feels like testing the real thing. On this machine it does not run at all; on a machine
with a working key it runs and becomes unreliable. This is what the real-model path actually produces
here, observed from `run.py adk`, and an eval wired to that path inherits it exactly:

```console
google.genai.errors.ClientError: 400 INVALID_ARGUMENT. {'error': {'code': 400, 'message': 'API key not valid. Please pass a valid API key.', 'status': 'INVALID_ARGUMENT', 'details': [{'@type': 'type.googleapis.com/google.rpc.ErrorInfo', 'reason': 'API_KEY_INVALID', 'domain': 'googleapis.com', 'metadata': {'service': 'generativelanguage.googleapis.com'}}, {'@type': 'type.googleapis.com/google.rpc.LocalizedMessage', 'locale': 'en-US', 'message': 'API key not valid. Please pass a valid API key.'}]}}
```

Somebody shipped that evalset on a Friday. It could not run in CI at all, because CI had no key, so
they gave CI a key — and then it went red on a Tuesday with no code change, twice, and on the third
time somebody marked the step as allowed to fail. The check is now decoration and the repository
still contains it, which is worse than not having one. The smallest fix is the seam day 8 built:
`agent.build_desk(model)` with a scripted double, so the run needs no key, costs nothing, and is the
same every time.

## In production

**What a senior writes instead.** They keep this shape and add a second tier above it. The scripted
evalset stays in `check` and runs on every push, because it is deterministic and free. A separate
suite that does hit a live model runs on a schedule, never in the pull-request gate, and is judged on
a trend rather than on a single run — because a live-model suite that blocks a merge will be
disabled, and one that reports a weekly number will be read. They also make the trajectory assertion
ordered where order matters: `expects_tools` here is a set membership test, and a case that requires
`search_notes` *before* `fetch_note` needs a sequence assertion, which this harness would have to
grow a field for.

**What degrades at scale.** A suite of forty cases against a live model is forty provider requests on
every push, and on a free tier whose ceiling this project could not even find published, that is a
suite which begins failing for quota reasons rather than for quality reasons. Against the double it
is zero requests and the same wall-clock cost on every machine. The number that matters more than
either is the flake rate: at even 2% per case, a forty-case live suite is red on more than half its
runs for no reason, and a check that is usually red for no reason has already been switched off in
everybody's head before anybody switches it off in the file.

**The review comment.** "This eval only checks the text of the answer. Add the tool assertion —
otherwise a model that hallucinates the right status string passes, and that is the exact regression
we are trying to catch. And point it at the scripted model: as written it needs a key, which means it
cannot run in CI, which means it will not run."

**The interview question.** "Your agent's eval suite has been green for two months and then somebody
notices the agent has been answering from memory instead of calling the search tool. Explain how a
green suite is compatible with that, and describe the assertion you would add — then tell me how you
would prove that the new assertion can actually fail."
