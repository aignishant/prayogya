## One-line answer

One turn against this provider is a POST to a URL that names the model, a key carried in a header
rather than in the address, a JSON body holding the whole conversation and the standing orders, and
a reply whose words live at `candidates[0].content.parts[].text` — and the moment the reply is sent
the server has forgotten every part of it.

## The idea

You write a letter. You put it in an envelope, you address the envelope, you put a stamp on it, and
you post it. Some while later a reply comes back through the door. That is the entire transaction,
and it has a property so ordinary that it is easy to miss: **the post office kept nothing.** There
is no file at the sorting office with your name on it. If you want to know what you wrote, you look
at your own carbon copy.

Four things go into that envelope and each one has a decision behind it.

**The address.** Which model, spelled out. The provider's reference page gives the endpoint as a
template, and from `https://ai.google.dev/api/generate-content`, checked 2026-09-09, it is verbatim:

> `https://generativelanguage.googleapis.com/v1beta/{model=models/*}:generateContent`

The model ID is *in the URL*. It is not a field you can forget in the body and it is not negotiated;
the address names the correspondent, which is why part 1.1 spent a whole document on the string that
goes in that slot.

**The credential.** It travels in a header — a separate line on the outside of the envelope that
the sorting office reads and the recipient's filing clerk does not copy into the record. Put it in
the address instead, as a query parameter, and it lands in the server's access log, in your shell
history, and in every proxy between you and them. It is one extra line of code and it is the
difference between a secret and a published one.

**The body.** JSON, and its most important field is called `contents` — plural, a list. Each item is
one **turn**: a piece of the conversation together with who produced it. The producer is the `role`,
and the provider is precise about what may go there. From the same page, verbatim:

> The producer of the content. Must be either 'user' or 'model'.

Two values. You are `user`; the thing answering is `model`. Nothing else is a legal producer of a
turn, and that fact becomes the whole of part 2.2. Alongside `contents` the body may carry a
**system instruction** — standing orders that are not part of the back-and-forth — and, from day 5,
the tools the model is allowed to reach for.

**And the reply**, which is where most first attempts go wrong, because the words are not at the top
level. The response carries a list of **candidates**: complete alternative answers the model could
have given, of which this project ever asks for one. Inside a candidate is a `content` — the same
shape as a turn you sent, with a role and a list of parts — and inside the parts are the pieces. A
part holding text has a `text` key. On day 5 a part can hold a request to call a tool instead. So
the words are three levels down, and code that reaches for `response["text"]` is code that has
guessed.

Now the thing this project owes you in plain words, because it changes what you should do with this
document. **The provider no longer recommends this endpoint for new work.** From
`https://ai.google.dev/gemini-api/docs/migrate-to-interactions`, checked 2026-09-09, verbatim:

> While `generateContent` remains fully supported, we recommend the Interactions API for all new
> development.

That is the whole quotation, and both halves of it are load-bearing. `generateContent` is not
deprecated: its reference page is live, it carries the complete request and response schema, and it
is absent from the deprecations list. The newer Interactions API is *stateful* — it holds the
conversation on the server, and the next turn refers back to the previous one by identifier.

This project uses the stateless one deliberately, and the reason is the subject of tomorrow's half
of this day rather than a preference. The loop this day is about — you hold the conversation, you
resend it, you can drop a turn and watch what happens — is exactly the part the stateful API
performs on your behalf. Teaching it there would mean teaching a loop that is mostly not there.
Build first, compare after: the comparison is owed and the decision is written down, dated, in
`docs/adr/ADR-0004-generatecontent-by-hand-and-unpublished-limits.md`, along with what it costs.

## The mechanism

`projects/01-ask-desk/ask_desk/provider.py` as day 4 leaves it — the whole file, standard library
only, nothing between your code and the wire. Day 5 appends to the bottom of it; everything below
is what exists today:

```python
# ask_desk/provider.py
"""One turn against the provider: build a request, send it, read the reply. No framework.

This is the whole surface this project uses on day 1, written with the standard library only, so
that nothing between your code and the wire is hidden.

The endpoint is `generateContent`, which is **stateless**: it holds no memory of previous calls, so
every turn resends the entire conversation. That is not a limitation to work around — it is the
reason the loop in `loop.py` is visible code rather than something the server does for you.

The provider now recommends a newer, stateful Interactions API for new development. Its migration
page says, on 2026-09-09, that `generateContent` "remains fully supported"; the endpoint's own
reference page is live and it is absent from the deprecations list. This project uses it
deliberately, and `PROJECT.md` says why.

Verified against https://ai.google.dev/api/generate-content on 2026-09-09.
"""

from __future__ import annotations

import json
import urllib.error
import urllib.request
from typing import Any

from ask_desk.util import keys, models


class ProviderError(RuntimeError):
    """A request reached the provider and the provider refused it.

    Carries the HTTP status and the parsed body, because code that retries needs the status and a
    human reading the log needs the message, and collapsing them loses one or the other.
    """

    def __init__(self, status: int, body: dict[str, Any]) -> None:
        error = body.get("error", {})
        self.status = status
        self.code = error.get("code")
        self.message = error.get("message", "")
        self.body = body
        super().__init__(f"HTTP {status}: {self.message or body!r}")


def build_request(
    contents: list[dict[str, Any]],
    *,
    model: str = models.ANSWERING,
    system_instruction: str | None = None,
    tools: list[dict[str, Any]] | None = None,
) -> tuple[str, dict[str, Any]]:
    """Return the (url, body) this turn would send. Sends nothing.

    Split out from `send` on purpose: a function that builds a request and a function that performs
    one are two different things to test, and only one of them needs the network or a key.
    """
    models.require_pinned(model)
    url = f"{models.BASE_URL}/{models.API_VERSION}/models/{model}:generateContent"
    body: dict[str, Any] = {"contents": contents}
    if system_instruction is not None:
        body["system_instruction"] = {"parts": [{"text": system_instruction}]}
    if tools:
        body["tools"] = [{"function_declarations": tools}]
    return url, body


def send(url: str, body: dict[str, Any], *, timeout: int = 60) -> dict[str, Any]:
    """POST the body and return the parsed response, or raise `ProviderError`."""
    request = urllib.request.Request(
        url,
        data=json.dumps(body).encode("utf-8"),
        headers={
            "Content-Type": "application/json",
            # The key travels in a header, never in the query string: a key in a URL is a key in
            # the server's access log, in your shell history, and in every proxy in between.
            "x-goog-api-key": keys.require("GOOGLE_API_KEY"),
        },
        method="POST",
    )
    try:
        with urllib.request.urlopen(request, timeout=timeout) as response:
            return json.loads(response.read().decode("utf-8"))
    except urllib.error.HTTPError as exc:
        raw = exc.read().decode("utf-8", errors="replace")
        try:
            parsed = json.loads(raw)
        except json.JSONDecodeError:
            parsed = {"error": {"message": raw}}
        raise ProviderError(exc.code, parsed) from exc


def first_candidate(response: dict[str, Any]) -> dict[str, Any]:
    """The one candidate this project ever asks for, or a clear failure saying there was none.

    A response with no candidates is a real outcome — the prompt was blocked, or generation stopped
    before anything was produced — and `response["candidates"][0]` would meet it with an IndexError
    that names nothing.
    """
    candidates = response.get("candidates") or []
    if not candidates:
        feedback = response.get("promptFeedback", {})
        raise ProviderError(200, {"error": {
            "message": f"the response carried no candidates; promptFeedback={feedback!r}"}})
    return candidates[0]


def text_of(candidate: dict[str, Any]) -> str:
    """Join every text part of a candidate. Parts that are not text are skipped, not stringified."""
    parts = candidate.get("content", {}).get("parts", [])
    return "".join(part["text"] for part in parts if "text" in part)
```

**Line by line:**

- The module imports **four standard-library names and two of this project's own modules**, and
  nothing else. That is not minimalism for its own sake: a framework between you and this request
  would be doing the thing the day is about, and you would learn its API instead of the protocol.
  Day 6 brings the framework in, and by then you will know what it is doing.
- `ProviderError` stores `status`, `code`, `message` **and** the whole `body`, and only then calls
  `super().__init__` with a formatted string. Three audiences, three needs: retry logic branches on
  the status, a human reads the message, and whoever is debugging next month wants the field the
  other two threw away. Collapsing them into one string is the commonest version of this class and
  the one that makes a 429 indistinguishable from a 400 without parsing English.
- `error = body.get("error", {})` with `.get` at every level. This object is constructed on the
  failure path, and an exception constructor that raises `KeyError` because the error body was not
  the shape you expected replaces a useful message with a confusing one, at the worst moment.
- `build_request` takes `contents` positionally and everything else **keyword-only**, which is what
  the bare `*` in the signature does. `build_request(contents, model, system)` is a call whose
  arguments can silently swap places on the next edit; `build_request(contents, model=...)` cannot.
  The conversation is the argument this function is *about*, so it is the one that stays positional.
- `models.require_pinned(model)` is the **first statement in the body**, before the URL is even
  built. An unregistered model is caught while the request is a dict on your machine rather than
  after a round trip, and the message you get names your registry rather than the provider's
  catalogue.
- The URL is assembled from `models.BASE_URL`, `models.API_VERSION` and the model, in that order,
  and it matches the provider's documented template with the `{model=models/*}` slot filled in.
  Nothing about the address is spelled locally, so a version bump is one edit in `models.py`.
- `body: dict[str, Any] = {"contents": contents}` — the annotation on the assignment is there so
  that adding `body["tools"]` below does not make a type checker infer the dict as
  `dict[str, list[...]]` from its first key and then object. Small, and it is why the annotation is
  on the variable rather than left to inference.
- `if system_instruction is not None` — `is not None`, not truthiness. An empty string is a
  deliberate instruction to say nothing extra, and the truthy test would silently drop it and send
  a request with no standing orders at all.
- The system instruction is wrapped as `{"parts": [{"text": ...}]}`. It is the same `parts` shape as
  a turn, because the provider models it as content rather than as a header, and code that sends a
  bare string here gets a rejection about the field's type rather than about its value.
- `if tools:` is truthiness here, and deliberately different from the line above it. An empty list of
  tools and no tools at all are the same situation — nothing to offer — and sending `"tools": []`
  would be a claim about an empty toolbox rather than the absence of one. Day 4 never passes this
  argument; day 5 is where it is filled, and part 2.1 shows the call site that leaves it out.
- `build_request` **returns and sends nothing**. That single decision is what makes the rest of the
  day possible: the shape of a turn can be printed, diffed, asserted on and put in a document with
  no key, no network and no cost. It is also how this day's deliberate failure is demonstrated, in
  part 2.2, without a single request being made.
- `send` takes the `url` and `body` it was given rather than rebuilding them. Two functions, two
  responsibilities: one that needs nothing and one that needs a key, a socket and a live provider.
  Only one of them is hard to test, and it is now the small one.
- `json.dumps(body).encode("utf-8")` — explicit encoding rather than leaving it to a default.
  Whatever locale this runs under, the bytes on the wire are the bytes the provider parses.
- `"x-goog-api-key"` in `headers`, with the comment kept in the file. This is the line most worth
  copying out of this project. A key in a query string is recorded by every hop that logs URLs, and
  none of those logs are treated as secret storage.
- `keys.require("GOOGLE_API_KEY")` is called **here, at send time**, not at import. A module that
  reads a secret when it is imported cannot be imported by a check that is trying to report the
  secret is missing, and `run.py check` does exactly that.
- `method="POST"` is passed explicitly even though supplying `data` already makes the request a
  POST. The explicit argument is for the reader: the alternative is knowing a rule about `urllib`.
- `timeout=timeout` on `urlopen`, with a default in the signature. That argument is the only bound
  this call has on how long it will wait. Remove it and a connection that never answers holds this
  worker until something outside the process intervenes.
- The `except urllib.error.HTTPError` block **reads the body before doing anything with it**. That
  exception object is also a file-like response, and the error detail is in its body; code that
  catches it and prints only `exc.code` has thrown away the sentence that says what was wrong.
- The nested `try` around `json.loads` handles a non-JSON error body — an HTML page from a proxy, or
  a gateway's own text. Without it a bad gateway becomes a `JSONDecodeError` raised from inside your
  error handler, and the original status is lost entirely.
- `raise ProviderError(...) from exc` — the `from` keeps the original exception as the cause, so the
  traceback shows both the HTTP failure and the class you raised. Dropping `from` produces a
  traceback that starts at your `raise` and hides where it came from.
- `first_candidate` refuses an empty list **with a message**, and it is worth being clear about why
  this is not paranoia: a response carrying zero candidates is a documented outcome, not a bug, and
  `response["candidates"][0]` meets it with an `IndexError` that names no file, no field and no
  cause. Including `promptFeedback` in the message means the reason is in the log the first time it
  happens rather than after somebody adds a print statement.
- `ProviderError(200, ...)` — a **200** on the failure path, which looks odd and is honest. The
  request succeeded; the outcome was empty. Reusing the class keeps one type for callers to catch,
  and the status field still tells the truth about what the transport did.
- `text_of` filters with `if "text" in part` rather than indexing every part. A candidate may hold
  parts that are not text — from day 5, a request to call a tool — and the indexing version raises a
  `KeyError` on a perfectly valid reply. Skipping is the behaviour that keeps working when the
  protocol grows.
- `"".join(...)` and not `parts[0]["text"]`. A reply may arrive in several text parts, and taking
  the first one silently truncates the answer, which is a failure nobody notices because the answer
  still reads like an answer.

### The request, without sending it

`build_request` sends nothing, so the exact bytes of a turn can be printed on a machine with no key
and no network. This is the shape of one letter, addressed and stamped, sitting on the desk:

```console
$ uv run --frozen python run.py plan "Is the VPN down?"
POST https://generativelanguage.googleapis.com/v1beta/models/gemini-3.8-flash:generateContent

{
  "contents": [
    {
      "role": "user",
      "parts": [
        {
          "text": "Is the VPN down?"
        }
      ]
    }
  ],
  "system_instruction": {
    "parts": [
      {
        "text": "You are an internal IT ask desk. Answer from the notes you are given and nothing else. If the notes do not cover the question, say so plainly and do not guess."
      }
    ]
  }
}
```

**Line by line:**

- The first line is the address, and the model ID is sitting in it — `gemini-3.8-flash`, from
  `models.ANSWERING`, through `require_pinned`, into the URL. Every request this project makes can
  be checked for which model it named by looking at one line.
- `contents` is a **list with one item**, on the first turn. That is the fact part 2.1 is built on:
  it is a list because it is going to grow, and it grows in your process because it grows nowhere
  else.
- The one item has `"role": "user"` — one of the two values the provider's reference permits — and
  `parts`, a list, holding one object with a `text` key. This is the same shape the reply will come
  back in, which is what makes filing a reply into the thread a plain `append` in part 2.1.
- `system_instruction` is a **sibling of `contents`, not a member of it**. The standing orders are
  not a turn in the conversation; nobody said them in the exchange. That placement is why they can
  be resent on every request without the transcript filling up with copies of themselves.
- There is **no `tools` key**, because `build_request` was not given any. Day 5 changes the caller
  and this same command grows a third top-level key; that difference is the clearest picture of what
  tools actually are — a field in a request.
- There is **no key anywhere in this output**, and there is nothing to redact before pasting it into
  a bug report. That is the header decision paying off in an unexpected place.
- Nothing was sent. This command needs no credential and consumes no quota, which makes it the right
  thing to reach for when a request is behaving strangely: look at the letter before blaming the
  post.

*Observed on this machine on 2026-09-09, uv 0.12.3, CPython 3.12.12, with `next_request` as day 4
leaves it.*

## When it breaks

The request above is correct in every particular, and the provider still refuses it, because the
value in `.env` on this machine is the synthetic one day 2 wrote. This is what `ProviderError`
carries back, verbatim — part 2.1 shows the same rejection travelling all the way out of the driver:

```text
HTTP 400: 'API key not valid. Please pass a valid API key.'
```

Notice what did not happen: `keys.require` raised nothing. The value is present and non-empty, every
check that runs on this machine passed, and the credential is still wrong — only the provider holds
the other half, and only the provider can settle it.

The status is the trap. The provider's own error page at
`https://ai.google.dev/gemini-api/docs/api-errors`, checked 2026-09-09, lists this case verbatim as
`authentication` · **401 Unauthorized** · *"The API key is missing, invalid, or expired."* What
actually arrives is **400**, on this machine, with the status string `INVALID_ARGUMENT` — the same
disagreement day 3 hit against the models endpoint, so it is not a one-off. Somebody wrote
`if exc.status == 401:` to mean *bad credentials*, this rejection fell past it into the retry
branch, and a request that could never succeed was sent again until a quota stopped it. The smallest
fix is to branch on the status you have observed and to leave a comment saying the documentation
disagrees; the observation is what your code will meet.

## In production

**What a senior writes instead.** An HTTP client with connection reuse and a configured timeout —
`httpx` or `requests` behind a small wrapper — and a response parsed into a typed object rather than
walked as nested dictionaries, so a change in the reply's shape is a failure at the boundary instead
of a `KeyError` in the middle of business logic. They also separate the two functions the same way
this file does, because the only part that needs a network is `send`, and a test suite that needs a
network for every case is a test suite that gets skipped. `urllib` is here so that nothing is
hidden; it is not what ships.

**What degrades at scale.** The number is **60**, and it is the only bound in this file. `timeout=60`
is what stops one unresponsive connection from holding a worker indefinitely — and it is per
request, not per question, so on day 5 a question that makes six provider calls can hold a worker
for six of those bounds end to end. Run eight workers, get eight simultaneous stalls, and the
service is fully occupied while doing nothing. Bounds compose by multiplying, which is why the
per-question call limit day 5 adds is a different bound and not a redundant one.

**The review comment.** "The key is going out as `?key=...` on the URL. That puts a live credential
into the access log of every hop between us and the provider, and into the shell history of anyone
who reproduces the call. Move it to the `x-goog-api-key` header. Separately, this reads
`response['candidates'][0]['content']['parts'][0]['text']` inline — a blocked prompt returns no
candidates and a tool call returns no text part, and both of those become an unlabelled `IndexError`
in the request handler."

**The interview question.** "You are integrating a JSON HTTP API you do not control. Describe every
place the response can differ from the shape you coded against, which of those differences your code
should treat as a bug and which as a normal outcome, and how you would find out which is which
before your users do."
