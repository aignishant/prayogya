## One-line answer

`session_service` is the only keyword argument on `Runner` with no default — every other one is
`None` — which is the framework refusing to build an agent that has nowhere to keep a conversation,
and that refusal is the exact bug day 4 had to cause on purpose; the failure worth studying today is
not that one, but the one underneath it, where a request that can never succeed is retried anyway.

## The idea

The agency has a counter, and there is one thing you cannot get past it without. Not the brief — they
will take a job with half the brief missing and ask you later. Not the deadline, not the budget code,
not even a name for the job. What they will not do is open a job with no file to put it in. The
clerk turns the form round and points at the empty box, and the conversation stops there.

It looks like bureaucracy until you have seen the alternative. A job with no file is a job where every
call starts from nothing: you ring on Tuesday about the thing you rang about on Monday, and you are
asked, politely, what this is regarding. Everybody involved is working properly. Every individual
exchange is correct. The whole arrangement is useless, and it is useless in a way that nobody inside
it can see — the clerk on Tuesday has no evidence that Monday happened.

Day 4 built that failure deliberately, in your own code, by not filing the model's reply: the same
question, asked twice, arriving as two openings rather than a conversation. The framework has made
that particular mistake impossible to make by accident. It is the one thing the counter refuses.

The second half of this part is a different kind of failure, and it is the one this document is
`failure: true` for. Ask the desk a real question with a key that is not valid, and the request is
refused by the provider — correctly, immediately, permanently. What comes back is not a clean
refusal. It is a stack in which something has been *retrying*, which is what you do with a queue that
is busy, not with a door that is locked. Nothing about a bad key gets better by asking again.

## The mechanism

Two of the four lines from the probe printed whole in part 1.2 — the same run, the same command, the
two failures it caused on purpose:

```text
ValidationError -> Value error, Node name 'ask desk' must be a valid Python identifier. [type=value_error, input_value='ask desk', input_type=str]
TypeError -> Runner.__init__() missing 1 required keyword-only argument: 'session_service'
```

**Line by line:**

- Both arrive at **construction**. No key was read, no network existed, nothing was asked of a model.
  This is the cheapest possible moment for a failure to happen and the framework is spending it well.
- `Value error, Node name 'ask desk' must be a valid Python identifier.` — the name in part 1.1 is
  `ask_desk` with an underscore for this reason, and the message tells you something the field name
  did not: the framework thinks of an agent as a **node**, addressable by name. A space is refused
  because a name that cannot be an identifier cannot be referenced the way the framework references
  it. Pydantic raises this at the constructor, which — because `desk` is built at module scope — means
  it raises on *import*.
- `missing 1 required keyword-only argument: 'session_service'` — this is plain Python, not pydantic:
  the signature itself has no default there, so the interpreter refuses before ADK's own code runs.
  It cannot be caught by a linter that does not know the signature and it cannot be missed by anyone
  who runs the code once.
- Read the two together and the design is visible. Of everything on `Runner` — `app`, `app_name`,
  `agent`, `node`, `plugins`, `artifact_service`, `memory_service` — every one defaults to `None`. You
  can build a runner with **no agent** and the interpreter will not object. You cannot build one with
  no session service.

### Which is to say: the framework refuses to let you rebuild day 4's bug

Sit with the shape of that decision, because it is the reason this is a *good* failure. If
`session_service` had a default — if the constructor had quietly given you a store and not mentioned
it, or accepted `None` and skipped the filing — nothing would break at construction, and the desk
would answer. It would answer every question as though it were the first. That is day 4's deliberate
failure exactly: two `user` turns in a row, no `model` turn between them, and a conversation that is
not one. The bug is undetectable from a single question and obvious from two, which is the worst
combination a bug can have.

`build_runner`'s docstring, printed in part 1.1, says this in three lines and is not repeated here.
What is worth adding is the general form, because you will write constructors of your own: **a
required argument is a refusal you are choosing to make on your caller's behalf.** Every default you
add is a decision you are making for somebody who is not in the room, and the ones worth refusing to
make are the ones whose wrong answer is silent. A missing store is silent. A missing agent, which
this constructor does default, fails loudly the moment anything runs — so the asymmetry in that
signature is not sloppiness, it is the same judgement applied twice with opposite results.

## When it breaks

Now the real thing. The desk is asked a real question, with the synthetic key this project has
carried since day 4 in place of a working one. This is the tail of the traceback:

```console
$ uv run --frozen python run.py adk "Is the VPN down?"
  File ".../site-packages/tenacity/__init__.py", line 413, in exc_check
    raise retry_exc.reraise()
  ...
  File ".../site-packages/google/genai/errors.py", line 287, in raise_error_async
    raise ClientError(status_code, response_json, response)
google.genai.errors.ClientError: 400 INVALID_ARGUMENT. {'error': {'code': 400, 'message': 'API key not valid. Please pass a valid API key.', 'status': 'INVALID_ARGUMENT', 'details': [{'@type': 'type.googleapis.com/google.rpc.ErrorInfo', 'reason': 'API_KEY_INVALID', 'domain': 'googleapis.com', 'metadata': {'service': 'generativelanguage.googleapis.com'}}, {'@type': 'type.googleapis.com/google.rpc.LocalizedMessage', 'locale': 'en-US', 'message': 'API key not valid. Please pass a valid API key.'}]}}
```

**Line by line:**

- **`tenacity` is in the stack.** That is a retry library, and its presence in the traceback of a `400`
  says that the request was not simply refused and reported — it was refused, and asked again. Read
  `raise retry_exc.reraise()`: what finally reached you is a stored exception being re-raised after
  the retrying gave up.
- A `400` is a client error. The request is wrong, and it will be exactly as wrong the next time. The
  provider's own guidance is not ambiguous about this. From
  `https://ai.google.dev/gemini-api/docs/troubleshooting`, checked 2026-09-09, verbatim:

  > Retry on specific errors: Only retry on transient errors (like 429, 408, or 5xx). Do not retry on
  > client errors (like 400 or 403)

  So the framework, on this path, on this version, did the thing the provider's documentation tells
  you not to do. **This is not something today fixes.** Honest backoff — reading `Retry-After`,
  distinguishing what is worth repeating from what is not, escalating rather than swallowing — is
  P05's subject, and naming it here is a pointer, not a patch. What today buys you is knowing it is
  happening, which is more than the traceback volunteers.
- How many times it retried is **not visible in the tail captured above**, and no number is written
  here for it. That is a real limit of this observation and it is left as a limit.
- `ClientError` — not `provider.ProviderError`. Day 4's hand-rolled path raised this project's own
  error type, carrying the status and the message, because day 4's code was the thing that read the
  response. This path raises the provider SDK's type instead, from `google/genai/errors.py`, and
  `run.py`'s `adk` function deliberately does not catch it. An exception you have not decided how to
  handle is worth more on the screen in full than flattened into a tidy message.
- The message is the same one the hand-rolled path produced from the same key: *API key not valid.
  Please pass a valid API key.* Two entirely different code paths, one provider, one truth.

### The documentation and the machine disagree, and the machine is what you ship against

The provider's error reference at `https://ai.google.dev/gemini-api/docs/api-errors`, checked
2026-09-09, tabulates an invalid key as:

> `authentication` | 401 Unauthorized | "The API key is missing, invalid, or expired."

What was observed on this machine on 2026-09-09, twice, on two independent code paths — day 4's
hand-rolled request and the ADK runner above — is **`400 INVALID_ARGUMENT`**, with
`'reason': 'API_KEY_INVALID'` in the details. Those two statements do not agree, and this document
does not pick a winner: the table is what the provider publishes, and the 400 is what arrived. Code
that branches on `401` to mean *bad credentials* will not catch this on this endpoint today, and code
that branches on `400` alone will treat a malformed request as an auth problem. The lesson generalises
past this one row — when a documented status and an observed status differ, the one you must handle is
the one that arrived, and the disagreement itself goes in the day's notes with the date, which is what
the hub's §9 is for.

## In production

**What a senior writes instead.** They do not pass `InMemorySessionService()` at all outside a test.
The point of `session_service` being an injected argument with no default is that the store is a seam:
the same `build_runner` takes a persistent implementation and nothing else in the file changes. And on
the error side they wrap the provider call in *their own* retry policy — statuses they choose,
attempts they choose, a ceiling they choose — rather than inheriting whatever the library's default
happens to be this release, because "the framework retries" is not a specification.

**What degrades at scale.** Retrying a client error multiplies a failure that was already total. A
five-attempt backoff turns one impossible request into **five** impossible requests, and a deployment
that starts with a bad key does that for every question every user asks, against a rate ceiling this
project cannot even print because the provider withdrew the numbers (`PACKAGES.md`, and ADR-0004).
The first symptom is not an auth error in a log — it is a quota problem that hides the auth error, and
the on-call engineer chases the wrong one.

**The review comment.** "Two things. `build_runner` takes the session service as an argument, which is
right — but every caller passes `InMemorySessionService()`, so we have the seam and no benefit from
it; make the caller own the store's lifetime before this goes near staging. And the client error path
retries: I can see `tenacity` in the traceback for a 400. Add an explicit retry predicate that only
covers 429, 408 and 5xx, and a test that asserts a 400 is raised on the first attempt."

**The interview question.** "Your service's provider returns 400 with a message saying the API key is
invalid. The provider's own documentation says an invalid key is a 401. Your retry layer treats 4xx
generically. Walk me through what your system does on a bad-key deploy, what your dashboards show,
and how you would change the code so the first person paged sees the real cause."
