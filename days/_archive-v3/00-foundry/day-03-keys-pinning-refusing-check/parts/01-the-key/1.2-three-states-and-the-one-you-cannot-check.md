## One-line answer

A key can be wrong in three ways — absent, present-but-empty, and present-but-not-accepted — and a
check that runs on your machine can settle the first two by name while being structurally incapable
of settling the third, so it must say which one it is doing.

## The idea

The locksmith finishes the cut and puts the key on the counter. Before it leaves the shop they check
two things, and both are things the counter can decide. Is there a key here at all, or did the
machine jam and produce a blank with no cuts on it? And is it the right profile — will it even enter
a lock of this make? Those are questions about the brass, and the brass is right there.

Then they hand it to you and say the sentence every good locksmith says: *try it before you go.*
Because the third question — does this open **your** door — is not answerable at the counter. Not
with better tools, not with more care. The shop does not have your door. The only instrument that
settles it is the door, and the only way to use that instrument is to walk over and turn the key.

A check that tried to answer the third question at the counter would have to guess, and here is what
makes guessing worse than useless: a confident wrong answer stops you trying it before you go. The
honest shop says "these two I have checked, this one you check", and you leave knowing precisely
which risk you are still carrying.

Our key has the same three states, and they are worth naming because two of them get collapsed
constantly.

**Absent.** No one has set this name anywhere. `os.environ` does not have it and the file does not
have it. Python gives you `None`.

**Present and empty.** Somebody set it, and set it to nothing — a line reading `GOOGLE_API_KEY=` in
the file, or `export GOOGLE_API_KEY=` in a shell, or a CI secret that was never populated so the
runner substituted the empty string. Python gives you `''`. This is a **different situation from
absent**, and it is the more dangerous of the two, because it is nearly always somebody's failed
attempt to set the key rather than nobody having tried. Something ran and did not work, and the
empty string is the fingerprint.

The reason these get collapsed is one line of Python that everybody writes:

`if not os.environ.get("GOOGLE_API_KEY"):`

`None` is falsy. `''` is falsy. That condition is `True` for both, so a program built on it can
never tell the two apart, and its error message has to be vague enough to cover both — which is how
you get *GOOGLE_API_KEY is not set* printed to somebody staring at a file where `GOOGLE_API_KEY`
plainly is set. They read the message, they look at the file, they conclude the message is lying,
and they start looking in the wrong place. `is None` and `not value.strip()` are two tests because
they are two situations, and the sentences you want said back are different sentences.

**Present, non-empty, and not accepted.** The value is there, it looks like a key, and the provider
says no. Expired, revoked, from the wrong project, copied with a character missing, or a placeholder
somebody left in. And here is the structural fact this part exists for: **nothing running on your
machine can decide this one.** A credential is not valid or invalid by inspection; it is valid
because a server that holds the other half of the secret says so. There is no local test. There is
only the request.

Which is exactly why `looks_like_a_placeholder` is written as a guess and reported as a warning. It
catches `fake-not-a-real-key-000` and it would catch `your-key-here`, and it will never catch a real
key that was revoked last Tuesday. Making it a failure would put a check in the project that goes
red on some bad keys, green on other bad keys, and — the genuinely bad outcome — red on a good key
that happens to contain the letters `xxx`. A check with that shape teaches people to ignore it.

This is also where P00 Foundry stops, deliberately. The plan gives this project no provider, no tier
and no agent; its subject is the machine. So the third state is one this project can describe and
cannot exercise, and the request that settles it is day 4's, in P01, where the first real call is
made.

## The mechanism

Everything below uses `projects/00-foundry/keys.py` exactly as part 1.1 printed it. Nothing new is
added; the point is to drive the same three functions through the three states and watch them
answer differently.

The three states, one at a time, each against a throwaway file so the project's real `.env` is left
alone:

```console
$ cd projects/00-foundry
$ uv run --frozen python -c "
import keys
from pathlib import Path
tmp = Path('.env.probe')
for label, body in [('absent','OTHER=x\n'), ('empty','GOOGLE_API_KEY=\n'), ('present','GOOGLE_API_KEY=fake-not-a-real-key-000\n')]:
    tmp.write_text(body, encoding='utf-8')
    keys.ENV_FILE = tmp
    try:
        v = keys.require('GOOGLE_API_KEY')
        print(f'{label:8} -> returned {v!r}; placeholder guess = {keys.looks_like_a_placeholder(v)}')
    except keys.MissingKey as e:
        print(f'{label:8} -> MissingKey: {e}')
tmp.unlink()
"
absent   -> MissingKey: GOOGLE_API_KEY is not set. Add a line `GOOGLE_API_KEY=...` to .env.probe in ., or export it in this shell. `.env.example` lists every name this project reads.
empty    -> MissingKey: GOOGLE_API_KEY is present in .env.probe with an empty value. An empty string is a value, so every `if not os.environ.get(...)` upstream of here will disagree about whether this key is set.
present  -> returned 'fake-not-a-real-key-000'; placeholder guess = True
```

**Line by line:**

- The two refusals carry **different sentences**, and that is the entire return on writing two tests
  instead of one. The first sends you to add a line. The second tells you the line is already there
  and the value is the problem — which is the sentence that would have saved the evening.
- Both messages name the file **by the path actually used** (`.env.probe`, because the probe
  reassigned `ENV_FILE`), not a hard-coded `.env`. An error that names the wrong file sends a reader
  to edit a file that was never being read.
- `keys.ENV_FILE = tmp` works at all only because of the `path = ENV_FILE if path is None else path`
  line from part 1.1. Written the obvious way, as `path: Path = ENV_FILE`, the default would have
  been frozen at import and all three probes would have read the project's real `.env` — and the
  transcript would have shown three identical `present` rows, which is exactly what the first draft
  of this document produced before the bug was found.
- The third row **returns**. `require` has no complaint: something is set, and it is not empty. That
  is the honest limit of a local check.
- `placeholder guess = True` is printed as a guess and labelled one. It happens to be right here,
  and being right here is not evidence it is right in general.

Now the third state, settled the only way it can be — by asking the thing that holds the other half.
This is the request P00 does not otherwise make, run once so you have seen the shape of the answer:

```console
$ uv run --frozen python -c "
import json, urllib.request, urllib.error, keys
key = keys.require('GOOGLE_API_KEY')
url = 'https://generativelanguage.googleapis.com/v1beta/models'
req = urllib.request.Request(url, headers={'x-goog-api-key': key})
try:
    with urllib.request.urlopen(req, timeout=20) as r:
        print('HTTP', r.status)
except urllib.error.HTTPError as e:
    print('HTTP', e.code)
    err = json.load(e)['error']
    print(json.dumps({k: err[k] for k in ('code','message','status')}, indent=2))
"
HTTP 400
{
  "code": 400,
  "message": "API key not valid. Please pass a valid API key.",
  "status": "INVALID_ARGUMENT"
}
```

**Line by line:**

- `keys.require` ran first and was **happy**. Every local check passed, and the key is still wrong.
  That sequence — green locally, rejected remotely — is the shape of the third state, and seeing it
  once is what stops you trusting a green config check as proof of a working credential.
- The key travels in the `x-goog-api-key` header rather than in the URL. A key in a query string is
  a key in the server's access log, in your shell history, and in any proxy in between; a header is
  none of those. It costs one extra line and it is the difference between a secret and a published
  one.
- `400 INVALID_ARGUMENT`, not `401` or `403`. The status is worth noticing because the obvious guess
  is wrong, and code that branches on `if status == 401` to mean "bad credentials" will miss this
  entirely and retry a request that can never succeed.
- The message is `API key not valid. Please pass a valid API key.` — flat, and it says nothing about
  *why*. Expired, revoked, mistyped and never-real all arrive here identically, which is why the
  local warning about placeholders has any value at all: it is the only one of those four the
  machine in front of you can spot.

*Observed on this machine on 2026-09-09 against the live endpoint, with the synthetic value day 2
put in `.env`.*

## When it breaks

The check is green, the deploy goes out, and the first user request fails. The variable was set in
the CI runner and the secret it pointed at was never populated, so what actually landed in the
container was the empty string, and a config check written the usual way had nothing to say about
it:

```console
$ GOOGLE_API_KEY= uv run --frozen python -c "
import os
if not os.environ.get('GOOGLE_API_KEY'):
    raise SystemExit('GOOGLE_API_KEY is not set')
print('key loaded')
"
GOOGLE_API_KEY is not set
```

The message is a lie, and the person reading it at eleven at night has a terminal open showing the
variable *is* set — so they conclude the deployment did not pick up their change, and spend the next
hour on the deployment. The smallest fix is the one in `require`: test `is None` and
`not value.strip()` separately, and say which of the two happened. The sentence *present with an
empty value* would have pointed at the CI secret in about ten seconds.

## In production

**What a senior writes instead.** They validate the whole configuration once, at process start, and
crash before serving a single request — a `Settings` class with `pydantic-settings`, or one
`load_config()` called from `main`. The principle is that a process which cannot do its job should
fail while somebody is still watching the deploy, not on a customer's request an hour later. What
they never do is scatter `os.environ["KEY"]` through the codebase, because then the failure happens
wherever the code path happens to reach first, and which one that is depends on the request.

**What degrades at scale.** The number is **three**: a placeholder guess has three ways to be wrong
and only one to be right, and the two failure directions are not symmetric. A real key containing
`example` gets a warning on every single run until people stop reading warnings — and once they have
stopped, the one it correctly fires on goes past unread too. This is why it warns and does not fail,
and why the marker list is short. A heuristic that fires falsely often enough trains its audience to
ignore it, and then it has negative value.

**The review comment.** "Good that this distinguishes absent from empty. Two notes: `MissingKey`
puts `{value!r}` in the message on one path — drop it, because the day somebody widens that branch
to cover short keys, this prints a live credential into the build log. And please say in the
docstring that a green `require` is not a claim the key works; the last person to read this shipped
on the assumption that it was."

**The interview question.** "Your config check passes in CI and the service fails on its first real
request with an authentication error. The environment variable is set and non-empty in both places.
Name three things that could be true, and say which of them a check running inside your own process
could ever have caught."

## Check yourself

- **Run:** `cd projects/00-foundry && uv run --frozen python -c "import keys; keys.require('NOT_A_REAL_NAME')"`
  — expect a `MissingKey` traceback whose message names `NOT_A_REAL_NAME` and tells you which file
  to put it in.
- **Say out loud:** which of the three states your project's check can decide, which one it cannot,
  and what a check should print so that a reader knows the difference without reading its source.
