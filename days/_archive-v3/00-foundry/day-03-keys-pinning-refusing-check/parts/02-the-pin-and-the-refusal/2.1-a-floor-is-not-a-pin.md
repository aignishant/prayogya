## One-line answer

`>=4.11.8` and `>=3.12` are floors — they say what is *too old* and leave the actual choice to
whichever machine resolves them on whichever day — so the thing that makes two machines agree is
never the floor but the two files that record what was chosen: `.python-version` and `uv.lock`.

## The idea

Inside a cylinder lock there is a row of little brass pins, and each one is cut to an exact height.
The key's ridges push every pin to precisely the level where the cylinder can turn. Not roughly. A
pin stack that would accept anything from three millimetres upward is not a loose lock; it is not a
lock. The whole mechanism is the word *exactly*.

The locksmith's word for setting those heights is **pinning**, and it is worth borrowing whole,
because the software habit that shares its name is usually done in the manner of the lock that
accepts anything from three millimetres upward — and it is called pinning anyway, which is how it
gets away with it.

Here is what your project actually says right now. Open `pyproject.toml` and it asks for
`requires-python = ">=3.12"` and, as day 1 left it, `platformdirs>=4.11.8`. Read those out loud as
what they are: *any Python from 3.12 upward*, and *any platformdirs from 4.11.8 upward*. Neither
sentence names a version. Both of them say what is too old and then hand the decision to whoever
runs the install next.

That is not a hypothetical. Look at the ledger this repository already keeps. `docs/PINS.md` has a
row saying platformdirs **4.11.7**, observed on 2026-09-08, added by day 1. Look in the project
today and the version present is **4.11.8**. Nothing was edited, no one changed their mind, and
nobody was told. Version 4.11.8 was published at 22:20 UTC on the same day day 1 wrote its row, the
floor said `>=`, and the next resolution walked straight through it. Between 2026-08-24 and
2026-09-08 that package published **five** releases. A floor is a door held open, and packages walk
through doors held open.

Both halves of the toolchain have this shape, and it is worth being exact about which file does
what, because three files are involved and they answer three different questions.

**`pyproject.toml` records what you asked for.** It is the requirement, and a requirement is
allowed to be a range — that is what makes a library installable alongside other people's
constraints. This is the file a human edits.

**`uv.lock` records what the asking produced.** Exact versions, exact hashes, for every package
including the ones you never named. Day 1 defined this: the lockfile is the tool-written record of
what a resolution actually produced, as against `pyproject.toml`, which records what was requested.
This is the file no human edits and every machine reads.

**`.python-version` records which interpreter.** The lockfile pins your dependencies and says
nothing about the thing that runs them. `requires-python = ">=3.12"` is a floor exactly like the
others, and on this machine it resolved to 3.12.12 — a version that appears nowhere in
`pyproject.toml`, and which day 1 already caught being different from the 3.12.10 that the bare name
`python` resolves to here.

So: the floor is the request, and the two pin files are the answer, and a project that ships only
the request has not pinned anything. The question that decides whether you actually have a pin is
not *is there a version number in my config* — it is **if I hand this folder to somebody on a
different machine next March, what makes them get what I got?** If the honest answer is "resolution,
and I hope it lands the same", then you have a floor.

There is one more thing to say and it is the reason a floor is not simply a mistake. A floor is
correct for a **library**, because a library that pins exactly makes itself uninstallable next to
anything else that pinned exactly. Floors are for things other people depend on; pins are for things
that get deployed. Every project in this curriculum is an application — it is deployed and never
imported — so every one of them pins, and the check that arrives in part 2.2 makes that mechanical
instead of remembered.

## The mechanism

The state to start from is the one day 2 left: `requires-python` a floor, the dependency a floor, and
no `.python-version` at all. The machine happily produces a working environment, and that is the
trouble — nothing is broken, so nothing complains:

```console
$ cd projects/00-foundry
$ grep -E 'requires-python|platformdirs' pyproject.toml
requires-python = ">=3.12"
    "platformdirs>=4.11.8",
$ uv run --frozen python -c "
import sys
from importlib.metadata import version
print('interpreter ', '.'.join(map(str, sys.version_info[:3])))
print('platformdirs', version('platformdirs'))
"
interpreter  3.12.12
platformdirs 4.11.8
```

**Line by line:**

- Two floors asked for, two exact things delivered, and **neither delivered value appears in the
  file that asked**. `3.12.12` and `4.11.8` were chosen by a resolver, on this machine, today.
- The resolution succeeded, which is precisely why this is worth a document. There is no error to
  notice and no warning to read. The failure mode of a floor is that it works, right up until the
  day it resolves differently for somebody else.
- `--frozen` is doing real work in that command and part 2.2 is about why. Without it, `uv run`
  updates the lockfile before running anything.

The interpreter half, pinned. `uv python pin` writes the file rather than you typing it, so the value
is the one actually in use and not the one you believed was in use:

```console
$ uv python pin 3.12.12
Pinned `.python-version` to `3.12.12`
$ cat .python-version
3.12.12
```

**Line by line:**

- The whole file is `3.12.12` and a newline. `projects/00-foundry/.python-version` is printed in
  full by that transcript — there is nothing else in it, which is the point: one fact, one line, no
  syntax to get wrong.
- `uv python pin` takes the value you name and writes it; running it with no argument would pin
  whatever is currently resolved. Naming it explicitly is the habit worth keeping, because it makes
  the command fail if you were wrong about what you were running.
- This file is **committed**. `.venv/` is not, and day 2's `.gitignore` already excludes it. The
  distinction is the one from day 1: the environment is rebuildable, so it is never committed; the
  record of *which* environment is not rebuildable from anything, so it always is.

The dependency half, pinned — as a marked diff against the `pyproject.toml` day 1 printed:

```toml
# projects/00-foundry/pyproject.toml
[project]
name = "foundry"
version = "0.1.0"
requires-python = ">=3.12"
dependencies = [
-    "platformdirs>=4.11.8",
+    "platformdirs==4.11.8",
]
```

Written with `uv add` rather than by hand, so the lockfile is updated in the same step:

```console
$ uv add "platformdirs==4.11.8"
Resolved 2 packages in 9ms
Checked 1 package in 0.24ms
$ grep -A2 '^dependencies' pyproject.toml
dependencies = [
    "platformdirs==4.11.8",
]
```

**Line by line:**

- `uv add` with an exact specifier edits `pyproject.toml` **and** re-resolves the lock in one
  action, so the two files cannot disagree because you did one and forgot the other.
- `Checked 1 package` rather than `Installed`: the environment already held 4.11.8, so nothing was
  downloaded. The pin here changed the *request*, not the result — which is exactly the situation
  where hand-editing feels unnecessary and is not.
- `requires-python = ">=3.12"` is deliberately left as a floor. It is the wider statement — *this
  code needs at least 3.12* — and it stays true and useful. `.python-version` is the narrower one —
  *and here is the interpreter we actually use*. They are not duplicates and the second does not
  replace the first.

*Observed on this machine on 2026-09-09, uv 0.12.3. The five platformdirs releases between
2026-08-24 and 2026-09-08, and the 22:20 UTC upload time of 4.11.8, were read from
`https://pypi.org/pypi/platformdirs/json` on 2026-09-09.*

## When it breaks

The classic version is a build that has worked for months failing on a morning when nobody touched
it. Here it is in miniature — the lockfile says one thing, `pyproject.toml` says another, and the
command that will not paper over the difference says so:

```console
$ uv lock --check
Resolved 2 packages in 610ms
error: The lockfile at `uv.lock` needs to be updated, but `--check` was provided.

hint: To update the lockfile, run `uv lock`.
```

Somebody edited a version in `pyproject.toml`, committed it, and did not commit the regenerated
lock — so every machine that installs from the lock gets the old version while the file everybody
reads claims the new one. The smallest fix is `uv lock` and a second commit; the fix that stops it
recurring is `uv add` instead of an editor, because `uv add` cannot leave the two files disagreeing.

## In production

**What a senior writes instead.** For an application, exactly this: `==` on every direct dependency,
a committed lockfile, a committed `.python-version`, and installs that use the lock rather than
re-resolving. For a library, the opposite — floors on everything, and no lockfile shipped at all,
because pinning a library exactly makes it uninstallable alongside anything else. The judgement is
one question: is this imported by other people, or deployed? They are opposite answers and the
mistake is applying either one everywhere.

**What degrades at scale.** The number is **five** — platformdirs shipped five releases in the
fifteen days from 2026-08-24 to 2026-09-08, and that is one small, stable, dependency-free package.
A project with forty direct dependencies pulling perhaps two hundred transitive ones is sitting on
that rate multiplied out; unpinned, the set of code you are actually running changes on a timescale
of days, silently, and "it worked yesterday" stops being evidence of anything.

**The review comment.** "`requires-python = ">=3.12"` plus no `.python-version` means CI picks the
newest 3.x the runner image happens to ship, so this will move under us the next time the image is
rebuilt and it will look like our change broke it. Please add the pin file, and commit `uv.lock` in
the same PR as the `pyproject.toml` edit — the two are one change."

**The interview question.** "Your `pyproject.toml` says `requests>=2.31`, your lockfile says 2.31.0,
and a colleague's machine is running 2.34.2. Nobody edited anything. Explain how both machines are
obeying the same repository, and say which file you would look at first to find out what your
production containers are actually running."

## Check yourself

- **Run:** `cd projects/00-foundry && uv lock --check` — expect `Resolved 2 packages` and exit `0`.
  Then change `4.11.8` to `4.11.7` in `pyproject.toml`, run it again, and read the error. Put it
  back.
- **Say out loud:** which of `pyproject.toml`, `uv.lock` and `.python-version` records a request,
  which records a result, and which one you would delete first if you wanted a colleague's build to
  differ from yours without either of you being able to see why.
