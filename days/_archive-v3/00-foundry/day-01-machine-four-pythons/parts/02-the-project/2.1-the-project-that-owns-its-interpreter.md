## One-line answer

A project turns "which Python?" from a question about your shell into a question answered by two
files that travel with the code — and the proof that it worked is that the project **refuses** an
interpreter that does not satisfy it.

## The idea

Stop saving numbers under labels. Put the plumber's full number on the job sheet for the job, and
staple it to the job. Now it does not matter whose phone the sheet is read from, whose contacts are
a mess, or how many numbers anyone else has saved under the same word — the sheet carries the
answer, and the answer arrives with the work.

That is the entire move, and everything else in this part is detail. Up to now the machine has been
answering questions about itself: which interpreters exist, which one a name reaches, where an
interpreter is standing. Those are facts about a laptop, and a fact about a laptop cannot be
committed, reviewed or handed to anybody. What can be committed is a **project** — a directory that
states what it needs, in files, so that the requirement outlives the shell it was typed in.

Two files do it, and they have different jobs that people routinely blur.

The first records **what you asked for**: a name, a version of the project, the range of Python it
will run under, and the packages it depends on. It is written by a person and it is short, because
it is a statement of intent.

The second records **what was actually resolved**: exact versions, for every package, including the
ones you never named. It is written by the tool and it is not for editing. A **lockfile** is the
difference between "this project needs a recent enough Python and some packages" and "on this date,
these exact things were what that meant".

The distinction matters because only one of them can make two machines agree. Intent cannot: two
people can satisfy the same intent with different packages and both be correct. The lock can,
because it is not a description of what is acceptable — it is a record of one specific answer.

And the reason this is the day's turning point rather than a filing exercise: once the requirement
lives in a file, a tool can **enforce** it. A requirement nobody checks is a comment. The last
transcript in this part is the project declining to run, and that refusal is the whole return on
the two files above it.

## The mechanism

One command creates the project. `--bare` asks for the files and nothing else — no sample module, no
README, no git repository — because P00 Foundry is about the machine and every extra file would be
something to explain that is not the subject:

```console
$ uv init --name foundry --python 3.12 --bare
Initialized project `foundry`
```

**Line by line:**

- `--name foundry` — the distribution name, set explicitly rather than inherited from the folder
  name. The folder is `00-foundry`, which is a curriculum ordering device, and a package cannot be
  called that. Letting the folder name decide is how a project ends up named after wherever someone
  happened to clone it.
- `--python 3.12` — the version this project is being created for. It is what turns into
  `requires-python` in the file below, and stating it at creation is cheaper than discovering later
  that the default did not match what the code assumes.
- `--bare` — files only. Every file this project contains should be one this curriculum prints and
  explains, and a scaffold that generates a `hello.py` nobody teaches is a file with no day, which
  is exactly what `CODEMAP.md` exists to make impossible.

Here is what it wrote, whole, at its real path:

```toml
# projects/00-foundry/pyproject.toml
[project]
name = "foundry"
version = "0.1.0"
requires-python = ">=3.12"
dependencies = []
```

**Line by line:**

- `[project]` — the standard table that packaging tools read. It is not uv's invention and not uv's
  property, which is the reason to prefer it: a project described here can be built by tools that
  have never heard of uv.
- `name = "foundry"` — the importable, installable identity of this project. It is not the folder,
  and the two being different here is deliberate rather than untidy.
- `version = "0.1.0"` — required by the standard even for something that will never be published.
- `requires-python = ">=3.12"` — **the line that does the work in this part.** It is a floor, not a
  pin: 3.12.10 and 3.12.12 both satisfy it, and so would 3.13. It says what the code needs in order
  to be correct, which is a different claim from what it was tested on, and conflating those two is
  what makes a pin argument go round in circles. The pinning of an exact interpreter is
  day 3's subject in this project's day map; today's job is only to establish that a
  requirement exists in a file and is enforced.
- `dependencies = []` — empty and present. An empty list is a decision recorded; a missing key is a
  decision nobody made, and the difference shows up the first time someone adds a package by hand.

Now build the environment the project describes:

```console
$ uv sync
Using CPython 3.12.12
Creating virtual environment at: .venv
Resolved 1 package in 20ms
Checked in 0.06ms
```

**Line by line:**

- `Using CPython 3.12.12` — uv picked the **uv-managed** interpreter that `uv python find` reported
  in [part 1.1](../01-the-name/1.1-four-things-called-python.md), not the `3.12.10` that the bare
  name `python` resolves to. Both satisfy `>=3.12`; uv's search order put its own first. Read that
  line every time — it is the project telling you which of the six it chose.
- `Creating virtual environment at: .venv` — the place from
  [part 1.2](../01-the-name/1.2-an-environment-is-a-place.md), created for you, in the project
  directory, with the `pyvenv.cfg` that makes it one. You did not choose a location and should not:
  a conventional location is what lets every later tool find it without configuration.
- `Resolved 1 package` — the one package is `foundry` itself. A project is a package that depends on
  its dependencies, so it appears in its own resolution.
- uv writes a `.gitignore` containing a single `*` inside `.venv` as it creates it, so the directory
  excludes itself from git without anybody adding a rule. The environment is a build output; the two
  files that describe it are the source.

And the file uv wrote to record what it resolved, whole:

```toml
# projects/00-foundry/uv.lock
version = 1
revision = 3
requires-python = ">=3.12"

[[package]]
name = "foundry"
version = "0.1.0"
source = { virtual = "." }
```

**Line by line:**

- `version = 1` and `revision = 3` — the format of the lockfile, not of your project. They exist so
  a future uv can read a lock an older uv wrote, and they are the first thing to look at when a lock
  file causes an argument between two machines running different uv versions.
- `requires-python = ">=3.12"` — copied down from the intent file. The lock carries the constraint it
  was resolved under, so a lock can be checked for relevance rather than trusted blindly.
- `[[package]]` with `source = { virtual = "." }` — `foundry` itself, marked *virtual*: a package
  that is part of this project rather than something downloaded. When a real dependency arrives in
  [part 2.2](2.2-the-two-commands-that-disagree.md), it appears here as a second `[[package]]` block
  with a version and a hash, and the contrast between the two entries is the clearest statement of
  what a lock is for.
- The file is committed to git. uv's own documentation is explicit — *"This file should be checked
  into version control, allowing for consistent and reproducible installations across machines"* —
  and it is described there as *"a universal or cross-platform lockfile"*, so one lock covers every
  platform the project runs on rather than one per operating system.
- It is generated. uv's documentation says it *"is a human-readable TOML file but is managed by uv
  and should not be edited manually"*, which puts it in the same category as the generated documents
  under `docs/` in the authoring repository: readable on purpose, editable never.

*Both quotations from `https://docs.astral.sh/uv/concepts/projects/layout/`, fetched 2026-09-08.*

Now the payoff. Ask the project to run under an interpreter that does not satisfy it:

```console
$ uv run --python 3.11 foundry/whoami.py
Using CPython 3.11.9 interpreter at: C:\Users\nisha_gnzw\AppData\Local\Microsoft\WindowsApps\PythonSoftwareFoundation.Python.3.11_qbz5n2kfra8p0\python.exe
error: The requested interpreter resolved to Python 3.11.9, which is incompatible with the project's Python requirement: `>=3.12` (from `project.requires-python`)
```

**Line by line:**

- The first line shows uv **found** exactly what was asked for, and names the file — the Microsoft
  Store interpreter from part 1.1. Finding it was never the problem.
- The second line is the refusal, and notice it cites its authority: `` `>=3.12` (from
  `project.requires-python`) ``. It does not say "incompatible"; it says which rule, from which key,
  in which file. An error that names the line that caused it is an error someone can fix without
  understanding the tool.
- The command exits `2`, so this is available to a script and not only to a person reading a
  terminal.
- **This is the difference the two files bought.** In part 1.1 the wrong interpreter ran happily and
  the mistake surfaced later as something unrelated. Here it cannot start at all.

## When it breaks

Write a floor nothing on the machine can satisfy — a typo of exactly one character in a version
number is enough — and the project stops before it starts:

```console
$ uv sync
error: No interpreter found for Python >=3.99 in managed installations, search path, or registry

hint: uv embeds available Python downloads and may require an update to install new versions. Consider retrying on a newer version of uv.
```

Read where it looked: *managed installations, search path, or registry* — the three places from
[part 1.1](../01-the-name/1.1-four-things-called-python.md), quoted back at you in an error message.
Someone hit this after a merge that took `>=3.9` from one branch and `>=3.99` from a bad conflict
resolution on the other, and spent the evening on the hint about updating uv, because the hint is
about the general case and their fault was a typo. The smallest fix is to read the version in the
error rather than the advice under it.

The quieter failure has no error text at all, which is why it is worse. `>=3.12` is satisfied by
3.13, so on a machine with 3.13 and no 3.12 this same `uv sync` succeeds, prints
`Using CPython 3.13.x` in a line that scrolls past, and builds a working environment on an
interpreter nobody intended. A floor is a statement of compatibility and was never a statement of
reproducibility; the exact pin that closes that gap is day 3's subject, in the plan's §12 map for
this project.

## In production

A senior engineer does not treat `requires-python` as the pin. They write the floor in
`pyproject.toml` for correctness, pin the exact interpreter separately for reproducibility, and then
make CI fail when the two disagree — because those are three different jobs and one key cannot hold
all of them.

What degrades is the size of the gap between "allowed" and "tested". `>=3.12` currently admits
**four** minor versions that `uv python list` can install on this machine — 3.12, 3.13, 3.14 and
3.15 — and you have tested on exactly one. Every release widens that gap without anybody editing a
file, which makes it the rare kind of technical debt that grows while the repository sits
untouched.

The review comment: *"The lock is in the diff but `pyproject.toml` is not. What resolved
differently, and was it deliberate?"* A lock that moves on its own is either a dependency update
somebody meant or a machine that disagreed, and the diff cannot tell you which unless someone says.

The interview question: **"What is the difference between `requires-python` and a pinned
interpreter, and which one makes two machines agree?"** A weak answer treats them as the same
mechanism written two ways. A strong one says the first states what the code needs and the second
states what was tested, and only the second is reproducible — then points out that a project wants
both, for different reasons.

## Check yourself

- **Run:** `uv run --python 3.11 foundry/whoami.py; echo "exit $?"` — expect the refusal, expect it
  to quote `requires-python`, and expect exit `2`.
- **Say out loud:** which of `pyproject.toml` and `uv.lock` is intent and which is record, and why
  can only one of them make two machines agree?
