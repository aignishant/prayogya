## One-line answer

A `.gitignore` file decides what git **offers** you next, and never what git already holds — so it
has to be written before the file it exists to stop, not after.

## The idea

Somebody puts a sticker on their front door: *no leaflets*. It works. For a year nothing comes
through the slot but real post, and they forget the sticker is there.

Then they move, and on the first morning in the new place the slot goes twice and there are two
leaflets on the mat. They put the sticker up that afternoon. The leaflets on the mat do not move.
Nobody expected them to — the sticker is a fact about the door, and the mat is inside the house.
Getting the sticker up on the second morning instead of the first cost them exactly two leaflets,
and the only way to deal with those two is to pick them up.

That is the whole shape of this part, and the two words it turns on are **untracked** and
**tracked**. A file in your project folder is *untracked* when git has never been told to hold it:
git can see it sitting there, it will mention it, and it will do nothing else. A file is *tracked*
when git has been told to hold it — from that moment git is following its contents, and it will
keep following them.

The ignore file only ever speaks about the first kind. It is a list of patterns saying *do not
offer me these*, and the documentation is blunt about the boundary:

> A `gitignore` file specifies intentionally untracked files that Git should ignore. Files already
> tracked by Git are not affected.

Read that sentence twice, because the mistake it describes does not announce itself. The file that
matters here is `.env`: the one file in a project that holds the values you cannot afford to hand
out — an API key, a database password. It does not exist yet. Nothing has been created that needs
it. And that is exactly why now is the moment to write the rule that keeps it out, because the
alternative is to write the rule on the morning after the slot has already gone twice.

So the order in this day's title is not a stylistic preference. It is the only order in which the
rule does anything at all.

## The mechanism

Day 1 left `projects/00-foundry/` holding two files it can account for — `pyproject.toml` and
`uv.lock`. The project has no secrets, no keys and no build output yet. Write the rule now, into
the project's own ignore file:

```gitignore
# projects/00-foundry/.gitignore
# The rule comes first. This file exists before any file it names does.

# Secrets. Never committed — not once, not "just to test the pipeline".
.env
.env.*
*.key
*.pem
service-account.json

# Written by uv from uv.lock. Rebuildable, so never committed and never copied.
.venv/
__pycache__/
*.pyc
```

**Line by line:**

- `.env` — the exact name, no wildcard. This is the file that will hold real values on a real
  laptop. Matching it by its exact name rather than by a pattern means the rule cannot be widened
  by accident later; a pattern that grows is a pattern that starts swallowing files you wanted.
- `.env.*` — the variants people reach for without thinking: `.env.local`, `.env.production`,
  `.env.bak`. The one that actually leaks is almost never `.env`. It is the copy somebody made
  before editing, and the copy is the one nobody remembers is there.
- `*.key` and `*.pem` — two extensions rather than one rule for "certificates", because these are
  the two that arrive as downloads from a provider's console and land in whatever directory the
  browser was pointed at. A downloaded file does not get a considered name.
- `service-account.json` — named in full and singular, because this is the one credential format
  that arrives *looking like* project configuration. A `.json` file among other `.json` files
  reads as settings, and `git add .` treats it as settings.
- `.venv/`, with the trailing slash — the slash says *directory*, so the pattern cannot match a
  file that happens to be called `.venv`. Day 1 established what is in there: a link back to a
  real interpreter and a set of installed packages, all of it rebuildable from `uv.lock`.
- `__pycache__/` and `*.pyc` — the compiled output the interpreter writes beside your source. Two
  rules for one idea, because the directory and the loose files are matched by different shapes,
  and a directory pattern will not catch a stray `.pyc` sitting outside it.
- Both comment blocks say **why**, not what. `*.pem` is self-describing; "never committed, not
  once" is the part a reader six sittings from now cannot reconstruct from the pattern.

Note what the file does **not** contain. There is no `!` line yet — nothing is being taken back
out. That is part 1.2's problem, and it is better met as a surprise than as a footnote.

Now watch the order pay. Nothing exists but the rule, so git has nothing to say about this project
except that the ignore file itself is new:

```console
$ cd projects/00-foundry
$ git status --short .
?? .gitignore
```

Now the secret arrives, the way it really arrives — a value pasted into a new file:

```console
$ printf 'GOOGLE_API_KEY=fake-not-a-real-key-000\n' > .env
$ git status --short .
?? .gitignore
```

`.env` is on disk and git has stopped mentioning it. Ask which line made that decision:

```console
$ git check-ignore -v .env
projects/00-foundry/.gitignore:5:.env	.env
```

And the proof that it is a refusal rather than an oversight — git will not take the file even if
you ask it to by name:

```console
$ git add .env
The following paths are ignored by one of your .gitignore files:
projects/00-foundry/.env
hint: Use -f if you really want to add them.
hint: Disable this message with "git config set advice.addIgnoredFile false"
$ echo $?
1
```

*Observed on this machine on 2026-09-09, git version 2.54.0.windows.1.*

## When it breaks

Read that last transcript again as somebody in a hurry reads it. They are wiring up a deployment,
the pipeline needs the environment file, git is in the way, and git itself has just told them the
flag that makes the problem go away.

```console
$ git add -f .env
$ echo $?
0
$ git status --short .
A  .env
?? .gitignore
```

No warning, no second hint, nothing. `-f` is the door being propped open, and it is silent because
you asked for it explicitly. One commit later the key is in the history, and the leaflet is on the
mat. The smallest fix is not `git rm` — it is rotating the key at the provider, because a value
that has been committed has to be treated as a value that has been read.

## In production

**What a senior writes instead.** The ignore file is in the repository's *first* commit, before any
code, and secrets never live in the repository at all: the values come from the platform's secret
store, and a `.env` file exists only on a laptop as a local convenience. The ignore rule is the
seatbelt, not the plan.

**What degrades at scale.** Reading the ignore file and reasoning about it stops working almost
immediately, because it is not the only source of rules. For a path like
`projects/00-foundry/foundry/whoami.py` git will consult a `.gitignore` in the directory holding
it and in every parent up to the top of the working tree — **four** files here — plus
`.git/info/exclude`, plus the file named by `core.excludesFile`. **Six** sources for one path, and
the file you are looking at is one of them. That is why part 2.1 exists.

**The review comment.** "This commit adds `.env`. Two things: put the ignore rule in a commit
*before* this one, and rotate the key — it is in the history now, and removing the file will not
take it back out."

**The interview question.** "A teammate pushed a `.env` with a live key, then added `.env` to
`.gitignore` in the next commit and said it was handled. Was it? What do you do first?"

## Check yourself

- **Run:** `git check-ignore -v .env` from inside `projects/00-foundry` — expect one line naming
  the ignore file, a line number, the pattern, then the path.
- **Say out loud:** if you deleted line 5 from that ignore file, what would `git status --short .`
  print, and what would still be true about the file on disk?
