## One-line answer

`git check-ignore -v` names the file, the line number and the pattern that decided a path — and you
need it rather than your own reading, because six different places can hold the rule and only
four of them are in the repository.

## The idea

The sticker on your own door is not the only sticker. There is one on the street door of the
building, put there before you moved in, and the postman passes it first. There is a third list in
the caretaker's office, which you have never seen, and a fourth kept by the sorting office, which
you cannot see. When a letter does not arrive, "I know what my sticker says" is not an answer to
the question of why.

The building this project sits in already has a sticker. The authoring repository has its own
ignore file at the root, written on day 0, and `projects/00-foundry/` sits inside it. So there are
now two files with opinions about `.env`, and the interesting question is not *what do they say* but
*which one did git actually obey*.

Git resolves this with a rule that reads backwards from what most people guess. The documentation
gives the order of precedence, highest first:

> - Patterns read from the command line for those commands that support them.
> - Patterns read from a `.gitignore` file in the same directory as the path, or in any parent
>   directory (up to the top-level of the working tree), with patterns in the higher level files
>   being overridden by those in lower level files down to the directory containing the file.
> - Patterns read from `$GIT_COMMON_DIR/info/exclude`.
> - Patterns read from the file specified by the configuration variable `core.excludesFile`.

Two things fall out of that list, and both matter more than they look.

The first: **nearer wins**. A rule in `projects/00-foundry/.gitignore` overrides a rule about the
same path in the repository root's file. That is not a quirk — it is what makes the plan's
independence rule possible. `projects/00-foundry/` is meant to be liftable onto a machine where the
root file does not exist, and the way to prove its own rules are the live ones is to check which
file git names.

The second: of those sources, `.git/info/exclude` and the file named by `core.excludesFile` are
**not in the repository**. Nobody reviewing a change can see them. A rule you added to your own
machine-wide ignore file years ago will make a path behave one way for you and another way for
everyone else, and the difference will not show up in any diff.

Which is why the answer to "is this ignored?" is a command and not a reading. And the command has
one sharp edge of its own, in its exit status, which the last transcript below walks into on
purpose.

## The mechanism

Both ignore files are in place: the root one from day 0, and the project's own from parts 1.1 and
1.2. Ask about three paths at once, from inside the project:

```console
$ cd projects/00-foundry
$ git check-ignore -v .env .env.example .venv
projects/00-foundry/.gitignore:5:.env	.env
projects/00-foundry/.gitignore:7:!.env.example	.env.example
projects/00-foundry/.gitignore:13:.venv/	.venv
```

**Line by line:** the output shape is documented exactly, as
`<source> <COLON> <linenum> <COLON> <pattern> <HT> <pathname>` — and each field answers a different
question you would otherwise have guessed at.

| Field | What it answers, and the guess it replaces |
| --- | --- |
| `projects/00-foundry/.gitignore` | *Which* file held the rule. All three lines name the project's own file, not the root's — that is "nearer wins", observed rather than assumed, and it is the proof that this project's rules travel with it. |
| `5`, `7`, `13` | *Which line*, so you can go and read it. Without the number you grep for the pattern and find three lines that look like it. |
| `.env`, `!.env.example`, `.venv/` | The pattern **as written**, `!` and trailing `/` preserved. Line 7 keeping its `!` is how you can tell an exclusion from an exception at a glance. |
| a tab, then the path | The path you asked about, so the output can be read when you passed several paths, and split by a machine when you passed a hundred. |

Now the same three names asked from the repository root, where a different file is nearer:

```console
$ cd ../..
$ git check-ignore -v .env .env.example
.gitignore:2:.env	.env
.gitignore:4:!.env.example	.env.example
```

Same two answers, different source, different line numbers. Two files, both correct, each governing
its own subtree — and nothing but this command tells you which was consulted for a given path.

And the sharp edge. Line 7 of the project's file is a *negation*: `.env.example` is emphatically
**not** ignored. Ask about it two ways:

```console
$ cd projects/00-foundry
$ git check-ignore -v .env.example
projects/00-foundry/.gitignore:7:!.env.example	.env.example
$ echo $?
0
$ git check-ignore .env.example
$ echo $?
1
```

**Line by line:**

- With `-v`, the command's job changes. The documentation for the flag says it prints "for each
  path that matches an exclude pattern, print the exclude pattern together with the path" — and it
  adds the parenthesis that explains everything above: "Matching an exclude pattern usually means
  the path is excluded, but if the pattern begins with `!` then it is a negated pattern and
  matching it means the path is NOT excluded."
- So `-v` reports **matches**, and the exit status came out `0` for a file that is not ignored. The
  documented meaning of `0` — "One or more of the provided paths is ignored" — is the meaning it
  carries *without* `-v`, and the plain form on the same file exits `1`.
- The practical rule: **read the output when you use `-v`, read the exit status when you do not.**
  A script that runs `check-ignore -v` and branches on `$?` will treat every negated path as
  ignored, which is precisely backwards, and it will do it silently.

*Observed on this machine on 2026-09-09, git version 2.54.0.windows.1.*

## When it breaks

The dangerous version of "nearer wins" is not a rule that fails to apply. It is a rule that
applies and undoes a protection written above it. Somebody appends one line to the project's ignore
file — perhaps debugging why an environment file would not stage, perhaps copied from an answer
online.

```console
$ cat -n .gitignore | tail -3
    14	__pycache__/
    15	*.pyc
    16	!.env
$ git check-ignore -v .env
projects/00-foundry/.gitignore:16:!.env	.env
$ git status --short .
?? .env
?? .env.example
?? .gitignore
```

The root repository still says `.env` is ignored, on line 2 of its own file, and it has been
overruled by a lower-level file — that is precedence working exactly as documented. `git status` is
now offering the real secret as a new file, ready for the next `git add .`. The smallest fix is to
delete line 16; the thing worth noticing is that the *only* symptom was a path appearing in
`git status`, which is the one output nobody reads carefully.

## In production

**What a senior writes instead.** They do not assert in review that a path is ignored; they paste
the `check-ignore -v` output, or the repository has a check that asserts it. A test that runs
`git check-ignore --no-index .env` and fails on a non-zero exit is three lines, runs in CI, and
cannot be fooled by anyone's personal configuration.

**What degrades at scale.** Of the six sources git consults for one path, exactly **two** —
`.git/info/exclude` and `core.excludesFile` — live outside the repository and cannot be reviewed by
anybody but their owner. So a third of the rule set is invisible to code review by construction,
and "it's ignored on my machine" is a statement about a machine and not about the project.

**The review comment.** "You verified this by reading the ignore file. Please paste
`git check-ignore -v` for the two paths — a leftover rule in your `core.excludesFile` would make
this behave for you and leak for everyone else."

**The interview question.** "Two `.gitignore` files in the same repository disagree about a path.
Which one wins, and how do you find out without guessing? Then: name a source of ignore rules that
would not appear in a diff."

## Check yourself

- **Run:** `git check-ignore -v .env .env.example` from inside `projects/00-foundry` — expect two
  lines naming two different patterns from the same file, one of them starting with `!`.
- **Say out loud:** why the exit status of that command was `0` even though the second path is not
  ignored, and which form of the command you would put in a script.
