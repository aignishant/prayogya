## One-line answer

`.env.example` is the committed half of the pair — every key's **name** and no key's **value** —
and it only survives the rule from part 1.1 because one line puts it back, positioned after the
line that swallowed it.

## The idea

The sticker works. Two weeks later a letter from the council does not arrive, and then a second one
does not arrive, and eventually somebody explains that the postman has been reading *no leaflets*
generously. So a second line goes on the sticker, underneath the first: *no leaflets — except
anything from the council*. Underneath, not above, because the postman reads down the card and does
what the last line he read told him.

The project has the same two-line problem, and it starts from a question a stranger has to be able
to answer. Somebody clones this project onto a machine that has never seen it. They need to know
that it reads a key called `GOOGLE_API_KEY`, and they need to know it *before* they try to run
anything, because the alternative is running it, watching it fail, and going to read the source to
find out what was missing. That knowledge is part of the project. It is not a secret — the *name*
of a key gives nothing away. Only the value does.

So the project keeps two files where a careless one keeps one. `.env` holds the values and is never
committed, on any machine, ever. `.env.example` holds the same key names with nothing after the
`=`, is committed, and is read by every stranger who arrives. One is the lock and one is the
drawing of the lock, and you can hand out the drawing.

The catch is the rule you have just written. Part 1.1's ignore file has a line reading `.env.*`,
and `.env.example` is a file whose name begins `.env.` — so the rule intended to catch `.env.bak`
catches the one file in the pair you actually wanted to keep. Nothing announces this. The example
file simply never appears in `git status`, gets left out of the commit, and the stranger clones a
project that does not say what it needs.

The fix is a **negated pattern**: a line beginning `!`, which takes a path back out of the ignore
list. It comes with a position requirement, and the position is the whole of the danger, because
getting it wrong fails exactly as silently as not writing it.

## The mechanism

The committed half of the pair, whole, at its real path:

```ini
# projects/00-foundry/.env.example
# Every key this project reads, with no value after any "=".
# Copy to .env and fill it in:  cp .env.example .env

GOOGLE_API_KEY=
```

**Line by line:**

- Line 1 is the path, so a file that gets copied somewhere still says where it came from. Every
  file this curriculum prints carries it.
- Line 2 states the invariant as a rule a reader can check by looking: *no value after any `=`*.
  A reviewer can hold the whole file to that in one glance, which is what makes it enforceable.
- Line 3 is the command, spelled out. A stranger should not have to work out that `.example` is a
  convention and not part of the name; give them the line to paste.
- Line 4 is blank, separating the instructions from the contents. The keys begin where the comments
  stop, so a reader knows which lines are the list.
- `GOOGLE_API_KEY=` — the name, the `=`, and nothing. Not a placeholder, not `your-key-here`, not
  a truncated real key. A value-shaped string here is an instruction to paste a real one beside it,
  and the next person will.
- One key, because P00 Foundry needs one. The file grows a line every time the code learns to read
  another; a key the code reads and this file does not name is a project that cannot be started by
  anyone but its author.

Now write it into the project and watch part 1.1's rule work against you:

```console
$ git status --short .
?? .gitignore
```

The file is on disk. Git is not offering it. Ask which line decided:

```console
$ git check-ignore -v .env.example
projects/00-foundry/.gitignore:6:.env.*	.env.example
```

Line 6 — `.env.*`, the rule written to catch `.env.bak`. And git refuses this one by name too,
with the identical message it gave for the real secret in part 1.1:

```console
$ git add .env.example
The following paths are ignored by one of your .gitignore files:
projects/00-foundry/.env.example
hint: Use -f if you really want to add them.
hint: Disable this message with "git config set advice.addIgnoredFile false"
$ echo $?
1
```

So take it back out. One line, inserted **after** line 6 — the marked diff against the version
part 1.1 printed:

```gitignore
# projects/00-foundry/.gitignore — marked diff against the file part 1.1 printed
# ── lines 1-4 unchanged from part 1.1: the path comment, the "rule comes first" note,
#    the blank line, and the "# Secrets." comment ──
.env
.env.*
!.env.example
*.key
*.pem
service-account.json
# ── lines 11-15 unchanged from part 1.1: the blank line, the uv comment, and
#    .venv/ · __pycache__/ · *.pyc ──
```

**Line by line:**

- `!.env.example` — the `!` prefix negates, and the documentation states what that buys: "any
  matching file excluded by a previous pattern will become included again." *Previous* is the load-
  bearing word.
- It sits on line 7, immediately below `.env.*` on line 6, because within one ignore file **the
  last matching pattern decides the outcome**. Both lines match `.env.example`; the later one wins.
  Put this line above `.env.*` and `.env.*` is the later match, and the negation does nothing —
  which is what "When it breaks" below actually looks like.
- It names the file exactly rather than using a pattern like `!.env.*example`. A negation is the
  one kind of rule where being generous is expensive: every path you take back out of the ignore
  list is a path `git add .` will pick up.
- It stays inside the secrets block rather than being tidied to the bottom of the file. A reader
  who reads `.env.*` needs to see the exception in the same glance, and the exception is only
  correct relative to the line above it.
- Nothing else in the file moves. The three lines above and the four below are exactly as part 1.1
  printed them, which is why this is a diff and not a second whole file.

The result — the secret ignored, the example offered:

```console
$ git check-ignore -v .env.example
projects/00-foundry/.gitignore:7:!.env.example	.env.example
$ git status --short .
?? .env.example
?? .gitignore
```

*Observed on this machine on 2026-09-09, git version 2.54.0.windows.1.*

## When it breaks

Somebody tidies the file and puts the exception first, because exceptions read better at the top.
Line 5 is now `!.env.example`, and `.env.*` has slid down to line 7.

```console
$ git check-ignore -v .env.example
projects/00-foundry/.gitignore:7:.env.*	.env.example
$ git status --short .
?? .gitignore
```

The negation is still in the file, still spelled correctly, and doing nothing — line 7 is the last
match, so line 7 decides. There is no error, no warning and no red check. What happens instead is
that `.env.example` quietly stops being committed, and the person who finds out is a stranger
cloning the project six weeks later who cannot work out what key it wants. The smallest fix is to
move one line down two lines.

## In production

**What a senior writes instead.** The example file is not maintained by hand. Either the code that
reads the environment is the single list and the example is generated from it, or the loader
validates `.env` against `.env.example` at startup and refuses to run when a name is missing from
either side. Both turn "somebody remembered to update the example" into something a check can fail.

**What degrades at scale.** The invariant is a number, and the number is **zero**: zero characters
after any `=` in the committed file. A single realistic-looking value — `GOOGLE_API_KEY=AIza…` —
teaches every contributor who opens the file that this is where keys go, and one of them will edit
the example instead of the copy. Zero is checkable by a reviewer at a glance and by a one-line CI
grep; "no real secrets" is not.

**The review comment.** "`.env.example` has something after the `=` on line 5 — blank it. Also, the
loader you added reads `SESSION_SECRET` and this file does not name it, so a fresh clone cannot
start."

**The interview question.** "Why commit an example environment file at all, when the names are in
the code anyway? And what would you put in CI to stop it going stale?"

## Check yourself

- **Run:** `git status --short .` from inside `projects/00-foundry` — expect `.env.example` offered
  and `.env` absent, with both files sitting on disk.
- **Say out loud:** which single line you would move, and where to, to make `.env.example`
  disappear from that output — and why nothing would tell you that you had done it.
