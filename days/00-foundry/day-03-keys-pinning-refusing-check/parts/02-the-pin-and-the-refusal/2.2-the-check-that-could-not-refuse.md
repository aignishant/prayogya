## One-line answer

A check communicates its verdict to a machine through exactly one channel — the process exit status
— so a check that prints `RED` and exits `0` is green everywhere it matters, and the two commonest
ways to build one are forgetting `sys.exit` and running the check through a tool that repairs what
the check was looking at.

## The idea

The last thing the locksmith does is turn the key in the lock on the bench. Not look at it. Not hold
it against the code sheet and nod. Turn it, and feel the cylinder go round. That final act has a
property none of the earlier ones have: it produces an answer that does not depend on anybody's
opinion, and it produces the *same* answer for the apprentice and for the master.

Everything you have built today reports to a person. `RED    interpreter: .python-version is
missing` is a sentence, and sentences are for humans reading a terminal. But the reason a check
exists is that eventually **nobody is reading the terminal.** It runs in a hook before a commit, in
a pipeline at three in the morning, in the `done` command that refuses to close a day. In every one
of those places the reader is a program, and a program cannot read your sentence. It reads one
number: the **exit status** the process handed back to whatever started it. Zero means it worked.
Anything else means it did not. That convention is older than every tool in this repository and
every one of them obeys it.

So there are two audiences and only one of them can be fooled. The human audience gets colour and
paragraphs and the name of the file to edit. The machine audience gets a number, and if that number
is wrong then it does not matter what was on the screen — the pipeline goes green, the commit lands,
the day closes. **The screen is decoration. The status is the verdict.**

This is the day's deliberate failure, and it is chosen because it is invisible in exactly the way
that matters: the broken version *looks more correct than usual*. It prints the word RED. It prints
the count of problems. Everything a person would check by eye is present and accurate. The one thing
that is wrong is the thing no person looks at, and it is the only thing the pipeline looks at.

There is a second way to build a check that cannot refuse, and it is subtler because the exit status
is honest — the check simply has nothing left to complain about by the time it runs. If you invoke
your check through a tool that **repairs** the thing being checked, the repair happens first and the
check inspects the repaired state. It reports green, correctly, on a repository that was red a
moment earlier. Nobody wrote a bug; the ordering did it. Today that tool is `uv run`, which brings
the lockfile up to date before it runs your command, and part 2.1 has been passing `--frozen` since
its first transcript for precisely this reason.

Both failures have the same shape underneath, and it is worth saying once in the general form: **a
check is only worth what its red case is worth, and the red case is the one nobody runs.** Green is
self-testing — you see it every day. Red happens rarely, usually on somebody else's machine, usually
under pressure. If you have never watched your check go red, you do not have evidence it can.

## The mechanism

`projects/00-foundry/run.py`, whole file — this project's own driver, and the first of the forty
that every project in this curriculum will carry:

```python
# projects/00-foundry/run.py
"""This project's own driver. `python run.py check` is the only verdict that counts.

Every project in this curriculum carries one of these and depends on nothing above it. This is
the reference version: four checks, each of which can go red on its own, and an exit status that
is the answer rather than a decoration on it.
"""

from __future__ import annotations

import subprocess
import sys
import tomllib
from pathlib import Path

import keys

HERE = Path(__file__).parent


def check_keys() -> list[str]:
    """Every name `.env.example` declares must be wired. Wired is all this can prove."""
    problems = []
    names = keys.names_this_project_reads()
    if not names:
        return [".env.example declares no key names: the committed file is the list of names"]
    for name in names:
        try:
            value = keys.require(name)
        except keys.MissingKey as exc:
            problems.append(str(exc))
            continue
        if keys.looks_like_a_placeholder(value):
            print(f"warn   keys: {name} looks like a placeholder. This check cannot tell a bad "
                  f"key from a good one; only a request to the provider can.")
    return problems


def check_interpreter() -> list[str]:
    """The interpreter actually running must be the one `.python-version` pins."""
    pin_file = HERE / ".python-version"
    if not pin_file.exists():
        return [".python-version is missing: requires-python is a floor, not a pin"]
    pinned = pin_file.read_text(encoding="utf-8").strip()
    running = ".".join(str(n) for n in sys.version_info[:3])
    if running != pinned:
        return [f".python-version pins {pinned}; this interpreter is {running}"]
    return []


def check_pins_are_pins() -> list[str]:
    """A dependency written with `>=` is a floor. Two machines can honour it differently."""
    data = tomllib.loads((HERE / "pyproject.toml").read_text(encoding="utf-8"))
    loose = [d for d in data["project"]["dependencies"] if "==" not in d]
    return [f"{d!r} is a floor, not a pin: one machine gets a version another never saw"
            for d in loose]


def check_lock_is_obeyed() -> list[str]:
    """`uv lock --check` proves the lockfile still answers pyproject, and writes nothing.

    It has to write nothing. A check that repairs what it is inspecting reports on a repository
    that no longer exists, and the drift it was built to catch is gone before anyone sees it.
    """
    result = subprocess.run(
        ["uv", "lock", "--check"],
        cwd=HERE, capture_output=True, text=True,
    )
    if result.returncode != 0:
        lines = [ln.strip() for ln in result.stderr.splitlines() if ln.startswith("error:")]
        detail = lines[0] if lines else "uv printed no error line"
        return [f"uv lock --check exited {result.returncode}: {detail}"]
    return []


CHECKS = {
    "keys": check_keys,
    "interpreter": check_interpreter,
    "pins": check_pins_are_pins,
    "lock": check_lock_is_obeyed,
}


def check() -> int:
    """Run every check, report all of them, and return the verdict as an exit status."""
    failures = 0
    for name, run_check in CHECKS.items():
        problems = run_check()
        failures += len(problems)
        if problems:
            for problem in problems:
                print(f"RED    {name}: {problem}")
        else:
            print(f"green  {name}")
    print(f"\n{failures} problem(s)")
    return 1 if failures else 0


def main(argv: list[str]) -> int:
    if len(argv) != 2 or argv[1] != "check":
        print("usage: python run.py check", file=sys.stderr)
        return 2
    return check()


if __name__ == "__main__":
    sys.exit(main(sys.argv))
```

**Line by line:**

- `import keys` — a plain module import, and it works because `run.py` sits beside `keys.py` and
  Python puts the script's own directory on the import path. No package, no `__init__.py`, no
  install step. This is the smallest arrangement that satisfies the curriculum's rule that a project
  imports nothing from outside itself.
- Every `check_*` function returns `list[str]` — a list of problems, empty when there are none —
  rather than a bool or `None`. Three consequences, and all three are the reason: a check can report
  **more than one** problem, the caller can count them without asking each check to count, and an
  empty list is the natural spelling of "nothing wrong" without anybody having to remember whether
  `True` meant passed or failed.
- No check raises. A check that raises stops every check after it, so the first failure hides the
  other three and you fix them one run at a time. Collecting problems and continuing means one run
  tells you everything — which is the difference between four minutes and four pipeline round-trips.
- `check_keys` **prints** its placeholder warning and does not return it. That is the line where
  warning and failure are separated: the string goes to the human, and nothing is added to the list,
  so `failures` does not move and the exit status does not change. Part 1.2 argued why this one
  cannot be a failure; this is that argument spelled as code.
- `check_interpreter` compares against `sys.version_info` — the interpreter **actually executing
  this line** — and not against `uv python find` or anything else that reports what *should* be
  running. A check must observe the state, not re-ask the question the state came from.
- `tomllib` is standard library from Python 3.11 and reading `pyproject.toml` needs nothing
  installed. `"==" not in d` is deliberately crude, and honest about it: it will not catch
  `platformdirs>=4.11.8,<4.12`, which is a range and would pass. It catches the case that actually
  happens — a bare floor written by `uv add` — and a check that catches the common case reliably is
  worth more than one that attempts full specifier parsing and gets it subtly wrong.
- `subprocess.run([...], capture_output=True, text=True)` with a **list**, never a string and never
  `shell=True`. The list form does not go through a shell, so nothing in it can be word-split or
  glob-expanded, and the failure mode where a path with a space becomes two arguments cannot occur.
- `uv lock --check` and not `uv sync --locked`. Both detect the drift; only one of them leaves the
  repository alone. `sync` would rewrite the virtual environment this very process is running out
  of — and on Windows that fails outright with `Access is denied`, because the interpreter holds its
  own files open. A check must not mutate what it inspects, and here the operating system enforces
  it for you.
- The `CHECKS` dict maps a short name to its function, so adding a fifth check is one line and
  the loop never changes. The order is insertion order, which is a language guarantee since 3.7 and
  not an accident worth relying on nervously.
- `return 1 if failures else 0` — `check` computes the verdict and returns it as a number. It does
  not exit. A function that exits cannot be called by anything else, cannot be tested, and cannot be
  composed into a bigger driver later.
- `main` returns `2` for a usage error, and prints it to `stderr`. Two exit values are two different
  answers: `1` means *I ran the checks and they failed*, `2` means *I never ran them*. A pipeline
  that treats those identically will report a typo in the command as a code failure.
- `sys.exit(main(sys.argv))` — **the whole point of the document.** `main` returns an integer, and
  this is the one line that turns that integer into the process's exit status. It is also the line
  that is easiest to write without, because without it the script still runs, still prints, and
  still looks entirely correct.

Green, with everything today's parts put in place:

```console
$ cd projects/00-foundry
$ uv run --frozen python run.py check
warn   keys: GOOGLE_API_KEY looks like a placeholder. This check cannot tell a bad key from a good one; only a request to the provider can.
green  keys
green  interpreter
green  pins
green  lock

0 problem(s)
$ echo $?
0
```

**Line by line:**

- The warning is above the `green  keys` line, and the check is still green. That is the design from
  part 1.2 working: a hint was printed for the human, and the verdict was not touched.
- `0 problem(s)` and exit `0` agree, which is the state you should stop trusting until you have seen
  them disagree — which is next.
- This is the phase gate's first half, on a machine that had none of this three days ago: **a bare
  machine reaches a green check.**

### The failure: a check that says RED and means green

Two edits. Remove `sys.exit` from the `__main__` block — the single commonest way this bug is
written, because `main(sys.argv)` reads perfectly well and does run — and empty the key, so that the
check has something real to refuse:

```diff
# projects/00-foundry/run.py — the break, at the bottom of the file
 if __name__ == "__main__":
-    sys.exit(main(sys.argv))
+    main(sys.argv)
```

```console
$ printf 'GOOGLE_API_KEY=\n' > .env
$ uv run --frozen python run.py check
RED    keys: GOOGLE_API_KEY is present in .env with an empty value. An empty string is a value, so every `if not os.environ.get(...)` upstream of here will disagree about whether this key is set.
green  interpreter
green  pins
green  lock

1 problem(s)
$ echo $?
0
```

**Line by line:**

- Read the last two lines together, because that pairing is the whole failure: **`1 problem(s)` and
  exit `0`.** The check found the problem, described it accurately, named the file, and then told
  every machine downstream that everything was fine.
- Nothing was caught. `main` returned `1` exactly as it was written to, and the value was simply
  dropped on the floor — Python discards the return value of a top-level call, then exits `0`
  because the script finished without an exception. There is no error, because nothing went wrong;
  the number just went nowhere.
- The screen is *more* convincing than usual. The word RED, in the right place, with a precise
  message. Every review by eye passes. This is why the bug survives: the only witness that disagrees
  is `echo $?`, and nobody types it.
- A commit hook wired to this script would let the commit through. A pipeline step would go green. A
  `done` command would close the day. Each of them asked the only question they can ask, and got
  `0`.

Put the one line back — change nothing else, not the emptied key:

```console
$ uv run --frozen python run.py check
RED    keys: GOOGLE_API_KEY is present in .env with an empty value. An empty string is a value, so every `if not os.environ.get(...)` upstream of here will disagree about whether this key is set.
green  interpreter
green  pins
green  lock

1 problem(s)
$ echo $?
1
```

**Line by line:**

- Byte for byte the same output on screen, and the opposite verdict underneath. That is the cleanest
  possible demonstration that the screen was never carrying the answer.
- The only difference between a working gate and a decorative one was `sys.exit(...)` around a call
  that was already returning the right number.

### The second failure: the tool that fixed it before you looked

Now the ordering bug, which needs no code change at all. Make `pyproject.toml` and `uv.lock`
genuinely disagree, then run the check the way it is natural to run it — through plain `uv run`:

```console
$ grep 'requires-dist' uv.lock | head -1
requires-dist = [{ name = "platformdirs", specifier = "==4.11.8" }]
$ sed -i 's/platformdirs==4.11.8/platformdirs>=4.11.0/' pyproject.toml
$ uv run python run.py check > /dev/null
$ grep 'requires-dist' uv.lock | head -1
requires-dist = [{ name = "platformdirs", specifier = ">=4.11.0" }]
```

**Line by line:**

- The lockfile changed, and the only command run between the two `grep`s was **the check**. `uv run`
  brings the lock up to date before it runs your program; that is documented, useful behaviour, and
  here it means the drift was repaired before `check_lock_is_obeyed` was reached.
- So the lock check reported on a repository that no longer had the problem. Its verdict was
  accurate and worthless: green, about a state that the act of checking had created.
- `--frozen` is the fix, and it is why every transcript in this day has carried it. It tells `uv run`
  to use the lockfile exactly as committed and change nothing. Re-run the same experiment with
  `uv run --frozen` and `uv.lock` is byte-identical afterwards.

*Observed on this machine on 2026-09-09, uv 0.12.3, CPython 3.12.12.*

## When it breaks

The version that reaches production is worse than the one above, because it is a check somebody
wrote *deliberately* to be tolerant and then forgot the tolerance. On Windows the mutating form of
the lock check does not merely repair the repository — it falls over on the interpreter's own open
files:

```console
$ uv run python run.py check
error: failed to remove directory `...\projects\00-foundry\.venv\Lib\site-packages\platformdirs`: Access is denied. (os error 5)
```

That was the first draft of `check_lock_is_obeyed`, running `uv sync --locked` from inside a process
that `uv run` had started out of the very environment being synced. The error is confusing, it is
platform-specific, and it arrives at whoever runs the check on Windows rather than at whoever wrote
it. The smallest fix is the one in the file above: ask a question that writes nothing, `uv lock
--check`, so there is no window in which the check and the thing it checks are fighting over the
same directory.

## In production

**What a senior writes instead.** They do not hand-roll the exit plumbing — the entry point is
`typer`, `click` or `argparse` behind a `console_scripts` entry, and those call `sys.exit` for you
so it cannot be forgotten. And in CI they add `set -euo pipefail` at the top of every script, so a
non-zero status anywhere in a pipeline stops it rather than being swallowed by the next command. The
rule underneath both: never let a status be discarded silently, and prefer arrangements where
discarding it requires an explicit act.

**What degrades at scale.** The number is **zero** — the number of failures a green-on-red check
reports, for as long as it exists. This failure does not degrade gradually; it removes the check
completely while leaving every appearance of it in place. That is worse than having no check, and
measurably so: a team with no check knows it is unprotected, while a team with this one has stopped
looking. The cost is paid in whatever the check was guarding, over however many months pass before
somebody types `echo $?`.

**The review comment.** "This runs the checks and drops the result. `main` returns an `int` and the
`__main__` block ignores it, so the script always exits 0 and the CI step can never fail — please
wrap it in `sys.exit(...)`. And add a test that asserts a known-bad fixture exits non-zero; the
reason this got through review is that everybody read the output and nobody read the status."

**The interview question.** "Your CI has been green for three months. Somebody points out that the
lint step's log has contained errors the whole time. Describe every mechanism by which a step can
print failures and still report success, and say how you would prove, today, that the rest of your
pipeline does not have the same problem."
