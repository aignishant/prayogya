## One-line answer

A `.env` file is an ordinary text file that nothing reads on your behalf — not Python, not `uv run`,
not the shell — so the project has to contain the code that reads it, and that code has to decide
what wins when the same name is in two places at once.

## The idea

You take a key to a locksmith to have a copy cut. They do not measure your key by eye. They read the
code stamped on its shoulder — a short string like `SC1-24680` — and that code, not the lump of
brass, is the thing that says what the key is. The brass in your pocket and the code in their book
are two different objects, and the shop's whole trade depends on knowing which one they are holding
at any moment.

Now watch what the good ones do. They write the code on the docket, and they never write it on the
tag that hangs off the finished key, because a tag with a code on it turns a lost keyring into a
lost house. The code lives in the book. The tag says *front door*. Two files, and the split between
them is the point.

Yesterday the project got that split: `.env` holds the values and never leaves the building,
`.env.example` holds the names and is committed so a stranger knows what to ask for. What yesterday
did not answer is the question you hit the moment you write a line of code — **when the program is
running, where is the value?**

The tempting answer is "in `.env`", and it is wrong in a way that costs an afternoon. A running
program does not read your repository. It has an **environment**: a set of name-to-string pairs the
operating system handed it when it started, which Python shows you as `os.environ`. That set was
built by whatever launched the program — your shell, a container runtime, a scheduler — and by
default it has never heard of a file called `.env`. The file is inert. It is a convention among
tools, not a feature of the machine, and the tool that honours the convention is one you either
install or write.

So there are two places a value can be, and they can disagree. The environment the process was
launched with, and the file sitting next to the code. Every project in this curriculum has to answer
which of those wins, and answer it the same way every time, because the moment two projects answer
differently the same command produces different behaviour in two folders and nobody can see why.

The answer this curriculum takes, and the reason for it: **the process environment wins.** The file
is the fallback. A file is what you keep for your own machine; the environment is how every
deployment target on earth injects a secret — a container gets `-e`, a scheduler gets a secret
mount, a CI runner gets a masked variable, and not one of them writes a `.env` for you. If the file
won, you would have a project that behaves one way on your laptop and another way everywhere it
actually runs, and the difference would appear only in production. Letting the environment win means
your laptop is the special case, which is the correct place for the special case to be.

## The mechanism

`projects/00-foundry/keys.py`, whole file — the first Python this project has owned:

```python
# projects/00-foundry/keys.py
"""Read this project's secrets, and refuse — by name — when one of them is not wired.

Nothing loads a `.env` file for you. Python does not, `uv run` does not, and the shell does not.
This module is the thing that does it, and it is deliberately small enough to read in one pass.

It settles two of the three ways a key can be wrong. The third — present, non-empty and not
accepted by the provider — is not decidable here, and `looks_like_a_placeholder` is a guess that
says so out loud rather than a check that pretends otherwise.
"""

from __future__ import annotations

import os
from pathlib import Path

ENV_FILE = Path(__file__).with_name(".env")
EXAMPLE_FILE = Path(__file__).with_name(".env.example")

# Strings that are almost certainly not credentials. This is a hint, never a verdict: a real key
# is not on this list either, and only the provider can tell the two apart.
PLACEHOLDER_MARKERS = ("fake", "changeme", "change-me", "your-", "todo", "tbd", "xxx", "example")


class MissingKey(RuntimeError):
    """Raised with the name of the key, where it was looked for, and what to do about it."""


def read_env_file(path: Path | None = None) -> dict[str, str]:
    """Parse `KEY=value` lines into a dict. Nothing is exported; the caller decides.

    The default is resolved on every call, not bound at import. A default argument is evaluated
    once, when Python reads the `def`, so `path: Path = ENV_FILE` would freeze the module-level
    value and quietly ignore anyone who reassigned it afterwards.
    """
    path = ENV_FILE if path is None else path
    values: dict[str, str] = {}
    if not path.exists():
        return values
    for line in path.read_text(encoding="utf-8").splitlines():
        line = line.strip()
        if not line or line.startswith("#") or "=" not in line:
            continue
        name, _, value = line.partition("=")
        values[name.strip()] = value.strip().strip('"').strip("'")
    return values


def names_this_project_reads(path: Path | None = None) -> list[str]:
    """Every key name `.env.example` declares. The committed file is the list of names."""
    return sorted(read_env_file(EXAMPLE_FILE if path is None else path))


def get(name: str) -> str | None:
    """The process environment wins; the file is the fallback. Absent is `None`, never `''`."""
    from_process = os.environ.get(name)
    if from_process is not None:
        return from_process
    return read_env_file().get(name)


def require(name: str) -> str:
    """Return the value, or raise `MissingKey` naming the key and the file it belongs in."""
    value = get(name)
    if value is None:
        raise MissingKey(
            f"{name} is not set. Add a line `{name}=...` to {ENV_FILE.name} in "
            f"{ENV_FILE.parent}, or export it in this shell. `.env.example` lists every name "
            f"this project reads."
        )
    if not value.strip():
        raise MissingKey(
            f"{name} is present in {ENV_FILE.name} with an empty value. An empty string is a "
            f"value, so every `if not os.environ.get(...)` upstream of here will disagree about "
            f"whether this key is set."
        )
    return value


def looks_like_a_placeholder(value: str) -> bool:
    """A guess, reported as a warning. Only a request to the provider settles this one."""
    return any(marker in value.lower() for marker in PLACEHOLDER_MARKERS)
```

**Line by line:**

- `from __future__ import annotations` — makes every annotation in the file a string rather than an
  object evaluated at import. It is here so `dict[str, str]` and `Path | None` are free to be
  written the modern way without the file caring which 3.x it lands on. It costs nothing and it is
  the line that stops a type annotation from becoming a runtime error.
- `ENV_FILE = Path(__file__).with_name(".env")` — the path is anchored to **this file**, not to the
  working directory. `Path(".env")` would resolve against wherever the shell happened to be, so the
  same program would find the file when run from the project folder and silently find nothing when
  run from the repository root. `with_name` swaps the filename and keeps the directory, which is
  exactly the sibling relationship these two files have on disk.
- `PLACEHOLDER_MARKERS` is a tuple of substrings and it is deliberately not a set of whole values.
  It exists to catch `fake-not-a-real-key-000` and `your-key-here` without pretending it can catch
  the general case. Its comment says it is a hint, not a verdict, and part 1.2 is about why that
  distinction is the honest one.
- `class MissingKey(RuntimeError)` — a named exception rather than `raise RuntimeError(...)`,
  because a caller that wants to catch *this* failure and not every other runtime error needs a type
  to name. One class, defined where the failure is raised, is the cheapest version of that.
- `def read_env_file(path: Path | None = None)` and then `path = ENV_FILE if path is None else path`
  — this is the two-line dance that avoids Python's oldest trap. **A default argument is evaluated
  once, when the interpreter reads the `def` line, not on each call.** Writing
  `path: Path = ENV_FILE` would bind the value `ENV_FILE` had at import time into the function
  object; reassigning `keys.ENV_FILE` afterwards would change the module attribute and the function
  would go on reading the old path, cheerfully and for ever. `None` as the sentinel and the lookup
  inside the body is how you say "the default is *whatever it is now*".
- `if not path.exists(): return values` — an absent file is an empty dict, not an exception. A
  machine with every value already in its environment has no `.env` at all, and that is a correct
  and common state, not an error. The refusal belongs in `require`, where a *name* is being asked
  for; a reader that raises on a missing file would make the environment-only case impossible.
- `if not line or line.startswith("#") or "=" not in line: continue` — three cheap rejections, in
  the order that costs least. The last one is the one that matters: a line without `=` is not a
  malformed assignment to be reported, it is not an assignment at all, and skipping it is what lets
  the file carry prose.
- `name, _, value = line.partition("=")` — `partition`, not `split("=")`. A value may itself contain
  `=` (base64 padding ends in it constantly), and `split("=")` on
  `TOKEN=abc==` gives you four pieces and a bug. `partition` splits on the **first** occurrence
  only and always returns exactly three parts, so it cannot raise and cannot lose the tail.
- `.strip().strip('"').strip("'")` — trims whitespace, then a wrapping pair of double quotes, then
  single. Editors and shell exports both add quotes, and a value that arrives as `"abc"` with the
  quotation marks still attached fails at the provider with an error that says nothing about quotes.
- `names_this_project_reads` reads `.env.example`, not `.env`. The committed file is the list of
  names precisely because it is the one a stranger has. Deriving the list from `.env` would mean the
  check could only ever verify the keys you already had.
- `os.environ.get(name)` first, then the file — the precedence decision from *The idea*, in one
  function, in two lines, so there is exactly one place in the project where it can be changed.
- `if from_process is not None` — `is not None`, not truthiness. `GOOGLE_API_KEY=` in the
  environment gives you `''`, which is falsy, and a truthiness test would silently fall through to
  the file and read a *different* value than the one the operator set. That is the wrong answer, and
  it is wrong in the direction that hides the operator's mistake. Part 1.2 is built on this line.
- `get` returns `str | None` and never `''` as a stand-in for absence, because the caller needs to
  tell "nobody set this" from "somebody set this to nothing" — and those two need different
  sentences said back to the user.

Running it against the project as day 2 left it:

```console
$ cd projects/00-foundry
$ uv run --frozen python -c "
import os, keys
print('os.environ.get       ->', os.environ.get('GOOGLE_API_KEY'))
print('read_env_file        ->', keys.read_env_file()['GOOGLE_API_KEY'])
print('keys.get             ->', keys.get('GOOGLE_API_KEY'))
print('names from .env.example ->', keys.names_this_project_reads())
"
os.environ.get       -> None
read_env_file        -> fake-not-a-real-key-000
keys.get             -> fake-not-a-real-key-000
names from .env.example -> ['GOOGLE_API_KEY']
```

**Line by line:**

- `os.environ.get` is `None`. This is the whole lesson in one line: the file has existed since
  yesterday, it has the name in it, and the process environment has never heard of it. Nothing read
  it, because nothing was asked to.
- `read_env_file` finds the value, so the file is fine and the parser works.
- `keys.get` returns the file's value **because the environment had nothing** — the fallback fired,
  which is the second branch, not the first.
- `names_this_project_reads` returns `['GOOGLE_API_KEY']` from `.env.example`, the committed file,
  which is the list a stranger cloning this project would get.

And the precedence, proved rather than asserted — the same command with the name set in the shell:

```console
$ GOOGLE_API_KEY=from-the-shell uv run --frozen python -c "
import keys
print('file says   ->', keys.read_env_file()['GOOGLE_API_KEY'])
print('keys.get -> ', keys.get('GOOGLE_API_KEY'))
"
file says   -> fake-not-a-real-key-000
keys.get ->  from-the-shell
```

**Line by line:**

- Both sources hold a value and they differ, which is the only situation where a precedence rule can
  be observed at all.
- `read_env_file` still reports the file's value — it has one job and the environment does not
  change it.
- `keys.get` returns `from-the-shell`. The environment won, exactly as *The idea* said it must, and
  the file is now the thing that gets ignored on every machine that sets the variable properly.

*Observed on this machine on 2026-09-09, uv 0.12.3, CPython 3.12.12.*

## When it breaks

The value is right, the name is right, and the provider rejects it — because the file was edited in
an editor that helpfully wrapped the value in quotes, or a trailing space rode in on a copy-paste.
Strip the `.strip('"')` calls out of `read_env_file` and the same key comes back with its quotation
marks attached:

```console
$ printf 'GOOGLE_API_KEY="fake-not-a-real-key-000"\n' > .env
$ uv run --frozen python -c "import keys; print(repr(keys.get('GOOGLE_API_KEY')))"
'"fake-not-a-real-key-000"'
```

Somebody spends an evening on this, because every error they get is from the provider and every one
of them is about authentication, and authentication errors do not mention punctuation. The smallest
fix is the one already in the file — strip the wrapping quotes at the parser, once, rather than at
each of the twelve call sites that will exist by P05. The habit that finds it faster is printing
`repr()` and not the value: `repr` is the only form in which a trailing space is visible.

## In production

**What a senior writes instead.** They do not write `keys.py` at all — they add
`python-dotenv` and call `load_dotenv()`, or they let the platform inject the variables and read
`os.environ` directly. Both are right, and this file exists anyway, because the curriculum's rule is
build first and compare after: a library you adopted before you could write its twenty lines is a
library you cannot debug at eleven at night. The comparison arrives with the real thing.

**What degrades at scale.** `read_env_file` opens and parses the file **on every call to `get`**.
That is fine at four calls per process and it is not fine inside a retry loop: an agent that reads
three keys per model call, at the free tier's rate, turns a config lookup into thousands of
filesystem reads per run for a file whose contents cannot change. The fix is a module-level cache
and an explicit way to clear it — and the reason it is not in the teaching version is that a cache
added before the read is understood is a cache nobody can reason about.

**The review comment.** "Two things. `get` re-reads the file on every call — cache it, or the retry
loop in `backoff.py` will read `.env` once per attempt. And `require` interpolates `{value!r}` into
the message on the placeholder path; that is fine for a placeholder and it will print a real
credential into CI logs the first time somebody widens the condition. Log the *name*, never the
value."

**The interview question.** "Your service reads its database password from a `.env` file and it
works locally. It is deployed to a container where the password is injected as an environment
variable, and the file is not in the image. What does your config code have to do for both to work,
and which of the two wins if both are present?"
