## One-line answer

An ignore rule written after `git add` does nothing at all, and the way git reports that is by
saying nothing: `check-ignore` prints no line and exits `1` for a tracked file, which reads exactly
like "you are fine".

## The idea

The leaflet is on the mat. You put the sticker up that afternoon and it is a good sticker — the
right words, in the right order, on the right door. Now stand in the hall and ask the sticker about
the leaflet at your feet. It has nothing to say. Not because it is broken; because the leaflet is
not at the door any more, and the door is the only thing the sticker has an opinion about.

This is the failure this day exists to cause, and its whole danger is in the shape of the answer.
Part 2.1 built the habit of asking git rather than guessing, and asking git is the right habit. But
the command has a documented behaviour that turns a warning into a reassurance:

> By default, tracked files are not shown at all since they are not subject to exclude rules; but
> see `--no-index`.

Read that as the person in the hall. They have just written the rule. They run the command that
proves rules. It prints nothing and exits non-zero — the same output, character for character, that
a path with no matching rule produces. Two completely different situations, one indistinguishable
answer: *no pattern applies to this path*, and *this path is past the point where patterns apply*.

The word that separates them is **the index** — the staging area, the list of paths git is holding
for the next commit. `git add` writes into it. Once a path is in the index it is tracked, and
tracked is the state the ignore file cannot reach. So the useful question is never "is this
ignored?" but "is this ignored, *and* has git already got hold of it?", and there are two commands
because those are two questions.

There is one more turn, and it is the reason this part is the day's last. Getting a path back out
of the index is easy. Getting it back out of a commit is not, and getting it back out of a commit
somebody has already pulled is not possible at all. The fix for a leaked value is never a git
command; it is a new value.

## The mechanism

The wrong order, run on purpose. A credential file lands in the project before the rule covering it
exists — so, for this rep, the ignore file is moved aside first, which is exactly the state a
project is in on its first morning:

```console
$ cd projects/00-foundry
$ printf '{"type":"service_account","private_key":"synthetic-000"}\n' > service-account.json
$ mv .gitignore /tmp/gitignore-parked
$ git status --short .
?? .env.example
?? service-account.json
```

Both files are offered, and they look alike. Now the habit that does the damage — the one everybody
has, because it is nine characters shorter than naming files:

```console
$ git add .
$ git status --short .
A  .env.example
A  service-account.json
```

`git add .` was right about one of those and wrong about the other, and it did not distinguish. Now
write the rule — the good rule, from parts 1.1 and 1.2, with `service-account.json` on line 10 —
and ask the question:

```console
$ mv /tmp/gitignore-parked .gitignore
$ git check-ignore -v service-account.json
$ echo $?
1
```

**Line by line:**

- There is no output line at all between the command and the next prompt. That is the entire
  failure: the rule is present, correct, and matches this exact filename, and the command that
  exists to report rules reported nothing.
- The exit status `1` is documented as "None of the provided paths are ignored" — which is true,
  and is true for the *other* reason. A path nobody wrote a rule for gives this identical pair of
  outputs.
- Nothing here is a bug. It is the documented behaviour quoted above: tracked files are not shown,
  because tracked files are not subject to exclude rules. The tool is being precise and the
  precision is what misleads.

And the state it was hiding:

```console
$ git status --short .
A  .env.example
A  service-account.json
?? .gitignore
```

Still staged. One `git commit` away from being permanent. The flag that tells the truth is
`--no-index`, whose documentation names this exact situation — "this can be used to debug why a
path became tracked by e.g. `git add .` and was not ignored by the rules as expected by the user":

```console
$ git check-ignore -v --no-index service-account.json
projects/00-foundry/.gitignore:10:service-account.json	service-account.json
$ echo $?
0
```

**Line by line:**

- `--no-index` asks git to answer the question about *patterns only*, ignoring what it is currently
  holding. Line 10 was always going to match; the index was standing in front of it.
- Comparing the two runs is the diagnosis, and it is the only reliable one: plain `check-ignore`
  silent and `--no-index` naming a rule means **the rule is fine and the file is already tracked**.
  Neither command says that on its own.
- This is also why part 2.1 recommended `check-ignore --no-index` for a check in CI. A test that
  used the plain form would pass on a repository that had already committed the secret.

The fix for the index — remove the path from what git is holding, leave the file on disk:

```console
$ git rm --cached service-account.json
rm 'projects/00-foundry/service-account.json'
$ git check-ignore -v service-account.json
projects/00-foundry/.gitignore:10:service-account.json	service-account.json
$ git status --short .
A  .env.example
?? .gitignore
```

**Line by line:**

- `--cached` is the whole flag. Without it, `git rm` deletes the file from disk as well, which on a
  credential file you have not backed up is a second incident on top of the first.
- The output `rm 'projects/00-foundry/service-account.json'` is git reporting the index change, not
  a deletion. The file is still there; `ls` proves it.
- The moment the path leaves the index, `check-ignore` starts answering again, and names line 10 —
  the same line that was there all along.
- `.env.example` stays staged, and should. `git add .` was correct about that one: it is the
  committed half of the pair from part 1.2.

*Observed on this machine on 2026-09-09, git version 2.54.0.windows.1.*

## When it breaks

The second mistake is made while fixing the first. The path is typed from memory, or the command is
run from the wrong directory, and git answers with the one message in this part that is loud:

```console
$ git rm --cached foundry.log
fatal: pathspec 'foundry.log' did not match any files
$ echo $?
128
```

Somebody at the end of a long evening reads `did not match any files` as *there is nothing there,
so nothing to remove*, and stops. It means the opposite of reassuring: `git rm` looks in the index,
so this is git saying it is not holding that path — under any name, including the one you meant.
The smallest fix is `git status --short` first and copy the path from the output rather than typing
it.

And the part no command fixes. Once the staged file has been committed, `git rm --cached` removes it
from the index and from the next commit, and from **zero** of the commits already made. It is in
`git log -p` for as long as that commit exists, which after a push means as long as any clone
exists. At that point the file is not the problem — the value inside it is, and the only action that
changes anything is issuing a new one at the provider and revoking the old.

## In production

**What a senior writes instead.** Two things, neither of them a git command. The ignore file is in
the repository's first commit, before any code, so the wrong order is not reachable. And a secret
scanner runs as a pre-commit hook and again in CI, because the rule only covers filenames somebody
thought of, and the key that leaks is in `notes.txt`.

**What degrades at scale.** The number is **zero** — the number of already-made commits that
`git rm --cached` changes. Removing a file from history means rewriting the commit that added it and
every commit descended from it, which changes their hashes, which invalidates every branch, tag,
open pull request and clone built on them. That is why the honest incident response is rotation:
rotation costs one new credential, and rewriting shared history costs everybody's working copy.

**The review comment.** "This commit removes `service-account.json`, thanks. Two follow-ups: the
file is still in the diff of the commit that added it, so the key has to be rotated and this pull
request should say it has been — and please move the `.gitignore` change into its own commit ahead
of the one that added the file, so the log reads in the order it should have happened."

**The interview question.** "You find a live credential in a repository's history, added eight
months ago and pushed. Rank what you do, and say what `git rm --cached` gets you and what it does
not."
