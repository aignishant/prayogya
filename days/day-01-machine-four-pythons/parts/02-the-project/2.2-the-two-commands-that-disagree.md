## One-line answer

`python foundry/whoami.py` and `uv run foundry/whoami.py` are the same file in the same directory
and they do not do the same thing — and until you have watched one of them fail, the project you
built in part 2.1 has not actually been shown to be doing anything.

## The idea

The number is on the job sheet now. That was part 2.1, and it was the right fix. But watch what
happens on the morning you are busy: you glance at the sheet, recognise the job, and dial from your
contacts anyway — because that is where your thumb goes. The sheet was correct the whole time. It
simply was not the thing you used.

This is the failure that survives every fix so far, and it is the one worth building a habit
against, because it does not come from not knowing. It comes from knowing perfectly well and typing
the short thing.

A project now describes the interpreter it needs and the packages it depends on. None of that
reaches out and changes what the word `python` means in your shell. `python` still walks `PATH` and
still finds whatever it found on the first page of this day. The project's answer is only used by
commands that ask the project.

So there are two ways to run a file that lives inside a project, and they are not two spellings of
one thing:

One asks the machine — resolve this name, start that interpreter, and run the file in whatever
environment that interpreter happens to be standing in. The project is not consulted, and it does
not need to exist.

The other asks the project — work out what this project requires, make sure the environment matches,
then run the file inside it. uv's documentation is direct about the guarantee: *"When using `run`,
uv will ensure that the project environment is up-to-date before running the given command."*

While the project has no dependencies, both commands appear to work, and that appearance is the
trap: nothing about the first one is correct, it is merely not yet wrong. Add a single dependency
and the two answers separate — permanently, loudly, and with an error message that names the
package rather than the mistake.

## The mechanism

Give the project one real dependency. This is the first thing `foundry` has ever needed that is not
in the standard library:

```console
$ uv add platformdirs
Using CPython 3.12.12
Creating virtual environment at: .venv
Resolved 2 packages in 37ms
Installed 1 package in 50ms
 + platformdirs==4.11.7
```

**Line by line:**

- `uv add` does three things people often do as three commands: it records the dependency in
  `pyproject.toml`, it re-resolves and rewrites `uv.lock`, and it installs into `.venv`. Doing them
  together is what stops the three from disagreeing, which is the ordinary way a lockfile goes
  stale.
- `Resolved 2 packages` — `foundry` and `platformdirs`. The project counts itself, as in part 2.1.
- `+ platformdirs==4.11.7` — the exact version resolved on this machine on this date. It is a
  double-equals even though nobody asked for one: what you request is a range, what you get is a
  version, and the lock is where that becomes durable.

`pyproject.toml` gains the dependency, as a marked diff against the file part 2.1 printed whole:

```diff
  # projects/00-foundry/pyproject.toml
  [project]
  name = "foundry"
  version = "0.1.0"
  requires-python = ">=3.12"
- dependencies = []
+ dependencies = [
+     "platformdirs>=4.11.7",
+ ]
```

**Line by line:**

- `"platformdirs>=4.11.7"` — a floor, not a pin, and written by the tool rather than by you. `uv add`
  defaults to "at least what I just resolved", which keeps the door open for upgrades while
  recording that older versions were never tested here.
- This is intent, so it is a range. The exact version lives in the lock below, which is the division
  part 2.1 set up and this diff is the first real illustration of it.

`uv.lock` gains rather more, and this is the promised contrast — a marked diff against the lock
part 2.1 printed whole:

```diff
  # projects/00-foundry/uv.lock
  version = 1
  revision = 3
  requires-python = ">=3.12"

  [[package]]
  name = "foundry"
  version = "0.1.0"
  source = { virtual = "." }
+ dependencies = [
+     { name = "platformdirs" },
+ ]
+
+ [package.metadata]
+ requires-dist = [{ name = "platformdirs", specifier = ">=4.11.7" }]
+
+ [[package]]
+ name = "platformdirs"
+ version = "4.11.7"
+ source = { registry = "https://pypi.org/simple" }
+ sdist = { url = "https://files.pythonhosted.org/packages/69/b7/802a56eca9f2fac455b8bab5375a2647b0f0e14a2cd63ef077de3c4a7658/platformdirs-4.11.7.tar.gz", hash = "sha256:4f41487eeeeeb07f3a6625e61d9bc0ae6809f92d3386dbd74392fbb76108104d", size = 35127, upload-time = "2026-09-01T13:35:10.502Z" }
+ wheels = [
+     { url = "https://files.pythonhosted.org/packages/27/6e/80993e10a0482f630cef528635789233224f36b1ffd11592aa15d13ff9ce/platformdirs-4.11.7-py3-none-any.whl", hash = "sha256:8a02cb259042c79d1cd0450facc2fe6dc9d303ae7901afbe33bf8ea0b188cef6", size = 23938, upload-time = "2026-09-01T13:35:09.02Z" },
+ ]
```

**Line by line:**

- `source = { registry = "https://pypi.org/simple" }` — where it came from, recorded rather than
  assumed. A project resolved against an internal mirror says so here, which is how you discover
  that a build was not using the index you thought.
- `version = "4.11.7"` — exact. Compare it with the `>=4.11.7` in `pyproject.toml`: same day, same
  package, two different statements, and this is the one that reproduces.
- `hash = "sha256:..."` on both the sdist and the wheel — the lock does not merely name a version, it
  names the **bytes**. This is the line that turns a lockfile from a convenience into a security
  control: a package that resolves to the right version but the wrong content fails here rather than
  at run time.
- `upload-time` — when the artifact was published. It is what lets a later audit ask "was this
  version even available on the day we claim we built this?"
- The `foundry` entry gained a `dependencies` list while keeping `source = { virtual = "." }`. The
  project is still not something you download; it is now something with an edge to something you do.

Now the two commands. Same file, same directory, one after the other:

```console
$ python foundry/whoami.py
Traceback (most recent call last):
  File "C:\Users\nisha_gnzw\OneDrive\Desktop\Projects\agentic-projects\projects\00-foundry\foundry\whoami.py", line 10, in <module>
    import platformdirs
ModuleNotFoundError: No module named 'platformdirs'

$ uv run foundry/whoami.py
version    3.12.12
executable C:\Users\nisha_gnzw\OneDrive\Desktop\Projects\agentic-projects\projects\00-foundry\.venv\Scripts\python.exe
prefix     C:\Users\nisha_gnzw\OneDrive\Desktop\Projects\agentic-projects\projects\00-foundry\.venv
in_venv    True
cache_dir  C:\Users\nisha_gnzw\AppData\Local\foundry\foundry\Cache
```

**Line by line:**

- The first command reached `3.12.10` at the installer path, which has no `platformdirs`, because
  nothing ever installed one there. It is behaving perfectly. It was never told about the project.
- The second reports `3.12.12` and a `prefix` inside `.venv` — `in_venv True`, the test from
  [part 1.2](../01-the-name/1.2-an-environment-is-a-place.md) — so the import resolves.
- **Two different interpreters, two different environments, one file, one directory, one moment in
  time.** Nothing was misconfigured and no step was skipped. The difference is entirely which of the
  two questions from *The idea* each command asked.
- `cache_dir` is the new line the dependency bought, and it is worth noticing that it points outside
  the project — a machine-level location that `platformdirs` computed. Even the answer to "where does
  this project keep things" is a fact about the machine until something writes it down.

## When it breaks

This is the day's deliberate failure, so cause it rather than read it. The error, verbatim, is the
one above:

```text
Traceback (most recent call last):
  File "C:\Users\nisha_gnzw\OneDrive\Desktop\Projects\agentic-projects\projects\00-foundry\foundry\whoami.py", line 10, in <module>
    import platformdirs
ModuleNotFoundError: No module named 'platformdirs'
```

Read what it tells you and what it does not. It names the package, which you already knew, and the
line, which you could count. It does not name the interpreter, it does not name the environment, and
it does not mention that a perfectly good `.venv` containing that exact package is sitting one
directory away. Someone deployed on a Friday with a start command of `python -m app`, watched the
build install every dependency successfully, and spent the evening on an error that says a package
is missing while looking at a log line that says it was installed. The smallest fix is one word in
front of the command.

And note that this is the **same message** you produced in part 1.2 by moving one file out of
`.venv`. One error text, two unrelated causes — which is exactly why the answer is never to guess
from the message, and always to make the failing command print `sys.executable`.

## In production

A senior engineer does not rely on remembering which command to type. They delete the choice: every
entry point in the repository — the Makefile target, the CI step, the container's `CMD`, the
contributing guide — says `uv run`, and no document anywhere says `python`. The reasoning is that a
habit is not a control, and the failure mode here is specifically the failure mode of people who
know better and are in a hurry.

What degrades is the cost of the same mistake at each stage it survives. Caught locally it is
**one** command retyped. Caught in CI it is a pipeline run. Caught in a container image, it is a
build, a push, a deploy and a rollback for a bug whose fix is four characters — and the reason it
gets that far is that every earlier stage had a machine where the ambiguous name happened to resolve
to something with the package installed. The bug is not that it failed in production; it is that it
worked anywhere else.

The review comment: *"This Dockerfile installs with uv and starts with `python`. Which interpreter
is the container's `python`, and is it the one uv installed into?"* On a slim base image the honest
answer is frequently "nobody has checked", and it survives review because the image happens to have
exactly one.

The interview question: **"Your CI installs dependencies successfully and the next step fails with
`ModuleNotFoundError` for one of them. What are the two most likely causes, and what single piece of
output distinguishes them?"** A weak answer starts reinstalling. A strong one names both — the
install and the run used different environments, or the environment was built and then not activated
— and asks for `sys.executable` from both steps, because that one line tells them apart and nothing
else does.

## Check yourself

- **Run:** `python foundry/whoami.py; echo "exit $?"` and then `uv run foundry/whoami.py; echo "exit
  $?"` — expect `1` and `0`, and expect the traceback to name a line number you can point at in the
  file you typed.
- **Say out loud:** both commands were correct in the sense that neither was misconfigured. So what,
  exactly, was the mistake — and why does adding a dependency make it visible when nothing else did?
