## One-line answer

`python` is not a program, it is a **name**, and the machine turns that name into a program by
walking a list — so the only honest way to know what you are running is to make something read the
list out loud.

## The idea

You need a plumber. You open your phone, scroll to **Plumber**, tap the first one, and someone
answers who has never been to your house. You saved four numbers under that label over five years —
the one from the letterbox flyer, the one your neighbour swore by, the emergency one at two in the
morning, the good one — and your phone did exactly what you asked. It dialled *Plumber*. It never
promised which.

Nothing was broken. There was no error and no warning, because from the phone's point of view
nothing went wrong: you gave it a label, it looked the label up, it found more than one match, and
it rang the first. The mistake was never in the dialling. It was in believing that a label you had
reused was a label that identified somebody.

A computer does the same thing with the word `python`, and it hides it better because the wrong one
usually works. It starts, it prints a version, it runs your file. You only find out on the day the
package you installed is not there, and by then the evidence of which one answered has scrolled
away.

Three words, and each is a thing you can point at.

An **interpreter** is one actual program on disk — a `python.exe` at a real path, of one exact
version. It is the person who picks up. An **environment** is an interpreter together with a
particular set of installed packages; two environments on one machine can hold different versions
of the same package and never see each other. And the **search order** is the list the machine
walks when you type a name: a sequence of places, checked in order, first match wins.

Those three were introduced on [day 0 part 1.1](../../../day-000-toolchain-skeleton-driver/parts/01-the-workbench/1.1-one-tool-owns-the-environment.md)
and each has a row in `docs/GLOSSARY.md`. Day 0 used them to pin the interpreter that runs the
authoring driver: one file, one repository, one decision. This part is about the layer underneath
that decision — what the machine does *before* any pin exists, on a machine where the name is
already ambiguous, because that is the state every one of the forty projects starts from.

The plan calls this **the four Pythons that ruin a Monday**. That is not a figure of speech. It is
a count, and on this machine the count is higher.

## The mechanism

uv documents the list it walks. Three places, checked in this order:

```text
When searching for a Python version, the following locations are checked:

- Managed Python installations in the UV_PYTHON_INSTALL_DIR.
- A Python interpreter on the PATH as `python`, `python3`, or `python3.x` on macOS and Linux,
  or `python.exe` on Windows.
- On Windows, the Python interpreters in the Windows registry and Microsoft Store Python
  interpreters (see `py --list-paths`) that match the requested version.
```

*Quoted from `https://docs.astral.sh/uv/concepts/python-versions/`, fetched 2026-09-08.*

Now make the machine read its own list out loud. This is real output from the machine this
curriculum is being written on, today:

```console

cpython-3.15.0rc1+freethreaded-windows-x86_64-none    <download available>

cpython-3.14.7+freethreaded-windows-x86_64-none       <download available>
cpython-3.13.15-windows-x86_64-none                   <download available>
cpython-3.13.15+freethreaded-windows-x86_64-none      <download available>
cpython-3.12.13-windows-x86_64-none                   <download available>

cpython-3.12.10-windows-x86_64-none                   C:\Users\nisha_gnzw\AppData\Local\Programs\Python\Python312\python.exe

cpython-3.11.9-windows-x86_64-none                    C:\Users\nisha_gnzw\AppData\Local\Microsoft\WindowsApps\python.exe

cpython-3.10.20-windows-x86_64-none                   <download available>
```

**Line by line:**

- Rows ending `<download available>` are **not on this machine.** They are versions uv could fetch
  if asked. They are listed because the question `uv python list` answers is "what could I run
  here?", and a version you have not installed yet is a real answer to that. Reading them as
  installed is the first mistake this output invites.
- Rows ending in a path **are on this machine, right now.** Count them: six lines, six real
  `python.exe` files. The plan's "four Pythons" was a conservative figure.
- `cpython-3.12.12` under `AppData\Roaming\uv\python\...` is a **uv-managed** interpreter — uv
  downloaded and owns it. It is first in the search order, and nothing about the shell's `PATH`
  affects it.
- `cpython-3.12.10` under `AppData\Local\Programs\Python\Python312\` came from an installer someone
  ran. It is a different file and a different patch version from the one above, and both are 3.12.
  "We are on 3.12" is not a statement that distinguishes them.
- The four `3.11.9` rows under `WindowsApps\` are the Microsoft Store Python, listed once per name
  it answers to — `python3.exe`, `python3.11.exe`, `python.exe`, and the real file behind them
  inside the `PythonSoftwareFoundation.Python.3.11...` folder. One installation, four names. This
  is the single biggest source of the confusion on Windows: the same interpreter appearing to be
  several, and several appearing to be the same.

Two commands, and the disagreement between them is the whole part:

```console
$ where python
C:\Users\nisha_gnzw\AppData\Local\Programs\Python\Python312\python.exe
C:\Users\nisha_gnzw\AppData\Local\Microsoft\WindowsApps\python.exe

$ uv python find
C:\Users\nisha_gnzw\AppData\Roaming\uv\python\cpython-3.12-windows-x86_64-none\python.exe
```

**Line by line:**

- `where python` walks **`PATH`**, in order, and prints every match. Two matches: the installer
  Python first, the Store Python second. The shell will use the first, and the second is the one
  that answers on a machine where the installer was never run — which is why a command that works
  for you fails for a colleague with no error either of you can see.
- `uv python find` walks **uv's** list, and reports the first available executable. It answers with
  the uv-managed 3.12.12 — a file `where` did not mention at all, because it is not on `PATH`.
- **Read those two outputs together.** On this machine, `python` and "the Python uv would pick" are
  different files with different patch versions, and neither command is wrong. They are answering
  two different questions, and the reason it matters is that you are about to run tools that ask
  each one.
- The fix is never "clean up `PATH`". It is to stop typing the ambiguous name, which is what the
  rest of this day builds.

## When it breaks

Ask for a version by name and watch what the name gets you. This is real, on this machine:

```console
$ python --version
Python 3.12.10

$ python3 --version
Python 3.11.9
```

Two names, one machine, two interpreters, one minor version apart. Someone wrote a setup document
saying `python3 -m pip install ...` and tested it on a laptop where both names meant the same file;
the person following it on a Monday installed into 3.11.9 and ran their program under 3.12.10, and
got a `ModuleNotFoundError` for a package they had just watched install successfully. The smallest
fix is not to choose the right name — it is to stop letting a name choose, which is what
`uv python find` makes visible and what [part 2.1](../02-the-project/2.1-the-project-that-owns-its-interpreter.md)
makes permanent.

## In production

A senior engineer does not put `python` in a script that other people run. They put an absolute
path, or a `uv run`, or a container image whose interpreter is a build artifact — anything whose
answer does not depend on whose shell it is. The rule they are following is narrower than "pin your
Python": it is *never let a name resolve at run time when it could resolve at build time*.

What degrades is the number of ways to be wrong, and it multiplies rather than adds. **Six**
interpreters on this one quiet workstation, and it has nothing exotic installed. Six per machine
across a team of **five** is up to thirty distinct interpreters that all answer to the word
`python`, and the first symptom is never an error message — it is one person's tests passing and
another's failing on identical code, which is the most expensive kind of bug because it is
initially indistinguishable from someone being careless.

The review comment: *"This runs `python`. On the CI runner, which of the interpreters in the image
is that — and did you check, or assume?"* It reads pedantic right up to the release where the base
image adds a second one.

The interview question: **"On a machine you have never seen, how do you find out which Python a
command actually used — after the command has already finished?"** A weak answer says `which
python`. A strong one says: ask the process that ran, not the shell that launched it, because the
shell's answer is about `PATH` and the process's answer is about what actually happened.

## Check yourself

- **Run:** `uv python list` then `where python` on Windows, or `which -a python` elsewhere, then
  `uv python find` — expect to be able to point at each installed interpreter and say where it came
  from, and to say whether the last two commands agree on your machine.
- **Say out loud:** what is the difference between a name, a search order and an interpreter, and
  which of the three does `where python` actually report?
