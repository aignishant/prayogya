## One-line answer

An environment is a **directory**, and a single file inside it is the only reason the interpreter
treats it as one — so "am I in the right environment?" is a question you answer by asking the
running process, never by remembering what you activated.

## The idea

The number you finally dialled in [part 1.1](1.1-four-things-called-python.md) reached somebody.
Now think about what "reaching them" actually got you. You did not reach a person floating in the
air; you reached a person **standing somewhere** — in a van with a full set of parts, or at home on
a day off with none of them. Same person, same number, and whether they can help you depends
entirely on where they are standing when they pick up.

That is the second half of the confusion, and it is the half that survives after you have sorted
out the first. You can identify the interpreter exactly — right file, right version, no ambiguity —
and still get a program that cannot find the package you installed ten seconds ago, because the
interpreter was standing somewhere else.

The place has a name. A **virtual environment** is a directory holding a link back to a real
interpreter and its own folder of installed packages. It is not a mode the shell is in and it is
not a variable you set. It is a folder on disk, and the interpreter decides it is standing in that
folder by finding one small text file, `pyvenv.cfg`, next to itself.

That single fact is the one worth carrying out of this part, because it turns a vague question into
a mechanical one. "Is my environment active?" is a feeling. "Does the running process report a
`prefix` different from its `base_prefix`?" is a fact, and the process will tell you if you ask.

Two more terms, and then the code that asks. `sys.prefix` is where the running interpreter believes
its packages live. `sys.base_prefix` is where the interpreter it was built from lives. When those
two differ, you are inside a virtual environment; when they are equal, you are standing in the base
installation no matter what your prompt says. Nothing else is required to know.

## The mechanism

The first file this project prints. It belongs to P00 Foundry, it imports nothing but the standard
library, and its whole job is to make the machine describe itself:

```python
# foundry/whoami.py
"""Report which interpreter is running this file, and which environment it is standing in.

Nothing here is about Foundry. It is about the machine: every fact below is read out of the
running interpreter itself, so the answer cannot be a setting someone believes.
"""

import sys


def report() -> dict[str, str]:
    """The four facts that identify a running Python, read from the interpreter, not from PATH."""
    return {
        "version": sys.version.split()[0],
        "executable": sys.executable,
        "prefix": sys.prefix,
        "in_venv": str(sys.prefix != sys.base_prefix),
    }


def main() -> None:
    for name, value in report().items():
        print(f"{name:<11}{value}")


if __name__ == "__main__":
    main()
```

**Line by line:**

- `import sys` and nothing else — deliberately. This file has to be runnable by *any* interpreter on
  the machine, including one with no packages installed at all, because the moment it needs a
  dependency it can only answer the question for environments that already work. A diagnostic that
  fails in exactly the situation you are diagnosing is worse than none.
- `sys.version.split()[0]` — `sys.version` is a long string carrying the build date and the
  compiler. Splitting on whitespace and taking the first field gives `3.12.10` and drops the rest.
  `sys.version_info` would be the tidier source, but it prints as a named tuple and this file exists
  to be read by a person at a terminal.
- `sys.executable` — **the load-bearing line.** This is the absolute path of the interpreter that
  is running this very process. It is not a lookup, not `PATH`, and not what your shell would find
  if you asked it again; it is the answer to "what actually started?", which is the only version of
  the question that cannot be wrong.
- `sys.prefix` — the root the interpreter searches for packages. Inside a virtual environment this
  is the environment's own directory.
- `str(sys.prefix != sys.base_prefix)` — the whole test for "am I in a virtual environment",
  expressed as the comparison it actually is. `str(...)` because the surrounding dictionary is
  `dict[str, str]` and a bare `bool` would make the annotation a lie. There is a `sys.real_prefix`
  in old tutorials; it belongs to a tool that predates the standard library's `venv` and is absent
  here, and reaching for it is how this check gets written wrong.
- `f"{name:<11}{value}"` — left-align the key in an eleven-character column so the values form a
  readable second column. Eleven because `executable` is ten characters and one space separates.
- `if __name__ == "__main__":` — the file is importable as well as runnable, so a later day can call
  `report()` from a check rather than parsing this output as text.

Run it with the interpreter the bare name resolves to — no project yet, nothing set up:

```console
$ python foundry/whoami.py
version    3.12.10
executable C:\Users\nisha_gnzw\AppData\Local\Programs\Python\Python312\python.exe
prefix     C:\Users\nisha_gnzw\AppData\Local\Programs\Python\Python312
in_venv    False
```

**Line by line:**

- `3.12.10` and the `Programs\Python\Python312` path are the installer Python that `where python`
  named first in part 1.1. The name resolved exactly as predicted, which is the point: this is not a
  surprise, it is a confirmation that the prediction method works.
- `prefix` equals the interpreter's own installation directory, and `in_venv` is therefore `False`.
  Anything installed from here goes into the machine's shared packages, where every other project on
  this machine will also find it — which is convenient exactly until two projects want different
  versions.
- Note what is **not** here: the uv-managed `3.12.12` that `uv python find` reported. Nothing has
  told this command about uv, so nothing about uv applies.

## When it breaks

An environment is a place, and one file is what makes the place a place. Delete it and watch a
working interpreter forget everything it could reach. Same `python.exe`, same directory, one file
moved aside between the two runs:

```console
$ ./.venv/Scripts/python.exe -c "import sys, platformdirs; print(sys.prefix != sys.base_prefix); print(platformdirs.__file__)"
True
C:\Users\nisha_gnzw\OneDrive\Desktop\Projects\agentic-projects\days\day-01-machine-four-pythons\lab\venv-demo\.venv\Lib\site-packages\platformdirs\__init__.py

$ mv .venv/pyvenv.cfg .venv/pyvenv.cfg.bak

$ ./.venv/Scripts/python.exe -c "import sys, platformdirs; print(sys.prefix != sys.base_prefix); print(platformdirs.__file__)"
Traceback (most recent call last):
  File "<string>", line 1, in <module>
ModuleNotFoundError: No module named 'platformdirs'
```

Nothing was uninstalled. `platformdirs` is still sitting in `site-packages` where it was, and the
executable is byte-for-byte the same file — but without `pyvenv.cfg` beside it the interpreter no
longer believes it is standing in an environment, so it never looks there. Someone hit this by
adding `.venv` to a build cache that copied files selectively and dropped the ones it judged to be
config; every install still logged success and every import failed. The smallest fix is to stop
treating `.venv` as a folder of files and start treating it as one object that is recreated, never
edited — which is what [part 2.1](../02-the-project/2.1-the-project-that-owns-its-interpreter.md)
makes routine.

Remember this error text. You will see it again in
[part 2.2](../02-the-project/2.2-the-two-commands-that-disagree.md) from a completely different
cause, and the fact that one message covers both is exactly why the answer is always to print
`sys.executable` rather than to guess.

## In production

A senior engineer does not ask whether the environment is activated. They make the program say so:
a startup line that logs `sys.executable` and `sys.prefix`, or a check that refuses to run when
`sys.prefix == sys.base_prefix`. The reasoning is that activation is a property of a shell, shells
are not reproducible, and anything that depends on one has a failure mode nobody can reconstruct
from the logs.

What degrades is your ability to tell two different faults apart. One machine with **six**
interpreters, each able to be either inside or outside an environment, is more than **twelve**
states a program could have started in — and every one of them produces the same
`ModuleNotFoundError`. The message names the package, which is the one piece of information you
already had; it never names the interpreter, which is the piece you need. At that point the only
thing standing between you and an afternoon of guessing is whether the process wrote down where it
was standing.

The review comment: *"This build step runs `pip install` and the next one runs the app. Are those
two the same environment, or does it work because the image only has one?"* The honest answer is
usually the second, and it stops being true the first time the base image changes.

The interview question: **"A colleague says the package is installed but the import fails. What do
you ask for first?"** A weak answer starts suggesting fixes. A strong one asks for the output of
`python -c "import sys; print(sys.executable, sys.prefix)"` from the *same command that failed*,
because every fix worth trying depends on that answer and none of them can be chosen without it.
