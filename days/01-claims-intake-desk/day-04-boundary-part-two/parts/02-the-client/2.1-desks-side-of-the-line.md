## One-line answer

One module is the desk's whole knowledge of the boundary — sixty lines, one environment variable
deciding the transport, and nothing above it ever learns which wire carried the answer.

## The idea

The adjusters at the branch do not know whether the file room is downstairs or in another building.
They ask, and a folder arrives. When the department moved its records to a central store two towns
away, the adjusters found out from the internal newsletter, because the way they asked did not
change.

That is the property this part builds, and it is worth being precise about what makes it real
rather than aspirational. It is not that the desk *tries not* to know which transport it is using.
It is that there is exactly one module that could know, and every other module reaches the boundary
through it. The moment a second file constructs a `Client`, the desk has two opinions about how to
reach its data and one of them will be out of date.

An **MCP client** is the near side of the line: the code that launches or connects to a server,
asks for what it offers, and forwards each call. In this project it is one context manager and two
functions, and the whole of its configuration is one environment variable.

The choice that variable makes is the one from part 1.1. Absent, the desk **launches** the boundary
as a subprocess and owns its lifetime. Set to a URL, the desk **connects** to a boundary somebody
else started. Both are correct; they suit different deployments; and by day 19 the container will
set the variable and nothing else will change.

## The mechanism

The whole file, at `claims_desk/boundary.py`:

```python
"""The desk's side of the line: how this project reaches its boundary.

Everything above here asks for policies through these two functions and never learns which
transport carried the answer. That is the whole point of a transport: it decides how a message
travels, never what it means.

    CLAIMS_BOUNDARY unset          launch `python -m claims_mcp` as a subprocess, over stdio
    CLAIMS_BOUNDARY=http://.../mcp connect to a boundary that is already running

Nothing in this file opens a file, knows a path, or imports anything from `claims_mcp`.
"""

from __future__ import annotations

import os
from contextlib import asynccontextmanager
from typing import Any

from mcp import Client, StdioServerParameters

from claims_desk.util.logging import log

#: The environment variable that decides which transport is used. A URL means the boundary is
#: already running somewhere; its absence means this process starts one and owns its lifetime.
ENDPOINT = "CLAIMS_BOUNDARY"

#: How to launch the boundary when there is no URL. The command, and nothing about what it can do.
LAUNCH = StdioServerParameters(command="python", args=["-m", "claims_mcp"])


def target() -> str | StdioServerParameters:
    """The thing a `Client` should be pointed at, from the environment."""
    url = os.environ.get(ENDPOINT, "").strip()
    return url or LAUNCH


@asynccontextmanager
async def connected():
    """Open a connection to the boundary, whichever transport the environment selects.

    Yields a connected `Client`. The caller writes `async with connected() as client:` and never
    finds out which of the two it got — which is the property that lets day 19 put the boundary in
    a container without touching a single caller.
    """
    where = target()
    async with Client(where) as client:
        log(
            "boundary.connected",
            transport="http" if isinstance(where, str) else "stdio",
            protocol=client.protocol_version,
            server=client.server_info.name,
        )
        yield client


async def fetch_policy(number: str) -> dict[str, Any]:
    """Ask the boundary for one policy. Returns the tool's structured answer.

    A connection per call, on purpose and only for now: the desk makes one lookup at a time and a
    long-lived connection is state this project has nowhere to keep yet. Day 9's cast is where
    that stops being true, and the shape of this function is what makes the change local.
    """
    async with connected() as client:
        result = await client.call_tool("fetch_policy", {"number": number})
        if result.is_error:
            raise RuntimeError(f"boundary refused fetch_policy({number!r})")
        return dict(result.structured_content or {})
```

**Line by line:**

- **"Nothing in this file opens a file, knows a path, or imports anything from `claims_mcp`."** —
  three prohibitions, in the docstring, and the third is the one that matters most. Importing
  `claims_mcp.server` here would make the tests pass, the code shorter and the boundary imaginary.
- `import os` — the only configuration mechanism in this file. No settings object, no config file:
  one variable, read where it is used.
- `from mcp import Client, StdioServerParameters` — the client side of the same SDK the boundary
  uses. **That is a shared dependency, not a shared import path**: both sides speak a protocol, and
  they would still work if the far side were written in another language.
- `ENDPOINT = "CLAIMS_BOUNDARY"` — the variable's name as a constant, so the tests can change it
  without hard-coding the string in two places, and so a reader can grep one name to find every
  place the choice is made.
- `LAUNCH = StdioServerParameters(command="python", args=["-m", "claims_mcp"])` — **module-level,
  built once.** Its comment carries the point from day 3: this object says how to *start* the
  server and nothing about what the server can do. A client knows how to launch a process; what it
  offers, it must ask.
- `def target() -> str | StdioServerParameters:` — **the whole decision, in one function, three
  lines long.** Extracting it is what lets part 2.2 assert on the choice without opening a
  connection, and it is why there is no `if` anywhere else in this file.
- `os.environ.get(ENDPOINT, "").strip()` — `.strip()` because an environment variable set to a
  space is a real thing that happens in shell scripts and container definitions, and `" "` is
  truthy.
- `return url or LAUNCH` — **empty means launch.** The absent case and the empty-string case
  collapse into one, which is right: both mean "nobody told me where the boundary is".
- `@asynccontextmanager` — makes `connected()` usable as `async with`. The alternative is every
  caller remembering to close a client, and a caller that forgets leaves a subprocess running.
- `where = target()` **before** the connection — the decision is made once, held in a local, and
  used twice: to connect and to say which it was. Calling `target()` twice would allow the
  environment to change between them, which is the kind of race nobody debugs.
- `async with Client(where) as client:` — **one line handles both transports.** `Client` takes a URL
  string or a `StdioServerParameters` and does the right thing. This is the payoff for the SDK's
  design and the reason this file is short.
- `transport="http" if isinstance(where, str) else "stdio"` — the log line says which wire was
  used. **The only place in the desk that mentions a transport at all**, and it mentions it in order
  to record it, not to branch on it.
- `protocol=client.protocol_version` — the revision that governed the connection, logged on every
  connect. On the day an SDK upgrade changes it, the log says so before anything else does.
- `yield client` inside the `async with` — the client is yielded *while the connection is open*, and
  the context manager's exit closes it. A caller that keeps the object past the `with` block gets a
  closed client, which is the correct and obvious failure.
- `async def fetch_policy(number: str) -> dict[str, Any]:` — **the same name as the tool**, on
  purpose. The desk calls `boundary.fetch_policy(...)`; the boundary declares `fetch_policy`. When a
  log line mentions the name there is no translation step.
- **"A connection per call, on purpose and only for now"** — the honest note. Every lookup starts a
  subprocess, does one thing and stops it, which is wasteful and is the right amount of machinery
  for a desk that makes one lookup at a time. Naming it as temporary, with the day that changes it,
  is what stops it becoming permanent by silence.
- `if result.is_error: raise RuntimeError(...)` — **the error flag is checked.** A result can carry
  `is_error` and still have content, and a caller that read only the content would treat a failure
  as an answer. Note what this does *not* do: a missing policy is not an error, so this never fires
  for `SYN-POL-9999`.
- `return dict(result.structured_content or {})` — a plain dictionary, copied. `or {}` because
  `structured_content` is optional in the protocol and `None` would propagate into the desk's rules
  as a mystery; `dict(...)` because handing callers the SDK's own object invites them to depend on
  its type.

The same code, both ways round. First with nothing set:

```bash
uv run python -c "
import asyncio
from claims_desk import boundary
print(asyncio.run(boundary.fetch_policy('SYN-POL-1002'))['perils'])
"
```

```
{"ts": "2026-09-10T12:04:56.308+00:00", "event": "boundary.connected", "transport": "stdio", "protocol": "2026-07-28", "server": "claims-boundary"}
{"ts": "2026-09-10T12:04:56.318+00:00", "event": "boundary.fetch_policy", "number": "SYN-POL-1002", "found": true}
['escape-of-water', 'fire', 'storm']
```

**Line by line:**

- **Two log lines, then the answer.** The first is the desk's own, from `connected()`; the second is
  the *boundary's*, from inside `fetch_policy` on the far side of the line.
- `"transport": "stdio"` — no `CLAIMS_BOUNDARY` was set, so `target()` returned `LAUNCH` and a
  subprocess was started for this one lookup.
- `"protocol": "2026-07-28"` — the revision that governed the exchange, logged on connect.
- **The boundary's line appears in your terminal because the boundary is this process's child**, and
  a child's standard error goes to the same place as its parent's by default. Remember that; it is
  about to be the difference between the two runs.

Then with a boundary already running from `./run mcp --http`, and one variable set:

```bash
CLAIMS_BOUNDARY="http://127.0.0.1:8931/mcp" uv run python -c "
import asyncio
from claims_desk import boundary
print(asyncio.run(boundary.fetch_policy('SYN-POL-1002'))['perils'])
"
```

```
{"ts": "2026-09-10T12:05:02.362+00:00", "event": "boundary.connected", "transport": "http", "protocol": "2026-07-28", "server": "claims-boundary"}
['escape-of-water', 'fire', 'storm']
```

**Line by line:**

- **The Python is identical.** Not similar: the same three lines, run twice, with one environment
  variable different. That is the claim this part exists to make and it is the whole of the
  evidence for it.
- `"transport": "http"` — `target()` found a URL, so no subprocess was started and the desk
  connected to something already running.
- `"protocol": "2026-07-28"` in both runs — the same revision over both wires, which is the point
  about transports: they carry messages, they do not change them.
- `['escape-of-water', 'fire', 'storm']` — the identical answer. SYN-POL-1002's cover, in the same
  order, because the boundary sorts it.
- **This run is missing the `boundary.fetch_policy` line, and that is not an omission.** The
  boundary logged it, as it always does — into the terminal running `./run mcp --http`, because
  that is where *its* standard error goes. Same log line, same logger, different console. On day 17
  that is exactly the problem a correlation id exists to solve, and this is the first time in this
  project that one run's story is split across two screens.

## When it breaks

Point the desk at a URL where nothing is listening:

```bash
CLAIMS_BOUNDARY="http://127.0.0.1:8932/mcp" uv run python -c "
import asyncio
from claims_desk import boundary
print(asyncio.run(boundary.fetch_policy('SYN-POL-1002')))
" 2>&1 | tail -4
```

```
    |     raise mapped_exc(message) from exc
    | httpx2.ConnectError: All connection attempts failed
    +------------------------------------
```

The tail of a longer traceback, verbatim, and it is the failure mode a subprocess does not have.
On stdio the boundary cannot be *down*: it is started on demand and if it fails to start you find
out immediately. On HTTP it is a thing that must already be running, and "must already be running"
is a new class of outage — the boundary was restarted during a deploy, the port changed, a firewall
rule appeared. Somebody moved the boundary into a container, forgot the port mapping, and got this
one line with no mention of claims, policies or MCP in it. The smallest fix is to check the
listener: `netstat -ano | grep 8932`. The one that lasts is day 15's, where this call gets a retry
policy and an honest escalation instead of a traceback.

## In production

**What a senior writes instead.** The same module, with a connection that is opened once and reused
— a pool, or a client held for the lifetime of the process — because a connection per call over
HTTP is a TCP handshake per policy lookup. They would also put a timeout on it, which this file does
not have: `Client` accepts `read_timeout_seconds` and the default is none, so a boundary that
accepts a connection and never answers hangs the desk forever. That is left for day 15 deliberately,
because a timeout without a retry policy is half an answer.

**What degrades at scale.** One connection per lookup is one process start per lookup on stdio, and
on this project's twelve notifications that is twelve interpreter startups where one would do — most
of the seventeen seconds this project's test suite now takes. On a real desk it would be several
hundred a day, which is the argument for the HTTP transport existing at all, and the reason day 9's
cast will hold one connection across five agents rather than one per agent.

**The review comment.** *"This agent builds its own `Client` because it needed a different timeout.
Put the timeout in `boundary.py` — the second module that knows how to reach the boundary is the
one that will still be pointing at stdio after we move to a container."*

**The interview question.** *"Your client can talk to a service over a pipe or over HTTP, chosen by
configuration. Which failure modes exist in one and not the other, and where in your code should the
difference between them appear?"*
