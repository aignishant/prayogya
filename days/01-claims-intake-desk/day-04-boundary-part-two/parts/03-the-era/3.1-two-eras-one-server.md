## One-line answer

The same boundary answers a modern client with `2026-07-28` and a handshake-shaped client with
`2025-11-25`, the HTTP transport's **default** is the older behaviour, and one line in this
project's own code is all that stands between the two.

## The idea

The branch office got a new phone system, and for a year both systems were live. Ring the new
number and you got the new switchboard: say who you are and what you want in one sentence, and you
are put through. Ring the old number and you got the old one: state your extension, wait to be
connected, and then talk.

Everybody who thought about it assumed the old number had been switched off, because the
announcement said the new system was live. It had not been. The two ran side by side, which was
sensible, and which meant that "what does the office do when you call it" had no single answer — it
depended entirely on which number you dialled.

MCP is in exactly that year. The **protocol era** is the specification's own name for the two sides
of the `2026-07-28` line. **Modern** revisions carry version, identity and capabilities as
per-request metadata; **legacy** revisions establish a session with an `initialize` handshake.
`docs/adr/ADR-0009` records that this project runs the modern side.

That is true and it is not the whole truth, and the difference is what this part is for. The server
this project built answers both. Which era governs a given exchange is a property of **how the
caller asked**, not of the server — and the SDK's HTTP transport defaults to the older behaviour,
so the modern side is the one you have to ask for.

Everything below was driven by hand with `curl`, against this project's own boundary, because the
only way to know which era you are in is to speak to it and read what comes back.

## The mechanism

Start the boundary as a URL, exactly as part 1.1 printed it — with `stateless_http=True` — and ask
it for its tools the simplest way possible:

```bash
curl -s -i -X POST "http://127.0.0.1:8931/mcp" \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{}}'
```

```
HTTP/1.1 200 OK
date: Thu, 10 Sep 2026 11:59:23 GMT
server: uvicorn
cache-control: no-cache, no-transform
connection: keep-alive
content-type: text/event-stream
x-accel-buffering: no
Transfer-Encoding: chunked

event: message
data: {"jsonrpc":"2.0","id":1,"result":{"tools":[{"description":"Look up one policy by its number.\n\n    Returns the policy's cover and its dates, or `{\"found\": false}` when the store has never heard\n    of that number. ... ","inputSchema":{"properties":{"number":{"title":"Number","type":"string"}},"required":["number"],"type":"object","title":"fetch_policyArguments"},"name":"fetch_policy","outputSchema":{"type":"object","additionalProperties":true,"title":"fetch_policyDictOutput"}}]}}
```

The tool's description is elided in the middle where it repeats the docstring from part 1.2;
everything else is verbatim.

**Line by line:**

- `-i` — include the response headers. **The headers are half of what this part is about**, and a
  `curl` without `-i` would have hidden the entire finding.
- `Accept: application/json, text/event-stream` — **both**, and it is required. The Streamable HTTP
  binding may answer with a single JSON document or with an event stream, and a client that accepts
  only one of them is refused.
- `content-type: text/event-stream` — it chose the stream. **Server-Sent Events**: an HTTP response
  whose body is a sequence of small blocks — an `event:` line and a `data:` line, separated by
  blank lines — rather than one document, so the server can keep sending after it has begun
  answering.
- `event: message` then `data: {...}` — one block, carrying one JSON-RPC response. For a request
  with one answer this is a stream of length one, which looks like overhead and is the same shape
  that will carry a long tool call's progress later.
- **No `mcp-session-id` header in the response**, and none was sent. The request stood alone.
- `"inputSchema"` and `"outputSchema"` — **camelCase on the wire.** The Python objects from day 3
  spell these `input_schema` and `structured_content`; this is the same data in its transport form,
  and seeing both is what stops the two spellings being a mystery.
- `"outputSchema": {"type": "object", "additionalProperties": true, ...}` — derived from the
  function's `-> dict[str, Any]` return annotation. A tool that returned a typed object would get a
  precise output schema here, and day 13 is where that matters.

Now remove one argument from `claims_mcp/__main__.py` — `stateless_http=True`, the SDK's default —
and send exactly the same request:

```
HTTP/1.1 400 Bad Request
date: Thu, 10 Sep 2026 11:58:11 GMT
server: uvicorn
content-type: application/json
mcp-session-id: 236a1f1f46a0445e85d2d2125156ee19
content-length: 95

{"jsonrpc":"2.0","id":null,"error":{"code":-32600,"message":"Bad Request: Missing session ID"}}
```

**Line by line:**

- `400 Bad Request` — **the same request, refused.** Nothing about the message changed; the server
  changed what it requires around it.
- `mcp-session-id: 236a1f1f...` — the server minted a session and told you its identifier, in the
  response to the request it just rejected. That is a **protocol session**: connection-scoped state
  a server keeps about one client, minted by the transport and quoted back on every later request.
- `"Missing session ID"` — the error, and it is the legacy era speaking. In that era a client
  performs an `initialize` handshake, receives a session id, and includes it thereafter. The
  `2026-07-28` revision removed protocol-level sessions; this transport still implements them, and
  **runs them by default**.
- **One keyword argument is the whole difference.** A project that never passed `stateless_http` —
  which is to say, a project that wrote the obvious thing — would be running the older mechanism
  while believing otherwise.

Ask the server the old way, and it obliges:

```bash
curl -s -X POST "http://127.0.0.1:8931/mcp" -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":4,"method":"initialize","params":{"protocolVersion":"2026-07-28","capabilities":{},"clientInfo":{"name":"curl","version":"0"}}}'
```

```
event: message
data: {"jsonrpc":"2.0","id":4,"result":{"capabilities":{"experimental":{},"prompts":{"listChanged":false},"resources":{"listChanged":false,"subscribe":false},"tools":{"listChanged":false}},"instructions":"The policy store and the claim file for a first-notice-of-loss desk. Every policy in it is synthetic. Ask for a policy by its number; there is no way to list them all, and no way to read a file.","protocolVersion":"2025-11-25","serverInfo":{"name":"claims-boundary","title":"Claims Intake Desk boundary","version":"0.2.0"}}}
```

**Line by line:**

- **`initialize` works.** The handshake the current revision removed is answered by a server this
  project believes is modern.
- `"protocolVersion":"2025-11-25"` — **and it is not the version that was asked for.** The request
  said `2026-07-28`; the server countered with the legacy revision, because a handshake is a legacy
  construct and answering one means agreeing to that era. **Version negotiation**: the client names
  the revision it wants and the server names the one that will actually govern, and the two may
  differ.
- `"capabilities": {...}` with `listChanged: false` everywhere — **capability negotiation**, the
  other thing a handshake bought: each side declaring, before either asks for anything, which
  optional features it supports. Scoped to the connection, which is why a stateless protocol cannot
  have it in this form.
- `"instructions"` — the same prose from part 1.2, delivered here as part of the handshake result.
- **Compare with the Python client**, which reported `protocol_version` as `2026-07-28` against this
  same server on day 3. Both are true. The era is a property of the exchange.

So how does a caller speak the modern era by hand? Not obviously — and the server says so, one
requirement at a time. Adding the per-request version to `_meta`:

```
{"jsonrpc":"2.0","id":5,"error":{"code":-32602,"message":"params._meta is missing the required envelope key(s): io.modelcontextprotocol/clientCapabilities"}}
```

Adding the capabilities too:

```
{"jsonrpc":"2.0","id":9,"error":{"code":-32020,"message":"mcp-method header does not match the request body's method"}}
```

And finally, with all three — the `_meta` envelope, and an `mcp-method` header naming the method:

```bash
curl -s -X POST "http://127.0.0.1:8931/mcp" \
  -H 'Content-Type: application/json' -H 'Accept: application/json, text/event-stream' \
  -H 'MCP-Protocol-Version: 2026-07-28' -H 'mcp-method: server/discover' \
  -d '{"jsonrpc":"2.0","id":10,"method":"server/discover","params":{"_meta":{"io.modelcontextprotocol/protocolVersion":"2026-07-28","io.modelcontextprotocol/clientCapabilities":{}}}}'
```

```
{
  "jsonrpc": "2.0",
  "id": 10,
  "result": {
    "cacheScope": "private",
    "capabilities": {
      "prompts": {"listChanged": true},
      "resources": {"listChanged": true, "subscribe": true},
      "tools": {"listChanged": true}
    },
    "instructions": "The policy store and the claim file for a first-notice-of-loss desk. Every policy in it is synthetic. Ask for a policy by its number; there is no way to list them all, and no way to read a file.",
    "resultType": "complete",
    "supportedVersions": ["2026-07-28"],
    "ttlMs": 0,
    "_meta": {
      "io.modelcontextprotocol/serverInfo": {
        "name": "claims-boundary",
        "title": "Claims Intake Desk boundary",
        "version": "0.2.0"
      }
    }
  }
}
```

**Line by line:**

- **Three things are required together**, and the server refuses until all three are present: the
  protocol version in `_meta`, the client's capabilities in `_meta`, and an `mcp-method` header that
  matches the body's method. Each refusal names exactly what is missing, which is why this was
  discoverable by hand at all.
- `io.modelcontextprotocol/protocolVersion` — **the version, on the request.** This is what replaced
  the handshake: there is no session to agree it in, so it rides on every message.
- `io.modelcontextprotocol/clientCapabilities` — and so do the capabilities. Empty here, because
  `curl` supports nothing optional. The same information the handshake exchanged once, now sent
  every time — the trade the revision made: more bytes per request, no connection state at all.
- `mcp-method: server/discover` **matching the body** — a header that duplicates the message. It
  lets an intermediary route or cache a request without parsing the body, and the server checks
  the two agree so the duplication cannot be used to lie.
- `server/discover` — the RPC the versioning page calls mandatory, "which returns the server's
  supported protocol versions, capabilities, and identity in a single request". **It answers only
  in the modern era**: asked without the envelope it returns `Method not found`.
- `"supportedVersions": ["2026-07-28"]` — **one version, and it is the modern one.** Read this next
  to the `initialize` response above, which said `2025-11-25`. The same server, asked two ways,
  gives two different answers about what it speaks — and both are honest, because each is an answer
  about the era it was asked in.
- `"capabilities"` with `listChanged: true` and `subscribe: true` — **richer than the handshake's
  answer**, which said `false` to everything. The legacy path is a compatibility shim; the modern
  path is where this server actually lives.
- `"cacheScope": "private"` and `"ttlMs": 0` — result metadata the older revision had nowhere to
  put. The server is telling a caller whether this answer may be cached and for how long: `0`
  means do not.
- `"resultType": "complete"` — this is the whole answer rather than a page of one.
- `_meta.io.modelcontextprotocol/serverInfo` — **identity has moved into the metadata**, where the
  handshake used to carry it as a top-level `serverInfo`. Same three fields, different place, and a
  client written for one shape finds nothing in the other.

## When it breaks

The failure is not any of the errors above. Every one of them is a server telling you precisely what
is wrong, which is the best possible behaviour. **The failure is the default.**

Write `server.run("streamable-http", host=HOST, port=PORT)` — the obvious line, the one in most
examples — and this project's boundary runs the session-based transport that the current revision
removed. Nothing warns you. The Python client still reports `protocol_version` as `2026-07-28`,
because it negotiates that on its own. `./run check` stays green, because every test in this project
either connects in-process or over stdio, and **neither of them touches the HTTP session
machinery at all**. There is no assertion anywhere in this repository that would notice.

What it costs is not visible until something else is on the other end: a client that sends one
request and expects an answer gets `Bad Request: Missing session ID`, at which point the argument
starts about whose implementation is wrong. It happened while this day was being written, in the
most confusing possible form — a stale boundary from an earlier experiment was still holding the
port, the new one with `stateless_http=True` failed to bind *after* printing `Application startup
complete`, and every request went to the old server. The error looked like a bug in code that was
never running.

The smallest fix is the keyword argument. The one that lasts is a test that speaks HTTP: this
project does not have one, it is left as a rep in the hub §5, and its absence is the reason a
one-word change could alter which protocol era the boundary serves without a single check going red.

## In production

**What a senior writes instead.** They pin the behaviour rather than inheriting it — every transport
option stated explicitly, even where the value matches the default — and they put one test on the
real HTTP endpoint that asserts a bare request succeeds. The general habit: **a default is a
decision somebody else made, at a date you do not know, for a use case that may not be yours.**
Where the decision matters, write it down in your own code so that a change of default is a change
of behaviour you find out about.

**What degrades at scale.** Session state is per client and lives in the server's memory, so a
session-based boundary serving five agents holds five sessions, and a restart drops all of them
mid-notification. Stateless means any request can be answered by any instance, which is what makes
the compose file on day 19 able to run more than one. This is the whole reason the revision removed
protocol sessions, and it stops being an abstraction the moment there are two containers.

**The review comment.** *"We are on `mcp` 2.x and the boundary is running session-based HTTP because
`stateless_http` was not passed. Set it, and add a test that POSTs a bare `tools/list` — otherwise
the next SDK upgrade can move us between protocol eras and nothing in CI will mention it."*

**The interview question.** *"Your server reports that it speaks the current version of a protocol,
and a client using the previous version connects to it successfully. Explain how both can be true,
and tell me what you would put in place before you would be willing to say which era you are on."*
