## One-line answer

The same server object serves a second transport — an HTTP endpoint instead of a subprocess — and
the only thing that changes is who owns the boundary's lifetime.

## The idea

There are two ways to get something out of the branch office. You can walk in and stand at the
hatch, which is what yesterday built: you arrive, the clerk is there for you, and when you leave
the arrangement ends. Or you can ring the office, which is a different shape entirely — the office
was open before you called, it will be open after you hang up, and three people can be on the line
at once.

Neither is better. They answer different questions. The hatch is right when you are the only person
who needs the file room and you would like it to exist for exactly as long as you do. The phone is
right when the office serves a department, when it should survive one caller hanging up, and when
somebody other than the caller decides when it opens.

In protocol terms a **transport** is the arrangement that carries protocol messages from one
process to another. The specification calls it a binding: it decides how messages are framed and
delivered and how termination is signalled, and **never what a message means.** That last clause is
what this part is really demonstrating. The tool, its schema, its answer and the rules around it are
all identical across both. Only the wire changes.

The second transport here is **Streamable HTTP**: the server is a URL rather than a process — one
endpoint that accepts POST, one HTTP request per message, and an answer that is either a single
JSON object or an event stream scoped to that request.

## The mechanism

`claims_mcp/__main__.py`, in full. Day 3 printed a four-line version of this file; this is that
file with a transport switch, and every line is here because the file is small enough that a diff
would be harder to read than the whole:

```python
"""Run the boundary, on one of its two transports.

    python -m claims_mcp            stdio: the client owns this process's lifetime
    python -m claims_mcp --http     Streamable HTTP: the boundary is a URL, and outlives its clients

On stdio there is nothing else in this file on purpose. A client launches this module as a
subprocess and speaks the protocol down its standard input and output, so **anything else printed
to standard output would be read as a protocol message** and would corrupt the connection. The
desk's logger writes to standard error for exactly this reason.

On HTTP the same rule does not apply — a response has a body of its own — and the same server
object serves both. The transport decides how messages travel; it never decides what they mean.
"""

from __future__ import annotations

import sys

from claims_mcp.server import server

#: Where the boundary listens when it is a URL. Loopback, deliberately: this server has no
#: authentication of any kind, and day 16 is where that becomes a decision rather than a default.
HOST = "127.0.0.1"
PORT = 8931
PATH = "/mcp"

if __name__ == "__main__":
    if "--http" in sys.argv[1:]:
        server.run(
            "streamable-http",
            host=HOST,
            port=PORT,
            streamable_http_path=PATH,
            stateless_http=True,
        )
    else:
        server.run("stdio")
```

**Line by line:**

- **The docstring now documents two commands**, and the difference it names is not technical: it is
  *who owns this process's lifetime*. On stdio the client starts and stops the server. On HTTP
  something else does, and the client is a caller rather than a parent.
- **"On HTTP the same rule does not apply — a response has a body of its own"** — the stdout
  prohibition from day 3 is a property of the stdio binding, not of the protocol. On HTTP a stray
  `print` goes to the server's own console and corrupts nothing. Knowing *why* a rule exists is how
  you know where it stops applying.
- `import sys` — for `sys.argv`. No argument parser: one flag, checked by membership. A project
  that reaches for `argparse` to read one flag has spent a dependency's worth of reading on a
  boolean.
- `HOST = "127.0.0.1"` — **loopback, and the comment says why.** This server has no authentication
  of any kind: anyone who can reach the port can read the policy book. Binding to `0.0.0.0` would
  make that a network-wide fact rather than a machine-local one, and day 16 is where that becomes a
  decision instead of a default.
- `PORT = 8931` — a constant, high enough to avoid the crowded ranges. It is here rather than
  inline so the tests and the client can be pointed at the same number by reading it.
- `PATH = "/mcp"` — the endpoint. One path, accepting POST, and it is the whole HTTP surface: there
  is no `/tools` and no `/policies`, because the URL structure is not the API. The **method inside
  the message** is.
- `if "--http" in sys.argv[1:]:` — `[1:]` skips the program name. Membership rather than
  positional, so `./run mcp --http` works whatever else is on the line.
- `server.run("streamable-http", ...)` — **the same `server` object as the stdio branch.** Not a
  second server, not a shared configuration: one object, two ways of being reached. Everything
  declared in `claims_mcp/server.py` is available on both, automatically, and nothing has to be
  registered twice.
- `stateless_http=True` — **the most consequential argument in this file, and the least obvious.**
  Without it the SDK runs the session-based HTTP mode: it mints an `Mcp-Session-Id`, expects it
  back on every later request, and refuses anything that arrives without one. That is the mechanism
  the current protocol revision removed. Part 3.1 drives both modes by hand and shows the two
  answers. The default is the old one.
- **The `else` branch is unchanged from day 3.** Adding a transport did not touch the one that
  already worked, which is the property a transport switch is supposed to have.

Then the driver gains argument forwarding, so the flag can reach the command. This is a **marked
diff against the `run` printed on day 1 part 1.3**, with the line day 3 added to `COMMANDS`
already in place:

```diff
     ./run setup          the day-0 machine check
     ./run mcp            the boundary, on stdio, until you stop it
+    ./run mcp --http     the boundary, as a URL, until you stop it

@@ in main() @@
     if command not in COMMANDS:
         print(f"no such command: {command}", file=sys.stderr)
         return usage()
+    extra = argv[1:]
     for step in COMMANDS[command]:
-        status = run(step)
+        status = run(step + extra if len(COMMANDS[command]) == 1 else step)
```

**Line by line:**

- `extra = argv[1:]` — everything after the command name. `./run mcp --http` gives `["--http"]`.
- `step + extra if len(COMMANDS[command]) == 1 else step` — **arguments are forwarded only to
  single-step commands.** `mcp`, `lint`, `test` and `setup` are one step each and can take
  arguments; `check` is three steps, and forwarding `--http` into all three would pass it to ruff
  and to pytest, which is nonsense. The condition is doing real work and it is the kind of line
  worth a comment in a bigger driver.
- **The forwarding is why this is one command rather than two.** `./run mcp-http` would also work
  and would mean the driver has to learn every combination; forwarding means the driver stays a
  dispatcher.

Start it:

```bash
./run mcp --http
```

```
--- uv run python -m claims_mcp --http
INFO:     Started server process [12072]
INFO:     Waiting for application startup.
StreamableHTTP session manager started
INFO:     Application startup complete.
INFO:     Uvicorn running on http://127.0.0.1:8931 (Press CTRL+C to quit)
```

**Line by line:**

- `--- uv run python -m claims_mcp --http` — the driver echoing the command it is about to run, from
  day 1. The `--http` arrived, which is the forwarding working.
- `Started server process [12072]` — an HTTP server, with a process id, listening. **Nothing
  launched it on demand**: it is running because you started it, and it will keep running.
- `StreamableHTTP session manager started` — the SDK's own line, and it is a hint worth noticing:
  even with `stateless_http=True` there is a session manager in the stack. The transport was built
  session-first and statelessness is a mode of it, which is exactly the era gap part 3.1 measures.
- `Uvicorn running on http://127.0.0.1:8931` — the address. On stdio there is no address, because
  there is nothing to address: the server is a child, reached down a pipe.
- **This blocks.** Ctrl-C stops it, and while it runs, several clients can call it at once — which
  is the property the next part's client is written to take advantage of.

## When it breaks

Start it twice and the second one cannot have the port:

```
INFO:     Started server process [15960]
INFO:     Waiting for application startup.
StreamableHTTP session manager started
INFO:     Application startup complete.
ERROR:    [Errno 10048] error while attempting to bind on address ('127.0.0.1', 8931): [winerror 10048] only one usage of each socket address (protocol/network address/port) is normally permitted
INFO:     Waiting for application shutdown.
StreamableHTTP session manager shutting down
INFO:     Application shutdown complete.
```

Verbatim, from this project. Read the order carefully, because it is the trap: **application
startup completes, and then the bind fails.** The server announces itself as started, and the error
arrives four lines later — so a script that starts the boundary and waits for "Application startup
complete" before proceeding will happily carry on talking to *the older server*, which is a
different process with a possibly different version of your code.

That happened while this day was being written. A boundary was left running from an earlier
experiment, a new one was started with `stateless_http=True`, and the requests that followed were
answered by the old stateful one — producing a "Missing session ID" error that looked like a bug in
the new code and was not. The smallest fix is to find the listener and stop it:
`netstat -ano | grep 8931`, then kill the process id it names.

## In production

**What a senior writes instead.** Not a `__main__.py` that binds a port — an ASGI application
handed to a process manager. The SDK exposes `server.streamable_http_app()`, which returns the app
without running it, and that is what goes into a container with a real server in front of it and a
health endpoint beside it. Day 19 does exactly that. `server.run(...)` is the right thing while the
answer to "who starts this" is "you, in a terminal".

**What degrades at scale.** A subprocess per client is fine for one desk and hopeless for five
agents, which is where day 9 is heading: five stdio clients means five Python interpreters, five
copies of the policy store parsed into five heaps, and five processes to start on every
notification. One HTTP boundary serving five clients is one copy of the data and one place to look
when something is wrong. The cost is that it is now a thing that can be down, which is a failure
mode a subprocess does not have.

**The review comment.** *"The boundary binds `0.0.0.0` so we can hit it from the other container.
Bind loopback and put them in the same network namespace, or add authentication in this PR —
right now anything that can route to this host can read the whole policy book."*

**The interview question.** *"You have a service that speaks the same protocol over a pipe and over
HTTP. Name three things that differ between those two deployments that have nothing to do with the
protocol itself."*

## Check yourself

- **Run:** `./run mcp --http` in one terminal, and in another
  `curl -s -o /dev/null -w "%{http_code}\n" -X POST http://127.0.0.1:8931/mcp` — expect a status
  code rather than a connection refusal. The body will be an error; that is part 3.1's subject.
- **Say out loud:** The stdio version forbids printing to standard output and the HTTP version does
  not. State the rule that explains both, in one sentence, without mentioning either transport.
