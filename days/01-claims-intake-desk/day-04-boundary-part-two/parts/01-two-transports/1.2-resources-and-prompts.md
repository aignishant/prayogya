## One-line answer

A boundary offers three kinds of thing, not one: tools are actions a caller takes, resources are
reference data a caller reads, and prompts are the wording the boundary itself supplies for talking
about what it owns.

## The idea

Behind the counter at the branch office there are three different objects and everybody who works
there can tell them apart without thinking.

There is the **docket** — the list of things you can ask the clerk to do. Fetch a file, log a
return. Each one is an action, each one changes what the clerk is doing, and you ask for one at a
time.

There is the **laminated sheet on the wall** — the peril codes, the abbreviations, the list of
which forms need a photograph attached. Nobody asks the clerk for it; you read it. It is the same
every day, it is the same for everybody, and going to the clerk for it would be a waste of both
people's time.

And there is the **house style**: the standard wording for a letter telling a policyholder what is
missing. It lives with the department that owns the claim file, not with whoever happens to be
writing the letter, because the department is accountable for what goes out on its paper.

The protocol has exactly these three. **Tools** are what a caller does. **Resources** are what a
caller reads, addressed by a URI. **Prompts** are named pieces of wording a server offers for
asking a model about the things the server owns. Yesterday declared one tool. Today the boundary
gets one of each of the others, and the interesting question is not how — the decorators are three
lines — but **which of the three each thing should be.**

The test that decides it: does it take an argument that varies per claim and do work, or is it the
same for everybody? `fetch_policy("SYN-POL-1001")` is a tool. The peril vocabulary is a resource.
And the wording of a deficiency letter is a prompt, because the boundary owns the claim file, so
the boundary owns the house style for writing about it.

## The mechanism

The whole file, at `claims_mcp/server.py`. Day 3 printed this file with a tool and no resource or
prompt; the tool below is unchanged from that version, and everything after it is new:

```python
"""The claims boundary: the only process that opens the policy store.

One server object; a tool, a resource and a prompt. The tool's description and its parameter names
are the whole interface a caller gets — there is no import, no shared type and no file path
crossing this line.

Run it over stdio with `python -m claims_mcp`, over Streamable HTTP with
`python -m claims_mcp --http`, or in-process from a test by handing the `server` object straight
to a `Client`.
"""

from __future__ import annotations

from typing import Any

from mcp.server import MCPServer

from claims_desk.domain import PHOTO_REQUIRED_FOR
from claims_desk.store import Store
from claims_desk.util.logging import log

#: The server's identity. A client reads this back and it appears in every log the boundary keeps,
#: so the version moves when the tools this server declares change.
server = MCPServer(
    name="claims-boundary",
    title="Claims Intake Desk boundary",
    version="0.2.0",
    instructions=(
        "The policy store and the claim file for a first-notice-of-loss desk. "
        "Every policy in it is synthetic. Ask for a policy by its number; there is no way to "
        "list them all, and no way to read a file."
    ),
)

#: The one object in this process that touches the disk. It is created here, at import, so that
#: exactly one `Store` exists per server process.
store = Store()


@server.tool()
def fetch_policy(number: str) -> dict[str, Any]:
    """Look up one policy by its number.

    Returns the policy's cover and its dates, or `{"found": false}` when the store has never heard
    of that number. A number that does not exist is an answer, not an error: an intake desk is
    given wrong policy numbers every day, and the caller needs a letter rather than a traceback.

    Args:
        number: The policy number exactly as the caller gave it, for example `SYN-POL-1001`.
    """
    policy = store.policy(number)
    log("boundary.fetch_policy", number=number, found=policy is not None)
    if policy is None:
        return {"found": False, "number": number}
    return {
        "found": True,
        "number": policy.number,
        "product": policy.product,
        "status": policy.status,
        "inception": policy.inception.isoformat(),
        "expiry": policy.expiry.isoformat(),
        "excess": policy.excess,
        "fast_track_limit": policy.fast_track_limit,
        "perils": sorted(policy.perils),
    }


@server.resource(
    "claims://cover/perils",
    name="perils",
    title="The perils this book of business knows",
    description=(
        "Every peril slug that appears on a policy in this store, and whether a photograph is "
        "part of a complete notification for it. Reference data: it does not change per claim, "
        "so a client reads it once rather than asking a tool on every notification."
    ),
    mime_type="application/json",
)
def perils() -> dict[str, Any]:
    """The peril vocabulary, with the photograph rule attached to each."""
    known = sorted({peril for policy in store.policies() for peril in policy.perils})
    log("boundary.read_resource", uri="claims://cover/perils", count=len(known))
    return {peril: {"photo_required": peril in PHOTO_REQUIRED_FOR} for peril in known}


@server.prompt(
    name="deficiency_letter",
    title="Draft a deficiency letter",
    description="The house style for telling a policyholder what is missing from their claim.",
)
def deficiency_letter(claim_id: str, reason: str) -> str:
    """The instructions for writing one deficiency letter.

    A prompt is the server's contribution to how a model should be asked, kept beside the data it
    is about. The desk does not hard-code this wording: the boundary owns the claim file, so the
    boundary owns the house style for writing about it.
    """
    log("boundary.get_prompt", name="deficiency_letter", claim=claim_id, reason=reason)
    lines = [
        f"Write a short deficiency letter for claim {claim_id}.",
        f"The single reason this claim cannot be fast-tracked is: {reason}.",
        "",
        "Rules:",
        "- Name exactly one missing or failing item. Do not list alternatives.",
        "- Say precisely what the policyholder must send or confirm.",
        "- Do not quote a policy number the caller did not give you.",
        "- Do not promise a decision, a timescale or a settlement figure.",
        "- Four sentences at most, plain words, no apology.",
    ]
    return "\n".join(lines)
```

**Line by line:**

- `version="0.2.0"` — **the boundary's version moved, and it had to.** Day 3's comment on this line
  says the version moves when what this server declares changes, and a resource and a prompt are
  changes to the docket. Day 3's test pinned `0.1.0`, so it went red the moment this file was
  saved — which is the test doing its job, and part 2.2 is where the assertion is updated with the
  change rather than before it.
- `from claims_desk.domain import PHOTO_REQUIRED_FOR` — **a second import from the desk into the
  boundary**, in the same direction as the first. The photograph rule was written on day 2 as part
  of the domain; the boundary publishes it rather than restating it, so the two cannot disagree.
- `@server.resource("claims://cover/perils", ...)` — the decorator takes a **URI first**, because a
  resource is addressed rather than called. `claims://` is this project's own scheme, and it is not
  a URL: nothing resolves it, nothing fetches it over a network, it is a name with a shape that
  clients already know how to hold.
- `claims://cover/perils` — read as a path: the `cover` part of this boundary's world, and within
  it, `perils`. When day 12 adds retrieval, `claims://` gains siblings and the scheme is already
  doing the organising.
- `name="perils"` and `title="The perils this book of business knows"` — the short identifier and
  the human label. Both, because a client shows one to a person and uses the other in code.
- **The `description` says why it is a resource rather than a tool** — *"it does not change per
  claim, so a client reads it once rather than asking a tool on every notification"*. That sentence
  is the design rule from the scene above, written where the next person will read it.
- `mime_type="application/json"` — what the reader gets. It is `application/json` rather than
  `text/plain` because the body is structured, and a client that knows the type can parse without
  guessing.
- `def perils() -> dict[str, Any]:` — **no parameters.** That is the shape of a resource: it takes
  its identity from its URI, not from arguments. A resource that needed a claim id would be a tool
  wearing the wrong decorator.
- `sorted({peril for policy in store.policies() for peril in policy.perils})` — a set comprehension
  across every policy, flattened and sorted. **It publishes the vocabulary, not the policies**: the
  output is eight or so slugs, and a caller cannot recover from it which policy covers what.
- `{peril: {"photo_required": peril in PHOTO_REQUIRED_FOR} for peril in known}` — each peril mapped
  to the rule that applies to it. A nested object rather than a bare boolean because this will grow:
  the next field is likely an excess rule, and a caller that unpacked a boolean would break.
- `@server.prompt(name="deficiency_letter", ...)` — a **named** prompt, so a client asks for it by
  name. The name is a stable identifier the way a tool's is; the title and description are for a
  person choosing between prompts in an interface.
- `def deficiency_letter(claim_id: str, reason: str) -> str:` — **a prompt takes arguments**, which
  is what distinguishes it from a resource. It is a template with holes, filled in on the server
  side.
- **"the boundary owns the claim file, so the boundary owns the house style"** — the argument for
  this being here at all. The desk could hard-code this wording in `claims_desk/`, and then two
  things would be true: the wording would live away from the data it is about, and changing it would
  be a change to the desk rather than to the department that answers for the letters.
- `lines = [...]` then `"\n".join(lines)` — a list of lines joined, rather than a triple-quoted
  string or a chain of `f"...\n"` fragments. It reads as the document it produces, it survives
  reformatting, and every line is individually greppable when somebody asks why a letter said
  something.
- **The five rules in the prompt are constraints, not encouragements.** *Name exactly one item. Do
  not quote a policy number the caller did not give you. Do not promise a decision, a timescale or a
  settlement figure.* Every one of them is a thing an insurer would be held to, and every one is
  something a fluent model will do by default if not told otherwise. This is the first appearance in
  this project of instructions written against a model's helpfulness rather than against its
  ignorance.
- `log(...)` in all three — the boundary records what was asked of it, whichever of the three shapes
  it was. Same logger, same stream, same reason as day 3.

Read them back, in-process:

```bash
uv run python -c "
import asyncio
from mcp import Client
from claims_mcp.server import server
async def main():
    async with Client(server) as c:
        rs = await c.list_resources()
        print('resources:', [(r.name, str(r.uri)) for r in rs.resources])
        ps = await c.list_prompts()
        print('prompts:', [p.name for p in ps.prompts])
        got = await c.get_prompt('deficiency_letter', {'claim_id': 'FNOL-4477', 'reason': 'missing_photo_reference'})
        print(got.messages[0].content.text)
asyncio.run(main())
"
```

```
resources: [('perils', 'claims://cover/perils')]
prompts: ['deficiency_letter']
Write a short deficiency letter for claim FNOL-4477.
The single reason this claim cannot be fast-tracked is: missing_photo_reference.

Rules:
- Name exactly one missing or failing item. Do not list alternatives.
- Say precisely what the policyholder must send or confirm.
- Do not quote a policy number the caller did not give you.
- Do not promise a decision, a timescale or a settlement figure.
- Four sentences at most, plain words, no apology.
```

**Line by line:**

- `resources: [('perils', 'claims://cover/perils')]` — the URI as a string. Note the SDK hands back
  a URI object, so `str(r.uri)` is needed; comparing it to a string without that gives a false
  negative that looks like a missing resource.
- `prompts: ['deficiency_letter']` — one prompt, by name.
- **The prompt comes back as a message with the arguments already substituted.** `FNOL-4477` and
  `missing_photo_reference` are in the text; the client did not template anything. The server did
  the filling in, which means the wording and the substitution are versioned together.
- **Nothing here has called a model.** A prompt is a string a server offers. Day 7 is the first time
  one of these is sent anywhere.

## When it breaks

Ask the resource for something it was never given a way to answer:

```bash
uv run python -c "
import asyncio
from mcp import Client
from claims_mcp.server import server
async def main():
    async with Client(server) as c:
        await c.read_resource('claims://cover/policies')
asyncio.run(main())
" 2>&1 | tail -3
```

```
mcp.shared.exceptions.MCPError: Unknown resource: claims://cover/policies
```

Verbatim. `claims://cover/perils` exists and `claims://cover/policies` does not, and the difference
is not a permission check — there is simply no function registered at that URI. Somebody assumed the
scheme was a namespace they could explore, the way a URL path often is, and found that a resource
URI is a **name and not a directory**: guessing a sibling gets you nothing. That is a property worth
relying on. The boundary's `instructions` promise there is no way to list the policies, and the
reason that promise holds is that nothing implements one.

## In production

**What a senior writes instead.** The same three shapes, with the resource served from wherever the
reference data actually lives — a table, a config service — and cached by the client rather than
re-read per notification. They would also treat the prompt as reviewable text with a version on it,
because it is the wording that goes out on the company's paper. What they would push back on is the
temptation to make everything a tool: a tool call is a decision a model has to make, and reference
data that arrives as a decision is a decision the model can get wrong.

**What degrades at scale.** The peril vocabulary is eight slugs today. On a real book it is
hundreds, per product, and re-reading it on every notification is a request a desk makes several
hundred times a day for an answer that changed last quarter. That is the argument for it being a
resource: resources are read once and cached, and the protocol has a `listChanged` capability for
telling clients when to look again — which this server advertises and does not yet use.

**The review comment.** *"`get_deficiency_wording` is a tool. It takes a claim id and returns a
string the model then follows — that is a prompt. Making it a tool means the model has to decide to
call it, and on the day it does not, the letter goes out in whatever voice the model felt like."*

**The interview question.** *"Your server can expose the same information as a tool or as a
resource. Give me the test you apply to decide, and an example where you would get it wrong by
following your own rule too literally."*
