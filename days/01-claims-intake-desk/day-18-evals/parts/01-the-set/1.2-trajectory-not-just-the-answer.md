## One-line answer

A right answer reached by the wrong route is a right answer nobody can rely on, so every claim is
also marked on **which boundary tools the desk called, in what order, and how many model calls it
spent** — read from day 17's spans, and attributed to a claim by the one span that closes around
each of them.

## The idea

The file audit has a column that catches more handlers than any other, and it is not about the
decision.

It is the column headed *policy checked?* — and the auditor does not tick it because the file says
the policy was checked. They tick it because there is a cover query in the file, dated before the
decision, with the policy department's answer stapled to it. A handler who fast-tracked a claim that
was, as it happens, perfectly eligible, but never sent the query, fails the file. The decision was
right. The next one will not be, and the audit's job is the next one.

That is the difference between marking an answer and marking a **trajectory** — what the system
actually did, in what order, before it answered. This desk has produced right answers by the wrong
route before, and two of them are still in its data: FNOL-4471 and FNOL-4480 are both fast-tracked
correctly by a desk that guesses the peril without reading a word, because the guessed peril
happens to be covered too. Part 2.2 shows the number. The point here is that an answer-only audit
cannot see it, and a trajectory audit can.

Two things about the route are worth a mark on this desk. **Which boundary tools were called** — a
fast-track with no `check_in_force` in its route is the failure the project brief names as the one
the eval must catch. And **how many model calls were spent** — day 7 ordered the rules so a
notification with no date of loss costs nothing, and nothing has ever verified that it does.

The awkward part is where the route is written down. The desk does not return it. Nothing returns
it. It is in the log — specifically in day 17's `span` lines, which say `boundary.call` with a
`tool` field for every call the desk made — and those lines do not say which claim they were for.
`boundary.call` is opened inside `decide`, which knows the claim, and inside `boundary.call` which
does not. So the trajectory has to be **reconstructed** from the order of the lines, using the one
fact day 10 settled: the queue works one claim at a time, and a `claim` span closes after everything
that claim did. Every line since the previous close belongs to the claim whose span closes next.

That is the same reasoning a person applies to a paper file: the query is stapled behind the
decision it preceded because nobody was working two files at once. It holds here for the same
reason, and it stops holding the day somebody switches the desk to day 10's parallel morning — which
is why the assumption is written into the function's docstring rather than left implicit.

## The mechanism

From `claims_desk/evals.py`, printed whole in part 1.1. Attribution first:

```python
def by_claim(lines: list[dict[str, Any]]) -> dict[str, list[dict[str, Any]]]:
    """Every record that belongs to each claim, attributed by the span that closed around it.

    Day 17 put a `claim` span round each notification and the queue works one claim at a time, so
    every line between one claim span's close and the next belongs to the next. That includes the
    `boundary.call` spans, which carry the tool's name and not the claim's — and it is the only way
    to know which claim a tool was called for. **This attribution is only right because the queue
    is sequential.** Day 10's parallel morning would interleave two claims' lines, and the
    trajectory would need the claim on every line; part 1.2 says what that costs.
    """
    buckets: dict[str, list[dict[str, Any]]] = {}
    pending: list[dict[str, Any]] = []
    for line in lines:
        pending.append(line)
        if line.get("event") == "span" and line.get("span") == "claim":
            buckets[str(line["claim"])] = pending
            pending = []
    return buckets
```

**Line by line:**

- `pending.append(line)` **before** the check — the closing span line itself belongs to the claim it
  closes. It carries `spent` and `held`, and both are marks.
- `line.get("event") == "span" and line.get("span") == "claim"` — **the closing line, by two fields.**
  Day 17's `log` puts `span` on every line written *inside* a span, so a `desk.decided` line also
  says `"span": "claim"`; the `event == "span"` half is what distinguishes the span's own closing
  record from the lines inside it.
- `buckets[str(line["claim"])] = pending` — **the whole run of lines, handed over, including lines
  that are not about this claim.** The boundary subprocess writes `boundary.fetch_policy` with a
  policy number and no claim; a framework warning about token usage has no claim either. They land
  in the bucket and nothing reads them. Filtering them out here would mean knowing every event the
  desk can write, which is the coupling this module exists not to have.
- `pending = []` — **and start again.** Lines after the last claim — `desk.queue_finished`, the
  `queue` span — belong to nobody, and are dropped when the function returns. Part 4.1 asserts that.

The expected route, derived from the answer:

```python
def expected_tools(expected: dict[str, Any], held: bool) -> list[str]:
    """The boundary calls a correct desk makes for a claim with this answer, in order.

    Derived from the answer rather than written out twelve times, because the route follows from the
    verdict by day 7's ordering: fetch the policy, ask about cover only when there is a policy and a
    date, draft a letter only for a deficiency, record only what a person has not put on hold.
    """
    route = ["fetch_policy"]
    if expected["reason"] not in BEFORE_IN_FORCE:
        route.append("check_in_force")
    if held:
        return route
    if expected["outcome"] == Outcome.DEFICIENCY:
        route.append("draft_letter")
    route.append("record_decision")
    return route


def expected_calls(expected: dict[str, Any], held: bool) -> int:
    """How many model calls a correct desk spends on a claim with this answer.

    One reading, unless the fields settle it. One draft, if a letter goes out — which every
    deficiency gets except a held one. So a fast-track costs one, a deficiency the classifier had to
    read costs two, and a deficiency the fields settled costs one: the letter, and nothing else.
    """
    reading = 0 if expected["reason"] in SETTLED_BY_FIELDS else 1
    draft = 1 if expected["outcome"] == Outcome.DEFICIENCY and not held else 0
    return reading + draft
```

**Line by line:**

- **Derived, not declared.** The framework's own evalset format, which part 3.2 shows, writes the
  expected tool calls into each case by hand. Twelve hand-written routes would be twelve places to
  be wrong in the same way as the desk, because the person writing them reasons the way the desk
  does. Deriving them from the answer means the route is stated once, as four rules, and a change to
  day 7's ordering is a change to four lines here rather than twelve entries there.
- `route = ["fetch_policy"]` — **always.** There is no claim the desk decides without asking the
  boundary who the policyholder is, including one with no date of loss: day 7's `decide` fetches
  first and reads the fields second.
- `if expected["reason"] not in BEFORE_IN_FORCE:` — **the cover question is asked when there is a
  policy and a date.** `unknown_policy` means there was no policy to ask about;
  `missing_date_of_loss` means no date to ask with. Every other claim — including
  `missing_contact`, which the rules settle *after* the date and before anything else — has both, and
  the desk asks. This is the mark that goes red in part 3.1.
- `if held: return route` — **a held claim's route stops at the decision.** Day 16's gate means no
  letter and no write; a route that expected either would fail the gate for working.
- `draft_letter` only for a deficiency, then `record_decision` — **in that order**, because the
  letter is passed into the write. A desk that recorded first and drafted second would produce a
  claim file with no letter in it, and the order of two tool names is what would catch it.
- `reading = 0 if ... else 1` and `draft = ...` — **two terms, added.** The first draft of this
  function had three branches and was wrong; see below. The sum is right because the two costs are
  independent: whether the sentence was read and whether a letter went out are separate questions,
  and a claim can be any combination.

And the two marks, from `mark`:

```python
    called = [
        str(line["tool"])
        for line in lines
        if line.get("event") == "span" and line.get("span") == "boundary.call"
    ]
    result.marks.append(Mark("tools", expected_tools(expected, held), called))
    result.marks.append(Mark("calls", expected_calls(expected, held), closing.get("spent")))
```

**Line by line:**

- `line.get("span") == "boundary.call"` — **the outer boundary span, not `boundary.tool`.** Both
  carry `tool`; `boundary.call` is the one that closes whether or not the connection succeeded, so a
  claim whose boundary launch failed still shows the attempt in its route.
- `Mark("tools", expected_tools(...), called)` — **a list compared to a list.** Order matters and
  extras matter: `["fetch_policy", "record_decision", "check_in_force"]` fails, and so does a route
  with a second `fetch_policy` in it. The framework's trajectory metric offers three looser
  comparisons; part 3.2 says why this desk uses the strict one.
- `closing.get("spent")` — **the bill, from the span that day 17 wrote it on.** `run_queue` puts
  `budget.spent` on the `claim` span at the moment it closes, so the audit reads the desk's own
  count rather than counting `hooks.model` lines — which would count what the model *said* and not
  what the desk *paid*, the distinction day 11 spent a day on.

## When it breaks

The first version of `expected_calls` was written from the wrong end. It reasoned about readings:
none for a claim the fields settle, one for a fast-track, two for a deficiency — and it forgot that a
deficiency the fields settled still gets a letter, and a letter is a model call:

```diff
-    reading = 0 if expected["reason"] in SETTLED_BY_FIELDS else 1
-    draft = 1 if expected["outcome"] == Outcome.DEFICIENCY and not held else 0
-    return reading + draft
+    if expected["reason"] in SETTLED_BY_FIELDS:
+        return 0
+    if held or expected["outcome"] == Outcome.FAST_TRACK:
+        return 1
+    return 2
```

Exactly the four claims in `SETTLED_BY_FIELDS`, each one call over what the sheet expected — and the
desk was right. Every one of those claims had a letter to send, and every letter cost the draft it
should have. The marking scheme was wrong, and it was wrong in the direction that is easy to write:
a rule about readings that forgot correspondence exists.

That is the failure mode of a trajectory audit, and it is worth sitting with. **The expected route is
code, and code that marks other code is exactly as capable of being wrong.** The report made it
cheap to find — the mark, the two values, and the pattern across four claims pointed at the rule
inside a minute — and the fix was to stop reasoning in branches and add two independent costs. Part
4.1 keeps a test whose docstring says the first draft of this rule said zero, so the next person to
rewrite it in branches meets it.

## In production

**What a senior writes instead.** The claim id on every line. `boundary.call` would take the claim
as a field, or — better — the correlation id would be per claim rather than per queue, so that
attribution is a `grep` rather than an inference about ordering. That removes the sequential
assumption entirely, which is what makes day 10's parallel morning usable: today it is not, because
the audit would attribute one claim's tool calls to whichever claim's span closed next. The cost is
the one day 17 weighed — threading a value through code that does not otherwise need it — and it is
paid the day parallelism arrives, not before.

**What degrades at scale.** A tool trajectory compared as an exact ordered list is right for a desk
with four tools and one route per verdict. A real intake desk with fraud screening, a sanctions
check, a repair-network lookup and a document request has a dozen tools and several legitimate
orders, and an exact match fails every valid variation — so the audit gets relaxed to "these calls,
any order", and the day the sanctions check moves *after* the payment, the relaxed audit is green.
Three hundred claims a day through a route with one check in the wrong place is three hundred
decisions a regulator asks about. The answer is not a looser comparison but a stated partial order:
which calls must precede which, checked as constraints rather than as a list.

**The review comment.** *"`by_claim` attributes lines by the closing span and says in its docstring
that this only works because the queue is sequential. That is a comment enforcing an invariant. Add
an assertion: if two `claim` spans open before either closes — which the `span` field on the lines
inside them would show — refuse to attribute at all and fail the run. A silent misattribution here
is a green eval on a wrong desk."*

**The interview question.** *"Your agent's evaluation compares only the final answer, and it is at
one hundred per cent. What is it not telling you, and what is the cheapest thing you could add that
would tell you?"*
