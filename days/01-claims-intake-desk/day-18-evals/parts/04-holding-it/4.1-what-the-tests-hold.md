## One-line answer

Thirty-three tests, and most of them never run the desk: they hand the marking scheme records shaped
like the ones the desk writes and assert what it says about them — because **the sheet is code, and
code that marks other code is exactly as capable of being wrong**, which this day proved twice before
lunch.

## The idea

Who audits the auditor?

It is not a rhetorical question at an insurer. The senior handler with the marking sheet is
themselves sampled: a second person takes a few of the audited files and marks them again, blind,
and the two sheets are compared. Not because the auditor is suspected — because the audit's number
goes on a chart that decisions are made from, and a number nobody has checked is a number that will
be trusted exactly until the day it is wrong, which is the worst possible day to find out.

This day's marking sheet was wrong twice. Part 1.2's `expected_calls` forgot that a field-settled
deficiency still sends a letter, and failed four correct claims. And the first version of this test
file read the claim files from the wrong store — the project's real `data/claims/` rather than the
one the fixture had pointed at a temporary directory — so the in-process audit marked whichever run
had last written there. Both were found by running the thing and reading the result; neither would
have been found by looking at the code, which read perfectly well. The sheet needs its own sheet.

So this file has a shape that most test files in this project do not. **Most of these tests do not
run the desk.** They construct a handful of log records with `a_run` — a `boundary.call` span per
tool, a `desk.decided` line, a closing `claim` span with a `spent` on it — and hand them to `mark`,
and assert on the marks that come back. That is fast, and it is also the only way to test the cases
the real queue does not contain: a claim the provider never answered, a claim the log never
mentions, a held claim with no letter. The audit has to be right about those before it is trusted
about the twelve it sees every run.

Then two tests run the whole desk in-process, with day 17's in-process boundary, and mark it for
real — once against the key, expecting green, and once against a key that has been deliberately
changed, expecting exactly the four marks that should object. That second one is the **inverted
case**: an eval whose declared expectation is its own failure, so it goes red when the audit stops
objecting. It tests the detector rather than the desk, and it is the test that catches a loosened
mark, which part 3.1 showed goes quiet rather than red.

And two tests run the framework's evaluator: one that it agrees with the audit about the classifier,
and one that holds part 3.2's finding as a number — the text judge scores a wrong injury flag exactly
as it scores the right answer — so that nobody fixes it by raising the threshold and finds out on a
claim.

```python
Most of these tests never run the desk. They hand `mark` and `judge` records shaped like the ones

code too, and code that marks other code is exactly as capable of being wrong. Two of them run the

    monkeypatch.setattr(tools.store, "claims", tmp_path / "claims")
    monkeypatch.setattr(sessions, "service", InMemorySessionService())

    @asynccontextmanager
    async def connected():
        async with Client(server) as client:

    token = trace.trace_id.set("")
    spans = trace.span_stack.set(())

def a_run(claim_id: str, tools_called: list[str], spent: int, **decided) -> list[dict]:
    """The records one claim leaves behind, in the order the desk writes them."""
    lines = [{"event": "span", "span": "boundary.call", "tool": tool} for tool in tools_called]
    if decided:
        lines.append({"event": "desk.decided", "claim": claim_id, **decided})
    lines.append({"event": "span", "span": "claim", "claim": claim_id, "spent": spent})
    return lines

# --- the whole desk, marked -----------------------------------------------------------------------


def the_desk_marked(capsys, expectations: dict) -> list[evals.CaseResult]:
    """Run the queue in this process, read what it logged, and mark it against `expectations`.

    The claim files are read from `tools.store`, the boundary's own store, because that is the one
    the fixture pointed at `tmp_path`. A fresh `Store()` here would read `data/claims/` — whatever
    the last `./run eval` left there — and mark this run against another run's files.
    """
    asyncio.run(desk.run_queue())
    logged = capsys.readouterr().err
    files = {claim_id: tools.store.claim(claim_id) for claim_id in expectations}
    return evals.evaluate(logged, files, expectations)


def test_the_desk_passes_its_own_audit(capsys) -> None:
    results = the_desk_marked(capsys, Store().expectations())
    assert [result.claim_id for result in results if not result.passed] == []
    assert len(results) == 12
    assert sum(len(result.marks) for result in results) == 84


def test_the_gate_goes_red_when_the_key_and_the_desk_disagree(capsys) -> None:
    """The inverted case: change the answer and the audit must object, or it is marking nothing.

    Four marks fail, and `calls` is not one of them: the key now says fast-track, which costs one
    call, and the desk spent one — on a letter. A count agrees by accident; the route does not.
    """
    key = Store().expectations()
    key["FNOL-4474"] = {**key["FNOL-4474"], "outcome": "fast-track", "reason": None}
    results = the_desk_marked(capsys, key)
    failed = {r.claim_id: [mark.name for mark in r.failed] for r in results if not r.passed}
    assert failed == {"FNOL-4474": ["outcome", "reason", "loss_type", "tools"]}

# --- the framework's evaluator, over the same twelve --------------------------------------------


def test_the_frameworks_evaluator_passes_the_classifier_on_the_same_twelve() -> None:
    asyncio.run(
        AgentEvaluator.evaluate(
            agent_module="claims_desk.evalset.agent",
            eval_dataset_file_path_or_dir="data/evalset/classifier.evalset.json",
            num_runs=1,
            print_detailed_results=False,
        )
    )


def an_invocation(answer: dict) -> Invocation:
    return Invocation(
        user_content=types.Content(role="user", parts=[types.Part(text="a description")]),
        final_response=types.Content(role="model", parts=[types.Part(text=json.dumps(answer))]),
    )


def test_the_frameworks_text_judge_cannot_see_an_inverted_injury_flag() -> None:
    """The scar. A fuzzy match over the answer's words scores a wrong injury flag 0.89 — above 0.8.

    The peril is several words; the flag is one. So a wrong peril fails and the one bit that sends
    a claim to an adjuster passes. This test holds the number so nobody fixes it by raising the
    threshold — at 0.9 the *correct* answer fails too, because the stand-in adds `scripted: true`.
    """
    judge = RougeEvaluator(EvalMetric(metric_name="response_match_score", threshold=0.8))
    said = an_invocation(
        {"scripted": True, "loss_type": "escape-of-water", "injury_reported": False}
    )
    wrong_flag = an_invocation({"loss_type": "escape-of-water", "injury_reported": True})
    wrong_peril = an_invocation({"loss_type": "fire", "injury_reported": False})
    right = an_invocation({"loss_type": "escape-of-water", "injury_reported": False})

    scored = {
        name: judge.evaluate_invocations([said], [expected])
        for name, expected in (
            ("right", right),
            ("wrong_flag", wrong_flag),
            ("wrong_peril", wrong_peril),
        )
    }
    assert scored["right"].overall_eval_status == EvalStatus.PASSED
    assert scored["wrong_flag"].overall_eval_status == EvalStatus.PASSED
    assert scored["wrong_peril"].overall_eval_status == EvalStatus.FAILED
    assert scored["right"].overall_score == scored["wrong_flag"].overall_score
```

**Line by line:**

- `_in_process` — **day 17's fixture with day 17's trace reset folded in**, `autouse` because every
  test in this file that touches the desk needs all of it, and the ones that do not are unaffected.
  It points the boundary's store at `tmp_path`, replaces the session service, and swaps
  `boundary.connected` for a client that holds the `server` object directly — the in-process
  boundary this project has used since day 3, which is what makes an end-to-end run of twelve
  claims take seconds here and a minute from the command line.
- `a_run(claim_id, tools_called, spent, **decided)` — **the desk's footprint, in miniature.** The
  order is the desk's: tool spans, then the decision, then the closing `claim` span with `spent`.
  Getting the order right matters because `by_claim` reads it; a helper that put the closing span
  first would be testing a queue that does not exist.
- `FAST_TRACK`, `NO_DATE`, `NO_PHOTO` — **three declared answers, reused.** The key's shape is four
  fields, and the tests build every other case from these with `{**NO_DATE, "reason": ...}` so that
  the shape is stated in one place.
- `test_lines_after_the_last_claim_belong_to_nobody` — **the `desk.queue_finished` line is
  dropped.** A test for the `pending = []` at the end of `by_claim`: lines after the last claim's
  span must not be attributed to a claim that does not exist, and must not crash.
- `test_the_route_follows_from_the_verdict` — **five routes, one per branch of `expected_tools`**,
  including the held one that stops at two calls. The fourth case is `unknown_policy`, which shares
  a route with `missing_date_of_loss` for a different reason: no policy to ask about rather than no
  date to ask with.
- `test_the_bill_follows_from_the_verdict` and its docstring — **the scar from part 1.2.** Four
  cases, and `(NO_DATE, False, 1)` is the one the first draft got wrong. The docstring says so
  because the next person to rewrite the function in branches should meet the sentence.
- `test_every_rubric_row_has_an_id_a_check_and_a_reason` — **a test about the department's
  reasoning.** It fails on a row with no `why`, which is a row somebody added because it seemed
  sensible. Same test `alerts.RULES` and `security.THREATS` have, for the same reason.
- `test_each_row_fails_the_letter_it_was_written_for` — **one row per bad letter, and exactly
  one.** `assert failed == [row]` is stricter than "the row failed": a letter with a figure in it
  must fail L2 and *only* L2, or the rows are not independent and the report cannot name the fault.
- `test_the_reference_is_the_one_figure_a_letter_may_carry` — **L2 with the wrong reference.** The
  good letter judged as `FNOL-0000` fails L2, because `FNOL-4477`'s digits are no longer stripped.
  That is the test that would catch somebody simplifying `letter.replace(claim, "")` away.
- `test_a_claim_the_desk_could_not_decide_says_what_it_was_waiting_for` — **`pending:
  provider_unavailable` as the found value**, not `None`. The report reads differently for a desk
  that was wrong and a provider that was down, and the queue never contains this case, so only a
  constructed one can hold it.
- `test_a_claim_the_desk_never_reached_fails_rather_than_being_skipped` — **an empty list of lines
  is a failed claim.** A queue that stopped at claim six leaves six claims with nothing in the log;
  `evaluate` hands `mark` an empty list for each, and this is the test that the empty list fails
  rather than being skipped.
- `test_a_held_claim_is_marked_on_the_decision_it_would_have_recorded` — **`held` on the closing
  span, no letter rows, and `passed`.** FNOL-4481 is the queue's one held claim, and this test
  constructs it rather than relying on the queue, so the rule is tested even on a queue where
  nothing is held.
- `the_desk_marked` and `tools.store.claim(claim_id)` — **the boundary's store, not a fresh one.**
  Read the docstring; then read the failure below, which is what the first version did.
- `test_the_desk_passes_its_own_audit` and `== 84` — **the whole desk, and the total number of
  marks.** Eighty-four is five on each of four fast-tracks, five on the held claim, eight on each of
  four field-settled deficiencies, nine on each of three read deficiencies. A mark added or removed
  anywhere changes this number, which is the point of asserting it.
- `test_the_gate_goes_red_when_the_key_and_the_desk_disagree` — **the inverted case.** The key is
  changed to say FNOL-4474 should have been fast-tracked; the desk, correctly, disagrees; the audit
  must fail exactly that claim on exactly four marks. The docstring names the one mark that does
  *not* fail and why — a count that agrees by accident is the kind of thing a reader assumes is a
  bug in the test.
- `test_report_names_the_claim_the_mark_and_both_values` — **the report's lines, asserted as
  strings.** `said.append` is the printer; the first line, the mark line and the last line are
  checked verbatim, because the report is what a person reads at eleven at night and its exact
  wording is the product.
- `test_a_desk_that_reads_nothing_scores_nine_or_six_depending_on_the_question` — **both baseline
  numbers, and the six claims.** The name says the finding. If somebody improves the guess and the
  numbers move, this test is the conversation about whether they should have.
- `test_the_three_claims_the_model_earns_are_the_three_the_rules_cannot_reach` — **the model's
  contribution, as a set of three claim ids.** The docstring names what each one is. This is the
  test that turns part 2.2's argument into something that goes red when the fixture changes.
- `test_the_frameworks_evaluator_passes_the_classifier_on_the_same_twelve` — **no `assert`.**
  `AgentEvaluator.evaluate` asserts internally and raises on any failed case; the test is green when
  it returns. `num_runs=1` because the stand-in does not vary and the default of two would double a
  real provider's bill for nothing.
- `test_the_frameworks_text_judge_cannot_see_an_inverted_injury_flag` — **the finding, held as
  four assertions.** Right passes, wrong flag passes, wrong peril fails, and the right and wrong-flag
  scores are *equal* — not merely both above the threshold. The last assertion is the one that
  rules out fixing this with a threshold, and its docstring says why 0.9 does not work either.

## When it breaks

The first version of `the_desk_marked` built a fresh `Store()` to read the claim files:

```diff
-    files = {claim_id: tools.store.claim(claim_id) for claim_id in expectations}
+    files = {claim_id: Store().claim(claim_id) for claim_id in expectations}
```

A fresh `Store()` reads `data/claims/` — the project's real claims directory, which the fixture never
touched. So the two end-to-end tests were marking this run's log against whatever files the last
`./run eval` had left on disk. While those files happened to be from a green run, both tests were
green. After part 2.1's experiment left a run with no letter on FNOL-4477 there, one went red on a
letter the in-process run had written perfectly well. And with `data/claims/` empty:

```
E       AssertionError: assert ['FNOL-4473',...OL-4479', ...] == []
E
E         Left contains 7 more items, first extra item: 'FNOL-4473'
```

Seven claims — every deficiency that sends a letter — failing all four letter rows, because the
files were being read from a directory nobody had written to. **The test was green by coincidence
and red by coincidence, and neither state said anything about the audit.** The smallest fix is the
one line: read from `tools.store`, the object the fixture redirected, so the test reads the files the
run it is marking actually wrote. The general rule is the one day 17's `fresh` fixture taught from
the other side: a test that reaches outside its fixture is a test whose result depends on what ran
before it.

## In production

**What a senior writes instead.** The audit's tests in the same pipeline stage as the audit, and a
rule that a change to `evals.py` requires a change to this file in the same commit — because the
sheet and its sheet drift apart otherwise, and part 3.1 showed which direction that drifts: quiet.
And a **golden report**: one full `./run eval` output, committed, diffed against every run's output
in CI, so that a mark that changes its wording or a claim that changes its mark count is visible as a
diff rather than as a number that moved.

**What degrades at scale.** Two of these tests run the whole desk in-process, which is seconds here
and grows with the queue: three hundred cases through the in-process boundary is minutes inside
`./run check`, the fast gate. The answer is to keep the two end-to-end tests on a **fixed sample** —
the twelve claims that exercise every route — and leave the full set to the slow gate, with the
sample's membership asserted so nobody trims it to make the check faster.

**The review comment.** *"`test_the_desk_passes_its_own_audit` asserts eighty-four marks. That
number is derived from the queue's shape and the marking rules; the test hard-codes it. Write the
derivation beside it — four fast-tracks times five, and so on — or the next person to add a mark
will change the number to whatever the run says and the assertion will have become a snapshot."*

**The interview question.** *"You have written an evaluation harness for an agent. How do you know
the harness is right? Give me one test that would catch the harness passing everything, and one that
would catch it failing the wrong thing."*
