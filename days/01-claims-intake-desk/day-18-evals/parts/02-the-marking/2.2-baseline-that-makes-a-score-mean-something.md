## One-line answer

Twelve out of twelve is a number; twelve out of twelve **beside nine out of twelve for a desk with
no model in it** is a measurement — and on this queue the model's whole contribution is three claims,
which is what the score has to be compared against before anybody calls it good.

## The idea

The audit total goes on a chart, and the chart has a second line on it.

A department that scores ninety-four per cent on its file audit has learned nothing until somebody
asks what a handler who did the minimum would score. If the minimum — check the dates, check the
policy, send the standard letter — scores ninety, then the training, the experience and the
judgement bought four points, and the meeting is about whether four points was worth what it cost.
If the minimum scores sixty, the department is in a different conversation. Same ninety-four. The
number did not change; what it means did.

That second line is a **baseline**: the score of the cheapest thing that could possibly be put in
the system's place. Not a random guesser, which no department would run, and not last year's number,
which measures drift rather than worth. The cheapest *plausible* alternative — the one somebody
would actually propose in the meeting where the model's cost comes up.

On this desk that alternative is easy to name, because the desk was built in this order. Day 2 wrote
eight rules that decide a claim from fields, and they decide most of it: a missing date, a missing
contact, an unknown policy, a policy off risk, a photograph, an estimate over the limit. What they
cannot decide is the peril and whether somebody was hurt, because both are in a sentence, and day 7
added a model to read the sentence. So the baseline is **day 2's rules with the sentence unread** —
the loss type guessed from the policy's own schedule, and nobody ever hurt. It costs nothing, it
needs no key, and it is precisely what a sceptical manager means by "do we actually need the model
for this".

The answer, measured, is that the baseline gets nine of twelve verdicts right. The model earns three
claims. And three of the nine the baseline gets right, it gets right for the wrong reason — the
guessed peril is wrong and the verdict comes out the same anyway — which is a second number, and a
second lesson about what a score can hide.

Neither number is on the chart if nobody computes it. So `./run eval` prints both, on the line
under the desk's own score, every time.

## The mechanism

From `claims_desk/evals.py`, printed whole in part 1.1:

```python
def baseline() -> dict[str, Any]:
    """The same twelve claims, decided by a desk with no reader in it.

    Day 2's rules, with the loss type guessed as the first peril on the policy's own schedule and no
    injury ever noticed. It is the cheapest desk that can be built from this project's parts, and it
    is what the classifier's score has to be measured against: a claim this desk gets right is a
    claim the model contributed nothing to.

    Two numbers come back, because they say different things. `verdict` counts claims where the
    outcome and the reason were right, whatever peril was guessed — a claim can be right for the
    wrong reason. `verdict_and_reading` also requires the guessed peril to be the real one wherever
    the rules read it at all, which is the standard the desk itself is marked to.
    """
    store = Store()
    policies = {policy.number: policy for policy in store.policies()}
    verdicts = 0
    readings = 0
    wrong: list[dict[str, Any]] = []
    for note in store.notifications():
        expected = store.expectations()[note.id]
        policy = policies.get(note.policy_number)
        cover = (
            Cover(
                in_force=policy.in_force_on(note.date_of_loss) if note.date_of_loss else False,
                perils=policy.perils,
                fast_track_limit=policy.fast_track_limit,
            )
            if policy
            else None
        )
        guess = sorted(policy.perils)[0] if policy else ""
        outcome, reason = assess(note, cover, guess, injury_reported=False)
        got = (outcome.value, reason.value if reason else None)
        want = (expected["outcome"], expected["reason"])
        read_right = expected["reason"] in SETTLED_BY_FIELDS or guess == expected["loss_type"]
        verdicts += got == want
        readings += got == want and read_right
        if got != want or not read_right:
            wrong.append({"claim": note.id, "guessed": guess, "got": got, "wanted": want})
    return {
        "of": len(store.expectations()),
        "verdict": verdicts,
        "verdict_and_reading": readings,
        "wrong": wrong,
    }
```

**Line by line:**

- `store.policies()` **directly, not through the boundary.** The baseline is not the desk and does
  not pretend to be: it is the audit asking "what would the rules alone say", and the audit may read
  the store — `Store.expectations`' docstring has said since day 2 that tests and the evalset can.
  Going through the boundary would cost forty subprocess launches to answer a question about
  arithmetic.
- `Cover(in_force=policy.in_force_on(note.date_of_loss) if note.date_of_loss else False, ...)` —
  **the same cover the desk builds, by hand.** `Cover.from_policy` needs a date and FNOL-4473 has
  none; the desk's `decide` handles that by leaving `in_force` false, and this does the same so that
  the baseline's rules see what the desk's rules see. A baseline that fed the rules different facts
  would be measuring the facts.
- `guess = sorted(policy.perils)[0]` — **the cheapest guess that is not random.** Alphabetical
  first peril: `accidental-damage` on most of these policies, `escape-of-water` on the buildings
  policies, `fire` on one. It is deliberately dumb and deliberately deterministic, so the number is
  the same every run. A smarter guess — the most common peril in the book — is a `TODO(me)` in the
  hub, and the point of it is to see how much smarter a baseline can get before it needs a model.
- `assess(note, cover, guess, injury_reported=False)` — **day 2's rules, unchanged, with the two
  facts they cannot compute filled in by the guess.** This is the same function the desk calls with
  the classifier's answer. The whole baseline is that one argument.
- `read_right = expected["reason"] in SETTLED_BY_FIELDS or guess == expected["loss_type"]` — **a
  guessed peril only counts where the rules read it.** For a claim with no date of loss the peril
  never mattered, so a wrong guess there is not a wrong reading; for a fast-track it mattered
  completely, because `loss_type not in cover.perils` is the rule that stood between the claim and
  a deficiency letter.
- `verdicts += got == want` and `readings += got == want and read_right` — **two counts, the second
  stricter.** `verdict` is what a manager asks for. `verdict_and_reading` is the standard part 1.1's
  marks hold the desk to, so the two scores on the report line are comparable.
- `wrong.append({...})` — **every miss, with the guess that caused it.** The number without the list
  is a chart; the list is what tells you the model's three claims are the theft, the injury and the
  excluded peril, which is a sentence about what the model is *for*.

**Line by line:**

- **Three wrong verdicts, and they are the three kinds of claim day 2 said it could not decide.**
  FNOL-4475 is a theft — no photograph needed — that the guess turned into an accidental-damage
  claim with a photograph missing. FNOL-4478 is the injury; a baseline that never hears "hurt"
  fast-tracks it. FNOL-4479 is the radiator on a policy with no escape-of-water cover; guessing
  `fire` makes it covered. Those three are what the classifier is for, and nothing else on the queue
  is.
- **Three right verdicts with the wrong peril.** FNOL-4471, 4472 and 4480 come out fast-tracked
  because the guessed peril happened to be on the schedule too. A desk that scored these as
  correct would report nine of twelve for a system that read nothing — which is the number a manager
  would have been shown if `verdict` were the only count.
- **The model's contribution is `12 - 9 = 3` claims, or a quarter of the queue.** That is the
  measurement. Whether a quarter of the queue is worth a model call per claim, a provider dependency
  and a security boundary is the meeting, and this is the number the meeting needs.

## When it breaks

Baselines break by being too good, and the way that happens is somebody improves the guess.
Replace the alphabetical first peril with the peril that actually appears most across the book:

```diff
-        guess = sorted(policy.perils)[0] if policy else ""
+        guess = "fire" if policy else ""
```

`fire` is on every one of the eight policies. The detail again:

```
9 5 of 12
FNOL-4471  guessed fire               got ('fast-track', None)                         wanted ('fast-track', None)
FNOL-4472  guessed fire               got ('fast-track', None)                         wanted ('fast-track', None)
FNOL-4475  guessed fire               got ('deficiency', 'missing_photo_reference')    wanted ('fast-track', None)
FNOL-4478  guessed fire               got ('fast-track', None)                         wanted ('deficiency', 'injury_reported')
FNOL-4479  guessed fire               got ('fast-track', None)                         wanted ('deficiency', 'peril_not_covered')
FNOL-4480  guessed fire               got ('fast-track', None)                         wanted ('fast-track', None)
FNOL-4481  guessed fire               got ('deficiency', 'above_fast_track_limit')     wanted ('deficiency', 'above_fast_track_limit')
```

Seven rows where there were six, and the last one is new. The verdict count did not move: nine
before, nine after. The strict count **fell** from six to five,
because FNOL-4481 — a mains leak on a policy that happens to cover fire as well — is now right for the
wrong reason too. The "better" guess got the same verdicts on every claim and read one more of them
wrongly, and only the stricter number noticed. FNOL-4479's radiator is still fast-tracked; FNOL-4475's
shed still wants a photograph a theft does not need; FNOL-4478's shoulder is still unheard. The
three claims the model earns did not change, because no guess reaches them.

That is the failure to watch for, in both directions: **a baseline tuned until it looks good is a
ceiling somebody built by hand**, and a count that only reads verdicts cannot tell a better baseline
from a luckier one. The smallest fix is a rule about the baseline rather than about the code — it is
the *cheapest* alternative, chosen once, written down with the reason, and not revisited every time
the model's score is uncomfortable. The hub's `TODO(me)` asks for a smarter guess precisely so that
the difference between "a baseline" and "a competitor" is felt rather than described.

## In production

**What a senior writes instead.** Two baselines rather than one: the cheapest alternative, as here,
and **the previous release of the same system**, run on the same evalset in the same job. The first
says what the model is worth; the second says whether this change made it better or worse, which is
the question a pull request actually asks. Both numbers are printed beside the score, and a change
that lowers the second one fails the gate even if the absolute score is still high — because "still
above ninety" is how a system loses two points a month for a year.

**What degrades at scale.** A twelve-claim evalset makes the model's contribution three claims, which
is a quarter — a number nobody could act on if it were two, or four. At three thousand notifications
a month, the same quarter is seven hundred and fifty claims that the rules alone would have decided
wrongly: an injury sent down the fast-track, a theft told to photograph what was stolen, an excluded
peril paid. That is the number the meeting is about, and it comes from the same three rows scaled
up. The evalset has to be large enough that the difference between the desk and the baseline is a
count, not an anecdote, and twelve is not.

**The review comment.** *"`baseline()` reads `store.expectations()` inside the loop, once per claim.
It is twelve file reads today. When the evalset is three hundred cases it is three hundred reads of
the same file, and the audit will be slower than the desk. Read it once above the loop."* (It is
right. It is also the review comment on a function that runs once per day, and the fix is one line;
do it, and notice that the reviewer read the loop rather than the number.)

**The interview question.** *"Your agent scores ninety-two per cent on its evaluation set. I say
the rules engine we already have scores eighty-nine. What do you say, and what do you go and
measure?"*
