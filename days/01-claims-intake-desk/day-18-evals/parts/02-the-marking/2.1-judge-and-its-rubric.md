## One-line answer

A letter has no single right answer to compare against, so it is marked by a **judge** applying a
**rubric** — four rows, each one thing a reader can check and each carrying the reason the
department cares — and on this desk the judge is code, because every row the house style actually
enforces is a row a program can read.

## The idea

Two columns on the file audit sheet are not ticks. They are the ones headed *letter*.

The auditor cannot compare a letter against a correct letter, because there is no such thing. Two
handlers writing to the same policyholder about the same missing photograph produce two different
letters, both fine. So the sheet does not say *matches the model letter*. It says four things a
reader can check without an opinion: does it quote the claim reference, does it name a figure, is it
short, does it tell the person what to do. Each one has a reason written beside it, because the day
an auditor cannot say why a row exists is the day they stop applying it — and the row about figures
exists because a letter once promised a settlement amount the file could not support, and the
insurer paid it.

That sheet is a **rubric**: a marking scheme for output that has no reference answer, written as
separate rows so a letter can fail one and pass three, and so the failure names which. The person
applying it is the **judge**. Everything about evaluating prose comes down to two questions: what is
on the sheet, and who is holding it.

On this desk the judge is a function, and it is worth being precise about why that is not a
shortcut. The house style has four rules — day 9's letter writer was given them, day 10's
`HouseStyle` node enforces one of them inside the loop, and the boundary's `deficiency_letter`
prompt repeats them. All four are **readable by a program**: a reference is a substring, a figure is
a digit, sentences are full stops, an ask is one of three phrases the department allows. A rule that
a program can read is a rule a program should judge, because the program's verdict is the same on
Monday and Friday and a person's is not.

The rule that a program cannot read is the one this desk does not have yet: *is the letter kind*. Or
*does it sound like us*. Those rows need a reader, and in a system like this the reader is another
model — a **model-as-judge**, given the letter and the rubric and asked to mark. Part 3.2 shows the
framework's version and what it needs to run, and this project cannot run it today: its stand-in
model reads nothing, and a judge that reads nothing is not a judge. What can be said, and is said in
the production note, is what a model judge is for and what it must never be trusted with.

The other thing the sheet gives you is the reason column. `alerts.RULES` and `security.THREATS` both
carry a `why`, and for the same argument: a rule whose justification cannot be written in one
sentence is a rule that will fail a good letter. Row L2's `why` — *a figure in a letter is a figure
the insurer can be held to* — is why the reference is stripped before the check and nothing else is.
Without it, somebody adds an exception for dates, then for policy numbers, and the row is gone.

## The mechanism

From `claims_desk/evals.py`, printed whole in part 1.1. The rubric:

```python
#: What the house style refuses in a letter: a figure. The claim reference is the one exception, and
#: `judge` removes it before looking, exactly as `workflow.HouseStyle` does.
A_FIGURE = re.compile(r"\d")

#: The three things a deficiency letter is allowed to ask for. A letter that asks for none of them
#: has told the policyholder something is wrong and not what to do about it, which is the failure
#: the whole letter exists to prevent.
AN_ASK = ("please send", "please confirm", "nothing further for you to send")

#: The marking scheme for a letter. Each row is one thing a reader of the letter can check, with the
#: check itself and the reason the department cares — the `why` is there for the same reason it is
#: in `alerts.RULES`: a rubric row nobody can justify in a sentence is a row that fails good
#: letters.
RUBRIC: tuple[dict[str, Any], ...] = (
    {
        "id": "L1",
        "asks": "names the claim reference",
        "why": "a letter with no reference is filed against nothing",
        "check": lambda letter, claim: claim in letter,
    },
    {
        "id": "L2",
        "asks": "carries no figure except the reference",
        "why": "a figure in a letter is a figure the insurer can be held to",
        "check": lambda letter, claim: A_FIGURE.search(letter.replace(claim, "")) is None,
    },
    {
        "id": "L3",
        "asks": "is four sentences at most",
        "why": "the house maximum; a longer letter is read less, not more",
        "check": lambda letter, claim: sentences(letter) <= 4,
    },
    {
        "id": "L4",
        "asks": "tells the policyholder what to send, or that there is nothing to send",
        "why": "a letter that names a problem and no action is a letter that generates a call",
        "check": lambda letter, claim: any(ask in letter.lower() for ask in AN_ASK),
    },
)


def sentences(text: str) -> int:
    """How many sentences a letter has, counted the way a reader counts them: by full stops."""
    return len([piece for piece in text.split(".") if piece.strip()])
```

**Line by line:**

- `RUBRIC` **is data with a function in each row**, not four functions. The shape is the point: a
  row has an id the report prints, a sentence saying what it asks, a sentence saying why, and the
  check. A test in part 4.1 iterates the rows and asserts every one has a non-empty `why` — which is
  a test about the department's reasoning, and it fails the day somebody adds a row they cannot
  justify.
- `"check": lambda letter, claim: ...` — **every check takes the letter and the claim reference**,
  even the ones that ignore the reference, so a row can be added without changing `judge`. A lambda
  rather than a `def` per row because each check is one expression and the table is meant to be
  read top to bottom as a sheet.
- `A_FIGURE.search(letter.replace(claim, "")) is None` — **the reference is stripped before the
  digits are counted.** Day 10's `HouseStyle` does exactly this through `body_of`, and the rubric
  repeats the rule rather than importing it, because an audit that imports the desk's own checker is
  an audit that agrees with it by construction. Two copies of a four-word rule is the price of an
  independent verdict.
- `sentences(letter) <= 4` and `text.split(".")` — **counted the way a reader counts, and honestly
  crude.** "Mr." and "approx." would each add a sentence. No letter this desk writes contains
  either, so the crude count is right today, and the docstring says what it does rather than what
  it would need to do for letters this desk does not write.
- `any(ask in letter.lower() for ask in AN_ASK)` — **an ask is one of three phrases.** This is the
  row most likely to be wrong for a real model's prose, because a model can ask in a thousand ways.
  For this desk it is right: the boundary's `deficiency_letter` prompt says *say precisely what the
  policyholder must send or confirm*, and the eight scripted letters use exactly these three forms.
  The day a real model writes "we would be grateful for a photograph", L4 fails a good letter — and
  that is the row a model judge replaces first.

The judge, and where it is called:

```python
def judge(letter: str | None, claim_id: str) -> list[Mark]:
    """Mark one letter against every row of the rubric. No letter fails every row at once."""
    return [
        Mark(
            f"letter.{row['id']}",
            expected=True,
            got=bool(letter) and bool(row["check"](letter, claim_id)),
        )
        for row in RUBRIC
    ]
```

**Line by line:**

- `for row in RUBRIC` — **the judge is a loop over the sheet**, and nothing else. Adding a row is
  adding a dictionary; the judge does not change, and neither does the report, which prints
  whatever id the row carries.
- `expected=True` — **every row expects a tick.** A rubric row phrased as a prohibition — *carries
  no figure* — still passes as `True`, because the check returns whether the letter satisfies the
  row, not whether it contains the fault.

Where the judge is called, in `mark`:

```python
    if expected["outcome"] == Outcome.DEFICIENCY and not held:
        letter = (claim_file or {}).get("letter")
        result.marks.extend(judge(letter, claim_id))
```

**Line by line:**

- `f"letter.{row['id']}"` — **the mark is named after the row**, so the report says `letter.L2:
  expected True, got False` and a reader with the table open knows it was a figure. A mark named
  `letter` that failed would say a letter was wrong and not how.
- `bool(letter) and bool(row["check"](...))` — **no letter fails every row at once**, rather than
  raising inside a lambda that tried to search `None`. A deficiency with no letter is four crosses,
  which is right: the policyholder received nothing, and every row on the sheet is about what they
  received.
- `if expected["outcome"] == Outcome.DEFICIENCY and not held:` — **judged where a letter should
  exist.** A fast-track sends no letter; a held claim sends none until a person signs. Judging the
  absence of a letter that was never owed would fail every fast-track in the queue.
- `(claim_file or {}).get("letter")` — **from the claim file, not the log.** Day 11's `hooks.model`
  records how many characters a model said and never what. The only place the letter's text exists
  after the run is the file the boundary wrote, which is where a policyholder's copy came from too.

**Line by line:**

- **Eight letters, thirty-two ticks.** Expected — they were written by hand to the house style on
  day 9 — and worth seeing, because a rubric that has never been run over the good letters is a
  rubric whose rows might fail them for a reason nobody thought of. `sentences` was the row to
  worry about; it counts three on every one.
- `text.format(claim='FNOL-0000')` — **a reference with digits in it**, on purpose. L2 strips the
  reference before counting; a test claim id with no digits would let a broken L2 pass.

## When it breaks

Give one of the scripted letters a figure — the kind a helpful writer adds:

```diff
     "missing_photo_reference": (
         "We have opened claim {claim} and need to see the damage. "
-        "Please send a photograph of the damage. "
+        "Please send a photograph of the damage within 14 days. "
         "We will continue as soon as we have it."
     ),
```

```
RED  FNOL-4477
       calls: expected 2, got 4
       letter.L1: expected True, got False
       letter.L2: expected True, got False
       letter.L3: expected True, got False
       letter.L4: expected True, got False
```

All four rows, not one — and a fifth mark that has nothing to do with letters. L2 is the row the
figure breaks, but the report does not say L2 failed and the other three passed. It says there was
**no letter**, and it says the claim cost four model calls instead of two. Read together, those two
facts are the whole story: day 10's `HouseStyle` refused the draft, the loop wrote it again, refused
it again, and ran to its bound of three — one reading and three drafts is four — then `write_letter`
logged `desk.letter_failed` and the decision was recorded with `letter: null`. The desk's own checker
caught the figure before the audit ever saw it, and what the audit saw was the consequence: a
policyholder who received nothing, and a bill for a loop that could never succeed.

Which is a fair mark. But somebody reading `letter.L1` fails on a claim whose letter is fine is
going to look in the wrong place, and the smallest fix is in the report rather than the rubric: the
line `desk.letter_failed` is in the claim's own bucket, and `mark` could say so beside the four
crosses. Part 4.1's `TODO(me)` is that line. The general lesson is that **a judge and an inner
checker that enforce the same rule will disagree about where the failure is** — the checker sees a
figure, the judge sees an absence — and the report has to carry enough of the route for a reader to
join them up.

## In production

**What a senior writes instead.** The same table, with a fifth row the program cannot read — *the
letter is courteous and does not blame the policyholder* — judged by a model given the letter, the
rubric row and a one-line instruction to answer `yes` or `no` with a quoted phrase as evidence. Three
disciplines around it: the judge is a different model from the writer, or at least a different
prompt, so it does not grade its own style; every judge verdict on a sample is checked by a person
each quarter, and the agreement rate is a number the team tracks; and **the judge never sees the
answer key**, only the letter — a judge told what the reason was will find it in any letter.

**What degrades at scale.** A model judge costs a model call per letter per row it reads. Eight
letters a day is nothing. An intake desk sending eleven hundred deficiency letters a month, judged on
three prose rows, is thirty-three hundred judge calls a month before anybody has evaluated a change
— and the temptation is to judge a sample of fifty. Fifty is fine for a trend and useless for a
gate: the letter that promised a figure is one in eleven hundred, and a fifty-letter sample sees it
one time in twenty-two. Code rows run on every letter for free; model rows run on samples. Put the
rule that would cost money to get wrong in the code row.

**The review comment.** *"L4 accepts three phrases. That is a rubric written from the eight letters
we have, and it will fail the first letter a real model writes in its own words. Either state that
L4 is a house-style rule — *these three phrases and no others* — and add it to the writer's
instruction so it is enforced rather than merely observed, or move it to the model-judged rows and
accept the cost."*

**The interview question.** *"You want to evaluate the letters an agent writes. There is no correct
letter to compare against. Walk me through what you would mark, who or what would mark it, and how
you would know the marker is right."*
