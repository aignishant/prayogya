## One-line answer

ADK ships an evaluator — an `.evalset.json` of conversations, a `test_config.json` of metric
thresholds, `adk eval` and `AgentEvaluator.evaluate` — and it evaluates **one agent, one turn at a
time**, which is why it is given the classifier and not the desk, and why its text-similarity judge
scores a wrong injury flag exactly as it scores the right answer.

## The idea

Every insurer eventually buys an audit tool, and the first thing the department learns is what it
was built to audit.

The tool arrives with its own marking sheet, its own file format, and a score it computes for you.
It is good at the thing it was designed for — a handler's individual decisions, one at a time, each
with a question and an expected answer — and it has no column for the thing the department actually
worries about, which is whether the file as a whole was handled right: the query sent, the letter
matched to the reason, the hold applied above the threshold. So the department does what departments
do. It uses the tool for the part it fits, keeps its own sheet for the rest, and runs both.

This desk has built its own sheet over three parts, hand-rolled, before looking at the tool. That
order was the point: **build first, compare after**, so that the comparison is between two things
you understand. Now the tool.

The framework's evaluation is organised around an **eval case**: one conversation with an agent,
where each turn has what the user said, what the agent should have answered, and which tools it
should have called on the way. A file of those is an **evalset**. A separate configuration names the
**metrics** — each a named judgement with a threshold — and the evaluator runs every case through a
root agent, scores it against every metric, and passes or fails it. Two of the metrics run locally:
`tool_trajectory_avg_score`, which compares tool calls, and `response_match_score`, which compares
the answer's text to the expected text by word overlap. The rest — rubric-based response quality,
tool-use quality, hallucination, safety — send the conversation to a model and ask it to judge.

Two things follow, and both matter here. The unit is an **agent**, not a system: the evaluator wants
a module with a `root_agent` in it, and this desk has none. Its agents live inside workflows inside
Python, and the thing worth auditing — a claim through the whole desk — is not a conversation with
anybody. So the framework gets the one agent that *is* a conversation: the classifier, twelve
descriptions in, twelve readings out. And the local judge for a text answer is **word overlap**,
which is a sensible measure of whether two paragraphs say the same thing and a poor one for whether
two JSON objects do — a fact this part demonstrates with a number rather than asserts.

The rest of the comparison is what the framework is good at that this desk's sheet is not, and the
production note is honest about it: a model-judged rubric, a user simulator, a results history. None
of them is free, and the price is the first thing the transcript below shows.

And the metrics, at `data/evalset/test_config.json`:

```json
{
  "criteria": {
    "tool_trajectory_avg_score": 1.0,
    "response_match_score": 0.8
```

**Line by line:**

- `"eval_set_id"`, `"eval_cases"`, `"eval_id"`, `"conversation"` — **the names are the framework's
  own `EvalSet` and `EvalCase` models**, read from the installed package rather than from memory. A
  case must have exactly one of `conversation` or `conversation_scenario`; this desk uses the first,
  because the second is for a model-simulated user and there is no user here.
- `"user_content"` **is the bare description**, not the quarantined one. The desk sends the
  classifier `security.quarantine(description)`; this file sends what the caller said. For the
  stand-in it makes no difference — it matches phrases — and for a real model it might, which is the
  hub's `TODO(me)`.
- `"final_response"` **is the answer key, as text.** `{"loss_type": ..., "injury_reported": ...}`
  and nothing else — not `scripted: true`, because the key describes what a *correct* reading
  contains, and the stand-in's flag is not part of a reading. That difference is what the judge
  below is about.
- `"intermediate_data": {"tool_uses": []}` — **the classifier calls no tools**, and day 16's
  allowlist says so; an expected trajectory of nothing is what makes the trajectory metric check
  that it stays nothing.
- `"tool_trajectory_avg_score": 1.0` — **exact match, every case.** The framework's trajectory
  evaluator offers exact, in-order and any-order comparisons; the default and the one used here is
  exact, for the reason part 3.1 gave.
- `"response_match_score": 0.8` — **the framework's own default threshold**, taken as it comes so
  that what follows is a measurement of the default and not of a number this desk chose.

And the judge, measured. The word-overlap metric on the classifier's actual answer against three
expected answers:

```bash
uv run python -c "
import json
from google.adk.evaluation.eval_case import Invocation
from google.adk.evaluation.eval_metrics import EvalMetric
from google.adk.evaluation.final_response_match_v1 import RougeEvaluator
from google.genai import types

def said(answer):
    return Invocation(
        user_content=types.Content(role='user', parts=[types.Part(text='a description')]),
        final_response=types.Content(role='model', parts=[types.Part(text=json.dumps(answer))]),
    )

judge = RougeEvaluator(EvalMetric(metric_name='response_match_score', threshold=0.8))
actual = said({'scripted': True, 'loss_type': 'escape-of-water', 'injury_reported': False})
for name, expected in [
    ('right', {'loss_type': 'escape-of-water', 'injury_reported': False}),
    ('wrong flag', {'loss_type': 'escape-of-water', 'injury_reported': True}),
    ('wrong peril', {'loss_type': 'fire', 'injury_reported': False}),
]:
    result = judge.evaluate_invocations([actual], [said(expected)])
    print(f'{name:<12} {result.overall_score:.3f}  {result.overall_eval_status.name}')
"
```

```
right        0.889  PASSED
wrong flag   0.889  PASSED
wrong peril  0.625  FAILED
```

**Line by line:**

- `RougeEvaluator` — **the class behind `response_match_score`**, named for the text-summarisation
  measure it computes: the overlap of words between the answer and the reference, as a fraction.
  Read from the installed `final_response_match_v1.py`; the metric's own docstring calls values near
  one desirable and says nothing about JSON.
- `right        0.889` — **not 1.0, for a correct answer.** The stand-in adds `scripted: true`, two
  words the reference does not have, and the overlap drops to eight ninths. Raise the threshold to
  0.9 to be stricter and the *correct* answer fails.
- `wrong flag   0.889  PASSED` — **the same score as the right answer.** `false` and `true` are one
  word each; swapping one for the other changes the overlap by exactly what `scripted: true` already
  cost. The one bit that sends a claim to an adjuster instead of the fast-track is invisible to this
  judge at this threshold, and there is no threshold that separates it from the right answer.
- `wrong peril  0.625  FAILED` — **a wrong peril is caught**, because `escape-of-water` is three
  words after tokenising and `fire` is one. The judge can see the long field and not the short one,
  which is a property of word counts and not of claims.
- **So the framework's twelve passes prove less than part 1.1's twelve.** Part 1.1 compares
  `loss_type` to `loss_type` and `injury_reported` to `injury_reported`, as values. This compares
  paragraphs. For an agent that writes paragraphs that is the right tool; for one that returns a
  structured reading, the metric that means something is field equality — which the framework
  offers only as a model-judged metric, `final_response_match_v2`, and which this desk does in a
  `Mark`.

## When it breaks

Ask the framework to evaluate the thing that actually matters — the desk — by pointing it at the
module that runs the queue:

```bash
PYTHONPATH=. uv run adk eval claims_desk data/evalset/classifier.evalset.json --config_file_path data/evalset/test_config.json
```

```
Traceback (most recent call last):
  ...
ValueError: Agent module should have either `root_agent` or `get_agent_async`.
```

That is the honest boundary of the tool, stated by the tool. `claims_desk` is a package with a
`__main__` and no root agent, because a root agent is a conversation and the desk is a queue. There
is no way to hand the evaluator "twelve notifications through `run_queue`, then read the claim
files"; its unit is an invocation of an agent, and its judgement is of that agent's reply. Somebody
who shipped this on a Friday would have spent the evening building a wrapper agent whose one tool
is *run the desk* — and would have evaluated the wrapper's ability to call one tool, which is not
the question.

The smallest fix is the one this day already made: the framework evaluates the classifier, which is
an agent; the desk's own audit evaluates the desk, which is not. Two instruments, each pointed at
the thing it can see.

## In production

**What a senior writes instead.** The framework's evaluator for every agent that is a conversation,
with the model-judged rubric metrics switched on — `rubric_based_final_response_quality_v1` with
rows like part 2.1's fifth, `hallucinations_v1` against the tool results, `safety_v1` — because
those are the judges a hand-rolled sheet cannot hold, and the framework has already done the work of
prompting them. Beside it, a system-level audit like part 1.1's, in CI, for the thing no agent-level
evaluator can see. And `num_runs` left at its default of two for a real model, with the variance
between the two runs reported as its own number: a case that passes once and fails once is a case
the key is not sure about.

**What degrades at scale.** The extra. Fifty-two packages, among them a cloud client, a numerical
stack and a tokeniser library, in a container whose job is to decide claims. Day 19's image is built
from `uv.lock`, and every one of those packages is in it unless somebody splits the dependency
groups — the desk in one, the evaluation in another, installed only where evaluation runs. At one
insurer's scale that is the difference between a container that starts in a few seconds and one that
pulls a few hundred megabytes onto every node that decides a claim, and the pull happens on the
morning the queue is longest.

**The review comment.** *"`response_match_score` at 0.8 passed an inverted injury flag in a probe.
That metric is on the classifier's evalset. Either replace it with a custom metric that compares the
two fields as values — the framework has a `custom_metric_evaluator` for exactly this — or drop it
and let `tool_trajectory_avg_score` and the desk's own audit carry the classifier. A metric that
cannot fail the answer we care about is not a metric, it is a green light."*

**The interview question.** *"A framework gives you an evaluator with a text-similarity metric and
a threshold. Your agent returns JSON. Tell me what that metric measures on your output, and show me
a wrong answer it would pass."*
