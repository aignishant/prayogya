## One-line answer

`python` is not a program, it is a word your machine resolves to whichever program it finds first,
and this project replaces that lookup with a one-line file that says the version out loud.

## The idea

Two people run the same claims desk on the same morning and get different answers about the same
policy. The notification is a water-damage claim, the policy number is real, and one of them sees
the claim fast-tracked while the other sees it fall out to an adjuster. Neither of them has changed
any code. They are not even running different code — they cloned the same folder from the same
place an hour apart.

They are running different interpreters, and nothing on either screen said so.

This is the most ordinary failure in this entire curriculum and it is worth being precise about
why it happens. When you type `python`, your machine does not look for "Python". It walks a list of
directories — the **search order** — and the first directory containing a file called `python` (or
`python.exe`) wins. Nothing announces that there was a choice. On a Windows machine that list
routinely holds three or four candidates: one installed from the official installer, one that came
with an application, one that is a stub which opens a store page, and one that a tool downloaded
for its own use. They are different files, at different paths, of different versions.

An **interpreter** is one of those files: one executable, at a real path, of one exact version. A
**pin** is a written-down exact version, recorded in a file so that a machine and not a memory
decides which one runs. And a **pin file** is where that written-down version lives — here,
`.python-version`, a file whose entire content is a version number and a newline.

The reason this matters for a claims desk rather than for a hobby project: this desk will decide
whether a claim can be fast-tracked, and it will do that partly with code you write and partly with
a model you call. Every part of that has to be reproducible, and reproducibility starts one level
below your code, at the question of which program is reading it. The pair in that scene will spend
their morning reading claim logic that is identical on both machines. The difference is in a
directory listing neither of them has looked at.

## The mechanism

First, look at what this machine actually has. `uv` knows, and it will tell you without changing
anything:

```bash
uv python list
```

```
cpython-3.15.0rc1-windows-x86_64-none                 <download available>
cpython-3.15.0rc1+freethreaded-windows-x86_64-none    <download available>
cpython-3.14.7-windows-x86_64-none                    <download available>
cpython-3.14.7+freethreaded-windows-x86_64-none       <download available>
cpython-3.13.15-windows-x86_64-none                   <download available>
cpython-3.13.15+freethreaded-windows-x86_64-none      <download available>
cpython-3.12.13-windows-x86_64-none                   <download available>
cpython-3.12.12-windows-x86_64-none                   C:\Users\...\AppData\Roaming\uv\python\cpython-3.12-windows-x86_64-none\python.exe
cpython-3.12.10-windows-x86_64-none                   C:\Users\...\AppData\Local\Programs\Python\Python312\python.exe
cpython-3.11.15-windows-x86_64-none                   <download available>
cpython-3.11.9-windows-x86_64-none                    C:\Users\...\AppData\Local\Microsoft\WindowsApps\python3.exe
cpython-3.11.9-windows-x86_64-none                    C:\Users\...\AppData\Local\Microsoft\WindowsApps\python3.11.exe
cpython-3.11.9-windows-x86_64-none                    C:\Users\...\AppData\Local\Microsoft\WindowsApps\python.exe
```

That is the head of the list on the machine this was written on, with the home directory shortened
so the lines fit; yours will differ and the shape will not.

**Line by line:**

- `uv python list` — asks `uv` for every interpreter it can see: the ones installed on this machine
  and the ones it could download. It is a read; it installs nothing.
- `cpython-3.12.12-…` followed by a path — an interpreter that exists on disk right now. The long
  name is not decoration: it carries the implementation (`cpython`), the version, the platform, and
  the build variant, because all four can differ between two files that both answer to `python`.
- `<download available>` — not installed. `uv` embeds a catalogue of interpreters it can fetch, so
  a version you do not have is one command away rather than an afternoon of installer pages.
- **The three lines that all say `3.11.9`** — three separate files, in `WindowsApps`, all the same
  version. Those are the stubs Windows ships. One of them is called `python.exe`, and if it comes
  first in the search order, that is what the bare word `python` means on this machine.
- **The two lines that matter here**: `3.12.12` under `AppData\Roaming\uv`, which `uv` downloaded
  and manages, and `3.12.10` under `Programs\Python\Python312`, which somebody installed by hand.
  Both are CPython 3.12. Neither is more correct. They are different files, and one of them is what
  you get when you do not choose.

Now find out which one you get when you do not choose:

```bash
python -c "import sys; print(sys.executable)"
```

```
C:\Users\nisha_gnzw\AppData\Local\Programs\Python\Python312\python.exe
```

**Line by line:**

- `python -c "…"` — runs a short program instead of a file. It is the shortest way to make an
  interpreter identify itself, and unlike `--version` it answers with a path, which is the thing
  you actually need to know.
- `sys.executable` — the path of the interpreter running this code, as it sees itself. Not a
  setting, not an inference: the running program's own location on disk.
- The answer is the hand-installed 3.12.10, not the `uv`-managed 3.12.12. **That is the search
  order deciding for you**, silently, in favour of whichever entry happens to come first in this
  machine's path. Nothing here is broken. Nothing here is chosen, either.

So choose. This is the entire mechanism of the pin:

```bash
uv python pin 3.12.12
```

```
Pinned `.python-version` to `3.12.12`
```

**Line by line:**

- `uv python pin 3.12.12` — writes the version into a file rather than into your memory or your
  shell. It does not install anything, it does not change your path, and it does not affect any
  other folder: it creates one file in the current directory.
- `3.12.12` — the full three-part version, taken from the `uv python list` output above rather than
  from memory. `3.12` would also be accepted and would be a floor rather than a pin: it says
  "some 3.12", which is the ambiguity this file exists to remove.
- The command's output names the file it wrote. Read it. If it says it *updated* a pin rather than
  creating one, there was already a pin here and you have just changed what this folder runs.

The file it wrote is one line long, and it is the first file of this project that will be committed:

```text
3.12.12
```

That is the entire contents of `.python-version`, at the root of the project, beside `PROJECT.md`.
It is a real file the reader types or generates, not a description of one, and there is nothing
else in it — no comment syntax, no key, no quotes. One version, one newline.

Read the pin back, and this is the point of the whole part:

```bash
uv run python -V
uv run python -c "import sys; print(sys.executable)"
```

```
Python 3.12.12
C:\Users\nisha_gnzw\AppData\Roaming\uv\python\cpython-3.12.12-windows-x86_64-none\python.exe
```

**Line by line:**

- `uv run …` — runs a command with the interpreter this folder has pinned, rather than with the one
  your shell would find. `uv` reads `.python-version` from the working directory, and if it finds
  no interpreter matching the pin, it downloads one. This is the command every other command in
  this project will be run through.
- `python -V` prints `3.12.12` — the pinned version, not the `3.12.10` that the bare `python`
  printed in part 1.1. Same machine, same folder, same word `python` in both commands, two
  different programs.
- `sys.executable` prints a path under `AppData\Roaming\uv\python\…` — a different file, in a
  different directory, from the one the bare `python` reported. This is the observation worth
  keeping: a pin is not a version label attached to an interpreter, it is a *choice of file*.
- Neither command created a virtual environment. There is no `.venv` in this folder yet and there
  is nothing installed. On day 0 there is nothing to install; day 1 is where an environment
  appears.

## When it breaks

`uv` looks for `.python-version` in the working directory **and in each of its parents**. So a pin
you wrote once in a folder above this one governs everything underneath it, and it never mentions
that it is doing so. This is a folder with no pin of its own, sitting inside a folder that has one:

```text
--- no .python-version here:
.
..
Python 3.11.9
```

The desk runs on 3.11.9, the empty directory listing shows nothing that explains why, and every
version command inside the folder agrees with itself. Somebody put a claims desk inside a parent
folder that had been pinned for something else, spent an evening on an error that mentioned a
standard-library function, and found it by running `ls -a` one directory up. The smallest fix is to
give every project its own pin file and commit it — which is what this part just did, and why
`.python-version` is committed rather than ignored.

## In production

**What a senior writes instead.** The same one-line file, plus a check that reads it back rather
than trusting it. Writing a pin proves nothing; the pinned version and the running version can
still disagree, because a pin is a request and the interpreter that shows up is the answer. Part
3.1 turns that comparison into the first line of this project's check, and it is red the moment
somebody runs the desk with a bare `python`.

**What degrades at scale.** A claims desk is not one process for long. This project ends with a
container, a compose file with the boundary running beside it, and a CI job running the evalset —
that is at least three places an interpreter gets chosen, and by then "it works on my machine" has
three machines in it. Pinning on day 0 costs one line. Discovering on the ship day that the
container runs a different patch version than the desk was written against costs a day, and it
costs it at the worst point in the project.

**The review comment.** *"`.python-version` is in `.gitignore`. Take it out — the pin is not a
local preference, it is part of how this desk is defined, and a clone without it runs on whatever
the cloner happens to have."*

**The interview question.** *"On a machine with four Pythons on the path, what decides which one
`python` means, and what would you put in a repository so that the answer stops depending on the
machine?"*

## Check yourself

- **Run:** `uv run python -V` and then `python -V` in the same folder — expect two different
  version numbers, and expect the second one to be whatever your machine happened to install first.
  If they are the same, run `uv python list` and pin a version you do not currently have.
- **Say out loud:** You pinned `3.12.12` and `uv run python -V` says `3.12.12`. Name the thing that
  could still be wrong, and the command that would tell you.
