## One-line answer

The repository carries the *names* the claims desk expects in its environment and never the
values, so a new clone can be told what is missing without anybody ever being told what it was.

## The idea

Above the intake counter there is a blank first-notice form. Every box on it is empty: policy
number, date of loss, description, whether there was a third party. Nobody has ever filed the blank
one, and it is the most-read piece of paper at the desk, because it is the only thing that says
what a complete notification consists of. A new starter can look at it and know exactly which
questions to ask, without being shown a single real policyholder's answers.

A repository needs the same object, and for the same reason. The claims desk will need a key to
call a model. The key is a secret: it belongs to one person, it costs money, and it is worth
stealing. But *the fact that a key is needed, and the name it goes under*, is not a secret at all.
It is the most important thing a new clone can be told. Splitting those two — the names in the
repository, the values on the machine — is what `.env.example` is for.

Some care with a word that gets used loosely. The **process environment** is the set of
name-to-string pairs the operating system handed a program when it started, which Python exposes as
`os.environ`. It is built by whatever launched the program — your shell, a container runtime, a CI
runner — and **it has never heard of any file.** No file is consulted, on any platform, ever.

Which means `.env` is not the environment. It is a text file with lines in it, in a shape that a
library will later read and copy *into* the environment on request. On day 0 nothing reads it
automatically, and nothing has to: this part writes the file, and part 3.1 reads it the same way
you would read any other text file, with no dependency at all.

Two files, then, with a hard line between them:

- `.env.example` — committed, holds names, holds no values, and is exempted from the ignore rules
  by the negation written in the previous part.
- `.env` — never committed, holds the values, matched by the very first rule in `.gitignore`.

The blank form goes on the wall. The filled-in one goes in the drawer.

## The mechanism

The whole file, at the root of the project:

```ini
# Claims Intake Desk — the shape of .env, with no value in it.
#
# Copy this file to .env and fill the value in. .env is ignored and never leaves your machine;
# this file is committed, and it is the only place a new reader can learn which names the desk
# expects to find in its environment.

# The key the desk answers claims with. Get one at https://aistudio.google.com/apikey
# Setting this name alone is what selects the AI Studio path. Nothing else is needed here.
GOOGLE_API_KEY=
```

**Line by line:**

- **The header comment** — says what the file is *and* what to do with it, because this is the
  first file a stranger opens after cloning, and "copy me and fill me in" should not require
  reading a separate document.
- **"never leaves your machine"** — the promise the previous part's ignore rule makes true. Stating
  it here, next to the name of the file, is how the two parts stay connected for someone reading
  only one of them.
- `# The key the desk answers claims with. Get one at https://aistudio.google.com/apikey` — the
  comment carries the URL. A name with no source is a puzzle: the reader knows what to set and not
  where to get it. This is where the free key comes from, and it is a page you sign in to and click
  once.
- **"Setting this name alone is what selects the AI Studio path."** — the desk will reach the model
  through an API key rather than through a cloud project, and the presence of this one variable is
  what selects that route. There is no second variable to set here and no mode flag to turn on;
  adding one because it appears in an unrelated example is how a working setup gets broken.
- `GOOGLE_API_KEY=` — **the name, the equals sign, and nothing after it.** A value here would be a
  secret published on purpose. A missing equals sign would make the line a comment-shaped noise
  that no parser reports. The empty value is a declaration: this name exists, and it is your job to
  fill it.
- **One name, not five.** The temptation on day 0 is to write down every variable the project might
  eventually want. Every one of those is a guess about a file that does not exist yet, and a guess
  in this file is worse than an omission — the check in part 3.1 refuses to go green until every
  name declared here is set, so an invented name is a check that can never pass.

Copy it, fill it in, and confirm that git cannot see the copy:

```bash
cp .env.example .env
git status --short --untracked-files=all
git check-ignore -v .env
```

```
?? .env.example
.gitignore:8:.env	.env
```

**Line by line:**

- `cp .env.example .env` — a copy, so the names arrive in the right shape and in the right order.
  On PowerShell the same thing is `Copy-Item .env.example .env`. Then open `.env` in an editor and
  put the key after the equals sign; nothing in this project ever asks you to paste a key into a
  terminal, where it would land in your shell history.
- `git status --short --untracked-files=all` — `--untracked-files=all` is the strict form: it lists
  every untracked file individually instead of collapsing directories, which is exactly what you
  want when the question is "is there anything here git can see that I do not want it to see".
- `?? .env.example` — two question marks mean untracked. **This is the whole result.** `.env` exists
  on disk, holds a real key, and does not appear: git is not hiding it, git is ignoring it, and the
  status output is the plainest evidence you will get.
- `git check-ignore -v .env` naming line 8 — the same rule as the previous part, now firing on a
  file that really exists. The rule was already true; the file arriving changed nothing.
- `.env.example` shows as untracked because it has not been committed yet — it goes in with the
  check, in the next part, in one commit that means "here is what the desk needs and here is the
  thing that verifies it".

## When it breaks

Copy the example, forget to open it, and the desk tells you exactly which name it is waiting for:

```text
ok   interpreter       interpreter 3.12.12, as pinned in .python-version
ok   ignore rule       git ignores .env, by the rule at .gitignore:8:.env
ok   secret untracked  .env is not tracked by git
RED  key present       empty in .env: GOOGLE_API_KEY

claims desk: 1 check(s) red
```

Someone cloned the desk, ran `cp .env.example .env` because a document said to, and moved on. The
check is red, it names the variable, and it does not print a single character of any value —
including the empty one. The smallest fix is to open `.env` and paste the key from
<https://aistudio.google.com/apikey> after the equals sign. What makes this a good failure rather
than an annoying one: it happens at setup, on a check, rather than deep inside a claim being
processed at the moment the model is first called.

## In production

**What a senior writes instead.** Not a file. In anything deployed, the values are injected by the
platform — a secret manager, a container runtime's secret mount, the CI provider's encrypted
variables — and the process environment is populated before the program starts, which is what it
was designed for. `.env` is the local-development shape of the same idea, and the reason it is
still worth having is that it keeps development and deployment agreeing about **names**. The names
in `.env.example` are the contract; where the values come from is an implementation detail that
changes per environment. This project injects rather than bakes on day 19, and the sentence to
carry there is: the container gets the name from the image and the value from the platform.

**What degrades at scale.** A free AI Studio key has a rate ceiling, and this desk's cast is five
agents — one notification is at least five model calls before any retry. A queue of twelve
synthetic notifications is well inside anything; an intake queue that arrives in a Monday-morning
burst of several hundred is not, and the failure will be a 429 rather than a wrong answer. What the
free tier actually allows is not published as a number — the current limits are shown per account
at <https://aistudio.google.com/rate-limit>, so read yours there rather than trusting a figure
written down anywhere, this document included. Honest 429 handling is day 15, and the budget that
refuses before the provider does is day 9.

**The review comment.** *"`.env.example` has a real-looking key in it. Even if it is expired,
replace it with an empty value — an example file with a value in it teaches every future reader
that values belong in this file."*

**The interview question.** *"Your application reads a `.env` file locally and gets its
configuration from the environment in production. What in the repository keeps those two agreeing,
and what happens the day someone adds a variable to only one of them?"*

## Check yourself

- **Run:** `git status --short --untracked-files=all` with your filled-in `.env` on disk — expect
  `.env` to be absent from the output entirely.
- **Say out loud:** Nothing in this project has read `.env` yet, and no library that could has been
  installed. So what, precisely, has been achieved by creating it — and what would happen if you
  ran the desk right now?
