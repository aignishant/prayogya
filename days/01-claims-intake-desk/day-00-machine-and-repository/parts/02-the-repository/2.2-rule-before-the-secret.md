## One-line answer

`.gitignore` is written before the first secret exists, because an ignore rule speaks only about
paths git has never been told to hold — and by the time the secret is on disk, the cheapest moment
to say "not this one" has already passed.

## The idea

There is a drawer at the intake counter where the day's claim notes go. On the front of it,
somebody has taped a card: **nothing with a policyholder's bank details in this drawer.** The card
was taped there on the day the drawer was installed, when the drawer was empty and the rule cost
nothing to write.

Consider the alternative version of that morning. The drawer goes in, the claims start arriving, and
three weeks later somebody notices a photocopy of a bank statement in with Tuesday's notes and
tapes the card up then. The card now says exactly the same words. It does not remove the statement.
It does not tell you how many people have been through the drawer. And the awkward part is that
from the front, the two drawers look identical: same card, same handwriting, same rule.

That is precisely how git ignore rules work, and the resemblance is not a metaphor stretched to
fit — it is the mechanism. An ignore rule is a statement about **paths git has never been told to
hold**. A path git has been told to hold, from a `git add` onwards, is **tracked**, and ignore
rules do not reach a tracked path. They never did. Writing the rule after the file is already
tracked produces a repository that looks protected and is not.

Two more terms, both used from here to the end of this project:

- An **ignore source** is one of the places git reads exclude patterns from for a single path.
  There are several — this file, one in each subdirectory, a per-repository one inside `.git`, a
  per-machine global one — and two of them are invisible to anybody reviewing your repository.
  That is why the rule belongs in the committed file and not in your own machine's settings.
- A **negated pattern** is an ignore line beginning `!`, which takes a path back out of the ignore
  list. It only works *below* the pattern it is excepting, because within one file the last
  matching line decides.

So the order of this day is not stylistic. `.gitignore` is written and committed **before** the
part that creates `.env`. The card goes on the drawer before the drawer is opened.

## The mechanism

The whole file, at the root of the project, beside `PROJECT.md`:

```gitignore
# Claims Intake Desk — what git must never be told to hold.
#
# This file exists before a single file it names does. That order is the whole point: an ignore
# rule speaks only about paths git has never tracked, so a rule written after the first
# `git add` has nothing to say about the file it was written for.

# Secrets. Never committed — not once, not "just to check the key works".
.env
.env.*
!.env.example
*.key
*.pem
service-account.json

# The environment. Rebuilt from the lockfile by uv, so it is never committed and never copied
# from one machine to another.
.venv/
__pycache__/
*.pyc

# Editors and operating systems, which have opinions about every folder they open.
.DS_Store
Thumbs.db
.idea/
.vscode/
*.swp
```

**Line by line:**

- **The header comment** — this file will be read by somebody who is deciding whether to add a
  line to it, and the first thing they need to know is why the order of writing mattered. A
  `.gitignore` with no comments is a list of superstitions.
- `.env` — the exact filename, and the single most important line in the repository on day 0. This
  is the file that will hold the key the claims desk answers with. It does not exist yet. That is
  the point.
- `.env.*` — everything that starts with `.env` and a dot: `.env.local`, `.env.production`,
  `.env.backup`. The realistic leak is not `.env`; it is the copy somebody made while debugging and
  named `.env.old`.
- `!.env.example` — the negation, and **its position is load-bearing**. It sits *below* `.env.*`,
  so for the path `.env.example` the last matching line is this one, and the file is not ignored.
  Move it above `.env.*` and the last match becomes the wildcard: the example is silently ignored,
  never committed, and every clone is missing the one file that says which names the desk needs.
- `*.key` and `*.pem` — private keys, by extension rather than by name, because these arrive with
  names nobody predicts. Neither exists in this project yet either.
- `service-account.json` — a credentials file by its conventional name. This project uses an API
  key rather than a service account, so this line will most likely never match anything, and it
  stays: an ignore rule that never fires costs nothing, and the one time it fires it is the only
  thing standing between a credential and a public repository.
- `.venv/` — the environment day 1 creates, with a trailing slash so the pattern matches a
  directory and not a file that happens to share the name. It is rebuilt from a lockfile on any
  machine, so committing it would mean shipping one machine's binaries to another.
- `__pycache__/` and `*.pyc` — the interpreter's compiled cache. Machine-specific, regenerated on
  every run, and pure noise in a diff.
- `.DS_Store`, `Thumbs.db`, `.idea/`, `.vscode/`, `*.swp` — the files an operating system or an
  editor writes into a folder without being asked. They belong to the person, not to the project,
  and the reason they are in the committed file rather than in a personal global one is that this
  desk will be cloned by people whose editors you cannot predict.
- **The grouping and the blank lines** — three groups, each with a heading comment: secrets, build
  artefacts, tools. When somebody adds a line in six months, the group tells them whether they are
  adding a rule about a secret or a rule about noise, and those two get very different review.

Commit it, on its own, before anything it names exists:

```bash
git add .gitignore
git commit -m "P01 day 0: the ignore file, written before the secret exists"
```

```
[main 54c8947] P01 day 0: the ignore file, written before the secret exists
 1 file changed, 26 insertions(+)
 create mode 100644 .gitignore
```

**Line by line:**

- `git add .gitignore` — one path, again named rather than swept. The file is tracked from here on,
  which is correct: the rules have to travel with the repository or they protect only this machine.
- **A commit of its own** — no other file rides along. The history of this project can now be read
  as a sequence of decisions, and this decision is "the rule exists as of here". Anything committed
  after this commit was committed under the rule.
- `1 file changed, 26 insertions(+)` — the count is the whole file, because it is new. There is no
  `.env` in this commit, no key, and nothing to clean up later.

Now ask git whether the rule works, for a file that does not exist:

```bash
git check-ignore -v .env
echo "exit=$?"
```

```
.gitignore:8:.env	.env
exit=0
```

**Line by line:**

- `git check-ignore` — the command that answers "would git ignore this path?", which is a different
  and much better question than "does the word appear in `.gitignore`?". Nobody should be grepping
  an ignore file to find out what git thinks.
- `-v` — verbose, and the reason to always use it: it prints **which source, which line and which
  pattern** decided. Without `-v` you get the path back and no explanation.
- `.gitignore:8:.env` — file, line number, pattern. Line 8 is the bare `.env` rule. When a rule
  fires that you did not expect, this triplet is what tells you whether it came from the committed
  file or from something invisible on your own machine.
- The tab between the pattern and the path is a real tab, not spaces. This matters in exactly one
  place — a program parsing this output — and part 3.1 is that program.
- `exit=0` — **the verdict is the exit status**, not the text. Zero means "yes, ignored". The text
  is for you; the number is for the check.
- **`.env` does not exist yet, and the command still answers.** Ignore rules are about *paths*, not
  about files. This is the whole reason the rule can be written first, and it is the sentence to
  remember out of this part.

## When it breaks

Move the negation above the wildcard it is excepting, which reads perfectly well to a human — deny,
then make an exception — and the example file disappears:

```text
--- .gitignore
.env
!.env.example
.env.*
--- git check-ignore -v .env.example
.gitignore:3:.env.*	.env.example
exit=0
--- git add -A ; git ls-files
.gitignore
```

`git check-ignore` says `.env.example` is ignored, by line 3, and `git add -A` quietly adds
everything except it. Nothing errors, nothing warns, and the repository is committed and pushed
with the one file missing that tells a new clone which environment variables the desk expects. It
was found by someone cloning the project on another machine and having nothing to copy. The
smallest fix is to put `!.env.example` **after** `.env.*`: within one file, the last matching line
decides.

## In production

**What a senior writes instead.** The same file, plus a scan in CI that fails the build when a
committed path looks like a credential — because `.gitignore` is a rule about what you tell git to
hold, and it cannot help with `git add -f` or with a file somebody pasted into a test fixture. The
ignore file is the cheap layer, not the only one. This project adds the second layer as a check on
day 0 itself, in part 3.1, and a threat model for the whole desk on day 16.

**What degrades at scale.** One `.gitignore` at the root is right for a repository this size. A
claims platform with a dozen services grows per-directory ignore files, and a rule in a
subdirectory quietly overrides the root for everything beneath it — so "is this path ignored, and
by which of the sources?" stops being answerable by reading and starts requiring `check-ignore -v`.
The habit of asking git rather than reading the file is what survives that growth.

**The review comment.** *"This adds `.env` to `.gitignore` in the same commit that adds `.env` to
the repository. The rule came too late — the file is tracked, so the rule does nothing. Untrack it
and rotate the key."*

**The interview question.** *"A colleague says the secret is safe because it is in `.gitignore`.
Give the two situations where that is false, and say what you would check first."*

## Check yourself

- **Run:** `git check-ignore -v .env.example; echo "exit=$?"` — expect **exit 1 and no output**:
  the example is not ignored, which is the answer you want, delivered as silence.
- **Say out loud:** `git check-ignore -v .env` prints a line and exits 0 even though `.env` does not
  exist on your disk. What is git actually answering a question about, and why does that make the
  order of this day's commits matter?
