## One-line answer

The first thing in this repository's history is not code, it is the one page that says what the
desk decides and when it is allowed to decide it — because a system nobody can describe in a page
is a system nobody can tell is finished.

## The idea

A new starter joins the claims team and is put on the intake desk for a week. She asks the person
handing over: what does this desk actually do? The answer runs long, takes three
digressions, involves the phrase "well, it depends", and ends with "you'll pick it up". By Thursday
she has picked up that the desk fast-tracks small property claims, except when the policy lapsed,
except when there is no date of loss, except when the description mentions injury — and none of
that is written down anywhere, because everyone who knows it is busy doing it.

That is a desk without a brief, and the cost is not confusion. The cost is that nobody can say what
"working" means, so nobody can say what "broken" means either.

This project is built doc-first for exactly that reason. Before any code exists, one page says what
this desk is: what arrives at it, what it decides, which tools it has, which agents do the
deciding, where its data lives, and — the load-bearing sentence — **what has to be true before it
can be called done**. That page is `PROJECT.md`, and writing it before the code is not ceremony. It
is the only moment in the project when the shape of the thing is still cheap to change.

Then that page becomes the first thing in the repository's history.

A **repository** is a folder plus a complete record of every change ever made inside it. Three
words for the three states a file can be in, and they are easy to confuse because git uses one
verb, `add`, for two of them:

- the **working tree** is the folder as it exists on disk right now;
- the **staging area** is the list of paths git is holding for the next commit — what `git add`
  writes into;
- a **commit** is a permanent, named snapshot of everything that was staged, with a message saying
  why.

A path git has been told to hold, from a `git add` onwards, is **tracked**. That word does almost
nothing in this part and it does everything in the next two, so it is defined here where it is
still calm.

The new starter's real problem was that the desk's rules lived in people. This part moves the rules
into a file, and the file into a history.

## The mechanism

The whole brief, at its real path at the root of the project:

````markdown
# P01 · Claims Intake Desk

**Industry.** Insurance — first notice of loss.

**What it is.** A desk that reads a synthetic insurer's first-notice-of-loss queue. Each
notification arrives as free text with a policy number, a description of what happened and
sometimes a photograph reference. The desk classifies the loss type, checks the policy was in
force on the date of loss, decides whether the claim can be fast-tracked, and writes either a
fast-track confirmation or a deficiency letter naming exactly what is missing.

**Days.** 20 · **Deploy tier.** D3 · **Depends on nothing, and references nothing.**

## The triad

| Leg | This project |
| --- | --- |
| **Tools** | `fetch_policy(number)` · `check_in_force(number, date)` · `classify_loss(text)` · `draft_letter(claim_id, kind)` |
| **MCP boundary** | `claims_mcp/` — owns the policy store and the claim file; no agent touches a file |
| **Cast** | `intake` → `classifier` ‖ `policy_checker` → `adjuster` → `letter_writer` |

## The feature set — every one taught here, in full

| Subsystem | Where this project teaches it | The failure it prevents here |
| --- | --- | --- |
| The machine and the repository | day 0 | a key in the history of the repository that holds the claims desk |
| The skeleton and the kit | day 1 | four call sites each retrying a policy lookup differently |
| The domain and its data | day 2 | a fixture that looks like a real policyholder |
| The boundary, part one | day 3 | an agent that opens the claim file itself |
| The boundary, part two | day 4 | a boundary that works on one machine and nowhere else |
| Tools | day 5 | a model that invents a policy number because the description let it |
| The tool that must refuse | day 6 | a missing date of loss reported as a crash instead of as a deficiency |
| The first agent | day 7 | an unpinned model quietly answering claims four generations behind |
| Sessions and state | day 8 | yesterday's claim leaking into today's letter |
| The cast | day 9 | five agents, five model calls, one unbounded queue |
| The workflow runtime | day 10 | a classifier and a policy check that loop on each other |
| Callbacks and plugins | day 11 | a photograph reference written into a log in plain text |
| Memory and retrieval | day 12 | a citation to a policy clause that does not contain the quoted words |
| Structured output | day 13 | a fast-track decision that is a paragraph of prose |
| The decision record | day 14 | a fast-tracked claim nobody can explain to an auditor |
| Reliability | day 15 | a fabricated in-force answer covering a 429 |
| Security and privilege | day 16 | an instruction arriving inside a loss description and being obeyed |
| Observability | day 17 | a claim that went wrong and no way to find which hop did it |
| Evals | day 18 | a change that silently stops checking whether the policy was in force |
| Ship | day 19 | a clone that will not start on anybody else's machine |

**Done when.** A cold clone processes twelve synthetic notifications, fast-tracks the four that
qualify, writes eight deficiency letters that each name a real missing field, and the eval goes
red the moment the policy in-force check is disabled.

**All data in this project is synthetic.** Every policy, every policyholder, every loss
description and every photograph reference is invented for this repository. No real claim, real
policy number or real person appears anywhere in it.
````

**Line by line:**

- **`# P01 · Claims Intake Desk`** — the project's own name and number, at the top of its own
  repository. This folder does not know about any other; everything it needs is inside it, and
  everything it teaches is taught in it.
- **`**Industry.** Insurance — first notice of loss.`** — first notice of loss is the moment a
  policyholder tells the insurer that something happened, before anyone knows whether it is
  covered. Naming the industry in the second line is what stops this brief being a generic agent
  demo: every decision below inherits meaning from it.
- **`**What it is.**`, in one paragraph** — the whole system in the order the work happens:
  something arrives, four things happen to it, one of two documents comes out. If this paragraph
  needs a second one, the project is two projects.
- **"classifies the loss type, checks the policy was in force on the date of loss, decides whether
  the claim can be fast-tracked, and writes either …"** — four verbs, and every one of them becomes
  a tool or an agent below. A brief whose verbs do not appear in its own architecture table is
  describing a different system from the one being built.
- **`**Days.** 20 · **Deploy tier.** D3`** — the size of the commitment, up front. D3 is this
  project's deploy floor: a running container with a health endpoint, a compose file with the
  boundary beside it, and CI running the evalset. Written on day 0 because it changes what day 1
  builds.
- **"Depends on nothing, and references nothing."** — a promise about this repository, and the one
  a reader can check most easily: if any file in this folder needs something outside it, the
  sentence is false and the project is not finished.
- **The triad table — Tools, MCP boundary, Cast** — three rows because these are the three
  decisions that are expensive to change later. The tool signatures name their arguments, because
  `check_in_force(number, date)` and `check_in_force(claim)` are different systems.
- **`claims_mcp/` — "no agent touches a file"** — the boundary stated as a prohibition rather than
  as a component. The policy store and the claim file live behind a separate process, and the only
  way to them is a declared tool. A component can be added; a prohibition has to be designed for,
  which is why it is in the brief and not in a later day.
- **The cast line, `intake` → `classifier` ‖ `policy_checker` → `adjuster` → `letter_writer`** —
  the arrow is "hands off to", and `‖` is "at the same time". Five agents means at least five model
  calls for one notification, and that number is a budget the brief is committing to on day 0.
- **The feature-set table, one row per subsystem** — the left column is what gets built, the middle
  is which day of *this* project builds it, and the right is the failure that day exists to
  prevent. The right-hand column is the one that earns its place: it turns a syllabus into a list
  of things that can go wrong at an insurer.
- **`**Done when.**`** — the only paragraph in this file that can be false. Twelve notifications,
  four fast-tracked, eight letters that each name a real missing field, and an eval that goes red
  when the in-force check is disabled. Every number is checkable, and the last clause is the one
  that matters: **a test that cannot fail is not evidence**, so the brief commits on day 0 to a
  check that has been seen to go red.
- **The synthetic-data paragraph** — last, and not optional. Every policy number, name and loss
  description in this project is invented. A claims system that trains its author on real
  policyholder data is a different kind of project with a different kind of review, and this one
  never becomes that by accident.

Now the repository. Three commands, in a folder that already holds `PROJECT.md`, `PACKAGES.md` and
`.python-version`:

```bash
git init
git config user.name "your name"
git config user.email "you@example.com"
```

```
Initialized empty Git repository in .../claims-intake-desk/.git/
```

**Line by line:**

- `git init` — creates the `.git` directory, which is the entire history and everything git knows.
  It changes nothing else in the folder: your files are exactly where they were, and none of them
  are tracked yet.
- The word **empty** in the output is precise. There is a repository and it holds nothing. A folder
  with an empty repository in it looks identical to one without, which is why the next command is
  the one that matters.
- `git config user.name` / `user.email`, without `--global` — sets the identity for this repository
  only. Every commit records who made it, and git refuses to write one until it knows. Setting it
  per-repository rather than globally is a habit worth having when one machine holds work for more
  than one purpose.

Then the first commit:

```bash
git add PROJECT.md PACKAGES.md .python-version
git status --short
git commit -m "P01 day 0: the brief, and the interpreter this desk runs on"
```

```
A  .python-version
A  PACKAGES.md
A  PROJECT.md

[main (root-commit) 47036c2] P01 day 0: the brief, and the interpreter this desk runs on
 3 files changed, 71 insertions(+)
 create mode 100644 .python-version
 create mode 100644 PACKAGES.md
 create mode 100644 PROJECT.md
```

**Line by line:**

- `git add PROJECT.md PACKAGES.md .python-version` — three paths, named. Not `git add -A` and not
  `git add .`. On a day whose subject is a secret that must never be committed, typing the paths is
  the habit being built: **you say what goes in, rather than sweeping up whatever is lying around.**
- `git status --short` — the two-column form. `A` in the left column means the path is staged as a
  new file; the left column is the staging area and the right column is the working tree, which is
  why `--short` is worth learning early.
- `git commit -m "…"` — writes the snapshot. The message opens with the project and the day so that
  the history reads as a build log, and says what landed rather than "initial commit".
- `[main (root-commit) 47036c2]` — `main` is the branch, `root-commit` says this one has no parent
  and there will only ever be one of those, and `47036c2` is the abbreviated hash. Your hash will
  differ: it is computed from the contents, the message, the author and the time.
- `create mode 100644` on each path — the file is now tracked. From this point on, ignore rules
  have nothing to say about these three paths, which is the mechanism the next part is built on.

## When it breaks

Commit on a fresh machine before telling git who you are, and it stops rather than guessing:

```text
Author identity unknown

*** Please tell me who you are.

Run

  git config --global user.email "you@example.com"
  git config --global user.name "Your Name"

to set your account's default identity.
Omit --global to set the identity only in this repository.

fatal: unable to auto-detect email address (got '<your-user>@<your-machine>.(none)')
```

The last line is the real output with the machine's own guessed address replaced by placeholders,
because that value is different for every reader and identifies the machine it ran on; every other
line is verbatim. Somebody set up a new laptop, cloned the desk, made a change, and lost the thread
of what they were doing to a five-word config command. The smallest fix is the two `git config`
lines above — and the reason the message is this long is that git would rather be tedious than
attribute your work to a hostname.

## In production

**What a senior writes instead.** The same page, plus a decision record beside it for anything the
brief asserts without arguing — why the boundary is a separate process, why the cast is five agents
and not one. `PROJECT.md` says *what*; a record says *why*, and the difference shows up the first
time somebody proposes collapsing the cast to save calls. This project writes its decision record
for a different reader on day 14: an auditor asking why one claim was fast-tracked.

**What degrades at scale.** A brief is written once and read by everyone who joins. An intake desk
at a mid-sized insurer takes thousands of notifications a week and the rules around them change
every renewal season; when the brief stops being updated, the first symptom is not confusion but
divergence — two people implementing two policies about lapsed cover in the same repository,
because the file that would have said which one was right is six months stale.

**The review comment.** *"`Done when` says the desk 'works well'. Replace it with something a
script can decide: how many notifications, how many fast-tracked, and which check goes red when you
break it on purpose."*

**The interview question.** *"Your first commit is the project brief rather than code. Argue for it
against someone who says the code is the only thing that is true."*

## Check yourself

- **Run:** `git log --stat` — expect one commit, three files, and no fourth file you did not name.
- **Say out loud:** `.python-version` is committed and, from the next part on, `.env` never will be.
  Both are one-line configuration files at the root of the same project. What is the difference,
  stated as a rule you could apply to a file you have not seen yet?
