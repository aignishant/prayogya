## One-line answer

Everything day 0 set up is now asserted by a program that exits non-zero when it is not true,
because a setup nobody can re-verify is a setup that quietly stops being true.

## The idea

Before the intake counter opens, the supervisor does a round: the float is in the till, the blank
forms are on the shelf, the drawer is locked, the log is on the right date. It takes a moment, it
finds nothing on most mornings, and it is not optional. The point of the round is not that things
usually go wrong. The point is that the counter has a defined state, and one person confirms it
rather than four people assuming it.

Everything this day has built is that state: an interpreter that was pinned, a rule that was
written before the secret, a secret that git cannot see, a key that is actually filled in. Each of
those was true at the moment it was done. None of them stays true on its own. Somebody clones the
project on a new machine, or runs the desk with a bare `python`, or force-adds a file, and one of
the four quietly stops holding — with no error, because none of these are the kind of thing that
errors.

So this part writes the round down as a program.

Two words to be exact about, because the rest of this project leans on both:

- The **exit status** is the single number a process hands back when it ends, and the only channel
  through which a check reports its verdict to another program. Zero means success; everything
  printed on the screen is for humans. When day 19 puts this project in CI, the pipeline will read
  the number and ignore the text entirely.
- A **check that can go red** is one somebody has actually seen fail. A check nobody has watched
  fail is not evidence — it is a green light with no wire behind it, and this project's rule is
  that every day ends with at least one check that has been made to go red on purpose.

Four questions, then, each with an answer a machine can produce without asking you anything: is the
interpreter the pinned one, does git ignore `.env`, is `.env` untracked, and is every name the
example declares actually set. The supervisor's round, in a file, on the morning of day 0.

## The mechanism

The whole file, at the root of the project. It imports nothing outside the standard library,
because this project has no dependencies yet and no environment to put them in:

```python
"""The claims desk's day-zero check: is this machine ready to hold a claims desk?

Four questions, asked of the machine rather than of the reader. It imports nothing that is not
in the standard library, because on day zero this project has no dependencies and no environment
to install them into.

Run it with the pinned interpreter:

    uv run python check.py

Exit status 0 means every question answered yes. Exit status 1 means at least one did not, and
the line that starts with RED says which.
"""

from __future__ import annotations

import platform
import subprocess
import sys
from pathlib import Path

ROOT = Path(__file__).resolve().parent


def git(*args: str) -> tuple[int, str]:
    """Run a git command in this project and return its exit status and its output.

    `text=True` so the output is a string. Errors are captured rather than printed, because the
    verdict this file prints is the only thing its caller should have to read.
    """
    done = subprocess.run(
        ["git", *args], cwd=ROOT, capture_output=True, text=True, check=False)
    return done.returncode, (done.stdout + done.stderr).strip()


def env_names(path: Path) -> list[str]:
    """The variable names declared in a .env-shaped file, in the order they appear."""
    names = []
    for line in path.read_text(encoding="utf-8").splitlines():
        line = line.strip()
        if line and not line.startswith("#") and "=" in line:
            names.append(line.split("=", 1)[0].strip())
    return names


def env_values(path: Path) -> dict[str, str]:
    """The name-to-value pairs in a .env-shaped file. Nothing here reads the process environment."""
    values = {}
    for line in path.read_text(encoding="utf-8").splitlines():
        line = line.strip()
        if line and not line.startswith("#") and "=" in line:
            name, value = line.split("=", 1)
            values[name.strip()] = value.strip()
    return values


def check_interpreter() -> tuple[bool, str]:
    pin_file = ROOT / ".python-version"
    if not pin_file.exists():
        return False, "no .python-version: nothing decides which interpreter runs this desk"
    pinned = pin_file.read_text(encoding="utf-8").strip()
    running = platform.python_version()
    if running != pinned:
        return False, f"pinned {pinned}, running {running}: run it with `uv run python check.py`"
    return True, f"interpreter {running}, as pinned in .python-version"


def check_ignored() -> tuple[bool, str]:
    if not (ROOT / ".gitignore").exists():
        return False, "no .gitignore: write the rule before the secret exists, not after"
    status, output = git("check-ignore", "-v", ".env")
    if status != 0:
        return False, ".env is NOT ignored by git: one `git add -A` away from a leaked key"
    source = output.splitlines()[0].partition("\t")[0]
    return True, f"git ignores .env, by the rule at {source}"


def check_untracked() -> tuple[bool, str]:
    # TODO(me): this answers "git does not hold .env" and "there is no git here" the same way,
    # and only one of those is good news. Make the second one red.
    status, _ = git("ls-files", "--error-unmatch", ".env")
    if status == 0:
        return False, ".env is TRACKED: an ignore rule cannot reach a path git already holds"
    return True, ".env is not tracked by git"


def check_key() -> tuple[bool, str]:
    example, real = ROOT / ".env.example", ROOT / ".env"
    if not example.exists():
        return False, "no .env.example: nobody can learn which names this desk expects"
    if not real.exists():
        return False, "no .env: copy .env.example to .env and fill the value in"
    declared, filled = env_names(example), env_values(real)
    missing = [n for n in declared if not filled.get(n)]
    if missing:
        return False, f"empty in .env: {', '.join(missing)}"
    return True, f"{len(declared)} name(s) from .env.example set in .env, none printed here"


# TODO(me): a fifth check. A value left in .env.example is a secret published on purpose,
# and nothing above would notice.
CHECKS = [
    ("interpreter", check_interpreter),
    ("ignore rule", check_ignored),
    ("secret untracked", check_untracked),
    ("key present", check_key),
]


def main() -> int:
    red = 0
    for name, run in CHECKS:
        ok, detail = run()
        red += not ok
        print(f"{'ok ' if ok else 'RED'}  {name:<17} {detail}")
    print("\nclaims desk: ready" if not red else f"\nclaims desk: {red} check(s) red")
    return 1 if red else 0


if __name__ == "__main__":
    sys.exit(main())
```

**Line by line:**

- **The module docstring** — says how to run the file and what its exit status means. This is the
  first thing anybody opens when the check goes red on their machine, so the instruction lives
  where they are already looking rather than in a separate document.
- `from __future__ import annotations` — makes every annotation in the file a string that is never
  evaluated at run time. It costs nothing and it means an annotation can name a type before it
  exists, which stops a check file from failing on a detail that has nothing to do with what it
  checks.
- `import platform` — for one function, `platform.python_version()`. `sys.version` would also
  answer, as a long string with the build and compiler in it; `platform.python_version()` returns
  exactly `"3.12.12"`, in the same shape `.python-version` holds, so the comparison can be `==`
  rather than a parse.
- `import subprocess` — the checks about git ask **git**, rather than reading `.gitignore` and
  reimplementing its pattern rules. Reimplementing them is where this file would start being wrong
  in ways nobody notices: negations, directory slashes, and the invisible per-machine ignore
  sources.
- `from pathlib import Path` — paths as objects, so `ROOT / ".env"` composes correctly on Windows
  and on Linux without a single backslash anywhere in the file.
- `ROOT = Path(__file__).resolve().parent` — the project root, computed from **this file's own
  location** rather than from the current working directory. `resolve()` makes it absolute and
  removes any `..`. It matters because a check that only works when you happen to be standing in
  the right folder is a check that will produce a confusing red the first time it is called from
  somewhere else — a habit that pays on day 19, when CI runs it from the repository root.
- `def git(*args: str) -> tuple[int, str]:` — one helper for every git call. `*args` so the call
  sites read like the command line: `git("check-ignore", "-v", ".env")`.
- `subprocess.run([...], cwd=ROOT, capture_output=True, text=True, check=False)` — four arguments
  and each is a decision. **A list, not a string**, so nothing goes through a shell and a path with
  a space in it cannot become two arguments. `cwd=ROOT` runs git in the project rather than
  wherever the caller stood. `capture_output=True` keeps git's own output off your screen, because
  this file's verdict is the only thing worth reading. `text=True` returns `str` instead of
  `bytes`, so nothing downstream has to decode.
- `check=False` — **the important one.** With `check=True`, a non-zero exit from git raises. Here a
  non-zero exit is not an accident, it is the answer: `check-ignore` exits 1 to mean "not ignored".
  A check that crashes on the very outcome it exists to detect is worse than no check.
- `return done.returncode, (done.stdout + done.stderr).strip()` — the number first, because the
  number is the verdict. Both streams are concatenated because git puts errors on one and answers
  on the other and this file wants whichever arrived.
- `def env_names(path)` — the names declared in an env-shaped file, in order. It skips blank lines
  and lines starting with `#`, and requires an `=`. This is a deliberately small parser for a
  deliberately small format; it does not handle quoting or `export`, and it does not need to,
  because it only ever reads files this project prints.
- `line.split("=", 1)[0].strip()` — split **once**, take the left. The `1` is what makes a value
  containing an equals sign — which base64-looking keys often do — parse as one value rather than
  becoming three fields.
- `def env_values(path)` — the same walk, keeping both halves. Kept as two functions rather than
  one because the two callers want different things: one asks *what names should be here* from the
  example, the other asks *what is set* in the real file. Merging them would mean every caller
  taking a dictionary and throwing half of it away.
- **The docstring on `env_values`: "Nothing here reads the process environment."** — a promise
  about what this function is. It reads a text file. `os.environ` is not consulted, so a variable
  exported in your shell cannot make this check pass while `.env` is empty. False greens are the
  only kind of green worth being paranoid about.
- `def check_interpreter()` — the four checks all return `tuple[bool, str]`: did it pass, and one
  line saying why. Uniform shape is what lets `main` be six lines and lets a fifth check be added
  without touching anything else.
- `if not pin_file.exists(): return False, "no .python-version: …"` — the missing-file case comes
  first and is a *failure*, not a skip. A check that quietly passes when its subject is absent is
  the most common way a green build stops meaning anything.
- `running != pinned` — string equality between what `.python-version` says and what
  `platform.python_version()` reports. Not a "compatible version" comparison: this project pinned
  an exact version, so anything else is a difference somebody should know about.
- **The red message names the fix**: ``run it with `uv run python check.py` ``. Every failing
  message in this file ends in something to do. A red line that only states a fact makes the reader
  do the diagnosis twice.
- `def check_ignored()` — asks git, in two steps. First, does `.gitignore` exist at all, because
  its absence has a different fix from a missing rule inside it. Then `check-ignore -v .env`.
- `if status != 0: return False, ".env is NOT ignored by git: one `git add -A` away from a leaked
  key"` — the exit status *is* the answer, as part 2.2 showed. The message says what the exposure
  actually is, in the terms of the accident that would cause it.
- `output.splitlines()[0].partition("\t")[0]` — `check-ignore -v` answers with
  `source:line:pattern`, a tab, then the path. `partition("\t")[0]` takes everything before the
  tab, which is the triplet naming which rule fired. `.splitlines()[0]` because the command answers
  per path and this call passes one. Quoting the source in the green line is what makes the check
  useful when the rule that fires is one you did not write.
- `def check_untracked()` — `git ls-files --error-unmatch .env` asks whether git is holding this
  path. `--error-unmatch` turns "I have never heard of it" into a non-zero exit, which is what makes
  this a question rather than an empty print.
- `if status == 0: return False, ".env is TRACKED: …"` — **the inverted one.** Everywhere else in
  this file, git exiting 0 is good news; here it means git is holding the secret, which is the worst
  state this project can be in. It is written as its own check rather than folded into the ignore
  one because the two have different fixes: one is a missing rule, the other is a file that has to
  be untracked and a key that has to be rotated.
- `# TODO(me): this answers "git does not hold .env" and "there is no git here" the same way` — an
  honest limit, left in the file. Run this check in a folder where nobody ran `git init` and it
  reports `ok`, because git exits non-zero for both "not tracked" and "not a repository". That is a
  false green, it is yours to fix, and the fix is in the build brief.
- `# TODO(me): a fifth check.` — the second rep. A value left in `.env.example` is a secret
  published on purpose, and nothing in this file would notice.
- `CHECKS = [("interpreter", check_interpreter), …]` — a list of pairs rather than four calls in
  `main`. The order is the order they print, the short name is what the reader scans for, and
  adding a check is one line in one place.
- `def main() -> int:` — returns the status rather than exiting, so the decision to end the process
  lives in exactly one place, at the bottom of the file.
- `red += not ok` — `not ok` is a `bool`, and `True` adds one. It counts failures rather than
  stopping at the first, because on a fresh machine three things are usually wrong at once and
  finding out about them one run at a time is miserable.
- `print(f"{'ok ' if ok else 'RED'}  {name:<17} {detail}")` — `ok ` has a trailing space so both
  labels are three characters and the columns line up; `{name:<17}` pads the short name to a fixed
  width. Alignment is not decoration in a check: a scanning eye finds the one word `RED` in a
  column far faster than in ragged prose.
- `return 1 if red else 0` — one non-zero status for "something is wrong", not a different number
  per failure. Callers branch on zero and non-zero; anything finer belongs in the text.
- `sys.exit(main())` under `if __name__ == "__main__":` — the exit status is the return value of
  `main`, and the guard means importing this file runs nothing. That matters from day 1, when the
  `run` driver calls into it.

Run it the way the docstring says:

```bash
uv run python check.py
echo "exit=$?"
```

```
ok   interpreter       interpreter 3.12.12, as pinned in .python-version
ok   ignore rule       git ignores .env, by the rule at .gitignore:8:.env
ok   secret untracked  .env is not tracked by git
ok   key present       1 name(s) from .env.example set in .env, none printed here

claims desk: ready
exit=0
```

**Line by line:**

- `uv run python check.py` — through `uv`, so the interpreter is the pinned one. Run it with a bare
  `python` and the first line goes red, which is the check doing its job rather than a mistake.
- **Four `ok` lines and a verdict** — the first check names the version, the second names the rule
  and the line that fired, the third states a negative, the fourth counts names. Each says what it
  saw, so a green run is still evidence rather than reassurance.
- **`none printed here`** — the fourth check has read a real key and says only how many names were
  set. A check that prints a secret to prove it found one has leaked it into every terminal
  scroll-back and CI log that ever runs it.
- `exit=0` — the verdict. `$?` holds the exit status of the last command in a POSIX shell; in
  PowerShell the same value is `$LASTEXITCODE`.

## When it breaks

The first version of this file used an em dash in the interpreter message. Run with a bare
`python`, on this machine's own console, it printed this:

```text
RED  interpreter       pinned 3.12.12, running 3.12.10 � run it with `uv run python check.py`
```

The check was right, the exit status was right, and the message had a replacement character in the
middle of it because a Windows console encoding could not represent the dash. Somebody debugging a
red check at the end of a long session should be reading the fix, not wondering whether the mangled
character is part of the error. The smallest fix is the one in the file above: **the check's output
is ASCII**, and the colon does the dash's job.

## In production

**What a senior writes instead.** The same four questions behind a single command everybody knows —
`./run check` — rather than a filename to remember, and the same command in CI so it runs on a
machine that has never been set up by hand. Day 1 builds that driver, and this file becomes the
first thing it calls. The other senior habit is already here: **the check refuses rather than
warns.** A warning is a red that somebody has to notice.

**What degrades at scale.** A check that runs on one developer's machine catches the mistakes that
developer makes. This desk ends up running in a container, beside a boundary process, with a CI job
running its evalset — and the failure that hurts is the one where the container's interpreter is a
patch version away from the one the desk was written against and nobody looks until behaviour
differs on a claim. Four checks now becomes a dozen by day 19, and the shape they are written in
here — a name, a boolean, a message that names the fix — is what makes adding the twelfth one a
line rather than a refactor.

**The review comment.** *"This check prints the first four characters of the key to prove it is
set. Delete that — 'set' and 'not set' is the whole answer, and a prefix in a CI log is still a
secret in a CI log."*

**The interview question.** *"Your setup check passes on every machine in the team and the service
still breaks on deploy. Name three things a check like this cannot see, and say which of them you
would add first."*
