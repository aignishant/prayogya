## One-line answer

`SETUP.md` is every command from a bare machine to a green check, written as a listing rather than
a lesson, and it is only true once somebody has followed it in an empty folder and watched it go
green.

## The idea

The insurer opens a second intake counter at a branch office. Same work, same forms, same drawer
rules — and nobody from the first counter is going to be standing there on the Monday it opens. All
that travels is a folder of instructions.

The first version of that folder is always written by someone who already knows. It says "set up
the till", which means seven things they do without thinking. It says "the usual forms". It assumes
a key that was cut years ago and lives on a hook the writer has never had to describe. Every line
is true and the folder does not work, and the way that is discovered is not by reading it. It is by
handing it to somebody who has never seen the first counter and watching where they stop.

`SETUP.md` is that folder for this project, and this part writes it and then does the handing-over.

The distinction that keeps it useful: **day 0 is the lesson and `SETUP.md` is the listing.** They
cover the same ground on purpose. The lesson explains why the ignore file is written before the
secret exists; the listing says write the ignore file, then the example, in that order. A reader
setting up this desk for the second time, on a new machine, does not want the reasoning again —
they want the commands, in order, with nothing missing. A reader setting it up for the first time
wants both, and the listing is what they will come back to.

One rule governs the whole file, and it is the one that is always broken first: **no step may be
"as you did before", and no step may assume a machine somebody else prepared.** Every command from
nothing. That is what makes it checkable, and being checkable is the only thing that keeps a setup
document from rotting.

## The mechanism

The whole file, at the root of the project:

````markdown
# Setup — bare machine to green check

Every command from a machine with nothing on it to `claims desk: ready`. Nothing here is assumed
and nothing here is optional. Day 0 is the lesson behind these commands; this file is the listing,
for a reader in a hurry or for the same reader on a new machine six months from now.

Commands are written for a POSIX shell (Git Bash on Windows, or any shell on macOS and Linux).
Where PowerShell differs, the PowerShell form is given underneath.

## 1 · The two tools this project needs

`uv` owns the interpreter and, from day 1, the environment. `git` owns the history.

```bash
uv --version
git --version
```

If `uv` is not installed, the install commands are at <https://docs.astral.sh/uv/getting-started/installation/>.
Whatever version you get, write it into `PACKAGES.md` with today's date. A version nobody wrote
down is a version nobody can reproduce.

## 2 · The folder, and the interpreter it runs on

```bash
mkdir claims-intake-desk
cd claims-intake-desk
uv python pin 3.12.12
cat .python-version
uv run python -V
```

Expect `.python-version` to hold `3.12.12`, and `uv run python -V` to print `Python 3.12.12`.
`uv` downloads that interpreter if the machine does not already have it.

`python -V` on its own may print something else entirely. That is not a problem to fix; it is the
reason this project pins.

## 3 · The repository

```bash
git init
git config user.name "your name"
git config user.email "you@example.com"
```

If `git init` prints a hint about `master`, set the default once and re-run it in a fresh folder:

```bash
git config --global init.defaultBranch main
```

## 4 · The files day 0 writes, in this order

The full contents of each are printed by day 0. The order is not decoration — `.gitignore` is
written **before** `.env` exists, because an ignore rule speaks only about paths git has never
been told to hold.

| Order | File | What it is |
| --- | --- | --- |
| 1 | `PROJECT.md` | the brief: what this desk is, its tools, its cast, its boundary, and what "done" means |
| 2 | `PACKAGES.md` | every version this project depends on, with the date it was observed |
| 3 | `.gitignore` | the paths git must never be told to hold, written before any of them exist |
| 4 | `.env.example` | the names the desk expects in its environment, with no values |
| 5 | `check.py` | the four questions this file's last section asks |

Commit as you go. One day, one commit is the habit; on day 0 the commits are smaller than that,
because `.gitignore` must land in the history before `.env` lands on disk.

## 5 · The key

The desk answers claims with a Gemini model on an AI Studio key.

1. Get a key at <https://aistudio.google.com/apikey>.
2. `cp .env.example .env` (PowerShell: `Copy-Item .env.example .env`).
3. Open `.env` and put the key after `GOOGLE_API_KEY=`.

Setting `GOOGLE_API_KEY` alone is what selects the AI Studio path. Nothing else goes in that file
yet. `.env` is ignored by `.gitignore`, has no place in any commit, and never leaves your machine.

What the free tier allows is not published as a number: AI Studio shows your own limits at
<https://aistudio.google.com/rate-limit>. Read them there rather than trusting a number written
down anywhere, including here.

## 6 · The green check

```bash
uv run python check.py
```

```text
ok   interpreter       interpreter 3.12.12, as pinned in .python-version
ok   ignore rule       git ignores .env, by the rule at .gitignore:8:.env
ok   secret untracked  .env is not tracked by git
ok   key present       1 name(s) from .env.example set in .env, none printed here

claims desk: ready
```

Exit status 0 is the verdict; the lines are for you. If any line starts with `RED`, it names the
smallest fix. Run it with `uv run`, not with a bare `python`: the bare name is whichever
interpreter your machine finds first, and the first check exists to say so.
````

**Line by line:**

- **`# Setup — bare machine to green check`** — the title states both endpoints. A setup document
  that does not say where it starts is the one that assumes your machine already has half of it.
- **"Nothing here is assumed and nothing here is optional."** — the promise being made, in the
  second sentence, so that a reader who finds an assumed step knows they have found a bug rather
  than a gap in their own knowledge.
- **"Day 0 is the lesson behind these commands; this file is the listing"** — says why the same
  ground is covered twice and stops the two documents competing. It also tells a returning reader
  which of the two to open.
- **"Commands are written for a POSIX shell … the PowerShell form is given underneath"** — stated
  once, at the top, rather than doubling every block. The reader on Windows now knows what to
  expect, and the one place the two genuinely differ (`cp` versus `Copy-Item`) carries both.
- **Section 1, the two tools** — `uv --version` and `git --version` are here as the first commands
  because they are the only two things this project cannot install for you. The install link is a
  link, not a copied command: an install line for somebody else's tool goes stale in the one file
  nobody re-reads.
- **"write it into `PACKAGES.md` with today's date"** — the setup document tells the reader to
  record what *their* machine said, not to match what this one said. Two people on two machines
  will have two different `PACKAGES.md` files and both will be correct.
- **Section 2, `mkdir` then `cd` then `uv python pin`** — the folder before the pin, because
  `.python-version` is created in the working directory and a pin written one level up governs
  everything beneath it. The order is the fix for a failure that is otherwise very hard to see.
- **"`python -V` on its own may print something else entirely. That is not a problem to fix"** —
  heads off the reader who tries to make the two agree by uninstalling something. The gap is the
  normal state of a machine, and the pin is how the project stops caring about it.
- **Section 3, `git init` and the identity** — the two `git config` lines are here rather than left
  to a first failing commit, because a document that lets you hit an avoidable error and then
  explains it has wasted the reader's attention on a thing it could have prevented.
- **"If `git init` prints a hint about `master`"** — conditional, because it depends on the
  reader's git configuration and not on this project. It says what to do and it does not pretend to
  know which case they are in.
- **Section 4, a table of five files in order** — the listing names the files and the order, and
  points at day 0 for their contents rather than duplicating them. A file's contents live in
  exactly one place in this project, and duplicating them here would guarantee two versions.
- **"`.gitignore` must land in the history before `.env` lands on disk"** — the one line of
  reasoning kept in the listing, because it is the one that decides an ordering the reader would
  otherwise change for convenience.
- **Section 5, the key, as three numbered steps** — get, copy, fill. Step 3 says to open the file
  in an editor rather than to echo the key into it, which keeps it out of shell history.
- **"Read them there rather than trusting a number written down anywhere, including here"** — the
  document explicitly refuses to quote a rate limit. Limits move, documents do not, and a stale
  number in a setup file is worse than no number, because it will be believed.
- **Section 6, the green check with its expected output** — the endpoint is a specific, quotable
  screen. That is what makes this document testable: a reader can tell whether they are done
  without asking anybody.
- **The closing sentence about `uv run`** — the one mistake most likely to produce a red on a
  correct setup, answered where the red would appear.

Now the part that makes it true. Follow it in a **second, empty folder**, on the same machine, as
if you had never seen this project: pin, `git init`, put the five files in, copy `.env.example` to
`.env`, fill in the key, and run the check.

```bash
uv run python check.py
echo "exit=$?"
git status --short --untracked-files=all
```

```
ok   interpreter       interpreter 3.12.12, as pinned in .python-version
ok   ignore rule       git ignores .env, by the rule at .gitignore:8:.env
ok   secret untracked  .env is not tracked by git
ok   key present       1 name(s) from .env.example set in .env, none printed here

claims desk: ready
exit=0
```

**Line by line:**

- **A second folder, not the one you built in** — the folder you built in has state you cannot see:
  a pin you set earlier, a git identity, a file you created and forgot. The only way to test a
  setup document is somewhere it has never run.
- **`claims desk: ready` on the first try** — the four questions were answered by a folder that was
  empty a moment ago, which is the strongest claim this document can make about itself.
- **`git status --short --untracked-files=all` printing nothing at all** — no untracked files, and
  in particular no `.env`, in a repository where every file was added with `git add -A`. The ignore
  rule was in place before the secret existed, in the correct order, in a fresh repository — the
  whole of section 2 of this day, verified by a command that prints silence.

## When it breaks

Follow the listing and skip one line — `git init`, the easiest to skip, because a folder without a
repository looks exactly like a folder with one:

```text
ok   interpreter       interpreter 3.12.12, as pinned in .python-version
RED  ignore rule       .env is NOT ignored by git: one `git add -A` away from a leaked key
ok   secret untracked  .env is not tracked by git
ok   key present       1 name(s) from .env.example set in .env, none printed here

claims desk: 1 check(s) red
```

What git itself says in that folder is `fatal: not a git repository (or any of the parent
directories): .git`, and the check never shows you that line, because it captures git's output and
prints its own. Someone followed the setup on a new laptop, hit one red line about an ignore rule,
and went looking at `.gitignore` — which was perfect. The smallest fix is `git init`. **And note
the third line: `secret untracked` says `ok` in a folder with no repository at all**, which is the
false green left as a rep in part 3.1. This is what it looks like from the outside.

## In production

**What a senior writes instead.** They stop writing the steps and write the script — a bootstrap
command, or a container that already has the tools — because a listing degrades every time somebody
changes a step and does not update it. The reason this project keeps the listing anyway is that a
script is only trustworthy if you already know what it does, and on day 0 you are the person who
needs to know. The senior habit worth taking from here is not the file, it is the test: **the
document is followed, cold, in an empty folder, by someone who did not write it.** Day 19 does
exactly that with a cold clone of the whole desk, and that run is the one that decides whether this
project is finished.

**What degrades at scale.** A setup document is read once per person per machine and edited never.
On a team of six with laptops, a CI runner and a container image, the same five steps exist in four
places, and they drift apart in the order they are least visible: the container is right because it
fails loudly, CI is right because it fails loudly, and the document is wrong for months because it
only fails for new joiners, one at a time, quietly, in their first week. The mitigation is the same
test: follow it cold whenever anything in it changes.

**The review comment.** *"Step 2 says 'install the dependencies as usual'. Which command, with
which tool, and what does it print when it works? If I have to ask, the next person will not — they
will guess."*

**The interview question.** *"How do you know your project's setup instructions are correct today?
Not whether they were correct when written — how would you find out, this afternoon, without
asking a teammate?"*
