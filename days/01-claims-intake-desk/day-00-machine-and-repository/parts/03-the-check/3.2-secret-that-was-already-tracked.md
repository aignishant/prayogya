## One-line answer

Track `.env` once and the ignore rule stops applying to it entirely — the check goes red, the fix
is one command, and the key in the history stays readable forever, so the real fix is to rotate it.

## The idea

The counter keeps a bound register. Every notification that comes in gets a line: time, policy
number, what the caller said. The pages are sewn in, and that is on purpose — a register you can
tear a page out of is not evidence of anything.

One afternoon a clerk writes a caller's card number into the description field, because the caller
read it out and the clerk was writing down everything the caller said. The mistake is noticed
immediately. And the register does what it was built to do: nothing can be removed. The line gets
struck through, a note is added, and the number is still there, still legible, under a single
horizontal line, for as long as the register exists.

A git history is that register. This is a feature — a repository whose past can be quietly edited
would be useless for exactly the audit question this project ends up answering on day 14. But it
means a secret committed once is a secret committed permanently, in every clone anyone ever made,
and the correct response is not to try to erase it.

This part causes that on purpose, watches the check catch it, and then does both halves of the fix
— the one that stops it recurring, and the one that actually protects the key.

There is one mechanism here worth arriving at slowly, because almost everybody gets it wrong the
first time. **Ignore rules and tracking are not two names for the same thing.** An ignore rule is
git's answer to "should I mention this path to you?" — and it is only ever asked about paths git is
not already holding. Tracked wins, always, and silently. The rule text does not change, the
`.gitignore` file does not change, and yet the answer to "is `.env` ignored?" flips from yes to no
the moment the file is staged.

## The mechanism

Force the file in, the way a hurried `git add -f` or an editor's "stage all" button would:

```bash
git add -f .env
git status --short
```

```
warning: in the working copy of '.env', CRLF will be replaced by LF the next time Git touches it
A  .env
```

**Line by line:**

- `git add -f .env` — `-f` is `--force`, and it exists precisely to override ignore rules. Without
  it, git refuses and tells you the path is ignored. With it, git does what you said. The rule was
  never a lock; it was an answer to a question, and `-f` stops asking.
- The **CRLF warning** is about line endings, not about the secret: this machine's git is
  configured to store LF in the repository and the file on disk has Windows line endings. It is
  noise here, and it is worth recognising because it appears on almost every file you add on
  Windows and has nothing to do with what you are adding.
- `A  .env` — staged as a new file. The path is now **tracked**: git is holding it for the next
  commit. Everything after this line follows from that one word.

Now ask the two questions that used to have the same answer:

```bash
git check-ignore -v .env
echo "exit=$?"
git ls-files --error-unmatch .env
echo "exit=$?"
```

```
exit=1
.env
exit=0
```

**Line by line:**

- `git check-ignore -v .env` prints **nothing** and exits 1. In part 2.2 the same command on the
  same file in the same repository printed `.gitignore:8:.env` and exited 0. Not one character of
  `.gitignore` has changed. The file is tracked, so git no longer considers it ignorable, and the
  ignore machinery has no opinion left to give.
- **Silence plus exit 1 is the answer.** This is why part 2.2 insisted the verdict is the exit
  status: a human skimming this output sees an empty line and moves on, and a program reading `$?`
  sees the alarm.
- `git ls-files --error-unmatch .env` prints the path and exits 0 — git is holding it.
  `--error-unmatch` is what makes the negative case a non-zero exit instead of empty output, which
  is what makes this usable as a check.
- **Together they are the whole failure**: the ignore rule that looks correct in the file, and the
  tracking that overrides it. Neither command alone would have told you.

Commit it, because that is what actually happens — the file was staged by a sweep and the commit
was about something else entirely:

```bash
git commit -m "P01 day 0: add env"
uv run python check.py
echo "exit=$?"
```

```
[main e5aac47] P01 day 0: add env
 1 file changed, 9 insertions(+)
 create mode 100644 .env

ok   interpreter       interpreter 3.12.12, as pinned in .python-version
RED  ignore rule       .env is NOT ignored by git: one `git add -A` away from a leaked key
RED  secret untracked  .env is TRACKED: an ignore rule cannot reach a path git already holds
ok   key present       1 name(s) from .env.example set in .env, none printed here

claims desk: 2 check(s) red
exit=1
```

**Line by line:**

- `1 file changed, 9 insertions(+)` — nine lines, one of which is the key. The commit message says
  nothing about a secret, which is exactly how this survives review.
- **Two checks go red, and they are the two that ask about different things.** The `ignore rule`
  check is red because `check-ignore` now exits 1. The `secret untracked` check is red because
  `ls-files` now exits 0. Written as one check, this would have produced one line and half the
  diagnosis.
- **The interpreter and key checks are still green**, and that is the right behaviour: they were
  not affected, and a check that fails everything when one thing is wrong tells you nothing about
  where to look.
- `exit=1` — non-zero, so anything reading the status stops here. On day 19 that is CI refusing to
  build.

The fix, in one command:

```bash
git rm --cached .env
git status --short
git commit -m "P01 day 0: stop tracking .env"
uv run python check.py
```

```
rm '.env'
D  .env

[main c57e829] P01 day 0: stop tracking .env
 1 file changed, 9 deletions(-)
 delete mode 100644 .env

ok   interpreter       interpreter 3.12.12, as pinned in .python-version
ok   ignore rule       git ignores .env, by the rule at .gitignore:8:.env
ok   secret untracked  .env is not tracked by git
ok   key present       1 name(s) from .env.example set in .env, none printed here

claims desk: ready
```

**Line by line:**

- `git rm --cached .env` — removes the path from the staging area and **leaves the file on disk**.
  Without `--cached`, `git rm` deletes your working copy too, and on this file that means deleting
  your only copy of the key. The flag is the whole command.
- `D  .env` — staged as a deletion. The next commit records that this path is no longer tracked.
- `1 file changed, 9 deletions(-)` — from git's point of view the file was removed from the project.
  From your point of view nothing was removed: `.env` is still sitting there, still holding the key.
- **The check is green again, all four lines.** The ignore rule started applying the instant the
  path stopped being tracked — the rule never changed, its applicability did.

## When it breaks

Here is the part that catches people: the green check does not mean the key is safe.

```bash
git log --oneline --all -- .env
git show e5aac47:.env
```

```text
c57e829 P01 day 0: stop tracking .env
e5aac47 P01 day 0: add env

# Claims Intake Desk — the shape of .env, with no value in it.
#
# Copy this file to .env and fill the value in. .env is ignored and never leaves your machine;
# this file is committed, and it is the only place a new reader can learn which names the desk
# expects to find in its environment.

# The key the desk answers claims with. Get one at https://aistudio.google.com/apikey
# Setting this name alone is what selects the AI Studio path. Nothing else is needed here.
GOOGLE_API_KEY=AIzaSyFAKE-KEY-FOR-DAY-ZERO-000000000000
```

Two commits mention the path, and the older one still hands over the whole file — comment about
never leaving your machine included, key included — to anybody with a clone, including anybody who
cloned it before the removal. Somebody force-added an env file on a Friday, untracked it that same
afternoon, saw the check go green, and told the team it was handled; the key stayed valid for
another month and was in every fork the whole time. **The
smallest fix is not a git command. It is rotating the key** at
<https://aistudio.google.com/apikey>: delete the exposed one, create a new one, put it in `.env`.
The commit stays in the register with a line through it, and the value it holds stops being worth
anything.

## In production

**What a senior writes instead.** They do not rely on remembering `-f` is dangerous. They add a
secret scanner to CI that fails on a committed credential, and they write the rotation procedure
down before it is needed — which key, where it lives, who can issue a new one, what breaks while
it is being replaced. The rewriting tools exist and have their place for a repository that has not
been shared, but on anything with clones, rotation is the fix and history surgery is theatre:
every clone, fork and CI cache already has the old object.

**What degrades at scale.** One key on one desk is a contained problem. This project's cast is five
agents on one shared key, and by day 19 it is running in a container with the key injected by the
platform — at which point "rotate the key" means a coordinated change across a running service, a
compose file and a CI secret, while an intake queue keeps arriving. Insurers measure that window in
claims, not in commits: a Monday-morning burst of several hundred notifications does not pause
while a credential is replaced. The cheap moment is now, on day 0, writing the rule before the file
exists.

**The review comment.** *"This PR untracks `.env` and the diff shows the key. Rotating it is not a
follow-up ticket — the value is public from the moment this branch was pushed, and the PR page
itself is now one of the places it is published."*

**The interview question.** *"A credential was committed to a repository that has been cloned by
the team and mirrored by CI. Walk me through what you do, in order, and say which step actually
reduces the risk."*

## Check yourself

- **Run:** the whole arc, on your own desk — `git add -f .env`, `uv run python check.py` (expect
  two red lines and exit 1), then `git rm --cached .env`, commit, and run the check again (expect
  `claims desk: ready`). A check you have watched go red is the only kind worth having.
- **Say out loud:** `.gitignore` was not edited at any point in this part, yet
  `git check-ignore -v .env` changed its answer twice. What is it actually reporting on, and what
  does that tell you about when an ignore rule has to be written?
