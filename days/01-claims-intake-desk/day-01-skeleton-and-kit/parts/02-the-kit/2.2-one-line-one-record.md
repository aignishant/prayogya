## One-line answer

Every line this desk writes is one JSON object, so a run can be filtered and counted months later,
and any field whose *name* looks like a secret is replaced before the line is written.

## The idea

The adjuster's pad has boxes on it. Policy number in this box, date of loss in that one, the
description in the ruled area at the bottom. It is not a prettier way of writing a paragraph — it
is what lets the branch pull every water-damage claim from March without reading a single one of
them.

The alternative is on the back of the pad, where adjusters write themselves notes in sentences.
Those notes are often better written and they are useless in aggregate, because "third party
present" and "TP at scene" and "neighbour was there" are the same fact and nothing can tell.

Logs have the same two forms. **Structured logging** is writing one machine-readable object per
line — here one JSON object — rather than a sentence assembled for a human, so a run's log can be
filtered, counted and diffed months later without a parser anybody maintains. It is the pad with
boxes.

This desk needs it for a specific reason that arrives on day 17: by then a single notification will
have passed through five agents and a boundary process, and the question "what happened to claim
SYN-4471" will have to be answerable from the log alone. A sentence per step cannot answer it. A
field called `claim` on every line can.

And there is a second job, which is why this module exists rather than a one-line `print`. A claims
desk writes about policyholders and calls a provider with a key. **Redaction** is removing a value
from a log record before it is written, decided by the field's name rather than by its contents,
and done at the writer so that no call site has to remember. Every call site *will* forget. That is
not a criticism of anyone; it is what happens across a project with dozens of log lines and a
deadline.

## The mechanism

The whole file, at `claims_desk/util/logging.py`:

```python
"""One JSON object per line, on standard error, with secrets redacted by field name.

A claims desk writes about policyholders. Every line this module emits is machine-readable, so a
run can be filtered and counted months later, and nothing that looks like a secret survives the
trip to the page.
"""

from __future__ import annotations

import json
import sys
from datetime import UTC, datetime
from typing import Any

REDACTED = "<redacted>"
SECRET_HINTS = ("key", "token", "secret", "password", "authorization", "credential")


def looks_secret(name: str) -> bool:
    """Does this field name suggest its value must not be written down?"""
    lowered = name.lower()
    return any(hint in lowered for hint in SECRET_HINTS)


def redact(fields: dict[str, Any]) -> dict[str, Any]:
    """A copy of `fields` with every secret-looking value replaced, at any depth."""
    clean: dict[str, Any] = {}
    for name, value in fields.items():
        if looks_secret(name):
            clean[name] = REDACTED
        elif isinstance(value, dict):
            clean[name] = redact(value)
        else:
            clean[name] = value
    return clean


def log(event: str, **fields: Any) -> dict[str, Any]:
    """Write one redacted JSON record and return it.

    Returning the record is what makes redaction testable without capturing a stream.
    """
    record = {
        "ts": datetime.now(UTC).isoformat(timespec="milliseconds"),
        "event": event,
        **redact(fields),
    }
    print(json.dumps(record, default=str), file=sys.stderr, flush=True)
    return record
```

**Line by line:**

- `from datetime import UTC, datetime` — `UTC` is a name the standard library gained in 3.11, and
  this project pins 3.12, so it is available. It replaces the older `timezone.utc` spelling, and
  the linter's `UP` rules would ask for this one anyway.
- `REDACTED = "<redacted>"` — a constant, not a literal repeated three times, so a test can assert
  against the same name the writer uses and neither drifts.
- `SECRET_HINTS = ("key", "token", "secret", "password", "authorization", "credential")` — a
  tuple of **substrings**, checked against the lowercased field name. `api_key`, `API_KEY`,
  `provider_key` and `authorization` all match; so does `keyring`, which is a false positive this
  file accepts on purpose. **When the choice is between redacting something harmless and printing
  something dangerous, the harmless loss is the cheap one.**
- `def looks_secret(name)` — a named function rather than an inline condition, because it is the
  one rule in this module a reviewer will want to argue with, and it should be findable.
- `def redact(fields)` — builds a **copy**. The caller's dictionary is not modified: a log call
  must not change the data the program is working on, and a redaction that mutated its input would
  do exactly that on a shared structure.
- `elif isinstance(value, dict): clean[name] = redact(value)` — **recursion, one line.** Nested
  structure is how secrets actually reach a log: not as `api_key=` at the top level, but three
  levels down inside a request object somebody logged whole.
- `else: clean[name] = value` — everything else passes through untouched. Note what this does *not*
  do: it does not walk lists, so a secret inside a list of dictionaries survives. That is a real
  limit, it is left as a rep in the hub §5, and naming it here is better than pretending the
  recursion is complete.
- `def log(event: str, **fields: Any)` — the event name is positional and everything else is a
  keyword. That shape is what makes call sites read like the record they produce:
  `log("policy.fetched", policy="SYN-4471", in_force=True)`.
- `"ts": datetime.now(UTC).isoformat(timespec="milliseconds")` — **UTC, always, and in ISO 8601.**
  A claims desk's log will one day be read next to a provider's log and a container's log, and
  local time is how two records an hour apart look simultaneous. `timespec="milliseconds"` keeps
  the line short and is still finer than anything this desk does.
- `"event": event` — a dotted name like `policy.fetched` rather than a sentence. It is the field
  everything else is grouped by, and a controlled vocabulary is what makes counting possible.
- `**redact(fields)` — the caller's fields are merged after `ts` and `event`, so those two are
  always first in the line. A field called `event` in the caller's arguments would overwrite the
  event name, which is a sharp edge worth knowing about and not worth code to prevent.
- `json.dumps(record, default=str)` — `default=str` is what stops a log call crashing the desk when
  somebody passes a `datetime`, a `Path` or an exception. **A logger that raises has turned an
  observation into an outage.**
- `file=sys.stderr` — logs go to standard error, so standard output stays free for a program's
  actual result. On day 3 this becomes load-bearing rather than tidy: the boundary process speaks a
  protocol over standard output, and a stray log line there would corrupt it.
- `flush=True` — a crash should not take the last few log lines with it.
- `return record` — the record, so a test can assert on redaction without capturing a stream, and
  so a caller can attach it to something. Returning what you wrote is the cheapest testability
  there is.

Call it with something that matters and something that must not appear:

```bash
uv run python -c "
from claims_desk.util import logging as desk_logging
desk_logging.log('policy.fetched', policy='SYN-4471', api_key='AIzaSy-not-a-real-key',
                 provider={'name': 'test-double', 'auth_token': 'also-not-real'})
"
```

```
{"ts": "2026-09-10T11:02:33.749+00:00", "event": "policy.fetched", "policy": "SYN-4471", "api_key": "<redacted>", "provider": {"name": "test-double", "auth_token": "<redacted>"}}
```

**Line by line:**

- `"ts"` and `"event"` lead the record, in that order, on every line this desk will ever write.
- `"policy": "SYN-4471"` — a synthetic policy number, passed straight through. This is the field
  day 17 greps for.
- `"api_key": "<redacted>"` — the name matched `key`, so the value never reached the page.
- `"provider": {"name": "test-double", "auth_token": "<redacted>"}` — **the nested one, which is
  the case worth checking.** `auth_token` is two levels down and contains `token`, so `redact`
  recursed into the dictionary and replaced it. `name` beside it is untouched, which is how you can
  tell the recursion is selective rather than blanket.
- **Read the line, not the function.** The way anybody establishes that redaction works is by
  looking at what was actually written; a function that appears to redact and a line that contains
  a key are indistinguishable until you print one.

## When it breaks

The redactor decides by name, so a secret under an innocent name walks straight through:

```
{"ts": "2026-09-10T10:55:31.972+00:00", "event": "policy.fetched", "policy": "SYN-4471", "api_key": "<redacted>", "note": "the key is AIzaSy-not-a-real-key"}
```

Verbatim, from this project's own logger. `api_key` was caught. `note` was not, and it contains the
same key. Somebody added a debugging line during an incident, put the whole request into a field
called `note`, and shipped it; the redaction was working perfectly the entire time. The smallest
fix is to delete the field. The real lesson is the shape of the guarantee: **name-based redaction
protects you from forgetting, not from deciding.** If you put a secret in a field called `note`,
you decided.

## In production

**What a senior writes instead.** The standard library's `logging` module with a JSON formatter and
a redacting filter, so that third-party libraries' log records go through the same treatment —
because the line that leaks the key is very often not one you wrote. This file is smaller than that
on purpose: it is twenty lines you can read, and it is enough for a desk whose whole cast is five
agents. The judgement worth taking forward is that redaction belongs **at the writer**. A rule
enforced at forty call sites is forty chances to forget.

**What degrades at scale.** One JSON object per line is a format that survives being thousands of
lines long. A single notification through this desk will produce a line per agent, per tool call
and per boundary hop — call it a dozen — so a Monday batch of five hundred notifications is six
thousand lines, and the only question anybody asks of them is "show me claim SYN-4471". Structured
means that is one filter. Sentences mean it is a morning.

**The review comment.** *"This logs the whole notification object on every step. Log the claim
reference and the fields you branched on — the description is free text a policyholder typed, and
you are about to put it in a log that is retained for seven years."*

**The interview question.** *"Your logger redacts fields whose names look sensitive. Name two ways
a secret still reaches your logs, and say which one you would defend against first."*
