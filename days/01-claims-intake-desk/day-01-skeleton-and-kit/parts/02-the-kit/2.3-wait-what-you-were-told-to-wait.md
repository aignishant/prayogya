## One-line answer

A retry doubles its wait only when nobody has told it what to wait, prefers the interval the other
side actually asked for, and re-raises rather than returning a substitute answer when the attempts
run out.

## The idea

The adjuster needs a policy detail and the underwriting desk is on another call. The right thing
is to ring back. The wrong thing has two versions, and both happen.

The first is ringing back immediately, over and over, while the other desk is trying to deal with
the queue that made them busy in the first place. The second is worse and quieter: writing "cover
appears to be in force" in the claim file because the call could not be completed and the file had
to go out today. Nobody decided to invent that. It arrived as a small accommodation under time
pressure, and it is now a statement about a policy that no one checked.

This part is the code that rings back properly. Three terms:

- A **transient failure** is one worth trying again — the other side was busy, a connection
  dropped, a rate limit was hit. It is distinguished from a permanent failure, which will fail
  identically forever, and telling them apart is the caller's job, not this module's.
- **Exponential backoff** is doubling the wait between attempts — one second, two, four — so that a
  service under load is not hit by every client at the same cadence.
- **`Retry-After`** is the header a provider uses to say how long to wait. When it is present, it
  is not advice, and it always beats arithmetic: a service that says "sixty seconds" knows
  something about its own recovery that your doubling does not.

The rule underneath all of it, and the one this project will not bend: **nothing here ever returns
a substitute answer.** A claims desk that invents an in-force date because the provider was busy
has not degraded gracefully. It has made something up about a policy, and it has done it in a
system whose whole purpose is deciding whether to pay.

## The mechanism

The whole file, at `claims_desk/util/backoff.py`:

```python
"""Honest retry: wait what you were told to wait, and escalate when the attempts run out.

Nothing in here ever returns a substitute answer. A claims desk that invents an in-force date
because the provider was busy has not degraded gracefully; it has made something up about a
policy.
"""

from __future__ import annotations

import time
from collections.abc import Callable, Iterator


class Transient(Exception):
    """A failure worth trying again.

    `retry_after` is the interval the other side asked for, in seconds, or `None` when it did not
    say. A provider's own instruction always wins over our arithmetic.
    """

    def __init__(self, message: str, retry_after: float | None = None) -> None:
        super().__init__(message)
        self.retry_after = retry_after


def delays(attempts: int = 4, base: float = 1.0) -> Iterator[float]:
    """The waits between attempts: base, 2x base, 4x base ...

    One fewer than `attempts`, because the last attempt is not followed by a wait — it is
    followed by the exception reaching the caller.
    """
    for step in range(max(attempts - 1, 0)):
        yield base * (2**step)


def retry[T](
    call: Callable[[], T],
    *,
    attempts: int = 4,
    base: float = 1.0,
    sleep: Callable[[float], None] = time.sleep,
    on_wait: Callable[[int, float, Transient], None] | None = None,
) -> T:
    """Call `call` until it returns, or re-raise its last `Transient` after `attempts` tries.

    `sleep` is a parameter so a test can watch the schedule without living through it. `on_wait`
    is called before each wait with the attempt number, the interval and the failure, which is
    where a caller puts its log line.
    """
    waits = list(delays(attempts, base))
    for attempt in range(1, attempts + 1):
        try:
            return call()
        except Transient as failure:
            if attempt == attempts:
                raise
            wait = failure.retry_after if failure.retry_after is not None else waits[attempt - 1]
            if on_wait is not None:
                on_wait(attempt, wait, failure)
            sleep(wait)
    raise AssertionError("unreachable: the loop above either returns or raises")
```

**Line by line:**

- `class Transient(Exception)` — **the only exception this module retries.** Anything else
  propagates on the first attempt, which is correct: a `TypeError` in your own code will happen
  four times in a row and the fourth traceback is no more informative than the first.
- `def __init__(self, message, retry_after=None)` — the interval rides on the exception rather than
  being returned separately, because it belongs to the failure. Whoever raises it — the code that
  read the provider's `Retry-After` header — is the only place that knows the number.
- `retry_after: float | None` — `None` means "not told", which is a different state from `0`
  ("try again immediately"). Collapsing those two into one is how a client ends up hammering a
  service that asked for a pause.
- `def delays(attempts=4, base=1.0) -> Iterator[float]` — the schedule as its own function, so it
  can be read and tested without running a retry. Separating "what are the waits" from "do the
  waiting" is what makes the next part's assertion a single line.
- `for step in range(max(attempts - 1, 0)): yield base * (2**step)` — **one fewer than the
  attempts.** Four attempts have three gaps. The `max(..., 0)` handles `attempts=1`, which is a
  legitimate way to say "try once, do not retry" and would otherwise produce a negative range.
- `base * (2**step)` — 1, 2, 4 with the default base. The doubling is the fallback, not the
  policy: it applies only when nobody said otherwise.
- `def retry[T](...)` — the square brackets are the type-parameter syntax this project's pinned
  Python supports, and they say that `retry` returns whatever `call` returns. It is here because
  the linter asked for it: with `target-version = "py312"` set in `pyproject.toml`, ruff's `UP047`
  flagged the older `TypeVar` spelling and named the replacement.
- `*` before the keyword arguments — everything after it must be named at the call site. `retry(f,
  4, 1.0)` is unreadable; `retry(f, attempts=4)` says what the four is.
- `sleep: Callable[[float], None] = time.sleep` — **the most valuable line in the file.** The
  waiting is a parameter, so a test can pass `list.append` and get the schedule as data instead of
  living through it. A retry loop that hard-codes `time.sleep` can only be tested by a test that
  takes seven seconds, so in practice it is not tested.
- `on_wait: Callable[[int, float, Transient], None] | None = None` — a hook called before each
  wait, with the attempt number, the interval and the failure. This module does not import the
  logger: it hands the caller the facts and lets them decide what to record. A utility that logs on
  its own behalf is a utility that logs in somebody else's format.
- `waits = list(delays(attempts, base))` — materialised once, outside the loop, so the generator is
  not restarted and the indexing below is honest.
- `for attempt in range(1, attempts + 1)` — one-based, because every message this produces is read
  by a person: "attempt 3 of 4" and not "attempt 2 of 4".
- `try: return call()` — the success path returns from inside the loop. There is no result variable
  and no flag; the only way out with a value is a call that worked.
- `if attempt == attempts: raise` — **bare `raise`, on the last attempt.** It re-raises the
  original exception with its original traceback, so the caller sees where it actually failed. This
  is the escalation, and it is three words: no fallback value, no `None`, no logged-and-swallowed.
- `wait = failure.retry_after if failure.retry_after is not None else waits[attempt - 1]` — the
  precedence rule in one line. **`is not None`, not truthiness**, so a `retry_after` of `0` means
  zero rather than falling through to the doubling.
- `if on_wait is not None: on_wait(attempt, wait, failure)` — before the sleep, not after, so a log
  line appears at the moment the desk goes quiet rather than when it wakes up.
- `raise AssertionError("unreachable: ...")` — the loop always returns or raises, and this line
  exists to say so out loud. If it ever executes, the loop's logic has changed and this is a better
  outcome than silently returning `None`.

Watch the schedule without living through it, by passing a `sleep` that only records:

```bash
uv run python -c "
from claims_desk.util.backoff import Transient, retry
waited = []
n = {'i': 0}
def flaky():
    n['i'] += 1
    if n['i'] < 4:
        raise Transient(f'503 from the policy service (attempt {n[\"i\"]})')
    return 'in force on 2026-03-14'
print(retry(flaky, attempts=4, sleep=waited.append))
print('waited:', waited)
"
```

```
in force on 2026-03-14
waited: [1.0, 2.0, 4.0]
```

**Line by line:**

- `sleep=waited.append` — the injected sleep, and it is a one-word test double: a bound method that
  takes a float and records it. Nothing waited; the schedule is now a list you can assert on.
- `waited: [1.0, 2.0, 4.0]` — three waits before the fourth attempt succeeded. The doubling, in the
  order it happens, with no `Retry-After` in play because this failure did not carry one.
- `in force on 2026-03-14` — the real answer, from the attempt that worked. The point of the whole
  module is that this string came from the policy service and not from a default.

## When it breaks

When the attempts run out, the desk stops:

```
Traceback (most recent call last):
  File "<string>", line 5, in <module>
  File "...\claims_desk\util\backoff.py", line 53, in retry
    return call()
           ^^^^^^
  File "<string>", line 4, in busy
claims_desk.util.backoff.Transient: 429 from the policy service
```

The path is shortened; the rest is verbatim. Note what the traceback points at: `return call()`,
inside `retry`, and then the caller's own function. The bare `raise` kept the original traceback,
so the failure still says where it happened rather than pointing at the retry machinery. Somebody
saw this at the end of a batch run and wanted to make it go away by adding `except Transient:
return "in force"` at the call site — which would have turned a visible outage into eight
fast-tracked claims on policies nobody checked. The smallest correct fix is to let it reach the
top: a claim that cannot be decided is not a claim that can be decided badly.

## In production

**What a senior writes instead.** The same loop with **jitter** — a random fraction added to each
wait — because a hundred clients that all back off by exactly 1, 2, 4 seconds arrive together
three times in a row. This file leaves it out to keep the schedule assertable in a test, and the
hub §5 leaves adding it as a rep. The senior writes one more thing that is not here: a cap, so a
long chain of doubling cannot produce a wait longer than the work is worth.

**What degrades at scale.** This desk's cast is five agents, so one notification is at least five
provider calls, and a retry multiplies whichever of them was unlucky. A Monday burst of five
hundred notifications against a free-tier key is where the 429s live — and the difference between
honest backoff and a tight loop is the difference between a queue that drains slowly and an account
that gets rate-limited harder for behaving badly. What the free tier allows is not published as a
number; AI Studio shows the limits for your own account, and day 15 is where this loop meets a real
one.

**The review comment.** *"This catches `Transient` and returns the last known good answer from the
cache. Say that out loud in a claims context: we will tell a policyholder their cover was in force
because our provider was busy. Let it raise."*

**The interview question.** *"A provider sends `Retry-After: 60` and your backoff schedule says
wait 2 seconds. Which do you honour, and what happens to your service if you get that choice
backwards?"*
