## One-line answer

`run` is the only command anybody needs to know: it holds every command this project has, it puts
each of them through `uv run` so the work always happens on the pinned interpreter, and it names
the ones that do not exist yet.

## The idea

Every counter in the branch has a laminated card taped beside the terminal: open the day, print
the batch, close the day. Three commands. Nobody keeps them in their head, nobody has a slightly
different version, and a new starter on their first morning can work the counter by reading the
card.

Take the card away and the commands do not disappear — they move into people. One person opens the
day with a shortcut somebody showed them, another has a different sequence that also works, and
the difference only surfaces on the morning when one of them is off and the other one is on
holiday.

A project's card is its **driver**: the one script a repository is operated through, so a command
is found by reading one file rather than by remembering. This project's driver is called `run`, it
sits at the root, and from today it is the answer to every "how do I…" question about this desk.

It does one more thing, and this is the part worth taking seriously. Every command it runs goes
through `uv run`. Day 0 pinned an interpreter and part 1.1 locked an environment; neither of those
helps if the command you actually type is `pytest`, because that `pytest` is whichever one your
shell finds. The driver closes that gap by construction: **you cannot run this project's tests on
the wrong interpreter by accident**, because the only spelling anybody learns already has `uv run`
inside it.

And it names what is missing. Four of this desk's eventual commands do not exist yet — the
boundary, the evalset, the container, the compose stack. They are in the file, each with the day
of this project that builds it. A driver that lists only what works is a map with the unbuilt roads
left off.

## The mechanism

The whole file, at the root of the project. It has no extension, and it is Python:

```python
#!/usr/bin/env python3
"""The one door into the claims desk.

Every command this project has is here, so a command is found by reading one file rather than by
remembering. Each one runs through `uv run`, which means the work always happens on the
interpreter pinned in `.python-version` and in the environment locked in `uv.lock`, whatever
Python you happened to launch this script with.

    ./run check          lint, tests, and the setup check, in that order
    ./run lint           ruff, on everything
    ./run test           pytest
    ./run setup          the day-0 machine check

On Windows PowerShell, where `./run` is not executable, the same commands are
`python run check`, `python run lint`, and so on.
"""

from __future__ import annotations

import subprocess
import sys
from pathlib import Path

ROOT = Path(__file__).resolve().parent

#: Commands that exist. Each is a list of argv lists, run in order, stopping at the first failure.
COMMANDS: dict[str, list[list[str]]] = {
    "lint": [["uv", "run", "ruff", "check", "."]],
    "test": [["uv", "run", "pytest", "-q"]],
    "setup": [["uv", "run", "python", "check.py"]],
}
COMMANDS["check"] = COMMANDS["lint"] + COMMANDS["test"] + COMMANDS["setup"]

#: Commands the project will have, and the day of this project that builds each one. Naming them
#: here rather than leaving them absent means `./run` is the map of the whole desk from day 1.
PLANNED: dict[str, str] = {
    "serve": "day 19, the container and its health endpoint",
    "mcp": "day 3, the boundary that owns the policy store",
    "eval": "day 18, the evalset and the gate that goes red",
    "up": "day 19, compose, with the boundary beside the desk",
}


def run(argv: list[str]) -> int:
    """Run one command in the project root, letting its output through to the terminal."""
    print(f"--- {' '.join(argv)}", flush=True)
    return subprocess.call(argv, cwd=ROOT)


def usage() -> int:
    print(__doc__.strip().splitlines()[0])
    print("\ncommands:")
    for name in COMMANDS:
        print(f"  {name}")
    for name, when in PLANNED.items():
        print(f"  {name:<8} not built yet: {when}")
    return 2


def main(argv: list[str]) -> int:
    if not argv or argv[0] in {"-h", "--help", "help"}:
        return usage()
    command = argv[0]
    if command in PLANNED:
        print(f"'{command}' is not built yet: {PLANNED[command]}", file=sys.stderr)
        return 2
    if command not in COMMANDS:
        print(f"no such command: {command}", file=sys.stderr)
        return usage()
    for step in COMMANDS[command]:
        status = run(step)
        if status != 0:
            print(f"\nFAIL {command}: `{' '.join(step)}` exited {status}", file=sys.stderr)
            return status
    print(f"\nOK {command}")
    return 0


if __name__ == "__main__":
    sys.exit(main(sys.argv[1:]))
```

**Line by line:**

- `#!/usr/bin/env python3` — the shebang, which is what lets `./run check` work in a POSIX shell
  without naming an interpreter. `env python3` rather than a hard path, because the path differs on
  every machine. Note what this line does *not* do: it picks whichever `python3` your shell finds,
  and that is fine here, because this file's own work is dispatch and every real command it issues
  starts with `uv run`.
- **No extension on the filename.** `run` rather than `run.py`, so the command reads as a verb.
  Python does not care what the file is called when you run it as `python run`.
- **The module docstring lists the commands twice over** — once as prose for a reader, and once in
  the two dictionaries below, which is what the program uses. That duplication is deliberate and
  it is small; `usage()` prints from the dictionaries, so the list a user sees can never be stale.
- `ROOT = Path(__file__).resolve().parent` — the project root from the file's own location, the
  same trick day 0's `check.py` uses, so `./run check` behaves identically whether you are standing
  in the project or three directories below it.
- `COMMANDS: dict[str, list[list[str]]]` — a name to a list of commands, each command a list of
  arguments. **A list, never a string**, so nothing is passed through a shell: a path with a space
  in it stays one argument, and there is no quoting to get wrong.
- `["uv", "run", "ruff", "check", "."]` — `uv run` first, always. This is the line that makes the
  pin real: `ruff` here is the `ruff==0.16.6` in this project's locked environment, not a `ruff`
  somebody installed globally two years ago.
- `["uv", "run", "pytest", "-q"]` — `-q` because the driver's job is a verdict; a hundred lines of
  passing dots is noise, and `./run test` without `-q` trains people to stop reading the output.
- `["uv", "run", "python", "check.py"]` — day 0's four questions, unchanged, now reachable through
  the same door as everything else. The setup check did not need rewriting to be adopted; it needed
  a caller.
- `COMMANDS["check"] = COMMANDS["lint"] + COMMANDS["test"] + COMMANDS["setup"]` — **`check` is
  composed rather than duplicated.** Lint first because it is the fastest and catches the most
  typing mistakes, tests second, then the machine check. Adding a step to `lint` adds it to `check`
  with no second edit, which is the whole reason the values are lists.
- `PLANNED` — the four commands this desk will have, each with the day that builds it. This is the
  file's second job: a person who types `./run mcp` today gets an answer, not a stack trace, and
  the answer tells them where in this project the thing is coming from.
- `def run(argv)` — prints the command before it runs it, with a `--- ` prefix. When three steps
  run in sequence and the second one fails, the prefix is how you know which output belongs to
  which step. `flush=True` because the subprocess writes straight to the terminal and an unflushed
  header would appear *after* the output it labels.
- `subprocess.call(argv, cwd=ROOT)` — `call` rather than `run(..., capture_output=True)`: the
  child's output goes straight to your terminal, live. This is the opposite decision from day 0's
  `check.py`, which captured git's output — and for the opposite reason. There, git's chatter was
  noise around a verdict; here, ruff's and pytest's output *is* the product.
- `def usage()` — prints the docstring's first line, then every real command, then every planned
  one with the day that builds it. **It returns 2**, not 0: being asked for help because the
  command was wrong is not success, and a CI job that types the wrong command should fail rather
  than pass quietly.
- `if command in PLANNED:` — checked *before* the "no such command" case, so a real future command
  gets the informative message rather than the generic one.
- `if status != 0: print(f"\nFAIL {command}: ...")` — names the step that failed and its exit
  status, then stops. Stopping matters: running the tests after the lint has already failed wastes
  the reader's attention on a second failure that may just be the first one wearing a different
  hat.
- `return status` — the driver's exit status is the failing step's exit status, not a flattened 1.
  Day 19's CI reads this number.
- `sys.exit(main(sys.argv[1:]))` — `[1:]` drops the script's own name. Everything above is a
  function taking an argument list, which means the driver could be tested like any other code.

Ask the driver what it can do:

```bash
python run
```

**Line by line:**

- **Four commands that work and four that do not**, in one screen, on day 1. The desk's whole shape
  is legible before most of it exists.
- `not built yet: day 3, the boundary that owns the policy store` — a person who wanted `mcp` now
  knows both that it is coming and which sitting builds it.
- The exit status of that call is 2, not 0. Try it: `python run mcp; echo "exit=$?"`.

## When it breaks

The first version of `PLANNED` used an em dash between the day and the description. On this
machine's console it came out like this:

```
'mcp' is not built yet: day 3 � the boundary that owns the policy store
```

Day 0's check learned this lesson and this file had to learn it again, which is the point worth
keeping: **the rule is about anything this project prints, not about the file that first taught
it.** A Windows console encoding could not represent the dash, and a person reading a message
about a missing command now has a second mystery to rule out. The smallest fix is a comma. The
general fix is a habit: what a program prints to a terminal is ASCII.

## In production

**What a senior writes instead.** A `Makefile`, or `just`, or whatever the team already has —
because the value is not the language, it is that there is exactly one place. This project uses a
Python file because it already has a pinned Python and no other tool, and adding a build tool to
run three commands would be a dependency bought for a convention. The senior instinct to copy is
narrower: **CI runs the same door as the developer.** Day 19's workflow calls `./run check`, not a
handwritten list of steps that can drift from what anybody actually runs.

**What degrades at scale.** Every command that exists outside the driver is a command that has to
be learned twice — once by the person and once by the pipeline — and they diverge silently. A
claims platform with a service, a boundary, an eval suite and a nightly batch has perhaps a dozen
operations; teams that keep them in a README find out which ones have rotted when somebody is
paged at two in the morning and follows the README exactly.

**The review comment.** *"CI runs `pytest -q` directly. Make it `./run test` — otherwise the day
somebody adds a step to the test command, CI keeps passing without it and nobody notices for a
month."*

**The interview question.** *"Your driver runs everything through `uv run`. What would break if it
did not, and how would that failure present itself to a developer who has both a global and a
project Python?"*

## Check yourself

- **Run:** `python run mcp; echo "exit=$?"` — expect the message naming day 3 and expect `exit=2`.
  A command that does not exist yet is a failure, and the number has to say so.
- **Say out loud:** The driver itself runs on whichever Python your shell found, but everything it
  does runs on the pinned one. Why is that safe, and what would you have to change for it to stop
  being safe?
