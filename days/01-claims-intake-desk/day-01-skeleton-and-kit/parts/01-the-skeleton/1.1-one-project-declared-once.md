## One-line answer

`pyproject.toml` is where this desk states its name, the exact Python it runs on and the exact
versions of everything it installs, so that "it works here" becomes a fact a second machine can
reproduce rather than a claim.

## The idea

A loss adjuster goes out to a flooded kitchen with a kit bag: camera, damp meter, moisture probe,
a pad of forms. The bag is standard issue. Every adjuster at the firm carries the same one, and
that is the point — when two adjusters report different moisture readings on the same wall, the
firm needs the difference to be about the wall.

Now imagine the bag is not standard issue. Each adjuster buys their own meter, whichever model was
in stock, and calibrates it however they were shown. The readings still look like readings. They
carry two decimal places, they go into the claim file, and somewhere down the line a claim is
declined on a number that was never comparable to anything.

Software has exactly this bag, and it is a file. `pyproject.toml` is where a project writes down
what it is and what it needs — its name, the interpreter it will run on, and every package it
installs, at an exact version. Day 0 pinned the interpreter in `.python-version`, which decides
*which Python*. This file decides everything else, and it does it for every machine that ever
clones this desk.

Two terms, because the difference between them is what this part is about:

- A **floor** is a requirement written as `>=`, which says what is too old and leaves the choice
  to whichever machine resolves it. It is correct for a library, which cannot know what else will
  be installed alongside it, and it is never sufficient for an application, which is a thing you
  deploy and have to be able to reproduce.
- A **lockfile** is the tool-written record of what a resolution actually produced — exact
  versions and content hashes — as against `pyproject.toml`, which records what was *asked for*.
  You write the request; the tool writes the answer; both are committed.

The kitchen has water in it either way. The question this file settles is whether two people
measuring it are holding the same instrument.

## The mechanism

The whole file, at the root of the project, beside `check.py` from day 0:

```toml
[project]
name = "claims-intake-desk"
version = "0.1.0"
description = "A first-notice-of-loss intake desk: classify the loss, check cover, fast-track or write a deficiency letter."
requires-python = "==3.12.*"
dependencies = []

[dependency-groups]
dev = [
    "ruff==0.16.6",
    "pytest==9.1.1",
]

[tool.uv]
package = false

[tool.ruff]
line-length = 100
target-version = "py312"

[tool.ruff.lint]
select = ["E", "F", "I", "B", "UP", "SIM"]

[tool.pytest.ini_options]
testpaths = ["tests"]
pythonpath = ["."]
```

**Line by line:**

- `[project]` — the standard table every Python tool reads. Not a `uv` table and not a `ruff`
  table: this section is the packaging standard, so a different tool tomorrow reads the same
  facts.
- `name = "claims-intake-desk"` — hyphens, because a distribution name is hyphenated by
  convention. The **import** name is `claims_desk`, with an underscore, because that is a Python
  identifier. The two are allowed to differ and here they do: the folder you clone is the desk,
  the package inside it is the code.
- `version = "0.1.0"` — this desk is never published, so the number is a label rather than a
  promise. It is here because the standard requires it, and it is worth moving when the meaning of
  the project changes rather than on every commit.
- `description` — one sentence, the same one as the brief's opening. When a stranger runs a
  command that lists the project, this is the line they get.
- `requires-python = "==3.12.*"` — **a range, deliberately, and not a pin.** It says: any 3.12,
  nothing else. The pin lives in `.python-version` and names 3.12.12 exactly. The two are doing
  different jobs: `.python-version` says which interpreter *this* checkout runs on, and
  `requires-python` says which interpreters this project's code is valid for at all. Writing
  `>=3.12` here would be a floor, and it would quietly permit 3.14 — a version this project has
  never been run on.
- `dependencies = []` — **empty, on purpose, and it stays empty today.** The kit this day builds —
  keys, logging, backoff, budget — is hand-rolled from the standard library. Build first, compare
  after: you cannot judge a library that does retries until you have written the retry loop that
  it replaces.
- `[dependency-groups]` with a `dev` list — the standard place for packages the project needs to
  be *checked* but not to *run*. Nothing in `dev` ever reaches the container that ships on day 19,
  and that separation is the reason to declare it rather than lumping everything into
  `dependencies`.
- `"ruff==0.16.6"` and `"pytest==9.1.1"` — **`==`, not `>=`.** Both versions were read from
  `https://pypi.org/pypi/<name>/json` on 2026-09-10 and written into `PACKAGES.md` with that date.
  A floor here would mean the gate that guards this desk changes underneath you: a new lint rule
  arrives, CI goes red on a Tuesday, and nothing in the repository changed.
- `[tool.uv]` / `package = false` — this project is an application, not a library: nobody
  `pip install`s the claims desk. `package = false` tells `uv` to build the environment without
  trying to install this project into it, which is right, and which has one consequence the next
  part has to deal with.
- `[tool.ruff]` / `line-length = 100` — one number, decided once. Line length arguments are the
  cheapest possible thing for a team to spend a review on, and a number in a file ends them.
- `target-version = "py312"` — ruff writes suggestions for the Python this project actually runs.
  It is what makes the linter propose 3.12 syntax rather than the compatible-with-everything form,
  and part 2.3 gets a real suggestion out of it.
- `select = ["E", "F", "I", "B", "UP", "SIM"]` — the rule families, named rather than defaulted.
  `E` and `F` are the classic style and logic errors; `I` sorts imports; `B` is `bugbear`, which
  catches the mistakes that are legal Python and still wrong; `UP` upgrades old syntax to the
  pinned version's; `SIM` flags a simplification. Six letters, and a reviewer can tell from the
  line what the linter is allowed to complain about.
- `[tool.pytest.ini_options]` / `testpaths = ["tests"]` — where the tests live, so `pytest` with
  no arguments does the right thing and CI does not need to know the layout.
- `pythonpath = ["."]` — **this line is here because of `package = false` above**, and the next
  part is where it is earned. Without it, `pytest` cannot import `claims_desk` at all.

Then let `uv` build the environment from it:

```bash
uv sync
```

```
Using CPython 3.12.12
Creating virtual environment at: .venv
Resolved 8 packages in 8ms
Installed 7 packages in 884ms
 + colorama==0.4.6
 + iniconfig==2.3.0
 + packaging==26.3
 + pluggy==1.6.0
 + pygments==2.21.0
 + pytest==9.1.1
 + ruff==0.16.6
```

**Line by line:**

- `uv sync` — reads `pyproject.toml`, resolves it, writes `uv.lock`, creates `.venv`, and installs.
  One command, and it is the only one that ever creates an environment in this project.
- `Using CPython 3.12.12` — the interpreter from `.python-version`, chosen before anything is
  installed. Day 0's pin is doing its job here, silently, and this is the line that proves it.
- `Creating virtual environment at: .venv` — a directory holding a link back to that interpreter
  and its own installed packages. It is ignored by `.gitignore` from day 0, because it is
  rebuildable and machine-specific: copying it to another machine is how people end up with an
  environment nobody can explain.
- `Resolved 8 packages` — eight, from two requests. That is the resolution: `pytest` needs
  `iniconfig`, `packaging` and `pluggy`, `pygments` comes with it, `colorama` arrives because this
  is Windows. **Two lines in `pyproject.toml` became seven installed packages**, and the file that
  records which seven is `uv.lock`.
- `+ ruff==0.16.6` and `+ pytest==9.1.1` — exactly what was asked for, which is what `==` bought.
  The other five were chosen for you, and they are pinned too — in the lockfile, not here.
- **`uv.lock` is written by this command and committed.** It is the one file in this project that
  no day prints in full: it is over a hundred lines of tool-written hashes, and printing it would
  be transcribing a machine's output for a reader who must never edit it. The command that writes
  it is `uv sync`, and that command is in this document, in the day's hub §3 and in `SETUP.md`.

## When it breaks

On a machine where the project folder sits in a cloud-synced directory — OneDrive, Dropbox,
iCloud — `uv sync` can fail part-way through, with a message about hardlinks:

```
warning: Failed to hardlink files; falling back to full copy. This may lead to degraded performance.
         If the cache and target directories are on different filesystems, hardlinking may not be supported.
         If this is intentional, set `export UV_LINK_MODE=copy` or use `--link-mode=copy` to suppress this warning.
error: Failed to install: ruff-0.16.6-py3-none-win_amd64.whl (ruff==0.16.6)
  Caused by: failed to hardlink file from ...\.venv\Lib\site-packages\ruff\__init__.py to ...\uv\cache\archive-v0\...\ruff\__init__.py: The cloud operation cannot be performed on a file with incompatible hardlinks. (os error 396)
```

The paths are shortened; everything else is verbatim. `uv` installs by hardlinking from its cache,
which is fast and costs no disk, and a cloud-sync filesystem refuses the operation. Somebody put
the desk in their synced Documents folder, watched half an environment appear, and read `os error
396` as a corrupt download. The smallest fix is the one the warning names: `uv sync
--link-mode=copy`, or `UV_LINK_MODE=copy` in the environment so every later `uv` command inherits
it. The environment it builds is identical; only the way the files got there changed.

## In production

**What a senior writes instead.** The same file, with `dependencies` also pinned with `==` and a
`uv.lock` committed beside it, plus a scheduled job that opens a pull request when a pin goes
stale. The pins do not exist to freeze the project; they exist so that *upgrading is an event with
a diff and a review*, rather than something that happens to a machine at three in the morning
because a resolver had a free choice.

**What degrades at scale.** An insurer's claims platform is audited on what it was running when a
decision was made. This desk ends up making fast-track decisions on twelve synthetic
notifications; a real one runs thousands a week, and the question "was the model the same on
Tuesday as on Monday" has to be answerable from the repository alone. A floor in a dependency
list makes that question unanswerable for every transitive package underneath it — and there were
five of those in a project that asked for two.

**The review comment.** *"`ruff>=0.16` in the dev group. Make it `==` and put the version in
`PACKAGES.md` with the date you read it — otherwise the next person to run CI gets a lint failure
in a file they did not touch, and spends the morning proving they did not break it."*

**The interview question.** *"Your `pyproject.toml` asks for two packages and your lockfile has
seven. Where did the other five come from, which file decides their versions, and what breaks if
you delete the lockfile?"*

## Check yourself

- **Run:** `uv sync` then `uv run python -V` — expect `Python 3.12.12`, and expect `.venv/` to be
  absent from `git status`.
- **Say out loud:** `requires-python` says `==3.12.*` and `.python-version` says `3.12.12`. Both
  are about which Python runs this desk. Why does the project need both, and what would go wrong
  if you deleted either one?
