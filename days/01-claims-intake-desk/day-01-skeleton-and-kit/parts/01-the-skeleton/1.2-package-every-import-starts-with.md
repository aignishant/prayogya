## One-line answer

Two directories with an `__init__.py` in each turn a folder of scripts into one importable name,
`claims_desk`, and every line of this desk from here to day 19 begins with that name.

## The idea

The kit bag has compartments, and they are labelled. Camera in the top pocket, damp meter in the
side, forms in the back. An adjuster who has used the bag once can find the meter in the dark,
because the meter is not "somewhere in the bag" — it is in the side compartment, and it is in the
side compartment in every bag the firm owns.

A project without a package is a bag with everything loose in the bottom. It works — you can reach
in and find things — right up until two things in there have the same name, or until somebody
takes one out and it stops working because it was quietly relying on being in that bag.

A **package** is a directory Python treats as one importable thing, marked by an `__init__.py`
file inside it. The name of the directory becomes the name you import. Once `claims_desk/` exists
with an `__init__.py`, `import claims_desk` is a sentence Python understands, and
`claims_desk.util.backoff` is a specific compartment of a specific bag rather than a file that
happened to be nearby.

That matters here more than it would in a smaller project, for a reason that arrives on day 3.
This desk will grow a second top-level package — the boundary that owns the policy store, running
in its own process. Two packages, one repository, and the import line will be the thing that says
which side of the boundary a piece of code is on. Getting the shape right on day 1 is what makes
that legible later.

There is a second, quieter decision in this part. `claims_desk/util/` is a package inside a
package, and it exists so that the four shared pieces — the key, the log, the retry, the budget —
have one home with one name. A helper that lives beside its first caller gets copied to its second
caller, and then the two copies drift; a helper in `util` is imported twice.

## The mechanism

Two files, both of them the whole file. First the desk itself:

```python
"""The claims intake desk.

A first-notice-of-loss desk: it reads a notification, classifies the loss, checks the policy was
in force on the date of loss, and either fast-tracks the claim or writes a deficiency letter
naming what is missing.

This package holds the desk itself. `claims_desk.util` holds the kit every part of it shares:
keys, logging, backoff, budget. Nothing in here imports anything from outside this project.
"""
```

That is `claims_desk/__init__.py` in full — a docstring and nothing else.

**Line by line:**

- **The file exists, and that is most of its job.** `__init__.py` is what makes the directory a
  package rather than a directory. An empty one would work identically.
- **It is a docstring rather than empty** because this is the first thing anybody reads when they
  open the package, and `help(claims_desk)` prints it. A project whose entry point explains itself
  in four lines has answered the question a new reader actually has.
- **"Nothing in here imports anything from outside this project."** — a rule stated where it is
  enforced, at the top of the package it governs. This desk depends on no shared library and no
  parent folder: everything it needs is either the standard library or a file in this repository.
- **No imports, no re-exports, no version constant.** The temptation is to `from .util import *`
  here so callers can write `claims_desk.log(...)`. Resist it: a re-export means two ways to name
  the same thing, and a reader tracing `log` has to know both.

Then the kit's own package:

```python
"""The kit: the four things every part of this desk needs and none of them should re-invent.

`keys` reads the secret, once, and never prints it. `logging` writes one JSON object per line and
redacts by field name. `backoff` waits the interval a provider asked for and escalates when the
attempts run out. `budget` counts model calls across the whole cast and refuses rather than
overspending.

Four modules, one import path, no third-party dependency.
"""
```

That is `claims_desk/util/__init__.py` in full.

**Line by line:**

- **A second `__init__.py`, one level down** — `claims_desk.util` is itself a package, so the four
  modules underneath it are `claims_desk.util.keys` and so on. Nesting is not required by Python;
  it is chosen here so that "the kit" is a thing with a name rather than four files that happen to
  be about infrastructure.
- **The docstring names all four modules and what each promises**, in one sentence each. This is
  the index a reader needs when they are looking for the retry loop and do not yet know it is
  called `backoff`.
- **"no third-party dependency"** — recorded here because it is a property that is easy to lose.
  The moment one of these four imports a package, `dependencies` in `pyproject.toml` stops being
  empty and the kit stops being something you can read in one sitting.

Make the directories and the files, then check that Python agrees they are a package:

```bash
mkdir -p claims_desk/util tests
uv run python -c "import claims_desk, claims_desk.util; print(claims_desk.util.__file__)"
```

```
.../claims-intake-desk/claims_desk/util/__init__.py
```

**Line by line:**

- `mkdir -p claims_desk/util tests` — `-p` creates the parent as well, so one command makes both
  levels. On PowerShell the same is `New-Item -ItemType Directory -Force claims_desk/util, tests`.
- `uv run python -c "import claims_desk…"` — through `uv run`, so the import is tested on the
  pinned interpreter rather than on whichever Python your shell finds.
- `claims_desk.util.__file__` — the path Python actually loaded, with the leading directories
  shortened here. Printing the path rather than a cheerful "it worked" is the habit: **an import
  that succeeds from the wrong directory is a bug that hides for weeks**, and the path is what
  tells you which copy you are running.

## When it breaks

Write the tests, run them, and Python cannot find the package it just imported successfully a
moment ago:

```
_____________________ ERROR collecting tests/test_kit.py ______________________
ImportError while importing test module '...\tests\test_kit.py'.
Hint: make sure your test modules/packages have valid Python names.
Traceback:
tests\test_kit.py:12: in <module>
    from claims_desk import models
E   ModuleNotFoundError: No module named 'claims_desk'
```

The import works under `uv run python` and fails under `uv run pytest`, which is the confusing
part. The cause is one line in the previous part: `package = false` means this project is not
installed into `.venv`, so `claims_desk` is importable only because the *current directory* is on
the import path — and `pytest` does not put it there. Somebody spent an afternoon on this
convinced the package was malformed. The smallest fix is `pythonpath = ["."]` under
`[tool.pytest.ini_options]`, which tells pytest to add the project root, and it is why that line
exists in `pyproject.toml`.

## In production

**What a senior writes instead.** For anything that gets published, a `src/` layout —
`src/claims_desk/` — with a build backend and the project installed into its own environment. The
reason is precisely the failure above, inverted: with a `src/` layout you *cannot* accidentally
import the package from the working directory, so the tests are forced to exercise the installed
copy, which is the copy your users get. A flat layout is the right call for an application that is
only ever run from its own checkout, and the price is that one pytest setting.

**What degrades at scale.** By day 19 this repository holds the desk, the boundary process, the
tests and the evals, and it runs in a container where the working directory is not what it is on
your laptop. Every one of those is a place a loose script would break and a package import will
not. The claims platform this desk stands in for has dozens of such moves a year — a service split
in two, a job moved to a scheduler — and the ones that hurt are always the ones whose imports
depended on where the process happened to start.

**The review comment.** *"This adds `helpers.py` next to the agent that uses it. Put it in
`claims_desk/util/` — the second caller is a fortnight away and it will copy this file rather than
import it."*

**The interview question.** *"`import claims_desk` works in your shell and fails in your test
runner. Give me two possible causes and say how you would tell them apart in one command."*

## Check yourself

- **Run:** `uv run python -c "import claims_desk.util; print(claims_desk.util.__file__)"` — expect
  a path that ends in your own project folder, and check that it does before moving on.
- **Say out loud:** `claims_desk/__init__.py` contains no code at all. Name two things that would
  stop working if you deleted it, and one thing that would not.
