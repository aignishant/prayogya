## One-line answer

`compose.yaml` runs two containers from one image on a network only they can see — the boundary
listening on every interface *of that network* with no port published, the desk reaching it by
service name over the Streamable HTTP transport day 4 built, and the key read from the machine's
`.env` at start-up and never from the image.

## The idea

The branch office needs two things on its first morning: a counter, and a line to the policy
department. The kit from part 1.1 is the counter. This part is the line — and the decision about
who else can pick it up.

Since day 3 the boundary has been the only process that opens the policy book, and since day 4 it
has been reachable two ways: launched as a subprocess by the desk, or running on its own as a URL.
On a laptop the first way has been the default every day since, and day 17 measured what it costs —
forty interpreter launches a queue, ninety-eight per cent of the run. In a container the second way
is the only way: the desk's container cannot launch a process inside the boundary's container, and
a boundary launched *inside* the desk's container would be a second copy of the policy book with
its own claim files, which is the failure day 3 built the boundary to prevent.

So the boundary becomes a **sidecar**: a second container, started alongside the desk, that the desk
talks to over the network and that outlives any single request. The word means what it says — the
two run beside each other, from the same image, and neither is the other's child.

That raises the question day 4 postponed. The boundary binds loopback on a laptop because it has no
authentication, and loopback is a container's own — a desk in another container cannot reach it.
The choice is between adding authentication and putting both containers on a network nobody else
can join. This part takes the second, and the honest form of it: the boundary listens on every
interface *of a private network that compose creates for these two services*, its port is never
published to the host, and the desk finds it by name — `boundary` — because compose resolves a
service's name to its container on that network. Day 4's review comment offered exactly these two
options; the README records which was taken and that the other was not.

The key is the last thing, and it is the shortest. The desk container reads its key from the
machine's `.env` file, at start-up, through compose's `env_file`. It is never in the image, never
in this file, and never in the boundary's container, which has no use for it — the same split day
16 named: the desk holds the provider key and the boundary holds the claim files, and neither holds
the other's.

None of this ran today, because this machine has no Docker. What did run is `./run up`, which is
how the day found out — and the driver's answer to that is part 1.2's last diff.

## The mechanism

The whole file, at `compose.yaml`:

```yaml
# The desk and its boundary, side by side, on a network only they can see.
#
# Two containers from one image. The boundary owns the policy book and the claim files and listens
# on the private network; the desk reaches it by service name, over the same Streamable HTTP
# transport day 4 built, and is the only container with a published port. Nothing here holds a
# secret: the key is read from the .env file on the machine that runs `./run up`, at run time,
# and never becomes part of an image.

services:
  boundary:
    build: .
    command: ["python", "-m", "claims_mcp", "--http"]
    environment:
      # Inside its own container the boundary must listen on every interface, or the desk's
      # container cannot reach it. Day 4 bound loopback because the machine was shared; here the
      # network is compose's own and the port is not published, so "every interface" is this
      # container's one interface on that network.
      CLAIMS_MCP_HOST: 0.0.0.0
    healthcheck:
      # The slim image has no curl. A POST with no body is refused with a status, and any status
      # from the endpoint means the boundary is answering; a refused connection means it is not.
      test: ["CMD", "python", "-c", "import urllib.request,urllib.error,sys\ntry:\n    urllib.request.urlopen(urllib.request.Request('http://127.0.0.1:8931/mcp', method='POST'), timeout=4)\nexcept urllib.error.HTTPError:\n    sys.exit(0)\nexcept Exception:\n    sys.exit(1)\nsys.exit(0)"]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 5s
    read_only: true
    tmpfs:
      - /app/data/claims

  desk:
    build: .
    env_file: .env
    environment:
      CLAIMS_BOUNDARY: http://boundary:8931/mcp
    ports:
      - "127.0.0.1:8080:8080"
    depends_on:
      boundary:
        condition: service_healthy
    read_only: true
```

**Line by line:**

- **No top-level `version`.** The compose reference this file was checked against documents
  `services` as the root and nothing about a version key; older files carried one and current tools
  ignore it.
- `build: .` **on both services** — **one image, two roles.** Both containers are built from part
  1.1's `Dockerfile`; what differs is the `command`. Building once and running twice is what makes
  "the boundary and the desk are the same code at the same commit" a property rather than a hope.
- `command: ["python", "-m", "claims_mcp", "--http"]` — **the boundary's own entry point, from day
  4, as a URL.** The image's default `CMD` is the desk's server; this overrides it for the sidecar.
  Exec form, as in the `Dockerfile`, for the same reason: the boundary is PID 1 and gets the stop
  signal itself.
- `CLAIMS_MCP_HOST: 0.0.0.0` — **the one place part 1.1's variable is set.** Every interface of
  this container, which on compose's network is one interface. No `ports:` on this service, so
  nothing outside the network can reach 8931 — that absence is the access control, and it is
  deliberate.
- `healthcheck: test: ["CMD", "python", "-c", ...]` — **the boundary proves it is answering with
  the standard library**, because the slim image has no `curl`. A `POST` with no body to `/mcp` is
  refused *by the boundary*, with an HTTP status — and any status means the process is there and
  parsing requests; only a refused connection means it is not. So `HTTPError` is a pass and anything
  else is a fail. The reference's four options, and a start period because the boundary imports the
  same framework the desk does.
- `read_only: true` and `tmpfs: - /app/data/claims` — **the boundary's filesystem is read-only
  except the one directory it writes.** `record_decision` writes claim files; everything else in the
  image is code and fixtures that a running container has no reason to change. A read-only root is
  the container-level version of day 16's rule that the boundary's powers are exactly the ones it
  needs.
- `env_file: .env` — **the key, from the machine, at start-up.** Compose reads the file on the host
  where `./run up` is typed and hands its lines to the container's environment, which is where
  day 1's `keys.require` looks. The file is not copied into the image (part 1.1's `.dockerignore`),
  not named in this file, and not given to the boundary, which has no `env_file` line.
- `CLAIMS_BOUNDARY: http://boundary:8931/mcp` — **the desk's day-4 switch, set to the sidecar's
  name.** `boundary` resolves, on compose's network, to that container; `8931` and `/mcp` are day
  4's constants. Nothing in `boundary.py` changes: it reads this variable and connects, exactly as
  day 4 part 2.1's transcript did against `127.0.0.1`.
- `ports: - "127.0.0.1:8080:8080"` — **the only published port, and only on the host's loopback.**
  The desk's `/healthz` and `/queue` are reachable from the machine running compose and from
  nowhere else, which is the honest scope for a route that runs the whole queue with the desk's key.
- `depends_on: boundary: condition: service_healthy` — **the desk does not start until the
  boundary's health check has passed.** Without the condition, compose starts both at once and the
  desk's first `/healthz` finds nothing listening — a `503` that is true for four seconds and
  confusing for an hour. With it, the sidecar is answering before the desk exists.

## When it breaks

Publish the boundary's port, which is what somebody does the first time they want to `curl` it from
the host:

```diff
   boundary:
     build: .
     command: ["python", "-m", "claims_mcp", "--http"]
+    ports:
+      - "8931:8931"
```

It works, which is the problem. The boundary now answers on every interface of the *host*, not of
the private network — and it has no authentication, so anyone who can route to the machine can
call `fetch_policy` for every number in the book and `record_decision` for any claim. Day 4's part
1.1 said exactly this about `0.0.0.0`; the container made the sentence true by a different route,
with a line that looks like the harmless one four lines below it on the `desk` service.

The smallest fix is not to add the lines — or, if the host must reach the boundary, to bind the
publication to loopback as the desk's is, `"127.0.0.1:8931:8931"`. Part 5.1 holds the invariant
the other way round: `compose.yaml` has exactly one `ports:` key, and it is the desk's.

## In production

**What a senior writes instead.** The same two services with the image pulled from a registry by
digest rather than built on the machine, so what runs is what the pipeline built and scanned; the
boundary's claim files on a named volume rather than `tmpfs`, because a decision that vanishes when
the container stops is a decision nobody made; and a third service, the file audit from day 18,
run as a one-shot container against the same sidecar — `./run eval` in compose — so the gate runs
against the boundary as deployed and not as launched.

**What degrades at scale.** One boundary container, one desk container, one machine. An insurer
with five regional desks and one policy book wants five desks and one boundary, and compose has no
way to say that across machines — the moment the desk and the boundary are on different hosts,
"a private network only they can see" is a network somebody has to build, and "reach it by service
name" is a DNS entry somebody has to own. That is the line between this tier and the next, and the
README says this desk stops on this side of it.

**The review comment.** *"`tmpfs` on `/app/data/claims` means every claim file the boundary writes
is gone when the container stops, and `read_only: true` means it cannot write anywhere else. That is
correct for a demonstration and wrong for a desk: mount a volume, or say in the README that the
claim file is not persistent."*

**The interview question.** *"You have two containers that must talk to each other and one of them
has no authentication. Describe two different ways to make that safe, and what each one assumes
about the network."*
