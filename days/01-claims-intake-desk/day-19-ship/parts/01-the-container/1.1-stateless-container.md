## One-line answer

An image is the desk packed as a sealed kit — the interpreter this project pinned, the packages
`uv.lock` names and nothing it does not, the code, and a user that is not root — with `.env` kept out
of the box by a rule written before the box is packed, because a layer that once held a secret holds
it forever.

## The idea

An insurer opens a branch office in another town, and the desk has to travel.

What travels is a kit: the forms, the handbook, the counter software on a sealed drive, a list of
exactly which version of each. What does not travel is the safe key. The branch manager is handed
that in person, on the day, and it never sits in the box — because the box goes through a courier,
sits in a warehouse, gets copied for the next branch, and every copy would carry the key with it.
And the kit is sealed so that the branch runs *this* desk, the one that was audited, and not
whatever the branch happened to have installed on its own machines.

A container image is that kit, and every choice in the file that builds it is one of those three
sentences. **Sealed:** the image starts from a base that *is* the interpreter this project pinned on
day 0 — `python:3.12.12-slim` — and installs the packages `uv.lock` names, with `--locked`, which
refuses to run if the lock disagrees with `pyproject.toml`. Not a newer interpreter, not a
re-resolved dependency, not the ruff and pytest a running desk never calls. **The key handed over on
the day:** the image contains no `.env`, no key and no name of a key; it is injected by whoever
starts the container, and part 2.1 shows how. **And a rule written before the box is packed:**
`.dockerignore`, which is to the image exactly what day 0's `.gitignore` is to the history — a list
of what `COPY . /app` must never carry, written before the first build for the same reason day 0
wrote its rule before `.env` existed. An image layer is a snapshot. A later layer that deletes a file
hides it from the running container and leaves it readable in the layer underneath, for anyone who
pulls the image.

There is one more property the kit needs, and it is the one the title names. **The container is
stateless.** Nothing in it outlives a request: the desk keeps no session between claims, no cache
of policies, no counter. Every fact comes from the boundary on every call, which is what days 3 and
4 built the boundary for. So a second copy of the container answers exactly as the first would, and
killing either one loses nothing — which is the only property that lets somebody run two, or restart
one at three in the morning without asking anybody.

Two honest limits, stated here because the transcripts below have to carry them. This machine has
no Docker, so the image was not built today: the build command is printed with the output it would
have to produce marked `TODO(me)`, and every line of the file was checked against the build tool's
own reference on the day. And the boundary's HTTP host — bound to loopback since day 4 — becomes a
variable today, because inside a container loopback is the container's own and the desk cannot
reach it. That is a four-line diff with a paragraph of reasoning, and the reasoning is the part
worth reading.

## The mechanism

The whole file, at `Dockerfile`:

```dockerfile
# syntax=docker/dockerfile:1

# The desk, as an image. One stage to build the environment, one to run it, and nothing in the
# second that the first did not put there on purpose.
#
# Two things are pinned by digest-free tag on purpose and recorded in PACKAGES.md: the interpreter
# is the same 3.12.12 that .python-version names, and uv is the same 0.12.3 this desk was built
# with. An image that resolves "latest" at build time is a desk that decides claims on whichever
# interpreter existed the morning somebody rebuilt it.

FROM python:3.12.12-slim AS builder

COPY --from=ghcr.io/astral-sh/uv:0.12.3 /uv /uvx /bin/

# Never download an interpreter inside the image: the base image *is* the interpreter, and a
# download would be a second one nobody pinned.
ENV UV_PYTHON_DOWNLOADS=0
ENV UV_COMPILE_BYTECODE=1
ENV UV_LINK_MODE=copy

WORKDIR /app

# Dependencies first, from the two files that define them, so this layer is rebuilt only when a
# pin changes and not when a line of code does. --locked refuses to run if uv.lock disagrees with
# pyproject.toml; --no-dev leaves ruff and pytest out of an image that will never run them.
RUN --mount=type=cache,target=/root/.cache/uv \
    --mount=type=bind,source=uv.lock,target=uv.lock \
    --mount=type=bind,source=pyproject.toml,target=pyproject.toml \
    uv sync --locked --no-dev --no-install-project

# Then the desk itself. .dockerignore decides what "the desk" means here, and .env is not in it.
COPY . /app
RUN --mount=type=cache,target=/root/.cache/uv \
    uv sync --locked --no-dev

FROM python:3.12.12-slim

# A user that is not root, created before anything is copied in so that the files it needs are
# readable and nothing else is writable.
RUN useradd --create-home --uid 1000 desk
WORKDIR /app
COPY --from=builder --chown=desk:desk /app /app
ENV PATH="/app/.venv/bin:$PATH"
USER desk

# The desk listens on every interface inside the container — the container's network is its own —
# and whoever runs it decides which host port, if any, reaches it.
ENV CLAIMS_DESK_HOST=0.0.0.0
ENV CLAIMS_DESK_PORT=8080
EXPOSE 8080

# The health check asks the desk, which asks the boundary. A container whose boundary is gone is
# unhealthy, and compose restarts nothing on its behalf — it reports, which is what a check is for.
HEALTHCHECK --interval=30s --timeout=5s --start-period=10s --retries=3 \
    CMD ["python", "-c", "import urllib.request,sys; sys.exit(0 if urllib.request.urlopen('http://127.0.0.1:8080/healthz', timeout=4).status == 200 else 1)"]

CMD ["python", "-m", "claims_desk.serve"]
```

**Line by line:**

- `# syntax=docker/dockerfile:1` — **the parser directive the build tool's reference says most
  users want**: it makes the builder fetch the current stable syntax before reading the file, which
  is what the `--mount` lines below need. It has to be the first line.
- `FROM python:3.12.12-slim AS builder` — **the interpreter, by the exact version day 0 pinned.**
  `.python-version` says `3.12.12`; this says `3.12.12`; part 5.1 has a test that reads the first and
  greps the second, so the two cannot drift apart without a red line. The tag was looked up on the
  registry today (hub §9). `slim` because the desk needs no compiler and no man pages, and every
  megabyte in an image is pulled onto every machine that runs it.
- `COPY --from=ghcr.io/astral-sh/uv:0.12.3 /uv /uvx /bin/` — **uv, from its own image, pinned to
  the version this desk was built with** — the same 0.12.3 `PACKAGES.md` recorded on day 0. The
  tool's own documentation shows this exact pattern and says pinning is best practice; `:latest`
  would make the build depend on the day it was run.
- `ENV UV_PYTHON_DOWNLOADS=0` — **no second interpreter.** uv will happily download a CPython to
  satisfy a pin; inside an image whose base already *is* that CPython, a download would be an
  unpinned copy nobody asked for. This turns it off, and a mismatch becomes a build error instead.
- `UV_COMPILE_BYTECODE=1` and `UV_LINK_MODE=copy` — **the two settings the tool recommends for
  images.** Bytecode compiled once at build time rather than on every container start; files copied
  rather than hard-linked, because a hard link across a cache mount and a layer is a link that does
  not survive the layer.
- `RUN --mount=type=cache,... --mount=type=bind,source=uv.lock,... uv sync --locked --no-dev
  --no-install-project` — **dependencies first, from two files, in their own layer.** The bind
  mounts put `uv.lock` and `pyproject.toml` into the build step without copying them into the
  image, so this layer's cache key is those two files alone: a change to a line of code does not
  reinstall fifty-two packages. `--locked` is the whole discipline of day 1 carried into the build:
  if the lock and the project disagree, refuse. `--no-dev` leaves out the `dev` group — ruff and
  pytest — and the dry run below shows exactly which five packages that is. `--no-install-project`
  because there is no project to install yet; day 1's `pyproject.toml` says `package = false` and
  the desk is run as modules, not installed as a distribution.
- `COPY . /app` — **the desk, as `.dockerignore` defines it.** Everything in the folder except what
  the second file below excludes. This is the line the whole `.dockerignore` exists for.
- `FROM python:3.12.12-slim` **again** — **the second stage.** The final image starts clean and
  receives only what the builder produced; uv itself, the cache, and the build tooling stay behind
  in a stage nobody ships.
- `RUN useradd --create-home --uid 1000 desk` and `USER desk` — **not root.** A desk that reads
  claim files and runs a model client has no business with root inside its own container; if
  anything in the model's answer ever reached a shell, this is the line that decides what it can
  do. The user is created *before* the copy so `--chown=desk:desk` can hand it the files.
- `ENV PATH="/app/.venv/bin:$PATH"` — **the environment on the path**, so `python` inside the
  container is the one with the desk's packages. The tool's reference shows this exact line.
- `ENV CLAIMS_DESK_HOST=0.0.0.0` — **the one setting that differs from a laptop**, and part 1.2
  explains it: on a machine, loopback; in a container, every interface, because the container's
  interfaces are its own and the port reaches the outside only if somebody publishes it.
- `HEALTHCHECK ... CMD ["python", "-c", "..."]` — **the container asks its own desk whether it is
  alive**, with the standard library, because the slim image has no `curl`. The desk answers by
  asking the boundary, so an unhealthy container is one whose boundary is gone. The four options are
  the reference's four, with a start period so a container is not declared dead while Python is
  still importing the framework.
- `CMD ["python", "-m", "claims_desk.serve"]` — **exec form, so the process is PID 1 and receives
  the stop signal itself**, and part 1.2's `serve.py` is what runs.

The rule written before the box is packed. The whole file, at `.dockerignore`:

```text
# What `COPY . /app` must never carry into an image.
#
# This file is to the image what .gitignore is to the history, and it is written for the same
# reason at the same moment: before the thing it excludes could be copied. A layer that once held
# .env holds it in every image built from it, whatever a later layer deletes.

# Secrets. Injected at run time by whoever runs the container; never a file in the image.
.env
.env.*
!.env.example
*.key
*.pem
service-account.json

# The environment and the history. uv rebuilds the first from the lockfile inside the image, and
# the second is nobody's business inside a container.
.venv/
.git/
__pycache__/
*.pyc
.pytest_cache/
.ruff_cache/
.adk/

# What a run leaves behind. A claim file from this machine is a decision this container never made.
data/claims/

# The teaching, and the tooling that only a developer runs.
tests/
.github/
```

**Line by line:**

- **The first block is day 0's `.gitignore`, verbatim** — the same six lines, including
  `!.env.example` *below* `.env.*` for the reason day 0 gave: within one file the last match
  decides, and a negation above the pattern it excepts does nothing. Part 5.1 asserts the order.
- `.venv/` — **the environment does not travel.** The image rebuilds it from `uv.lock` on its own
  interpreter; a `.venv` copied from a Windows machine into a Linux image is a folder of the wrong
  binaries with the right names.
- `.git/` — **the history stays home.** A clone's `.git` can be larger than the code, and inside a
  container it is a copy of every secret ever committed by mistake, which is why day 0 was so
  careful about the first one.
- `data/claims/` — **a run's output.** The audit's `run_desk` clears this directory for the same
  reason; a claim file baked into an image is a decision the container will report having made
  before it ever ran.
- `tests/` and `.github/` — **what only a developer runs.** The image runs the desk; the gates run
  in the pipeline, on a checkout, which is part 3.1.

The boundary's host, as a variable. **A marked diff against `claims_mcp/__main__.py` as printed on
day 4 part 1.1:**

```diff
 from __future__ import annotations

+import os
 import sys

 from claims_mcp.server import server

 #: Where the boundary listens when it is a URL. Loopback, deliberately: this server has no
 #: authentication of any kind, and day 16 is where that becomes a decision rather than a default.
-HOST = "127.0.0.1"
+#: Day 19 makes it a variable and nothing else: inside a container the boundary's network is a
+#: private one shared with the desk alone, and `0.0.0.0` there is one interface, not the world.
+HOST = os.environ.get("CLAIMS_MCP_HOST", "127.0.0.1")
 PORT = 8931
```

**Line by line:**

- `os.environ.get("CLAIMS_MCP_HOST", "127.0.0.1")` — **the default is unchanged.** On a laptop the
  boundary still binds loopback, for the reason day 4 gave: it has no authentication, and anyone
  who can reach the port can read the policy book. Nothing about running `./run mcp --http` today
  is different from day 4.
- **The variable is set in exactly one place**, part 2.1's `compose.yaml`, where the network the
  boundary joins is one that compose creates for these two containers and nothing else, and the
  boundary's port is never published. Day 4's review comment said *bind loopback and put them in the
  same network namespace, or add authentication* — this is the first of those, made explicit as a
  setting rather than an edit.
- **What it does not do:** authenticate. The `README` says so under *what is deliberately not
  built*, and that honesty is the whole of the boundary's access control.

## When it breaks

The mistake this file is shaped to prevent is the one the tool's reference makes easy: copy the
project in first, then install.

```diff
-RUN --mount=type=cache,target=/root/.cache/uv \
-    --mount=type=bind,source=uv.lock,target=uv.lock \
-    --mount=type=bind,source=pyproject.toml,target=pyproject.toml \
-    uv sync --locked --no-dev --no-install-project
-
 # Then the desk itself. .dockerignore decides what "the desk" means here, and .env is not in it.
 COPY . /app
 RUN --mount=type=cache,target=/root/.cache/uv \
     uv sync --locked --no-dev
```

It builds. It produces the same image. And every build after a one-line change to `desk.py`
reinstalls a hundred and twenty packages, because `COPY . /app` changed a layer and every layer
after it is rebuilt. That is the failure nobody files a bug about — a build that takes four minutes
instead of twenty seconds — and it is the reason the dependency step binds two files rather than
copying the tree.

The mistake that *does* get a bug filed is the other order of the other pair — `.env` written and
tested on the machine before `.dockerignore` exists:

## In production

**What a senior writes instead.** The same two stages with the base images pinned by digest —
`python:3.12.12-slim@sha256:…` — so that a rebuild six months later gets byte-for-byte the same
base and not the same tag pointing at a patched image; a `.dockerignore` generated from
`.gitignore` plus a short list, so the two cannot disagree about `.env`; and an image scanner in the
pipeline that fails the build on a known vulnerability in any of the hundred and twenty packages,
because a desk that reads a policy book is a desk somebody will try to reach through its
dependencies.

**What degrades at scale.** The image is the fifty-two packages problem from day 18 made physical.
A cloud evaluation client, a numerical stack and a tokeniser are in every copy of this container,
and an insurer running a desk per region pulls that image onto every node in every region on every
release. At a few hundred megabytes and thirty nodes, one release is several gigabytes of pulls
before a single claim is decided — and the morning the queue is longest is the morning the release
goes out. The fix is the one the README names: the evaluation extra in its own dependency group,
excluded like `dev` is, so the running desk carries only what decides claims.

**The review comment.** *"`HEALTHCHECK` asks the desk, which asks the boundary. So a container
whose *boundary* is down is marked unhealthy and, under an orchestrator that restarts unhealthy
containers, gets restarted — which does nothing for the boundary and loses whatever the desk was
doing. Split it: the health check proves the desk is up; readiness, which compose does not model
but the orchestrator will, is the one that asks the boundary."*

**The interview question.** *"You have a Python service and a lockfile. Walk me through a
Dockerfile for it, and tell me the order of the lines that matters and why."*
