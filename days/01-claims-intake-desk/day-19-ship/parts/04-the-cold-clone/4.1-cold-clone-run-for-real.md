## One-line answer

Clone the repository into an empty folder with an empty package cache, install from the lock, write
the one line `.env` needs, and run both gates — `292 passed` and `eval: green` from a tree that
inherited nothing — and then clone the commit that forgot `uv.lock` and read the one line that
stops it, because **a project whose cold clone was never run is not finished.**

## The idea

The branch opens with the kit and nothing else.

Nobody from head office goes with it. The branch manager has the sealed drive, the handbook, the
key handed over that morning, and a one-page card that says what to do first. If the card assumes a
step that only head office ever did — a folder that was always there, a setting somebody made once
in the spring — the branch does not open, and the failure is discovered by the one person least
able to fix it, on the morning it matters.

Every check this project has run for nineteen days ran on a machine that was set up over nineteen
days. `python p.py verify` copies the folder out and runs its check, and that proves the folder does
not reach outside itself — but the copy still shares this machine's interpreter, its package cache
and its `uv` binary. The test that proves a stranger can open the branch is the **cold clone**: a
fresh `git clone` into a folder that has never held this project, with a package cache that has
never held these packages, following the README and nothing else, and recording what it printed.
Not "should print". Printed.

Three things make a cold clone cold, and each one is a way a warm machine lies. **An empty folder**,
so nothing from the working copy — a `.venv`, a `.env`, a `data/claims/` from last week — comes
along. **An empty cache**, so every package is fetched as the lock names it and a package that was
never really pinned shows up as a download that fails or a version that differs. **And the README's
commands, verbatim**, so a step that lives only in somebody's memory is a step the clone does not
take.

Then the failure, and it is the one every project meets on the day it is handed over: the lockfile
was never committed. `uv.lock` is in the working copy; it was generated the first time `uv sync`
ran; it is in `.gitignore` in half the templates on the internet. The commit looks complete, the
warm machine is green, and the clone cannot install anything — or worse, installs something else.
`--locked` is what makes it the first of those and not the second.

## The mechanism

The clone. From a folder that has never held this project, with a cache that has never held these
packages, and the README open:

```bash
git clone <this project's repository> p01-clone
cd p01-clone
git log --oneline | wc -l
git ls-files | wc -l
ls .env .venv
```

```
--- 2 commit(s), 74 files
ls: cannot access '.env': No such file or directory
ls: cannot access '.venv': No such file or directory
```

**Line by line:**

- `74 files` — **every file in `CODEMAP.md` and no other.** The two `ls` errors are the point: the
  clone has no environment and no secret. Both would have come along with a copied folder, and
  neither may.
- `2 commit(s)` — this throwaway repository's whole history. Yours has twenty, one per day.

**Line by line:**

- `UV_CACHE_DIR=/tmp/uvcache-cold` — **an empty cache, named on the command.** Without it, `uv`
  would link every package from this machine's cache in under a second and the transcript would
  prove nothing about the network. With it, every one is fetched — the `Downloading` lines are the
  evidence — and the total says what a stranger's first install costs.
- `Using CPython 3.12.12` — **the interpreter day 0 pinned, chosen from the pin file**, before a

- `Resolved 125 packages in 1ms` — **one millisecond, because nothing was resolved.** `--locked`
  read the lock and checked it against `pyproject.toml`; the number is the lock's own. Compare the
  failure below, where this line does not appear at all.
- `Downloading scipy (35.0MiB)` — **the largest single download in the desk is a numerical library
  the desk never imports.** It came with day 18's evaluation extra, and this transcript is the
  moment the README's last bullet — the extra in its own group — stops being an opinion.
- `Prepared 123 packages` and `Installed 123 packages` — **123, not 125:** the lock counts the
  project's own two entries that are not installed as distributions. The image's `--no-dev` install
  would be five fewer.

- `292 passed` — **the same count as this machine**, from a tree that shares nothing with it but
  the commit. Sixty-two seconds against twenty on the warm machine, and the difference is the cold
  cache's first import of the framework and the audit's in-process runs.
- **Day 0's four `ok` lines, on a machine day 0 never touched.** The first of them — `interpreter
  3.12.12, as pinned` — is the whole of day 0's argument arriving: the pin file decided, not the
  machine.
- `eval: green` — **the slow gate, on the clone.** Twelve claims through forty boundary launches,
  and the baseline line beside the score. This is the sentence the project brief has been pointed at
  since day 0, and this is the machine it has to be true on.

Now the failure — the commit that forgot the lockfile. A branch with `uv.lock` removed from the
history, cloned the same way:

```bash
git clone --branch nolock <this project's repository> p01-clone-nolock
cd p01-clone-nolock
ls uv.lock
UV_CACHE_DIR=/tmp/uvcache-cold uv sync --locked
```

```
ls: cannot access 'uv.lock': No such file or directory
Using CPython 3.12.12
Creating virtual environment at: .venv
error: Unable to find lockfile at `uv.lock`, but `--locked` was provided. To create a lockfile, run `uv lock` or `uv sync` without the flag.
```

**Line by line:**

- **The interpreter was chosen and the environment created before the error** — the pin file was
  there; the lock was not. So the failure is precisely the lock and nothing upstream of it.
- `error: Unable to find lockfile at `uv.lock`, but `--locked` was provided.` — **the flag turned a
  silent resolve into a refusal.** Without `--locked`, this command resolves from `pyproject.toml`,
  writes a brand-new `uv.lock` on the stranger's machine, installs whatever it chose today, and runs
  green on an environment that has never been tested. The hint in the message — *run `uv lock`* —
  is the fix for the person who owns the repository, and exactly the wrong thing for the person who
  cloned it.
- **The commit looked complete.** `git status` on the warm machine was clean, because `uv.lock`
  had been untracked from the start; the warm machine's `.venv` was built from it months ago and
  never asked again. Only the clone finds this, and only a clone with `--locked` finds it as an
  error rather than as a different environment.

And the quieter cousin — the lock is committed, and a pin moves without it. In the clone, bump one
version in `pyproject.toml` and install:

```bash
sed -i 's/"ruff==0.16.6"/"ruff==0.16.7"/' pyproject.toml
uv sync --locked
```

```
error: The lockfile at `uv.lock` needs to be updated, but `--locked` was provided.

hint: To update the lockfile, run `uv lock`.
```

**Line by line:**

- **Same flag, second refusal.** The lock exists and disagrees with the project; `--locked` will not
  choose between them. This is the message part 3.1's pipeline prints on the push that bumped a pin
  and forgot the lock, and it is the message the `Dockerfile`'s builder stage prints on the same
  commit.
- **Three places, one flag, one sentence:** the pipeline, the image and the clone all run `uv sync
  --locked`, and all three refuse the same two mistakes with the same two messages. That is what
  it means for a lock to be the environment rather than a suggestion about it.

## When it breaks

The two failures above are the mechanism's. The one this section is for is the cold clone that was
*not* run — the project handed over on the strength of `python p.py verify` and a green check on
the machine it was built on. There is no error text for it, and that is what makes it the failure
worth naming: it goes wrong on the stranger's machine, in the stranger's terminal, in a form the
author never sees.

Here is the shape of what they see, assembled from what this clone would have shown had each of
its three protections been missing. Without an empty folder, `./run check` passes on a copied
`.venv` with a Windows interpreter that will never start on the branch's Linux. Without an empty
cache, `uv sync` links every package from the author's cache and a pin that was never really in
the lock is discovered by the first machine that has to download it. Without the README's commands
verbatim, the step the author always did by hand — `cp .env.example .env` — is the step the clone
never takes, and day 0's check says `no .env: copy .env.example to .env and fill the value in`,
which is at least a good message.

The smallest fix is to run it, once, before the project is called finished, and to paste what it
printed where the next person will read it — which is here, and in the ledger.

## In production

**What a senior writes instead.** The cold clone as a pipeline job rather than a ritual: a second
workflow that clones the repository into a fresh runner with `UV_CACHE_DIR` pointed at an empty
directory and `enable-cache: false`, and runs the README's commands and nothing else — so the
question "does a stranger's clone start" is asked by a machine on every release and not by a person
on the last day. And the README's commands extracted from the README by the job, so the document
and the job cannot drift.

**What degrades at scale.** Fifty-three seconds of downloads for one clone is nothing. An insurer
onboarding a desk per region with a team per desk is twenty clones a month, and the scipy line
alone is thirty-five megabytes each — small, until the day the artifact registry the packages come
from rate-limits the office's address and every clone in the building stalls at `Downloading`.
That is the day a private package mirror stops being a platform team's luxury, and the lock is
what makes a mirror possible: every version the desk will ever ask for is written down.

**The review comment.** *"The cold clone was run on the author's machine with an empty cache
directory, which proves the packages download. It does not prove they download on a machine with a
different operating system — `pywin32` is in that list and will not exist on the runner. Run it on
Linux before calling it cold."* (It is right. The pipeline in part 3.1 is where that run happens,
and the `TODO(me)` there is the missing transcript.)

**The interview question.** *"Your project works on your machine and in CI. Give me three things a
fresh clone on a colleague's laptop can still get wrong, and the one command that catches two of
them."*
