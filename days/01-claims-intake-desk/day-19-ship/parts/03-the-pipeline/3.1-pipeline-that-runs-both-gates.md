## One-line answer

A workflow file that runs day 18's two gates on a machine nobody prepared, on every push — `uv`
pinned to the version this desk was built with, the environment installed with `--locked`, the fast
gate before the slow one, and a key that is not a key so that day 0's check passes without a secret
ever reaching a runner.

## The idea

The regional inspector does not audit a branch when the branch feels ready. They audit on a
schedule the branch does not control, on files the branch did not choose, and the branch does not
open for business until the report says so.

That is what a pipeline is for, and it is the last thing this project builds because it is the
thing that makes everything else stick. Day 18's file audit is a gate on this machine, run when
somebody remembers. In a pipeline it is a gate on every change, run by a machine that was empty a
minute earlier, and a change reaches `main` only if the audit says twelve of twelve. The discipline
the pipeline adds is not a new check. It is that the checks stop being optional.

The machine being empty is the point, and it is the same point day 0 made: a check that passes on
a laptop that has been set up over twenty days proves that laptop is set up. A runner has nothing —
no interpreter, no `uv`, no packages, no `.env` — and every one of those has to arrive from the
repository, by a step in this file. So the file is a list of what a bare machine needs, in the
order it needs it, which is `SETUP.md` with a machine reading it instead of a person. If the two
disagree, one of them is wrong, and the runner is the one that finds out.

Two things about the key. The desk's stand-in models answer every call, so neither gate contacts a
provider and no secret is needed. But day 0's `check.py` refuses to pass with an empty `.env` —
correctly, because a clone with no key is a clone that will fail on its first real call — and `./run
check` runs that check. So the runner gets a value that is visibly not a key, written into `.env` by
a step that says so, and a real key is never stored in the pipeline's secrets because nothing in it
would use one. The day that changes is the day a gate runs against a provider, and that is the
production note.

Honesty about what ran: this file was not run by the service it is written for, because this
project's throwaway repository has no remote. It was parsed, its shape was checked against the
service's reference, and every action in it was looked up live today. The run itself is the
`TODO(me)` at the end, with the command that reads its result.

## The mechanism

The whole file, at `.github/workflows/check.yml`:

```yaml
# The two gates day 18 built, run by a machine nobody has prepared, on every push.
#
# The fast gate first, because it is seconds and fails on a typo. The slow gate second, because it
# launches the desk forty times and fails on a claim. A change reaches `main` only if both are
# green, and the report of the slow one is in the job's log where the reviewer reads it.

name: check

on:
  push:
    branches:
      - main
  pull_request:
    branches:
      - main

permissions:
  contents: read

jobs:
  gates:
    runs-on: ubuntu-latest
    timeout-minutes: 15
    env:
      # The desk's own stand-in models answer every call, so no provider is contacted and no key
      # is needed for either gate. The name is set to a value that is not a key so that day 0's
      # `key present` check passes and nothing can mistake this runner for a place that holds one.
      GOOGLE_API_KEY: not-a-key-ci-runs-the-stand-ins
    steps:
      - uses: actions/checkout@v7

      - uses: astral-sh/setup-uv@v10
        with:
          version: "0.12.3"
          enable-cache: true

      - name: the interpreter the desk pinned
        run: uv python install

      - name: the environment, exactly as locked
        run: uv sync --locked

      - name: the .env day 0's check insists on
        run: printf 'GOOGLE_API_KEY=%s\n' "$GOOGLE_API_KEY" > .env

      - name: the fast gate
        run: ./run check

      - name: the slow gate
        run: ./run eval
```

**Line by line:**

- `on: push: branches: - main` and `pull_request: branches: - main` — **every push to `main` and
  every pull request against it**, in the shape the workflow reference documents. A pull request
  runs the gates on the merge before it lands, which is the whole point; the push run is the record
  that what landed was green.
- `permissions: contents: read` — **the runner can read the repository and do nothing else.** The
  default grants more; a job that only runs checks needs only this, and the line is what stops a
  compromised dependency in the fifty-two from writing to the repository with the job's token.
- `runs-on: ubuntu-latest` — **the service's standard runner**, which its documentation maps to
  Ubuntu 24.04 today. A Linux machine, like the container; this desk was written on Windows, and the
  runner is where the difference would show.
- `timeout-minutes: 15` — **a bound, for the same reason day 10's loop has one.** The slow gate
  takes a minute here and a runner is not this machine; a job that hangs on a boundary launch that
  never returns would otherwise hold a runner for the service's default of six hours.
- `env: GOOGLE_API_KEY: not-a-key-ci-runs-the-stand-ins` — **a value that says what it is.** Day
  1's `keys.require` needs the variable non-empty; the stand-ins never read it; and if a future
  change makes a gate contact a provider, the provider's `401` will quote this string back, which
  is a better failure than a real key quietly spending money in a pipeline.
- `uses: actions/checkout@v7` — **the checkout action at its current major**, looked up on its
  releases page today (v7.0.1). Nothing runs before this: the runner has no code yet.
- `uses: astral-sh/setup-uv@v10` with `version: "0.12.3"` — **uv, pinned to the version this desk
  was built with**, the same 0.12.3 as `PACKAGES.md` and the `Dockerfile`. The action's README
  recommends pinning by commit hash; `@v10` is its current major, and the hash form is the
  production note. `enable-cache: true` keeps the packages between runs so the fifty-two are not
  downloaded every push.
- `run: uv python install` — **the interpreter, from `.python-version`.** The runner has a Python
  of its own and this desk does not use it: uv reads the pin file day 0 wrote and installs
  3.12.12, exactly as it did on day 0's machine.
- `run: uv sync --locked` — **the lock, or nothing.** The same flag as the `Dockerfile` and for the
  same reason; part 4.1 shows what it prints when the lock is stale. Without `--no-dev`, because
  this environment runs ruff and pytest and the image does not.
- `run: printf 'GOOGLE_API_KEY=%s\n' "$GOOGLE_API_KEY" > .env` — **the `.env` day 0's check
  insists on**, written from the job's own variable. `printf` rather than `echo` because `printf`
  does not interpret its argument; the file has one line and it is the one `.env.example` names.
- `run: ./run check` then `run: ./run eval` — **the two gates, in the order day 18 chose.** The
  driver is the same file a person runs, and it is executable in the checkout because git kept the
  bit day 1 set. A red `./run check` stops the job before the minute-long audit; a red `./run eval`
  is the report in the log, one claim per line.

What this machine can say about the file — the same reading part 2.1 gave `compose.yaml`:

```bash

from ruamel.yaml import YAML
flow = YAML(typ='safe').load(open('.github/workflows/check.yml'))
print(flow['name'], list(flow['on']))
print([step.get('uses') or step.get('name') for step in flow['jobs']['gates']['steps']])
"
```

```
['actions/checkout@v7', 'astral-sh/setup-uv@v10', 'the interpreter the desk pinned', 'the environment, exactly as locked', "the .env day 0's check insists on", 'the fast gate', 'the slow gate']
```

**Line by line:**

- `list(flow['on'])` — **the two triggers, read back.** (One parser quirk is worth knowing: in
  YAML's older spec `on` is a boolean, and some parsers return the key as `True`; this one returns
  the string.)
- **Seven steps, in the order the runner will take them**, and the names are sentences on purpose:
  a job log that says `the .env day 0's check insists on` failed tells the reader which day to
  open.

## When it breaks

The mistake this file is shaped to prevent is in the fifth step. Write `uv sync` without the flag:

```diff
       - name: the environment, exactly as locked
-        run: uv sync --locked
+        run: uv sync
```

It is green — today, and every day the lock is current. The day somebody bumps a pin in
`pyproject.toml` and forgets to run `uv lock`, it is still green: `uv sync` quietly re-resolves,
rewrites `uv.lock` on the runner, installs whatever it resolved to, and runs the gates against an
environment that exists nowhere but on that runner and matches no commit. The tests pass on
packages nobody chose. With the flag, the same push does this, which part 4.1 shows on a real
clone:

```
error: The lockfile at `uv.lock` needs to be updated, but `--locked` was provided.

hint: To update the lockfile, run `uv lock`.
```

That is a red step with the fix in the message, three minutes after the push, on the change that
caused it. Without the flag it is a green step, a `uv.lock` in the repository that no longer
describes any environment that has been tested, and a container built from it on release day. The
smallest fix is the flag, and the rule is day 1's: **the lock, or nothing.**

## In production

**What a senior writes instead.** Actions pinned by commit hash with the version in a comment —
`astral-sh/setup-uv@bec219d24cd3e171d82865faccec33120bb574f4 # v10.1.0` is the form the action's
own README shows — because a major tag is a pointer somebody else moves, and a workflow that reads
the repository with a token is exactly where a moved pointer costs most. A matrix of two operating
systems, since this desk was written on one and runs on another. And the slow gate against a real
provider, nightly rather than on every push, with the key in the service's encrypted secrets and a
budget assertion in the job: `./run eval` spends fifteen calls, and a job that spent sixteen is red
before anybody reads the audit.

**What degrades at scale.** Every push runs the desk forty times through a subprocess boundary — a
minute on this machine, and a runner is slower. At a team's pace of thirty pushes a day that is a
runner-hour a day spent launching Python, and the slow gate is the step people learn to skip with a
label. The fix is the one day 17 measured and the README names: the boundary as a sidecar in the
pipeline too, started once as a service container, so the audit's forty launches become forty
requests and the minute becomes seconds.

**The review comment.** *"`./run eval` prints its report to the job log, where it scrolls past. Post
the twelve lines and the baseline as a comment on the pull request — the reviewer should see
`FNOL-4474 RED` without opening a log."*

**The interview question.** *"Your CI installs dependencies with the package manager's default
command and the tests are green. Tell me a change that makes them pass in CI and fail in
production, and the one flag that would have caught it."*
