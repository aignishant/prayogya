## One-line answer

`date_of_loss: date` turns into `{"type": "string", "format": "date"}` in the schema a model reads,
and it turns a wrong date into a refusal at the boundary instead of a wrong comparison inside it.

## The idea

The request slips have boxes, and one of them is printed differently from the others. Most boxes are
a ruled line: write what you like. The date box is eight small squares with a caption underneath —
`D D / M M / Y Y Y Y`.

The squares are not decoration and they are not about neatness. They exist because a date written
freely is written eleven different ways by eleven people, and the department receiving the slip
cannot tell `03/04` from `04/03` without knowing who filled it in. The squares make one reading
possible and every other reading impossible to write down.

Every parameter on this desk's docket so far has been a ruled line: a policy number, a claim
reference, an outcome. Strings, and the description does the work of saying what shape they take.
`date_of_loss` is the first box with squares in it, and this part is about what that buys.

Two things, and they are separate. **On the way out**, the annotation appears in the schema a model
reads, in the standard vocabulary for saying "this is a date", so the model is *told* the format
rather than left to infer it from an example. **On the way in**, a value that is not a date is
refused before the function runs — by the SDK, at the boundary, with a message naming the parameter.

The second is the one that matters most for this project, and day 2 is why. A malformed date that
gets through does not fail: it compares, as text, and produces a policy that was never in force on a
day it plainly covered. The squares on the box are what stop that being possible.

## The mechanism

The declaration, from `claims_mcp/tools.py` as printed in part 1.1 — one line of signature and one
line of description:

```python
def check_in_force(number: str, date_of_loss: date) -> dict[str, Any]:
    """Was a policy on risk on the day the loss happened?

    Args:
        number: The policy number, for example `SYN-POL-1001`.
        date_of_loss: The day the loss happened, as `YYYY-MM-DD`. Not the day it was reported.
    """
```

**Line by line:**

- `date_of_loss: date` — the annotation, and `date` is `datetime.date`, imported at the top of the
  module. **This is the only non-string parameter in the whole docket**, which makes it the only one
  where the annotation changes what a caller is told.
- `number: str` beside it — unchanged, and worth the comparison. Both parameters are annotated;
  only one of them is *saying* anything a caller could not have guessed.
- **"as `YYYY-MM-DD`"** in the description — belt and braces. The schema already says `format:
  date`, and a model that ignores the schema still has the format in the prose. Neither is
  redundant: one is machine-readable and one survives being summarised.
- **"Not the day it was reported."** — the clause that rules out the plausible mistake. Every
  notification in this project has both fields, they differ by a day on most claims, and a model
  handed the whole notification will reach for the wrong one unless told which.

What a model is shown, on the wire:

```
check_in_force: Was a policy on risk on the day the loss happened?
    {"number": {"title": "Number", "type": "string"}, "date_of_loss": {"format": "date", "title": "Date Of Loss", "type": "string"}}
    required: ['number', 'date_of_loss']
```

**Line by line:**

- `"type": "string"` **and** `"format": "date"` — a date is carried as a string, because JSON has no
  date type. `format` is JSON Schema's standard annotation for saying which kind of string, and
  `date` means a calendar date in `YYYY-MM-DD`.
- **The pairing is the whole mechanism.** A caller that understands `format` gets a precise
  instruction; a caller that does not still knows to send a string, so nothing breaks for not
  understanding.
- `required: ['number', 'date_of_loss']` — both, because neither has a default. The optional
  parameter in this docket is `record_decision`'s `reason`, and it is absent from that tool's
  required list for exactly the same mechanical reason.
- `"title": "Date Of Loss"` — derived from the parameter name by splitting on the underscore. It is
  what a human-facing client shows above the input box, which is a pleasing symmetry with the pad of
  slips.

And what happens on the way in. Three dates a caller might plausibly send, none of them a date:

```bash
uv run python -c "
import asyncio, json
from mcp import Client
from claims_mcp.server import server
async def main():
    async with Client(server) as c:
        for bad in ('14/03/2026', '2026-3-14', 'last Tuesday'):
            r = await c.call_tool('check_in_force', {'number':'SYN-POL-1001','date_of_loss':bad})
            text = (r.content[0].text if r.content else '').replace(chr(10), ' | ')
            print(json.dumps({'sent': bad, 'is_error': bool(r.is_error), 'text': text[:170]}))
asyncio.run(main())
"
```

```
{"sent": "14/03/2026", "is_error": true, "text": "Error executing tool check_in_force: 1 validation error for check_in_forceArguments | date_of_loss |   Input should be a valid date or datetime, invalid character in year"}
{"sent": "2026-3-14", "is_error": true, "text": "Error executing tool check_in_force: 1 validation error for check_in_forceArguments | date_of_loss |   Input should be a valid date or datetime, input is too short [type="}
{"sent": "last Tuesday", "is_error": true, "text": "Error executing tool check_in_force: 1 validation error for check_in_forceArguments | date_of_loss |   Input should be a valid date or datetime, invalid character in year"}
```

**Line by line:**

- **All three refused, and none of them reached the function.** The validation happens in the SDK,
  between the request arriving and `check_in_force` being called, so there is no branch inside the
  tool for "the date was rubbish".
- `is_error: true` — and this is the right use of the error flag. The other refusals in this docket
  — an unknown policy, an unknown outcome — are answers, returned as data. **A malformed argument is
  not an answer**: the request itself was wrong, and the caller has to fix the request rather than
  read a result.
- `1 validation error for check_in_forceArguments | date_of_loss` — **the parameter is named.** A
  model receiving this can correct one field and try again, which is the difference between a
  recoverable failure and a dead end.
- `"14/03/2026"` → `invalid character in year` — the parser read `14` as a year and then met a
  slash. The message is about what the parser saw, not about what a person meant, and that is worth
  knowing when reading these: it will not say "looks like day/month/year".
- **`"2026-3-14"` → `input is too short`.** This is the one to stop on. That value is the exact
  failure from day 2 part 1.1 — a date with the leading zero dropped — and there it produced **no
  error at all**: compared as text it sorted after October and reported a live policy as not in
  force. Here, one annotation later, it is refused before anything compares anything.
- `'last Tuesday'` → refused. Not interpreted, not resolved against today, not passed through. A
  model that says something plausible instead of something correct gets told so.

## When it breaks

Take the annotation off — `def check_in_force(number: str, date_of_loss)` — and the boundary stops
objecting. The SDK falls back to `string` for an un-annotated parameter, as day 3 part 3.1 found, so
`'last Tuesday'` arrives at the function as a five-character string and the comparison
`policy.inception <= date_of_loss` raises inside the tool instead:

```
Error executing tool check_in_force
```

That is the whole message the caller gets. The comparison failed with a `TypeError` deep in the
function, the SDK wrapped it, and **the original message did not cross the line** — part 3.2 is the
same discovery from the other direction. A model on the other end is told that something went wrong
with a tool and given no way to tell which of its two arguments was the problem.

Somebody removed the annotation while adding a second date parameter and copying the first one's
signature. The smallest fix is `: date`. The lesson is that in this file an annotation is not a hint
for a reader or a checker — **it is the difference between a refusal that names a field and an error
that names nothing.**

## In production

**What a senior writes instead.** The same annotation, plus a constraint the type cannot carry: a
date of loss in the future is not a validation error in JSON Schema terms and is certainly an error
at an intake desk. That check belongs inside the tool, returning a refusal as data — the shape the
other three refusals in `record_decision` already use — because "your date is in the future" is
something a caller can act on, and the argument was well-formed.

**What degrades at scale.** Free-text dates are the single most reliable source of quiet wrongness
in claims systems, because every wrong reading is also a valid date. A desk taking several hundred
notifications a day, with dates arriving from a model that read them out of a sentence a caller
spoke, will produce a steady trickle of plausible mis-parses — and the ones that matter are the
ones near a policy's inception or expiry, which is exactly where a cover decision turns. One
annotation removes the entire class at the boundary.

**The review comment.** *"This takes `date_of_loss: str` and calls `date.fromisoformat` inside the
function. Annotate it as `date` — then the schema tells the model the format, the refusal names the
field, and the `try` block goes away."*

**The interview question.** *"Your tool takes a date. Walk me through everything that happens
between a caller sending `'2026-3-14'` and your function running — and tell me where you would
rather the failure happened."*

- **Say out loud:** A malformed date comes back with `is_error: true`, and an unknown policy number
