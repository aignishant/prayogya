## One-line answer

`server.py` stops being where tools live and becomes where they are *declared* — a server object, a
three-line registration loop, and the two things that are one expression each.

## The idea

The pad of request slips is printed by one department and used by another. When there was a single
slip, the two jobs were indistinguishable: somebody wrote the heading and somebody used it, and
they were the same person on the same afternoon.

At four slips they come apart. Writing a slip is deciding what a department can be asked for.
Printing the pad is deciding which of those slips actually goes out. They are different decisions,
made at different times, and the second one is where somebody says *no, we are not offering that
yet.*

This part is the second decision. `claims_mcp/tools.py` now holds four functions and a tuple naming
which of them are on the docket; `claims_mcp/server.py` holds the server's identity, the loop that
registers them, and the resource and prompt from day 4 — which stay here because each is a single
expression with a decorator, and a file called `tools.py` containing a prompt would be a lie.

The split is not tidiness. It is what makes **"what does this boundary offer"** answerable by
reading one screen, and it is the shape that survives the docket doubling.

## The mechanism

The whole file, at `claims_mcp/server.py`. Day 4 printed this file with `fetch_policy` inside it;
the tool has moved to `tools.py`, and the resource and the prompt below are unchanged from that
version:

```python
"""The claims boundary: the only process that opens the policy store.

This file is the wiring. It builds the server, registers everything the boundary offers, and holds
nothing else — the tools live in `claims_mcp/tools.py`, one function each, and the resource and the
prompt are here because they are one expression apiece.

Run it over stdio with `python -m claims_mcp`, over Streamable HTTP with
`python -m claims_mcp --http`, or in-process from a test by handing the `server` object straight
to a `Client`.
"""

from __future__ import annotations

from typing import Any

from mcp.server import MCPServer

from claims_desk.domain import PHOTO_REQUIRED_FOR
from claims_mcp.tools import DECLARED, store

#: The server's identity. A client reads this back and it appears in every log the boundary keeps,
#: so the version moves when what this server declares changes.
server = MCPServer(
    name="claims-boundary",
    title="Claims Intake Desk boundary",
    version="0.3.0",
    instructions=(
        "The policy store and the claim file for a first-notice-of-loss desk. "
        "Every policy in it is synthetic. Ask for a policy by its number; there is no way to "
        "list them all, and no way to read a file."
    ),
)

# Registration, in one loop. Each function's name, description and argument schema are derived
# from the function itself, so this file adds nothing to what `tools.py` already says.
for _tool in DECLARED:
    server.tool()(_tool)


@server.resource(
    "claims://cover/perils",
    name="perils",
    title="The perils this book of business knows",
    description=(
        "Every peril slug that appears on a policy in this store, and whether a photograph is "
        "part of a complete notification for it. Reference data: it does not change per claim, "
        "so a client reads it once rather than asking a tool on every notification."
    ),
    mime_type="application/json",
)
def perils() -> dict[str, Any]:
    """The peril vocabulary, with the photograph rule attached to each."""
    known = sorted({peril for policy in store.policies() for peril in policy.perils})
    return {peril: {"photo_required": peril in PHOTO_REQUIRED_FOR} for peril in known}


@server.prompt(
    name="deficiency_letter",
    title="Draft a deficiency letter",
    description="The house style for telling a policyholder what is missing from their claim.",
)
def deficiency_letter(claim_id: str, reason: str) -> str:
    """The instructions for writing one deficiency letter.

    A prompt is the server's contribution to how a model should be asked, kept beside the data it
    is about. The desk does not hard-code this wording: the boundary owns the claim file, so the
    boundary owns the house style for writing about it.
    """
    lines = [
        f"Write a short deficiency letter for claim {claim_id}.",
        f"The single reason this claim cannot be fast-tracked is: {reason}.",
        "",
        "Rules:",
        "- Name exactly one missing or failing item. Do not list alternatives.",
        "- Say precisely what the policyholder must send or confirm.",
        "- Do not quote a policy number the caller did not give you.",
        "- Do not promise a decision, a timescale or a settlement figure.",
        "- Four sentences at most, plain words, no apology.",
    ]
    return "\n".join(lines)
```

**Line by line:**

- **"This file is the wiring."** — the first line of the docstring is the file's job description,
  and it is a constraint on what may be added later. A tool appearing in this file is now a visible
  inconsistency rather than a matter of taste.
- `from claims_mcp.tools import DECLARED, store` — **two imports and no others from that module.**
  The tuple, so this file knows what to register, and the store, because the resource below reads
  the policies. Importing the four functions by name would mean adding a fifth tool touches two
  files.
- `version="0.3.0"` — moved again, and again the reason is that the docket changed: one tool became
  four. Day 3's assertion caught it, for the second time in three days, and part 3.1 is where it is
  updated.
- `for _tool in DECLARED: server.tool()(_tool)` — **three lines that replace four decorators.**
  `server.tool()` returns a decorator, and a decorator is an ordinary function, so applying it in a
  loop is the same act written once. The leading underscore on `_tool` says the loop variable is not
  part of this module's interface.
- **The loop registers in the order of the tuple**, so the docket a client sees is the order
  `tools.py` declares — which is the order a reader of that file encounters them. Two files agreeing
  about order without either of them saying so is the kind of coincidence that stops being true; one
  tuple, read by both, is not a coincidence.
- **The comment says the loop "adds nothing to what `tools.py` already says"**, and that is the
  property worth protecting. If registration ever needed an argument — a `title=`, an
  `annotations=` — it would have to be per tool, and the loop would have to become a table, at which
  point the interface would live in two files again.
- `@server.resource(...)` and `@server.prompt(...)` — **decorated in place, because each is one
  expression.** They stayed while the tools moved, and the docstring says why: a file named
  `tools.py` containing a prompt would be misleading, and a `prompts.py` holding one function would
  be a directory structure standing in for a decision.
- `def perils()` — its body now uses the `store` imported from `tools.py`, which is the same object
  the tools use. **One store per server process** is still true after the split, and it is true
  because the store is created in exactly one module.
- **The `log(...)` calls that were in `perils` and `deficiency_letter` on day 4 are gone.** They
  were recording that a resource was read and a prompt was fetched; the tools log, and these two do
  not. That is a deliberate narrowing and it is worth flagging as a small loss: day 17 will want
  those lines back when it wants one trace across every hop.

**Line by line:**

- **Four tools, in the tuple's order.** The registration loop preserved it, which is what makes
  `tools.py` the single place the docket is decided.
- `resources` and `prompts` unchanged from day 4 — the split moved code and not behaviour, and this
  is the evidence rather than the claim.
- `version: 0.3.0` — the one thing that did change, deliberately, and it is the reason a test went

**Line by line:**

- `async def call(tool, arguments)` — **day 4's `fetch_policy` body, with the tool name lifted into
  a parameter.** One place opens a connection, one place decides what `is_error` means, one place
  turns a result into a dictionary. The four functions below it are now two lines each.
- **The docstring moved with the body**, including the sentence about a connection per call, because
  that fact is about `call` and was never about policies.
- **"A tool that refuses does not come back through this path."** The distinction this whole project
  turns on, written where a reader will meet it: `is_error` means the tool could not run;
  `recorded: false` means it ran and said no. Day 6 part 3.2 is the run where the second was
  mistaken for success.
- `raise RuntimeError(f"boundary refused {tool}({arguments!r})")` — **the tool name and the
  arguments in the message.** With one tool the name was decoration; with four it is the first
  thing you need.
- `arguments: dict[str, Any] = {...}` then `if reason is not None:` — **an omitted argument rather
  than an explicit `None`.** Day 5 part 2.1 makes the boundary refuse a `reason` on a fast-track,
  and sending `reason=None` is a different message from sending nothing.
- **Four wrappers rather than four call sites of `call`.** They cost three lines each and they buy a
  desk that names tools in one file: rename a tool on the server and one line changes here, not
  wherever the desk happened to ask.
- `date_of_loss.isoformat()` — **the wrapper does the conversion.** Day 5 part 2.1 is about the
  boundary receiving a real `date`; this is where a Python `date` becomes the string that crosses
  the line, so no caller has to remember.

## When it breaks

Write a tool and forget the tuple:

```python
def draft_letter(claim_id: str, kind: str) -> dict[str, Any]:
    """Draft the letter this claim needs, in the house style."""
    ...
```

```
tools:     ['fetch_policy', 'check_in_force', 'record_decision', 'read_decision']
```

The function exists, it is importable, it has a good description, and **it is not on the docket** —
because `DECLARED` was not touched. A client asking for it gets `Unknown tool: draft_letter`.
Somebody spent a while on this convinced the registration loop was broken, because the loop is the
part that looks like it could be. It is not: the loop registers what it is given, and it was not
given this.

The smallest fix is one name in the tuple. Whether that is a good design is a real question and the
answer here is yes: **writing a tool and publishing a tool are different decisions**, and the second
one should cost a line in a place a reviewer looks. The version bump that follows it is the same
argument again.

## In production

**What a senior writes instead.** The same split, and a registry that carries per-tool metadata —
annotations saying a tool is read-only or destructive, so a client can treat `record_decision`
differently from the other three. The SDK's `server.tool()` takes an `annotations=` argument for
exactly this, and this project does not use it yet; day 16 is where a tool that writes needs to be
distinguishable from three that do not, and the loop will have to become a table then.

**What degrades at scale.** One `tools.py` is right for four tools and wrong for forty. The next
split is by subject — policy tools, claim tools — and the thing that makes it painless is that
`DECLARED` is already the only place the docket is assembled: it becomes a concatenation of tuples
and nothing else moves. The failure mode to avoid is splitting by *shape* — a `readers.py` and a
`writers.py` — which puts two halves of one subject in two files and guarantees that a change
touches both.

**The review comment.** *"This registers the tool inside `tools.py` with a decorator, which works.
Put it in `DECLARED` instead — otherwise `tools.py` imports the server, the server imports the
tools, and the next person to add a module gets a circular import at start-up."*

**The interview question.** *"You split a module into definition and registration. What did that buy
you, what did it cost, and what would make you put them back together?"*
