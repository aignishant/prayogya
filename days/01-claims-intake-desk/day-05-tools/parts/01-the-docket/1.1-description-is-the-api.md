## One-line answer

Four tools in one file, and the first line of each docstring is the entire basis on which a model
will choose between them — so it is written as a sentence a stranger could act on, not as a note to
whoever wrote the function.

## The idea

There is a pad of request slips at the claims desk, one for each department. *Underwriting: confirm
cover.* *Estimating: check a quote.* *Records: retrieve a file.* Each slip has a printed heading and
a small number of boxes, and the whole system rests on the heading, because the person who receives
it is in another building and has never met you.

A new handler was given a pad where somebody had reprinted the headings to save space. *Underwriting
query.* *Estimating query.* *Records.* Every one still meant what it had always meant to the person
who shortened them. To the new handler they meant nothing distinguishable, and the slips started
arriving in the wrong departments — not often, and not in a way anybody could attribute to the
headings.

That is the failure this part is about, and in a fortnight it will not be a metaphor. From day 7 a
model will hold this docket and pick one. It has no colleague to ask, no memory of why the function
was written, and no access to the code: **it sees a name, a sentence, and a schema.** That is the
whole interface.

So a tool's description is not documentation of the tool. It **is** the tool, as far as the only
thing that will ever choose between them is concerned. Written that way, it stops being an
afterthought and becomes the part of the function that gets the most review.

Today the docket goes from one entry to four, and the four are chosen to cover the shapes an intake
desk actually needs: a lookup, a question about a date, a write, and a read that will usually find
nothing.

## The mechanism

The whole file, at `claims_mcp/tools.py`. Day 3 and day 4 kept `fetch_policy` inside
`claims_mcp/server.py`; with four tools the functions move to a file of their own, and the next
part is the wiring that stayed behind:

```python
"""Every tool this boundary declares, and nothing else.

Four functions. Each one's **description is its API**: from day 7 a model chooses between these by
reading the first line of the docstring and nothing else, so each first line says what the tool
does in the caller's terms rather than in ours.

The rules this file keeps, all four of which are visible in every function below:

- **A parameter's annotation is part of the interface.** It becomes the schema a model is shown, so
  `date` means the model is told to send a date, not that we hope it does.
- **Nothing that is not cover crosses the line.** No paths, no filenames, no record ids.
- **An empty answer is an answer.** A policy that does not exist, a claim not yet decided: both come
  back as data with `found: false`, never as an exception.
- **Every call is logged, and the log carries the question rather than the answer.**
"""

from __future__ import annotations

from datetime import date
from typing import Any

from claims_desk.domain import Outcome, Reason
from claims_desk.store import Store
from claims_desk.util.logging import log

#: The one object in this process that touches the disk.
store = Store()


def fetch_policy(number: str) -> dict[str, Any]:
    """Look up one policy by its number.

    Returns the policy's cover and its dates, or `{"found": false}` when the store has never heard
    of that number. A number that does not exist is an answer, not an error: an intake desk is
    given wrong policy numbers every day, and the caller needs a letter rather than a traceback.

    Args:
        number: The policy number exactly as the caller gave it, for example `SYN-POL-1001`.
    """
    policy = store.policy(number)
    log("boundary.fetch_policy", number=number, found=policy is not None)
    if policy is None:
        return {"found": False, "number": number}
    return {
        "found": True,
        "number": policy.number,
        "product": policy.product,
        "status": policy.status,
        "inception": policy.inception.isoformat(),
        "expiry": policy.expiry.isoformat(),
        "excess": policy.excess,
        "fast_track_limit": policy.fast_track_limit,
        "perils": sorted(policy.perils),
    }


def check_in_force(number: str, date_of_loss: date) -> dict[str, Any]:
    """Was a policy on risk on the day the loss happened?

    Answers `in_force: true` or `in_force: false` with the reason, or `{"found": false}` when the
    policy number is unknown. Both halves are checked: a policy can sit inside its own dates and
    still have been cancelled, and a live policy is worth nothing before it incepted.

    Args:
        number: The policy number, for example `SYN-POL-1001`.
        date_of_loss: The day the loss happened, as `YYYY-MM-DD`. Not the day it was reported.
    """
    policy = store.policy(number)
    log("boundary.check_in_force", number=number, date_of_loss=date_of_loss.isoformat())
    if policy is None:
        return {"found": False, "number": number}
    within = policy.inception <= date_of_loss <= policy.expiry
    return {
        "found": True,
        "number": policy.number,
        "in_force": policy.in_force_on(date_of_loss),
        "status": policy.status,
        "within_dates": within,
        "inception": policy.inception.isoformat(),
        "expiry": policy.expiry.isoformat(),
    }


def record_decision(claim_id: str, outcome: str, reason: str | None = None) -> dict[str, Any]:
    """Write the desk's decision about one claim into the claim file.

    The only tool that changes anything. It refuses an outcome or a reason it does not recognise,
    because a claim file with `fasttrack` in it is a claim file no report will ever count.

    Args:
        claim_id: The notification reference, for example `FNOL-4471`.
        outcome: Either `fast-track` or `deficiency`.
        reason: Required when the outcome is `deficiency`, and one of the desk's reason codes.
            Must be omitted when the outcome is `fast-track`.
    """
    log("boundary.record_decision", claim=claim_id, outcome=outcome, reason=reason)
    if outcome not in set(Outcome):
        return {"recorded": False, "refused": f"unknown outcome {outcome!r}"}
    if outcome == Outcome.DEFICIENCY:
        if reason is None:
            return {"recorded": False, "refused": "a deficiency must name a reason"}
        if reason not in set(Reason):
            return {"recorded": False, "refused": f"unknown reason {reason!r}"}
    elif reason is not None:
        return {"recorded": False, "refused": "a fast-track has no reason"}
    store.write_claim(claim_id, {"claim_id": claim_id, "outcome": outcome, "reason": reason})
    return {"recorded": True, "claim_id": claim_id, "outcome": outcome, "reason": reason}


def read_decision(claim_id: str) -> dict[str, Any]:
    """What has this desk decided about one claim, if anything yet?

    Returns `{"found": false}` when no decision has been written. That is the honest answer to a
    question about work that has not happened, and it is different from an error: nothing went
    wrong, there is simply nothing to report.

    Args:
        claim_id: The notification reference, for example `FNOL-4471`.
    """
    record = store.claim(claim_id)
    log("boundary.read_decision", claim=claim_id, found=record is not None)
    if record is None:
        return {"found": False, "claim_id": claim_id}
    return {"found": True, **record}


#: The docket, in the order a client is shown it. Registration happens in `server.py`; keeping the
#: list here means the file that defines the tools is also the file that says which are declared.
DECLARED = (fetch_policy, check_in_force, record_decision, read_decision)
```

**Line by line:**

- **The module docstring is four rules, not a description.** Everything in this file is an interface
  a model reads, so the constraints on writing one belong at the top of the file where the fifth
  tool will be added.
- `from datetime import date` — **imported to be used as an annotation**, which is the subject of
  part 2.1. In every other file in this project a type hint is for readers and checkers; here it is
  a wire format.
- `from claims_desk.domain import Outcome, Reason` — the enumerations from day 2, imported so the
  boundary validates against the same vocabulary the rules use. **The alternative is a second list
  of reason codes in this file**, which would be correct on the day it was written.
- `store = Store()` — moved here from `server.py`, because the tools are what use it. One store per
  server process, as before.
- **`def fetch_policy(...)` is unchanged from day 3** except for its new home. A file split that
  also edits the thing being moved is a change nobody can review.
- **"Look up one policy by its number."** — a sentence, a verb first, and no jargon. Compare the
  version a hurried author writes: *"Policy lookup."* Both are true; only one tells a model what
  will happen if it calls this.
- `date_of_loss: date` — **the annotation that is doing the most work in this file.** It becomes
  `{"type": "string", "format": "date"}` in the schema, which tells a model to send `YYYY-MM-DD`,
  and it makes a malformed date a refusal at the boundary rather than a wrong comparison inside it.
  Part 2.1 is that, in full.
- **"Not the day it was reported."** — one clause in an argument description, and it is the most
  valuable sentence in the file. Every notification in this project carries both a `reported_at` and
  a `date_of_loss`, they are usually a day apart, and a model handed both will pick the wrong one
  unless told. **A parameter description's job is to rule out the plausible mistake**, not to
  restate the parameter's name.
- `def check_in_force(number, date_of_loss)` — the question it answers is a **question**, and the
  docstring's first line is phrased as one. That is not a style flourish: a tool that answers yes or
  no reads better on the docket as an interrogative, and the shape of the sentence tells a model
  what kind of thing comes back.
- `within = policy.inception <= date_of_loss <= policy.expiry` — computed and returned **separately**
  from `in_force`. The tool could return one boolean and be correct; returning both means a caller
  can tell "outside the dates" from "cancelled", which are two different letters. **A tool that
  collapses two reasons into one answer has made a decision that belonged to its caller.**
- `def record_decision(claim_id, outcome, reason=None)` — **the only tool in this project that
  changes anything**, and it says so in its own second line. When day 16 writes the threat model,
  this is the row that matters.
- `reason: str | None = None` — optional, with a default, which is what puts it outside `required`
  in the schema. The docstring then does what the type cannot: it says **when** the argument is
  required and when it must be absent, which is a rule about the *combination* of two arguments and
  has nowhere else to live.
- `if outcome not in set(Outcome):` — validated against the enumeration rather than a literal list.
  `set(Outcome)` works because `Outcome` is a `StrEnum` from day 2, so its members compare equal to
  their strings and the incoming string can be checked directly.
- **The three refusals are `return`, not `raise`.** `{"recorded": False, "refused": "..."}` is a
  result: the call succeeded, the boundary declined, and the caller is told exactly which rule it
  broke. Part 3.2 is what changes when that becomes an exception.
- `f"unknown outcome {outcome!r}"` — `!r` quotes the value, so `'fasttrack'` is visibly a string
  with no hyphen rather than something that might be a typo in the message itself.
- `store.write_claim(...)` — day 2's atomic replace, called from here and nowhere else. The write
  is behind the boundary, so a claim file cannot be half-written by something above it, and the
  reason that matters is now two layers away from the code that does it.
- `def read_decision(claim_id)` — **the tool that will usually find nothing**, and its docstring
  spends three lines saying that this is fine. "Nothing went wrong, there is simply nothing to
  report" is the sentence day 6 builds a whole day on.
- `return {"found": True, **record}` — the stored record, spread, with a `found` flag in front. The
  caller checks one field regardless of the answer, which means no caller needs a `try`.
- `DECLARED = (fetch_policy, check_in_force, record_decision, read_decision)` — **a tuple, at the
  bottom, naming the docket in order.** Immutable, so nothing can append at run time; explicit, so
  adding a function to this file does not silently publish it. Writing a tool and declaring a tool
  are two decisions and this line is the second one.

**Line by line:**

- **Four sentences, and they are distinguishable.** Read them as a stranger: a lookup, a
  yes-or-no about a date, a write, and a read. Nothing about the wording requires knowing this
  project.
- `"format": "date"` on `date_of_loss` and nowhere else — **the annotation crossed the line.** It is
  the only parameter in the docket that is not a plain string, and the schema says so in the
  standard vocabulary.
- `"anyOf": [{"type": "string"}, {"type": "null"}], "default": null` — `str | None = None`, in
  schema. A model reading this is told the argument may be omitted and may be null, which is
  exactly what the Python says.
- `required: ['claim_id', 'outcome']` — **`reason` is absent from the required list**, and no line
  of JSON anywhere says when it becomes necessary. That rule lives only in the prose, which is why
  the prose is part of the interface rather than a comment on it.
- `"title": "Date Of Loss"` — generated from the parameter name. Nobody wrote it; it is what a
  client shows a person choosing arguments by hand.

## When it breaks

The docstring's first line is load-bearing, and nothing about Python makes it so. Replace
`check_in_force`'s with the kind of heading somebody writes when they are shortening a pad of slips
— `"""Cover check."""` — and everything still works: the tool runs, the tests that call it pass,
the schema is unchanged. Only the docket changes:

```
fetch_policy: Look up one policy by its number.
check_in_force: Cover check.
record_decision: Write the desk's decision about one claim into the claim file.
read_decision: What has this desk decided about one claim, if anything yet?
```

Read that as the only information you have. *Cover check* could be the in-force question, or it
could be the peril question — this desk has both — and there is nothing to distinguish them. The
argument names help; they are also the thing a model reads *after* it has already chosen. Somebody
tidied a docstring in a pull request that touched eleven files, nobody read it as an interface
change, and the wrong tool started being called on a fraction of claims that nobody could
characterise. The smallest fix is the sentence. The check that catches it is in part 3.1:
`test_every_tool_says_what_it_does_in_its_first_line`, which requires a full stop or a question
mark and at least five words — crude, and enough to make a one-word heading impossible.

## In production

**What a senior writes instead.** The same functions, with the descriptions reviewed by whoever owns
the process rather than by whoever wrote the code — because "not the day it was reported" is a claims
rule, not a programming one, and the person who knows it is not the person typing. They would also
keep the docket small on purpose: every tool is an option a model weighs on every turn, and the
fifth similar-sounding tool costs accuracy on the other four.

**What degrades at scale.** Four tools is a docket anybody can hold. A boundary that has grown to
thirty is a menu, and the failure is not that a model cannot read thirty descriptions — it is that
descriptions written independently overlap, and overlapping options are chosen between at random.
An insurer's intake platform accumulates tools the way it accumulates forms: one per exception,
each obviously justified. The discipline that holds is refusing to add one until the sentence
distinguishing it from every existing tool has been written.

**The review comment.** *"`date_of_loss` is described as 'the date of loss'. Say what it is not —
we have `reported_at` on every notification, they differ by a day on most claims, and the model has
both in front of it."*

**The interview question.** *"Your tool descriptions are docstrings. Who reviews them, what happens
if two of them overlap, and how would you find out that they had?"*
