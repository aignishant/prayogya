## One-line answer

Every tool result arrives twice — a text block for a model to read and a structured copy for a
program to parse — and fourteen tests hold the docket to its names, its schemas, its refusals and
that pair.

## The idea

A slip comes back from underwriting with two things on it. There is the printed section, filled in:
policy number, in force, dates. And there is a line at the bottom in somebody's handwriting — *this
one lapsed in May, they've been chased twice.*

Both are the same answer. The printed section is what gets keyed into the system; the handwritten
line is what the handler actually reads. Neither is redundant, and a department that stopped
sending one of them would be worse at its job in a way that took months to notice.

A tool result has exactly this shape. It carries **content** — a list of typed blocks, in practice
one block of text — which is what a model reads. And it carries **structured content**, the same
value as data, which is what a program parses. The SDK produces both from one `return`: the
dictionary is serialised into the text block and attached as the structured copy.

Knowing there are two matters for a reason that will not be obvious until day 7: they can disagree.
A tool that builds the text itself and returns something else as data has two answers in one
envelope, and the model and the program will act on different ones. Nothing checks that they match.
So this project asserts it.

That is one of fourteen tests here. The rest hold the things the last three parts claimed: the
docket is four tools in a stated order, each description is a sentence somebody could act on, a date
is declared as a date, an optional parameter is not required, a malformed argument is refused before
the function runs, and a write refuses four shapes it does not recognise.

## The mechanism

The whole file, at `tests/test_tools.py`:

```python
"""The docket: four tools, what a model is shown of them, and what they refuse.

These tests are about the tools as an *interface* — the names, the schemas, the shape of an answer
and the shape of a refusal. What the tools do with the data is day 2's business and is tested
there.
"""

from __future__ import annotations

import asyncio
import json
from collections.abc import Awaitable, Callable
from typing import Any

import pytest
from mcp import Client

from claims_mcp import tools
from claims_mcp.server import server


def ask(work: Callable[[Client], Awaitable[Any]]) -> Any:
    """Run one coroutine against an in-process client and return what it produced."""

    async def run() -> Any:
        async with Client(server) as client:
            return await work(client)

    return asyncio.run(run())


@pytest.fixture(autouse=True)
def _isolate_claims(tmp_path, monkeypatch):
    """Point the boundary's store at a temporary directory for every test in this file.

    `record_decision` writes. Without this, running the suite would leave claim files in the
    project and the tests would pass or fail depending on what an earlier run had written.
    """
    monkeypatch.setattr(tools.store, "claims", tmp_path / "claims")


def test_the_docket_is_four_tools_in_a_stated_order() -> None:
    names = ask(lambda c: c.list_tools())
    assert [tool.name for tool in names.tools] == [
        "fetch_policy",
        "check_in_force",
        "record_decision",
        "read_decision",
    ]


def test_every_tool_says_what_it_does_in_its_first_line() -> None:
    """The first line of the docstring is what a model chooses on. It has to be a sentence."""
    listed = ask(lambda c: c.list_tools())
    for tool in listed.tools:
        first = (tool.description or "").splitlines()[0].strip()
        assert first.endswith((".", "?")), f"{tool.name}: {first!r}"
        assert len(first.split()) >= 5, f"{tool.name}: {first!r}"


def test_a_date_parameter_is_declared_as_a_date() -> None:
    listed = ask(lambda c: c.list_tools())
    by_name = {tool.name: tool for tool in listed.tools}
    schema = by_name["check_in_force"].input_schema
    assert schema["properties"]["date_of_loss"] == {
        "format": "date",
        "title": "Date Of Loss",
        "type": "string",
    }
    assert schema["required"] == ["number", "date_of_loss"]


def test_an_optional_parameter_is_not_required() -> None:
    listed = ask(lambda c: c.list_tools())
    by_name = {tool.name: tool for tool in listed.tools}
    schema = by_name["record_decision"].input_schema
    assert schema["required"] == ["claim_id", "outcome"]
    assert schema["properties"]["reason"]["default"] is None


@pytest.mark.parametrize("sent", ["14/03/2026", "2026-3-14", "last Tuesday"])
def test_a_malformed_date_is_refused_before_the_function_runs(sent: str) -> None:
    result = ask(
        lambda c: c.call_tool("check_in_force", {"number": "SYN-POL-1001", "date_of_loss": sent})
    )
    assert result.is_error is True
    assert "date_of_loss" in result.content[0].text


def test_in_force_checks_the_status_as_well_as_the_dates() -> None:
    lapsed = ask(
        lambda c: c.call_tool(
            "check_in_force", {"number": "SYN-POL-1003", "date_of_loss": "2024-09-01"}
        )
    )
    body = lapsed.structured_content
    assert body["within_dates"] is True
    assert body["in_force"] is False
    assert body["status"] == "lapsed"


def test_a_decision_is_not_there_until_it_is_written() -> None:
    before = ask(lambda c: c.call_tool("read_decision", {"claim_id": "FNOL-4471"}))
    assert before.is_error is False
    assert before.structured_content == {"found": False, "claim_id": "FNOL-4471"}

    ask(
        lambda c: c.call_tool(
            "record_decision", {"claim_id": "FNOL-4471", "outcome": "fast-track"}
        )
    )

    after = ask(lambda c: c.call_tool("read_decision", {"claim_id": "FNOL-4471"}))
    assert after.structured_content == {
        "found": True,
        "claim_id": "FNOL-4471",
        "outcome": "fast-track",
        "reason": None,
    }


@pytest.mark.parametrize(
    ("arguments", "refusal"),
    [
        ({"claim_id": "FNOL-4471", "outcome": "fasttrack"}, "unknown outcome"),
        ({"claim_id": "FNOL-4477", "outcome": "deficiency"}, "must name a reason"),
        (
            {"claim_id": "FNOL-4477", "outcome": "deficiency", "reason": "no_photo"},
            "unknown reason",
        ),
        (
            {"claim_id": "FNOL-4471", "outcome": "fast-track", "reason": "injury_reported"},
            "a fast-track has no reason",
        ),
    ],
)
def test_the_write_refuses_a_shape_it_does_not_recognise(arguments: dict, refusal: str) -> None:
    """A refusal is a result, not an exception — and it says what was wrong with the request."""
    result = ask(lambda c: c.call_tool("record_decision", arguments))
    assert result.is_error is False
    assert result.structured_content["recorded"] is False
    assert refusal in result.structured_content["refused"]


def test_an_answer_arrives_twice_over(tmp_path) -> None:
    """Every result carries a text block for a model and a structured copy for a program."""
    result = ask(lambda c: c.call_tool("fetch_policy", {"number": "SYN-POL-1001"}))
    assert result.structured_content["product"] == "home-contents"
    assert json.loads(result.content[0].text) == result.structured_content
```

**Line by line:**

- `def ask(work)` — **one helper instead of a nested coroutine in every test.** It takes a function
  of a client, opens a connection, runs it, returns the value. Every test below is one line of
  `ask(lambda c: ...)` and then plain synchronous assertions.
- `Callable[[Client], Awaitable[Any]]` — the argument is a function that takes a client and returns
  something awaitable. Annotating it is what makes the `lambda` at each call site readable.
- `@pytest.fixture(autouse=True)` — **applied to every test in the file without being asked for.**
  That is right here and would be wrong for most fixtures: this one exists to stop tests writing
  into the project, and a test that forgot to request it would be the one that did the damage.
- `monkeypatch.setattr(tools.store, "claims", tmp_path / "claims")` — reaches into the module-level
  store and repoints its claims directory. **Not a mock**: the real `Store`, the real atomic write,
  a real directory that pytest deletes afterwards.
- **Why it is needed at all**: `record_decision` writes, so without this the suite would leave
  `data/claims/FNOL-4471.json` in the project, and `test_a_decision_is_not_there_until_it_is_written`
  would pass on the first run and fail on the second. A test whose result depends on whether it has
  been run before is worse than no test.
- `assert [tool.name for tool in names.tools] == [...]` — **the whole docket, in order.** Same
  assertion as day 3, moved here and grown to four, and it is where it belongs now that `tools.py`
  owns the tuple that decides it.
- `test_every_tool_says_what_it_does_in_its_first_line` — the crude one, and the useful one.
  `endswith((".", "?"))` and `len(first.split()) >= 5`. Neither checks that a description is
  *good*; together they make `"""Cover check."""` impossible, which is the failure part 1.1
  demonstrates.
- `f"{tool.name}: {first!r}"` as the assertion message — the failure names the tool and quotes the
  offending line, so the report is actionable without opening the file.
- `assert schema["properties"]["date_of_loss"] == {...}` — **the whole schema object, compared
  exactly.** Not `["format"] == "date"`: comparing the dictionary means a change to the title or the
  type has to come past this test too.
- `assert schema["properties"]["reason"]["default"] is None` — the optional parameter, from the
  other side. Its absence from `required` and its `default` are two facts and both are asserted,
  because a parameter can be non-required for more than one reason.
- `@pytest.mark.parametrize("sent", [...])` — **three tests from one function.** They report
  separately, so a run that fails on `'2026-3-14'` and passes the other two says exactly that.
- `assert "date_of_loss" in result.content[0].text` — asserting on the *parameter name* in the error
  rather than on the error's wording. The wording belongs to the SDK and may change with a version;
  the promise this project cares about is that the failing field is named.
- `test_in_force_checks_the_status_as_well_as_the_dates` — `within_dates is True` **and**
  `in_force is False`. The lapsed policy from day 2, chosen because it is the case where the two
  disagree, and asserting both is what proves the tool is not just returning the date comparison
  twice.
- `test_a_decision_is_not_there_until_it_is_written` — read, write, read. **Three calls in one
  test**, because the point is the transition rather than either state. `before` is compared to the
  whole dictionary, so an implementation that returned `{"found": False}` without echoing the claim
  id would fail.
- `assert before.is_error is False` — **the most important line in that test.** Finding nothing is
  not an error, and part 3.2 is what happens when it becomes one.
- `@pytest.mark.parametrize(("arguments", "refusal"), [...])` — four refusals, four cases, each
  naming the phrase it expects. The tuple form takes two argument names and a list of pairs.
- `assert result.is_error is False` **in the refusal test** — the line that looks wrong and is the
  whole design. A refused write is a successful call that returned "no". `is_error` is reserved for
  the request being malformed, which is where part 2.1's date failures live.
- `assert refusal in result.structured_content["refused"]` — substring, not equality, so the message
  can gain context without breaking four tests.
- `test_an_answer_arrives_twice_over` — **the pair.** `structured_content` is read as data, and
  `json.loads(result.content[0].text)` parses the text block back. Asserting they are equal is what
  says the two copies of the answer agree.
- `result.content[0].text` — the first block. In this project every tool returns one dictionary, so
  there is always exactly one text block; a tool that returned an image or several blocks would
  make this index a decision rather than a fact.

## When it breaks

Make the two copies of the answer disagree — build the text block by hand while returning something
else as data, which is what a tool does the moment somebody wants nicer output for the model:

```python
    return {
        "found": True,
        "number": policy.number,
        "summary": f"{policy.number} is {policy.status}",
    }
```

That change alone does not break the pair, because the SDK still derives the text from the return
value. The pair breaks when a tool takes control of its own content blocks — and this project's test
is the thing that would notice:

```
>       assert json.loads(result.content[0].text) == result.structured_content
E       AssertionError
```

It is worth being honest about the status of that: with the tools as written here, **this assertion
cannot currently fail**, because every one of them returns a dictionary and lets the SDK do both
halves. It is a guard against a change nobody has made yet, and it is in the file because the change
is a tempting one — a model reads the text, so somebody will eventually write the text — and the day
they do, one line will say that the program and the model are now looking at different answers.

## In production

**What a senior writes instead.** The same tests, plus a stored snapshot of the entire docket —
names, descriptions and schemas — compared on every run, so that *any* change to what a model sees
appears as a diff rather than only the properties somebody thought to assert. The version pin and
the ordered name list here are a cheap approximation, and they are worth having because they cost
nothing.

**What degrades at scale.** Fourteen in-process tests take a few seconds and get run constantly.
The temptation as the docket grows is one test per tool per case, which is quadratic and ends up
being run on the branch instead of on the change. What holds is the shape here: **properties
asserted once across the whole docket** — every description is a sentence, every date is declared as
a date — rather than one assertion per tool. Adding the fifth tool then costs no new tests unless it
introduces a new *kind* of thing.

**The review comment.** *"This test asserts `result.structured_content` and ignores `is_error`. Add
it — a failed call still has content, and a test that reads only the body will go green on a tool
that is failing every time."*

**The interview question.** *"Your tool returns one value and the caller receives two
representations of it. Why does the protocol carry both, and what goes wrong the day they
disagree?"*
