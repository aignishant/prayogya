## One-line answer

A tool that raises instead of answering does not just turn an answer into an error — the SDK
replaces its message with `Error executing tool read_decision`, so the reason is destroyed on the
way across the line.

## The idea

A slip goes to records asking for the file on a claim, and there is no file, because nobody has
opened one yet. Records has two ways to answer.

They can send the slip back with the empty box ticked: *no file opened.* The handler reads it,
understands, and opens one. Four seconds.

Or they can not answer, and telephone the handler's supervisor to say a slip came through that they
could not process. Which is also true. It is now a conversation, an interruption and a thing
somebody has to make a decision about — and at the end of it the answer is still *no file opened*.

The second version is what a tool does when it raises. And the reason it is worse is not
temperament: it is that **the information does not survive the trip.** The telephone call reaches
the supervisor and not the handler; by the time it comes back, the specifics have gone.

This is measurable rather than rhetorical, and this part measures it. `read_decision` returns
`{"found": false}` for a claim nobody has decided. Change it to raise a `KeyError` carrying a
perfectly clear message — *no decision recorded for FNOL-4471* — and look at what the caller
actually receives.

## The mechanism

The tool as printed in part 1.1, and the three lines that matter:

```python
def read_decision(claim_id: str) -> dict[str, Any]:
    """What has this desk decided about one claim, if anything yet?

    Returns `{"found": false}` when no decision has been written. That is the honest answer to a
    question about work that has not happened, and it is different from an error: nothing went
    wrong, there is simply nothing to report.
    """
    record = store.claim(claim_id)
    log("boundary.read_decision", claim=claim_id, found=record is not None)
    if record is None:
        return {"found": False, "claim_id": claim_id}
    return {"found": True, **record}
```

**Line by line:**

- **The docstring spends three lines on the empty case**, which is more than it spends on the full
  one. That ratio is right: a caller can guess what a found record looks like, and cannot guess
  whether "not found" is a result or a failure.
- **"nothing went wrong, there is simply nothing to report"** — the distinction the whole part turns
  on, written where a model will read it. A model told this will not treat an empty answer as
  something to work around.
- `record = store.claim(claim_id)` — day 2's store, which already returns `None` rather than
  raising. **The honesty starts one layer down**, and this tool is passing it along rather than
  inventing it.
- `log(..., found=record is not None)` — the log records *whether* something was found, not what.
  Every call is visible, including the ones that found nothing, which is how you discover that a
  caller is asking for claims that never existed.
- `if record is None: return {"found": False, "claim_id": claim_id}` — a **result**, with the
  question echoed back. Three facts in one dictionary: nothing failed, nothing was found, and this
  is the claim that was asked about.
- `return {"found": True, **record}` — the same `found` key on the other branch. **A caller checks
  one field either way**, which is what makes a `try` unnecessary and therefore what makes this
  tool easy to use correctly.

Now the change. One `return` becomes one `raise`, with a message that says exactly what happened:

```python
    if record is None:
        raise KeyError(f"no decision recorded for {claim_id}")
```

**Line by line:**

- `raise` where there was `return` — **one word, and nothing else in the function changes.** The
  store still returns `None`, the log line still fires, the found branch is untouched.
- `KeyError` — a reasonable choice. The claim id was a key and there was nothing under it, which is
  exactly what a `KeyError` means in Python.
- `f"no decision recorded for {claim_id}"` — **a good message.** It names the claim, says precisely
  what is absent, and would be the first thing anybody wanted to read in a log. Remember it; the
  next block is where it goes.

And this is what the caller gets:

```bash
uv run python -c "
import asyncio, json
from mcp import Client
from claims_mcp.server import server
async def main():
    async with Client(server) as c:
        r = await c.call_tool('read_decision', {'claim_id': 'FNOL-4471'})
        print(json.dumps({'is_error': bool(r.is_error), 'structured': r.structured_content,
                          'text': (r.content[0].text if r.content else '')[:160]}))
asyncio.run(main())
"
```

```
{"is_error": true, "structured": null, "text": "Error executing tool read_decision"}
```

**Line by line:**

- `"is_error": true` — the call is now a failure. Everything downstream that distinguishes results
  from failures will take the other branch.
- `"structured": null` — **there is no answer at all.** Not an empty one: none. A program that reads
  `structured_content` gets `None` and has to have been written to expect it.
- `"text": "Error executing tool read_decision"` — **and here is the loss.** The `KeyError` said *no
  decision recorded for FNOL-4471*. That sentence named the claim, said precisely what was absent,
  and is **nowhere in what the caller received.** The SDK wrapped the exception in an
  `UnexpectedToolError` and sent across the tool's name and nothing else.
- **This is correct behaviour by the SDK**, and it is worth understanding rather than resenting. An
  arbitrary exception from a tool may carry a file path, a connection string, a fragment of another
  policyholder's data. Refusing to forward it across a process boundary is the same instinct as day
  1's redaction, applied by somebody else's library on your behalf.
- **The consequence is the design rule.** If a tool's answer matters, it has to be a *return value*,
  because a return value crosses the line and an exception's message does not. Raising is for things
  the caller cannot act on.

The server's own log, meanwhile, still records what happened — on the far side, where the caller
cannot see it. That asymmetry is the shape of the problem: **the information exists, and it is on
the wrong side of the boundary.**

## When it breaks

The test in part 3.1 catches it, and what it says is worth reading closely:

```
uv run pytest tests/test_tools.py -q -k until
```

```
FAILED tests/test_tools.py::test_a_decision_is_not_there_until_it_is_written
1 failed, 13 deselected in 3.10s
```

One test, and it is the one that reads before writing. Notice what did **not** go red: the docket is
unchanged, the schemas are unchanged, every refusal in `record_decision` still behaves, and the
answer-arrives-twice test still passes because it asks about a policy that exists. **A tool that
raises on the empty case looks completely healthy from every angle except the empty case** — and the
empty case is the common one, because most claims have not been decided yet when something asks.

Somebody made this change to "surface the problem properly", which is a real instinct and is usually
right. It is wrong here for a mechanical reason rather than a philosophical one: the message they
wanted to surface is the thing that gets deleted. The smallest fix is to return the dictionary. The
way to keep the instinct is to notice that **there was no problem** — a claim not yet decided is the
system working.

## In production

**What a senior writes instead.** The same rule, stated as a boundary policy rather than a habit:
tools return results; exceptions are reserved for the caller having asked something malformed, and
even then the message is written by you rather than by whatever raised. In practice that means every
tool body that can fail catches its own exceptions and converts them into a refusal with a reason —
which is what `record_decision` already does for its four cases, and what day 6 does for the whole
question of a deficiency being an answer.

**What degrades at scale.** A desk that processes several hundred notifications a day asks
`read_decision` about every one of them, and most of those asks happen before a decision exists. If
that is an error, the error rate on this boundary is the *majority* of its traffic — which means
every alert threshold has to be set above it, and a real failure arrives inside a band nobody is
watching. **The cost of calling a normal outcome an error is that you lose the ability to alert on
errors at all.**

**The review comment.** *"This raises `ValueError('policy not found')` and the caller gets 'Error
executing tool fetch_policy'. Your message does not cross the boundary — return `{"found": false}`
with the number in it, the way the other three tools do."*

**The interview question.** *"A tool of yours raises an exception with a clear, specific message and
the model on the other side reports that the tool is broken. Explain what happened to your message,
and tell me what you would change."*
