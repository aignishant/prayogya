## One-line answer

`replay` re-derives the verdict from the record alone and every one of this desk's twelve claims
passes — and the same function accepts a record whose facts were edited to produce a different
verdict, which is the limit worth stating out loud rather than discovering during an audit.

## The idea

The replay is the day's whole claim, so it is worth saying precisely what it establishes.

`defensible(record)` is `True` when the record's own facts, run through this desk's own rules,
produce the verdict the record states. That is a real property and it is not a small one. It rules
out a decision that was made some other way and labelled afterwards. It rules out a rule that was
applied inconsistently. It rules out a record assembled from memory, because a reconstruction that
did not have the facts to hand will not replay.

Now the other half, which matters more because nobody says it.

**A replay proves the arithmetic, not the arithmetic's inputs.** Change the estimate in a stored
record from 4800 to 400 and it replays perfectly — to `fast-track`, because that is what the rules
say about a claim of 400. The record is internally consistent, `defensible` returns `True`, and it
describes a claim that never happened.

That is not a flaw in the design. It is what "defensible" means and it is what an auditor actually
gets: a document that hangs together. Whether the facts in it are the facts the desk had is a
different question with a different answer — integrity, not consistency — and it needs signing or
hashing or append-only storage, none of which this project has.

The reason to be explicit is that the two are routinely confused. A system with replayable records is
often described as tamper-evident, and it is not. It is **inconsistency-evident**, which catches the
careless edit and the honest mistake and does nothing about the deliberate one.

## The mechanism

Every claim in the queue, decided over the real boundary, replayed from its own file:

```bash
uv run python -c "
import json, pathlib
from claims_desk import record

for path in sorted(pathlib.Path('data/claims').glob('*.json')):
    stored = json.loads(path.read_text(encoding='utf-8'))
    loaded = record.DecisionRecord.model_validate(stored['decision'])
    print('%-11s %-11s %-24s replay=%-32s %s' % (
        loaded.claim_id, loaded.outcome, loaded.reason or '-',
        record.replay(loaded), 'defensible' if record.defensible(loaded) else 'NOT DEFENSIBLE'))
"
```

```
FNOL-4471   fast-track  -                        replay=('fast-track', None)             defensible
FNOL-4472   fast-track  -                        replay=('fast-track', None)             defensible
FNOL-4473   deficiency  missing_date_of_loss     replay=('deficiency', 'missing_date_of_loss') defensible
FNOL-4474   deficiency  policy_not_in_force      replay=('deficiency', 'policy_not_in_force') defensible
FNOL-4475   fast-track  -                        replay=('fast-track', None)             defensible
FNOL-4476   deficiency  unknown_policy           replay=('deficiency', 'unknown_policy') defensible
FNOL-4477   deficiency  missing_photo_reference  replay=('deficiency', 'missing_photo_reference') defensible
FNOL-4478   deficiency  injury_reported          replay=('deficiency', 'injury_reported') defensible
FNOL-4479   deficiency  peril_not_covered        replay=('deficiency', 'peril_not_covered') defensible
FNOL-4480   fast-track  -                        replay=('fast-track', None)             defensible
FNOL-4481   deficiency  above_fast_track_limit   replay=('deficiency', 'above_fast_track_limit') defensible
FNOL-4482   deficiency  missing_contact          replay=('deficiency', 'missing_contact') defensible
```

**Line by line:**

- **Twelve claims, twelve records, twelve replays that agree.** Nothing was replayed against the
  store, the boundary or a model — each row is a JSON file, `assess`, and a comparison.
- **All eight reasons appear**, one claim each, plus four fast-tracks. That is day 2's fixture set
  paying off five days later: every rule in `assess` has a claim in the queue that fires it, so this
  listing is a replay of the whole rule set rather than of one path through it.
- **`FNOL-4473` replays to `missing_date_of_loss` with an empty `loss_type`.** The date check comes
  first in `assess` and returns before anything reads the peril, so the record's empty field is
  never consulted — the ordering of the rules is visible in what the replay does not need.
- **`FNOL-4476` replays to `unknown_policy` from `policy_found: false`.** Part 1.1's decision to
  record that as a boolean with empty cover fields, rather than as an absent section, is what makes
  this row a replay rather than a special case.
- **The `replay=` column is the tuple, printed raw.** Deliberately not formatted: a reader comparing
  it against the two columns to its left is doing the audit, and prettifying it would hide the
  comparison being made.

Now edit one. A claim refused on the limit, changed to say it was fast-tracked:

```bash
uv run python -c "
import json, pathlib
from claims_desk import record

stored = json.loads(pathlib.Path('data/claims/FNOL-4481.json').read_text(encoding='utf-8'))
loaded = record.DecisionRecord.model_validate(stored['decision'])
print('as filed  : %-11s %-24s defensible=%s' % (loaded.outcome, loaded.reason, record.defensible(loaded)))
loaded.outcome = 'fast-track'
loaded.reason = None
print('as edited : %-11s %-24s defensible=%s' % (loaded.outcome, loaded.reason, record.defensible(loaded)))
print('replays to:', record.replay(loaded))
print()
loaded = record.DecisionRecord.model_validate(stored['decision'])
loaded.facts.fast_track_limit = 9000
print('limit edited to 9000 :', record.replay(loaded), 'defensible=%s' % record.defensible(loaded))
"
```

```
as filed  : deficiency  above_fast_track_limit   defensible=True
as edited : fast-track  None                     defensible=False
replays to: ('deficiency', 'above_fast_track_limit')

limit edited to 9000 : ('fast-track', None) defensible=False
```

**Line by line:**

- **Editing the verdict is caught.** `defensible=False`, and `replay` says what the record's own facts
  actually produce — so the failure names the right answer rather than only reporting a mismatch.
- **Editing a fact is caught too, in the other direction.** Change the policy's limit to 9000 and the
  facts now produce `fast-track` while the record still claims `deficiency`. Same detection, opposite
  cause.
- **Both of these are inconsistencies**, and that is the pattern: `defensible` compares two halves of
  one document and notices when they stop agreeing.
- **Neither run needed anything but the file.** No policy store was consulted to find out what
  SYN-POL-1002's limit really is, which is the property that makes the replay portable and is exactly
  the property that makes the next failure possible.

## When it breaks

Edit the fact **and** the verdict together, so the record still agrees with itself:

```bash
uv run python -c "
import json, pathlib
from claims_desk import record

stored = json.loads(pathlib.Path('data/claims/FNOL-4481.json').read_text(encoding='utf-8'))
loaded = record.DecisionRecord.model_validate(stored['decision'])
loaded.facts.estimate = 400
loaded.outcome = 'fast-track'
loaded.reason = None
print('estimate 4800 -> 400, outcome deficiency -> fast-track')
print('replays to :', record.replay(loaded))
print('defensible :', record.defensible(loaded))
"
```

```
estimate 4800 -> 400, outcome deficiency -> fast-track
replays to : ('fast-track', None)
defensible : True
```

Verbatim, from this project. **`defensible` is `True`** on a record describing a claim that was never
decided this way, for an estimate the policyholder never reported.

Everything about that is working as designed, which is why it needs saying rather than fixing. The
replay checks that a document is internally consistent. A consistent document is not a true one.
Change enough of it and it stays consistent.

Notice how little had to change: **two fields.** And notice which two — the estimate and the outcome.
Nothing about the letter, the citations, the provenance, the rules version. The letter still says
*the amount reported is above our fast-track limit*, which contradicts the record it sits inside, and
`defensible` does not look at prose.

So the honest statement of what this project has is:

- **Inconsistency-evident.** A careless edit, a partial migration, a record assembled from memory, a
  rule applied wrongly — all caught, by one comparison, on every claim.
- **Not tamper-evident.** A deliberate edit by somebody who understands the rules is not caught, and
  nothing in this design could catch it.

The fix is not in this file. It is a hash over the stored record written somewhere the same person
cannot edit — an append-only log, a signature, a second system. That is a real piece of work with
real operational cost, and the point of naming it here is that **the choice to skip it should be a
decision rather than an assumption.** This project skips it, and the hub carries it as a `TODO(me)`
with what it would take.

One more limit, smaller and closer: `calls` in the provenance is the budget breakdown at the moment
the verdict was reached, so every deficiency record under-reports by however many drafts its letter
took afterwards. Part 1.2 showed a record with `{"classifier": 1}` for a claim that also spent a
letter call. That is not a hole in the replay — provenance is not evidence — and it is a number
somebody will quote in a cost report. Also a `TODO(me)`.

## In production

**What a senior writes instead.** The record hashed at the moment it is written, with the hash in an
append-only store — which turns "the document agrees with itself" into "the document is the one we
wrote". What they would want first, though, is cheaper and this project already has it: the replay
run over **every stored record as a test**, so a rule change that silently invalidates history is
caught by CI rather than by an auditor. Part 3.1's
`test_every_decided_claim_replays_to_its_own_verdict` is that test.

**What degrades at scale.** Replaying twelve records is instantaneous. Replaying a year of a morning's
several hundred notifications — somewhere around a hundred thousand records — is still only a hundred
thousand calls to a function of eight comparisons, so the arithmetic scales fine. What does not is
`RULES_VERSION`: replaying an old record against today's `assess` answers a question nobody asked. At
that volume the replay has to select records by rules version and run each cohort against the rules it
was decided under, which means keeping old versions of `assess` around — and that is the real cost of
promising replayability, arriving about two rule changes in.

**The review comment.** *"`defensible` is described in the ticket as making records tamper-proof. It
does not. Edit two fields consistently and it passes — I have tried it. Either add the hash or change
the wording in the ticket, because somebody will repeat the claim to a regulator."*

**The interview question.** *"You can re-derive every decision your system made from its own records.
What class of problem does that catch, and what class does it not?"*
