## One-line answer

Take the `scripted/` prefix off the stand-in and the registry refuses it — not by a special rule
about doubles, but because a model with an ordinary name has to be a model this project agreed to
use, and this one is not.

## The idea

The training telephone is a different colour, and somebody paints it black to match the others
because the room is being photographed for a brochure.

Nothing breaks that afternoon. The phone still works, the script is unchanged, the practice calls go
exactly as they did. What has gone is the one mechanism that stopped a practice call being quoted as
a real one — and it went for a reason that had nothing to do with practice calls, which is how this
kind of thing always goes.

Part 1.2 gave the stand-in three announcements. This part is about what the third one is actually
for, because it is the only one that is *enforced* rather than merely present.

The name and the `scripted: true` flag are labels. They are excellent labels — they appear in every
log line and every answer — and a label is a thing a reader has to notice. The registry check is
different: it is a **gate**. A double whose name stops saying what it is does not get quietly used
with a misleading label; it does not get used at all.

That distinction is worth being precise about, because it decides where you put effort. Labels
prevent misreading. Gates prevent happening.

## The mechanism

The double, given an ordinary-looking name — the change somebody makes when a name in a log looks
untidy, or when copying the class to make a second one:

```bash
uv run python -c "
from claims_desk import models
from claims_desk.scripted import ScriptedClassifier
quiet = ScriptedClassifier(model='claims-classifier')
try:
    models.pinned(quiet)
except models.UnpinnedModel as refusal:
    print('refused:', refusal)
"
```

```
refused: 'claims-classifier' is not in this project's registry: ['gemini-3.7-flash', 'gemini-3.8-flash']
```

**Line by line:**

- `ScriptedClassifier(model='claims-classifier')` — the field is overridable, because it is an
  ordinary pydantic field. **The double cannot be prevented from being renamed**, and trying to
  prevent it would be the wrong design: a class that cannot be reconfigured cannot be reused.
- `models.pinned(quiet)` — day 1's registry, called exactly as `classifier.build` calls it.
- **`refused: 'claims-classifier' is not in this project's registry`** — and read *which* rule
  refused it. Not "this is a double pretending not to be". Not a special case about stand-ins at
  all. It fell through to the last check in `pinned` — the general one — and was refused for the
  same reason `gemini-4-flash` would be: **it is not a model this project agreed to use.**
- `['gemini-3.7-flash', 'gemini-3.8-flash']` — the message lists what *is* acceptable, which is the
  same helpful refusal day 1 built. A reader who meets this sees two provider IDs and no mention of
  doubles, and the right next question is "why is my double not announcing itself".
- **This is the whole design, and it is worth stating plainly.** There is no `if is_test:`, no
  `ALLOW_FAKES` environment variable, no exemption list to forget to remove before shipping. The
  registry has one extra rule — a name beginning `scripted/` is allowed — and everything else
  follows from rules that were already there.

Compare with the shape this could have taken. An exemption:

```python
    if name == "claims-classifier":       # our test double, allow it
        return model
```

**Line by line:**

- `if name == "claims-classifier":` — **one specific double, named in the registry.** The registry
  now knows about a particular fake rather than about a property of fakes.
- `# our test double, allow it` — the comment is the only thing saying why this line exists, and a
  comment is not a mechanism. Delete the comment and the line is inexplicable; delete the double and
  the line is dead code nobody notices.
- `return model` — the same pass-through as the prefix rule, reached for the wrong reason.

That line works, passes every test, and is the thing this project does not do. It has to be
maintained, it has to be remembered at release, it names one specific double, and — worst — it makes
*being a double* a property the registry knows about somebody's say-so rather than from the name
itself. The prefix rule inverts that: the double earns its exemption by declaring itself, on every
call, in a string that ends up in every log line it touches.

## When it breaks

The failure this prevents is not the refusal. The refusal is the mechanism working. The failure is
what happens in a project that has the exemption instead — and it is worth walking through, because
nothing about it looks wrong at any step.

Somebody adds `if name == "claims-classifier": return model` to unblock a rename. The double is now
allowed under an ordinary name. Its log lines say `"model": "claims-classifier"`. Its answers no
longer need to carry `scripted: true` for the registry's sake, so the next person to simplify the
answer shape drops it. And then a run of this desk over the twelve notifications produces a
transcript that reads exactly like a real one.

At that point somebody quotes it. Not maliciously — in a status update, as *"the classifier gets all
twelve right"* — and the sentence is true about the double and false about anything else.

There is a smaller, sharper version of the same failure available today, and this project has it:

```
Skipping missing token usage metadata for agent classifier and model scripted/claims-classifier
```

That is the framework, on every call, saying that the thing it just used produced no usage data.
**It names the model while doing it**, which is the whole point of the prefix — and if the double
were called `claims-classifier`, that warning would read as a real model failing to report usage,
which is a genuine and much more alarming condition.

The smallest fix is to keep the prefix. The rule worth carrying: **make the exemption depend on the
announcement, so that removing the announcement removes the exemption.**

## In production

**What a senior writes instead.** The same rule, and one more: the double lives in a module that
production code cannot import — a test package, or a plugin registered only in the test
configuration — so the gate is a packaging fact as well as a naming one. This project keeps it in
`claims_desk/` because the whole of `claims_desk/` is what a reader is meant to read, and it accepts
the weaker guarantee in exchange. That is a real trade and it is worth knowing you have made it.

**What degrades at scale.** One double, one prefix, one rule. A platform with a stand-in per external
service accumulates a dozen, and the failure is not that a double gets used in production — that is
loud — but that a *test* double gets used in a **staging** environment that somebody then quotes
numbers from. Staging is where this bites, every time, because staging is where transcripts look
real enough to repeat.

**The review comment.** *"This adds `if name == "claims-classifier": return model` so the fake works
after the rename. Rename it back to `scripted/claims-classifier` instead — the exemption should
depend on the name, or the day somebody deletes the comment we have a fake that looks like a
model."*

**The interview question.** *"You have a test double for an expensive external service. How do you
stop a transcript produced against it from being mistaken for a real one, six weeks later, by
somebody who was not there?"*
