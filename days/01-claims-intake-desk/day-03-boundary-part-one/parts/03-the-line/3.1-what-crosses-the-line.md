## One-line answer

Six tests hold the boundary to its docket — one tool, a schema derived from the function, a missing
policy that is an answer rather than an error, no path in the reply — and one of them launches the
server as a real subprocess so that "it works in-process" is never the only evidence.

## The idea

The thing that makes a hatch trustworthy is not the clerk's intentions. It is that somebody can
stand on the outside and check: ask for something that is not on the docket and be refused, ask for
a folder that does not exist and get "no such file" rather than a shouting match, look at what came
through the hatch and confirm it is a folder and not a key to the shelves.

Every one of those is a test, and they are all written from the outside — through the protocol,
which is the only way a caller can reach this server anyway.

There is a decision inside this file worth naming, because it is the one people get wrong. Five of
the six tests connect to the server **object** in this process. That is not a shortcut past the
boundary: the request is still built, routed, dispatched and wrapped in a result envelope, so it
exercises everything except the pipe. It is fast, and speed is what makes a test suite get run.

But it is not what this project ships. So one test launches `python -m claims_mcp` as a real
subprocess and asks it a question. That test is slower than all the others put together, and it is
the only one that proves the module starts at all. **In-process is the convenience; the process
line is the product**, and a suite with only the first kind is a suite that goes green on the day
the boundary stops being runnable.

## The mechanism

The whole file, at `tests/test_boundary.py`:

```python
"""The boundary, exercised the way a caller has to exercise it: across the protocol.

Two shapes of test. Most of them connect to the server object in this process, which is fast and
still goes through the whole protocol — request, dispatch, result envelope. One of them launches
`python -m claims_mcp` as a real subprocess, because in-process is a convenience and the thing
this project actually ships is a process line.

There is no `pytest-asyncio` here. Each test calls `asyncio.run` on a coroutine, which is three
extra words and one fewer dependency.
"""

from __future__ import annotations

import asyncio

from mcp import Client, StdioServerParameters

from claims_mcp.server import server


def test_the_server_declares_one_tool_and_says_who_it_is() -> None:
    async def ask() -> tuple[str, str, list[str]]:
        async with Client(server) as client:
            tools = await client.list_tools()
            return (
                client.server_info.name,
                client.server_info.version,
                [tool.name for tool in tools.tools],
            )

    name, version, tools = asyncio.run(ask())
    assert name == "claims-boundary"
    assert version == "0.1.0"
    assert tools == ["fetch_policy"]


def test_the_tool_schema_is_derived_from_the_function() -> None:
    async def ask() -> dict:
        async with Client(server) as client:
            tools = await client.list_tools()
            return tools.tools[0].input_schema

    schema = asyncio.run(ask())
    assert schema["type"] == "object"
    assert schema["required"] == ["number"]
    assert schema["properties"]["number"]["type"] == "string"


def test_a_known_policy_comes_back_as_structured_content() -> None:
    async def ask() -> dict:
        async with Client(server) as client:
            result = await client.call_tool("fetch_policy", {"number": "SYN-POL-1001"})
            assert result.is_error is False
            return result.structured_content

    policy = asyncio.run(ask())
    assert policy["found"] is True
    assert policy["status"] == "active"
    assert "escape-of-water" in policy["perils"]


def test_an_unknown_policy_is_an_answer_and_not_an_error() -> None:
    """`found: false` with `is_error: false`.

    The desk asks about numbers callers read off old letters. A tool that raised here would turn
    an ordinary intake event into a traceback, and the deficiency letter it deserves would never
    be written.
    """

    async def ask() -> tuple[dict, bool]:
        async with Client(server) as client:
            result = await client.call_tool("fetch_policy", {"number": "SYN-POL-9999"})
            return result.structured_content, bool(result.is_error)

    body, errored = asyncio.run(ask())
    assert body == {"found": False, "number": "SYN-POL-9999"}
    assert errored is False


def test_nothing_the_tool_returns_carries_a_file_path() -> None:
    """The boundary hands back cover, not storage.

    If a path ever crosses this line, something above it can be written to open the path, and the
    whole arrangement is decoration.
    """

    async def ask() -> dict:
        async with Client(server) as client:
            result = await client.call_tool("fetch_policy", {"number": "SYN-POL-1001"})
            return result.structured_content

    policy = asyncio.run(ask())
    flattened = repr(policy)
    for smell in ("data/", "\\\\", ".json", "policies"):
        assert smell not in flattened, f"{smell!r} crossed the boundary"


def test_the_same_call_over_a_real_process_line() -> None:
    """The one test that launches the server as a subprocess.

    Slower than the others and the only one that proves `python -m claims_mcp` starts at all,
    speaks the protocol on its standard output, and agrees with the in-process version.
    """

    async def ask() -> tuple[str, dict]:
        params = StdioServerParameters(command="python", args=["-m", "claims_mcp"])
        async with Client(params) as client:
            result = await client.call_tool("fetch_policy", {"number": "SYN-POL-1004"})
            return client.protocol_version, result.structured_content

    version, policy = asyncio.run(ask())
    assert version == "2026-07-28"
    assert policy["product"] == "motor-private"
    assert policy["fast_track_limit"] == 1500
```

**Line by line:**

- **"There is no `pytest-asyncio` here."** — every test defines a coroutine and calls `asyncio.run`
  on it. That is three extra words per test and it keeps `dependencies` free of a plugin whose
  configuration is a common source of confusing collection errors. When the async surface grows, the
  plugin becomes worth it; today it is not.
- `from claims_mcp.server import server` — the test imports the **server object**, which is the
  in-process door. Note what it does not import: `Store`, `Policy`, or anything the tool returns.
  A test that reached for the domain types would be checking the boundary against the thing on the
  far side of it, which is the one comparison a caller cannot make.
- `async def ask() -> ...` **nested inside each test** — the coroutine is defined where it is used
  and returns plain values, so all the assertions live in the synchronous body. A test whose
  assertions are inside an `async with` block is a test that can pass by not running.
- `async with Client(server) as client:` — the context manager owns the connection. On exit it
  closes it; without it, a test that fails leaves a connection open and the next one is flaky for a
  reason that has nothing to do with what it tests.
- `assert tools == ["fetch_policy"]` — **the whole docket, as a list, compared exactly.** Not `in`:
  the assertion is that this server declares one tool and no others. When day 5 adds three more,
  this line has to change, and that is the point — a new capability should not be able to appear
  without a test acknowledging it.
- `assert name == "claims-boundary"` and `version == "0.1.0"` — the identity, read back across the
  protocol. It is the first thing that is wrong when a client is talking to a different server than
  it thinks.
- `schema["required"] == ["number"]` and `schema["properties"]["number"]["type"] == "string"` —
  **the derived schema, asserted.** Nobody wrote that JSON: it came from `def fetch_policy(number:
  str)`. Worth knowing exactly how much the annotation is doing here, because it is less than it
  looks: removing it entirely leaves `{"title": "number", "type": "string"}` — the SDK falls back to
  string — so this test still passes without it. The annotation earns its place the moment a
  parameter is **not** a string, which is day 5, when a tool takes a date. Until then it is a
  promise being kept rather than a guard being enforced, and it is better to know which.
- `assert result.is_error is False` **inside** the coroutine in one test, and returned as a value in
  another — two shapes, both fine. The important part is that `is_error` is checked at all: a result
  can carry an error flag and still have content, and reading only the content is how a failed call
  becomes a plausible answer.
- `test_an_unknown_policy_is_an_answer_and_not_an_error` — the contract from part 2.1's docstring,
  turned into an assertion. `body == {"found": False, "number": "SYN-POL-9999"}` compares the whole
  dictionary, so a future version that adds a field has to come past this test deliberately.
- `test_nothing_the_tool_returns_carries_a_file_path` — **the boundary test that is not about the
  protocol at all.** It flattens the reply with `repr` and looks for four smells: `data/`, a
  backslash, `.json`, and the word `policies`. Any of them means storage crossed a line that is
  supposed to carry cover.
- `for smell in (...): assert smell not in flattened, f"{smell!r} crossed the boundary"` — a loop
  with the failing value in the message, so the report names which smell was found rather than
  saying an assertion failed.
- **`"\\\\"` is one escaped backslash** — Python source for the two characters that would appear in
  a Windows path inside a `repr`. It is the fiddliest line in the file and it is the one that
  catches `C:\\Users\\...` arriving in a reply.
- `test_the_same_call_over_a_real_process_line` — the subprocess test. `StdioServerParameters` with
  `command="python"` and `args=["-m", "claims_mcp"]`, exactly what part 2.2 printed.
- `assert version == "2026-07-28"` — **the protocol revision, pinned in a test.** If the SDK is
  upgraded and starts speaking a different revision, this goes red, and that is the day the project
  wants to know rather than the day something behaves oddly.
- `assert policy["product"] == "motor-private"` and `fast_track_limit == 1500` — a *different*
  policy from the in-process tests, chosen on purpose: the motor policy with the lower limit. A
  subprocess test that asked about the same policy as the fast tests would pass on a stale cache
  and prove nothing about the store the child process loaded.

## When it breaks

Add a tool to the boundary — a small, obviously useful one — and the docket test refuses it:

```python
@server.tool()
def list_all_policies() -> list[str]:
    """Handy for debugging: every policy number in the store."""
    return [p.number for p in store.policies()]
```

```
        name, version, tools = asyncio.run(ask())
        assert name == "claims-boundary"
        assert version == "0.1.0"
>       assert tools == ["fetch_policy"]
E       AssertionError: assert ['fetch_polic...all_policies'] == ['fetch_policy']
E         
E         Left contains one more item: 'list_all_policies'
E         Use -v to get more diff

tests\test_boundary.py:34: AssertionError
```

Verbatim, from this project. Nothing is broken — the new tool works perfectly, and that is the
point. Somebody added a debugging helper on a Friday and gave every agent above the boundary the
ability to enumerate the entire policy book, which is precisely the capability the server's own
`instructions` promise it does not have: *"there is no way to list them all"*. **`Left contains one
more item` is a capability appearing without a signature on it.** The smallest fix is to delete the
tool. If it is genuinely needed, the fix is to change this test in the same commit, so the new power
and the acknowledgement of it arrive together.

## In production

**What a senior writes instead.** The same six, plus a test that pins the tool descriptions
themselves — a snapshot of the docket, so that editing a docstring is a visible change to the
interface a model reads. They would also run the subprocess test in CI on the same operating system
the container uses, because "it starts" is a claim about a platform.

**What degrades at scale.** One subprocess test costs about a second and a half. Thirty of them
cost a minute, and a minute is where people start running the suite less. The shape that survives
is the one here: **most tests in-process, a small number over the real line**, chosen so that every
distinct thing about the process line — that it starts, that it speaks the right revision, that it
reads the same store — is covered exactly once.

**The review comment.** *"This test asserts `"fetch_policy" in tools`. Make it `== ["fetch_policy"]`
— otherwise the day somebody adds a tool to the boundary, no test says so, and a new capability has
appeared with nobody's signature on it."*

**The interview question.** *"You have a service behind a protocol. How many of your tests should
go over the real transport, which ones, and what do you lose by making that number zero?"*
