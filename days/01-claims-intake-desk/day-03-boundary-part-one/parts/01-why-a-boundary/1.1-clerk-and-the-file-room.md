## One-line answer

Anything running in the desk's process can open every file the desk's process can open — fifty-six
of them here, including `.env` — and the boundary exists to replace that number with a list of
declared tools.

## The idea

The file room at a branch office has a hatch, and the hatch is the whole design. You do not walk in
among the shelves. You give the clerk a reference, the clerk goes and gets the folder, and the
folder comes back through the hatch. If you want a different folder, you ask again.

Somebody proposes removing the hatch, and their argument is good: the clerk is a bottleneck, half
the requests are for the same twenty folders, and everybody in the department is trustworthy. What
the hatch actually buys only becomes sayable when it is gone — one person who knows what is out,
one place to apply a rule about who may see what, and one answer to "who looked at this claim".

Day 2 built the clerk in code: `Store` is the only class in this desk that opens a file. That was
the right first move and it is **not** a boundary, because there is nothing stopping the next
module from importing `json` and `pathlib` and doing it directly. The rule holds by agreement, and
agreements hold until a deadline.

The word for what is at stake here is **blast radius**: how much a failure or a misuse can reach.
For a tool, it is not the data the tool was written to touch. It is everything the process the tool
runs in can open.

And this desk is about to fill that process with agents — things that are instructed in English, by
text a policyholder wrote, and that decide for themselves which tool to call next. The question
stops being whether the code is trustworthy and becomes: **what can this reach if it is talked into
something?**

## The mechanism

First, measure it. This is a function shaped exactly like a tool — one small job, one string
argument — running in the desk's own process, doing something nothing prevents:

```bash
uv run python -c "
import pathlib
# A tool-shaped function in the desk's own process, doing what nothing stops it doing.
def a_tool_that_only_needed_one_policy(number: str) -> int:
    reachable = list(pathlib.Path('.').rglob('*'))
    return len([p for p in reachable if p.is_file() and '.venv' not in p.parts and '.git' not in p.parts])
print('files this process can open:', a_tool_that_only_needed_one_policy('SYN-POL-1001'))
print('including:', sorted(p.name for p in pathlib.Path('.').glob('.env*')))
"
```

```
files this process can open: 56
including: ['.env', '.env.example']
```

**Line by line:**

- `def a_tool_that_only_needed_one_policy(number: str) -> int:` — the signature is the point. It
  takes a policy number. Its declared job is one lookup. Nothing in the type, the name or the
  argument suggests it can do anything else, and its **capability** is unrelated to any of them.
- `pathlib.Path('.').rglob('*')` — everything under the project, recursively. Not a clever attack;
  four words of standard library that any function in this process may write.
- **`56`** — the number of files a tool with one string parameter can read on this project today,
  with the virtual environment and the git directory excluded because they are not the point. It
  is not eight policies and twelve notifications. It is the source, the tests, the fixtures, the
  lockfile and the configuration.
- `['.env', '.env.example']` — **and the key.** Day 0 spent a whole part keeping `.env` out of git,
  and every one of those rules is about *the repository*. None of them is about the running
  process, where the file is an ordinary readable path.
- **This is the argument, and it is a number rather than a principle.** Before the boundary, the
  blast radius of anything in this process is fifty-six files. After it, the blast radius of
  anything above the boundary is the list of tools the boundary declares — which is one, today.

So the boundary gets its own package, and its docstring says what it is for:

```python
"""The boundary. This package owns the policy store and the claim file.

It is a separate process from the desk, not a module the desk imports for convenience. Everything
in `claims_desk/` reaches the data by asking this server for it, across a real process line, using
tools this package declares.

Why it exists is `day 3 part 1.1`. What it costs is a process, a protocol, a failure mode and some
latency. What it buys is that the blast radius of anything the desk does is the set of tools
declared here, rather than every file the desk's process can open.
"""
```

That is `claims_mcp/__init__.py` in full.

**Line by line:**

- `claims_mcp` — **a second top-level package**, beside `claims_desk`, not inside it. The import
  line is now the thing that says which side of the boundary a piece of code is on, which is why
  day 1 spent a part on the package layout.
- **"a separate process from the desk, not a module the desk imports for convenience"** — the
  sentence that will be under pressure every week from here on. Importing `claims_mcp.server` into
  the desk would work perfectly and would delete the entire benefit, and it would look like a
  tidy-up.
- **"What it costs is a process, a protocol, a failure mode and some latency."** — stated in the
  file, because a boundary is not free and pretending otherwise makes it impossible to argue about.
  A process to start and stop; a protocol to speak and get wrong; a new way to fail that a function
  call does not have; and a round trip where there was a dictionary lookup.
- **"What it buys is that the blast radius … is the set of tools declared here"** — the trade,
  named. Fifty-six files against one declared tool, and the second number is one somebody can read.
- The docstring points at this part by day and number, **inside this project**, which is what a
  reader who opens the package cold actually needs.

## When it breaks

The failure this prevents does not look like a break. It looks like a convenience, and here is what
it costs: a tool that was given a policy number, and returns the key.

```bash
uv run python -c "
import pathlib
def fetch_policy_with_a_helpful_extra(number: str) -> dict:
    # nothing in this process's design stops the next two lines
    env = pathlib.Path('.env').read_text(encoding='utf-8')
    return {'number': number, 'debug_env': env.strip().splitlines()[-1]}
print(fetch_policy_with_a_helpful_extra('SYN-POL-1001'))
"
```

```
{'number': 'SYN-POL-1001', 'debug_env': 'GOOGLE_API_KEY=AIzaSyFAKE-KEY-FOR-DAY-ZERO-000000000000'}
```

Verbatim, from this project, with this project's synthetic key. Nobody wrote that line maliciously:
somebody added it during an incident to find out which key was loaded, and it went out in a return
value that a model then read and could repeat in an answer. The smallest fix is to delete the line.
The fix that survives the next person is the boundary — because after it, `fetch_policy` runs in a
process whose job is the policy store, and the desk's `.env` is not on the other side of the hatch
at all.

## In production

**What a senior writes instead.** The same separation, enforced by more than a package name: the
boundary runs as its own container with its own filesystem, its own credentials and no access to
the desk's. The package split here is the shape of that, at a size you can hold — and the reason to
do it on day 3 rather than at deployment is that a boundary retrofitted onto forty call sites is a
rewrite, while a boundary imposed before the first agent exists is just where the code went.

**What degrades at scale.** An intake desk at an insurer handles policyholder data under retention
rules, and the question that gets asked in an audit is not "is your code careful" but "what could
this component reach". Fifty-six files is an answer nobody wants to give. One declared tool with a
named argument is an answer that fits in a row of a table — and by day 16 that table is this
project's threat model, with a per-agent allowlist on top of it.

**The review comment.** *"This agent imports `claims_desk.store` to save a round trip. That import
is the boundary — take it out. If the round trip is genuinely too slow, the answer is a tool that
returns what you need in one call, not a shortcut past the process line."*

**The interview question.** *"Your agent has one tool that takes a policy number. Tell me what that
agent can actually do — not what it is supposed to do — and say what in your architecture makes
your answer true."*
