## One-line answer

Nodes do not pass arguments to each other — they write into the session's state and read out of it,
one key per thing, declared where the node is built; and the same dictionary is what puts the
checker's objection into the writer's instruction on the next pass.

## The idea

The running sheet is how a claims department passes work between people.

Nobody hands the next person a parcel of facts. The sheet goes in the folder, the next person picks
the folder up, and what they need is on the sheet under a heading they already know: *peril*,
*policy in force*, *what the policyholder must send*. The headings are agreed in advance and that is
the entire protocol. It survives people going home, jobs being done out of order, and two clerks
working the same claim in the same morning.

It also fails in exactly one way, and every department has seen it: **two people write different
things under the same heading.**

A workflow's state is that sheet. Day 8 introduced it as a small dictionary that travels with a
conversation and must never hold anything personal. Today it does a second job: it is **the edge
between two nodes**. The classifier writes under `reading`; the rules node reads `reading`. Nothing
was passed and no node knows who the other one is.

Two mechanisms make that work, and both are worth naming because they look like ordinary Python and
are not:

- **`output_key`** on a model-backed agent: the framework writes that agent's final text into state
  under the key. The agent does not know it happened.
- **`state_delta`** on an event: a node changes state by *declaring the change on an event it
  yields*, not by assigning to the dictionary. The assignment would work in memory and leave no
  record; the delta is what the session service actually stores.

And there is a third that closes the circle. An instruction may contain `{key}`, and the framework
substitutes it from state before the request goes out — so **state flows back into a prompt**, which
is how a checking node talks to a writing node without either importing the other.

**Line by line:**

- **Five keys, and each one has exactly one writer.** `claim` was seeded by the caller, `reading` by
  the framework because of `output_key`, and the other three by the rules node's `state_delta`.
- `reading` holds **the model's text, not an object** — and it is cut off at sixty-four characters
  by the print, not by the framework. The framework writes what the agent said; the parsing is the
  reading node's problem, which is why `parse_reading` sits next to the node that calls it.
- `error` is present and empty — **the success path writes it too**, so no reader has to distinguish
  "no error" from "this run did not get that far".
- `reason unknown_policy` — this run passed `None` for the cover, so the rules had no policy to
  check against. **The state shows the verdict and not the reason it was reached**, which is the
  honest limit of a sheet: it records conclusions.
- **Nothing personal is here.** The description was the question, not a state key, and day 8's
  `check_state` still refuses anything whose name says otherwise.

## When it breaks

Write the loop's writer instruction with `{feedback}` instead of `{feedback?}` and run it:

```
KeyError: 'Context variable not found: `feedback`.'
```

Verbatim, from this project. The first pass through the loop is the one that fails, because on the
first pass no checker has run and nothing has written `feedback` — the key the instruction demands
exists only after the thing that needs it has already happened once.

That is the shape of the mistake worth remembering: **a template read from state is a dependency on
another node having run**, and the first iteration of any loop is the one where that is false. The
`?` is the framework saying it knows.

The smallest fix is the question mark. The fix a reviewer will ask for is a seeded key — writing
`feedback: ""` into the state when the run starts — and it is worth arguing about, because a seeded
empty string and an absent key are different facts and only one of them says *nobody has objected
yet*.

## In production

**What a senior writes instead.** The same keys, with a **state schema** — the framework accepts one
on a workflow node — so that a key nobody declared is refused rather than silently created. What
they would insist on immediately is what this project already does by hand: **every key a node reads
or writes appears where the node is built**, so a mismatch between two nodes is visible at
construction rather than at three in the morning.

**What degrades at scale.** Five keys for one claim is a sheet you can read. The failure is not the
number of keys, it is the number of writers: with two nodes per claim and twelve claims in one
invocation, `outcome` has twelve writers and the last one wins. That is why `morning()` names its
keys after the claim, and part 3.1 is the run where they were not. In an insurer's terms, a shared
key across a morning's several hundred notifications is one verdict surviving and several hundred
lost — silently, because a dictionary does not complain about being written twice.

**The review comment.** *"This node writes `outcome` and so does the node in the other branch. One
of these two claims is going to get the other's verdict, and no test you have will notice, because
they pass individually."*

**The interview question.** *"Two stages of your pipeline communicate through shared state rather
than arguments. Name two things you lose by that, and say what you would put in place of each."*
