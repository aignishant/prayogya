## One-line answer

Sixteen tests hold the arrangement to its shape, the loop to its bound, the state to one key per
claim — and three of them assert on the workflow **object** without running it at all, which is the
thing day 9's `for` loop made impossible.

## The idea

There is a kind of test that only became available today.

Yesterday, to find out whether the classifier runs before the rules, you had to run the desk and
look at what came out. The order was a fact about a function body, and the only way to observe a
function body is to execute it. Every test about the order was therefore also a test about the
model, the boundary, the store and the session — and when one failed, the order was the last thing
you would suspect.

Today the order is an object with a shape, so three of this file's tests build a workflow, ask it
what it is, and assert on the answer. They call no model, touch no boundary and take no measurable
time. **A test that can fail for exactly one reason is worth more than a test that covers more
ground**, and this is the first day this project could write one about its own control flow.

The rest of the file is the other kind, and there is no getting away from it: whether the loop
actually stops, what it costs when it does not, and what twelve branches do to one dictionary are
all questions you can only answer by running the thing.

## The mechanism

def stubborn_loop() -> LoopAgent:
    return LoopAgent(
        name="correspondence",
        description="A loop whose writer cannot take the objection.",
        sub_agents=[
            Agent(
                name="letter_writer",
                model=NeverImproves(),
                description="Writes the same thing every time.",
                instruction="Write the letter.",
                output_key="letter",
            ),
            workflow.HouseStyle(name="house_style", description="Refuses a figure."),
        ],
        max_iterations=3,
    )


def test_the_bound_is_what_stops_a_loop_that_cannot_converge() -> None:
    """Three drafts, all refused, and then it stops. Without `max_iterations` it would not."""

    async def run() -> tuple[list, str]:
        _answer, events = await sessions.turn(
            stubborn_loop(),
            "FNOL-4480",
            "Claim: FNOL-4480",
            state={"claim": "FNOL-4480"},
            thread="stubborn",
        )
        stored = await sessions.stored("FNOL-4480", "stubborn")
        return events, str(stored.state.get("feedback", ""))

    events, feedback = asyncio.run(run())
    drafts = [event for event in events if event.author == "letter_writer"]
    assert len(drafts) == 3
    assert feedback == workflow.OBJECTION

def test_one_message_reaches_every_branch_so_twelve_claims_read_as_one() -> None:

    queue = list(Store().notifications())

    async def run() -> list[str]:

            workflow.morning(queue),
            "morning",

- **The fixture is the same three lines as days 6, 8 and 9** — scratch claims directory, fresh
  session service, transport swapped at `boundary.connected`. This is the fourth file to carry them
  and the rep to move it into a shared fixture is now overdue rather than optional.
- `def a_notification(claim_id="FNOL-4477")` — **a helper, not a fixture**, because it is cheap and
  four tests want it. A fixture would make each of those tests take an argument that adds nothing.
- `test_the_triage_workflow_is_two_stages_and_one_of_them_is_code` — **three assertions, one per
  column of `stages()`**: the names in order, the kinds in order, the depths in order. Splitting them
  is deliberate: a failure says *the kinds changed* rather than *the shape changed*.
- `["SequentialAgent", "LlmAgent", "Rules"]` — **the third one is this project's own class name.**
  If somebody replaces the code node with a model-backed agent — the obvious "improvement" — this is
  the line that objects, and it objects loudly.
- `test_only_one_node_in_triage_costs_anything` — **one assertion, and it is about money.** Adding a
  second model node to triage doubles the desk's per-claim bill; this makes that a decision somebody
  has to make on purpose.
- `assert loop.max_iterations == 3` — **the bound, pinned by a test.** Part 2.2 argues that a loop
  without its own bound is unbounded; this is what stops the argument being lost.
- `writer.instruction.endswith("{feedback?}\n")` — **including the question mark**, which is the
  whole of part 1.2's failure. An instruction ending `{feedback}` would pass a substring check and
  fail on the first pass of every loop.
- `assert budget.by == {"letter_writer": 1}` and `== {"letter_writer": 2}` — **the same assertion on
  two claims, and the difference between them is the whole of part 2.1.** One clean draft, one that
  needed the objection.
- `assert "2500" not in letter` **and** `assert "fast-track limit" in letter` — **the repair removed
  the figure and kept the point.** Either assertion alone is satisfied by a wrong answer: an empty
  letter passes the first, and the offending draft passes the second.
- `test_the_house_style_allows_the_one_number_a_letter_must_carry` — `scan = ...search` bound to a
  local name first, because the three assertions that follow are already long enough to wrap.
- `assert workflow.body_of("about FNOL-4477 only", "FNOL-4477") == "about  only"` — **two spaces**,
  and that is the honest output of a `replace`. A test that tidied it would be testing a function
  nobody wrote.
- `@pytest.mark.parametrize(("said", "complaint"), ...)` — **two failures of the parser, each with
  its own message.** The messages are asserted by equality, because "it returned some error" is not
  what the desk logs and not what a person reads.
- `test_triage_leaves_its_verdict_in_state_and_charges_one_call` — **the run and the state together.**
  `state["outcome"] == out["outcome"]` asserts the return value and the session agree, which is the
  seam `run_triage` sits on: it reads the state back out and could read the wrong key.
- `state["reading"].startswith("{")` — **the raw text, not an object.** A weak assertion on purpose:
  the strong one belongs to the parser's own test, and this one is about `output_key` having fired.
- `class NeverImproves(BaseLlm)` — **the fourth stand-in in this project**, announced with the
  `scripted/` prefix like the other three, and the only one whose defect is the point.
- `def stubborn_loop()` — **a whole workflow built inside the test file.** The nodes are the real
  `HouseStyle` and a fake writer, so what is being tested is the framework's loop and this project's
  checker, with only the thing under suspicion replaced.
- `assert len(drafts) == 3` — **the bound held.** Without `max_iterations` this test does not fail
  slowly; it fails with the framework's ceiling error, which is part 2.2's argument in one assertion.
- `assert feedback == workflow.OBJECTION` — **state after a give-up.** The loop ended with the
  objection still standing, which is how a caller can tell "accepted" from "ran out".
- `pytest.raises(LlmCallsLimitExceededError)` — **the framework's exception, imported from
  `google.adk.agents.invocation_context`.** Naming it in a test is also how a reader finds out where
  it lives.
- `assert "limit of \`1\` exceeded" in str(raised.value)` — **substring, including the backticks the
  framework puts round the number.** The number is the part that matters and the phrasing is the
  part that might change.
- `assert len(named) == 1 + 3 * len(queue)` — **arithmetic rather than 37**, so the test still says
  what it means if the queue fixture grows.
- `test_every_branch_shares_one_agent_name_so_the_bill_cannot_be_split` — **a test that asserts a
  defect**, and its name says so. It is not a wish; it is a record of what this arrangement does, and
  it will fail the day somebody fixes it, which is the correct moment to delete it.
- `test_one_message_reaches_every_branch_so_twelve_claims_read_as_one` — **`len(set(perils)) == 1`.**
  Twelve claims, one peril. The same shape: an assertion that the thing is broken, so that the day it
  is not, something red says so.

## When it breaks

Take `max_iterations` off `correspondence()` — the change part 2.2 argues against — and run the
file:

```
FAILED tests/test_workflow.py::test_the_correspondence_workflow_is_a_bounded_loop
1 failed, 15 passed in 2.38s
```

Verbatim, from this project. **One test out of sixteen**, and it is the one that never runs
anything.

Look at what stayed green. `test_a_draft_that_names_a_figure_is_written_again` passes: two drafts,
the second accepted, the loop exits on `escalate` exactly as before. An unbounded loop behaves
identically **on every input that converges**, and every input in this project's fixtures converges.

Worse, the test whose name is about the bound —
`test_the_bound_is_what_stops_a_loop_that_cannot_converge` — also passes, and that one is on me. It
builds `stubborn_loop()`, its own `LoopAgent`, with its own `max_iterations=3`. It is a good test of
the framework's loop and **it defends nothing about `correspondence()`**, because it never touches
it. A test that constructs its own subject cannot notice a change to the real one.

So the only thing standing between this desk and an unbounded letter loop is
`assert loop.max_iterations == 3` — a single line that builds the real workflow and asks it a
question. **Assert on the object for the properties that are about the object**, because the
properties that only show up on inputs you do not have are the ones no run test will ever reach.

The smallest fix is putting the bound back. The second fix, which this project owes, is a
`TODO(me)`: rewrite `test_the_bound_is_what_stops_a_loop_that_cannot_converge` so that it swaps only
the writer's model into `workflow.correspondence()` rather than rebuilding the loop, and confirm it
goes red when the bound is removed.

## In production

**What a senior writes instead.** The same split — shape tests and run tests — with the shape tests
generated from a declaration: a table of workflows and their expected node lists, so adding a
workflow without adding its shape test is impossible rather than merely rude. What they would insist
on for the run tests is a **timeout**, because a loop bug that used to be a failing assertion becomes
a hanging suite the day somebody removes both bounds.

**What degrades at scale.** Sixteen tests for three workflows, and the run tests already dominate
the wall clock: 2.11 seconds, almost all of it in the four that execute something. At a dozen
workflows the shape tests stay instantaneous and the run tests do not, so what survives is running
every shape and a chosen few end to end. For this desk the chosen few are obvious — the ones that
spend money.

**The review comment.** *"This test asserts that all twelve branches read the same peril. That is a
bug, not a requirement. Either the name says it is a bug and the test is a tripwire, or delete it —
right now it reads like we meant this."*

**The interview question.** *"Show me a test you would write about a pipeline that never executes
it. Then tell me what class of defect that test can catch and what it cannot."*
