## One-line answer

A `LoopAgent` runs its children over and over until one of them sets `escalate` on an event it
yields — so the desk's letter is drafted, checked by a node with no model in it, and drafted again
with the objection in its instruction, which costs a second call on exactly one claim in twelve.

## The idea

Nobody posts the first draft.

A letter that goes out on the company's paper is read by someone else first, and the reading is
narrow: not *is this good*, but *does it break a rule we have written down*. In a claims department
the shortest of those rules is the one about amounts. A deficiency letter names what is missing. It
does not name a figure, because a figure in an outgoing letter is a number the company has now
stated, and the person who wrote it had no way to check it.

The letter comes back with one line on it, and it is an instruction rather than a critique: *no
figures — rewrite it*. The second draft goes out.

That arrangement has a shape a workflow can hold. Two stages, in a cycle, with something that
decides when the cycle stops. In ADK that is a **`LoopAgent`**: it runs its children in order,
again and again, until an event goes past carrying `escalate`.

Two things about it are worth having straight before reading any code.

**The checker is not an agent with an opinion.** It is code. It scans for a digit, and the whole of
its judgement is a regular expression somebody can argue with. A model asked *is this letter
acceptable* would be a second thing that can be wrong, in a way nobody can audit, about the work of
the first thing that can be wrong.

**The objection has to reach the writer.** It cannot be handed over — nodes do not pass arguments —
so it goes where part 1.2 put everything else: into state, under `feedback`, and from there into the
writer's instruction through `{feedback?}`. The writer is not told it is on its second attempt. It
is given a sentence it did not have before.

## The mechanism

The loop, from `claims_desk/workflow.py`, printed whole in part 1.1:

```python
def correspondence() -> LoopAgent:
    """Draft, check, and draft again if the house style refuses — at most three times."""
    writer = Agent(
        name="letter_writer",
        model=models.pinned(ScriptedLetterWriter()),
        description="Writes a deficiency letter from a claim reference and one reason.",
        instruction=letter_writer.INSTRUCTION + FEEDBACK_CLAUSE,
        output_key="letter",
    )
    return LoopAgent(
        name="correspondence",
        description="Writes a letter and rewrites it until it passes the house style.",
        sub_agents=[
            writer,
            HouseStyle(name="house_style", description="Refuses a draft that names a figure."),
        ],
        max_iterations=3,
    )
```

**Line by line:**

- `sub_agents=[writer, HouseStyle(...)]` — **order is the cycle.** Write, then check, then write,
  then check. Putting the checker first would check an empty draft, refuse it, and spend the whole
  bound before a single letter existed.
- `output_key="letter"` — **the draft lands in state**, which is the only place the checker can look
  for it. The writer does not hand it over and the checker does not receive it.
- `instruction=letter_writer.INSTRUCTION + FEEDBACK_CLAUSE` — **day 9's five rules, plus the slot the
  objection arrives in.** The rules are not restated here; the module that owns them still owns them,
  and this line is the whole of the loop's addition to the prompt.
- `max_iterations=3` — the bound. Part 2.2 is about what it is for; here it is enough to say that
  three drafts is a decision somebody made about money, written where it can be found.
- **The checker gets a `description` even though nothing reads it.** A workflow node's description is
  what `stages()` and any future diagram will show, and "Refuses a draft that names a figure" is the
  one-line summary of a rule that would otherwise only exist as a regular expression.

The checker, printed in part 1.1, is where the loop actually ends:

```python
    async def _run_async_impl(self, ctx: InvocationContext) -> AsyncGenerator[Event, None]:
        state = ctx.session.state
        draft = str(state.get("letter", ""))
        claim = str(state.get("claim", ""))
        offending = FORBIDDEN_IN_A_LETTER.search(body_of(draft, claim))
        accepted = draft.strip() != "" and offending is None
        log(
            "workflow.house_style",
            claim=claim,
            accepted=accepted,
            found=offending.group(0) if offending else None,
            chars=len(draft),
        )
        yield Event(
            author=self.name,
            invocation_id=ctx.invocation_id,
            actions=EventActions(
                escalate=accepted,
                state_delta={"feedback": "" if accepted else OBJECTION},
            ),
        )
```

**Line by line:**

- `draft = str(state.get("letter", ""))` — **the key the writer's `output_key` wrote.** Two lines
  apart in the file that builds them, which is the only thing keeping them in agreement.
- `body_of(draft, claim)` — **the claim reference is removed before the scan.** `FNOL-4477` is four
  digits, and a check that refuses it refuses every letter this desk will ever write.
- `accepted = draft.strip() != "" and offending is None` — **empty is not acceptable.** A writer that
  produced nothing has failed, and without this clause an empty draft would sail past a scan that
  finds no digits in it.
- `found=offending.group(0) if offending else None` — **the log says which character caused it.**
  Not "rejected": rejected on a `2`. That is the difference between a log you can act on and a log
  you can only count.
- `escalate=accepted` — **the entire stopping condition**, and it is a boolean on an event. The
  `LoopAgent` reads `event.actions.escalate` as each event goes past and breaks when it is true.
- `state_delta={"feedback": "" if accepted else OBJECTION}` — **cleared on acceptance**, which
  matters more than it looks: a leftover objection in state would arrive in the next claim's
  instruction, and the writer would obey an instruction about a letter it never wrote.
- **One event carries the decision and its consequence.** A reader of the session sees, in one
  place, that the check failed and what was written for the next pass.

**Line by line:**

- `-from claims_desk.agents import classifier, letter_writer` — **the desk no longer imports either
  agent.** It imports the workflow, and the workflow imports the agents. That is the direction of
  the day: the thing that owns the order is between the desk and the specialists.
- `CALLS_PER_NOTIFICATION = 5` — **three to five**, and the comment says the arithmetic: one
  classification, up to three drafts, one spare. Part 2.2 is about why the loop still needs its own
  bound as well.
- `read = await workflow.run_triage(notification, cover, budget)` — **one call replaces a call and a
  rule application.** `assess` used to be invoked here; it is now invoked by the rules node, inside
  the workflow, in the same event stream as the reading that fed it.
- `if read["error"] or not read["outcome"]:` — **two conditions where there was one.** A workflow can
  fail in a way a function call cannot: it can run to completion, report no error, and leave nothing
  in state — which is what happens if a node is removed. `not read["outcome"]` is the guard for that.
- `- loss_type=read["loss_type"],` — **gone from the log line**, because the desk no longer sees the
  loss type. It is in the workflow's own `workflow.rules` line instead, next to the verdict it
  produced. Moving a fact out of one log and into another is a real cost, and the trade is that the
  reading and the rule are now logged together.
- `+ async def write_letter(...)` — **day 9's `letter_writer.write`, minus the drafting.** The

  `run_correspondence`.

  exactly where it would have been lost: `materials` is fetched, `refused` is checked, and only then
  does anything cost money.

- `letter = await write_letter(verdict.claim_id, verdict.reason, budget)` — **five lines become
  one** in `run_queue`, because the error handling moved into the function that can describe the
  error.

## When it breaks

Take the `escalate` out — make the checker log its verdict and yield an event that says nothing:

```
{"ts": "2026-09-10T15:44:54.345+00:00", "event": "workflow.house_style", "claim": "FNOL-4477", "accepted": true, "found": null, "chars": 138}
{"ts": "2026-09-10T15:44:54.346+00:00", "event": "workflow.house_style", "claim": "FNOL-4477", "accepted": true, "found": null, "chars": 138}
{"ts": "2026-09-10T15:44:54.347+00:00", "event": "workflow.house_style", "claim": "FNOL-4477", "accepted": true, "found": null, "chars": 138}
{"ts": "2026-09-10T15:44:54.347+00:00", "event": "session.turn", "claim": "FNOL-4477", "session": "claim-FNOL-4477/correspondence", "yielded": 6, "chars": 138}
{"ts": "2026-09-10T15:44:54.348+00:00", "event": "workflow.correspondence", "claim": "FNOL-4477", "reason": "missing_photo_reference", "drafts": 3, "accepted": true, "chars": 138}
```

Verbatim, from this project. Nothing failed. The letter is correct, the check passed on the first
pass — `"accepted": true` on all three lines — and the desk wrote it **three times**, because a
`LoopAgent` with nothing to stop it runs to `max_iterations` every single time. `"yielded": 6` is the
same fact from the runner's side: six events where two would do.

Read what that costs before the fix. Eight letters in this queue, three drafts each instead of one:
**sixteen extra model calls per run of a twelve-claim queue**, for output that is thrown away.
Nothing is red. No test that only checks the letter would notice. The only evidence is that the log
has three identical lines in it where it should have one, and `drafts: 3` where it should say 1.

The smallest fix is `escalate=accepted`, one keyword on one event. The general lesson is worth more:
**a loop's exit is a thing you write, not a thing you get.** Every `LoopAgent` needs a node that can
say stop, and the bound is what happens when that node never does.

## In production

**What a senior writes instead.** The same two nodes, with the checker's rules in a list rather than
one expression — no figures, no timescale, no apology — each with its own objection sentence, so the
writer is told which rule it broke rather than the only rule anyone bothered to encode. What they
would add immediately is a **record of the rejected drafts**: this loop keeps only the last one, and
the interesting artefact when a letter goes wrong is the draft that was thrown away.

**What degrades at scale.** One extra draft in twelve claims is one extra call. The number that
matters is not the average, it is the tail: a wording change to the house style that suddenly makes
a common phrasing fail turns one-in-twelve into most-in-twelve, and the morning's several hundred
notifications cost three drafts each instead of one. **A repair loop converts a quality problem into
a cost problem silently**, which is exactly why the bound is not optional and why `drafts` is in
every log line.

**The review comment.** *"The checker returns a boolean and writes one fixed objection. When we add
the second rule, the writer gets an objection about figures for a letter that mentioned a timescale.
Make the objection come from the rule that failed."*

**The interview question.** *"You have a generate-and-check loop. Say who decides it has finished,
what happens if that decision is wrong in each direction, and which of the two you would rather
have."*
