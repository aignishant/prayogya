## One-line answer

There are two bounds and they do different jobs: `max_iterations` says how many times a loop may go
round, and `max_llm_calls` says how many model calls one run may make in total — the first shapes
the work, the second is the thing that actually stops a runaway, and it raises rather than returning
a poor answer.

## The idea

Every department has a rule that exists because of one incident.

Not the sensible ones about photographs and excesses — those are policy. This is the other kind: the
one somebody wrote after a morning where a letter went back and forth between two desks eleven times
because neither would sign it, and nobody noticed until the post did not go out. The rule that came
out of it is not about quality. It is *three attempts, then it comes to me*.

A repair loop is that arrangement, built out of software, with the same failure available to it and
none of the friction that would make a person notice. Two clerks arguing take a morning. Two nodes
arguing take four seconds and a bill.

So the loop needs a number, and the interesting thing about the number is that **one is not enough**.

`max_iterations` bounds the loop. It is a good bound and it is a *local* one: it knows about this
loop and nothing else. If the letter loop is inside something else that also repeats, or if a claim
runs two loops, `max_iterations` on each of them says nothing about the total.

`max_llm_calls` bounds the **invocation** — one run, everything inside it, however deeply nested. It
is the framework's own ceiling, it is set on `RunConfig`, and when it is reached it does not return a
partial answer or a default: it raises. Which is right, and is worth arguing about, because a
system that quietly finishes with less work than it should have done is the harder failure to find.

This desk now has three numbers about the same thing, and they have to agree: `max_iterations = 3`
inside the loop, `CALLS_PER_NOTIFICATION = 5` in the desk, and `max_llm_calls` passed per run from
whatever the budget has left. Part of the job today is making them agree on purpose rather than by
luck.

## The mechanism

The bound reaches the framework through one line of `sessions.turn`, printed as a marked diff in
part 1.2, and it is derived rather than chosen:

```python
    _answer, events = await sessions.turn(
        agent,
        claim_id,
        question,
        state={"claim": claim_id},
        thread="correspondence",
        max_calls=budget.remaining,
    )
```

**Line by line:**

- `max_calls=budget.remaining` — **not a constant.** The framework's ceiling for this run is
  whatever the desk's budget has left after everything else this claim has already spent, so the two
  bounds cannot drift apart: there is only one number and the other is computed from it.
- **`remaining`, not `limit`.** A claim that spent one call on triage arrives at the letter loop with
  four, and the loop's ceiling is four. Passing `limit` would give the loop the whole allowance a
  second time, which is day 9 part 3.2's mistake wearing a different hat.
- **The loop's own `max_iterations=3` is still there and still does something.** It bounds the number
  of *passes*, which is what the department's rule is actually about; the call ceiling bounds the
  *bill*. A pass that spent no model call — because a node is code — costs nothing against the
  second and everything against the first.

Now break the thing the bound exists for. A writer that cannot take the objection:

```python
class NeverImproves(BaseLlm):
    """A stand-in that ignores the objection and writes the same offending draft every time."""

    model: str = "scripted/never-improves"

    async def generate_content_async(
        self, llm_request: LlmRequest, stream: bool = False
    ) -> AsyncGenerator[LlmResponse, None]:
        yield LlmResponse(
            content=types.Content(
                role="model", parts=[types.Part(text="We will settle at 2500 pounds.")]
            ),
            turn_complete=True,
        )
```

**Line by line:**

- `model: str = "scripted/never-improves"` — **announced**, like every double in this project, and
  the name says what it does rather than what it is for.
- **It ignores `llm_request` entirely.** Day 9's transfer stand-in read what it had been sent; this
  one does not, and that is the behaviour being modelled: a writer that does not use the feedback.
- `"We will settle at 2500 pounds."` — **a figure and a promise**, which breaks the house style twice.
  It only needs to break it once; the second is there so the draft is obviously wrong to a reader.
- **This is not a far-fetched model.** A real writer that has been told *no figures* and is holding a
  reason called `above_fast_track_limit` has a strong pull toward the number, and "it ignored the
  objection" is a thing that happens.

Put it in the loop and watch:

```
  author=letter_writer  escalate=None
  author=house_style    escalate=False
  author=letter_writer  escalate=None
  author=house_style    escalate=False
  author=letter_writer  escalate=None
  author=house_style    escalate=False
drafts: 3
```

**Line by line:**

- **Three passes, then it stops.** Not because anything succeeded — every check refused — but because
  `max_iterations` ran out. That is the bound doing its only job.
- `escalate=None` **on every writer event** — the field is unset rather than `False`, which is day
  8's three-state lesson again. A `LoopAgent` breaks on `True` and treats `None` and `False` alike.
- `escalate=False` **on every checker event** — the checker is deciding, every pass, and deciding no.
- **The loop ended with `feedback` still set to the objection.** The last thing written into state is
  a complaint about a draft nobody is going to fix, which is exactly what a caller needs in order to
  know the difference between "accepted" and "gave up".
- **`run_correspondence` returns an empty string for this claim**, because the accepted-draft check
  runs again outside the loop. The desk logs `desk.letter_failed` and records the decision without a
  letter — a claim decided and a letter owed, which is a state a person can act on.

Now take the outer ceiling below what the loop needs:

```bash
uv run python -c "
import asyncio
from claims_desk import workflow
from claims_desk.util.budget import Budget

async def main():
    try:
        await workflow.run_correspondence(
            'FNOL-4480', 'above_fast_track_limit', 'nothing further', Budget(limit=1)
        )
    except Exception as raised:
        print(type(raised).__name__ + ': ' + str(raised))

asyncio.run(main())
"
```

```
LlmCallsLimitExceededError: Max number of llm calls limit of `1` exceeded
```

**Line by line:**

- **A budget of one, and this claim needs two drafts.** The first draft is written, the checker
  refuses it, the second draft is requested, and the framework stops the invocation.
- `LlmCallsLimitExceededError` — **the framework's own exception**, from
  `google.adk.agents.invocation_context`. It is not this project's `BudgetExceeded`, and the two now
  coexist: one is the desk's rule, the other is the runtime's.
- **It raises out of `run_correspondence` and out of `desk.write_letter`**, and nothing catches it.
  That is deliberate: `BudgetExceeded` means *this claim asked for more than its share*, which the
  queue can absorb by leaving the claim pending; this means *a run went past the ceiling the runtime
  was given*, and continuing after that is how a bad morning becomes an expensive one.
- **The message names the number and not the agent.** Which agent asked for the call that broke the
  ceiling is in the events, not in the exception — one more reason the log line comes first.

## When it breaks

The failure worth causing is not the exception. It is the version with the ceiling and **no
`max_iterations`**, because that is the one that looks fine.

Take the bound off the loop — build it without `max_iterations` — and run the stubborn writer with
the desk's real budget of five:

```
LlmCallsLimitExceededError: Max number of llm calls limit of `5` exceeded
```

Verbatim, from this project. The loop ran until the money ran out, and the thing that stopped it was
a ceiling meant for the whole claim, not a bound meant for this loop. Everything about that is
wrong in a way that only shows up later:

- **The claim is lost, not degraded.** With `max_iterations`, this claim ends with a decision and no
  letter, and the log says which. With only the outer ceiling, the invocation dies and the desk gets
  an exception where a verdict should be.
- **The allowance for the rest of the claim is gone.** Day 15's retry is supposed to be able to spend
  the fifth call. A loop with no bound of its own will always take it.
- **The number in the message is the wrong number to act on.** Somebody reading `limit of \`5\``
  starts by asking whether five is too low. The answer is that five is fine and the loop is broken.

The smallest fix is `max_iterations=3`. The rule underneath it is the one to carry to the next
project: **an outer ceiling is a safety net, not a bound.** If the only thing stopping a loop is the
budget for the whole unit of work, the loop is unbounded and you have not noticed yet.

## In production

**What a senior writes instead.** The same two bounds, with the loop's own bound in configuration
next to the ceiling it must stay under, and a check at startup that the inner numbers cannot exceed
the outer one. What they would add first is a **counter that survives the run**: not "this loop hit
its bound", but "this loop hit its bound on 4% of claims this week", because one claim reaching the
bound is noise and a rising fraction is a wording change nobody tested.

**What degrades at scale.** Three drafts on one claim is invisible. On a morning's several hundred
notifications with two thirds deficient, a house-style rule that starts refusing a common phrasing
takes the letter cost from roughly two hundred calls to six hundred — **and every one of those runs
still succeeds**, so nothing is red, the queue finishes, and the only signal is the bill. The
mitigation is the same counter: `drafts` in every log line, aggregated.

**The review comment.** *"This loop has no `max_iterations` and you have told me it terminates
because the checker always eventually passes. The checker is the thing most likely to change. Put
the bound in."*

**The interview question.** *"Your agent loop has a per-run call ceiling that would stop it. Explain
why it still needs its own iteration bound, and describe an incident where having only the ceiling
would have made things worse."*
