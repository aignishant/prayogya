## One-line answer

A `ParallelAgent` built from the queue runs twelve triages in one invocation in a fifth of a second —
and this desk does not use it, because it fans out the *invocation* and not the *input*, so all
twelve branches read the same message and answer the same thing.

## The idea

The morning queue is a stack of twelve notifications and one person working through it. The obvious
improvement is more people, and the obvious way to get it wrong is to give all of them the same
sheet.

That sounds too stupid to be a real failure mode, and in an office it is. In software it is the
default, because the thing being parallelised is not the work — it is the *run*. A parallel
arrangement takes one request and gives it to several branches at the same time. Every branch gets
the same request. That is what parallel means here.

For most uses that is exactly right: three specialists reading the same claim from three angles, all
given the same claim. It is precisely wrong for twelve claims, because the twelve claims are twelve
different inputs and there is only one message.

This part builds it anyway and measures it, for two reasons. The first is that `ParallelAgent` is
part of the spine and a project that ships it untested has not shipped it. The second is better:
**the version that does not work is more instructive than the version that does**, because the
reason it does not work is a property of the runtime rather than a bug in this desk, and it will be
true in the next project too.

## The mechanism

The arrangement, from `claims_desk/workflow.py`, printed whole in part 1.1:

```python
def morning(notifications: list[Notification]) -> ParallelAgent:
    """Every notification in the queue, triaged at the same time, in one invocation."""
    return ParallelAgent(
        name="morning",
        description="The whole queue at once.",
        sub_agents=[
            SequentialAgent(
                name=f"triage_{slug(note.id)}",
                description=f"Triage for {note.id}.",
                sub_agents=[
                    classifier.build(output_key=f"reading_{slug(note.id)}"),
                    Rules(
                        name=f"rules_{slug(note.id)}",
                        description=f"Rules for {note.id}.",
                        notification=note,
                        reading_key=f"reading_{slug(note.id)}",
                        verdict_key=f"outcome_{slug(note.id)}",
                    ),
                ],
            )
            for note in notifications
        ],
    )
```

**Line by line:**

- **A list comprehension inside a constructor.** The arrangement is built from the queue at run time,
  which is only possible because a workflow is a value. There is no declaration of this shape
  anywhere; there is a function that makes one the size of whatever it was handed.
- `name=f"triage_{slug(note.id)}"` — **every node in one workflow needs a distinct name**, and the
  claim reference is the only thing to hand that is unique. `slug` exists because `FNOL-4471` is not
  an identifier and the framework wants one.
- `reading_key=` and `verdict_key=` — **the state keys, namespaced by claim.** Part 1.2 explained why
  the `Rules` node has those fields at all, and this is the caller that needs them: twelve nodes
  writing `outcome` into one dictionary is eleven verdicts lost.
- **Each branch is a `SequentialAgent` inside a `ParallelAgent`.** The parallelism is across claims;
  the ordering is within one. Nesting is how a workflow expresses that, and it is why `stages()`
  reports a depth.
- **The classifier node has the same name in every branch.** `classifier.build()` sets it, and this
  code does not override it. That is a defect, and it is measured below.

Build it and run it:

```bash
uv run python -c "
import asyncio, json, time
from claims_desk import sessions, workflow
from claims_desk.store import Store

queue = list(Store().notifications())

async def main():
    agent = workflow.morning(queue)
    print('nodes:', len(workflow.stages(agent)), '| model nodes:', workflow.model_nodes(agent))
    t = time.perf_counter()
    answer, events = await sessions.turn(
        agent, 'morning', chr(10).join(n.description for n in queue), thread='parallel'
    )
    print('events:', len(events), 'in %.2f seconds' % (time.perf_counter() - t))
    stored = await sessions.stored('morning', 'parallel')
    perils = [
        json.loads(v)['loss_type']
        for k, v in sorted(stored.state.items())
        if k.startswith('reading_')
    ]
    print('readings:', len(perils), '| distinct perils:', sorted(set(perils)))

asyncio.run(main())
"
```

```
nodes: 37 | model nodes: {'classifier'}
events: 24 in 0.22 seconds
readings: 12 | distinct perils: ['escape-of-water']
```

**Line by line:**

- `nodes: 37` — **one parallel parent, and twelve branches of three.** `1 + 12 × 3`. The whole
  arrangement is inspectable before it runs, which is the entire argument of part 1.1 arriving where
  it is most useful: nobody would read thirty-seven nodes out of a `for` loop.
- `model nodes: {'classifier'}` — **the first defect, and it is a set of one.** Twelve nodes call a
  model and they all answer to the same name, so `charge()` — which counts by author — would record
  twelve calls against `classifier` and there would be no way to tell which claim cost what.
- `events: 24` — two per branch, the reading and the verdict, and **no event says which claim it was
  about** except through the node names inside it.
- `in 0.22 seconds` — **fast, and the number is meaningless.** The stand-in answers from a table, so
  what is being measured is twelve dictionary lookups running concurrently. Against a provider this
  is where the saving would be; this project cannot show it.
- `readings: 12` — **the namespacing worked.** Twelve keys, one per claim, no collisions. That part
  of the design is sound and is the part worth taking to the next project.
- `distinct perils: ['escape-of-water']` — **the second defect, and it is the fatal one.** Twelve
  claims, twelve different descriptions, and every branch answered *escape-of-water*.

The reason is one sentence and it is not a bug in this code: **the message is the invocation's, not
the branch's.** `sessions.turn` sends one user message; the `ParallelAgent` runs twelve branches
against it. Every classifier saw all twelve descriptions concatenated, and the stand-in matched the
first phrase it recognised — which is FNOL-4471's flexible hose, an escape of water.

A real model would do something worse than uniform: it would answer *something* for a blob of twelve
unrelated incidents, differently in each branch, and nothing in the run would say the input was
wrong.

## When it breaks

Remove the namespacing — let every branch write `outcome`, `reason` and `reading`, as a first draft
naturally would:

```
{"event": "workflow.rules", "claim": "FNOL-4471", "loss_type": "escape-of-water", "outcome": "deficiency", "reason": "unknown_policy"}
{"event": "workflow.rules", "claim": "FNOL-4472", "loss_type": "escape-of-water", "outcome": "deficiency", "reason": "unknown_policy"}
{"event": "workflow.rules", "claim": "FNOL-4473", "loss_type": "escape-of-water", "outcome": "deficiency", "reason": "missing_date_of_loss"}
...
verdict keys kept: ['error', 'outcome', 'reading', 'reason']
outcome: deficiency | reason: missing_contact
```

Verbatim, from this project, and the thing to notice is that **nothing complains**. No error, no
warning, no refusal. Twelve rules nodes ran, twelve verdicts were computed, twelve events were
emitted saying so — and the session ends holding **one** of them.

Read the last two lines together. Four keys survive where forty-eight were written. The reason that
survives is `missing_contact`, which belongs to exactly one of the twelve claims, and there is
nothing in the state to say which. Eleven verdicts were computed correctly, written correctly, and
overwritten.

The failure is a race, which makes it worse than merely wrong: which branch writes last depends on
scheduling, so the run can keep a different claim's verdict tomorrow with nothing changed. And the
per-claim log lines are all still there and all still correct, so a person reading the log sees
twelve good verdicts and a person reading the state sees one.

The smallest fix is the two fields on `Rules` and a key built from the claim reference. The sentence
worth keeping: **shared state plus parallelism is a data race, and a dictionary never complains
about being written twice.** Any state a parallel branch writes is named after the branch, and a
reviewer should be able to see that where the workflow is built rather than by running it.

## In production

**What a senior writes instead.** For twelve independent claims: not this. Twelve invocations run
concurrently with `asyncio.gather`, each with its own session, its own state and its own budget —
which gives real isolation, per-claim ceilings and a per-claim record, and costs nothing but a
semaphore. `ParallelAgent` is for **several agents over one input**, and using it for several inputs
is using it against its grain.

**What degrades at scale.** The measurement that decides it is not the 0.22 seconds. This desk's
queue takes **42.2 seconds** for twelve notifications, and almost all of that is the boundary: a
policy fetch, an in-force check, a letter draft and a decision record, each over a fresh stdio
process — **42 subprocess launches**. The model calls are seventeen and, against this stand-in, free.
So the parallelism on offer here parallelises the part that is not the bottleneck. On a morning's
several hundred notifications the same shape holds: the win is in the input/output, and it is not
what `ParallelAgent` fans out.

**The review comment.** *"This builds one workflow with a branch per queue item. Every branch gets
the same user message — check what your third claim actually classified before this goes any
further."*

**The interview question.** *"When would you fan out inside one agent run, and when would you run
several agent runs concurrently instead? Give the property of the work that decides it."*
