## One-line answer

With a schema declared, the framework validates the answer inside the turn and writes a **dict** into
state instead of a string — so day 10's parser loses two of its three jobs, and the refusal it could
never make arrives as a `ValidationError` raised out of the turn, which would stop the queue if
nobody caught it.

## The idea

There are three ways for a model's answer to be wrong, and only one of them is interesting.

**It is not JSON.** The model wrote a sentence, or wrapped the object in a code fence, or apologised
first. Easy to detect, easy to describe, and largely a solved problem — providers with a structured
output mode do not do this.

**It is JSON with a field missing.** Also easy: the key is not there.

**It is complete, well-typed JSON that says something this desk does not recognise.** A peril called
`water damage`. A confidence score nobody asked for. `injury_reported` as the string `"probably"`.
This is the one that matters, because **nothing about it looks like a failure.** It parses. It has
the right keys. It flows into the rules, and the rules do what rules do with an unrecognised peril —
they refuse the claim as not covered. A policyholder gets a letter saying their loss is not covered
by their policy, and the truth is that the classifier said something odd and nobody checked.

Day 10's `parse_reading` caught the first two and was blind to the third. It could not have done
otherwise: it did not know what a peril was.

A schema knows. And what happens when it knows is worth watching carefully, because the shape of the
failure moves: a bad answer stops being a value the caller inspects and becomes an **exception raised
inside the turn**. Day 11 spent a whole part on why that distinction matters, and today it happens
again from the other direction.

## The mechanism

With `output_schema=Reading` on the agent, what lands in state is not what landed there yesterday:

```bash
uv run python -c "
import asyncio
from claims_desk import sessions, workflow
from claims_desk.store import Store
from claims_desk.util.budget import Budget

note = {n.id: n for n in Store().notifications()}['FNOL-4477']

async def main():
    await workflow.run_triage(note, None, Budget(limit=5))
    stored = await sessions.stored('FNOL-4477', 'triage')
    reading = stored.state['reading']
    print('type: ', type(reading).__name__)
    print('value:', reading)

asyncio.run(main())
"
```

```
type:  dict
value: {'loss_type': 'fire', 'injury_reported': False, 'scripted': True}
```

**Line by line:**

- **`dict`, not `str`.** Day 12's version of this same command printed a JSON string that
  `parse_reading` had to load. The framework now validates the answer and writes the validated
  object.
- **`'injury_reported': False` is a Python boolean**, not the string `"false"`. The conversion
  happened inside the schema, once, in the place that declares what the type is.
- **`'loss_type': 'fire'` is a string and not `Peril.FIRE`** — that is `use_enum_values=True` from
  part 1.1, and it is what lets day 2's `assess` compare it against the policy's peril set unchanged.
- **`scripted: True` survived**, because part 1.1 declared it. Without that field and with
  `extra="forbid"`, this project's own stand-in would fail validation on every call — which is the
  kind of thing you find out immediately and would rather find out immediately.

So day 10's parser loses most of its reason to exist. A **marked diff against
`claims_desk/workflow.py` as printed on day 10 part 1.1, with day 11's hooks already in place**:

```python

-    needs the fields is the node that has to survive not getting them. **It never guesses on the
-    model's behalf** — an unparseable answer is reported, not repaired.

+    the agent an `output_schema`, so the framework validates the answer and writes a **dict** into
+    state — already parsed, already typed, already refused if the peril was not one of ours.
+

+    refused, or the node did not run, or somebody changed `output_key`. That is not a bad answer.
+    It is no answer, and it is the only thing this function still has to say.
```

**Line by line:**

- **Fourteen lines become four**, and the `json` import goes with them. A schema did not add
  validation to this project; it moved validation to a place that could do it properly and deleted
  the version that could not.
- `def parse_reading(reading: object)` — **the parameter is no longer a string.** It is whatever is
  in state, which is a dict on the happy path and `None` when nothing ran.
- **The docstring says what it no longer does**, which is the most useful thing a shrinking function
  can say. Somebody who remembers this function catching malformed JSON needs to know where that
  went.
- `if isinstance(reading, dict) and reading:` — **two conditions.** Not a dict at all, or an empty
  one; both mean nothing useful is there. An empty dict is what an agent that ran and produced
  nothing leaves behind.
- `return dict(reading), ""` — **a copy.** The value in state belongs to the session; handing the
  rules node a reference to it would let a node mutate the record of what the model said.
- `"the classifier left no reading in state"` — **one message where there were two.** It describes a
  missing key rather than a bad answer, because a bad answer can no longer get this far.
- `parse_reading(state.get(self.reading_key))` — **`str(...)` is gone from the call site.** That
  coercion was day 10 defending against `None`; the function now handles it, which is where it
  belongs.

## When it breaks

Ask the classifier about a description its stand-in has no answer for. Day 12's version returned an
error object and the desk marked the claim pending. Today:

```bash
uv run python -c "
import asyncio
from claims_desk import sessions
from claims_desk.agents import classifier

asyncio.run(
    sessions.turn(classifier.build(output_key='reading'), 'FNOL-9001', 'something nobody scripted')
)
"
```

```
ValidationError: 3 validation errors for Reading
error
  Extra inputs are not permitted [type=extra_forbidden, input_value='no scripted answer for this description', input_type=str]
loss_type
  Field required [type=missing, input_value={'scripted': True, 'error...r for this description'}, input_type=dict]
```

Verbatim, from this project. **Three errors, and the first one is the interesting one.** The stand-in
answered `{"scripted": true, "error": "no scripted answer for this description"}` — a perfectly
sensible refusal, and `extra="forbid"` refuses it, because `error` is not a field this desk declared.

Now read what that means for the queue. `ValidationError` is raised **inside** `sessions.turn`,
which means it comes out of `run_triage`, out of `desk.decide`, out of `run_queue` — and the
morning's remaining claims are never looked at. One description the classifier could not read stops
everything.

This is day 11's lesson arriving from the opposite direction. There, an exception was wrapped by a
framework and never reached the caller who expected it. Here, an exception arrives at a caller who
never expected one at all, because until today a bad answer was a returned value.

The fix is to catch it once, at the boundary where every other failure is already reported. A
**marked diff against `claims_desk/workflow.py` as printed on day 10 part 1.1**:

```python
+#: What `run_triage` reports when the model answered in a shape the schema will not accept. Day 13
+#: made that a `ValidationError` raised out of the turn, and a raised error would stop the queue on
+#: one bad answer — so it is caught once, here, and reported the way every other failure is.
+REFUSED_SHAPE = "refused_shape"

 async def run_triage(notification, cover, budget) -> dict[str, Any]:
     agent = triage(notification, cover)
     token = hooks.current_budget.set(budget)
     refused = hooks.refusals.set([])
+    rejected = ""
+    events: list = []
     try:
         _answer, events = await sessions.turn(...)
+    except ValidationError as refusal:
+        # The schema refused the answer. That is the classifier being wrong in a way day 10's
+        # hand-rolled parser could not see, and it arrives as an exception because the framework
+        # validates inside the turn. One claim's bad answer must not stop the morning's queue.
+        rejected = "; ".join(
+            f"{'.'.join(str(part) for part in error['loc'])}: {error['type']}"
+            for error in refusal.errors()
+        )
+        log("workflow.refused_shape", claim=notification.id, detail=rejected)
     finally:
         ...
+    if rejected:
+        return {"outcome": "", "reason": None, "error": REFUSED_SHAPE, "turned_away": turned_away}
```

**Line by line:**

- `REFUSED_SHAPE = "refused_shape"` — **a third failure mode with its own name**, beside day 11's
  `OVER_BUDGET`. Three reasons a claim goes pending, three constants, and a `waiting_for` that says
  which. Day 11's argument, applied again: a claim pending for the wrong reason is a claim nobody
  re-runs.
- `rejected = ""` **and** `events: list = []` **before the `try`** — both names are read after the
  block, and a `finally` that runs on the exception path would otherwise reference an unbound local.
- `except ValidationError as refusal:` — **caught by type, from pydantic**, not by message. The
  framework raises it unwrapped because it is raised by the agent rather than by a plugin, which is
  exactly the distinction day 11 part 3.1 drew.
- `"; ".join(f"{'.'.join(...)}: {error['type']}" ...)` — **field and error type, never the value.**
  `refusal.errors()` carries `input_value`, which on a claim is a fragment of what the model said
  about somebody's loss. Day 11's logging rule applies to exception text too.
- **The comment gives the consequence, not the mechanism**: *one claim's bad answer must not stop the
  morning's queue.* That is the reason the `try` exists, and it is not obvious from the code.
- `if rejected: return {...}` **before the normal return** — the same shape as day 11's over-budget
  check, and placed for the same reason: this is a specific failure and the general branch below
  would report it as a missing reading.

With that in place, the same unreadable description ends the way every other failure does:

```
{"event": "workflow.refused_shape", "claim": "FNOL-9001", "detail": "error: extra_forbidden; loss_type: missing; injury_reported: missing"}
{"event": "desk.classification_failed", "claim": "FNOL-9001", "detail": "refused_shape"}
Verdict(claim_id='FNOL-9001', outcome='pending', reason=None, waiting_for='needs_classification')
```

**Line by line:**

- **Two log lines and a verdict**, and the queue would have carried on to the next notification.
- `"detail": "error: extra_forbidden; loss_type: missing; injury_reported: missing"` — **three
  complaints, by field and type, and not one word of what the model actually said.**
- `"event": "desk.classification_failed", "detail": "refused_shape"` — the desk's own line, carrying
  the constant. A person reading the log can tell this from a claim that ran out of budget.
- `waiting_for='needs_classification'` — **and this is the one thing still worth improving.** The
  desk collapses `refused_shape` into `needs_classification`, so the verdict does not distinguish
  what the log does. It is honest — the claim genuinely is waiting for a classification — and it
  loses a distinction one line earlier in the same file. That is a `TODO(me)` in the hub rather than
  a change made quietly here.

## In production

**What a senior writes instead.** The same catch, with the refused answer written somewhere a person
can look at it — not the log, which day 11 established is the wrong place for a model's words, but
the claim's own record, where it has the claim's retention rules. A schema refusal is the single most
useful artefact for improving a prompt, and this project currently throws it away.

**What degrades at scale.** One refusal in twelve is a claim a person picks up. At a morning's
several hundred notifications, a prompt change that makes the model add a field to every answer turns
into several hundred pending claims and a queue that finishes with nothing decided — because
`extra="forbid"` refuses all of them equally. That is the correct behaviour and it is also a
cliff-edge: the number to watch is refusals as a share of the queue, and a rise means a prompt or a
model changed underneath you.

**The review comment.** *"This catches `ValidationError` around the whole turn. That also catches a
validation error from anything else in there — a tool argument, a state schema. Narrow it, or at
least log what raised, because 'the classifier answered badly' will eventually be the wrong story."*

**The interview question.** *"You add an output schema to an agent that was previously parsing JSON
by hand. Name two things that get better and one new failure mode you have to handle."*
