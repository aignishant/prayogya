## One-line answer

A schema is the set of answers this desk will accept, written down once as a type — so the same
declaration tells the model what to say, tells the framework what to validate, and tells the rules
what they are reading.

## The idea

The list of perils this desk recognises was written down three times.

Once in the classifier's instruction, as a sentence: *the peril slugs are: escape-of-water, fire,
theft, storm, accidental-damage, windscreen.* Once in `PHOTO_REQUIRED_FOR`, as a frozenset of four
of them. And once in `data/policies.json`, spread across eight policies, which is where the list is
actually *true* — a peril is covered when a policy says so.

Three copies of a list is a list that disagrees with itself. Not immediately: on the day somebody
adds subsidence to the policy data and does not add it to the instruction, at which point the
classifier cannot name a peril the desk covers, and the rules refuse the claim as
`peril_not_covered` — a correct refusal for the wrong reason, produced by a system where nothing is
wrong in any one file.

A schema is where that stops. Not because validation is virtuous, but because **a schema is the one
artefact that every party reads**: the model is given it, the framework enforces it, the rules
receive what it produced, and the tests argue with it in milliseconds.

That is the shift worth naming. Up to today, "structure" in this project meant a convention —
day 7's instruction asking for JSON, day 10's `parse_reading` hoping for it. A convention is a
sentence somebody has to obey. **A schema is a value**, and this day is mostly about what becomes
possible once the shape is a thing you can pass around, print, diff and evolve.

## The mechanism

The whole file, at `claims_desk/schemas.py`:

```python
"""The shapes this desk will accept from a model, declared once and enforced by the framework.

Day 7 asked the classifier for JSON in a sentence of prose and hoped. Day 10 moved the parsing into
`workflow.parse_reading`, which caught two ways of being wrong — not an object, missing a field —
and could not catch the third, which is a field that is present, well-typed and **not a thing this
desk recognises**. A model answering `{"loss_type": "water damage", "injury_reported": false}`
has produced valid JSON with both required fields, and `water damage` is not a peril any policy
in `data/policies.json` covers.

A schema is where that is caught. It is declared here rather than in the agent for two reasons: the
same shape is used by the agent, by the rules node and by the tests, and a schema written next to
one caller is a schema the other callers copy.

**Nothing in this file knows about ADK.** These are pydantic models over this project's own domain
enums, so they can be validated in a test with no framework, no runner and no event loop.
"""

from __future__ import annotations

from pydantic import BaseModel, ConfigDict, Field

from claims_desk.domain import Peril

#: What the classifier is allowed to say. Two fields the rules need, one flag the stand-in sets, and
#: nothing else — `extra="forbid"` is what turns an invented field into a refusal rather than a
#: silently dropped one.
#:
#: The peril is typed as the domain's own enum, so the set of acceptable answers is the set of
#: perils this desk's policies are written against. There is exactly one list, in `domain.py`, and
#: this is the file that points a model at it.


class Reading(BaseModel):
    """What one classifier turn is allowed to return.

    `loss_type` is the domain enum, not a string: a model that answers `water damage` is refused
    here rather than three functions later, where the message would be about cover rather than
    about the answer.
    """

    model_config = ConfigDict(extra="forbid", use_enum_values=True)

    loss_type: Peril = Field(description="The peril, exactly one of this desk's slugs.")
    injury_reported: bool = Field(
        description="True only if the description says a person was hurt."
    )
    scripted: bool = Field(
        default=False,
        description="Set by this project's stand-in model. A real provider never sets it.",
    )
```

**Line by line:**

- **The docstring names the failure this file exists for**, and it is specifically the *third* kind:
  not malformed, not incomplete, but confidently wrong in a way no parser can see. Day 10's
  `parse_reading` caught the first two and was blind to this one.
- **"Nothing in this file knows about ADK."** One import from pydantic, one from this project's own
  domain, and no framework anywhere. That is what lets part 3.1's thirteen tests run in about a
  second with no event loop.
- `from claims_desk.domain import Peril` — **the schema points at the domain, never the reverse.**
  The list of perils is a fact about this insurer's policies, not about how a model is prompted.
- `class Reading(BaseModel)` — **named for what it is, not for what produced it.** Not
  `ClassifierOutput`: the rules node reads a `Reading`, the tests build a `Reading`, and one day
  something other than the classifier may produce one.
- `model_config = ConfigDict(extra="forbid", use_enum_values=True)` — **two settings, and both are
  decisions.**
- `extra="forbid"` — **an invented field is a refusal, not a shrug.** Pydantic's default is to drop
  unknown keys silently. A model that starts returning `{"confidence": 0.91}` is telling you
  something about how it was prompted, and dropping it means never finding out. Part 2.1 is where
  this setting turns out to cut both ways.
- `use_enum_values=True` — **the validated object holds `"fire"`, not `Peril.FIRE`.** Day 2's
  `assess` compares `loss_type` against `cover.perils`, which is a set of strings out of the policy
  data. Without this the comparison silently fails on every claim.
- `loss_type: Peril` — **the type is the list.** This one annotation is what makes "the set of
  answers this desk accepts" a thing the model is told, the framework enforces, and a test can
  enumerate.
- `Field(description=...)` **on every field** — and these are not comments. Day 5 established that a
  tool's description is its API; a schema's descriptions are the same thing for an answer, and they
  cross to the provider inside the JSON schema. The mechanism section below prints what actually
  crosses.
- `injury_reported: bool` **with a description that says when it is true** — *"only if the
  description says a person was hurt"*. Day 2's keyword scan called "No one hurt" an injury; this
  sentence is the correction, in the place a model reads.
- `scripted: bool = Field(default=False, ...)` — **the stand-in's announcement survives into the
  schema.** Day 7 made the double announce itself three ways; a schema with `extra="forbid"` would
  have refused the announcement, so the announcement becomes a declared field with a default,
  and its description says what its presence means.

The list it points at, in `claims_desk/domain.py`. A **marked diff against `claims_desk/domain.py` as
printed on day 2 part 2.1, with day 7's `Cover` already in place**:


**Line by line:**

- `class Peril(StrEnum)` — **`StrEnum`, so a member *is* a string.** `Peril.FIRE == "fire"` is true,
  which means every existing comparison in `assess` keeps working and this is an additive change
  rather than a rewrite.
- **Six members, and the order is the order the instruction lists them in** — because part 3.1
  asserts that the instruction and the enum agree, and an assertion on ordered lists is stricter and
  reads better in a failure than one on sets.
- `PHOTO_REQUIRED_FOR = frozenset({Peril.ESCAPE_OF_WATER, ...})` — **the subset names its members
  from the enum.** Retyping the four strings would have worked identically today and would not fail
  the day somebody renames a slug.
- **The comment says what the change buys**: a peril added to the enum and forgotten here is *a
  visible omission* — you can see four of six listed — where a mistyped string is invisible.
- **The docstring is dated and gives the reason.** Somebody who finds a six-member enum in a domain
  file will wonder why it is not just strings; the answer is in the file rather than in a commit
  message.

And the classifier is told the list rather than holding a copy. A **marked diff against
`claims_desk/agents/classifier.py` as printed on day 7 part 1.1, with day 10's `output_key` already

**Line by line:**

- `INSTRUCTION = f"""` — **the prompt becomes an f-string**, which is a small change with one sharp
  edge: every literal brace in it must double. That is the `{{` and `}}` on the JSON example, and
  forgetting it fails at import time rather than at run time, which is the good kind.
- `{', '.join(peril.value for peril in Peril)}` — **the sentence is generated from the enum.** Add
  subsidence to `Peril` and the model is told about it in the same commit, with nothing to remember.
- `output_schema=Reading` — **one keyword, and it changes what `output_key` receives.** Part 1.2 is
  the whole of what that does.
- **The instruction still describes the shape in prose as well.** Belt and braces, and deliberately:
  the schema is what a provider is given as a constraint, and the sentence is what it reads. Day 9
  made the same argument about an instruction restating a prompt.

**Line by line:**

- `"enum": ["escape-of-water", "fire", ...]` — **the six slugs, in the schema, in the enum's order.**
  This is the sentence in the instruction and the type annotation in the model arriving at the
  provider as the same fact.
- `"additionalProperties": false` — **`extra="forbid"`, translated.** Pydantic's setting and JSON
  Schema's keyword are two spellings of one decision, and this is where the first becomes the second.
- `"required": ["loss_type", "injury_reported"]` — **two of three.** `scripted` has a default, so it
  is optional, and part 2.1 is about how much difference that one property makes.
- **Every `description` from the model is here**, including the two-paragraph docstring on `Peril`.
  That is more prose than intended: the enum's docstring is an internal note about why the enum
  exists, and it is now something a provider reads on every call. Worth knowing before writing a long
  docstring on a schema type.
- `"$ref": "#/$defs/Peril"` — **the enum is factored out into `$defs`**, which is what pydantic does
  for any named type. Harmless here, and it is the reason a schema that looks small in Python can
  arrive large.
- `"title": "Injury Reported"` — **pydantic invents titles from field names.** Nobody wrote that, and
  it crosses on every request. A schema is a prompt whether or not it is thought of as one.

## When it breaks

Forget to double a brace in the instruction after making it an f-string:

```
  File "claims_desk/agents/classifier.py", line 36, in <module>
    {"loss_type": "<one of the peril slugs>", "injury_reported": true or false}
ValueError: Invalid format specifier ' "<one of the peril slugs>", "injury_reported": true or false' for object of type 'str'
```

Verbatim, from this project, at **import time** — before any agent is built and before any request
is made. The f-string reads `{"loss_type"` as a format field, then everything after the colon as a
format specifier, and complains about a specifier nobody wrote.

The message is about format specifiers and the mistake is a missing brace, which is the usual
distance between the two. What saves you is the line number: it points straight at the JSON example
in the prompt.

This is the good kind of failure and it is worth saying why. The whole file fails to import, so
nothing runs, so no claim is decided with a half-formatted prompt. Compare it with the version of
this mistake that does not fail: a `.format()` call at run time on a template with a stray brace,
which raises on the one claim whose description happens to reach it.

The smallest fix is `{{` and `}}` on the JSON example. The general point is about where a prompt is
assembled: **an f-string is evaluated once, at import, and a template is evaluated per call.** If a
prompt can be built at import time, build it there, and the failure will be at the start of the
process rather than in the middle of a queue.

## In production

**What a senior writes instead.** The same models, in the same module, with one addition: a version
on the schema itself, because part 2.1's evolution problem needs somewhere to record which shape a
stored answer was written against. What they would push back on is the two-paragraph docstring on
`Peril` — it is a note to maintainers that now travels to a provider on every call, and the fix is
to keep the reasoning in a comment above the class rather than in its docstring.

**What degrades at scale.** One schema with three fields is a few hundred bytes on every request,
which is nothing. Twelve tools each with a schema, plus an output schema, plus the descriptions, is
the majority of a request's fixed cost — and it is paid on every one of a morning's several hundred
notifications, cached only while the prefix does not change. The number that matters is not the
schema's size but how often it changes: day 9's transfer warning made the same point about prompt
prefixes, and a schema is part of the prefix.

**The review comment.** *"`loss_type` is `Peril` now, good — but `Cover.perils` is still
`frozenset[str]` built out of JSON. Those two agree today because a test says so. Type the store's
side as well, or the schema is enforcing a list the policy data is free to disagree with."*

**The interview question.** *"You declare an output schema for a model. Name three different
consumers of that declaration and what each one does with it."*
