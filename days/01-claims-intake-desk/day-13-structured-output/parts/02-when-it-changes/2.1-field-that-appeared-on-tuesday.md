## One-line answer

A schema with a default accepts every answer written before the field existed; the same field
without a default refuses all of them — and `extra="forbid"` means the old reader refuses the new
answer too, so a schema change is two migrations and not one.

## The idea

The correspondence team asks for one more thing on theft claims: the police reference.

It is a small ask. One field, obviously optional — most claims are not theft — and the change to
`Reading` is one line. It goes in on a Tuesday.

Two things happen next, and neither is the thing anybody was thinking about.

**The claims decided before Tuesday.** They are stored, they were validated against the old shape,
and something will read them again — a report, an audit, day 14's decision record. Whether they still
load depends entirely on one word in the new declaration.

**The readers that have not been updated.** The desk is not one process. There is a queue runner and
a boundary, and on any real system there is a reporting job somebody deployed in March. When the
model starts returning a field they do not know about, `extra="forbid"` — the setting part 1.1 chose
deliberately, for good reasons — refuses the answer.

So a schema change is not one migration. It is two, in opposite directions, and they have different
answers:

- **Old data, new reader.** Fixed by a default. The new field is absent from old answers and the
  default fills it.
- **New data, old reader.** Not fixed by anything on the writing side. The old reader has to be
  updated first, or it has to be tolerant — and part 1.1 chose intolerance on purpose.

The order matters and it is counter-intuitive: **readers before writers.** Update everything that
consumes the shape to accept the new field, deploy that, and only then start producing it.

## The mechanism

Three versions of the same model, in `tests/test_schemas.py`, printed whole in part 3.1:

```python
class ReadingWithOptional(BaseModel):
    """Tuesday's version, adding a field the old answers do not have."""

    model_config = ConfigDict(extra="forbid", use_enum_values=True)

    loss_type: Peril
    injury_reported: bool
    scripted: bool = False
    police_reference: str | None = Field(default=None, description="Theft claims only.")


class ReadingWithRequired(BaseModel):
    """The same field, required. One word different and every stored answer is now invalid."""

    model_config = ConfigDict(extra="forbid", use_enum_values=True)

    loss_type: Peril
    injury_reported: bool
    scripted: bool = False
    police_reference: str
```

**Line by line:**

- **These live in the test file, not in `schemas.py`.** They are not shapes this desk uses; they are
  the two candidate futures, kept where they can be argued with. A project that put both in the
  production module would have two models one of which is a comment.
- `police_reference: str | None = Field(default=None, ...)` — **optional twice over.** `| None` says
  the value may be null; `default=None` says the key may be absent. They are different statements and
  a field can have either without the other.
- `police_reference: str` **with no default** — **one word of difference from the line above**, and
  it is the whole of this part. Nothing else in the class changed.
- **Both keep `extra="forbid"`**, because the point being measured is the field, not the setting.

The three cases, run:

```bash
uv run pytest tests/test_schemas.py -q -p no:warnings -k "optional or required or old_reader"
```

```
...                                                                      [100%]
3 passed, 10 deselected in 1.07s
```

**Line by line:**

- **Three passed, ten deselected.** The `-k` expression picks the evolution tests out of a file that
  is mostly about today's shape; the ten left behind are part 3.1's.
- **All three pass, and two of them assert a refusal.** A test that expects `ValidationError` is
  green when the schema refuses, which is worth saying once because "passed" and "accepted" are not
  the same thing anywhere in this file.

And what each of them asserts:

```python
def test_an_optional_new_field_accepts_every_answer_written_before_it_existed() -> None:
    reading = ReadingWithOptional.model_validate(GOOD)
    assert reading.police_reference is None


def test_the_same_field_made_required_refuses_all_of_them() -> None:
    """The only change is the default. Every claim decided before Tuesday now fails to load."""
    with pytest.raises(ValidationError) as refused:
        ReadingWithRequired.model_validate(GOOD)
    assert refused.value.errors()[0]["loc"] == ("police_reference",)


def test_an_old_reader_refuses_a_new_answer_because_extra_is_forbidden() -> None:
    """The direction people forget. `extra="forbid"` cuts both ways: today's reader, tomorrow's
    answer, and the field that was added to help."""
    tomorrow = {**GOOD, "police_reference": "CR/2026/118"}
    with pytest.raises(ValidationError) as refused:
        Reading.model_validate(tomorrow)
    assert refused.value.errors()[0]["type"] == "extra_forbidden"
    assert ReadingWithOptional.model_validate(tomorrow).police_reference == "CR/2026/118"
```

**Line by line:**

- `GOOD = {"loss_type": "escape-of-water", "injury_reported": False}` — **one fixture standing for
  every answer written before Tuesday.** Two fields, exactly what the old shape required.
- `assert reading.police_reference is None` — **the default did its job.** Old data loads under the
  new shape and the absent field reads as absent, which is a fact the reader can act on.
- `assert refused.value.errors()[0]["loc"] == ("police_reference",)` — **the required version refuses
  the same object**, and the error names the field. Every claim in the store, unreadable, from one
  word.
- **The test name says the scope**: *refuses all of them*. Not "refuses an old answer" — all of them,
  because the field is absent from every answer written before it existed.
- `tomorrow = {**GOOD, "police_reference": "CR/2026/118"}` — **an answer from after the change**, fed
  to the shape that is still deployed.
- `assert refused.value.errors()[0]["type"] == "extra_forbidden"` — **the old reader refuses it.**
  This is the direction that surprises people: nothing is wrong with the answer, the field was added
  on purpose to help, and a reader that has not been redeployed rejects the claim.
- **The last line is the same object through the new shape**, accepted, with the reference intact.
  One object, two readers, opposite outcomes — which is what "deploy readers first" means in a test.

## When it breaks

The failure is the ordinary way this is done: add the field to the model, deploy the writer, and
update the readers next week.

```
1 validation error for Reading
police_reference
  Extra inputs are not permitted [type=extra_forbidden, input_value='CR/2026/118', input_type=str]
    For further information visit https://errors.pydantic.dev/2.13/v/extra_forbidden
```

Verbatim, from this project. Every theft claim, from the moment the writer ships, refused by
whatever has not been updated — and by part 1.2's catch, every one of them becomes a claim pending
for `refused_shape`.

There are three responses and only one of them is right.

**Loosen the reader to `extra="ignore"`.** Tempting, and it throws away the setting that made part
1.2's failure visible: the day a model starts inventing a `confidence` field, nobody finds out. This
is trading a known migration cost for an unknown silent one.

**Make the field required on the writer so it is always present.** Does nothing about the reader,
which refuses it either way, and now the old data will not load either. Both directions broken at
once.

**Deploy the readers first.** Add the optional field to every consumer of the shape, ship that, then
start producing it. Boring, requires knowing what all the consumers are, and is the reason a schema
should live in one module that everything imports rather than being copied into each service.

That last point is the one to carry: **the migration cost of a schema is proportional to how many
copies of it exist.** Part 1.1 put `Reading` in one file for reasons that sounded like tidiness;
this is the reason that actually pays.

And one honest limit. This project has exactly one process and one reader, so the second migration
costs nothing here and the tests above are the only place it is visible at all. That is why they are
written: a failure a project cannot experience yet is a failure a project can still be shown.

## In production

**What a senior writes instead.** The same model with a version on it — a `schema_version` field, or
the shape's version in the stored record — so a reader can tell which shape an answer was written
against instead of inferring it from which fields are present. What they would insist on before any
of that is knowing **who reads this shape**, written down, because "deploy readers first" is not
actionable without that list.

**What degrades at scale.** One field on one model with one reader is a five-minute change. The same
change with four services, a reporting job and two years of stored claims is a project, and the
part that costs is not the code — it is that a hundred thousand stored answers were written against
three different versions of the shape and nothing records which. At that point the only safe reader
is a tolerant one, which is how systems end up with `extra="ignore"` everywhere and no idea what
their models are actually returning.

**The review comment.** *"This adds `police_reference` as required because 'we always send it now'.
The claim files from before this week do not have it, and day 14's decision record reads them. Make
it optional, or write the migration that backfills them — but say which."*

**The interview question.** *"You need to add a field to a schema that a model produces and three
services consume. What order do you deploy in, and what breaks if you get it backwards?"*
