## One-line answer

The three numbers `PROJECT.md` promised on day 0 — twelve notifications, four fast-tracked, eight
deficiencies with eight distinct reasons — become ten assertions, and the fixture set stops being a
pile of examples and becomes a contract.

## The idea

The branch manager's weekly figure is not "we processed some claims". It is: *ninety-one
notifications, thirty-four settled on the fast track, fifty-seven letters out.* Three numbers, and
the reason they are said out loud every week is that they are the only version of the desk's
behaviour that somebody can disagree with. "The desk is working well" cannot be contradicted;
"thirty-four" can.

Day 0 wrote three numbers into `PROJECT.md`: twelve notifications, four fast-tracked, eight
deficiency letters each naming a real missing field. That was a promise made before a line of code
existed. This part is where it becomes something that can fail.

Two of the assertions here are more interesting than the rest, and both are about what a fixture
set is *for*.

The first is that the eight deficiency reasons must be **eight different reasons**. A fixture set
with eight missing dates would satisfy "eight deficiencies" and would test one rule eight times.
The assertion that makes the set worth having is the one about variety.

The second is that the declared answers and the rules must agree — every one of the twelve, decided
by `assess`, matching what was written by hand in the file. That test can fail in two directions,
and both are useful: the code can be wrong, or the fixture can be. On the day this project was
built it failed for the second reason, and part 3.2 is what it found.

## The mechanism

The whole file, at `tests/test_domain.py`:

```python
"""The fixture set, asserted as a contract.

`PROJECT.md` says this desk is done when a cold clone processes twelve notifications, fast-tracks
the four that qualify and writes eight deficiency letters that each name a real missing field.
Those numbers are a promise, and this file is where the promise becomes a thing that can go red.

Nothing here runs a model. Every assertion is about the fixtures and the rules that read them.
"""

from __future__ import annotations

import json

import pytest

from claims_desk.domain import (
    Outcome,
    Reason,
    assess,
    mentions_injury_keyword_scan,
)
from claims_desk.store import Store


@pytest.fixture
def store() -> Store:
    return Store()


def test_the_queue_is_twelve_notifications(store: Store) -> None:
    assert len(list(store.notifications())) == 12


def test_four_qualify_and_eight_do_not(store: Store) -> None:
    expected = store.expectations()
    outcomes = [entry["outcome"] for entry in expected.values()]
    assert outcomes.count(Outcome.FAST_TRACK) == 4
    assert outcomes.count(Outcome.DEFICIENCY) == 8


def test_every_deficiency_names_a_reason_the_desk_can_produce(store: Store) -> None:
    reasons = [
        entry["reason"]
        for entry in store.expectations().values()
        if entry["outcome"] == Outcome.DEFICIENCY
    ]
    assert len(reasons) == len(set(reasons)), "each deficiency exercises a different rule"
    assert len(set(reasons)) == 8
    for reason in reasons:
        assert reason in set(Reason), f"{reason} is not a Reason this desk can name"


def test_every_fast_track_has_no_reason(store: Store) -> None:
    for entry in store.expectations().values():
        if entry["outcome"] == Outcome.FAST_TRACK:
            assert entry["reason"] is None


def test_the_rules_reproduce_every_declared_outcome(store: Store) -> None:
    """The whole fixture set, decided by `assess`, compared with what was declared by hand.

    The loss type and the injury flag are taken from the expectation rather than derived: reading
    a sentence is the model's job from day 7, and this test is about the rules.
    """
    expected = store.expectations()
    for notification in store.notifications():
        declared = expected[notification.id]
        policy = store.policy(notification.policy_number)
        outcome, reason = assess(
            notification, policy, declared["loss_type"], declared["injury"]
        )
        assert outcome == declared["outcome"], notification.id
        assert (reason.value if reason else None) == declared["reason"], notification.id


def test_the_keyword_scan_is_still_wrong_about_a_real_notification(store: Store) -> None:
    """An inverted case: it asserts that the stand-in fails, so nobody promotes it to a decision.

    FNOL-4471 ends "No one hurt." The scan sees the word and says injury; the declared truth says
    no injury. If this test ever goes red, either the fixture changed or somebody taught the scan
    to read English — and the second one is day 7's job, with a model, not a longer word list.
    """
    declared = store.expectations()
    notifications = {n.id: n for n in store.notifications()}
    wrong = [
        n.id
        for n in notifications.values()
        if mentions_injury_keyword_scan(n.description) != declared[n.id]["injury"]
    ]
    assert "FNOL-4471" in wrong


def test_a_lapsed_policy_is_not_in_force_even_inside_its_dates(store: Store) -> None:
    lapsed = store.policy("SYN-POL-1003")
    assert lapsed is not None
    from datetime import date

    assert lapsed.inception <= date(2024, 9, 1) <= lapsed.expiry
    assert not lapsed.in_force_on(date(2024, 9, 1))


def test_an_unknown_policy_number_is_none_rather_than_an_error(store: Store) -> None:
    assert store.policy("SYN-POL-9999") is None


def test_every_fixture_says_it_is_synthetic(store: Store) -> None:
    for name in ("policies.json", "notifications.json"):
        document = json.loads((store.data / name).read_text(encoding="utf-8"))
        assert "_synthetic" in document
        assert "invented" in document["_synthetic"]


def test_a_claim_file_is_replaced_in_one_step(store: Store, tmp_path) -> None:
    scratch = Store(tmp_path)
    scratch.write_claim("FNOL-4471", {"outcome": "fast-track", "version": 1})
    scratch.write_claim("FNOL-4471", {"outcome": "fast-track", "version": 2})
    assert scratch.claim("FNOL-4471") == {"outcome": "fast-track", "version": 2}
    leftovers = list((tmp_path / "claims").glob(".*tmp"))
    assert leftovers == [], "the temporary file is moved, never left behind"
```

**Line by line:**

- `@pytest.fixture def store() -> Store:` — a fresh `Store` per test. It is one line and it earns
  its place by naming the thing: every test below takes `store` as an argument, so a reader can see
  at a glance which tests touch data.
- `test_the_queue_is_twelve_notifications` — the first number from `PROJECT.md`. `len(list(...))`
  because `notifications()` yields; forcing the generator is also what proves every one of the
  twelve parses without raising.
- `test_four_qualify_and_eight_do_not` — the other two numbers, counted off the **declared**
  outcomes rather than off the rules. This test is about the fixture set: it says the queue is
  two-thirds deficient by design, which is a statement about what this desk is for.
- `outcomes.count(Outcome.FAST_TRACK)` — comparing an enumeration member with the strings in the
  file works because `Outcome` is a `StrEnum`. That is the payoff for the choice in part 2.1, and
  it is why no conversion appears anywhere in this file.
- `test_every_deficiency_names_a_reason_the_desk_can_produce` — **the variety assertion**, and it
  takes two lines rather than one for a reason worth dwelling on. `len(set(reasons)) == 8` alone
  looks sufficient and is not: add a thirteenth notification duplicating an existing reason and
  there are nine deficiencies with eight distinct reasons, which satisfies it perfectly. The first
  version of this file made exactly that mistake, and it was found by adding the thirteenth
  notification and watching the test pass.
- `assert len(reasons) == len(set(reasons))` — **the duplicate check**: as many reasons as distinct
  reasons. This is the one that catches a copied fixture.
- `assert len(set(reasons)) == 8` — and then the count, so the set is the eight the desk can
  produce rather than some other eight.
- The message `"each deficiency exercises a different rule"` is the reason for the rule, not a
  restatement of it. When this fails, whoever added the thirteenth notification reads the sentence
  that explains what they broke.
- `assert reason in set(Reason)` — every declared reason is one the code can actually produce.
  `set(Reason)` works because a `StrEnum` is iterable and its members compare equal to their
  strings, so this catches a typo in the fixture — `missing_photo_ref` instead of
  `missing_photo_reference` — which would otherwise sit there looking plausible.
- `test_every_fast_track_has_no_reason` — the other half of the shape: a fast-track with a reason
  attached is a contradiction, and it is the kind that gets copied when somebody duplicates a
  fixture entry to add a thirteenth.
- `test_the_rules_reproduce_every_declared_outcome` — **the central test of the day.** Twelve
  notifications, decided by `assess`, compared against what a person wrote by hand.
- `assert outcome == declared["outcome"], notification.id` — **the id as the assertion message.**
  Without it a failure says `assert <Outcome.DEFICIENCY> == 'fast-track'` and you do not know which
  of twelve it was. With it, the first line of the failure is `FNOL-4471`.
- `declared["loss_type"], declared["injury"]` — the two facts that require reading English, taken
  from the answer key. This is the test being honest about its own scope: it tests the rules, not
  the classifier, and day 7 is where the classifier gets tested against these same fields.
- `test_the_keyword_scan_is_still_wrong_about_a_real_notification` — **an inverted case**: an eval
  or test whose declared expectation is its own subject's failure, so it goes red when the thing it
  depends on stops being broken. It exists because the scan is a stand-in, and a stand-in that
  quietly starts looking adequate is one somebody will use.
- `wrong = [n.id for n in notifications.values() if scan(...) != declared[...]["injury"]]` — build
  the list of disagreements, then assert `FNOL-4471` is in it. Asserting on the specific
  notification rather than on `len(wrong) > 0` means the test still means something after somebody
  adds a thirteenth notification the scan also gets wrong.
- `test_a_lapsed_policy_is_not_in_force_even_inside_its_dates` — the conjunction from part 2.1,
  tested where it is easy to get wrong. The first assertion establishes that the date **is** inside
  the period; the second establishes that the answer is still no. One without the other proves
  nothing.
- `from datetime import date` **inside the function** — deliberately local, because it is used by
  one test and the import block above is about this project's own modules. Ruff's `I` rules do not
  object to a local import, and a reader gets the type next to its use.
- `test_an_unknown_policy_number_is_none_rather_than_an_error` — the read contract from part 2.2,
  asserted rather than described. `is None`, not `== None`, because identity is what the contract
  says.
- `test_every_fixture_says_it_is_synthetic` — **the `_synthetic` marker, enforced.** A convention
  nobody checks is a convention that lasts until the first hurried pull request. Two assertions:
  the key exists, and it contains the word `invented`, so an empty string does not pass.
- `test_a_claim_file_is_replaced_in_one_step(store, tmp_path)` — `tmp_path` is pytest's per-test
  temporary directory, and `Store(tmp_path)` is the parameter from part 2.2 earning its place: the
  test writes real files, exercises the real `os.replace`, and touches nothing in the project.
- `leftovers = list((tmp_path / "claims").glob(".*tmp"))` and `assert leftovers == []` — **the
  temporary file is gone.** This is the assertion that catches a cleanup which only runs on the
  happy path, and it is written as a glob rather than a count so the failure message names the file
  that was left behind.

Run just this file:

- **Ten dots.** Ten assertions about a fixture set and the rules that read it, none of which

## When it breaks

Add a thirteenth notification by copying the twelfth and changing its id, and the variety assertion
catches the duplicate reason:

Verbatim, from this project. `9 == 8` is nine deficiencies carrying eight distinct reasons, and
pytest prints both the list and the set so you can see which one repeats. Somebody adding a case to
"improve coverage" has added a row that cannot fail on its own. The smallest fix is to give the new
notification a reason nothing else exercises — or, if there isn't one, to accept that this fixture
set is complete and add the case to day 18's evalset instead, where breadth rather than coverage is
the point.

**This failure is also how the assertion above got its second line.** The first version asserted
only `len(set(reasons)) == 8`, the thirteenth notification was added to demonstrate the failure,
and the test passed — nine deficiencies, eight distinct reasons, exactly the condition it was
supposed to catch. A test that cannot go red for the reason you wrote it is worth finding out about
on the day you write it.

## In production

**What a senior writes instead.** The same assertions, plus a property test that generates
notifications and checks invariants rather than outcomes — every result is either a fast-track with
no reason or a deficiency with exactly one, no matter what the fields are. The hand-written twelve
stay, because they are the cases somebody chose; the generated ones catch the combinations nobody
thought about. What a senior would not accept is a test file that only counts: **counting twelve
proves the file loaded**, and only the comparison against declared answers proves anything about
behaviour.

**What degrades at scale.** Twelve cases with hand-written expectations is a set one person can
hold in their head. A real claims desk's regression set runs to thousands, at which point nobody
reads the fixtures and the answer key becomes the only description of the system that anybody
trusts — so the day somebody regenerates it from the current behaviour, every historical decision
quietly becomes "correct". The defence is procedural rather than technical, and it is the sentence
in `data/notifications.json`: the expected block **is never produced by a model**, or by the code
under test.

**The review comment.** *"This test asserts `len(deficiencies) == 8`. Assert the eight reasons are
distinct as well — otherwise the day somebody copies a fixture to make a number go up, we lose a
rule's only test and nothing goes red."*

**The interview question.** *"Your fixture set has twelve cases and your system passes all twelve.
What does that actually tell you, and what would you add to make it tell you more?"*
