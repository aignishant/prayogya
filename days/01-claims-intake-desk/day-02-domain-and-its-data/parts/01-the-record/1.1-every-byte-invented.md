## One-line answer

The policy store is eight invented policies in a file that says so in its first line, and the
fields it carries are chosen by one test: does the desk have to read this to decide a claim?

## The idea

Pick up the phone at an intake desk and the first thing you ask for is a policy number. Not because
the number is interesting, but because everything the caller is about to tell you means something
different depending on what is behind it. The same sentence — *water everywhere in the kitchen* —
is a fast-tracked claim on one policy and a letter explaining that escape of water is not covered
on another.

So before the desk can hear a single call, it needs the thing it looks numbers up in.

Two decisions to make deliberately, because both get made by accident otherwise.

The first is **what the record holds.** A real insurer's policy record has hundreds of fields:
premium history, payment method, marketing preferences, the broker who sold it, endorsements,
schedules. Almost none of that decides a first-notice-of-loss. The test for this project is narrow
and worth saying out loud: **a field earns its place if some rule in this desk reads it.** Eight
fields survive that test, and the discipline of applying it is why day 3 has a boundary worth
defending rather than a shapeless bag of data.

The second is **where the data comes from**, and this project's answer is absolute: **all data is
synthetic, always.** Every policy number, address and amount below is invented. There is no
anonymised extract, no scrubbed sample, no "it's only test data". The reason is not squeamishness.
A claims system is built by running it over and over against its fixtures — printing them,
committing them, pasting them into documents like this one — and the *only* version of that which
is safe is the one where there was never anything real to leak. A file that says so in its own
first line is a file nobody has to ask about.

**Line by line:**

- `"_synthetic": "Every policy in this file is invented…"` — **the first key in the file**, before
  the data, so it is the first thing a reader or a reviewer sees. The leading underscore marks it
  as metadata rather than a record. A test in part 3.1 asserts it is present, which turns a
  convention into something that can go red.
- `"policies": [ … ]` — the records under a named key rather than at the top level. A bare JSON
  array cannot grow a sibling; this file can gain a `"revision"` or a `"_source"` without every
  reader changing.
- `"number": "SYN-POL-1001"` — the key everything else joins on, and the `SYN-` prefix is doing
  work: a policy number that turns up in a log, a letter or a screenshot announces itself as
  synthetic without anybody having to explain.
- `"holder_ref": "H-2201"` — **a reference, not a name.** The desk never needs to know who the
  policyholder is in order to decide whether the policy was in force, so it does not hold a name at
  all. That is the narrow-fields test applied to the field most people would add without thinking,
  and it removes an entire category of accident.
- `"risk_address"` — invented streets in invented towns. Kept because the address is what
  distinguishes two policies to a human reading a claim file, and because day 12's retrieval needs
  something with words in it.
- `"product": "home-contents"` — three products across the eight policies: contents, buildings and
  private motor. Enough that the fixture set has real variety, few enough that every one of them
  can be reasoned about.
- `"inception"` and `"expiry"`, as ISO dates — the period the policy was on risk. Two fields
  rather than one duration, because the question the desk asks is "was it on risk on this
  particular day", and that is a comparison against both ends.
- `"status": "active"` — and the store deliberately contains one `lapsed` (SYN-POL-1003) and one
  `cancelled` (SYN-POL-1007). **Status and dates are separate checks that both have to pass**: a
  cancelled policy can sit happily inside its own inception and expiry, and part 2.1 is where that
  becomes a rule.
- `"excess": 150` — what the policyholder pays before the insurer does. It does not decide
  fast-tracking, and it is here because a fast-track confirmation letter has to state it, which is
  day 6's business. A field that is only ever printed still has to be stored.
- `"fast_track_limit": 2500` — **per policy, not global.** SYN-POL-1004, the motor policy, carries
  1500. A limit that lives on the policy is one the desk reads; a limit that lives in the code is
  one somebody has to redeploy to change, and insurers change these at renewal.
- `"perils": [...]` — the list of things this policy covers, as a JSON array of short slugs.
  SYN-POL-1008 covers `fire`, `theft` and `storm` and **not** escape of water, which is what makes
  one of the twelve notifications a deficiency rather than a claim. Slugs rather than prose because
  a peril is compared, not read.
- **Eight policies, and one of them is never claimed on.** SYN-POL-1007 exists so the store is not
  a set of exactly the records the queue needs. A fixture where every row is used is a fixture that
  quietly tests lookup by iteration order.

## When it breaks

The fields are ISO date strings in a JSON file, and JSON has no dates. Ask Python to compare two of
them as they arrive and it will happily do the wrong thing:

This is SYN-POL-1001's period, and the date of loss on the first notification in the queue, asked
twice — once with the leading zero on the month and once without:

```bash
uv run python -c "
print('2025-11-01' <= '2026-3-14' <= '2026-10-31')
print('2025-11-01' <= '2026-03-14' <= '2026-10-31')
"
```

```
False
True
```

A policy that was plainly on risk in March is reported as not in force, because as **text**
`2026-3-14` sorts after `2026-10-31`: the comparison never reaches the day, it stops at `3` against
`1`. Somebody hand-edited a fixture, dropped one zero, and produced a deficiency letter for a
covered claim — with no error anywhere, because comparing two strings is a perfectly legal thing to
do. The smallest fix is the one part 2.1 makes: parse every date into a `date` object at the edge,
once, so the comparison is between dates and a malformed one raises instead of sorting.

## In production

**What a senior writes instead.** The policy store is a database and the record is a schema, with
the dates as real date columns so the comparison cannot be done wrong. JSON files are the right
call here for one reason: this project needs its fixtures to be **printable, reviewable and
committed**, so that a change to the data is a diff somebody can read. What a senior would keep
from this file is the `_synthetic` marker and the narrow-fields test; what they would not keep is
the linear scan in part 2.2.

**What degrades at scale.** Eight policies scanned per lookup is nothing. A real intake desk sits
in front of a book of several hundred thousand policies, and the same `for policy in
self.policies()` reads and parses the entire store on every single notification — twelve
notifications is twelve full passes. The fix is not more clever code in this file; it is the
boundary on day 3, which is where the store stops being a file everyone can open and becomes a
process that answers questions.

**The review comment.** *"This fixture has a real-looking postcode in it. Change it, and add the
`_synthetic` line — the fixtures in this repository get pasted into documentation and CI logs, and
the only test data that is safe to paste is data that was never real."*

**The interview question.** *"How do you decide which fields belong in a domain record? Give me a
test you can apply to a field, and a field you have seen carried for years that would fail it."*
