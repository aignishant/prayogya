## One-line answer

Two frozen records, two enumerations and one function that decides a notification from four facts —
and the order of its eight checks is the design, because the first rule that fails is the one the
letter names.

## The idea

A supervisor listens to a new starter working the phones and stops them after the third call.
*"You asked for the policy number, then the date, then whether anyone was hurt, then you went back
and asked what day it was again."* The complaint is not about the questions. Every one of them was
right. It is about the order — and the order matters because the caller only stays on the line
once.

The desk's rules have the same property. Eight things can make a notification something other than
a fast-track, and a naive implementation checks all eight and reports whatever it finds. That
produces a letter saying *your date of loss is missing, your policy may not have been in force, and
a photograph is required* — three requests, one of which is a guess, because you cannot tell
whether a policy was in force on a date you do not have.

So this module does two things. It turns the JSON of the previous two parts into types that cannot
be misread, and it decides one notification with the checks in a deliberate order, returning **one**
reason.

Three terms:

- A **domain record** is a type whose fields are the facts the business reasons about — as against
  a row, which is how they happen to be stored. The store's `"2026-03-14"` becomes a `date` here,
  once, at the edge.
- **Frozen** means the object cannot be changed after it is made. A policy is something this desk
  reads; a desk that could quietly edit one has a much larger problem than a bug.
- A **stand-in** is code that occupies the place of the real thing so its absence is visible. This
  module contains exactly one, it is named for what it is, and nothing decides anything with it.

## The mechanism

The whole file, at `claims_desk/domain.py`:

```python
"""The two records this desk works with, and the rules that decide between them.

A notification arrives; a policy either backs it or does not; the desk fast-tracks the claim or
writes a deficiency letter naming exactly what is missing. Everything in this module is decided by
reading fields — no model, no network, no guessing. The model's job, from day 7, is to turn free
text into the one field this module cannot read off the form: the loss type.
"""

from __future__ import annotations

from dataclasses import dataclass
from datetime import date
from enum import StrEnum

#: The perils for which a photograph is part of a complete notification. Theft has nothing left to
#: photograph and a windscreen is inspected by the fitter, so neither is on the list.
PHOTO_REQUIRED_FOR = frozenset({"escape-of-water", "fire", "storm", "accidental-damage"})


class Outcome(StrEnum):
    """What the desk decides about one notification."""

    FAST_TRACK = "fast-track"
    DEFICIENCY = "deficiency"


class Reason(StrEnum):
    """Why a notification could not be fast-tracked.

    One value per way a notification can be incomplete or ineligible. A deficiency letter names
    exactly one of these, because a letter that lists five possible problems is a letter that
    makes the policyholder guess which one to fix first.
    """

    MISSING_DATE_OF_LOSS = "missing_date_of_loss"
    MISSING_CONTACT = "missing_contact"
    UNKNOWN_POLICY = "unknown_policy"
    POLICY_NOT_IN_FORCE = "policy_not_in_force"
    PERIL_NOT_COVERED = "peril_not_covered"
    MISSING_PHOTO_REFERENCE = "missing_photo_reference"
    INJURY_REPORTED = "injury_reported"
    ABOVE_FAST_TRACK_LIMIT = "above_fast_track_limit"


@dataclass(frozen=True)
class Policy:
    """One policy, as the store holds it. Frozen: a policy is read, never edited by this desk."""

    number: str
    holder_ref: str
    risk_address: str
    product: str
    inception: date
    expiry: date
    status: str
    excess: int
    fast_track_limit: int
    perils: frozenset[str]

    @classmethod
    def from_record(cls, record: dict) -> Policy:
        """Build a Policy from one entry of `data/policies.json`."""
        return cls(
            number=record["number"],
            holder_ref=record["holder_ref"],
            risk_address=record["risk_address"],
            product=record["product"],
            inception=date.fromisoformat(record["inception"]),
            expiry=date.fromisoformat(record["expiry"]),
            status=record["status"],
            excess=int(record["excess"]),
            fast_track_limit=int(record["fast_track_limit"]),
            perils=frozenset(record["perils"]),
        )

    def in_force_on(self, day: date) -> bool:
        """Was this policy on risk on `day`?

        Both halves are required: an `active` policy is not on risk before its inception or after
        its expiry, and a policy whose dates contain the day is worth nothing if it was cancelled.
        """
        return self.status == "active" and self.inception <= day <= self.expiry


@dataclass(frozen=True)
class Notification:
    """One first notice of loss, exactly as it was taken down.

    `date_of_loss`, `photo_ref` and `contact_ref` are optional **because a real call is**. The
    desk's job is to notice which of them is absent and say so; a record type that refused to hold
    an incomplete notification would move the failure to the moment of taking the call, which is
    the one moment nothing can be done about it.
    """

    id: str
    policy_number: str
    description: str
    estimate: int
    date_of_loss: date | None = None
    photo_ref: str | None = None
    contact_ref: str | None = None

    @classmethod
    def from_record(cls, record: dict) -> Notification:
        """Build a Notification from one entry of `data/notifications.json`.

        The `expected` block is deliberately not read here: it is this project's declared correct
        answer, used by tests and evals, and the desk must never see it.
        """
        loss_day = record.get("date_of_loss")
        return cls(
            id=record["id"],
            policy_number=record["policy_number"],
            description=record["description"],
            estimate=int(record["estimate"]),
            date_of_loss=date.fromisoformat(loss_day) if loss_day else None,
            photo_ref=record.get("photo_ref"),
            contact_ref=record.get("contact_ref"),
        )


def assess(
    notification: Notification,
    policy: Policy | None,
    loss_type: str,
    injury_reported: bool,
) -> tuple[Outcome, Reason | None]:
    """Decide one notification from four facts, and read no English while doing it.

    `loss_type` and `injury_reported` are **given**, not derived. Both of them require reading a
    sentence a person spoke, which is the one thing this module refuses to guess at: day 7 puts a
    model behind them. Everything else here is a field comparison.

    The order of the checks is the whole design. Missing fields come first, because a policy check
    against an absent date of loss is not a stricter test — it is a meaningless one. Cover comes
    before money, because "you are not covered for this" and "this is too large to fast-track" are
    different letters. The first rule that fails is the one the letter names.
    """
    if notification.date_of_loss is None:
        return Outcome.DEFICIENCY, Reason.MISSING_DATE_OF_LOSS
    if not notification.contact_ref:
        return Outcome.DEFICIENCY, Reason.MISSING_CONTACT
    if policy is None:
        return Outcome.DEFICIENCY, Reason.UNKNOWN_POLICY
    if not policy.in_force_on(notification.date_of_loss):
        return Outcome.DEFICIENCY, Reason.POLICY_NOT_IN_FORCE
    if loss_type not in policy.perils:
        return Outcome.DEFICIENCY, Reason.PERIL_NOT_COVERED
    if loss_type in PHOTO_REQUIRED_FOR and not notification.photo_ref:
        return Outcome.DEFICIENCY, Reason.MISSING_PHOTO_REFERENCE
    if injury_reported:
        return Outcome.DEFICIENCY, Reason.INJURY_REPORTED
    if notification.estimate > policy.fast_track_limit:
        return Outcome.DEFICIENCY, Reason.ABOVE_FAST_TRACK_LIMIT
    return Outcome.FAST_TRACK, None


#: Words that appear near an injury. Not a classifier and not used by `assess`.
INJURY_WORDS = ("hurt", "injur", "hospital", "ambulance", "walk-in centre")


def mentions_injury_keyword_scan(description: str) -> bool:
    """A STAND-IN for reading the sentence, kept so its failure can be demonstrated.

    Nothing in this desk decides anything with it. It scans for words that appear near an injury,
    which means it cannot tell "the caller's shoulder was hurt" from "no one hurt" — and one of
    this project's own twelve notifications says exactly the second thing. Day 7 replaces it with
    a model that reads the sentence; `tests/test_domain.py` asserts that it is still wrong, so
    that nobody quietly promotes it to a decision.
    """
    lowered = description.lower()
    return any(word in lowered for word in INJURY_WORDS)
```

**Line by line:**

- `from enum import StrEnum` — an enumeration whose members **are** strings, so `Outcome.FAST_TRACK
  == "fast-track"` is true and the value can be written straight into JSON without a conversion. It
  is the right choice exactly when a value crosses a boundary into text, which every one of these
  does: into a claim file, into a log line, into an evalset.
- `PHOTO_REQUIRED_FOR = frozenset({...})` — module level, so the rule is visible without reading
  the function, and `frozenset` so nothing can extend it at run time. Its comment says why theft
  and windscreen are absent, which is the kind of decision that looks arbitrary in six months.
- `class Outcome(StrEnum)` with two members — the desk's whole output space. Two, not three: there
  is no "maybe" and no "refer", because a first-notice-of-loss desk that can produce a third
  outcome has a third process behind it and this project does not.
- `class Reason(StrEnum)` with **eight members, one per way to fail** — and the docstring carries
  the rule that makes them worth enumerating: a letter names exactly one. The eight are the eight
  in the fixture set, so a rule and a test case exist in pairs.
- `MISSING_DATE_OF_LOSS = "missing_date_of_loss"` — the member name is Python's convention and the
  value is what is written to a file. Keeping them in step by hand is fine at eight; the alternative
  is a lookup table nobody reads.
- `@dataclass(frozen=True)` on `Policy` — **immutability as a statement about ownership.** This
  desk reads policies; underwriting writes them. `frozen=True` makes the wrong thing an error at
  the moment it is attempted rather than a surprise in a claim file later, and it makes the object
  hashable, which the store will want.
- `inception: date` and `expiry: date` — **the types are `date`, not `str`.** This is the fix for
  the failure in part 1.1: text that looks like a date sorts like text, and one missing zero
  silently reverses a comparison. From here inward, nothing in this project compares date strings.
- `perils: frozenset[str]` — a set, because the only question ever asked of it is membership, and
  frozen because the `Policy` is frozen and a mutable field inside an immutable object is a lie.
- `@classmethod def from_record(cls, record: dict) -> Policy` — the parsing lives on the type, so
  there is exactly one place where the file's shape is known. Anything else that wants a `Policy`
  gets one from here, and the day the store becomes a boundary call rather than a file, this method
  is the only thing that changes.
- `date.fromisoformat(record["inception"])` — **and it raises on a malformed date.** That is the
  point. `2026-3-14` gets a `ValueError` here, at the edge, naming the field, instead of quietly
  sorting wrong eight lines later.
- `int(record["excess"])` — an explicit `int`, because JSON will hand you a float if somebody typed
  `150.0`, and money in this desk is whole units.
- `def in_force_on(self, day: date) -> bool` — **a method on the policy, not a function in the
  rules.** "Was this on risk" is a question about a policy; putting it here means the rule is found
  by anybody reading the type, and it can be tested without constructing a notification.
- `return self.status == "active" and self.inception <= day <= self.expiry` — **two conditions,
  both required.** A cancelled policy sits inside its own dates, and this project's store contains
  exactly that case (SYN-POL-1007) so the conjunction is exercised rather than assumed. The chained
  comparison is one expression because that is how the question is asked in English.
- `class Notification` with **four required fields and three optional ones** — id, policy number,
  description and estimate always exist; the date of loss, the photograph and the contact may not.
  That split is the domain, written down: it says which parts of a call are always taken and which
  are what the desk chases.
- The `Notification` docstring: *"a record type that refused to hold an incomplete notification
  would move the failure to the moment of taking the call"* — the reasoning behind the optionals,
  kept next to them, because the instinct of anybody reading this later will be to make them
  required.
- `date.fromisoformat(loss_day) if loss_day else None` — `None` for a missing date, and note it
  handles both an absent key and a JSON `null`, since `record.get` returns `None` for the first and
  `None` is falsy for the second.
- **"The `expected` block is deliberately not read here"** — the answer key is in the same file as
  the questions and this constructor walks past it. One line of docstring, and it is the line that
  keeps the fixture honest.
- `def assess(notification, policy, loss_type, injury_reported)` — four parameters, and the last
  two are the ones worth arguing about. **They are given rather than derived**, because both
  require reading a sentence, and this module's promise is that it reads no English. Day 7 puts a
  model behind them; until then the tests supply them from the answer key.
- `policy: Policy | None` — the policy may be absent, and the type says so, so the `None` case
  cannot be forgotten. That is `UNKNOWN_POLICY`, and it is a letter rather than an exception.
- `if notification.date_of_loss is None:` **first** — nothing downstream is meaningful without it.
  `in_force_on` cannot be asked, and asking it anyway is how you get a letter that says a policy
  was not in force on a date the insurer never had.
- `if not notification.contact_ref:` **second** — a letter that cannot be delivered is not a
  letter. Both of the first two checks are about the notification alone, and neither of them needs
  the store, so they are also the two that would still work if the policy lookup were down.
- `if policy is None:` third, `if not policy.in_force_on(...)` fourth — **existence before
  validity.** "We cannot find that policy number" and "that policy had lapsed" are different
  conversations with the caller.
- `if loss_type not in policy.perils:` fifth — cover before everything that follows, because there
  is no point asking for a photograph of a loss this policy was never going to pay for.
- `if loss_type in PHOTO_REQUIRED_FOR and not notification.photo_ref:` sixth — the compound
  condition is the rule from part 1.1: a photograph is required for some perils and not others.
- `if injury_reported:` seventh — an injury does not make a claim invalid, it makes it unsuitable
  for a *fast track*, which is why it sits below cover and above money.
- `if notification.estimate > policy.fast_track_limit:` eighth — the limit is read off the policy,
  not off a constant, so the motor policy's 1500 applies to motor claims without a branch.
- `return Outcome.FAST_TRACK, None` — the only way to reach the last line is to pass all eight, and
  the `None` reason is what part 3.1 asserts on every fast-track.
- **The tuple return, `(Outcome, Reason | None)`** — two values that are always produced together
  and read together. A single object would be tidier and would need a name; two values keep the call
  site honest about the fact that a reason without a deficiency is meaningless.
- `mentions_injury_keyword_scan` at the bottom, with `STAND-IN` in capitals in its first line —
  named so that nobody can call it by accident thinking it is the classifier. Its docstring names
  the exact notification it gets wrong and points at the test that holds it to being wrong.

## When it breaks

Give the parser a date somebody typed by hand and it stops at the edge, naming the value:

```bash
uv run python -c "
from claims_desk.domain import Policy
Policy.from_record({'number': 'SYN-POL-1001', 'holder_ref': 'H-2201', 'risk_address': '12 Kiln Row',
                    'product': 'home-contents', 'inception': '2026-3-14', 'expiry': '2026-10-31',
                    'status': 'active', 'excess': 150, 'fast_track_limit': 2500, 'perils': []})
"
```

```
Traceback (most recent call last):
  File "<string>", line 3, in <module>
  File "...\claims_desk\domain.py", line 68, in from_record
    inception=date.fromisoformat(record["inception"]),
              ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
ValueError: Invalid isoformat string: '2026-3-14'
```

The path is shortened; the rest is verbatim. Compare it with part 1.1, where the same missing zero
produced no error at all and simply reversed the answer. Somebody edits a fixture, drops a zero,
and the difference between the two versions of this project is whether they find out in the next
second or in a deficiency letter. The smallest fix is to write the date properly — and the reason
it is a one-second problem is that parsing happens **once, at the edge**, in the one method that
knows what the file looks like.

## In production

**What a senior writes instead.** The same records, validated by a schema library that produces the
type and the error message together, and the enumerations generated from whatever the business
maintains its reason codes in — because eight reason codes become forty, and forty maintained by
hand in a Python file will not match the ones on the letters. What they would fight for is the
thing this file already does: **parse at the edge, and let the types carry the domain inward**, so
that nothing beyond this module ever sees a string that might be a date.

**What degrades at scale.** Eight ordered checks are readable. Real claims rules run to hundreds,
they differ by product and by territory, and they change at renewal — at which point an `if` chain
becomes a rules engine, and the ordering that is obvious here becomes a decision table somebody
maintains. The thing that survives is the principle: **one reason per letter**, chosen by the first
rule that fails, because a policyholder who is asked for three things sends one and waits.

**The review comment.** *"`assess` now takes the description and looks for the word 'hurt'. Take it
back out — this function's whole value is that it reads fields. The moment it reads English it
needs a test set instead of a test, and it will be wrong about a sentence nobody thought of."*

**The interview question.** *"You have eight validation rules and a caller who will only stay on
the phone once. How do you decide which failure to report, and what does your answer cost when the
rules grow to eighty?"*
