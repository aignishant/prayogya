## One-line answer

One question produced one event for the caller and two in the record — because the runner yields
what an agent *said* and the session keeps the whole exchange, including the question.

## The idea

The running sheet has the caller's words on it as well as the handler's. When a supervisor reads it
back, they are reading a conversation: *she said the hose let go overnight; I told her we would need
a photograph.* Half of that came from outside the building.

The handler, in the moment, was only dealing with one half. They asked and they waited for an
answer, and the answer is what they acted on. Both accounts are correct and they are different
lengths, and confusing them is how somebody ends up believing a conversation was shorter than it
was.

A **turn** is one exchange. An **event** is one thing that happened inside it — a question arriving,
a tool being asked for, a tool answering, a fragment of text, the finished text. Several events make
a turn, and the two numbers this part is about are:

- what the runner **yields**, which is what the agent produced and what a caller reacts to;
- what the session **holds**, which is the record, and includes the question.

Today the numbers are one and two, which is the smallest possible version of the difference. There
are no tools on this agent and no streaming from the stand-in, so the yielded stream is a single
final response. Both numbers grow — day 9 has five agents, and a real provider streams — and
knowing which number you are looking at is the difference between "the classifier answered in one
step" and "the record of this claim has two entries in it".

## The mechanism

Ask once, then look at both accounts of the same turn:

```bash
uv run python -c "
import asyncio
from claims_desk import sessions
from claims_desk.agents import classifier

async def main():
    agent = classifier.build()
    answer, yielded = await sessions.turn(agent, 'FNOL-4471', 'the flexible hose let go overnight')
    print('runner yielded:', len(yielded))
    for e in yielded:
        print(f'  author={e.author!r} final={e.is_final_response()} partial={e.partial!r} content={\"yes\" if e.content else \"none\"}')
    s = await sessions.stored('FNOL-4471')
    print('session holds:', len(s.events))
    for e in s.events:
        print(f'  author={e.author!r} final={e.is_final_response()} invocation={e.invocation_id[:14]!r}')
asyncio.run(main())
"
```

```
runner yielded: 1
  author='classifier' final=True partial=None content=yes
session holds: 2
  author='user' final=True invocation='e-697b3a32-48e'
  author='classifier' final=True invocation='e-697b3a32-48e'
```

**Line by line:**

- **`runner yielded: 1`.** One event came out of `run_async`. That is what `sessions.turn` collected
  and what part 1.1's log line calls `yielded`, and it is the number a caller sees.
- `author='classifier'` — **every event says who produced it**, by agent name. With one agent that
  looks like decoration. With five it is the field that tells you which of them said the thing you
  are objecting to, and it is why day 7 chose the agent's name to read well.
- `final=True` — this event concludes the turn. `is_final_response()` is not a flag on the wire; it
  is computed, and it is `True` when the event carries no function call, no function response, is
  not partial, and has no trailing code-execution result. **An event can be final and still carry
  nothing** — that is an error event, and it is part 3.2.
- `partial=None` — **not `False`.** The field has three states, and unset reads as `None`. That is
  why a check for "this is a complete piece of text" is written as *not `True`* rather than as
  `False`: a fragment sets it to `True`, and everything else leaves it alone. This project's
  stand-in never streams, so it is always `None` here — and against a real provider it would be
  `True` on every fragment and the yielded count would be many rather than one.
- `content='yes'` — there is content. The three-condition check in part 1.1 —
  `is_final_response() and event.content and event.content.parts` — exists because each of those can
  independently not hold.
- **`session holds: 2`.** The record has one more entry than the caller saw.
- `author='user'` — **and there it is.** The question is an event, authored by the user, stored in
  the conversation. The runner did not yield it because the caller had just sent it and does not
  need it back; the session keeps it because a record with only the answers in it is not a record of
  a conversation.
- **Both stored events carry the same `invocation_id`.** An **invocation** is one call to the runner
  for one user message, and every event in it is stamped with the same id. A session accumulates
  invocations; an invocation is one exchange inside it. When day 17 wants to find "what happened to
  this claim on this run", `invocation_id` is the field it groups by — and `claim` is how it found
  the session in the first place.
- `final=True` on the user's event too — which reads oddly until you look at the definition again.
  `is_final_response()` asks whether an event is a complete, user-facing response; a user message
  carries no function call and is not partial, so it satisfies the test. **The method is about the
  shape of an event, not about who sent it**, which is exactly why part 1.1's check is guarded by
  `event.content` and by the loop being over *yielded* events rather than stored ones.

## When it breaks

The two numbers being different is not a problem. Believing they are the same is, and the way it
bites is in a count.

Part 1.1's log line reports `yielded`, and this project's own day-7 log line reports `events`:

```
{"ts": "...", "event": "classifier.answered", "model": "scripted/claims-classifier", "events": 1, "chars": 76}
{"ts": "...", "event": "session.turn", "claim": "FNOL-4471", "session": "claim-FNOL-4471", "yielded": 1, "chars": 76}
```

Both say `1`, both are correct, and **neither of them is the number of entries in the claim's
conversation record**, which is two. A dashboard built on either of those fields and labelled
"messages per claim" would be half right, permanently, with nothing to indicate it.

The version of this that costs real money arrives with a provider. The stand-in yields one complete
response; a streaming model yields a fragment per word and one final event, so the same turn that
reports `events: 1` here would report `events: 40`. Any threshold, alert or cost estimate built on
this project's numbers is built on a stand-in that does not stream — which is one more line for the
list day 7 part 1.2 started, and one more reason the honest `TODO(me)` is to run a notification
against a real model and write down what differed.

The smallest fix is the naming, and part 1.1 already made it: the field is called `yielded` rather
than `events`, because it is the count of what came out of the runner. The general habit: **a count
in a log line should say what it counted.**

## In production

**What a senior writes instead.** The same loop, with the events pushed into a trace rather than
counted — one span per event, correlated by `invocation_id`, so the question is never "how many"
but "what happened and in what order". Day 17 is that. What they would insist on now is the
distinction this part is about: a run's **record** and a run's **output** are different objects, and
a system that keeps only the second cannot explain itself afterwards.

**What degrades at scale.** Two events per turn, twelve notifications, one agent: twenty-four
entries. Five agents with tool calls, against a streaming provider, is a few hundred events per
notification — several hundred thousand for a morning's queue. At that point the session is not a
record you read, it is a stream you index, and the fields that matter are the ones this project is
already stamping: the agent's name, the invocation, and the claim the session is addressed by.

**The review comment.** *"This logs `len(session.events)` as `turns`. Those are events, not turns,
and one of them is the question we just sent. Count invocations if you want turns, or rename the
field."*

**The interview question.** *"Your agent framework yields events as a turn runs and also stores
them. Why are those two collections different sizes, and which one would you use to answer 'what did
we say to this customer'?"*
