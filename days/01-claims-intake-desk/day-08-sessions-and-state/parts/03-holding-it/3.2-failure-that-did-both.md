## One-line answer

When the model fails, the exception reaches the caller **and** an error event goes into the
conversation — and the event is a final response with no content at all, which is why every read of
`event.content` in this project is guarded.

## The idea

A call drops mid-sentence. Two things happen, and a department that only arranges for one of them
has a gap.

The handler knows immediately: the line is dead, and they have to do something about it now. And the
running sheet gets a line — *call terminated, 14:32* — which is not for the handler, who was there.
It is for whoever opens the file next week and needs to understand why there is no date of loss on
it.

The first is an interruption. The second is a record. They serve different people at different
times, and it is entirely possible to build a system with the first and not the second: a
department where a dropped call produces an urgent problem and leaves no trace.

The framework does both, and this part is about what the second one looks like — because it has a
shape that will break a naive reader, and this project has been guarding against it since day 7
without having seen it.

## The mechanism

A stand-in that fails instead of answering. It announces itself, like every double in this project:

```python
class BrokenDouble(BaseLlm):
    """A stand-in that fails. Announced like every other double in this project."""

    model: str = "scripted/broken"

    async def generate_content_async(
        self, llm_request: LlmRequest, stream: bool = False
    ) -> AsyncGenerator[LlmResponse, None]:
        raise RuntimeError("the provider was unreachable")
        yield  # pragma: no cover - unreachable, and required to make this a generator
```

**Line by line:**

- `model: str = "scripted/broken"` — **the prefix, so day 7's registry admits it.** A double that
  fails is still a double, and it announces itself for the same reason.
- `raise RuntimeError("the provider was unreachable")` — an ordinary exception, of the kind a real
  client raises when a connection cannot be made. Nothing framework-specific.
- `yield` **after the raise** — unreachable, and **required**. A function containing `yield` is a
  generator function; without this line the method would be an ordinary coroutine, the framework
  would fail on the shape of the return value rather than on the provider, and the error you got
  would be about a signature.
- `# pragma: no cover` — says the line is deliberately never executed, so a coverage report does not
  report it as a gap somebody should close.

Run a turn against it and catch what comes out:

```bash
uv run python -c "
import asyncio
from collections.abc import AsyncGenerator
from google.adk.models.base_llm import BaseLlm
from google.adk.models.llm_request import LlmRequest
from google.adk.models.llm_response import LlmResponse
from claims_desk import sessions
from claims_desk.agents import classifier

class BrokenDouble(BaseLlm):
    model: str = 'scripted/broken'
    async def generate_content_async(self, llm_request: LlmRequest, stream: bool = False) -> AsyncGenerator[LlmResponse, None]:
        raise RuntimeError('the provider was unreachable')
        yield

async def main():
    agent = classifier.build(BrokenDouble())
    try:
        await sessions.turn(agent, 'FNOL-9998', 'anything at all')
    except Exception as failure:
        print('raised:', type(failure).__name__ + ':', failure)
    s = await sessions.stored('FNOL-9998')
    for e in s.events:
        print(f'author={e.author!r:<14} error_code={e.error_code!r:<16} final={e.is_final_response()} content={\"yes\" if e.content else \"none\"}')
        if e.error_message:
            print('   error_message:', e.error_message)
asyncio.run(main())
"
```

```
raised: RuntimeError: the provider was unreachable
author='user'         error_code=None             final=True content=yes
author='classifier'   error_code='RuntimeError'   final=True content=none
   error_message: the provider was unreachable
```

**Line by line:**

- **`raised: RuntimeError: the provider was unreachable`.** The exception propagated all the way out
  of `sessions.turn` to the caller, unchanged. Nothing swallowed it, nothing replaced it with a
  return value, and the message the provider's client produced is the message the caller sees.
- **And then two events, because the conversation was recorded anyway.** The turn failed and the
  session still has a record of it.
- `author='user'` with `content='yes'` — **the question survived.** That matters more than it looks:
  a record showing that a question was asked and not answered is a record somebody can act on,
  whereas an empty session says only that nothing happened.
- `author='classifier'` — the failure is attributed to the agent that was running. With five agents,
  this field is the only thing that says which one.
- `error_code='RuntimeError'` — **the exception's class name, as a string.** An event is a record,
  and a record holds text; the exception object itself does not survive into a stored conversation
  and should not.
- `error_message: the provider was unreachable` — and the message does. Both halves of the
  exception, split into two fields, so a log or a query can group by code and read by message.
- **`final=True` and `content=none` on the same event.** This is the shape to remember. It concludes
  the turn — `is_final_response()` is `True` because there is no function call, no function
  response and no partial flag — **and it carries nothing at all.**
- **That combination is why every read in this project is guarded.** Day 7 wrote
  `if event.is_final_response() and event.content and event.content.parts:` and part 1.1 kept it.
  The first condition is `True` here. Without the second, this line would be
  `None.parts` and the failure a reader actually got would be an `AttributeError` inside the desk —
  with the real cause, an unreachable provider, nowhere in the traceback.

## When it breaks

Drop the guard. Write the loop the way it reads most naturally — check whether this is the final
response, then take its text:

```python
    async for event in runner.run_async(...):
        if event.is_final_response():
            answer = "".join(part.text or "" for part in event.content.parts)
```

That code is correct on every successful turn this project has ever run. It is correct on all twelve
notifications, in every test, against both transports. And on the first turn where the provider is
unreachable it raises:

```
AttributeError: 'NoneType' object has no attribute 'parts'
```

Now consider what the person on the other end of that has. A traceback pointing at a line that joins
text parts. No mention of a provider, no mention of a network, no error code and no error message —
because the error event carrying all three was never looked at. The actual failure is recorded, in
the session, in fields designed for it, and the code fell over before it got there.

**The two failures are also different in kind.** `RuntimeError: the provider was unreachable` is
something to retry, escalate or wait out; day 15 is built on being able to tell. `AttributeError:
'NoneType' object has no attribute 'parts'` is a bug in the desk, and it will be triaged as one —
by somebody who will spend the first hour looking at parsing code.

The smallest fix is `and event.content and event.content.parts`. The habit worth taking: **when a
framework hands you a stream of events, some of them are about failure, and the ones about failure
are shaped differently from the ones about success.** Reading only the successful shape works until
it does not.

## In production

**What a senior writes instead.** The same loop, with the error event handled explicitly rather than
skipped — which `sessions.turn` already does, logging `session.error_event` with the author, the
code and the message before the exception unwinds. That log line is the only trace that survives in
a process whose session store does not, and this project's does not. What they would add next is the
retry decision: an error event carries enough to decide whether this is worth trying again, and day
15 is where that judgement lives.

**What degrades at scale.** One failure in twelve notifications is a traceback somebody reads. A
provider having a bad ten minutes during a morning batch is several hundred, and at that point the
difference between the two failure modes above is the difference between a graph of
`RuntimeError` — obviously an outage — and a graph of `AttributeError` — obviously a deployment
somebody should roll back. Getting the wrong one costs the first hour of an incident, every time.

**The review comment.** *"This reads `event.content.parts` after checking `is_final_response()`. An
error event is final and has no content — add the guard, or the next provider outage reaches us as
an `AttributeError` in the parser and we lose the first hour."*

**The interview question.** *"Your framework reports a failure both by raising and by recording an
event. Why both, who is each one for, and what would you lose by only having the exception?"*
