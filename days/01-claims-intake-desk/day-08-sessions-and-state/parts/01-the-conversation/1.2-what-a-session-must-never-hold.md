## One-line answer

Session state is written down and kept, so `check_state` refuses a key whose *name* says it holds a
secret or a person's contact details — and it refuses by name, because the value of a telephone
number and the value of a claim reference look the same.

## The idea

There is a rule about the running sheet that new handlers are told twice, because the first time it
sounds like fussiness.

You write what the caller said. You do not write their card number, and you do not write the code
they read out from the letter. If they give you one, you use it and you do not put it on the sheet —
because the sheet goes in the file, the file is kept for years, it is copied when the claim moves
department, and it is disclosed if the claim is ever disputed.

The rule is not about the moment of writing. It is about **everywhere the sheet goes afterwards**,
and the handler writing it is the only person in that chain who can prevent anything.

A session's `state` is a running sheet. It is a dictionary that travels with the conversation, is
written into the store, survives every turn, and gets read by anything that later opens the
conversation. Day 1 already made this argument about logs and solved it with redaction at the
writer. This is the same argument about a different destination, and it needs a different answer:
**a log line can be redacted, and a state key cannot be un-kept.**

So state is not redacted. It is refused.

## The mechanism

The check is in `claims_desk/sessions.py`, printed whole in part 1.1. These are the lines that do
the refusing:

```python
FORBIDDEN_IN_STATE = ("key", "token", "secret", "password", "contact", "phone", "address", "email")


def check_state(state: dict[str, Any]) -> dict[str, Any]:
    """Return `state` if every key is safe to keep, or refuse and name the key that is not."""
    for key in state:
        lowered = key.lower()
        for smell in FORBIDDEN_IN_STATE:
            if smell in lowered:
                raise ForbiddenState(
                    f"{key!r} must not be written into session state: a session is retained, "
                    f"and {smell!r} names something that should not be"
                )
    return state
```

**Line by line:**

- **Eight substrings, and they are two lists joined.** `key`, `token`, `secret`, `password` are day
  1's secret hints, unchanged. `contact`, `phone`, `address`, `email` are new, and they are not
  secrets at all — they are personal data, which is a different problem with the same answer.
- **Why the two belong together**: a secret must not be *seen*, and personal data must not be
  *kept*. A session's state is both seen and kept, so one list covers both, and the message says
  which concern caught you.
- `for key in state:` — **the keys, never the values.** A value is checked by nobody here, and that
  is deliberate: `"C-3301"` is a contact reference and `"FNOL-4471"` is a claim reference and no
  inspection of the strings tells them apart. The name is the only reliable signal, and the caller
  chose the name.
- `lowered = key.lower()` and `if smell in lowered:` — substring, case-insensitive. `contact_ref`,
  `contactRef`, `holder_contact` and `CONTACT` all match. It over-matches on purpose: `keyword`
  would be refused, and a refused harmless key costs one rename while a retained telephone number
  costs something else entirely.
- `raise ForbiddenState(...)` — **refused, not redacted.** Day 1's logger replaces a secret's value
  with `<redacted>` and lets the line through, because a log line with a hole in it is still useful.
  A session's state with a hole in it is a caller who thinks they stored something. There is no
  useful partial success here, so there is no partial success.
- The message names **the key** and **the smell**: which of your keys, and which rule. A caller who
  believes the rule is wrong for their case can see exactly which of the eight to argue about.
- `return state` — the identity return, so `check_state(...)` wraps a value inline. In part 1.1 it
  appears as `state=check_state(state or {})` in the one place a session is created, which is the
  only place state is ever set on this desk.

What it lets through, and what it does not:

```bash
uv run python -c "
from claims_desk import sessions
for candidate in ({'claim': 'FNOL-4471'}, {'contact_ref': 'C-3301'}, {'api_key': 'x'}):
    try:
        sessions.check_state(candidate)
        print(f'{candidate} -> allowed')
    except sessions.ForbiddenState as refusal:
        print(f'{candidate} -> {refusal}')
"
```

```
{'claim': 'FNOL-4471'} -> allowed
{'contact_ref': 'C-3301'} -> 'contact_ref' must not be written into session state: a session is retained, and 'contact' names something that should not be
{'api_key': 'x'} -> 'api_key' must not be written into session state: a session is retained, and 'key' names something that should not be
```

**Line by line:**

- `{'claim': 'FNOL-4471'} -> allowed` — **a reference to a thing, rather than a fact about a
  person.** This is the whole of what this desk's sessions carry, and it is enough: anything else
  about the claim can be fetched from the boundary by that reference, at the moment it is needed,
  by something with a rule about who may see it.
- `'contact_ref'` refused, naming `'contact'` — and notice what was refused. `C-3301` is not a
  telephone number; it is a *reference* to one, in this project's synthetic data. **It is refused
  anyway**, because the rule is about names and the name says contact. That is the over-matching
  working: the day the field carries a real number, no rule has to change.
- `'api_key'` refused, naming `'key'` — the same check that day 1 applied to logs, applied to a
  destination that keeps things.
- **The refusals are readable by the person who caused them.** Each one says which key, and which
  word in the key was the problem, which is the difference between a rule people follow and a rule
  people work around.

## When it breaks

The rule is about names, and a name can be chosen to avoid it:

```bash
uv run python -c "
from claims_desk import sessions
print(sessions.check_state({'caller_ref': 'C-3301'}))
print(sessions.check_state({'notes': 'ring back on 0000 000000'}))
"
```

```
{'caller_ref': 'C-3301'}
{'notes': 'ring back on 0000 000000'}
```

Verbatim, from this project. Both allowed, and both are exactly the thing the rule exists to
prevent. `caller_ref` is a contact reference wearing a different name; `notes` is free text with a
telephone number in it.

This is the same limit day 2 found in the injury keyword scan and day 1 found in name-based
redaction, and it is worth being precise about what it means rather than treating it as a defeat.
**Name-based rules protect you from forgetting, not from deciding.** Somebody who writes
`contact_ref` was not thinking about retention and is stopped. Somebody who writes `notes` and puts
a number in it made a choice, and no check on key names was ever going to catch that.

The smallest fix for the second case is a review comment. The systematic fix is not a longer word
list — it is that state should carry **references, never contents**, and a reviewer can check that
rule by reading rather than by matching. The build brief asks for a stricter version: an allow-list
rather than a deny-list, where the only permitted keys are ones this desk has agreed to.

## In production

**What a senior writes instead.** An allow-list, and a retention policy the session store enforces
rather than a convention the callers keep. The deny-list here is the cheap version and it earns its
place by being cheap — it costs eight strings and it catches the ordinary mistake — but a system
holding personal data should be able to say what its conversation records **do** contain, not just
what they must not.

**What degrades at scale.** One state key, checked in one place, is easy. The pressure comes from
convenience: an agent that needs the policyholder's town to write a letter, and the easiest place
to put it is state, where it is already travelling. That is how a conversation record becomes a
second copy of the customer database — with none of the customer database's rules, in a store
nobody thought of as personal data, discovered during an audit. **The line to hold is that state
carries references and the boundary holds contents**, which this project has enforced since day 3
and which this file extends to conversations.

**The review comment.** *"This puts the full notification into state so the letter writer can see
it. Put the claim reference in and let the letter writer fetch what it needs — that description is a
policyholder's own words, and state is retained."*

**The interview question.** *"Your framework stores conversation state. Tell me what your system
puts in it, how you would prove that to somebody who asked, and what happens when a customer asks
you to delete everything you hold about them."*
