## One-line answer

Adding the approval gate turned five tests red — one each from days 6, 7, 9, 11 and 14 — and every one
of them was telling the truth: the desk's recorded output changed from twelve decided claims to eleven
recorded and one held, which is a change to the thing this project promised on day 0.

## The idea

The last thing the signature book changes is the daily figures.

Introduce an authority limit on a claims floor and the Monday report stops matching. It used to say
twelve claims settled; now it says eleven settled and one with the supervisor. Nobody thinks the
report is broken. Everybody understands that the number changed because the process changed, and the
report's job is to say what happened.

Software has the same moment and handles it worse, because the report is a test and a red test feels
like damage. The reflex is to make it green — and there are two ways to do that, which look identical
in a diff and are completely different acts. You can change the assertion to describe the new
behaviour, or you can change the assertion until it stops looking. `assert len(written) == 11` is the
first. `assert len(written) >= 10` is the second, and it will pass tomorrow when the gate holds four
claims by mistake.

So this part is about what it costs to add a control to a system that already works, and about being
precise while paying it. Five tests went red. None of them was wrong. Each was written on a different
day for a different reason and each of them, correctly, noticed that the queue's output is not what it
was.

That is the blast radius of the gate, and it is worth looking at directly rather than quietly fixing.
A control that changes nothing anywhere is a control that is not doing anything. Five reddened tests
across five days is the evidence that the gate is load-bearing — and the number is a fact about how
much of this project depends on the queue's totals, which is useful to know before the next change.

There is one more thing in here, and it is the least comfortable. The day-0 brief said **twelve
notifications, four fast-tracked, eight letters**. That is now false. Seven letters are written, and
the eighth claim is held. The honest response is not to weaken the test that quotes the brief, and it
is not to move the threshold until the brief comes true again. It is to notice that a security control
changed a product promise, write that down, and let somebody decide which of the two is wrong.

## The mechanism

Five diffs. Each is a marked change against the file the named day printed.

**Day 7**, `tests/test_agent.py` — the test that quotes the day-0 brief:

```diff
 def test_the_whole_queue_now_matches_what_the_brief_promised(_in_process_boundary) -> None:
     """`PROJECT.md`, written on day 0: twelve notifications, four fast-tracked, eight letters."""
     counts = asyncio.run(desk.run_queue())
-    assert counts == {"fast-track": 4, "deficiency": 8, "pending": 0}
+    # Day 16 put an approval gate in front of the write. FNOL-4481 is a 4800 deficiency, which
+    # is above the threshold, so it is decided and held rather than recorded.
+    assert counts == {"fast-track": 4, "deficiency": 7, "pending": 1}
 
     import json
 
     written = sorted((_in_process_boundary / "claims").glob("*.json"))
-    assert len(written) == 12
+    assert len(written) == 11
     reasons = [
         json.loads(path.read_text(encoding="utf-8"))["reason"]
         for path in written
         if json.loads(path.read_text(encoding="utf-8"))["reason"] is not None
     ]
-    assert len(reasons) == 8
-    assert len(set(reasons)) == 8, "eight letters, each naming a different missing field"
+    assert len(reasons) == 7
+    assert len(set(reasons)) == 7, "seven letters, each naming a different missing field"
+    # The eighth reason is the held one, and it is the coherent one to lose: the claim the rules
+    # called too big to fast-track is the claim the approval gate holds.
+    assert "above_fast_track_limit" not in reasons
```

**Line by line:**

- **The docstring is not edited.** It still quotes what day 0 promised, and the promise is now wrong.
  Leaving it there is deliberate: the divergence between the brief and the assertions is the thing
  somebody should trip over, and rewriting the docstring would tidy the evidence away.
- `{"fast-track": 4, "deficiency": 7, "pending": 1}` — **the totals still sum to twelve.** No claim was
  lost; one moved category.
- **The comment names the day, the claim and the figure.** A bare `== 7` invites a future reader to
  wonder whether the desk got worse. `FNOL-4481 is a 4800 deficiency` tells them in one line.
- **This test lost an assertion and gained one.** `len(set(reasons)) == 8` was a nice property — eight
  deficiencies, eight distinct reasons, so every reason code was exercised by the queue — and holding
  a claim takes one reason out of the recorded set. The replacement, `"above_fast_track_limit" not in
  reasons`, says which one and why it is the right one to lose. **When a control costs you an
  assertion, say what you lost.**

**Day 9**, `tests/test_cast.py` — the letter stored beside the decision:

```diff
     records = [
         json.loads(path.read_text(encoding="utf-8"))
         for path in sorted((_in_process / "claims").glob("*.json"))
     ]
-    assert len(records) == 12
+    # Day 16's approval gate holds FNOL-4481 before the letter is drafted, so seven letters are
+    # written rather than eight. A held claim costs one model call, not four.
+    assert len(records) == 11
     with_letter = [r for r in records if "letter" in r]
-    assert len(with_letter) == 8
+    assert len(with_letter) == 7
     assert all(r["outcome"] == "deficiency" for r in with_letter)
     assert all(r["claim_id"] in r["letter"] for r in with_letter)
```

**Line by line:**

- **The two `all(...)` assertions are untouched**, because the properties they check — every stored
  letter belongs to a deficiency, and every letter names its own claim — are unaffected by holding one
  claim back. Only the counts moved.
- **The comment records where the gate sits relative to the letter.** That is the fact this file cares
  about: not that a record is missing, but that no letter was drafted for it.

**Day 6**, `tests/test_desk.py` — every decided claim reaches the claim file:

**Line by line:**

**Day 14**, `tests/test_record.py` — every stored record replays to its own verdict:

```diff

-    assert counts == {"fast-track": 4, "deficiency": 8, "pending": 0}
+    # Day 16 put an approval gate in front of the write. FNOL-4481 is a 4800 deficiency, which
```

**Line by line:**

- **`undefendable == []` is untouched**, and that is the reassuring part of this diff. Every record
  that *was* written still replays to the verdict it claims. The gate removed a record; it did not
  make any surviving record less defensible.
- **The same comment appears in three files**, word for word. Duplicated prose is normally a smell.
  Here it is the point: three separate suites assert the same totals, and a reader arriving at any one
  of them needs the explanation without going to find it.

## When it breaks

The failure worth showing here is the one that does not look like a failure. Make the five tests green
the lazy way:

```diff
-    assert counts == {"fast-track": 4, "deficiency": 8, "pending": 0}
+    assert counts["fast-track"] == 4
+    assert sum(counts.values()) == 12
```

Green. And it stays green if the gate holds four claims, or eleven, or if `APPROVAL_ABOVE` is
accidentally set to zero and the desk records nothing at all — because twelve claims still went in and
twelve outcomes still came out. Every specific claim about what this desk produces has been replaced by
an arithmetic identity that cannot fail.

Nothing in a test run will ever tell you this happened. There is no red, no warning, no coverage drop.
The only symptom is that a suite which used to catch things stops catching them, and you find out on
the day it should have caught something.

The smallest fix is to assert the actual numbers. The general rule is the one to carry out of today:
**when a change reddens a test, the assertion is a witness — read what it says before you edit it.** If
the new behaviour is correct, write the new numbers down and say in a comment why they changed. If you
find yourself widening a comparison, relaxing an equality into a containment, or replacing a value with
a sum, stop: you are not updating a test, you are removing one.

## In production

**What a senior writes instead.** One place that owns the expected queue outcome — a fixture or a small
module — so twelve claims, their expected outcomes and their reasons are declared once and the five
suites assert against it. Then a control that changes the queue's output is a one-line change to the
expectation and five suites follow, which removes the temptation to weaken assertions and makes the
diff say exactly what changed about the system rather than what changed about the tests.

**What degrades at scale.** Five tests over twelve claims is a diff you can read. A claims platform
with an end-to-end suite over a few thousand synthetic notifications gets a control change that moves
several hundred expected outcomes, and at that size nobody reads the diff — they regenerate the golden
file and approve it. Which is exactly how a control that holds the wrong claims ships. The defence is
that the regeneration reports *deltas by category* — held claims went from 0 to 1, letters from 8 to 7
— so the review is over a summary a person can actually check.

**The review comment.** *"Five suites assert the queue's totals independently and all five had to change
for one control. That is duplication, and it is why the diff needed the same comment three times.
Extract the expectation. The tests keep their meaning and the next control costs one edit."*

**The interview question.** *"You add a required approval step and forty tests go red. Walk me through
how you decide which ones to update, which to delete, and which mean your change is wrong — and tell me
what you would refuse to do to make them green."*
