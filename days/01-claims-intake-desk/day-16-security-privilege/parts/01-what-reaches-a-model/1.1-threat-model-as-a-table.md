## One-line answer

A threat model is the list of everything that can reach a model in this system and everything a
model can reach from it — and if it lives in a document nobody opens it decays, so this desk keeps
it as a tuple of dictionaries in `claims_desk/security.py` where a test can read it and go red.

## The idea

Walk into a claims floor on a Monday and look at what is on a handler's desk.

There is the notification form, filled in by whoever took the call. There is the policy schedule,
printed off the policy system. There is a page of handwritten notes — the caller's own words, taken
down while they talked. And there is the departmental handbook, in a ring binder, with the version
number on the spine.

A handler who has been there a fortnight treats those four pieces of paper identically. A handler
who has been there ten years does not. The schedule is the insurer's own record and is as close to
fact as this floor gets. The form is somebody's typing and might have a transposed digit. The
handbook is authority — it is what the department will be held to. And the page of notes is not
information about the loss at all; it is a **record that somebody said something**. Ten years
teaches you to keep those categories apart, because the day you forget is the day a caller talks you
into something and you cannot say afterwards why you did it.

That distinction — *what is fact, what is merely something somebody said* — is the whole of security
for a system with a model in it. There is no separate security subject here. There is one question
asked twice: **what can reach a model, and what can a model reach.** Everything this day builds is
an answer to one half or the other.

The trouble with the question is that the answer is normally kept in the wrong place. It goes into a
wiki page written the week before a review, or a spreadsheet with a column marked *mitigation*, and
then the code changes and the page does not. Six months later the page says the description is
quarantined, and it is not, and nobody finds out until somebody is reading logs at the wrong end of
an incident.

So this desk keeps the answer in the source tree, as data, in the same repository as the code it
describes. Not because a tuple of dictionaries is elegant — it is not especially — but because a
tuple of dictionaries can be **read by a test**. A row that says a source is untrusted and leaves the
defence blank is a row a test can refuse. That is the difference between a threat model and a list of
worries: a list of worries cannot fail.

One more thing about today, said plainly at the start. Almost nothing in this file is new behaviour.
The boundary has been returning cover rather than policy records since day 3. The agents have had no
tools since day 7. Day 13's schema has been refusing anything outside its enum since it was written.
Today is mostly the act of **naming what was already true**, so that undoing it becomes visible. A
security control nobody wrote down is a security control one refactor from disappearing.

## The mechanism

The first version of this project's threat model, at `claims_desk/security.py`:

```python
"""The threat model for this desk, written down, and the four things that follow from it.

Security in an agent system is not a checklist bolted on at the end; it is a set of answers to *what
can reach a model here, and what can a model reach*. This desk has been answering that since day 3,
when the boundary was built — and most of what this file does is name what was already true so that
a change can be noticed.

The four answers:

- **Quarantine.** The description is what a person said on the telephone. It is untrusted, it goes
  to a model, and it is marked as data rather than left to look like instructions. The marker
  wording is modelled on the framework's own: day 9 watched ADK fence one agent's output for
  another between `<<<BEGIN_QUOTED_AGENT_CONTENT>>>` markers, with a sentence telling the reader it
  was data and not instructions.
- **An allowlist.** What an agent can reach is the docket the boundary declares, and this file
  states which agent may use which tool so that "none of them" is a decision rather than an absence.
- **Scoped credentials.** The desk holds the provider key. The boundary holds the claim files. Two
  processes, two sets of powers, neither holding the other's.
- **An approval gate.** Above a threshold, a decision is not recorded until a person says so — and
  the approval goes in day 14's record, because an approval nobody can trace is worth nothing.

What this project **cannot** show is whether a model obeys a quarantine marker. Its stand-in matches
phrases and reads no instructions at all. So the markers are asserted to be present, the reasoning
for them is written down, and whether they work against a real model is a `TODO(me)` rather than a
claim.
"""

from __future__ import annotations

#: What this desk trusts, what it does not, and why — the threat model as data rather than as prose
#: in a wiki nobody opens. Each row is a source of input, whether it is trusted, and what is done
#: about it. The test beside it asserts that every untrusted source has a named defence, which
#: is what stops this from becoming a list of worries.
THREATS: tuple[dict[str, str], ...] = (
    {
        "source": "notification.description",
        "trusted": "no",
        "why": "it is what a person said on the telephone, taken down verbatim",
        "reaches": "the classifier, as the user message",
        "defence": "quarantined, and never sent to the letter writer",
    },
    {
        "source": "notification fields",
        "trusted": "no",
        "why": "typed by a handler from a call, and never read by a model",
        "reaches": "the rules, as typed values",
        "defence": "parsed into a dataclass on day 2; a rule reads a date, not a sentence",
    },
    {
        "source": "policy records",
        "trusted": "partly",
        "why": "the insurer's own data, and it still holds a person's address",
        "reaches": "the rules, through the boundary",
        "defence": "the boundary returns cover, not the record",
    },
    {
        "source": "tool results",
        "trusted": "partly",
        "why": "structured by us, and their contents come from data we did not write",
        "reaches": "the letter writer, as the materials for a letter",
        "defence": "the wording comes from a table on the server, never from a claim",
    },
    {
        "source": "the model's own answer",
        "trusted": "no",
        "why": "a fluent answer is not a checked one",
        "reaches": "the rules, as a peril and an injury flag",
        "defence": "day 13's schema refuses anything not in the enum",
    },
    {
        "source": "the handbook",
        "trusted": "yes",
        "why": "written by the department and versioned with the code",
        "reaches": "a handler, through a citation",
        "defence": "citations resolve, and no model writes to it",
    },
)
```

**Line by line:**

- **The module docstring lists four answers and then admits what the project cannot show.** That last
  paragraph is the most important thing in the file. This desk runs a scripted stand-in that matches
  phrases; it does not read instructions, so it cannot be talked out of anything, so **no run here is
  evidence that a quarantine marker works.** Writing the caveat into the module means nobody reads
  the green suite as proof of something it never tested.
- `THREATS: tuple[dict[str, str], ...]` — **a tuple, not a list.** Module-level mutable state is
  something any part of the process can append to at run time, and a threat model assembled at run
  time is not reviewable. A tuple is fixed at import and the diff is the only way to change it.
- **Five keys per row: `source`, `trusted`, `why`, `reaches`, `defence`.** `source` and `defence` are
  the obvious pair. The other three are what make the table useful six months from now: `why` records
  the reasoning so a later reader can disagree with it on the merits, and `reaches` records the blast
  radius — which is the field that tells you what to go and look at when a source turns out to be
  worse than you thought.
- `"trusted": "partly"` — **three values, not two.** Policy records are the insurer's own data and are
  as trustworthy as anything here, *and* they carry a person's address, so "trusted" and "untrusted"
  are both wrong. Forcing a boolean here would have produced a row that lies in one direction or the
  other, and the honest middle value is what makes the `policy records` row say something useful.
- The `notification.description` row's defence has **two clauses** — `quarantined, and never sent to
  the letter writer`. Not redundancy: they are different defences against different failures. The
  first is about how a model is told to read the text; the second is that one of the two agents never
  receives it at all, which is a stronger guarantee than any wording.
- The `notification fields` row says `never read by a model` and its defence points at **day 2**. That
  is the row people are surprised by. The estimate, the date of loss and the photo reference are all
  attacker-influenced — a caller can say anything — but they are parsed into typed fields on day 2
  and read by rules, and a rule that compares two dates cannot be argued with. **Structure is a
  security control**, and it was built before this file existed.
- The `the model's own answer` row is the one that catches people out. It is easy to think of the
  model as the thing being protected. It is also an **untrusted source**: whatever it returns comes
  back into this system, and day 13's `Reading` schema is the thing that refuses a peril outside the
  enum. That row is why day 13 is a security day as much as a plumbing one.
- The `handbook` row is the only `yes`, and it still carries a defence — `citations resolve, and no
  model writes to it`. A trusted source is trusted **because** of the two properties named there, and
  writing them down is what stops "the handbook is fine" from surviving the day somebody makes it
  writable.
- **The comment above `THREATS` names the test that guards it.** A future reader who deletes a
  defence field finds out from the suite, not from a reviewer's memory.

Two tests hold it, and the second is the one that matters. Run them:

```bash
uv run pytest tests/test_security.py -q -p no:warnings -k "named_defence or named_untrusted"
```

```
..                                                                       [100%]
2 passed, 23 deselected in 8.92s
```

**Line by line:**

- The first asserts every row has all five keys, that `trusted` is one of the three permitted words,
  and that **anything not fully trusted has a non-empty defence**.
- The second asserts by name that `notification.description` and `the model's own answer` are
  recorded as untrusted. Those two are the rows somebody would reclassify while making something
  work, and pinning them by name means the reclassification is a red test rather than a diff nobody
  looks at closely.

## When it breaks

Blank one defence — the `tool results` row, on the grounds that the wording comes off the server so
there is nothing to defend against:

```
    def test_every_untrusted_source_has_a_named_defence() -> None:
        """A threat model with a row that says "no" and no defence is a list of worries."""
        for row in security.THREATS:
            assert set(row) == {"source", "trusted", "why", "reaches", "defence"}
            assert row["trusted"] in {"yes", "no", "partly"}
            if row["trusted"] != "yes":
>               assert row["defence"]
E               AssertionError: assert ''

tests\test_security.py:77: AssertionError
```

`assert ''` is a terse thing to read, and it is exactly the right failure. Somebody decided a source
was not fully trusted, and then wrote nothing in the column that says what is done about it. The
suite has no opinion about whether the defence is any good — it cannot have one — but it refuses to
let the sentence go missing.

The smallest fix is to write the defence back. The interesting fix is the other one: if you genuinely
believe there is nothing to defend against, then change `trusted` to `yes` and put your reasoning in
`why`, where a reviewer will see it. Both edits make the test pass. Only one of them is a lie, and
the table makes you choose in public which you are doing.

## In production

**What a senior writes instead.** The same table, with a sixth key — `owner`, naming the team that
answers for that row. On a claims platform the boundary is run by one group and the desk by another,
and a threat row whose defence lives in somebody else's repository is a row that goes stale first.
They would also generate the review document *from* this tuple rather than maintaining a second copy
of it in a wiki, so that the reviewed artefact and the tested one cannot drift.

**What degrades at scale.** Six rows is a system one person holds in their head. A real first notice
of loss platform has intake by telephone, web form, broker feed, mobile app and aggregator, and every
one of those is a separate row with a different trust level — the broker feed is contractually
trusted, the aggregator is not. Twenty-five to thirty rows is where a flat tuple stops being
readable and wants grouping by `reaches`, because at that size the question people actually ask is
never "what sources do we have" but "what reaches the classifier".

**The review comment.** *"`trusted` is a free string with three legal values checked in a test. Make
it an enum in `domain.py` beside `Reason` and `Outcome`, and the check becomes the type rather than
an assertion — and `"partly"` stops being one typo away from `"partial"` and a silently skipped
defence check."*

**The interview question.** *"Your agent reads a customer's free-text complaint and calls a refund
tool. List every untrusted input in that sentence. Most candidates name one; there are at least
three."*
