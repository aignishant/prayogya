## One-line answer

Neither agent in this desk has a single tool, and that is a decision rather than an oversight — so it
is written down as a table mapping each agent to the tools it may call, both entries empty, because an
absence nobody recorded is an absence the next person fills in.

## The idea

There is a door at the back of a claims floor with a keypad on it, and behind it are the claim files.

Ask who has the code and you get one of two answers. The good answer is a list — these four people,
because they do this job. The bad answer is "everyone knows it", which is not a policy at all, and
which is what you get when nobody ever decided. Both floors look identical from the counter. The
difference only shows up the day somebody new arrives and asks, and is told the code, because there was
no list for them not to be on.

An agent's tools are that keypad. The question *which tools may this agent call* has a good answer and
a bad answer, and the bad answer is not "all of them" — the bad answer is that nobody ever asked, so
tools got added as they were needed and the set is whatever accumulated.

This desk's answer is unusual and worth dwelling on: **neither agent has any tools.** Not a restricted
set. None.

That is not asceticism, it is the shape day 3 chose. Every external action this system takes goes
through the boundary, and the boundary is called by the **desk** — Python code — not by a model. The
desk fetches the policy, checks it was in force, asks for the letter's materials, records the decision.
The classifier is handed a description and returns a reading. The letter writer is handed materials and
returns prose. Neither of them can reach anything, because reaching is not their job.

The security consequence is large and easy to under-state. A model that cannot call a tool cannot be
talked into calling one. Every injection story in part 1.2 and part 1.3 ends the same way here: the
worst a diverted model can do is return the wrong words. It cannot record a decision, cannot write to a
claim file, cannot look up a policy it was not given. The blast radius of a successful injection
against this desk is **one wrong classification**, which day 13's schema then has to accept as a member
of the enum, and which day 14's record then replays against the rules.

Compare that with the shape people reach for first, where the classifier is given `fetch_policy` so it
can "see the cover while it reads". That version is more capable and more obvious, and it moves the
tool call inside the part of the system that reads attacker text. Nothing in it is wrong in a way a
reviewer would notice. It just means an injected sentence is now one step away from a boundary call.

So why write a table of two empty tuples at all? Because of the keypad. "These agents have no tools" is
currently true, discoverable only by reading two builder functions, and defended by nothing. Written
down as `TOOLS_ALLOWED`, it becomes a thing a test can read and a thing a diff has to change. Giving an
agent its first tool stops being a one-line addition in a file about classifiers, and becomes an edit
to a table in a file called `security.py` — which is a different conversation in review.

## The mechanism

The table, added to `claims_desk/security.py` — **a marked diff against the file part 1.1 printed**:

```diff

+#: Which agent may call which tool. Every agent in this desk has an empty list, and that is the
+#: point — the boundary is the allowlist, and an agent reaches data by the desk asking rather than
+#: by calling a tool. Written down so that giving an agent a tool becomes a change to this table.
+TOOLS_ALLOWED: dict[str, tuple[str, ...]] = {
+    "classifier": (),

 #: Phrases that look like instructions rather than an account of a loss. Not a filter: nothing is
 #: blocked on the strength of this. A **signal**, logged so somebody can find out how often it
 #: happens before deciding what to do about it.
```

**Line by line:**

- `dict[str, tuple[str, ...]]` — **agent name to tool names.** Strings on both sides rather than
  imported objects, deliberately: importing the agent builders here would make `security.py` depend on
  the thing it constrains, and a file that must be imported by the code it polices is a file people
  move things out of to break an import cycle.
- **The values are tuples, for the same reason `THREATS` is a tuple.** An allowlist something can
  `.append` to at run time is not an allowlist.
- **The keys are the two agent names, and nothing else.** That is what makes the second test below
  possible: the set of keys here must equal the set of agents this desk builds, so adding a third agent
  without a row goes red. An allowlist that silently omits an agent is worse than none, because it
  reads as complete.
- **Both values are empty, and the comment says that is the point.** Without that sentence the next
  reader finds two empty tuples and assumes somebody started the table and never finished it.
- `the boundary is the allowlist` — **the one sentence to remember from this part.** The list of things
  this system may do to the outside world is the docket the MCP server declares, and it is enforced in
  a different process by code, not by a model's restraint.

Three tests hold it:

```bash

```

```

```

**Line by line:**

- The first asserts `TOOLS_ALLOWED` is exactly two empty entries **and** that the built agents really
  have `tools == []`. Both halves, because the table is a claim about the code and a claim nobody
  checks against the code is documentation.
- The second asserts the table's keys equal the set of names the builders actually produce — the test
  that catches a third agent with no row.
- The third asks the running boundary what it declares and asserts the docket is those five tools in
  that order. That is the allowlist that actually matters, and it is checked against a live server
  rather than against the source, so a tool registered by accident shows up.

The docket, from the live server:

```
fetch_policy, check_in_force, record_decision, read_decision, draft_letter
```

**Line by line:**

- **Five tools, and every one of them is called by the desk.** A model has never called any of them.
- **`read_decision` is on the list and the desk barely uses it** — day 14 added it so a record could be
  read back and replayed. It is on the docket, so it is in the blast radius, and that is exactly the
  sort of thing a periodic reading of this list is for.

One test red, and note which half of it caught the change: not the `TOOLS_ALLOWED` line, which is still
perfectly true, but the assertion about what `build()` produces. The table and the code disagreed, and
the test existed to notice. Somebody who then "fixes" the test by adding `"classifier":
("fetch_the_policy",)` to the table has done the right thing — they have written the privilege
escalation down where a reviewer can see it, which is all this table was ever for.

The smallest fix is to remove the `tools=` argument. The general rule: **a capability that is currently
absent should be absent on purpose, in writing.** An empty allowlist is a sentence. No allowlist is a
shrug, and a shrug is what the next person fills in.

## In production

**What a senior writes instead.** The same table, consulted at build time rather than only in a test —
`build()` asks `security.TOOLS_ALLOWED[NAME]` for its tool list and constructs from that, so the table
is not a description of the code but the input to it. That inverts the failure above: adding a tool in
`classifier.py` would then do nothing at all until the table changed, which is a more annoying and much
safer place to be.

**What degrades at scale.** Two agents and five tools fits on one screen. An insurer running intake,
triage, fraud referral, repair scheduling and recovery on one platform has perhaps thirty agents and
upwards of sixty tools, and the useful question is no longer *which tools may this agent call* but
*which agents may reach the payment tool*, which is this table transposed. Past roughly twenty agents
the flat mapping wants to be generated from a per-capability view, because the question that gets asked
in an incident is the reverse of the one the table answers.

**The review comment.** *"`TOOLS_ALLOWED` is asserted in tests and read by nothing. That means it is
documentation with a test, which is better than documentation, but it will still drift the day somebody
adds an agent and copies an existing `build()`. Feed it into the builders and the table becomes the
source of truth."*

**The interview question.** *"Your agent has six tools. Which of them would you take away, and what is
your argument for keeping each of the others? And: what can an attacker who fully controls your model's
output actually do?"*
