## One-line answer

The desk holds the provider key and cannot touch a claim file; the boundary holds the claim files and
has no idea a provider key exists — and the thing that makes that true is not a policy document but the
fact that they are two operating-system processes with different imports, which is why the boundary
starts and serves with no `.env` on disk at all.

## The idea

Every claims floor has this arrangement, and nobody calls it security.

The person on the telephone taking first notifications has a headset, a form on screen, and no ability
whatsoever to authorise a payment. The person in the back office who moves money has no telephone
queue. Neither arrangement was designed by a security team; it is just how the work divides. And the
useful thing about it is that it holds *even when somebody is talked into something*. A caller who
persuades the intake handler that their claim must be paid today has persuaded a person who cannot pay
anything. The persuasion succeeded and the harm did not follow, because the capability was never in
that chair.

That is what separating capabilities buys, and it is why it beats every control that depends on
somebody deciding correctly.

This desk is built that way, and it has been since day 3, though the reason given then was not
security. The boundary was made a separate MCP server process because a boundary that is an import is
not a boundary — you cannot reason about what crosses it if crossing it is a function call. The
security consequence came free: two processes, and each one holds only what it needs.

Look at what each actually holds.

The **desk** holds the provider key. It runs models, so it needs one. It holds no claim files — it has
never opened `data/claims/` in its life, and its only route to a claim is asking the boundary. If the
desk's process is compromised, the attacker has a key to a model provider and a socket to a server
that answers five specific questions.

The **boundary** holds the claim files and the policy data. It runs no models. It has no key, and more
to the point it has no *code that could use one* — nothing in `claims_mcp/` imports the module that
reads secrets. If the boundary is compromised, the attacker has the claim files, which is bad, and no
ability to spend money on a provider, which matters because a stolen model key is a bill that arrives
whether or not anybody notices for a week.

Now the part that makes this a *mechanism* rather than an intention. There is exactly one place in this
project that turns a file on disk into a secret in memory: `claims_desk/util/keys.py`, written on day 1,
before there was anything to keep secret. Everything downstream of that is arithmetic. The boundary
cannot read a key not because it has been told not to, but because **it does not import the only code
that knows how**, and there is a test asserting it never will.

The strongest demonstration of this is not a test at all. It is deleting `.env` and watching the
boundary work perfectly.

## The mechanism

Move the key file out of the way entirely — `mv .env .env.away` — and start the boundary:

```
tools, with no .env on disk: ['fetch_policy', 'check_in_force', 'record_decision', 'read_decision', 'draft_letter']
fetch_policy, with no .env on disk: ['excess', 'expiry', 'fast_track_limit', 'found', 'inception', 'number', 'perils', 'product', 'status']
```

**Line by line:**

- **The boundary serves its whole docket with no key anywhere on the filesystem.** Not a degraded mode,
  not a warning, not a fallback. It never wanted one.
- **`fetch_policy` answers normally.** Every capability the boundary has is intact, because none of them
  had anything to do with a provider.
- **This is the demonstration to remember**, because it is a property of the system rather than an
  assertion about it. A test can be deleted. A process that has no code path to a secret is a different
  kind of statement.

And the desk, in the same state:

```
MissingKey: GOOGLE_API_KEY is not set: copy .env.example to .env and fill the value in
```

**Line by line:**

- `MissingKey` is day 1's own exception, and the message tells you what to do rather than what went
  wrong. That was day 1's argument: the person who hits this is a person setting the project up, and
  `KeyError: 'GOOGLE_API_KEY'` sends them reading source.
- **The name of the variable is in the message and its value never is.** `keys.require` returns the
  value to its caller and prints nothing, anywhere, ever.
- **The desk stops and the boundary does not**, which is the separation stated as behaviour: the same
  missing file is fatal to one process and irrelevant to the other.

Three tests pin it, and all three read this project's own source, which is unusual enough to
justify:

```bash
uv run pytest tests/test_security.py -q -p no:warnings -k "kit or key_file or holds_the_value"
```

```
...                                                                      [100%]
3 passed, 22 deselected in 7.20s
```

**Line by line:**

- The first walks every file in `claims_mcp/` and asserts none of them contains `util.keys` or
  `import keys`. **It tests an absence, and an absence cannot be tested any other way** — there is no
  behaviour to exercise, because the whole property is that a capability is not there.
- The second asserts that exactly two files in the project name the key file: `check.py`, which is the
  day-0 setup gate that checks the names are filled in, and `claims_desk/util/keys.py`, which is the
  one thing that reads it.
- The third distinguishes those two, because they are not the same kind of access: `check.py` contains
  no `os.environ` at all and says so in its own docstring — *nothing here reads the process
  environment* — so it can tell you a name is missing without ever holding a value.

That second test has a detail worth stealing, and it comes from getting it wrong first. The obvious
version searches every source file for the string `.env` and asserts only `keys.py` matches. It fails,
and the failure names `claims_desk/boundary.py`, which does not read the key file at all. The reason is
that `os.environ` contains `.env` as a substring. **The test now matches the quoted literal instead** —
`".env"` or `'.env'` — which is the difference between checking for a filename and checking for four
characters. A source-scanning test that matches too much gets loosened by whoever hits it next, and a
loosened test is one that stops catching the thing it was for.

## When it breaks

Somebody adds a feature to the boundary that needs a key — perhaps the server should classify a
document itself — and takes the shortest route to one:

```diff
 from claims_desk.domain import Outcome, Reason
 from claims_desk.store import Store
+from claims_desk.util import keys
 from claims_desk.util.logging import log
```

```
    def test_the_boundary_cannot_reach_the_key_because_it_never_imports_the_kit() -> None:
        """Two processes, two sets of powers. The boundary holds claim files; the key is not its
        business, and the way that is enforced is that it does not import the module that reads one."""
        for module in sorted((PROJECT / "claims_mcp").glob("*.py")):
            source = module.read_text(encoding="utf-8")
            assert "util.keys" not in source, module.name
>           assert "import keys" not in source, module.name
E           AssertionError: tools.py
E           assert 'import keys' not in '"""Every to...ft_letter)\n'
```

The `, module.name` on the assertion is why the message says `tools.py` — without it the failure would
say a string is contained in a blob and leave you grepping. A test that scans several files needs to
say which one, and a pytest assertion message is one argument away.

What went wrong is not the import. It is that a process which had one job now has two, and the second
one needs a credential the first never did. **The smallest fix is to delete the line.** The correct fix
is to ask why the boundary is classifying documents, and — if it genuinely must — to run that as a
third process with its own key and its own docket, rather than granting the file-holding process the
ability to spend money.

That is the general rule, and it is worth stating as a rule because the pressure to break it is
constant: **when a process needs a new kind of power, the question is whether it should be a new
process.** Merging is always easier in the moment, and it is how a system ends up with one component
that holds everything.

## In production

**What a senior writes instead.** No `.env` in either process. The desk gets its provider credential
from the platform's secret manager at start-up, with a short-lived token rather than a long-lived key,
and the boundary runs under an identity that can read the claims store and has no permission on the
provider account at all — so the separation is enforced by the infrastructure rather than by an import
graph. The import test stays anyway, because it fails in a pull request, and an IAM policy fails at
three in the morning.

**What degrades at scale.** One key, one process, one machine is a file. An insurer running this across
a claims estate has the desk in several regions, key rotation on a ninety-day cycle, and an auditor who
wants to know every principal that could have called the provider during a given week. At that point
`.env` is not a small solution, it is an unanswerable question — nothing records who read the file or
when. The property this part is really teaching survives the change of mechanism: **one place that
turns a credential into a value in memory**, whatever that place is.

**The review comment.** *"Both tests grep this project's own source. That is fine for the import test —
absence has to be tested that way — but `test_only_two_files_know_the_name_of_the_key_file` will fail
the first time somebody writes `.env` in a docstring, and the person it fails on will edit the
assertion rather than think about it. Consider restricting it to import and call sites."*

**The interview question.** *"Your agent service and your data service both run in the same cluster.
The agent service holds a model provider key. What does an attacker who lands in the data service get,
and what does the answer depend on?"*
