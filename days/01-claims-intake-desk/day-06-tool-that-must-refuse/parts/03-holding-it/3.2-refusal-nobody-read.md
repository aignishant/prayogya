## One-line answer

The desk reported four deficiencies and the claims directory was empty — because the boundary had
refused every write, as data, and nothing read the answer.

## The idea

A slip goes to records asking for a file to be marked closed. Records sends it back with a box
ticked: *reference not recognised.* The slip is in the return tray, correctly filled in, and nobody
looks in the return tray. At the end of the day the handler's own list says four files closed. None
of them are.

Nothing failed. Records did their job precisely, and said so, in writing. The failure is entirely in
the arrangement: **an answer was given and no part of the process was arranged to receive it.**

This is the exact failure this project shipped for about an hour while day 6 was being written, and
it is worth spelling out why it is the *right* failure for a day whose title is "a deficiency is an
answer, not an error".

Everything this day has argued for makes refusals into data. `record_decision` returns
`{"recorded": false, "refused": "..."}` rather than raising, because day 5 measured what an
exception loses on the way across a boundary. `draft_letter` returns `{"drafted": false}` for the
same reason. `PENDING` is a verdict rather than a gap.

All of which is correct, and all of which creates one new obligation: **if refusals are data, then
somebody has to read the data.** An exception forces a caller to deal with it. A returned refusal
does not force anything at all.

## The mechanism

The desk as it stood before this was found — the loop from `run_queue`, with the call and no check:

```python
    for notification in queue:
        verdict = await decide(notification)
        counts[verdict.outcome] += 1
        if verdict.decided:
            await boundary.record_decision(verdict.claim_id, verdict.outcome, verdict.reason)
```

**Line by line:**

- `counts[verdict.outcome] += 1` — **the count is incremented from the verdict**, which is a
  decision this process made, and not from anything the boundary said. That is the bug in one line:
  the desk is counting its own intentions.
- `await boundary.record_decision(...)` — **the return value is discarded.** It is not assigned, not
  checked, not logged. Written as a statement rather than an expression, it reads as an instruction
  being carried out, which is exactly what it is not: it is a request being made.
- **Nothing here is wrong in isolation.** Every function does what it promises, the boundary answers
  fully, the counts are computed from real verdicts. The gap is between two correct things.

Now make the boundary refuse. Send it a reason code it does not know — `no_date` instead of
`missing_date_of_loss`, which is exactly the kind of shortening somebody does — and run the queue:

```bash
uv run python -c "
import asyncio, json, pathlib
from claims_desk import desk
print('desk reports:', json.dumps(asyncio.run(desk.run_queue()), sort_keys=True))
d = pathlib.Path('data/claims')
print('claim files written:', sorted(p.name for p in d.glob('*.json')) if d.exists() else [])
"
```

```
desk reports: {"deficiency": 4, "fast-track": 0, "pending": 8}
claim files written: []
```

**Line by line:**

- `desk reports: {"deficiency": 4, ...}` — **the same summary as a healthy run.** Byte for byte the
  number this project has been quoting since part 1.1. Anything watching this output — a scheduler,
  a dashboard, a person — sees a successful batch.
- `claim files written: []` — **nothing.** Not three, not partially written, not corrupt. The
  boundary refused all four writes and the claim file is exactly as empty as it was before the run.
- **The boundary behaved perfectly.** It received four requests with an unrecognised reason code, it
  declined each one, and it said why: `unknown reason 'no_date'`. That refusal was returned four
  times and read zero times.
- **There is no error anywhere.** Not in the desk's exit status, not in the summary, not in an
  exception. The only trace is in the boundary's own log lines, on standard error, on the far side —
  and even those say `boundary.record_decision` with the arguments, not "and I refused".

The fix is four lines, and the comment is half of it:

```python
        if verdict.decided:
            written = await boundary.record_decision(
                verdict.claim_id, verdict.outcome, verdict.reason
            )
            # The boundary refuses a shape it does not recognise, and it refuses as *data*. A
            # caller that does not read the answer counts a decision it never recorded — which is
            # the failure this day exists to show. `recorded: false` here is not a claim outcome,
            # it is this desk sending something the boundary does not accept.
            if not written.get("recorded"):
                raise RuntimeError(
                    f"boundary refused to record {verdict.claim_id}: {written.get('refused')}"
                )
```

**Line by line:**

- `written = await boundary.record_decision(...)` — **assigned.** The single most important change:
  the call is now an expression with a value, and a value that is never used is something a reader
  notices.
- **The comment says what `recorded: false` means here**, and it is a distinction worth four lines.
  Everywhere else in this project a refusal is a legitimate answer about a claim. This one is not: it
  means *this desk sent something the boundary does not accept*, which is a defect in the desk.
- `if not written.get("recorded"):` — `.get`, not `[...]`, so a boundary that changed its answer
  shape produces a refusal rather than a `KeyError` inside the check that exists to catch problems.
- `raise RuntimeError(...)` — **raised, and this is the one place in the day where raising is
  right.** The distinction the whole day has been drawing: a refusal *about a claim* is data,
  because the caller can act on it; a refusal *about this program's own request* is a bug, and the
  caller cannot act on it except by being fixed.
- `f"boundary refused to record {verdict.claim_id}: {written.get('refused')}"` — the claim and the
  boundary's own words. The message the boundary produced is carried into the exception, so the
  reason survives even though it crossed the line as data.
- **The batch stops.** Twelve notifications, and this raises on the first refused write rather than
  continuing to produce eleven more decisions nobody will store. A batch that keeps going after
  discovering it cannot record anything is spending a minute and a half to produce a number that is
  not true.

## When it breaks

With the fix in place, the same break now escalates:

```
  File "C:\...\p01d\claims_desk\desk.py", line 119, in run_queue
    raise RuntimeError(
RuntimeError: boundary refused to record FNOL-4473: unknown reason 'no_date'
```

The path is shortened; the rest is verbatim. Read what it gives you: the claim that failed, the fact
that it was the boundary refusing rather than crashing, and **the boundary's own explanation of
what was wrong with the request.** That last part is the whole reason `refused` is a field in the
answer rather than a message in an exception on the far side — day 5 part 3.2 measured what happens
to those.

And a test now holds it. `test_a_refused_write_stops_the_batch_rather_than_being_counted` calls
through to the real boundary with a bad reason and asserts on the escalation, so the check cannot be
removed as tidy-up. Its docstring says what happened rather than what it checks, because the
what-happened is the reason anybody would keep it.

## In production

**What a senior writes instead.** The same check, and a rule applied to the whole codebase rather
than to one call site: **every boundary call's answer is read.** In a larger project that is a lint
rule or a return type that cannot be discarded — a result object the caller has to unwrap. What they
would not accept is the argument that made this bug: *the boundary validates, so the call is safe.*
The boundary validating is precisely why the call has an answer worth reading.

**What degrades at scale.** One unread refusal, on one desk, produced four missing claim files and a
summary that said otherwise. The property that makes this dangerous rather than merely wrong is that
**it scales silently**: a thousand notifications produce a thousand missing records and one
confident number. Reconciliation is how a real insurer finds this — the count of decisions against
the count of claim files, run daily — and the fact that this project has no such reconciliation is a
gap day 17 and day 18 will have to fill.

**The review comment.** *"`await boundary.record_decision(...)` with no assignment. That call
returns whether the write happened, and we refuse writes on four different grounds. Read it — and if
you think that cannot happen here, say which of the four grounds is impossible."*

**The interview question.** *"You decided that failures should be return values rather than
exceptions, for good reasons. Name the obligation that creates on every caller, and tell me how you
would enforce it across a codebase."*
