## One-line answer

`./run desk` processes the queue and prints one JSON summary, and the summary is the number this
project will be measured against from here to the ship day.

## The idea

At the end of the shift the counter closes and somebody writes three numbers on the board: taken,
settled, awaiting. Not a report — three numbers, in the same order, every day. The value is not in
any one evening's figures. It is that the same three numbers exist for yesterday, and for the same
Tuesday last year, and a change in the shape of them is visible without anybody analysing anything.

The desk now does real work, and this part gives it the one command that runs it and the one line
of output that says what happened. Everything about that line is chosen so it can be compared with
the same line tomorrow: the same keys, in every run, whether or not they are zero, as a machine
readable object rather than a sentence.

It is deliberately small. There is no report, no per-claim table, no progress bar. The per-claim
detail already exists — day 1's logger has been writing a `desk.decided` line for every notification
since part 1.1 — and duplicating it in the summary would create two accounts of the same run that
can disagree.

## The mechanism

The whole file, at `claims_desk/__main__.py`:

```python
"""Run the desk over the whole queue: `python -m claims_desk`.

Prints one line per notification and a summary. Everything it learns comes from the boundary; this
process opens no file except the notification queue itself.
"""

from __future__ import annotations

import asyncio
import json
import sys

from claims_desk.desk import run_queue

if __name__ == "__main__":
    counts = asyncio.run(run_queue())
    print(json.dumps(counts, sort_keys=True))
    sys.exit(0 if counts else 1)
```

**Line by line:**

- **`__main__.py` in `claims_desk`, mirroring `claims_mcp`.** Both packages are runnable, both with
  `python -m`, and the symmetry is not decoration: the desk and the boundary are two processes, and
  the way you start each of them is the same shape.
- **"Prints one line per notification and a summary"** — the per-claim lines are the logger's, on
  standard error, and the summary is this file's, on standard output. Two streams, two audiences:
  one for a person watching, one for whatever runs this.
- **"this process opens no file except the notification queue itself"** — a claim worth stating and
  worth checking. The queue is read by `Store`, everything else comes from the boundary, and by day
  19 the queue will move behind the boundary too.
- `asyncio.run(run_queue())` — one call, at the top level, and the only place in the desk that
  starts an event loop. Everything below is `async` and nothing below decides when to run.
- `print(json.dumps(counts, sort_keys=True))` — **JSON on standard output, sorted.** Sorted so two
  runs of the same shape produce byte-identical lines and a diff shows only what changed.
- `sys.exit(0 if counts else 1)` — **the honest version of a weak check**, and worth being clear
  about: `counts` is always a non-empty dictionary, so this always exits 0. It is a placeholder for
  a real verdict, and there is no verdict to give yet — the desk cannot say whether a run was
  *correct*, only what it did. Day 18's evalset is what makes this exit status mean something, and
  until then pretending otherwise would be worse.

And the driver gains a command. A **marked diff against the `run` printed on day 1 part 1.3**, with
day 3's and day 4's changes already in place:

```diff
     ./run mcp            the boundary, on stdio, until you stop it
     ./run mcp --http     the boundary, as a URL, until you stop it
+    ./run desk           decide every notification in the queue

     "mcp": [["uv", "run", "python", "-m", "claims_mcp"]],
+    "desk": [["uv", "run", "python", "-m", "claims_desk"]],
 }
```

**Line by line:**

- `"desk": [["uv", "run", "python", "-m", "claims_desk"]]` — one step, through `uv run`, like
  everything else. Because it is a single-step command, day 4's argument forwarding applies to it
  automatically.
- **`desk` is not added to `check`.** It takes a minute and a half and it writes claim files; a gate
  has to be fast and has to leave nothing behind. The tests exercise the same code in-process, which
  is part 3.1.
- **Nothing was removed from `PLANNED`.** `serve`, `eval` and `up` are still unbuilt, and `desk` was
  never listed there — it is a command this project did not know it needed until the desk existed,
  which is a fair description of most commands.

Run it:

```bash
./run desk
```

```
--- uv run python -m claims_desk
{"deficiency": 4, "fast-track": 0, "pending": 8}

OK desk
```

**Line by line:**

- `--- uv run python -m claims_desk` — the driver echoing the command, from day 1.
- `{"deficiency": 4, "fast-track": 0, "pending": 8}` — **alphabetical, because of `sort_keys`**, so
  the interesting number is not first. That is a fair trade for two runs being comparable with a
  plain text diff.
- **The per-claim log lines are not shown here** because they went to standard error, which the
  driver passes straight through to your terminal. Running `./run desk 2>/dev/null` leaves exactly
  the one summary line, and `./run desk >/dev/null` leaves exactly the twelve decisions. That
  separation is day 1's decision to log to standard error, paying off for the third time.
- `OK desk` and exit status 0 — the driver's verdict, which today means "the command finished"
  rather than "the run was correct".

## When it breaks

The queue is read from `data/notifications.json` by `Store`, and the desk assumes it is there. Move
it, and the failure arrives from a layer that has nothing to do with claims:

```bash
mv data/notifications.json data/notifications.json.bak && ./run desk 2>&1 | tail -4
```

```
FileNotFoundError: [Errno 2] No such file or directory: 'C:\\...\\p01d\\data\\notifications.json'

FAIL desk: `uv run python -m claims_desk` exited 1
```

The path is shortened; the rest is verbatim. Two things are worth noticing. The driver reported the
failure with the command and its exit status, which is day 1's `run` doing its job — the traceback
is ugly and the line under it is not. And **the desk crashed on the one file it still opens for
itself.** Every other piece of data it uses comes from the boundary, where a missing store would be
the boundary's problem to report; this one is the desk's, because the queue has not moved behind the
line yet. That asymmetry is a rep in the hub, and putting it right is what makes `claims_desk` a
process that owns nothing at all.

## In production

**What a senior writes instead.** The same entry point, with the summary emitted as a structured log
record rather than printed — so it lands in the same place as everything else and can be graphed
without anybody parsing standard output. They would also make the exit status mean something: a run
where every notification was pending is a working batch by this file's definition and an outage by
any useful one.

**What degrades at scale.** One process, one queue, start to finish, and a minute and a half for
twelve. A morning's real intake is several hundred, which at this rate is well over an hour of
mostly waiting for subprocesses — and if it fails at notification four hundred, it starts again from
the beginning, because nothing records where it got to. Day 15's checkpoints are that, and the shape
of this file is what makes them possible to add: the loop is in one function and the summary is a
dictionary.

**The review comment.** *"`./run desk` writes claim files and takes ninety seconds. Do not put it in
`check` — and while you are here, say in the docstring whether running it twice is safe. Somebody is
going to."*

**The interview question.** *"Your batch command prints a summary and exits zero. What would you
have to know before you would let a scheduler run it unattended overnight?"*

## Check yourself

- **Run:** `./run desk 2>/dev/null` and then `./run desk >/dev/null`. Expect one JSON line from the

- **Say out loud:** The exit status is always zero. Name the two things that would have to exist
