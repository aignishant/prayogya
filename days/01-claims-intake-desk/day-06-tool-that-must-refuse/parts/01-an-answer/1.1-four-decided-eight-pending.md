## One-line answer

The desk runs over all twelve notifications and decides four of them, and the honest answer for the
other eight is `pending` with a note saying what it is waiting for — which is the same shape as a
deficiency letter, pointed at the desk instead of the policyholder.

## The idea

There are two trays behind the intake counter. One is **out** — decided, letter written, gone. The
other has a card taped to it that says *awaiting information*, and it is the larger of the two on
most days.

The second tray is not a failure tray. Nobody looks at it and thinks the desk is broken. It is the
ordinary state of an intake desk: a claim arrives incomplete, somebody writes to ask for the
missing thing, and the file waits. **The work of the desk is mostly the second tray**, and a desk
that could not put anything in it would have to guess instead.

Today the desk runs for the first time, over the real queue, and discovers that it has a second
tray of its own.

Four of the eight rules from day 2 read fields: is there a date of loss, is there a contact, does
the policy exist, was it in force. The desk can apply those with nothing but the notification and
the boundary. The other four need somebody to have read the sentence the caller spoke — which peril
this is, and whether anyone was hurt — and day 2 part 3.2 is the proof that a keyword scan is not
that somebody.

So the desk decides what it can and refuses to decide the rest. **Refusing is the answer**, and it
comes back in the same shape a deficiency does: a verdict, with a field saying what is missing. The
only difference is who is being asked for something. A deficiency says *the policyholder must send
a photograph*. A pending verdict says *this desk must be given a classification*.

## The mechanism

The whole file, at `claims_desk/desk.py`:

```python
"""The desk itself: read the queue, ask the boundary, decide what can be decided.

This is the first module that does the actual work of an intake desk, and the first one that finds
out where its own knowledge stops. Four of this project's eight rules read fields; four of them
need somebody to have read the sentence a caller spoke. Until something can do that, the desk can
reach a verdict on some notifications and must refuse to reach one on the rest.

Refusing is not a failure here. `PENDING` is an answer with a reason attached, in exactly the shape
a deficiency letter has — which is the point day 6 is about.
"""

from __future__ import annotations

from dataclasses import dataclass

from claims_desk import boundary
from claims_desk.domain import Notification, Outcome, Reason
from claims_desk.store import Store
from claims_desk.util.logging import log

#: The verdict for a notification this desk cannot decide with the facts it has.
PENDING = "pending"

#: What a pending notification is waiting for. Not an error code: a description of the missing
#: input, so that whatever supplies it later knows what it is being asked for.
NEEDS_CLASSIFICATION = "needs_classification"


@dataclass(frozen=True)
class Verdict:
    """What the desk concluded about one notification, and why.

    `outcome` is a member of `Outcome`, or `PENDING`. A pending verdict carries `waiting_for`
    instead of `reason`: the first says what the desk needs, the second says what the
    policyholder needs to send.
    """

    claim_id: str
    outcome: str
    reason: str | None = None
    waiting_for: str | None = None

    @property
    def decided(self) -> bool:
        return self.outcome != PENDING


def rules_that_need_no_reading(
    notification: Notification, policy_found: bool, in_force: bool | None
) -> Reason | None:
    """The four rules that read fields, in the order day 2 fixed. `None` means they all passed.

    Deliberately not `assess`: that function takes a loss type and an injury flag, and this desk
    has neither yet. Duplicating the *order* here rather than the rules is the compromise, and it
    is a real one — day 7 deletes this function and calls `assess` with the model's answers.
    """
    if notification.date_of_loss is None:
        return Reason.MISSING_DATE_OF_LOSS
    if not notification.contact_ref:
        return Reason.MISSING_CONTACT
    if not policy_found:
        return Reason.UNKNOWN_POLICY
    if in_force is False:
        return Reason.POLICY_NOT_IN_FORCE
    return None


async def decide(notification: Notification) -> Verdict:
    """Reach a verdict on one notification, using only the boundary and the rules that read fields.

    Two boundary calls at most: the policy lookup, and the in-force question when there is a date
    to ask about. Both go over the process line; nothing here opens a file.
    """
    policy = await boundary.fetch_policy(notification.policy_number)
    in_force: bool | None = None
    if policy.get("found") and notification.date_of_loss is not None:
        answer = await boundary.check_in_force(
            notification.policy_number, notification.date_of_loss
        )
        in_force = bool(answer.get("in_force"))

    reason = rules_that_need_no_reading(notification, bool(policy.get("found")), in_force)
    if reason is not None:
        verdict = Verdict(notification.id, Outcome.DEFICIENCY, reason=reason.value)
    else:
        verdict = Verdict(notification.id, PENDING, waiting_for=NEEDS_CLASSIFICATION)

    log(
        "desk.decided",
        claim=verdict.claim_id,
        outcome=verdict.outcome,
        reason=verdict.reason,
        waiting_for=verdict.waiting_for,
    )
    return verdict


async def run_queue(store: Store | None = None) -> dict[str, int]:
    """Decide every notification in the queue and record the ones that were decided.

    Returns a count per outcome. A pending verdict is **not** written to the claim file: the desk
    has not decided anything about that claim, and a claim file saying `pending` would be a
    decision about a claim nobody has looked at.
    """
    queue = (store or Store()).notifications()
    counts = {Outcome.FAST_TRACK.value: 0, Outcome.DEFICIENCY.value: 0, PENDING: 0}
    for notification in queue:
        verdict = await decide(notification)
        counts[verdict.outcome] += 1
        if verdict.decided:
            written = await boundary.record_decision(
                verdict.claim_id, verdict.outcome, verdict.reason
            )
            # The boundary refuses a shape it does not recognise, and it refuses as *data*. A
            # caller that does not read the answer counts a decision it never recorded — which is
            # the failure this day exists to show. `recorded: false` here is not a claim outcome,
            # it is this desk sending something the boundary does not accept.
            if not written.get("recorded"):
                raise RuntimeError(
                    f"boundary refused to record {verdict.claim_id}: {written.get('refused')}"
                )
    log("desk.queue_finished", **counts)
    return counts
```

**Line by line:**

- **The module docstring says where the desk's knowledge stops**, in the file that would otherwise
  look complete. Somebody opening this in a month sees the limitation before they see the code, and
  is much less likely to paper over it.
- `PENDING = "pending"` — **a string constant beside the `Outcome` enumeration rather than in it.**
  That is deliberate: `Outcome` is what the desk *decides*, and pending is the absence of a
  decision. Adding it to the enumeration would let it be written into a claim file, and day 2's
  `assess` would have to grow a case for something that is not an outcome.
- `NEEDS_CLASSIFICATION = "needs_classification"` — what the desk is waiting for. Its comment says
  **"not an error code: a description of the missing input"**, which is the whole day in one line.
- `@dataclass(frozen=True) class Verdict` — frozen, like the domain records from day 2. A verdict is
  reached once; a verdict that could be edited afterwards is a decision with no moment.
- `reason: str | None` **and** `waiting_for: str | None` — two optional fields, and never both. The
  docstring says why they are separate: *the first says what the desk needs, the second says what
  the policyholder needs to send*. Collapsing them into one `why` field would save a line and lose
  the distinction that the day is about.
- `@property def decided(self) -> bool: return self.outcome != PENDING` — one place where the
  question is asked, so `run_queue` reads as English and no caller compares to the constant by hand.
- `def rules_that_need_no_reading(...)` — **the honest name.** Not `partial_assess`, not
  `quick_rules`: the name says exactly which subset of the rules these are and why they are a
  subset.
- **Its docstring admits a compromise**: the *order* of these four rules is duplicated from day 2's
  `assess`, and if somebody reorders one and not the other, the desk and the tests disagree about
  which reason a notification gets. That is a real cost, it is written down where it will be seen,
  and it names the day that removes it.
- `in_force: bool | None` — **three states, and they are all needed.** `True` and `False` are
  answers; `None` means the question was never asked, because there was no date of loss or no
  policy to ask about. `if in_force is False` rather than `if not in_force` is the line that keeps
  them apart.
- `policy = await boundary.fetch_policy(...)` — **the first line of real work in this project, and
  it goes over a process line.** The desk has no `Store` for policies. It asks.
- `if policy.get("found") and notification.date_of_loss is not None:` — the second boundary call is
  **conditional**, because asking whether an unknown policy was in force on a date that does not
  exist is two nonsense questions. This is the rule ordering from day 2 showing up as call
  avoidance.
- `answer.get("in_force")` — reading the field the tool promised. Not `answer["in_force"]`: the
  answer may be a `{"found": false}` shape, and `.get` returning `None` is the right value for "not
  asked".
- `Verdict(notification.id, Outcome.DEFICIENCY, reason=reason.value)` — `.value` because the claim
  file holds strings, and the enumeration member is converted once, here, at the point where the
  verdict becomes data.
- `log("desk.decided", ...)` with **all four fields, including the nulls** — every notification
  produces exactly one line with the same keys, so the log can be grouped and counted. A log line
  that omits its empty fields cannot be aggregated without knowing which fields to expect.
- `counts = {Outcome.FAST_TRACK.value: 0, Outcome.DEFICIENCY.value: 0, PENDING: 0}` — **all three
  keys initialised**, so a run with no fast-tracks reports `0` rather than omitting the key. The
  difference matters the first time something reads this summary and asks why a field vanished.
- `if verdict.decided:` — **pending verdicts are not written.** The docstring gives the reason and
  it is worth restating: a claim file saying `pending` is a record of a decision, and no decision
  was made. The absence of a claim file is the correct representation of "not yet looked at", and
  day 5's `read_decision` already answers `{"found": false}` for exactly that.
- `written = await boundary.record_decision(...)` and `if not written.get("recorded")` — **the
  answer is read.** The boundary refuses a shape it does not recognise, and it refuses as data; a
  caller that ignores the return value counts decisions it never recorded. Part 3.2 is that failure,
  and this check exists because it happened.
- `raise RuntimeError(f"boundary refused to record {verdict.claim_id}: ...")` — **raised, not
  logged.** A refusal here is not a claim outcome: it means this desk sent something the boundary
  does not accept, which is a bug in the desk, and the batch stops rather than continuing to produce
  decisions nobody will store.

- **Eight pending**, which is two thirds of the queue. The desk looked at every one of them, applied
  everything it knows, and stopped short of a verdict — with a field saying what it is waiting for.
- **`PROJECT.md` promised four fast-tracks and eight deficiency letters.** This is not that, and the

## When it breaks

The desk asks the boundary about a policy on every notification, and asks a second time when there
is a date. Twelve notifications, up to two calls each, plus a write for the four decided: about
twenty-eight round trips, and every one of them opens a connection. Time it:

```
{"fast-track": 0, "deficiency": 4, "pending": 8} in 91.4s
```

Verbatim. **Ninety-one seconds to process twelve claims.**

Nothing is broken. Every part of this is behaving as designed, and the design is the problem: day 4
part 2.1 wrote `fetch_policy` as a connection per call and said in its own docstring that this was
temporary. On stdio a connection is a **subprocess** — a Python interpreter starting, importing the
MCP SDK, building the server, answering one question and exiting — and twenty-eight of those is a
minute and a half.

Somebody would find this by running the desk for the first time on a real morning's queue and
watching it not finish. The smallest fix is the HTTP transport, which removes the interpreter
startup and leaves the connection setup. The real fix is one connection for the whole run, and it is
day 9's, because that is where the desk stops making one call at a time.

## In production

**What a senior writes instead.** The same shape, with the queue processed concurrently and one
connection shared across it — and, more importantly, with the pending verdicts going somewhere. A
count of eight in a summary is a number; eight claims sitting in a tray with nothing scheduled to
look at them again is a backlog. What this desk lacks is not the classification, it is a way to
re-run a pending notification when the missing input arrives.

**What degrades at scale.** Two thirds pending is fine for one run and is a queue that grows on
every run. At several hundred notifications a day it is several hundred claims a day accumulating,
and the thing that breaks first is not the software: it is that the pending tray becomes the largest
object in the system and nobody owns it. Every intake system that fails, fails here rather than at
the decision logic.

**The review comment.** *"`run_queue` counts a pending verdict and moves on. Where does that
notification go? If the answer is 'we run the batch again tomorrow', say so in the docstring — and
say what happens to a claim that is pending for the ninth day running."*

**The interview question.** *"Your system can decide two thirds of nothing and one third of
everything. How do you represent the cases it cannot decide, and what is the difference between
that representation and an error?"*
