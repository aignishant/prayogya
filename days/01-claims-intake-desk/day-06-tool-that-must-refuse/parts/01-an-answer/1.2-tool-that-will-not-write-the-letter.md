## One-line answer

`draft_letter` returns the claim, the one reason, what the policyholder must send and the house
style — and `drafted: false`, because this boundary has no model and will not invent prose that
goes out on an insurer's paper.

## The idea

A letter leaving a claims department has the company's name at the top of it. That is the whole
reason the department has a house style, a sign-off procedure and a person whose job includes
reading letters before they go: **the letter is the company speaking**, and a sentence in it that
promises something the company did not mean is a sentence the company said.

So there is a rule about the pad of standard wordings. You may take a wording from it. You may fill
in the boxes. You may not write a new paragraph and put it on the letterhead because the standard
one did not quite fit — that goes back to whoever owns the wording.

`draft_letter` is a tool that follows the same rule, and it is the day's title made literal. It is
asked to draft a letter. It has everything a letter needs: the claim, the reason, the thing to ask
for, and the house style — which lives on this same boundary as the prompt day 4 declared. And it
returns all of that with `drafted: false`, because **it cannot write, and a tool that cannot do
something must say so rather than produce something.**

There is a second thing in this part, and it is not decoration. The mapping from a reason code to
*what the policyholder must actually send* is domain knowledge — real wording, written by the people
who answer for the letters — and it lives behind the boundary with the claim file rather than in the
desk that happens to be asking. That is the same argument day 4 made for the prompt, applied to
data.

## The mechanism

Three additions to `claims_mcp/tools.py`. This is a **marked diff against the whole file as printed
on day 5 part 1.1**; everything above `WHAT_IS_NEEDED` is unchanged:

```python
#: What a policyholder has to send or confirm, for each way a claim can fall short. Written by the
#: department that answers for the letters, which is why it lives behind the boundary with the
#: claim file rather than in the desk that happens to be asking.
WHAT_IS_NEEDED: dict[str, str] = {
    Reason.MISSING_DATE_OF_LOSS: "the date the loss happened, even approximately",
    Reason.MISSING_CONTACT: "a telephone number or address we can reply to",
    Reason.UNKNOWN_POLICY: "the policy number from your schedule or renewal letter",
    Reason.POLICY_NOT_IN_FORCE: "confirmation of which policy was in force on that date",
    Reason.PERIL_NOT_COVERED: "nothing — this loss is not covered by the policy you hold",
    Reason.MISSING_PHOTO_REFERENCE: "a photograph of the damage",
    Reason.INJURY_REPORTED: "nothing — an adjuster will call you about the injury",
    Reason.ABOVE_FAST_TRACK_LIMIT: "nothing — an adjuster will review the estimate",
}


def draft_letter(claim_id: str, reason: str) -> dict[str, Any]:
    """Assemble everything needed to write a deficiency letter, and write none of it.

    Returns the claim, the one reason, what the policyholder must send, and the house style — with
    `drafted: false`, because nothing was drafted. **This boundary has no model and will not invent
    prose that goes out on an insurer's paper.** Whoever asked has the materials and the
    instructions; the writing is theirs, and so is the responsibility for it.

    Args:
        claim_id: The notification reference, for example `FNOL-4477`.
        reason: One of the desk's reason codes, for example `missing_photo_reference`.
    """
    log("boundary.draft_letter", claim=claim_id, reason=reason)
    if reason not in set(Reason):
        return {"drafted": False, "refused": f"unknown reason {reason!r}"}
    return {
        "drafted": False,
        "why": "this boundary has no model; the letter is written by the caller",
        "claim_id": claim_id,
        "reason": reason,
        "needed": WHAT_IS_NEEDED[reason],
        "house_style": "see the deficiency_letter prompt on this server",
    }


#: The docket, in the order a client is shown it. Registration happens in `server.py`; keeping the
#: list here means the file that defines the tools is also the file that says which are declared.
DECLARED = (fetch_policy, check_in_force, record_decision, read_decision, draft_letter)
```

**Line by line:**

- `WHAT_IS_NEEDED: dict[str, str]` — **keyed by `Reason`, which is a `StrEnum`**, so the members and
  their string values are interchangeable as keys. A caller sending the string `"missing_contact"`
  finds the same entry the enumeration member does.
- **Its comment says where it lives and why**: written by the department that answers for the
  letters. That sentence is the difference between this being reference data and being a hard-coded
  string somebody put in the nearest file.
- `"the date the loss happened, even approximately"` — **"even approximately" is the whole value of
  the line.** FNOL-4473's caller genuinely does not know the day; a letter demanding an exact date
  gets no reply, and a letter saying "even approximately" gets one. Nobody writing code would think
  of that clause. Somebody who has taken these calls would.
- `"nothing — this loss is not covered by the policy you hold"` — **three of the eight entries ask
  for nothing**, and they are the three where the deficiency is not the policyholder's to fix: not
  covered, an injury reported, an estimate over the limit. A letter that asks for a photograph when
  the answer is "an adjuster will call you" is worse than no letter.
- **Every one of the eight is present**, and part 3.1 asserts it. A reason code with no line here
  produces a letter that names a problem and asks for nothing, which is the most annoying document a
  claims department can send.
- `def draft_letter(claim_id: str, reason: str) -> dict[str, Any]:` — on the docket, so a model can
  reach it, with two string parameters and a description a stranger can act on.
- **"Assemble everything needed to write a deficiency letter, and write none of it."** — the first
  line, and it is doing something unusual: it tells the caller what the tool will *not* do, in the
  sentence the model chooses on. A model that reads this does not call it expecting prose.
- **"will not invent prose that goes out on an insurer's paper"** — the reason, in the docstring,
  where it survives. Somebody adding a model to this boundary later has to read past that sentence
  to do it.
- `if reason not in set(Reason): return {"drafted": False, "refused": ...}` — **a refusal, as data**,
  in the shape day 5 established. An unknown reason code is a bad request from a caller, not an
  error in the boundary, and it comes back with `drafted: false` like everything else this tool
  returns.
- `"drafted": False` **on both paths** — the successful path and the refused one. A caller checks
  one field and never has to distinguish "it refused" from "it worked and drafted nothing", because
  those are the same thing.
- `"why": "this boundary has no model; the letter is written by the caller"` — **the reason travels
  with the answer.** Day 5 part 3.2's lesson: an exception's message is destroyed at the boundary, so
  anything the caller needs to understand has to be a field.
- `"needed": WHAT_IS_NEEDED[reason]` — the sentence the letter must contain, chosen by the boundary
  rather than by whoever is writing. The caller cannot get this wrong by paraphrasing, because it is
  handed to them.
- `"house_style": "see the deficiency_letter prompt on this server"` — **a pointer to the prompt
  from day 4**, on the same server. The tool does not duplicate the wording rules; it says where
  they are, and a client that has the docket also has the prompt list.
- `DECLARED = (..., draft_letter)` — the fifth entry. Adding it moved the boundary's version to
  `0.4.0` and took two test assertions with it, which is part 3.1.

```bash
asyncio.run(main())
```

```
  "house_style": "see the deficiency_letter prompt on this server"

```

**Line by line:**

- `"drafted": false` **first in the answer**, because it is the field that changes what the caller
  does next.
- `"why"` immediately after it — a caller reading top to bottom learns that nothing was drafted and
  why, before reaching anything they might mistake for a letter.
- `"needed": "a photograph of the damage"` — the actionable sentence, for this specific reason. This
  is what will end up in the letter, whoever writes it.
- **There is no prose in this answer at all.** No greeting, no paragraph, no "we regret". The tool
  was asked to draft a letter and returned materials, and the difference is visible at a glance.
- `is_error` on this call is `false`. **Refusing to draft is not a failure**: the call worked, the
  boundary answered fully, and the answer is "not by me".

## When it breaks

Send a reason code the boundary does not know:

```bash
uv run python -c "
import asyncio, json
from claims_desk import boundary
print(json.dumps(asyncio.run(boundary.call('draft_letter', {'claim_id':'FNOL-4477','reason':'no_photo'}))))
"
```

```
{"drafted": false, "refused": "unknown reason 'no_photo'"}
```

Verbatim, from this project. `no_photo` is a perfectly reasonable thing for somebody to write — it
is shorter than `missing_photo_reference` and means the same to a person — and the boundary does not
accept it, because `WHAT_IS_NEEDED` has no entry for it and a letter with a blank in the middle is
worse than no letter.

What makes this the right failure rather than an annoying one: **the answer names the value it
rejected.** A caller — including a model — can compare `'no_photo'` against the reason codes it was
given and correct itself. Compare with what would happen if this raised: day 5 part 3.2 measured
that, and the caller would receive `Error executing tool draft_letter` and nothing else.

## In production

**What a senior writes instead.** The same tool, and the letter itself generated somewhere that has
a model, a review step and a record of what went out. The rule they would fight for is the one this
tool encodes: **the component that owns the data owns the wording about the data**, and the
component that owns neither must not be the one composing sentences on the company's paper. In a
regulated line of business that is not an architectural preference; it is who gets asked to explain
a letter.

**What degrades at scale.** Eight reason codes and eight sentences fit in one dictionary that a
person can read. At forty codes across three products it becomes a table somebody maintains, and the
failure mode is a code with no sentence — which produces a letter that names a problem and asks for
nothing. That is why part 3.1 asserts the mapping is total rather than trusting it, and why the
assertion iterates the enumeration rather than the dictionary.

**The review comment.** *"`draft_letter` builds the sentence with an f-string and returns it as
`letter`. That is prose, on our paper, composed by a function nobody reviews. Return the materials
and let the thing with a model write it — and put the wording rules in the prompt where the legal
team can find them."*

**The interview question.** *"A tool of yours is asked to do something it cannot do. What does it
return, and how does the caller tell that apart from the tool having done the thing badly?"*
