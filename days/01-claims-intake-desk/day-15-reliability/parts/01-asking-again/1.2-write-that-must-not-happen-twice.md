## One-line answer

A read may be repeated and a write may not, so every decision this desk records carries a key
derived from the decision itself — the same write twice lands once, and a *different* decision about
the same claim is refused rather than quietly overwriting the first.

## The idea

Part 1.1 retried a classification, and nothing about that was dangerous: asking the same question
twice costs a call and produces an answer.

Recording a decision is not like that. A retry there is a second write, and the interesting failure
is not "it failed twice" — it is the one where the **first attempt succeeded and the caller never
found out.** The write lands, the connection drops before the answer comes back, the retry fires, and
now there are two.

For this desk, "two" would mean two claim files if the store appended, or one file written twice if
it does not. Day 6's store overwrites by claim reference, so the visible damage is small — and that
is exactly why this is worth building now, while the damage is small, rather than on the day the
store becomes something that appends.

The fix has a name and a shape. An **idempotency key** is a name for one intended write, the same
every time that write is intended. The receiver keeps the key with what it wrote; a second arrival
carrying a key it already has is a repeat, and it says so rather than writing again.

Two decisions inside that, and they are the ones people get wrong.

**Where the key comes from.** From the write's own content, hashed — not a counter, not a timestamp,
not a random value generated per attempt. A random key makes every retry a new write, which is the
bug with extra steps. A key derived from the content has the property that matters in both
directions: two attempts at the same decision agree, and **a different decision about the same claim
produces a different key**, so the mechanism cannot hide a real change.

**Where the check happens.** At the receiver, against what it stored — not at the sender, against a
set of keys it has sent. A sender's memory answers for this process; after a restart it is empty, and
the question a retry actually asks is whether the *store* has the write.

## The mechanism

The key, from `claims_desk/reliability.py`, printed whole in part 1.1:

```python
def idempotency_key(claim_id: str, outcome: str, reason: str | None, letter: str | None) -> str:
    """A name for one intended write, the same every time the same write is intended.

    Derived from the write's own content rather than from a counter or a clock: two attempts at the
    same decision produce the same key, and a *different* decision about the same claim produces a
    different one. That second half is what stops the key hiding a real change.

    Sixteen hex characters of SHA-256. Not a security boundary — nothing here is defending against
    an attacker choosing inputs — just a short, stable name that fits in a log line.
    """
    payload = json.dumps(
        {"claim_id": claim_id, "outcome": outcome, "reason": reason, "letter": letter},
        sort_keys=True,
    )
    return hashlib.sha256(payload.encode("utf-8")).hexdigest()[:16]
```

**Line by line:**

- **Four arguments, and they are the whole of what a decision is** — the claim, the outcome, the
  reason and the letter. Day 14's `DecisionRecord` is not in here, and that is deliberate: the record
  contains provenance, provenance contains call counts, and call counts differ between a first
  attempt and a retry. Hashing it would give every retry a new key.
- `json.dumps(..., sort_keys=True)` — **a canonical form.** Two dictionaries with the same contents
  in a different order must hash the same, and `sort_keys` is the cheapest way to promise that.
- **JSON rather than an f-string of the four values.** A letter containing the separator character
  would collide with a differently-split decision; JSON escapes and quotes, so the encoding is
  unambiguous.
- `hashlib.sha256(...).hexdigest()[:16]` — **truncated deliberately**, and the docstring says why it
  is safe to truncate: nothing here is defending against an attacker choosing inputs. Sixteen hex
  characters fits in a log line and is far beyond collision by accident.
- **The docstring's second paragraph is the design's real content.** The first half of the property
  — same write, same key — is what everybody builds. The second half — different decision, different
  key — is what stops the mechanism from silently swallowing a change.

**Line by line:**

- `idempotency_key: str | None = None` — **optional, like every parameter this tool has gained.** Day
  6's tests and anything written before today keep working, and part 3.1 asserts a write without one
  is still accepted.
- **The check is placed after the shape refusals and before the write.** An unknown outcome should be
  reported as an unknown outcome, not as an idempotency problem — the same ordering argument day 9
  made when it added the letter refusal.
- `existing = store.claim(claim_id)` — **the store, on every call.** A dictionary of seen keys would
  be faster and would answer the wrong question after a restart, which is the exact circumstance a
  retry is most likely to be running in.
- `if existing and existing.get("idempotency_key") == idempotency_key:` — **the repeat case**, and it
  returns `recorded: True`. That matters: the caller asked for the decision to be recorded and it is
  recorded. Returning a failure would make a successful retry look like an error.
- `"repeat": True` **as an extra field** — so a caller that cares can tell, and one that does not can
  treat it as an ordinary success. Day 5's shape: refusals and outcomes are data.
- `log("boundary.record_decision.repeat", ...)` — **a repeat is worth a line.** It is evidence that a
  retry happened somewhere upstream, which is otherwise invisible from the boundary's side.
- `if existing and existing.get("idempotency_key"):` **without a key match** — **a different
  decision, refused.** Not overwritten and not quietly accepted: a claim that has been decided is
  decided, and changing it is a thing a person does deliberately.
- **The second condition tests that the *existing* record has a key at all**, so a claim written
  before today — with no key — can still be decided. That is the migration this project actually
  needs, in one clause.
- `record["idempotency_key"] = idempotency_key` — **stored beside the decision**, which is what makes
  `already_written` able to ask the store rather than a cache.

**Line by line:**

- **The key is computed from the same four values that are then sent.** Not from the verdict object,

**Line by line:**

- **Two different keys for two different decisions about one claim.** `ce7b0595e2a460d8` and
  `c84e7a056754e7c4` — the content decides the name, so the mechanism can tell a repeat from a
  change.
- `first write : {'recorded': True, ...}` **with no `repeat` field.** The first write is an ordinary
  write and says nothing about idempotency.
- `same again : {'recorded': True, 'repeat': True, ...}` — **success, and it says it did not write
  again.** A caller retrying after a dropped connection gets exactly what it needed: confirmation
  that the decision is recorded.
- `a real change : {'recorded': False, 'refused': ...}` — **refused, as data**, in the shape every
  refusal in this project has used since day 5. Not an exception, not an overwrite.
- `claim files : 1` — **one file, three calls.** That is the whole promise.

## When it breaks

Take the key out — retry the write without one, which is what the code did until today:

```bash
uv run python -c "
import asyncio, json, pathlib
from claims_desk import boundary

async def main():
    await boundary.record_decision('FNOL-4471', 'fast-track')
    await boundary.record_decision('FNOL-4471', 'deficiency', 'injury_reported')
    stored = json.loads(pathlib.Path('data/claims/FNOL-4471.json').read_text(encoding='utf-8'))
    print('after two writes with no key:', stored)

asyncio.run(main())
"
```

```
after two writes with no key: {'claim_id': 'FNOL-4471', 'outcome': 'deficiency', 'reason': 'injury_reported'}
```

Verbatim, from this project. **The second write won.** No error, no warning, and a claim that was
fast-tracked is now a deficiency — with day 14's decision record, if one had been sent, replaced
along with it.

Notice what this is not. It is not the retry bug: nothing here retried anything. It is the *general*
version, of which the retry bug is one instance — **any second write to a decided claim silently
replaces the first**, whether it came from a retry, a re-run of the queue, two processes working the
same morning, or somebody testing in production.

The key does not fix that by preventing writes. It fixes it by making the two cases distinguishable:
same decision arriving twice is a repeat and is fine; different decision arriving second is a change
and is refused. Without a key the boundary cannot tell them apart, so it treats both as fine.

The smallest fix is passing the key, which this desk now always does. The uncomfortable part is the
migration: every claim written before today has no key, so the second condition lets a keyless record
be overwritten once. That is deliberate and it is a real gap — a claim from last week can still be
silently replaced. Closing it means backfilling keys, which is a `TODO(me)` in the hub with the
reason it was not done here.

## In production

**What a senior writes instead.** The same key, with the write made conditional at the storage layer
— a compare-and-set, or a unique constraint on `(claim_id, idempotency_key)` — rather than a read
followed by a write. This version has a race: two processes can both read "no existing record" and
both write. It does not matter here, because `run_queue` is one process working one queue, and it
would matter the moment there are two workers.

**What degrades at scale.** The read before every write doubles the boundary calls for the write
path — this desk makes 42 subprocess launches for twelve claims and this makes it more. That is the
cost of asking the store rather than a cache, it is the right trade at this size, and the thing that
changes at a morning's several hundred notifications is not the count but the round trip: a
conditional write does it in one.

**The review comment.** *"The key includes the letter, so re-running a claim after a wording change
is a different write and gets refused. Is that what we want? I think it is — but somebody is going
to hit it during a prompt rollout and call it a bug, so write down that it is intentional."*

**The interview question.** *"Your service retries a write and the first attempt actually succeeded.
Describe the key you would use, where you would check it, and what you would return on the second
arrival."*

## Check yourself

- **Run:** the three writes. Then change the letter on the second one and say which of the three
  outcomes you would expect.
- **Say out loud:** the key is derived from content rather than generated per attempt. Say what a
  random per-attempt key would do to a retry, and what a per-claim constant key would hide.
