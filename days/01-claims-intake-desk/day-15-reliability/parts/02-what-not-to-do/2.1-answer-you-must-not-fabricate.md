## One-line answer

Every graceful degradation available to this desk — a default classification, a cheaper model, a
similar claim's answer — produces a decision that day 14's record cannot honestly describe, so the
desk escalates instead and says what it was waiting for.

## The idea

Three attempts have failed. The queue has eleven more claims. Something has to happen.

The pressure at this exact moment is the whole subject of this part, because every option that feels
like engineering is a way of deciding a claim without an answer.

**Assume the safe default.** Classify it as a peril the policy does not cover, so the claim goes to a
deficiency and a human sees it. Conservative, reversible, and it writes `peril_not_covered` into a
decision record — a sentence saying this policy does not cover this loss, which nobody established
and which is very possibly untrue.

**Fall back to a cheaper model.** The obvious move, and the one a reliability chapter normally
recommends. It produces an answer. It also produces a claim whose record says it was decided by a
model nobody chose for this, on a day nobody will remember, and two claims with identical facts now
have different verdicts depending on what was up at the time.

**Reuse a similar claim's reading.** Day 12 built a retriever; it would happily find the nearest
description. That is a classification by analogy, recorded as a classification by reading, and day 12
measured its own `recall@1` at 0.7.

**Return the last known answer.** There is no last known answer. This claim has never been decided.

Every one of those is a fabrication in the only sense that matters to an insurer: **the record would
assert something nobody established.** Day 14 built a record that can be replayed precisely so a
decision can be defended, and a replay of a defaulted classification replays perfectly — the
arithmetic is fine, the input was invented.

So the desk does the unglamorous thing. It marks the claim pending, names what it is waiting for, and
moves to the next one. Nothing is recorded, because day 6's rule still holds: a claim nobody decided
has nothing to record.

And it is worth being clear that this *is* graceful degradation. Eleven claims still get decided. The
queue finishes. One claim waits for a person and says so, which is a better morning than twelve
claims decided on a default nobody can account for.

## The mechanism

The escalation, in `claims_desk/desk.py`. A **marked diff against `claims_desk/desk.py` as printed on
day 7 part 2.1**, with days 10 to 14's changes already in place:

```python
+#: What a pending notification is waiting for when the provider could not be reached at all. A
+#: different wait from `needs_classification`: that one wants a person to look at a claim, this one
+#: wants the run repeated when the provider is back.
+UNAVAILABLE = "provider_unavailable"
+
 #: What a pending notification is waiting for.
 NEEDS_CLASSIFICATION = "needs_classification"

     ...
-    read = await workflow.run_triage(notification, cover, budget)
+    try:
+        read = await reliability.with_retry(
+            f"triage {notification.id}",
+            lambda: workflow.run_triage(notification, cover, budget),
+            budget_left=lambda: budget.remaining,
+        )
+    except reliability.Unavailable as gone:
+        # The attempts ran out. Day 1's rule, five days after it was written down: a desk that
+        # invents a classification because the provider was busy has made something up about a
+        # policy. This claim waits for a person, and the log says what was tried.
+        log("desk.provider_unavailable", claim=notification.id, detail=str(gone))
+        return Verdict(notification.id, PENDING, waiting_for=UNAVAILABLE)
+
     if read["error"] == workflow.OVER_BUDGET:
```

**Line by line:**

- `UNAVAILABLE = "provider_unavailable"` — **a fourth reason a claim can be pending**, beside
  `needs_classification`, day 11's `over_budget` and day 13's `refused_shape`. The comment gives the
  distinction that earns it a constant: this one wants *the run repeated*, the others want a person.
- **That distinction is operational, not cosmetic.** A morning with two hundred
  `provider_unavailable` claims is re-run when the provider is back. Two hundred
  `needs_classification` claims are two hundred claims a person has to read. Collapsing them would
  send somebody reading.
- `lambda: workflow.run_triage(notification, cover, budget)` — **a zero-argument callable**, which is
  what `with_retry` takes. The lambda closes over the arguments so the retry does not have to know
  anything about triage.
- `budget_left=lambda: budget.remaining` — **a callable, not a value**, for part 1.1's reason: the
  budget is being spent by the very calls being retried.
- `except reliability.Unavailable as gone:` — **one exception type, one branch.** `Transient` is
  handled inside the retry; what reaches here is the decision that the attempts are over.
- **The comment dates the rule to day 1** and restates it in this claim's terms: *a desk that invents
  a classification because the provider was busy has made something up about a policy.*
- `log("desk.provider_unavailable", claim=..., detail=str(gone))` — **the claim and what was tried.**
  `str(gone)` carries the attempt count and the underlying failure, which is everything an operator
  needs to decide whether to re-run.
- `return Verdict(notification.id, PENDING, waiting_for=UNAVAILABLE)` — **and no `record=`.** Day 14
  gives every *decided* verdict a record; this one is not decided, so there is nothing to defend and
  nothing is written.
- **Nothing reaches the boundary on this path.** No claim file, no decision record, no letter. Part
  3.1 asserts the claims directory is empty after a total outage on one claim.

A claim whose provider never answers:

```bash
uv run python -c "
import asyncio
from claims_desk import desk, reliability, workflow
from claims_desk.util.backoff import Transient
from claims_desk.util.budget import Budget

async def never(*a, **k):
    raise Transient('the provider was unreachable')

async def instantly(seconds):
    return None

original = reliability.with_retry
workflow.run_triage = never
desk.reliability.with_retry = lambda what, call, **kw: original(
    what, call, sleep=instantly, **kw
)

queue = {n.id: n for n in desk.Store().notifications()}
print(asyncio.run(desk.decide(queue['FNOL-4477'], Budget(limit=5, label='FNOL-4477'))))
"
```

```

{"event": "reliability.retrying", "what": "triage FNOL-4477", "attempt": 2, "of": 3, "waiting": 2.0, "asked_for": null, "detail": "the provider was unreachable"}

{"event": "desk.provider_unavailable", "claim": "FNOL-4477", "detail": "triage FNOL-4477 failed after 3 attempts: the provider was unreachable"}
Verdict(claim_id='FNOL-4477', outcome='pending', reason=None, waiting_for='provider_unavailable', record=None)
```

**Line by line:**

- **Four log lines from two levels**, which is day 11's arrangement holding: three from the retry
  about calls, one from the desk about a claim.
- `"asked_for": null` — **the provider said nothing**, so day 1's schedule applied: 1.0 then 2.0.
  Part 1.1's cap never came near.
- `"event": "desk.provider_unavailable"` — **the line an operator alerts on.** It names the claim,
  which the retry's lines do not, and it carries the retry's own summary as `detail`.
- `outcome='pending', reason=None, waiting_for='provider_unavailable', record=None` — **`reason` is empty and
  `waiting_for` is set**, which is day 6's distinction: `reason` is what the policyholder must send,
  `waiting_for` is what the desk needs. The policyholder needs to send nothing.
- **No letter, no claim file, no record.** The policyholder is not told anything, because there is
  nothing to tell them yet — and a letter saying "we could not reach our systems" is a letter about
  the insurer's problem sent to somebody with a flooded kitchen.

## When it breaks

Default the classification instead. Three lines, and they are the three lines somebody writes at
half past four on a bad afternoon:

```python
    except reliability.Unavailable:
        read = {"outcome": Outcome.DEFICIENCY.value, "reason": Reason.PERIL_NOT_COVERED.value,
                "error": "", "turned_away": [], "facts": record.facts_from(
                    notification, cover, "", False)}
```

Now run the queue during an outage and look at what it produces. **Nothing fails.** Twelve claims
decided, twelve claim files, twelve decision records, and every one of them defensible:

```
claims decided      : 12
all defensible      : True
FNOL-4477 outcome   : deficiency
FNOL-4477 reason    : peril_not_covered
FNOL-4477 model     : ''
FNOL-4477 replays   : ('deficiency', 'peril_not_covered')
```

Verbatim, from this project, with the default in place and the provider down.

Read the third and fourth lines together with what the policyholder receives. FNOL-4477's loss is an
escape of water on a policy that covers escape of water. The desk has recorded that **this policy
does not cover this loss**, and day 9's letter writer will send a letter saying so, citing day 14's
handbook section HB-01.

And day 14's replay says the record is fine. Of course it does: `assess` was given `loss_type=""`,
`""` is in no policy's peril list, and `peril_not_covered` follows correctly from that input. The
arithmetic is right. The input was invented.

**This is the failure this whole project has been pointed at since day 1**, and it is worth naming the
two things that make it so dangerous.

The first is that it is **invisible to every check this desk has.** The suite is green. The record
replays. The counts match the brief. The letter passes day 10's house style. Nothing in two hundred
tests objects, because nothing in two hundred tests knows that `loss_type=""` was a guess rather than
a reading.

The second is that the record **makes it worse rather than better.** Without day 14, this is a wrong
claim. With day 14, it is a wrong claim with a document attached asserting that it follows from the
rules — which it does. The record is honest about the arithmetic and silent about the provenance of
the input, and `model: ''` is the only trace, sitting in a field an auditor reads as *no model was
involved* because that is what day 7's ordering legitimately means on four claims in twelve.

The smallest fix is the one the desk has: do not do this. The rule, and it is the one to carry out of
this project:

> **An agent may be unavailable. It may not be approximate.** When the answer is not available, the
> system says so and stops. Anything that converts "we could not find out" into a value is a system
> that will one day assert something about a person that nobody established.

There is a narrower version worth keeping too, because it is testable: **a default is only safe where
the record can say it was a default.** This desk has nowhere to put that — `Facts` holds what the
rules read and a provenance field saying "this reading was invented" would be a field an auditor
should never have to look for. The absence of a place to record a guess is the design refusing one.

## In production

**What a senior writes instead.** Exactly this, and they would fight for it. What they would add is a
**queue of pending claims with a reason**, visible to somebody, with a count per reason — because
escalation is only honest if somebody is looking. A claim marked `provider_unavailable` that nobody
re-runs is the same outcome as a fabricated answer, arrived at more slowly.

**What degrades at scale.** One claim escalating is a claim. A morning's several hundred notifications
during a full outage is several hundred pending claims and a queue that finishes having decided
nothing — which is correct and is also an operational event, not a software one. The number that
matters is the share: a few per cent pending is a normal day, and a third pending is a page. That
threshold is day 17's subject, and it only exists because this day refused to make the number zero by
lying.

**The review comment.** *"This falls back to `peril_not_covered` when the classifier is down, with a
comment saying it is the safe default. It is not a safe default — it is a letter telling a
policyholder their loss is not covered, which we cannot support. Mark the claim pending and let the
queue report it."*

**The interview question.** *"Your classifier is unavailable and you have a queue to get through.
Argue for a conservative default, then argue against it, and tell me which argument you would make to
a regulator."*
