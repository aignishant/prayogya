## One-line answer

The framework will let one agent hand a conversation to another and take it back — three events,
driven here for real — and this desk calls its two agents in a fixed order instead, because a
handover decided by a model is a decision no rule can explain.

## The idea

There are two ways to get a call to the right person.

The switchboard puts it through to the front desk, and the front desk decides: *this one is for
correspondence*, and transfers it. The caller ends up talking to somebody else, and the front desk
is out of the conversation until it comes back.

Or the procedure decides. The call is taken, the sheet is filled in, and the sheet goes to
correspondence — always, in that order, for every claim of that kind. Nobody chooses. The front desk
could not send it somewhere else if it wanted to.

Both are real arrangements and both are used in real departments. The difference is what you can say
afterwards. With the first, *why did this call go to correspondence* is answered by asking the
person who transferred it. With the second, it is answered by reading the procedure.

**Delegation** is the first: an agent hands the conversation to another agent, which answers and
hands it back. The framework supports it directly — an agent with `sub_agents` gets a
`transfer_to_agent` tool it can call, and the runner does the rest.

This part drives that for real, so that what follows is a choice rather than an absence: **this
desk's decision path does not use it.** The classifier is called, then the rules run, then the
letter writer is called, in that order, by ordinary Python. Nothing decides who speaks next.

## The mechanism

Two agents, one with the other as a sub-agent, and a stand-in that asks to hand over:

```python
    specialist = Agent(
        name="specialist",
        model=Specialist(),
        description="Handles the thing the front desk hands over.",
        instruction="Answer.",
    )
    front = Agent(
        name="front",
        model=WantsToTransfer(),
        description="Takes the call and hands over when it is not for them.",
        instruction="Hand over to the specialist.",
        sub_agents=[specialist],
    )
```

**Line by line:**

- `sub_agents=[specialist]` — **the whole of the wiring.** Giving an agent sub-agents is what gives
  it a `transfer_to_agent` tool; there is no separate registration and no router object.
- `description="Handles the thing the front desk hands over."` — **the sub-agent's description is
  how the parent chooses.** Day 5 said a tool's description is its API; an agent's description is the
  same thing for delegation, read by a model deciding whether this is the right colleague.
- `instruction="Hand over to the specialist."` — the parent's own instruction. In this demonstration
  the stand-in ignores it and transfers unconditionally; with a provider, this sentence is the whole
  of the decision procedure.
- **Both agents are ordinary `Agent` objects.** A sub-agent is not a special kind of thing — which
  is what makes the arrangement composable and also what makes it hard to see in a codebase.

The stand-in that asks for the transfer:

```python
class WantsToTransfer(BaseLlm):
    """A stand-in that asks to hand over on its first turn, then answers."""

    model: str = "scripted/wants-transfer"

    async def generate_content_async(
        self, llm_request: LlmRequest, stream: bool = False
    ) -> AsyncGenerator[LlmResponse, None]:
        sent = json.dumps([c.model_dump(exclude_none=True) for c in (llm_request.contents or [])])
        if "transfer_to_agent" in sent:
            yield LlmResponse(
                content=types.Content(role="model", parts=[types.Part(text="handed back")]),
                turn_complete=True,
            )
            return
        yield LlmResponse(
            content=types.Content(
                role="model",
                parts=[
                    types.Part(
                        function_call=types.FunctionCall(
                            name="transfer_to_agent", args={"agent_name": "specialist"}
                        )
                    )
                ],
            ),
            turn_complete=True,
        )
```

**Line by line:**

- `model: str = "scripted/wants-transfer"` — announced, like every double in this project, and
  therefore admitted by day 7's registry for the same reason.
- `sent = json.dumps([...])` then `if "transfer_to_agent" in sent:` — **the double looks at what it
  has already been sent** to decide whether it has transferred once. Crude, and it is how a
  stand-in avoids an infinite loop of transferring to itself.
- `types.Part(function_call=types.FunctionCall(name="transfer_to_agent", args={"agent_name":
  "specialist"}))` — **the transfer is an ordinary tool call.** Not a special message type, not a
  field on the response: the model asks to call a function named `transfer_to_agent`, and the
  framework provided that function because the agent has sub-agents.
- `args={"agent_name": "specialist"}` — **by name.** The model picks a colleague out of the
  descriptions it was shown and names them, which is exactly as reliable as the descriptions are
  distinct.

Run it:

```
author='front'      calls=['transfer_to_agent'] transfer_to=None text=''
author='front'      calls=[] transfer_to='specialist' text=''
author='specialist' calls=[] transfer_to=None text='the specialist answered'
```

**Line by line:**

- **Three events for one question.** Day 8's part on the event model said the number grows; this is
  it growing.
- **Event one**: `author='front'`, `calls=['transfer_to_agent']`. The front desk asked to hand over.
  It is a function call like any other and appears in `event.get_function_calls()`.
- **Event two**: `author='front'` again, and now `transfer_to='specialist'` — the framework's
  response to the call, carried in `event.actions.transfer_to_agent`. **This is the field to watch
  in a log**: it is the moment the conversation changed hands, attributed to the agent that let go.
- **Event three**: `author='specialist'` with the answer. The specialist ran, in the same
  invocation, in the same session, and its answer is the turn's final response.
- **The handback is the absence of a fourth event.** The specialist answered and the turn ended;
  control did not return to the front desk because it had nothing left to do. A conversation where
  the parent needed to speak again would show a fourth event authored by `front`.

And the framework says something worth reading, on the same run:

```
App "demo" can transfer between agents but has no context_cache_config. Every transfer swaps the
system instruction and the tool set, so the request prefix changes and the whole prompt is re-sent
uncached after each transfer. Set context_cache_config on the app to give each agent its own cache.
```

**Line by line:**

- **"Every transfer swaps the system instruction and the tool set"** — a transfer is not a cheap
  message pass. The next request goes out with a different agent's instruction and a different tool
  list at the front of it.
- **"the request prefix changes and the whole prompt is re-sent uncached"** — and that is the cost,
  in the framework's own words. Providers cache on a shared prefix; changing the prefix throws the
  cache away.
- **The warning names the fix** — a cache configured per agent — which is worth knowing and is not
  the point here. The point is that **delegation has a price, the framework will tell you what it
  is, and this project's stand-in cannot measure it.**

## When it breaks

Nothing above breaks. The mechanism works, and the question is whether to use it for a claim
decision. This desk does not, and the argument is worth making rather than assuming.

Consider the version of this project that does. The `intake` agent reads the notification and
transfers to the `classifier`, which transfers to the `policy_checker`, which transfers to the
`adjuster`, which transfers to the `letter_writer`. It would work. It is the arrangement the
framework is designed around, and it reads beautifully in a diagram.

Now a claim is fast-tracked that should not have been, and somebody asks why.

With the arrangement this project has, the answer is a rule: `assess` ran, in the order day 2 fixed,
and `estimate > fast_track_limit` was false. Somebody can read those eight lines, disagree with
them, and change one.

With delegation, the answer is *the adjuster did not transfer to the letter writer*, and the reason
it did not is a sentence in an instruction, weighed against a description, by a model, on that
particular claim. **There is no rule to read.** The system did not follow a wrong procedure; it
formed a judgement, and the same input on a Tuesday might form a different one.

That is the trade, and it is not free in either direction. What this desk gives up is real:
delegation handles the cases nobody enumerated, and an intake desk meets those. What it keeps is
that **every decision about a claim can be explained by reading code**, which for a regulated
process is not a preference.

The smallest version of the rule: **use delegation for work, not for decisions.** Handing a letter
to a specialist writer is work. Deciding whether a claim is payable is a decision, and it stays in
the rules.

## In production

**What a senior writes instead.** The same split, made visible in the architecture rather than
implied: the deterministic pipeline in one place, and any delegated work behind an interface that
records what was handed over and why. What they would insist on is that a transfer decision is
**logged with the reason** — `event.actions.transfer_to_agent` says who received the conversation
and nothing says why — because the first incident involving a wrong handover will otherwise have no
evidence in it at all.

**What degrades at scale.** Two agents called in order is a pipeline anybody can read. Five agents
that transfer between themselves is a graph whose edges are decided at run time, and the number of
paths through it is not knowable from the code. Both scale; only one can be tested exhaustively. The
practical failure is subtler than a wrong route: with transfers, **the prompt prefix changes on
every hop**, so a five-agent conversation pays the uncached cost four times, and the bill for one
notification stops being predictable from the number of agents.

**The review comment.** *"This makes the classifier a sub-agent of the intake agent so it can decide
whether to bother classifying. That decision is now a model's, on every claim, and it will not be in
the audit trail. Call it unconditionally and let the rules decide what to do with the answer."*

**The interview question.** *"Your framework supports agents handing work to each other. Give me a
case where you would use it and a case where you would refuse, and say what distinguishes them."*
