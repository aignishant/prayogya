## One-line answer

The second agent writes the letter the first one made possible, and it is given a claim, a reason
and one sentence of instructions — not the policy, not the estimate, not the description — because
what it is *not* given is what it cannot get wrong.

## The idea

There are two people behind the counter and they do different jobs.

One takes the call. They listen, they write down what happened, and they hand the sheet across.
The other writes the letter that goes out — and they work from the sheet, not from the call. They
did not hear the policyholder, they do not have the policy in front of them, and if the sheet says
*photograph required* then the letter asks for a photograph and says nothing about excesses.

That second person is not less senior. They are differently constrained, and the constraint is the
job: **a letter goes out on the company's paper, and the person writing it is given exactly what the
letter needs and nothing that could end up in it by accident.** Somebody who had the estimate in
front of them would eventually mention a figure.

Day 7 built the first of these. Day 6 built the thing that connects them — `draft_letter`, the tool
that assembles the materials and refuses to write, saying so in its own answer: *this boundary has
no model; the letter is written by the caller.*

This part is the caller.

One agent was a function with a model behind it. Two is an **architecture**, and the questions that
arrive with the second one are all about the boundary between them: who is given what, who decides
which of them speaks, and what the two of them cost together. This part answers the first. Part 2.1
answers the second, and part 3.2 is what happens when nobody answers the third.

## The mechanism

The whole file, at `claims_desk/agents/letter_writer.py`:

```python
"""The letter writer: the one thing in this desk that produces prose a policyholder will read.

It is given a claim, one reason, and the materials the boundary hands over — what the policyholder
must send, and the house style. It writes four sentences. It is not given the policy, the estimate,
the excess or the description, because a letter that mentions a figure is a letter an insurer can
be held to, and this agent has no way to check one.

Day 6's `draft_letter` refuses to write, and says so in its own answer: *this boundary has no model;
the letter is written by the caller.* This is the caller.
"""

from __future__ import annotations

from typing import Any

from google.adk.agents import Agent

from claims_desk import boundary, models, sessions
from claims_desk.scripted import ScriptedLetterWriter
from claims_desk.util.budget import Budget
from claims_desk.util.logging import log

#: The name this agent answers to, in events and in the budget's breakdown.
NAME = "letter_writer"

#: What the letter writer is for, and what it must not do. The prohibitions are the same ones the
#: boundary's own prompt carries, restated here because an instruction and a prompt are sent to a
#: model at different moments and neither can be assumed present.
INSTRUCTION = """You write deficiency letters for an insurance intake desk.

You are given a claim reference, the single reason the claim cannot be fast-tracked, and the one
thing the policyholder must send or confirm. Write the letter and nothing else.

Rules:
- Name exactly one missing or failing item. Do not list alternatives.
- Say precisely what the policyholder must send or confirm, using the words you were given.
- Do not quote a policy number, an excess, an estimate or any amount. You have not been given any.
- Do not promise a decision, a timescale or a settlement figure.
- Four sentences at most, plain words, no apology.
"""


def build(model: Any | None = None) -> Agent:
    """Build the letter writer, with its model pinned explicitly."""
    chosen = model if model is not None else ScriptedLetterWriter()
    return Agent(
        name=NAME,
        model=models.pinned(chosen),
        description="Writes a deficiency letter from a claim reference and one reason.",
        instruction=INSTRUCTION,
    )


async def write(claim_id: str, reason: str, budget: Budget) -> dict[str, Any]:
    """Ask the boundary for the materials, then ask the model to write the letter.

    One boundary call and one model call. Returns the letter, or `{"error": ...}` — never a letter
    the agent made up when the boundary refused to supply the reason it was asked about.
    """
    materials = await boundary.call("draft_letter", {"claim_id": claim_id, "reason": reason})
    if "refused" in materials:
        log("letter_writer.refused_materials", claim=claim_id, detail=materials["refused"])
        return {"error": materials["refused"]}

    budget.spend(NAME)
    agent = build()
    question = (
        f"Claim: {claim_id}\n"
        f"Reason: {materials['reason']}\n"
        f"The policyholder must send or confirm: {materials['needed']}"
    )
    letter, events = await sessions.turn(agent, claim_id, question, thread=NAME)

    log(
        "letter_writer.wrote",
        claim=claim_id,
        reason=reason,
        model=agent.model.model,
        events=len(events),
        sentences=letter.count(".") if letter else 0,
    )
    if not letter.strip():
        return {"error": "the letter writer produced nothing"}
    return {"letter": letter.strip(), "reason": materials["reason"]}
```

**Line by line:**

- **The docstring lists what the agent is not given**, which is unusual and is the point. *"not the
  policy, the estimate, the excess or the description"* — four omissions, each one a thing that
  could otherwise appear in a letter.
- **"a letter that mentions a figure is a letter an insurer can be held to, and this agent has no way
  to check one"** — the reason, in the file. Not a style preference: a number in a letter is a
  statement the company made.
- `from claims_desk import boundary, models, sessions` — **three of this project's own modules and
  one framework import.** The agent reaches the boundary through day 4's client and runs its turn
  through day 8's sessions, so this file contains no transport and no runner.
- `NAME = "letter_writer"` — the same three-way use as day 7's classifier: the agent's identity, the
  key in the budget's breakdown, and the prefix on this module's log events.
- **The instruction's five rules are the boundary's prompt, restated.** Day 4 declared a
  `deficiency_letter` prompt on the server carrying these same constraints, and this repeats them.
  The comment says why: *"an instruction and a prompt are sent to a model at different moments and
  neither can be assumed present."* It is duplication, it is deliberate, and it is a rep in the hub
  to decide whether to keep it.
- `- Say precisely what the policyholder must send or confirm, using the words you were given.` —
  **"using the words you were given"** is the line that ties this agent to `WHAT_IS_NEEDED` from day
  6. The department wrote that sentence; the agent is told to use it rather than paraphrase it.
- `- Do not quote a policy number, an excess, an estimate or any amount. **You have not been given
  any.**` — the second sentence is doing the work. Telling a model not to use information it has is
  a rule it may weigh; telling it that it does not have the information is a fact.
- `def build(model=None)` — **the same shape as day 7's classifier**, deliberately. Two agents built
  the same way is a pattern; two built differently is two things to learn.
- `models.pinned(chosen)` — day 1's registry again, and the stand-in announces itself with the same
  `scripted/` prefix. A second agent does not get a second set of rules.
- `materials = await boundary.call("draft_letter", ...)` — **the boundary is asked first, before any
  model call.** The same ordering principle as day 7: the cheap, deterministic question goes first.
- `if "refused" in materials: return {"error": ...}` — **and the budget has not been spent yet.** A
  reason the department does not recognise costs nothing, because the model was never asked. Move
  `budget.spend` above this line and every bad reason code costs a call.
- `question = (f"Claim: {claim_id}\n" f"Reason: ...\n" f"The policyholder must send or confirm:
  ...")` — **three labelled lines, and that is the entire input.** Not the notification, not the
  policy, not the cover. Everything this agent could put in a letter is on these three lines — and
  the `thread=NAME` on the line below is what makes that sentence true rather than merely intended.
  Part 3.1 shows the version where it was intended and false.
- `materials['reason']` and `materials['needed']` rather than the local `reason` — **the boundary's
  words, echoed back.** The desk asked about a reason and the boundary returned one; using the
  returned value means a boundary that normalised the code is obeyed rather than second-guessed.
- `letter, events = await sessions.turn(agent, claim_id, question, thread=NAME)` — day 8's session,
  under the same claim reference the classifier used, but in **this agent's own thread**. The
  agent's name is the thread name, so a claim's conversations are `claim-FNOL-4477` and
  `claim-FNOL-4477/letter_writer` and both are found by asking for the claim.
- **`thread=NAME` is the whole of the isolation, and it is not obvious.** Day 8 had no threads and
  did not need them; this file is where one agent's conversation would otherwise become another
  agent's reading matter. Part 3.1 is that failure, in full, with what the letter writer was
  actually sent before this argument existed.
- `sentences=letter.count(".")` — a crude count in the log line, and it is honest about being crude.
  It is there because the instruction says "four sentences at most" and a number in a log is how you
  find out whether that is being obeyed at scale.
- `if not letter.strip(): return {"error": "the letter writer produced nothing"}` — **an empty
  answer is an error here**, unlike day 5's `read_decision` where an empty answer was a result. The
  difference: a claim not yet decided is a real state, and a letter that is a blank page is not.
- `return {"letter": ..., "reason": materials["reason"]}` — the letter **and** the reason it was
  written for, so a caller storing it stores both. Day 6 spent a whole part on refusals being read;
  this makes the pair impossible to separate by accident.

```

```

**Line by line:**

- **Three sentences, and the middle one is the department's.** *"Please send a photograph of the
  damage"* is `WHAT_IS_NEEDED[MISSING_PHOTO_REFERENCE]` from day 6, written by the people who answer
  for the letters and carried through the boundary unchanged.
- **The claim reference appears and nothing else does.** No policy number, no excess, no estimate,
  no mention of what the caller said. Every one of those was available somewhere in this project and
  none of them was given to this agent.
- **"We will continue as soon as we have it"** is not a timescale and not a promise about the
  outcome. The instruction forbids both, and this sentence is what is left.
- This came from the stand-in, which looked the reason up in a table. **What a provider would write
  is not known**, and that is the same `TODO(me)` day 7 opened.

## When it breaks

Ask for a letter about a reason the department does not recognise:

```bash
uv run python -c "
import asyncio
from claims_desk.agents import letter_writer
from claims_desk.util.budget import Budget
b = Budget(limit=3)
out = asyncio.run(letter_writer.write('FNOL-4477', 'no_photo', b))
print(out)
print('budget spent:', b.spent)
"
```

```
{'error': "unknown reason 'no_photo'"}
budget spent: 0
```

Verbatim, from this project. Two things happened, and the second is the one to notice.

The boundary refused, as data, in the shape day 5 established — and `letter_writer.write` read the
answer, which is day 6's lesson applied by a file written three days later. **No letter was
invented for a reason nobody recognises.**

And **the budget was not spent.** The refusal came from the boundary, before `budget.spend(NAME)`,
so a wrong reason code costs a round trip and no model call. That ordering is one line and it is
worth a review comment when it is wrong: a version that spends first would charge for every typo.

## In production

**What a senior writes instead.** The same narrow agent, with the letter going through a review step
before it is sent — the letter written here is stored, not posted, and this project stores it with
the decision for exactly that reason. What they would fight hardest for is the input: **an agent
that writes customer-facing text is given the minimum**, because every extra field is a thing that
can appear in a paragraph, and no reviewer catches everything.

**What degrades at scale.** Eight letters in a queue of twelve. A morning's several hundred
notifications at two thirds deficient is several hundred letters a day, all in one voice, all
carrying the same phrasing — which is a quality nobody notices until the phrasing is wrong, and then
it is wrong on every one of them. The mitigation is that the sentences come from the department's
table rather than from the model, so a bad sentence is one edit in one place rather than a prompt
change and a re-run.

**The review comment.** *"The letter writer is now passed the whole notification so it can mention
what happened. Take it back out — the description is what a policyholder said on the phone, and the
first time it appears in an outgoing letter we will be explaining why."*

**The interview question.** *"You have an agent that writes text a customer will read. List
everything you would refuse to give it, and say what each omission prevents."*
