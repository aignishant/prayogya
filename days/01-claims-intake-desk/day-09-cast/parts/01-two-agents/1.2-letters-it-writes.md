## One-line answer

Eight scripted letters, one per reason, stored with the decision they explain — and the boundary
refuses to attach a letter to a fast-track, because a confirmation is not a deficiency letter.

## The idea

The correspondence clerk has a folder of standard wordings, one for each way a claim can fall
short. They do not compose from nothing: they take the right wording, fill in the reference, and
that is the letter. The folder is maintained by the department, reviewed when the wording changes,
and the same eight letters have gone out for years.

What is kept afterwards is the pair. The claim file holds the decision **and** the letter that
explained it, in one record, because six months later the only useful question is not *what did we
decide* — it is *what did we tell them*, and those are different documents when they are stored
apart.

This part is the folder and the filing. The stand-in gets eight letters, one per reason, written by
hand in the house style. And `record_decision` — the boundary's only write, from day 5 — learns to
carry a letter alongside the outcome, with one new refusal: **a fast-track has no letter.**

That last refusal is worth pausing on. A fast-track confirmation is a real document and a real
insurer sends one. It is not this letter, it has different rules, and letting the deficiency letter
field carry it would put two kinds of document in one column — which is the sort of thing that is
invisible for a year and then makes a report meaningless.

## The mechanism

A **marked diff against `claims_desk/scripted.py` as printed on day 7 part 1.2** — everything above
`LETTERS` is unchanged:

```python

class ScriptedLetterWriter(BaseLlm):
    """Replays a deficiency letter for a reason. A stand-in, not a writer."""

    model: str = SCRIPTED_PREFIX + "letter-writer"

    async def generate_content_async(
        self, llm_request: LlmRequest, stream: bool = False
    ) -> AsyncGenerator[LlmResponse, None]:
        """Yield the scripted letter for the reason in the question, or refuse to invent one."""
        asked = ScriptedClassifier._description_from(llm_request)
        claim = ""
        reason = ""
        for line in asked.splitlines():
            if line.startswith("Claim:"):
                claim = line.split(":", 1)[1].strip()
            if line.startswith("Reason:"):
                reason = line.split(":", 1)[1].strip()
        text = LETTERS.get(reason, "")
        yield LlmResponse(
            content=types.Content(
                role="model",
                parts=[types.Part(text=text.format(claim=claim) if text else "")],
            ),
            turn_complete=True,
        )
```

**Line by line:**

- **Eight entries, one per `Reason`.** The same eight the fixture set exercises, the same eight
  `WHAT_IS_NEEDED` answers, and part 3.1 asserts all eight produce a letter.
- **The comment repeats the rule from day 7**: these are a script, not a model's output. The same
  reason `data/notifications.json` carries an answer key — a fixture generated by the system under
  test proves only that the system has not changed.
- `"{claim}"` as the only placeholder — **one substitution, and it is a reference.** Not the
  policyholder's name, not the address, not a date. The letters are as narrow as the agent that
  requests them.
- **"even approximately"** in the first letter — the same clause from day 6's `WHAT_IS_NEEDED`,
  because a letter demanding an exact date from somebody who does not know one gets no reply.
- **Three of the eight ask for nothing.** `peril_not_covered`, `injury_reported` and
  `above_fast_track_limit` all say *"There is nothing further for you to send"* — because in those
  three the deficiency is not the policyholder's to fix. A letter asking for a photograph when an
  adjuster is going to ring is a letter that wastes two people's time.
- `"If you believe another policy covers it, please tell us which."` — the not-covered letter's
  third sentence, and the only one in the eight that invites a reply without asking for a document.
  Somebody who has been told they are not covered deserves a way to disagree.
- `class ScriptedLetterWriter(BaseLlm)` with `model: str = SCRIPTED_PREFIX + "letter-writer"` — **a
  second double, announced the same way**, and therefore admitted by day 7's registry for the same
  reason.
- `asked = ScriptedClassifier._description_from(llm_request)` — reusing the first double's helper.
  It reaches for a private method, which is a small ugliness and the honest alternative to copying
  eight lines; a rep in the hub asks you to decide whether to promote it.
- `for line in asked.splitlines(): if line.startswith("Claim:")` — **the double parses the question
  the agent sent.** It behaves like a model: it is given text and has to find the fields in it. A
  double handed a dictionary would be standing in for the prompt construction as well.
- `text = LETTERS.get(reason, "")` and `text.format(claim=claim) if text else ""` — **an unknown
  reason produces an empty string**, and `letter_writer.write` turns that into
  `{"error": "the letter writer produced nothing"}`. The double does not guess a letter, exactly as
  day 7's classifier does not guess a peril.

**Line by line:**

- `letter: str | None = None` — **optional, so every existing caller keeps working**, and absent
  from the schema's `required` list for the same mechanical reason day 5's `reason` was.
- **"Stored with the decision so that what went out and why it went out are one record."** — the
  argument for the whole change, in the argument's own description where a model will read it.
- `letter_chars=len(letter) if letter else 0` in the log — **the length, never the text.** The letter
  is about a policyholder's claim; a log that carried it would be a second copy of the
  correspondence in a place with none of the correspondence's rules. Day 1's redaction instinct,
  applied by hand because the field name would not have triggered it.
- `if letter is not None and outcome != Outcome.DEFICIENCY: return {"recorded": False, "refused":
  "a fast-track has no letter"}` — **the new refusal**, in the shape all four existing ones use:
  data, with `recorded: false` and a sentence saying which rule.
- **Placed after the outcome and reason checks**, so an unknown outcome is still reported as an
  unknown outcome rather than as a letter problem. Order in a validation chain decides which message
  a caller gets.
- `record = {...}` then `if letter is not None: record["letter"] = letter` — **the key is absent
  rather than null when there is no letter.** A fast-track's claim file has three fields; a
  deficiency's has four. Reading a file tells you which kind it is without interpreting a null.
- The **return value is unchanged** — no `letter` in it. The caller sent the letter and does not need
  it echoed; what it needs is whether the write happened, which is day 6's lesson.

## When it breaks

Give a fast-track a letter:

```bash
uv run python -c "
import asyncio, json
from claims_desk import boundary
print(json.dumps(asyncio.run(boundary.call('record_decision', {
    'claim_id': 'FNOL-4471', 'outcome': 'fast-track', 'letter': 'anything'}))))
"
```

```
{"recorded": false, "refused": "a fast-track has no letter"}
```

Verbatim. Nothing was written, and the refusal names the rule.

The reason this matters is not tidiness. A fast-track confirmation is a real document that a real
insurer sends, and it is not a deficiency letter: different wording, different obligations,
different review. Letting one field carry both means that in six months the question *"how many
deficiency letters did we send last quarter"* is answered by counting a column that contains two
kinds of document — and nobody discovers that until somebody reconciles the count against the post
room.

Somebody would do it for the best reason: the confirmation needs storing somewhere, this field is
right there, and it is one line. The smallest fix is a second field and a second refusal. The rule
worth keeping: **one column, one kind of thing**, and a boundary is the right place to enforce it
because it is the only thing that sees every write.

## In production

**What a senior writes instead.** The letter stored with a version of the wording that produced it,
so that a letter sent in March can be explained by the template that existed in March. This project
stores the text and the reason, which answers *what did we say*; it cannot answer *why did we say it
that way*, because the wording lives in a dictionary that changes without a version. That is a real
gap and day 14's decision record is where the same problem gets solved for decisions.

**What degrades at scale.** Eight wordings, maintained by hand, is a folder. Forty across three
products, each with a regulator-approved phrasing, is a content management problem — and the failure
mode is a wording changed in the code and not in the approved set, which nobody notices because the
letters still go out and still read well. The mitigation this project already has is that the
sentences come from the department's table rather than from the model; the mitigation it lacks is
anything checking that table against what was approved.

**The review comment.** *"The confirmation letter for fast-tracked claims goes in the `letter` field
too. Add `confirmation` — otherwise every report that counts deficiency letters is wrong from this
commit onwards, and it will be a year before anybody reconciles it."*

**The interview question.** *"You store the text of a customer letter alongside a decision. What
else do you need to store before you can explain that letter to somebody eighteen months later?"*
