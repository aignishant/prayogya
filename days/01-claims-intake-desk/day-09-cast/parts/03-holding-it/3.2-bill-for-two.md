## One-line answer

The ceiling is per notification and shared across the cast, so two agents working one claim spend
from one allowance of three and the breakdown names both — and the version where each agent gets its
own budget quietly doubles the number the department was told.

## The idea

The department agreed a figure. Not a figure per person: a figure per claim.

That distinction is the entire content of this part, and it is the one that goes wrong when a desk
grows a second pair of hands. When one person handled a notification, *per claim* and *per person*
were the same number and nobody had to say which they meant. Now there are two, and the sentence
"we allow three calls" has two readings that differ by a factor of the size of the cast.

Day 7 built the ceiling: a `Budget` with a limit, a running total, and a refusal when the next call
would pass it. It carried a per-agent breakdown from the first day it existed, which looked like
bookkeeping for one agent and turns out to be the thing that makes a two-agent bill readable.

This part is about where that budget is created and how far it travels. **A ceiling is only a
ceiling if the thing being capped is the thing that was measured** — the claim, not the classifier;
the notification, not the turn. Everything else in this desk gets a per-notification budget by
accident of where a line of code sits, and this part is where that line is chosen deliberately.

## The mechanism

The constant, and the call that spends against it, in `claims_desk/desk.py`. A **marked diff against
`claims_desk/desk.py` as printed on day 7 part 2.1** — everything not shown is unchanged from that
day:

**Line by line:**

- `CALLS_PER_NOTIFICATION = 3` — **two, plus one.** One classification, one letter, and one spare
  that is not spare for long: day 15 adds a retry, and a retry with no headroom is a retry that
  refuses itself.
- **The comment changed, and it is the more important half of the hunk.** Day 7's said *"one
  classifier call"*; this one says *"across the whole cast"* and *"it is shared because two agents on
  one claim is two calls"*. A reader who finds `3` wants to know what the three are for, and a
  constant whose comment describes a cast of one is a constant that will be misread the first time
  somebody adds an agent.
- **Say what a number is a ceiling *on*, in the comment, every time.** "Three calls" is ambiguous
  between per claim, per agent and per run, and this desk has been all three at various points in
  its own history.
- `budget = Budget(limit=..., label=f"notification {notification.id}")` — **inside the loop.** One
  budget per notification, created where the notification is. A budget created above the loop would
  be a morning's allowance, and one looping claim would spend the queue's.
- `label=f"notification {notification.id}"` — the label appears in the refusal text, which is how a
  `BudgetExceeded` in a log says which claim ran out rather than only which agent asked.
- `letter = None` **before the condition** — so the variable exists on every path. A fast-track
  reaches `record_decision` with `letter=None`, which day 9 part 1.2 made the boundary insist on.
- `if verdict.outcome == Outcome.DEFICIENCY and verdict.reason:` — **two conditions, and the second
  is not redundant.** A deficiency always has a reason today; `verdict.reason` is typed optional, and
  a `None` reason would reach the boundary as an unknown reason and be refused mid-queue.
- `await letter_writer.write(verdict.claim_id, verdict.reason, budget)` — **the same `budget`
  object**, passed on rather than replaced. This is the line the whole part is about: the second
  agent spends from the first agent's allowance because they are working the same claim.
- `if "error" in drafted: log(...)` **and the queue continues** — a letter that could not be written
  does not lose the decision. The claim is still recorded, without a letter, and the failure is in
  the run's log. Losing a correct decision because prose could not be produced would be the wrong
  trade in both directions.
- `verdict.claim_id, verdict.outcome, verdict.reason, letter` — the fourth argument, added to the
  boundary in part 1.2 today. `None` on a fast-track, a string on a deficiency, and refused if those
  are the wrong way round.

What the two agents actually cost:

```bash
uv run python -c "
import asyncio
from claims_desk import desk
from claims_desk.agents import letter_writer
from claims_desk.util.budget import Budget, BudgetExceeded

queue = {n.id: n for n in desk.Store().notifications()}

async def shared():
    budget = Budget(limit=desk.CALLS_PER_NOTIFICATION, label='FNOL-4477')
    verdict = await desk.decide(queue['FNOL-4477'], budget)
    await letter_writer.write(verdict.claim_id, verdict.reason, budget)
    return budget

async def each():
    reading = Budget(limit=desk.CALLS_PER_NOTIFICATION, label='FNOL-4477 reading')
    writing = Budget(limit=desk.CALLS_PER_NOTIFICATION, label='FNOL-4477 writing')
    verdict = await desk.decide(queue['FNOL-4477'], reading)
    await letter_writer.write(verdict.claim_id, verdict.reason, writing)
    return reading, writing

b = asyncio.run(shared())
print('one shared budget : limit=%d spent=%d by=%s' % (b.limit, b.spent, b.by))
r, w = asyncio.run(each())
print('a budget each     : limits=%d+%d=%d spent=%d by=%s, %s'
      % (r.limit, w.limit, r.limit + w.limit, r.spent + w.spent, r.by, w.by))
"
```

```
one shared budget : limit=3 spent=2 by={'classifier': 1, 'letter_writer': 1}
a budget each     : limits=3+3=6 spent=2 by={'classifier': 1}, {'letter_writer': 1}
```

**Line by line:**

- **Both runs spend two.** On this claim, on this day, with two agents, the arrangements are
  indistinguishable by outcome and by cost. That is precisely why the wrong one gets shipped.
- `limit=3` against `limits=3+3=6` — **the ceiling is the thing that differs, and only the ceiling.**
  The department agreed three; the second arrangement permits six and will not say so until
  something spends it.
- `by={'classifier': 1, 'letter_writer': 1}` — **one dictionary, both agents.** This is a bill you
  can read: two calls, and here is who made them.
- `by={'classifier': 1}, {'letter_writer': 1}` — **two dictionaries and no total.** To answer "what
  did this claim cost" somebody must know that both objects exist and add them up, and the first
  time a third agent is added, one of them will not be in the sum.
- `desk.CALLS_PER_NOTIFICATION` rather than `3` — the demonstration reads the desk's own number, so
  it stays honest when the ceiling moves.

## When it breaks

Drop the ceiling to one and let both agents work the same claim:

```bash
uv run python -c "
import asyncio
from claims_desk import desk
from claims_desk.agents import letter_writer
from claims_desk.util.budget import Budget, BudgetExceeded

queue = {n.id: n for n in desk.Store().notifications()}

async def tight():
    budget = Budget(limit=1, label='FNOL-4477')
    verdict = await desk.decide(queue['FNOL-4477'], budget)
    try:
        await letter_writer.write(verdict.claim_id, verdict.reason, budget)
        return 'letter written'
    except BudgetExceeded as refused:
        return 'refused: %s' % refused

print('a ceiling of one  :', asyncio.run(tight()))
"
```

```
a ceiling of one  : refused: letter_writer asked for call 2 of 1 for FNOL-4477; already spent: {'classifier': 1}
```

Verbatim, from this project. Read what that sentence contains: **who asked** (`letter_writer`),
**for what** (call 2 of 1), **about which claim** (`FNOL-4477`), and **where the allowance went**
(`{'classifier': 1}`). Nobody has to reproduce anything to know what happened.

And notice who is refused. The classifier spent first and got its call; the letter writer arrived
second and was turned away. **A shared budget is first-come, first-served**, so the agent that runs
later is the agent that fails when the ceiling is too low — which means an incident report will name
the letter writer for a shortage the classification caused.

The smallest fix is a bigger ceiling, and it is the wrong instinct to reach for first. The right
question is whether two calls per claim is what this desk should cost, and the number in
`CALLS_PER_NOTIFICATION` is where that answer is written down. **A budget that is raised whenever it
refuses is not a budget.**

## In production

**What a senior writes instead.** The same shared budget, with the ceiling loaded from configuration
rather than a constant, and the spend emitted as a metric per claim rather than only in a refusal.
What they would insist on is the breakdown surviving into whatever collects it: a total tells you the
morning cost more than expected, and only `by` tells you which agent changed.

**What degrades at scale.** Three calls per notification across a morning's several hundred is
somewhere near a thousand model calls before lunch, and a two-thirds deficiency rate means two
thirds of those claims pay for a letter as well as a reading. Doubling the cast to four agents does
not double the bill — it doubles the *ceiling*, and the bill goes wherever the work goes. That is
the argument for costing a claim rather than an agent: the number of agents is an implementation
detail and the number of claims is the business.

**The review comment.** *"The new agent takes its own `Budget(limit=CALLS_PER_NOTIFICATION)`. That
does not add an agent to the claim's allowance, it gives the claim a second allowance. Pass the
budget you were given."*

**The interview question.** *"You cap model calls per unit of work. Say what your unit is, and what
breaks first when somebody adds a second agent to that unit without changing the cap."*
