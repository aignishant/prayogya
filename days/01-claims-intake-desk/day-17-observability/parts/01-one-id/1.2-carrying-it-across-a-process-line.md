## One-line answer

A `ContextVar` reaches every module in one process and stops dead at the boundary, so the desk puts
its trace id into the subprocess's **environment** at launch and the boundary reads it from there —
which is why a log line written by the server process carries the same id as the line the desk wrote
a millisecond earlier.

## The idea

Day 3 made the boundary a separate process, and gave a good reason: a boundary that is an import is
not a boundary, because you cannot reason about what crosses a line that is a function call. Day 16
found a second benefit — two processes hold different powers, and neither holds the other's.

Today the same decision sends a bill.

Everything part 1.1 built works because a `ContextVar` is attached to the current execution, and every
module in this process shares it. The boundary shares nothing. It is a separate program with its own
interpreter, its own imports, its own memory, and its own copy of `trace.py` in which `trace_id` is an
empty string that nothing has ever set. It writes log lines — `boundary.fetch_policy`,
`boundary.record_decision` — and they land on the same stderr, interleaved with the desk's, carrying
no id at all.

Which is the more damaging half of the file to lose. The desk's lines say what the desk decided; the
boundary's lines say what was actually written to a claim file. An investigation that can follow one
claim through the desk and then loses it at the point where the decision is recorded has lost the part
somebody is asking about.

So the id has to cross. There are three ways, and the choice is more interesting than it looks.

**In the tool arguments.** Add a `trace` parameter to `fetch_policy`, `record_decision` and the rest.
It works and it is wrong: the trace id would appear in the tool's declared schema, which is the
docket a model reads. Day 16's whole argument is that the docket is the list of things this system can
be asked to do, and putting plumbing into it means every tool gains a parameter that has nothing to do
with claims and that a model could set.

**In the protocol.** MCP has a metadata channel for exactly this sort of thing — `client.call_tool`
in this project's pinned version takes a `meta` argument alongside `name` and `arguments`, separate
from the tool's own parameters — and in a system where the boundary is a long-lived service reached
over HTTP, that is the right answer.

**In the environment.** The desk launches the boundary as a subprocess. A subprocess inherits an
environment. So the id goes in at launch, the boundary reads it once, and nothing in the protocol or
the docket changes.

The third is chosen here, and the reason is worth being honest about: **it is the one that matches the
transport this project actually runs.** It is also the one with the sharpest limit. It works because
the desk starts the boundary; it does nothing at all for the HTTP transport day 4 built, where the
boundary is already running and was launched by somebody else, long before this claim existed. That
limit is not hidden — it has a test.

## The mechanism

`claims_desk/boundary.py`, **a marked diff against the file day 4 printed**:

```diff
 from mcp import Client, StdioServerParameters
 
+from claims_desk.util import trace
 from claims_desk.util.logging import log
@@
 def target() -> str | StdioServerParameters:
-    """The thing a `Client` should be pointed at, from the environment."""
+    """The thing a `Client` should be pointed at, from the environment.
+
+    When it is a subprocess, the launch parameters carry this desk's trace id in the child's
+    environment. That is how one id spans two processes: the boundary has no argument to receive it
+    in, so it is handed the id the same way it is handed its `PATH`.
+    """
     url = os.environ.get(ENDPOINT, "").strip()
-    return url or LAUNCH
+    if url:
+        return url
+    carried = trace.current()
+    if not carried:
+        return LAUNCH
+    return LAUNCH.model_copy(update={"env": {**os.environ, trace.TRACE_ENV: carried}})
```

**Line by line:**

- `LAUNCH.model_copy(update=...)` — **a copy, not a mutation.** `LAUNCH` is a module-level constant
  describing how to start the boundary, and it must stay the same object for the life of the process.
  Editing it in place would mean the second claim launches with the first claim's trace id, which is
  the exact failure part 1.1's `ContextVar` exists to avoid, reintroduced one layer down.
- `{**os.environ, trace.TRACE_ENV: carried}` — **the whole environment, plus one.** `StdioServerParameters`
  replaces the child's environment rather than adding to it, so passing `{TRACE_ENV: carried}` alone
  would launch a Python subprocess with no `PATH`, no `SYSTEMROOT` and no virtual environment. That is
  a genuinely confusing failure — the boundary simply fails to start — and it is why the test below
  asserts `launch.env["PATH"]` as well as the trace.
- `if not carried: return LAUNCH` — **no trace, no copy.** Two reasons, and the second is the real
  one. It keeps the untraced path identical to what day 4 built; and it means the child is never
  handed `CLAIMS_TRACE=""`, which `start()` would have to defend against and which would read, to
  anybody inspecting the process, as an id that failed rather than an id that was never set.
- **The `url` branch returns before any of this.** An HTTP boundary gets nothing, because there is no
  child to hand anything to. That is the honest limit stated as control flow.
- **Nothing in `claims_mcp` changed.** The server reads the id through `trace.current()`, whose
  environment fallback part 1.1 built. One module knows how the id travels; the program at the other
  end just asks what the id is.

Two tests, and the second is the interesting one:

```bash
uv run pytest tests/test_observability.py -q -p no:warnings -k "launched or url_boundary"
```

```

2 passed, 23 deselected in 2.36s
```

**Line by line:**

- The first asserts the launch parameters carry the id **and** still carry a `PATH`. The second
  assertion has a message — `"the child needs the rest of the environment too"` — because it is the
  one somebody will break while tidying.
- The second asserts that an HTTP boundary gets a bare URL and no environment at all. **A test for a
  thing the mechanism cannot do**, which is worth writing precisely because the limit is invisible:
  everything looks fine until somebody switches transport and the traces silently stop joining up.

Now the proof, which is not a test. Run the queue and look at two consecutive lines — the first
written by the desk, the second by a different operating-system process:

```
{"ts": "2026-09-12T05:00:50.827+00:00", "trace": "t-c1de696d9398", "span": "boundary.connect", "event": "boundary.connected", "transport": "stdio", "protocol": "2026-07-28", "server": "claims-boundary"}
{"ts": "2026-09-12T05:00:50.827+00:00", "trace": "t-c1de696d9398", "event": "boundary.draft_letter", "claim": "FNOL-4477", "reason": "missing_photo_reference"}
```

**Line by line:**

- **Same `trace`, two processes.** The first line is the desk noticing a connection opened; the second
  is `claims_mcp/tools.py` in the child, writing about a tool call. Neither program passed the other
  an id.
- **The second line has no `span`.** Correct, and worth pausing on: the child has its own `span_stack`,
  which is empty, because spans are a property of one process's call stack and do not cross. The trace
  crosses; the span does not. A reader can tell which process wrote a line by whether it has a span —
  which is an accident of this design and a genuinely useful one.
- `"protocol": "2026-07-28"` — day 4's line, unchanged, now correlated.

And over the whole queue:

```
total lines: 302
traces: {'t-c1de696d9398'}
```

**Line by line:**

- **Three hundred and two lines, one trace.** Every line the desk wrote, and every line forty
  boundary subprocesses wrote, carries the same id.
- **One trace for the whole queue and a `claim` span per claim** is the shape chosen here. A trace per
  claim would also be defensible; this way round, the queue is the unit of work — one morning's run —
  and a single claim is found by its span rather than by its own id. Part 2.1 is what that buys.

## When it breaks

Pass only the trace id to the child, which is what anybody writes first because passing the whole
environment looks careless:

```diff
-    return LAUNCH.model_copy(update={"env": {**os.environ, trace.TRACE_ENV: carried}})
+    return LAUNCH.model_copy(update={"env": {trace.TRACE_ENV: carried}})
```

```
    def test_the_boundary_is_launched_with_this_desks_trace(fresh, monkeypatch) -> None:
        """The one mechanism that carries an id across a process line: the child's environment."""
        monkeypatch.delenv(boundary.ENDPOINT, raising=False)
        trace.start("t-222222222222")
        launch = boundary.target()
        assert launch.env[trace.TRACE_ENV] == "t-222222222222"
>       assert launch.env["PATH"], "the child needs the rest of the environment too"
               ^^^^^^^^^^^^^^^^^^
E       KeyError: 'PATH'

tests	est_observability.py:114: KeyError
```

`KeyError: 'PATH'` in a test about tracing, which is exactly the sort of failure that costs an
afternoon when it arrives without one. What happens without the test is that the boundary subprocess
cannot find its interpreter, the connection fails, and every claim escalates as
`provider_unavailable` — a symptom several layers away from a dictionary that was built too small.

The smallest fix is the spread. The general rule is about the shape of the interface rather than this
bug: **an API that replaces a whole environment is one that must be handed the whole environment**,
and the way you find out which kind you have is by reading the field's documentation before setting
it, not by testing the happy path.

## In production

**What a senior writes instead.** The W3C `traceparent` header over the protocol's metadata channel,
not the environment — because it works for both transports, it is what every other service in the
estate already emits, and a claims platform's trace has to join up with the policy system's and the
payments system's rather than only with itself. The environment mechanism is right for a subprocess
you launch and wrong for everything else, and the tell is that it is set once at start-up while a
trace id changes per request.

**What degrades at scale.** This works because the desk launches one boundary per call and can set the
environment each time — which part 2.1 is about to show is a catastrophically expensive way to run.
The moment the boundary becomes a long-lived process, whether behind HTTP or as a pool, the
environment is fixed at start-up and carries the id of whatever work happened to be first. So the
mechanism does not merely fail to scale; it **breaks silently at exactly the point where the
performance problem gets fixed**, and the traces afterwards are all labelled with one stale id.

**The review comment.** *"The environment propagation is fine for stdio and there is a test saying it
does nothing over HTTP, which I appreciate. But `test_a_url_boundary_carries_no_environment` records
the limit without warning anybody — if `CLAIMS_BOUNDARY` is set, log a line once at start-up saying
traces will not cross the boundary. A silent limit is one somebody discovers during an incident."*

**The interview question.** *"Your service shells out to a worker process. How does a request id get
into the worker's logs, and what are the three places you could put it? Now tell me which of them
survives the worker becoming a long-lived service."*
