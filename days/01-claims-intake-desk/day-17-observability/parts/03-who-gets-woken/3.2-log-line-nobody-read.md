## One-line answer

Day 1's redactor matches secret-looking field names by substring, so a field called `keys` contains
`key` and is replaced with `<redacted>` — and two log lines in this project had been emitting a
redaction marker instead of their contents since day 11 and day 15, which nobody noticed because
nobody had ever read them.

## The idea

There is a form in every claims office that everybody fills in and nobody reads.

It gets printed, initialled and filed, and the day somebody finally needs it — a complaint, an audit,
a query about a claim from two years ago — they discover the field they wanted has been blank on every
copy since a template change in the spring. Nobody was careless. The form was completed correctly
every time, by people who had no way to know that the thing they were writing into went nowhere.

Log lines are that form, and the property that makes them dangerous is that **writing one succeeds**.
There is no error, no exception, no failing test. `log("hooks.tool_result", tool=..., keys=...)` runs
perfectly and writes a line. Whether that line says anything is a question nobody asks, because
answering it requires somebody to actually read the output — which nobody does until an incident, and
during an incident is the worst possible time to discover your instrument is blank.

This project found two of them today, and it found them for the reason the whole day exists: putting a
span round `boundary.call` meant printing a trace and looking at it, and looking at it meant reading
lines that had been scrolling past for a fortnight.

The mechanism is a collision between two reasonable decisions, neither of which is wrong.

Day 1 built a redactor that never wants a secret on a page. Since it cannot know which values are
secret, it works on **field names**, and it matches by substring — because `api_key`, `API_KEY`,
`google_api_key` and `provider_key_path` should all be caught by one entry reading `key`. A prefix
match would miss most of those. Substring matching is the right call, and the cost is that it also
matches every name that merely contains those letters.

Day 11 logged which fields a tool answer came back with, and called that field `keys`, because they
are the keys of a dictionary. Also the right word.

Put the two together and `hooks.tool_result` has been saying `"keys": "<redacted>"` since the day it
was written. The redactor did its job. The log line did its job. The output is useless.

## The mechanism

Reproduce it in one command — no test, no fixture, just the two lines this project actually writes:

```bash
uv run python -c "
from claims_desk.util.logging import log
log('hooks.tool_result', tool='fetch_policy', keys=['found','number','perils'])
log('boundary.record_decision.repeat', claim='FNOL-4471', key='b2b321c4176487d7')
"
```

```
{"ts": "2026-09-12T05:16:59.794+00:00", "event": "hooks.tool_result", "tool": "fetch_policy", "keys": "<redacted>"}
{"ts": "2026-09-12T05:16:59.794+00:00", "event": "boundary.record_decision.repeat", "claim": "FNOL-4471", "key": "<redacted>"}
```

Both of them. Two log lines this project writes in ordinary operation, and the field that carries
their content says `<redacted>` in each.

**Line by line:**

- **The first is unambiguously a bug.** `keys=['found','number','perils']` is a list of field names
  from a tool answer. Nothing in it is a secret. Day 11's whole reason for logging it — knowing what
  shape came back from a tool without writing a policyholder's data to a log — is silently not
  happening, and has not been happening since the line was written.
- **The second is arguable, and worth arguing.** An idempotency key is a hash of a decision's own
  content; publishing it leaks nothing, and day 15 logged it so that a repeated write could be matched
  to its original. Redacting it is not a security failure — it is a line that no longer does the job
  it was added for. Whether that is worth fixing is a judgement; whether somebody should have known is
  not.
- **So there are two separate questions**, and conflating them is how this gets fixed badly: is the
  redactor too aggressive, or are these fields badly named?

The answer is that the fields are badly named, and the argument matters because the other fix is
tempting. Adding an exception list to `looks_secret` — *unless the name is `keys` or `key`* — would fix
both lines and would also exempt `api_keys`, `keys_path` and `signing_key`, which is a redactor that
no longer does the one thing it exists for. **A safety net that grows exceptions stops being a safety
net.**

So today's code says what it means. In `claims_desk/boundary.py`, part 2.1's new span reports the
answer's field names, and it does not call them `keys`:

```python
        timing["fields"] = sorted(answer)
```

**Line by line:**

- `fields` **is the more accurate word anyway.** They are the fields of the answer, and the only reason
  `keys` was ever the obvious name is that a Python dictionary calls them that.
- **This is the fix at the point of writing rather than at the point of redaction.** The redactor is
  untouched, still matching by substring, still catching everything it was built to catch.
- **And the collision now has a test**, in part 4.1: a test that runs a boundary call and asserts that
  **no field in any resulting log line is `<redacted>`**. It does not know about `keys` specifically.
  It asserts the property — a log line should say something — which is what catches the next name
  nobody thought about.

That test, and what it says when the field is renamed back:

```python
def test_the_field_list_is_not_called_keys(fresh, capsys) -> None:
    """Day 1's redactor matches `key` as a substring, so a field named `keys` is redacted whole.

    This test is the scar. Two log lines carried `<redacted>` for days because nobody read them.
    """
    trace.start()
    asyncio.run(boundary.fetch_policy("SYN-POL-1001"))
    for line in records(capsys.readouterr().err):
        for name, value in line.items():
            assert value != "<redacted>", f"{line['event']}.{name} says nothing"
```

**Line by line:**

- **It runs a real boundary call and reads what came out**, rather than calling `log` directly with a
  contrived field. The claim being tested is about this project's actual output.
- **The assertion is over every field of every line**, not over `keys`. A test that checked `keys`
  specifically would pass forever after the rename and catch nothing new; this one catches
  `monkey_patched`, `donkey_work` and whatever else somebody names a field in a year.
- `f"{line['event']}.{name} says nothing"` — **the message names the event and the field**, because the
  failure is otherwise a bare comparison of two strings and the whole point is knowing *which* line
  went quiet.
- **`<redacted>` as a literal in a test** is a mild smell and is correct here: the test is about the
  marker appearing where it should not, so the marker is the subject rather than an implementation
  detail.

## When it breaks

Rename it back, which is what somebody does when they notice a span field and a dictionary method have
different names for the same thing:

```diff
-        timing["fields"] = sorted(answer)
+        timing["keys"] = sorted(answer)
```

```
        trace.start()
        asyncio.run(boundary.fetch_policy("SYN-POL-1001"))
        for line in records(capsys.readouterr().err):
            for name, value in line.items():
>               assert value != "<redacted>", f"{line['event']}.{name} says nothing"
E               AssertionError: span.keys says nothing
E               assert '<redacted>' != '<redacted>'

tests	est_observability.py:202: AssertionError
```

`span.keys says nothing` is the whole finding in three words, which is what the assertion message was
for.

And here is the part that should be uncomfortable. **This project shipped that defect for six days.**
It was written on day 11, it was never printed in any transcript, and every check was green the entire
time — because a redacted field is not an error, it is a string. The thing that found it was not a
test and not a review. It was somebody printing a trace for a different reason and reading it.

The smallest fix is the name. The general rule has two halves, and the second is the one worth keeping:
**a log line with no reader is not instrumentation, it is a comment that costs disk**; and the way to
give it a reader before the incident is to assert something about the output, however weak. "No field
of any line is the redaction marker" is an almost trivially weak assertion, and it would have caught
this on day 11.

## In production

**What a senior writes instead.** Structured events with a declared schema — a typed record per event
rather than `**fields` — so a field's name and type are checked where it is defined, and the redactor
is applied to fields marked sensitive rather than guessed at by name. That removes the whole class of
bug: nothing can be accidentally called `keys`, because nothing is called anything without being
declared.

**What degrades at scale.** Substring matching over a hint list is fine at this project's size and gets
worse in both directions as the field vocabulary grows. False positives multiply — `monkey`, `donkey`,
`turkey`, `keyword`, `low_key` all contain `key`, and `passwordless` contains `password` — while false
negatives arrive from anything that does not use the vocabulary, like `bearer`, `pat`, or a field
called `authorization_header_value_b64` that happens to be spelled differently. At an insurer's scale
the answer is a scanner over log output in the pipeline, checking for things that *look* like secrets
by value rather than by name, with the name-based redactor kept as the cheap first line.

**The review comment.** *"The new test asserts no field is `<redacted>` in the lines one boundary call
produces, which is a good property and a small sample. Run it over the whole queue instead — the
`security` and `reliability` modules both log fields this test never sees, and the next collision will
be in one of them."*

**The interview question.** *"You have a redactor that hides fields whose names look sensitive. Name
three fields it would hide that it should not, and tell me how you would find out whether it currently
is."*
