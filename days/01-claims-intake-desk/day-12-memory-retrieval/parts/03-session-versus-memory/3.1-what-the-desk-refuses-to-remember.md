## One-line answer

A memory service is a session service that has stopped forgetting: hand it two claims and one query
reaches across them and returns a policyholder's exact words to somebody who never had the claim
reference — which is what HB-07 forbids, and why this desk registers no memory service at all.

## The idea

The framework offers a memory service, and taking it is one keyword argument.

It is genuinely useful. An assistant that helps the same person every week should remember that they
prefer the aisle seat; a support system that has handled your last four tickets should not ask your
account number a fifth time. In those systems, memory is the feature.

A claims intake desk is not one of those systems, and the reason is worth being precise about
because "we handle personal data" is not it. Plenty of systems handle personal data and remember
things about it perfectly lawfully.

The reason is in HB-07, which the department wrote before any of this existed:

> Nothing a policyholder says on the telephone is kept beyond the claim it was said about. Contact
> details, the description of the loss and any note a handler makes are held against the claim
> reference and are not carried into another claim, another policyholder's file, or **any list used
> to answer later questions**.

That last clause is a description of a memory service. Not an analogy — a description. A memory
service is a list, built out of what people said, used to answer later questions.

Day 8 built the desk's side of this rule and it holds: a session is addressed by the claim reference,
and asking about one claim finds nothing about another. Day 9 tightened it again when two agents
turned out to share a conversation. The rule has survived four days of the desk getting more
capable.

What this part shows is how one line would undo all of it — and, more usefully, **what the boundary
between "session" and "memory" actually is**, because it is not a difference in the data. It is the
same events. The difference is whether they can be reached without knowing which claim they belong
to.

## The mechanism

Two claims, two policyholders, two conversations. Then hand both to a memory service:

```bash
uv run python -c "
import asyncio
from google.adk.memory import InMemoryMemoryService
from claims_desk import sessions
from claims_desk.agents import classifier

def text_of(session):
    return ' '.join(
        part.text or ''
        for event in session.events
        if event.content
        for part in (event.content.parts or [])
    )

async def main():
    await sessions.turn(classifier.build(), 'FNOL-4471', 'the flexible hose let go overnight')
    await sessions.turn(classifier.build(), 'FNOL-4472', 'the ridge tiles came off in the storm')
    first = await sessions.stored('FNOL-4471')
    second = await sessions.stored('FNOL-4472')
    print('FNOL-4472 mentions the hose:', 'flexible hose' in text_of(second))

    memory = InMemoryMemoryService()
    await memory.add_session_to_memory(first)
    await memory.add_session_to_memory(second)
    found = await memory.search_memory(
        app_name=sessions.APP, user_id=sessions.BATCH_USER, query='flexible hose'
    )
    print('after remembering, a search for \\'flexible hose\\' finds', len(found.memories), 'entry')
    for entry in found.memories:
        said = ''.join(part.text or '' for part in (entry.content.parts or []))
        print('   author=%-6s %s' % (entry.author, said))

asyncio.run(main())
"
```

```
FNOL-4472 mentions the hose: False
after remembering, a search for 'flexible hose' finds 1 entry
   author=user   the flexible hose let go overnight
```

**Line by line:**

- `FNOL-4472 mentions the hose: False` — **day 8's isolation, still holding.** Two claims, two
  sessions, and nothing about the first is reachable through the second. Four days of rules, working.
- `await memory.add_session_to_memory(first)` — **one call, and it is not a copy of the events into
  a different shape.** It is the same events, registered somewhere that can be searched without a
  session id.
- `search_memory(app_name=..., user_id=..., query='flexible hose')` — **look at what this call does
  not take.** No claim reference. The two things it does take are the app and the batch user, which
  are constants: `claims-intake-desk` and `desk-batch`, the same for every claim this desk has ever
  handled.
- **So the address that day 8 built the whole isolation on is not part of the question.** That is the
  entire difference between a session and a memory. Not the data, not the retention, not the storage:
  **the session is reached by claim reference and the memory is reached by content.**
- `finds 1 entry` — **and it is the policyholder's own sentence**, word for word: *the flexible hose
  let go overnight*.
- `author=user` — **the framework knows it came from the caller and not from a model**, and stores it
  anyway, because that is what it was asked to do.
- **Nothing here is a bug.** The memory service behaved exactly as documented, this project got what
  it asked for, and what it asked for is against the department's own rule.

The desk's answer is that `sessions.turn` builds a runner with a session service and nothing else:

```python
    runner = Runner(
        app_name=APP, agent=agent, session_service=service, plugins=[DeskPlugin()]
    )
```

**Line by line:**

- **`session_service` and no `memory_service`.** The `Runner` accepts one — it is the next keyword in
  the signature — and this line does not pass it. That absence is a decision, and part 4.1 asserts it
  so the decision cannot be undone by an autocomplete.
- **The decision costs this desk nothing it wants**, and that is why it is easy here. A desk that
  genuinely needed to recognise a repeat caller would have a real argument to have, with the
  department, about what may be kept and for how long — and the answer would go in the handbook
  before it went in the code.
- **What replaces memory is the handbook.** Everything this desk looks up is in a corpus that belongs
  to nobody, and part 1.2's index has no per-policyholder state in it at all.

## When it breaks

The failure is not the demonstration above — that was deliberate. It is the version where nobody
decided anything.

`Runner` takes `memory_service` as an optional keyword. Add it, and the `load_memory` tool becomes
useful to an agent, and an agent given that tool will call it when a question looks like it needs
context. There is no error, no warning, and no red test unless somebody wrote one. The desk starts
answering better, because it now has more to go on.

Six months later, a policyholder asks what the company holds about them. The claim files answer for
themselves — day 6 made those one JSON object per claim, and day 14 will make them auditable. The
sessions are addressed by claim reference, so they can be found and produced.

And there is a third store, holding the same sentences, addressed by nothing, searchable by anybody
who can phrase a query — with no claim reference on the entries and no way to enumerate what belongs
to one person without searching for them by name.

**That is the failure: not that the data was kept, but that it was kept somewhere with no index on
the person it belongs to.** A store you cannot enumerate by subject is a store you cannot answer for.

The smallest fix is not adding the keyword. The rule worth carrying to the next project: **before
adding memory, say what the deletion path is.** If the answer is *search for their words and hope you
find them all*, there is no deletion path, and what is being proposed is a permanent record made out
of things people said on the telephone.

## In production

**What a senior writes instead.** For a desk like this: the same refusal, written down where the
decision lives rather than implied by an absent keyword — this project has the assertion in part 4.1
and the rule in HB-07, and a real one would have an ADR. For a system that genuinely needs memory:
entries keyed by the subject they are about, with a delete-by-subject path built **before** the first
write, and a retention period that expires things without anybody remembering to.

**What degrades at scale.** Twelve claims a morning is a memory nobody would notice. Several hundred
a day is roughly a hundred thousand conversations a year, each holding a description a person gave
over the telephone, in a store whose whole design is that you find things by content. The cost is not
storage. It is that the first subject access request, or the first request to delete, has to be
answered against it — and "we searched for their name" is not an answer anybody accepts.

**The review comment.** *"This passes `memory_service` so the classifier can see similar past claims.
Two questions before it goes in: how do we delete one policyholder's entries, and how do we prove we
did. If either answer is 'search for them', this is not going in."*

**The interview question.** *"You have a session store and a memory store holding the same
sentences. Regulation says a person may ask you to delete everything you hold about them. Which store
is harder to answer with, and why?"*
