## One-line answer

Day 10 counted the budget from events after the run; today the plugin charges the call before it is
made — which deletes a function, changes what a refusal is from an exception into a returned value,
and shows up in exactly one place in the desk.

## The idea

There is a difference between counting the post and franking it.

Counting the post tells you, at the end of the day, how many letters went out. It is accurate, it is
cheap, and it cannot stop anything: by the time you have the number, the letters are gone. Franking
happens at the moment each letter leaves, which costs nothing extra and gives you something the
count never could — **the ability to refuse one**.

Day 10 counted. `charge(budget, agent, events)` walked the events after a workflow finished, matched
authors against the workflow's model nodes, and spent one call per event. It worked. It was also
three assumptions deep: that one call produces one event, that the author of an event is the agent
that made the call, and that a workflow's model nodes can be listed in advance. The first of those
is false against any provider that streams.

Today the charge moves to `before_model_callback`, which is the moment the call is about to be made.
The number stops being a reconstruction and becomes an observation, and — because the hook can
replace the call — the budget stops being a record and becomes a limit.

One thing changes character in the move, and it is the part worth arguing about. **A refusal stops
being an exception.** Day 7 made `BudgetExceeded` raise, deliberately and with a good reason: a
caller that is out of allowance should stop, not continue with a default. Inside a plugin that is no
longer available — part 3.1 is the run that shows why — so the refusal comes back as a returned
value, and the desk has to read it.

That is a real loss. An exception cannot be ignored; a returned value can. What replaces it is a
check in one place and a test that would fail if the check were removed.

## The mechanism

The charge is registered on the runner, in `sessions.turn`. A **marked diff against
`claims_desk/sessions.py` as printed on day 8 part 1.1, with day 9's threads and day 10's
`max_calls` already in place**:

```diff

 from claims_desk.util.logging import log

@@ unchanged @@
-    runner = Runner(app_name=APP, agent=agent, session_service=service)
+    runner = Runner(
+        app_name=APP, agent=agent, session_service=service, plugins=[DeskPlugin()]
+    )
```

**Line by line:**

- `plugins=[DeskPlugin()]` — **one keyword argument, and it is the whole registration.** Every turn
  this desk takes goes through `sessions.turn`, so putting it here means no agent and no workflow can
  be run without it.
- **A new instance per turn.** It holds no state — the budget is in a context variable — so a new one
  costs nothing and cannot accumulate anything by accident. A shared instance would work today and
  would be the thing to blame the first time somebody adds a field to it.
- **The plugin is registered on the runner, not on the agent.** That is what makes it apply to every
  node inside a workflow, including nodes that did not exist when this line was written.
- `from claims_desk.hooks import DeskPlugin` — **`sessions` now imports `hooks`**, and `hooks`
  imports only `util`. The direction is worth checking whenever a cross-cutting file appears: a
  plugin that imported `workflow` or `desk` would make a cycle out of a post room.

**Line by line:**

- `- def charge(...)` — **eleven lines deleted, and with them three assumptions.** The one that
  mattered is `event.partial is not True`: a guess about streaming, written by somebody who had never
  seen this project stream, and now unnecessary because the hook counts calls rather than fragments.
- `token = hooks.current_budget.set(budget)` — **the caller registers the budget** and the plugin
  finds it. The workflow still owns the allowance; it has stopped owning the counting.
- `try: ... finally:` — **the reset is in a `finally`.** A run that raises must still put the context
  variable back, or the next claim in the queue inherits this claim's budget — which would be a bug
  that only appears after a failure and only on the claim after it.
- `turned_away = list(hooks.refusals.get() or [])` — **copied inside the `finally`, before the
  reset.** After the reset the list is unreachable, and reading it afterwards would silently give the
  outer context's value.
- `or []` — because the context variable's default is `None`, which part 1.1 explains was a lint
  rule's doing and is the right shape anyway.
- `OVER_BUDGET = "over_budget"` **as a constant** — the desk compares against it, part 4.1's tests
  compare against it, and `Verdict.waiting_for` carries it. Three places, one spelling.
- **The comment on that constant is the important half**: *the two look identical in state — an empty
  reading either way — and they are different incidents.* A claim that went pending because the desk
  ran out of allowance should be re-run tomorrow; a claim that went pending because the model
  answered badly should be looked at. Same empty string in state, different actions.
- `"turned_away": turned_away` — **the agents, not just the fact.** With one agent it is redundant;
  with a cast it is the difference between "this claim ran out" and "the letter writer ran out
  because the classifier spent it".

  wrong reason is a claim nobody re-runs*.

**Line by line:**

- **Two log lines and a verdict, and no exception anywhere.** The claim was refused, the desk noticed,
  and the queue would have continued to the next notification.
- `"event": "hooks.refused"` — **the plugin's line comes first**, and it carries the agent, the
  invocation and day 7's refusal message unchanged: *classifier asked for call 1 of 0 for nothing*.
- `"event": "desk.over_budget", "agents": ["classifier"]` — **the desk's line comes second**, and it
  names the claim and who was turned away. Two lines from two levels, and neither is redundant: the
  first is about a call, the second is about a claim.
- `waiting_for='over_budget'` — **the verdict says why it is pending**, so tomorrow's run can tell
  this claim apart from one whose classifier answered badly.
- **Nothing was written to the claims directory.** Day 6 established that a pending verdict is not
  recorded, and a claim nobody could afford to look at is exactly the case that rule was written for.

## When it breaks

Delete the `if read["error"] == workflow.OVER_BUDGET:` check — the version a refactor produces when
somebody notices that `over_budget` is "just another error":

```
Verdict(claim_id='FNOL-4477', outcome='pending', reason=None, waiting_for='needs_classification')
```

Verbatim, from this project. Nothing raises. The claim still goes pending, the queue still finishes,
and every count in `PROJECT.md` is still right.

What is lost is the only thing that told you what to do about it. `needs_classification` means *a
model read this and produced something the parser could not use* — a claim somebody should look at,
because the description may be unusual or the prompt may be wrong. `over_budget` means *nobody
looked at this at all* — a claim that should simply be re-run with an allowance.

Twelve claims in a morning is a person spotting the difference. Several hundred is a queue of
pending claims where the two kinds are mixed, indistinguishable, and both waiting for a human who
has no way to sort them.

The smallest fix is the four lines. The rule underneath: **when an exception becomes a returned
value, the thing you lose is that it cannot be ignored** — so the check that replaces it needs a test
of its own, which is part 4.1's `test_a_refused_claim_goes_pending_and_names_the_reason`.

## In production

**What a senior writes instead.** The same charge in the same hook, with the budget carried on the
invocation rather than in a context variable — most frameworks give you somewhere per-run to put
things, and a context variable is what you use when they do not. What they would want beyond this
project's version is **the refusal on the claim record**: this desk logs it and returns it, and a
claim that was never looked at leaves no file at all, so the evidence that it was skipped lives only
in the log.

**What degrades at scale.** A context variable is per-task, so twelve claims decided concurrently
each see their own budget — that part scales. What does not is the single `refusals` list per run: it
is fine for one claim with two agents, and it is the wrong shape the moment one run covers several
claims, which is exactly what day 10's parallel queue would have done. The shape that survives is a
refusal recorded **against the claim**, not against the run.

**The review comment.** *"`run_triage` sets the context variable and resets it in a `finally`. The
new `run_evaluation` you have added sets it and resets it at the end of the happy path. One
exception in there and every subsequent claim shares a budget — put it in a `finally` or make it a
context manager so nobody has to remember."*

**The interview question.** *"You move a limit from a function that raises into a hook that cannot.
What do you lose, and what do you put in place of it?"*
