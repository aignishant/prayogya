## One-line answer

Because the plugin sits below every agent, one claim's model calls come out as a flat run of lines
that name the agent and the invocation — three calls, two agents, two invocations, one claim — and
that is a record nobody had to write inside any of the agents.

## The idea

A claim file has a running sheet, and the sheet is only useful if every entry says who wrote it.

*Photograph requested.* Written by whom? On what day? During which conversation with the
policyholder? A sheet where entries are unattributed is a sheet that answers "what happened" and
never "who did that", and the second question is the one asked when something has gone wrong.

Day 8 gave this desk a session and day 9 gave each agent its own thread. Day 10 nested those inside
workflows, and by the end of it a single claim could touch two agents across two invocations, one of
them looping. The desk's own log lines are still there and they are still good — `workflow.rules`,
`workflow.house_style`, `desk.decided` — and every one of them was written by hand, in the file that
does the work, by somebody who remembered.

The plugin's lines are different in kind. They were not written by anybody who knew about claims.
They appear because a model was called, and they carry the two identifiers the framework has at that
moment: **which agent** and **which invocation**. Add an agent tomorrow and its calls are in the log
without anyone doing anything.

That is the whole value of a cross-cutting hook for observability, and it is also its limit: it can
only say what the framework knows. It does not know the claim reference, because the framework has
never heard of claims.

## The mechanism

Decide one claim and write its letter, with the desk's own lines and the plugin's lines interleaved:

```bash
uv run python -c "
import asyncio
from claims_desk import desk
from claims_desk.store import Store
from claims_desk.util.budget import Budget

queue = {n.id: n for n in Store().notifications()}

async def main():
    budget = Budget(limit=desk.CALLS_PER_NOTIFICATION, label='FNOL-4481')
    verdict = await desk.decide(queue['FNOL-4481'], budget)
    await desk.write_letter(
        verdict.claim_id, verdict.reason, budget, queue['FNOL-4481'].description
    )
    print('by:', budget.by)

asyncio.run(main())
"
```


**Line by line:**

- **Three `hooks.model` lines: one classifier, two letter writer.** Nobody wrote a log statement in
  either agent. Both agents are the same files day 7 and day 9 printed, and neither knows this record
  exists.
- **Two invocation ids, not three.** `e-d5cf…` for the triage and `e-7ae9…` for the correspondence —
  and **both drafts share the second one**, because a loop is one invocation that goes round twice.
  That is the identifier to group by when asking "what did this turn cost".
- `"chars": 180` **then** `"chars": 165` — **the first draft and its replacement**, and the fifteen
  characters that went are the figure the house style refused. The plugin has no idea that is what
  happened; it recorded two calls of different sizes, and the desk's own next line says why.
- `"event": "workflow.house_style", "found": "2"` — **the desk's line, immediately after.** The two
  kinds of line answer different questions: the plugin's says *a call was made and this is what it
  cost*, the desk's says *and here is what we decided about it*.
- **The plugin's lines carry no claim reference and the desk's lines carry no agent name.** Neither
  is an oversight. The plugin cannot know about claims and the desk does not need to repeat what the
  framework already stamped — and joining the two is what `invocation` is for.
- `"partial": null` — **against this stand-in, always.** Against a streaming provider these three
  lines would be dozens, and `partial` is what would let you count calls rather than fragments. It is
  recorded now precisely so that the day somebody points a real model at this, the log already knows
  the question.
- `by: {'classifier': 1, 'letter_writer': 2}` — **the same three calls, counted by the same hook that
  logged them.** Day 9 introduced this breakdown when there were two agents called in a fixed order;
  it now survives a workflow, a loop and a second invocation without changing.

## When it breaks

Log the answer instead of its size — one small edit to `after_model_callback`, `text=` instead of
`chars=`, the thing anybody debugging would reach for first:

```
{"event": "hooks.model", "agent": "letter_writer", "invocation": "e-be77a2f3-af26-4293-aaee-bb7d468f2d54", "parts": 1, "text": "We have opened claim FNOL-4481 and the amount reported is above our fast-track limit of 2500 pounds. There is nothing further for you to send. An adjuster will review the estimate.", "partial": null}
```

Nothing fails. The suite stays green, the letters stay correct, and debugging genuinely does get
easier.

What has also happened is that **every deficiency letter this desk writes is now in the log**,
including the drafts that were refused. Day 1 built a redacting logger for exactly this reason and
redacts by key name; `text` is not on its list, because nobody adds a key called `text` to a deny
list. Day 8 refused to put a policyholder's contact details in session state because *a session is
retained*. A log is retained too, usually longer, usually somewhere with wider access, and usually
by a system nobody on the claims team administers.

The version of this that reaches production is worse than the version above, because it is
conditional: *log the text when the house style rejects a draft*, which is a sentence nobody would
challenge in review and which puts exactly the wrong letters in the record.

The smallest fix is `chars`. The rule: **a cross-cutting hook sees everything, so what it records is
a retention decision and not a debugging preference.** If the text is genuinely needed, it belongs
somewhere with the claim's own retention rules — which for this desk is the claim file, where day 9
already put the accepted letter.

## In production

**What a senior writes instead.** The same two identifiers, emitted as structured fields to whatever
collects them, plus a **trace id that spans the whole claim** — this desk has `invocation` per turn
and nothing that spans two turns, so joining the triage to the correspondence means joining on time
and hoping. A claim reference passed into the plugin through the same context variable the budget
uses would fix it, and is a rep in this day's brief.

**What degrades at scale.** Seventeen model calls per twelve claims is roughly 250 plugin lines a
morning at this desk's several hundred notifications — trivial. What does not stay trivial is the
join: with one invocation id per turn and two turns per claim, finding everything about one claim
means two lookups and a correlation nobody wrote down. At twelve claims you eyeball it; at several
hundred you need the claim reference in the line, and adding it later means the old lines do not have
it.

**The review comment.** *"`after_model_callback` now logs the response text so we can debug the
letters. That puts every draft, including the rejected ones, in a log with a two-year retention and
company-wide read access. Log the length; if you need the text, take it from the claim file."*

**The interview question.** *"Your framework stamps every log line with an agent name and an
invocation id. Name the identifier it cannot give you, say why, and describe how you would get it
in there."*
