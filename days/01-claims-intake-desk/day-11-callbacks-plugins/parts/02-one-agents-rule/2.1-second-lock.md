## One-line answer

An agent callback is a field on one agent, so the rule that the letter writer must never be sent the
policyholder's own words lives on the letter writer — and it refuses the request rather than raising,
which the measurement shows still costs three drafts.

## The idea

Day 9 found the leak by accident. The letter writer, given three careful lines, was being replayed
the policyholder's exact words because both agents shared a session. The fix was one keyword —
`thread=NAME` — and it works.

It is also a **convention**. The isolation exists because two strings differ: `claim-FNOL-4477` and
`claim-FNOL-4477/correspondence`. Nothing enforces that they differ. A refactor that tidies thread
names, a new agent whose author copies the classifier's call site, a decision to "simplify" the
session addressing — any of those puts the two agents back in one conversation, and the only thing
that would notice is one test.

A department that cared would not stop at the filing rule. It would also instruct the person writing
letters: *if the call notes reach your desk, do not use them — send them back.* Two locks on
different things. The first is about where paper is filed; the second is about what this person is
allowed to act on, and it holds even when the filing goes wrong.

That second lock is an **agent callback**: a function passed as a field when the agent is built,
which the framework calls for that agent and no other. `before_model_callback` again, the same hook
the plugin uses — and that is the point of this part. **The same hook, at two levels, doing two
kinds of work.** The plugin's version is about the desk. This one is about one agent, so it belongs
on that agent, where somebody reading the letter writer will find it.

## The mechanism

The callback, from `claims_desk/hooks.py`, printed whole in part 1.1:

```python
def refuse_the_description(
    callback_context: CallbackContext, llm_request: LlmRequest
) -> LlmResponse | None:
    """An agent callback: refuse to send a request that carries a phrase this agent must not see."""
    forbidden = str(callback_context.state.get(FORBIDDEN_IN_A_WRITERS_REQUEST, "")).strip()
    if not forbidden:
        return None
    sent = "\n".join(
        part.text or ""
        for content in (llm_request.contents or [])
        for part in (content.parts or [])
    )
    if forbidden.lower() not in sent.lower():
        return None
    log(
        "hooks.refused_leak",
        agent=callback_context.agent_name,
        invocation=callback_context.invocation_id,
        chars=len(forbidden),
    )
    return LlmResponse(
        content=types.Content(role="model", parts=[types.Part(text="")]),
        turn_complete=True,
    )
```

**Line by line:**

- `def refuse_the_description(callback_context, llm_request)` — **positional, and a plain function.**
  The plugin's hooks are keyword-only methods on a class; an agent callback is a bare function taking
  two positional arguments. Two shapes for the same hook name, and swapping them fails at call time.
- `callback_context.state.get(FORBIDDEN_IN_A_WRITERS_REQUEST, "")` — **the phrase comes from session
  state**, so the function is fixed and what it refuses is per-claim. Day 10's `{feedback?}` used the
  same channel in the other direction; state is how everything reaches an agent that was not passed
  to it.
- `if not forbidden: return None` — **no phrase, no opinion.** Without this, the first caller who
  forgot to set the key would find every letter refused, and the log would say a leak had been caught.
- `sent = "\n".join(...)` over `llm_request.contents` — **the request as the model will see it**, and
  it is the same attribute day 9's spy used. That part uncovered the leak by looking; this refuses it
  by looking, in the same place, in production rather than in a probe.
- `forbidden.lower() not in sent.lower()` — **a case-insensitive substring, and that is all it is.**
  It catches the description arriving whole. It does not catch a paraphrase, a summary, or the
  description split across two parts, and the honest thing is to say so rather than to describe this
  as protection against leaks in general.
- `log("hooks.refused_leak", ..., chars=len(forbidden))` — **the length of the forbidden phrase, not
  the phrase.** A log line about a leak that quotes the leaked text is the joke that writes itself.
- `return LlmResponse(...text="")` — **the call is replaced by an empty answer.** No provider is
  contacted, the run continues, and the empty draft meets day 10's house style, which refuses an
  empty draft anyway. Two independent checks reaching the same conclusion is the arrangement you
  want.
- **It does not raise**, and part 3.1 is the run that shows what raising in a hook actually does.

It is attached where the agent is built, in `claims_desk/workflow.py`. A **marked diff against
`claims_desk/workflow.py` as printed on day 10 part 1.1**:

**Line by line:**

- `before_model_callback=hooks.refuse_the_description` — **one field on one agent.** The classifier
  does not have it, because the classifier is *supposed* to be given the description; that is its
  whole job.
- **The field is on the writer inside the loop**, so it runs on every draft, not only the first. A
  guard that only checked the first attempt would be a guard a repair loop walks around.
- `forbidden: str = ""` **defaulted** — every existing call site keeps working and gets no guard,
  which is the right default for a check that needs to be told what to look for.
- `hooks.FORBIDDEN_IN_A_WRITERS_REQUEST: forbidden` — **the constant as the key**, so the writer of
  the state and the reader of the state cannot disagree about the spelling.
- **The description travels from `run_queue` through `desk.write_letter` to here**, one parameter at
  a time, and never into the question. It is passed *in order to be refused*, which reads oddly until
  you notice that the alternative is a guard that does not know what it is guarding against.

**Line by line:**

- **The guard fired and no letter was written.** `letter: ''`, and day 10's `run_correspondence`
  reports an unaccepted draft the same way it reports any other, so the desk records the decision
  without a letter and logs `desk.letter_failed`.
- `"chars": 10` — the length of `photograph`, which is what was forbidden in this run. **The word
  itself is not in the log**, which is the whole reason that field is a length.
- `"found": null, "chars": 0` **on the house style line** — it refused an *empty* draft, not one with
  a figure in it. Two different checks, two different reasons, and the log distinguishes them.
- **Three rounds, and this is the number that was measured rather than assumed.** The callback
  refuses, the house style refuses the empty result, the loop tries again, and the writer is refused
  again — three times, because that is `max_iterations`.
- `spent: 3` — **and this is the finding.** The plugin charges in `before_model_callback` and the
  agent callback runs after it, so **a request that never reaches a provider still costs the
  budget.** Three refusals, three calls charged, no model contacted.
- **The order is the thing to take away**: plugin first, then agent callback. This project did not
  read that anywhere; it is what `spent: 3` means, and the same three lines with no `hooks.model`
  entries between them say the calls never happened.

## When it breaks

The defect is the transcript above, and it is worth being precise about which part is wrong.

Refusing costs nothing at the provider — no request is sent — and it costs the desk three of its five
calls for the claim. The budget is therefore measuring *attempts* rather than *spend*, which is the
right choice for bounding a runaway and the wrong number for a bill. Both readings are defensible;
what is not defensible is that nothing anywhere says which one it is.

Worse is the loop. **A guaranteed refusal is the one case a repair loop cannot help with.** The
writer is not going to produce a different draft, because it is never asked; the house style is not
going to accept an empty one; and the arrangement spins its full bound to arrive where it was after
the first pass. Day 10 argued that a bound turns an unbounded bill into a bounded one, and here is
the bounded bill being paid for nothing.

The fix this project did **not** take is worth naming: the callback could end the loop by escalating.
It does not, because an agent callback's contract is to return a response or `None`, and reaching
into the loop's control flow from a guard on one agent is exactly the sort of cleverness that makes
the next person's debugging session an hour long.

What it does instead is record the number honestly — in the function's own docstring, which first
said *a leak costs nothing* and now says three drafts — and leave a `TODO(me)` for the version that
short-circuits. **A measured cost written into the code is worth more than an unmeasured
optimisation.**

## In production

**What a senior writes instead.** The same guard, with the forbidden material passed as a set of
fields rather than one phrase, and a match that is not a substring — normalised whitespace at least,
because a description that reaches the request with different line breaks slips straight past
`in`. What they would insist on is the thing this part is really about: **the guard lives on the
agent it guards.** A leak check in the plugin would have to ask which agent it is looking at, and
that question in a cross-cutting file is the first line of the mess.

**What degrades at scale.** One substring search over a request is nothing; it is proportional to
the prompt, and the prompt is a few hundred characters here. The number that moves is the *false
refusal*: this desk forbids one phrase per claim, and a real one would forbid the description, the
contact details and the adjuster's notes — several fields, over a morning's several hundred
notifications, each a chance that a common word in a description matches something innocent in a
letter and refuses a letter that was fine. At which point the guard needs to be measured for how
often it fires, and a guard nobody measures is a guard somebody eventually disables.

**The review comment.** *"This is on the letter writer and the new summary agent does not have it. If
the rule is 'agents that produce customer-facing text must not see the description', say that
somewhere both agents are built, because right now it is a field on one of them and a habit."*

**The interview question.** *"You have a rule that one specific agent must never receive one specific
input. Where do you put it, what does it do when it fires, and how would you know if it were firing
on claims where it should not?"*
